# 资料库上传策略优化方案

## 目标

在保留当前主架构的前提下，提升资料库上传链路在大文件、文件夹批量上传、弱网、暂停恢复、失败重试场景下的稳定性。

当前主线可以继续保留：

```text
小文件直传
大文件分片上传
分片上传完成后异步合并
传输记录持久化状态
失败后支持续传或直接重新触发合并
```

优化重点不是推倒重来，而是补齐以下能力：

- transfer 按需创建，减少孤儿记录
- 小文件复用已有 transfer，避免重复记录
- 断点续传按缺失分片上传，避免跳过中间缺口
- 分片缓存按 transfer_id 隔离
- 后端合并单独限流
- 合并任务内部增加路径安全校验
- 增加定时清理，收敛异常状态

## 目标模型

```text
选择文件
  -> 轻量入队，不立刻创建 transfer
  -> 任务拿到上传并发槽
  -> 计算或读取 fileHash
  -> 创建或复用 transfer
  -> 小文件直传 / 大文件分片上传
  -> 分片上传完成
  -> 提交后端合并任务
  -> 前端轮询合并状态
  -> 后端合并成功后创建文件记录并更新 transfer
  -> 前端根据后端最终状态显示完成
```

## 第一阶段：稳定性修复

### 1. transfer 改成按需创建

当前问题：

- 文件入队时就创建 transfer。
- 大量文件夹上传时，会先产生大量 `PENDING` 记录。
- 如果用户中途关闭页面、暂停、取消，会留下很多未真正开始上传的记录。

建议方案：

- 队列项先只保存 `file`、`folderId`、`isPublic`、`uploadId`、`uniqueKey` 等轻量信息。
- 任务真正获得并发槽、准备上传时再创建 transfer。
- 如果队列项已有 `transferId`，直接复用。

重点修改位置：

- `spug_web/src/pages/document/stores/upload/core/coordinators/FileUploadCoordinator.js`
- `spug_web/src/pages/document/stores/upload/core/fileUpload.js`
- `spug_web/src/pages/document/stores/upload/core/chunkUpload.js`

验收标准：

- 批量选择 1000 个文件后，数据库不会立即出现 1000 条 `PENDING` transfer。
- 只有真正开始上传的任务才创建 transfer。
- 刷新页面或关闭页面后，不会留下大量无意义的空 transfer。

### 2. 小文件复用已有 transferId

当前问题：

- 队列初始化时可能已经创建 transfer。
- 小文件实际上传时 `uploadFileNormal()` 又创建一次 transfer。
- 会产生孤儿 `PENDING` 记录。

建议方案：

将 `uploadFileNormal` 改成支持复用已有 transfer：

```js
async uploadFileNormal(file, folderId, uploadId, isPublic = null, existingTransferId = null) {
  const item = this.queueStore.findUploadItemInCurrentTenant(uploadId);
  let transferId = existingTransferId || item?.transferId || null;

  if (!transferId) {
    transferId = await this.rootStore.transferStore.createTransfer({
      transfer_type: 'upload',
      file_name: file.name,
      file_size: file.size,
      is_public: targetIsPublic,
      total_chunks: 1,
      folder_id: folderId,
    });
  }

  this.queueStore.updateUploadItem(uploadId, { transferId });
}
```

验收标准：

- 上传一个小文件只产生一条 transfer。
- 小文件上传完成后，该 transfer 从 `PENDING/UPLOADING` 正确变为 `COMPLETED`。

### 3. 断点续传改成上传缺失分片

当前问题：

前端通过 `Math.max(...uploaded_chunks) + 1` 决定续传起点。

如果后端返回：

```js
[0, 2, 3]
```

前端会从 `4` 开始，漏掉分片 `1`。

建议方案：

不要使用最大分片号作为起点，而是遍历所有分片，跳过已上传分片：

```js
for (let chunkIndex = 0; chunkIndex < chunkCount; chunkIndex++) {
  if (uploadedChunks.has(chunkIndex)) {
    continue;
  }

  await this.uploadSingleChunk(
    file,
    uploadId,
    chunkIndex,
    chunkCount,
    fileHash,
    folderId,
    taskAbortController,
    targetIsPublic
  );
}
```

验收标准：

- 后端返回不连续分片列表时，前端会补齐缺失分片。
- 不再依赖分片必须连续上传成功。
- 未来支持并行分片上传时无需重写续传逻辑。

### 4. Redis 分片缓存加 transfer_id 隔离

当前问题：

- 物理分片目录已经按 `transfer_id` 隔离。
- Redis 缓存仍主要按 `file_hash + user + is_public` 维度。
- 同一用户同时上传同 hash 文件时，缓存可能互相污染。

建议方案：

新缓存 key 包含 `transfer_id`：

```text
chunk:{tenant}:{user}:{is_public}:{file_hash}:{transfer_id}
```

兼容策略：

- 新上传使用新 key。
- 查询续传时优先查新 key。
- 如果新 key 不存在，再查旧 key 作为历史兼容。

重点修改位置：

- `spug_api/apps/document/libs/chunk_cache.py`
- `spug_api/apps/document/views/upload/chunk.py`
- `spug_api/apps/document/views/upload/resume.py`

验收标准：

- 同一用户同时上传两个相同 hash 的文件，不会互相影响断点续传结果。
- 老的未完成上传仍然可以通过 legacy key 恢复。

## 第二阶段：并发与资源控制

### 5. 上传并发和合并并发分开控制

当前策略：

- 前端上传并发限制为 3。
- `merging` 状态不占前端上传槽。

这个策略对网络上传是合理的，但会把压力转移到后端合并。

建议方案：

- 前端继续保持上传并发 3。
- 后端单独限制合并并发。
- 为资料库合并任务创建独立 Celery 队列。

示例：

```text
document_upload: 处理普通接口请求
document_merge: 处理大文件分片合并
```

Celery worker 建议：

```text
document_merge worker 并发：1-2
```

验收标准：

- 多个大文件同时上传完成后，后端不会同时启动过多合并任务。
- 磁盘 IO 不会被多个大文件合并打满。
- 上传任务和合并任务互不挤占队列。

### 6. 合并状态轮询优化

当前问题：

- 合并状态轮询间隔固定。
- 大文件合并时间长时，前端会持续高频轮询。

建议方案：

使用渐进式轮询：

```text
0-30 秒：每 2 秒轮询一次
30 秒以后：每 5 秒轮询一次
超过 5 分钟：提示后台合并中，降低轮询频率
```

验收标准：

- 大文件合并时请求量明显降低。
- 用户仍能看到合并进度或合并中状态。
- 合并完成后前端能正确收敛到 completed。

## 第三阶段：数据可靠性

### 7. 增加分片级 hash 校验

当前问题：

- 超大文件使用抽样 MD5。
- 合并后只校验文件大小，无法发现部分内容损坏。

建议方案：

每个分片上传时携带分片 hash：

```text
chunk_index
chunk_size
chunk_hash
```

后端保存分片前校验：

```python
actual_hash = calculate_file_md5(temp_chunk_path)
if actual_hash != request_chunk_hash:
    return json_response(error='分片校验失败')
```

验收标准：

- 单个分片内容损坏时，后端能拒绝保存。
- 抽样 MD5 文件也能获得分片级完整性保护。
- 合并前不只是检查分片文件存在，还能确认分片内容正确。

### 8. Celery 合并任务内部增加路径安全校验

当前问题：

- view 层已经校验了 `chunk_dir` 和 `file_path`。
- Celery 任务仍应做二次校验，防止历史任务、异常任务、手工触发任务绕过 view 层。

建议方案：

在 merge task 的环境校验阶段增加：

```python
document_storage_base = os.path.join(settings.BASE_DIR, 'storage', 'documents')
chunk_base_dir = os.path.join(settings.BASE_DIR, 'storage', 'document_chunks')

if not is_safe_path(document_storage_base, self.task_manager.file_path):
    return False, '非法目标文件路径'

if not is_safe_path(chunk_base_dir, self.task_manager.chunk_dir):
    return False, '非法分片目录路径'
```

重点修改位置：

- `spug_api/apps/document/tasks/merge.py`

验收标准：

- Celery 任务收到非法路径时会拒绝执行。
- 合并任务不会写入或删除资料库存储目录之外的路径。

## 第四阶段：状态一致性与清理

### 9. transfer 状态以后端最终结果为准

建议状态语义：

```text
PENDING    已创建记录，但未开始上传
UPLOADING  上传中
PAUSED     用户暂停
MERGING    分片已上传，后端正在合并
COMPLETED  后端已成功创建文件记录
FAILED     上传或合并失败
CANCELED   用户取消
```

前端可以乐观显示进度，但最终完成状态应以后端为准：

- 小文件：后端保存文件并创建文件记录成功后，才算 completed。
- 大文件：Celery 合并并创建文件记录成功后，才算 completed。
- 前端轮询到后端 completed 后再最终显示完成。

验收标准：

- 不出现前端显示 completed，但后端文件记录未创建的情况。
- 合并失败时 transfer 能进入 `FAILED`，并保留错误信息。

### 10. 定时清理孤儿 transfer 和旧分片

建议增加定时任务：

```text
PENDING 超过 24 小时且 file_hash 为空 -> 删除或标记 CANCELED
UPLOADING 超过 24 小时且无分片更新 -> 标记 FAILED
MERGING 超过超时时间且 Celery task 不存在 -> 标记 FAILED
FAILED/CANCELED 超过保留期 -> 清理分片目录
```

验收标准：

- 长期运行后 transfer 表不会积累大量无效记录。
- 旧分片目录能被定期清理。
- 清理任务不会删除正在上传或正在合并的任务数据。

## 推荐落地顺序

### 第一优先级

1. 小文件复用已有 `transferId`
2. transfer 按需创建
3. 断点续传改成上传缺失分片
4. Redis 分片缓存加 `transfer_id`

### 第二优先级

1. 后端合并队列限流
2. 合并状态轮询优化
3. Celery 合并任务内部路径安全校验

### 第三优先级

1. 分片级 hash 校验
2. 孤儿 transfer 清理
3. 上传状态以后端最终结果收敛

## 总结

当前资料库上传架构不需要推倒重来。

建议继续保留：

- 小文件直传
- 大文件分片上传
- 异步合并
- transfer 状态持久化
- 失败后续传和直接合并

需要重点补强：

- transfer 创建时机
- 分片续传策略
- 缓存隔离
- 合并资源控制
- 后端最终状态一致性

按本方案优化后，上传链路可以从“基本可用且方向正确”提升到“弱网、大文件、文件夹批量上传都比较可靠”的水平。
