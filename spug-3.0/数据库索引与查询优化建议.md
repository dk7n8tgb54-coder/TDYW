# 数据库索引与查询优化建议

本文档用于规划本项目在业务数据持续增长后的数据库索引、查询和迁移优化策略。

当前判断基于项目代码中的 Django ORM 查询路径、已有模型索引，以及测试库中的表规模和 `EXPLAIN` 结果。长期目标是支持每个核心业务模块达到几十万条数据后，列表页、详情页、导出、统计和后台任务仍然保持稳定响应。

## 当前现状

测试库当前较大的表如下：

| 表名 | 约数据量 | 说明 |
| --- | ---: | --- |
| `audit_logs` | 34864 | 操作审计日志，持续增长，优先关注 |
| `tdyw_document_transfer` | 6844 | 文档传输记录，上传/下载频繁时增长较快 |
| `tdyw_document_file_public` | 3660 | 公共文档文件表 |
| `tdyw_document_file_private` | 177 | 私有文档文件表 |
| `tdyw_run_logs` | 56 | 当前较小，但长期可能增长 |
| `tdyw_device_resume` | 54 | 当前较小，但长期可能增长 |
| `tdyw_upgrade_records` | 53 | 当前较小，但长期可能增长 |
| `tdyw_fault_records` | 53 | 当前较小，但长期可能增长 |

目前项目已经有不少索引，例如：

- 多数多租户表已经包含 `tenant_id` 相关索引。
- 设备档案已有 `tenant_id + current_status`、`tenant_id + created_at + id`。
- 设备事件已有 `tenant_id + device_resume_id`、`tenant_id + event_time + id`。
- 运行日志已有 `tenant_id + status`、`tenant_id + severity`。
- 文档传输已有 `tenant_id + user`、`tenant_id + status`、`tenant_id + file_hash`、`user + status`、`created_at`。
- 审计日志已有 `tenant_id + id`、`tenant_id + created_at` 等索引。

但从长期高数据量角度看，仍有几个问题：

- 一些列表页只具备过滤索引，缺少“过滤 + 排序 + 分页”的组合索引。
- 一些明细表只按父级 ID 建索引，缺少父级 ID + 排序字段组合索引。
- 文档目录/文件列表查询长期会依赖 `parent_id`、`folder_id`、`is_deleted`、`created_at`，目前组合索引不足。
- 审计日志存在重复单列索引。
- 多个时间字段仍使用 `CharField`，长期统计和范围查询不如 `DateTimeField` 稳定。
- 多处 `icontains` 模糊搜索无法有效使用普通 BTree 索引。

## 优化原则

### 1. 优先优化真实查询路径

不要看到字段就加索引。索引应服务于真实查询，例如：

```python
queryset.filter(tenant_id=tenant_id).order_by('-created_at', '-id')[:20]
queryset.filter(tenant_id=tenant_id, status=status).order_by('-created_at', '-id')[:20]
queryset.filter(tenant_id=tenant_id, parent_id=folder_id, is_deleted=False).order_by('-created_at')
```

### 2. 组合索引要覆盖过滤和排序

长期高数据量下，单纯的过滤索引通常不够。

不推荐只加：

```python
models.Index(fields=['tenant_id', 'status'])
```

更推荐：

```python
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'])
```

这样可以同时支持：

```sql
WHERE tenant_id = ? AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT 20
```

### 3. 多租户表优先以 `tenant_id` 作为组合索引前缀

大多数业务查询都会先做租户隔离，因此多租户业务表的核心索引一般应以 `tenant_id` 开头。

典型模式：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'])
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'])
models.Index(fields=['tenant_id', 'parent_id', '-created_at', '-id'])
```

### 4. 明细表要按父级 ID + 展示顺序建索引

例如运行日志动态、设备事件、升级步骤、文档目录子项等，详情页通常会按父记录查询子记录，并按照时间或序号展示。

推荐模式：

```python
models.Index(fields=['tenant_id', 'runlog_id', 'update_date', 'sequence', 'id'])
models.Index(fields=['tenant_id', 'device_resume_id', '-event_time', '-id'])
models.Index(fields=['tenant_id', 'upgrade_id', 'sequence', 'id'])
```

### 5. 谨慎增加低选择性单列索引

像 `status`、`is_deleted`、`is_success` 这类字段值很少，单独建索引的收益通常有限。

更推荐把它们放入组合索引中：

```python
models.Index(fields=['tenant_id', 'is_deleted', '-created_at', '-id'])
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'])
```

### 6. 模糊搜索不要依赖普通索引

以下查询通常无法有效使用普通 BTree 索引：

```python
name__icontains='xxx'
system_name__icontains='xxx'
owner__icontains='xxx'
detail__icontains='xxx'
```

长期建议：

- 小数据量继续使用 `icontains`。
- 中等数据量改为前缀搜索，例如 `startswith`。
- 大数据量使用全文索引或独立搜索服务。

## 优先级建议

### P0：建议优先处理

P0 是低风险、高收益，或者会随着数据增长很快变成瓶颈的问题。

#### 1. 清理审计日志重复索引

位置：

```text
spug_api/apps/logs/models.py
```

当前 `request_hash`、`log_hash`、`request_id` 字段已经设置了 `db_index=True`，同时 `Meta.indexes` 又手动加了同字段索引，导致数据库中出现重复索引。

建议保留字段上的 `db_index=True`，删除 `Meta.indexes` 中以下三条：

```python
models.Index(fields=['request_hash'], name='audit_req_hash_idx')
models.Index(fields=['log_hash'], name='audit_log_hash_idx')
models.Index(fields=['request_id'], name='audit_req_id_idx')
```

理由：

- 减少重复索引占用空间。
- 降低审计日志写入成本。
- 不影响查询能力。

#### 2. 审计日志增加长期列表索引

审计日志会持续增长，是最应该提前规划的表。

当前已有：

```python
models.Index(fields=['tenant_id', '-id'], name='audit_tenant_id_idx')
models.Index(fields=['tenant_id', 'created_at'], name='audit_tenant_time_idx')
```

如果审计日志列表长期按 `id DESC` 展示，可以保留 `tenant_id + -id`。

如果希望时间筛选和分页都稳定，建议把审计日志列表排序统一为：

```python
queryset.order_by('-created_at', '-id')
```

并增加：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'], name='audit_tenant_ctime_id_idx')
```

如果经常按操作类型筛选：

```python
models.Index(fields=['tenant_id', 'action', '-created_at', '-id'], name='audit_tenant_action_time_idx')
```

如果经常按对象类型筛选：

```python
models.Index(fields=['tenant_id', 'target_type', '-created_at', '-id'], name='audit_tenant_target_time_idx')
```

注意：不要一次性加太多审计日志索引。建议先加主列表索引，再根据慢查询日志决定是否增加 `action`、`target_type` 组合索引。

#### 3. 文档目录和文件列表补组合索引

文档模块以后最容易增长。目录列表、文件列表、搜索、打包下载、回收站清理都会频繁访问。

建议为私有文件夹增加：

```python
models.Index(fields=['tenant_id', 'is_deleted', 'parent_id', '-created_at', '-id'], name='doc_pri_folder_list_idx')
```

建议为私有文件增加：

```python
models.Index(fields=['tenant_id', 'is_deleted', 'folder_id', '-created_at', '-id'], name='doc_pri_file_list_idx')
```

建议为公共文件夹增加：

```python
models.Index(fields=['is_deleted', 'parent_id', '-created_at', '-id'], name='doc_pub_folder_list_idx')
```

建议为公共文件增加：

```python
models.Index(fields=['is_deleted', 'folder_id', '-created_at', '-id'], name='doc_pub_file_list_idx')
```

这些索引服务于：

```python
FolderModel.objects.filter(parent_id=folder_id, is_deleted=False).order_by('-created_at')
FileModel.objects.filter(folder_id=folder_id, is_deleted=False).order_by('-created_at')
```

以及私有空间下的租户隔离：

```python
queryset.filter(tenant_id=request.user.tenant_id)
```

### P1：建议在下一个优化版本处理

P1 是面向未来几十万数据量的核心业务表索引基线。

当前查询路径：

```python
logs = logs.filter(status=...)
logs = logs.filter(severity=...)
logs = logs.filter(created_at__gte=...)
logs = logs.filter(created_at__lte=...)
```

```python
models.Index(fields=['tenant_id', 'status'])
models.Index(fields=['tenant_id', 'severity'])
```

长期建议增加：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'], name='runlog_tenant_time_idx')
```

```python
models.Index(fields=['tenant_id', 'event_type', '-created_at', '-id'], name='runlog_tenant_type_time_idx')
```

#### 2. 运行日志动态表

当前查询路径：

```python
RunLogUpdate.objects.filter(runlog_id=event.id).order_by('update_date', 'sequence', 'id')
RunLogUpdate.objects.filter(runlog_id=event.id).order_by('-update_date', '-sequence', '-id')
```

```python
models.Index(fields=['tenant_id', 'runlog_id', 'update_date', 'sequence', 'id'], name='runlog_update_list_idx')
```

```python
queryset = queryset.filter(upgrade_time__lte=...)
```

```python

```

长期建议增加：

```python
models.Index(fields=['tenant_id', '-upgrade_time', '-id'], name='upgrade_tenant_time_idx')
models.Index(fields=['tenant_id', 'status', '-upgrade_time', '-id'], name='upgrade_tenant_status_time_idx')

```

注意：`system__icontains`、`owner__icontains` 不适合普通索引，需要另行搜索优化。

#### 4. 设备档案主表

当前已有：

```python
models.Index(fields=['tenant_id', 'current_status'])
models.Index(fields=['tenant_id', '-created_at', '-id'])
```

长期建议把状态筛选索引升级为：

```python
models.Index(fields=['tenant_id', 'current_status', '-created_at', '-id'], name='device_status_time_idx')
```

如果软删除数据会保留很多，还应考虑：

```python
models.Index(fields=['tenant_id', 'is_deleted', '-created_at', '-id'], name='device_deleted_time_idx')
models.Index(fields=['tenant_id', 'is_deleted', 'current_status', '-created_at', '-id'], name='device_del_status_time_idx')
```

注意：`device_sn` 已有租户内唯一约束：

```python
models.UniqueConstraint(fields=['tenant_id', 'device_sn'], name='uniq_device_resume_tenant_sn')
```

这个约束已经能支持按 `tenant_id + device_sn` 精确查询，不需要重复加普通索引。

#### 5. 设备事件表

当前已有：

```python
models.Index(fields=['tenant_id', 'device_resume_id'])
models.Index(fields=['tenant_id', '-event_time', '-id'])
```

长期建议增加：

```python
models.Index(fields=['tenant_id', 'device_resume_id', '-event_time', '-id'], name='device_event_device_time_idx')
models.Index(fields=['tenant_id', 'event_type', '-event_time', '-id'], name='device_event_type_time_idx')
```

第一条服务于设备详情页和设备履历导出。第二条服务于按事件类型筛选的事件列表。

#### 6. 文档传输表

当前已有：

```python
models.Index(fields=['tenant_id', 'user'], name='idx_transfer_tenant_user')
models.Index(fields=['tenant_id', 'status'], name='idx_transfer_tenant_status')
models.Index(fields=['tenant_id', 'file_hash'], name='idx_transfer_tenant_hash')
models.Index(fields=['user', 'status'], name='idx_transfer_user_status')
models.Index(fields=['created_at'], name='idx_transfer_created')
```

长期建议增加：

```python
models.Index(fields=['tenant_id', 'user', '-created_at', '-id'], name='transfer_tenant_user_time_idx')
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'], name='transfer_tenant_status_time_idx')
models.Index(fields=['status', 'created_at'], name='transfer_status_created_idx')
```

说明：

- `tenant_id + user + created_at + id` 服务于用户传输记录列表。
- `tenant_id + status + created_at + id` 服务于状态筛选列表。
- `status + created_at` 服务于后台清理超时和终态过期传输任务。

### P2：根据数据量和慢查询日志再处理

#### 1. 故障、干扰、值班等日期型模块

这些模块当前数据量较小，但如果未来也会到几十万，建议统一模式：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'])
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'])
models.Index(fields=['tenant_id', 'fault_date', '-id'])
models.Index(fields=['tenant_id', 'datetime', '-id'])
models.Index(fields=['tenant_id', 'duty_date', '-id'])
```

具体使用哪个字段，应以各模块列表页和导出页的主排序字段为准。

#### 2. 检查表模块

检查表数据天然按年月日、项目、模板组织，当前已有唯一约束：

```python
unique_together = ['template', 'year', 'month', 'day', 'item_index']
unique_together = ['year', 'month', 'day']
```

长期建议围绕查询路径补：

```python
models.Index(fields=['template', 'year', 'month', 'day', 'item_index'], name='cs_record_month_idx')
models.Index(fields=['year', 'month', 'day'], name='cs_daily_day_idx')
```

如果多租户查询参与检查表模块，也应把 `tenant_id` 放入组合索引前缀。

## 时间字段优化建议

当前多个模型使用 `CharField(max_length=20)` 保存时间，例如：

```python
created_at = models.CharField(max_length=20)
upgrade_time = models.CharField(max_length=20)
event_time = models.CharField(max_length=20)
```

如果时间格式严格固定为：

```text
YYYY-MM-DD HH:MM:SS
```

字符串范围查询在字典序上可以工作。但长期仍建议逐步迁移为：

```python
models.DateTimeField()
models.DateField()
```

收益：

- 范围查询更可靠。
- 分组统计更自然。
- 数据库优化器更容易选择合适索引。
- 避免脏数据破坏排序。
- 后续按月归档、分区、报表统计更方便。

建议迁移策略：

1. 新增 `created_at_dt` / `event_time_dt` 等临时字段。
2. 数据迁移，把合法字符串转换为真实时间。
3. 代码读写切换到新字段。
4. 稳定一个版本后删除旧字段或保留兼容字段。
5. 最后重命名字段，保持接口语义一致。

不要在高峰期一次性修改大量时间字段，应该按模块逐步推进。

## 搜索优化建议

当前多处列表使用：

```python
field__icontains=keyword
```

长期大数据量下，普通索引无法有效优化 `%keyword%` 查询。

建议分阶段处理：

### 阶段一：保持现状

适用于几万到十几万数据量，且搜索不是高频操作。

### 阶段二：改为前缀搜索

如果业务允许，把：

```python
field__icontains=keyword
```

改为：

```python
field__startswith=keyword
```

此时可以考虑普通索引：

```python
models.Index(fields=['tenant_id', 'field'])
```

### 阶段三：全文索引或搜索服务

如果文档名、设备名、日志内容、审计详情需要高频模糊搜索，建议引入：

- MySQL/MariaDB FULLTEXT 索引。
- OpenSearch/Elasticsearch。
- 单独搜索表。

不要试图通过给所有文本字段加普通索引解决 `icontains`。

## 分页优化建议

当前多数列表使用 offset 分页：

```python
queryset[start:end]
```

当数据达到几十万或百万级，深分页会变慢：

```sql
LIMIT 100000, 20
```

长期建议核心列表支持游标分页：

```text
第一页：ORDER BY created_at DESC, id DESC LIMIT 20
下一页：WHERE (created_at, id) < (last_created_at, last_id)
```

对应索引：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'])
```

前端仍可保留普通页码，但高频大表建议逐步切换为“加载更多”或游标式分页。

## 导出优化建议

导出接口容易绕过分页，成为大表瓶颈。

建议：

- 所有导出必须有最大条数限制。
- 大导出改为异步任务。
- 导出条件必须走索引，例如租户、时间范围、状态。
- 禁止无条件导出几十万数据。
- 导出前先 `count()`，超过阈值返回异步任务或提示缩小范围。

推荐导出查询模式：

```python
queryset.filter(
    tenant_id=tenant_id,
    created_at__gte=start_time,
    created_at__lte=end_time,
).order_by('-created_at', '-id')[:MAX_EXPORT_COUNT]
```

对应索引：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'])
```

## 后台清理任务优化建议

文档传输、审计日志、临时文件、过期任务等后台清理会持续扫描数据。

建议所有清理任务都使用可索引条件：

```python
DocumentTransfer.objects.filter(status__in=[...], created_at__lte=cutoff)
```

对应索引：

```python
models.Index(fields=['status', 'created_at'])
```

如果清理按租户执行：

```python
models.Index(fields=['tenant_id', 'status', 'created_at'])
```

清理任务应分批执行：

```python
ids = queryset.order_by('id').values_list('id', flat=True)[:1000]
```

不要一次性加载或删除大量对象。

## 建议落地顺序

### 第一阶段：低风险清理

目标：减少冗余索引，建立最关键的大表基线。

- 清理 `audit_logs` 重复索引。
- 为审计日志增加 `tenant_id + created_at + id` 主列表索引。
- 为文档 folder/file 列表增加组合索引。

### 第二阶段：核心业务表基线索引

目标：让所有未来可能几十万数据的主表具备稳定列表索引。

- 运行日志主表。
- 运行日志动态表。
- 升级记录主表。
- 设备档案主表。
- 设备事件表。
- 文档传输表。

### 第三阶段：慢查询驱动补充索引

目标：根据真实使用情况补状态、类型、统计类索引。

- 打开数据库慢查询日志。
- 收集高频慢查询。
- 用 `EXPLAIN` 验证是否使用索引。
- 只对真实慢查询补索引。

### 第四阶段：结构性优化

目标：解决索引无法彻底解决的问题。

- 时间字段从 `CharField` 迁移到 `DateTimeField`。
- 大表改游标分页。
- 高频模糊搜索引入全文索引或搜索服务。
- 大导出改异步任务。
- 审计日志按时间归档或分区。

## 验证方式

每次新增索引前后都应验证。

### 1. 查看迁移计划

```powershell
cd E:\TDYW\spug-3.0\spug_api
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
```

### 2. 查看 SQL

```powershell
python manage.py sqlmigrate logs 0004
python manage.py sqlmigrate document 0007
```

### 3. 使用 EXPLAIN 验证

示例：

```sql
EXPLAIN
SELECT *
FROM audit_logs
WHERE tenant_id = 'admin'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

重点看：

- `key` 是否命中预期索引。
- `rows` 是否明显下降。
- `Extra` 是否减少 `Using filesort`。
- 是否出现全表扫描。

### 4. 观察写入成本

索引会提升查询，但会增加写入成本。

新增索引后应观察：

- 审计日志写入速度。
- 文档上传/传输状态更新速度。
- 批量导入或批量创建速度。
- 数据库磁盘占用。

## 注意事项

### 不要一次性加太多索引

索引不是越多越好。每新增一个索引，写入、更新、删除都会多维护一份结构。

建议每个大表先控制在 3 到 6 个核心索引，再根据慢查询补充。

### 不要重复建立等价索引

例如已经有：

```python
models.Index(fields=['tenant_id', 'status', '-created_at', '-id'])
```

通常不需要再保留：

```python
models.Index(fields=['tenant_id', 'status'])
```

因为前者的左前缀可以覆盖 `tenant_id + status` 查询。

但是否删除旧索引，需要通过 `EXPLAIN` 和线上查询模式确认。

### 索引命名要稳定

建议手动命名核心索引，避免 Django 自动生成过长且不易识别的名称。

示例：

```python
models.Index(fields=['tenant_id', '-created_at', '-id'], name='runlog_tenant_time_idx')
```

### 大表建索引要注意上线窗口

当表已经很大时，创建索引可能耗时较长，并影响写入。

建议：

- 尽量在数据量还小时提前建核心索引。
- 大表上线索引选择低峰期。
- MariaDB/MySQL 版本允许时使用在线 DDL。
- 生产执行前在测试库或备份库测耗时。

## 总结

如果按“每个模块未来都有几十万条数据”考虑，本项目应该提前建立一套索引基线：

- 主表：`tenant_id + 时间倒序 + id倒序`
- 状态列表：`tenant_id + 状态 + 时间倒序 + id倒序`
- 明细表：`tenant_id + 父级ID + 展示顺序`
- 文档目录：`tenant_id/is_deleted + parent/folder + created_at`
- 审计日志：清理重复索引，强化租户 + 时间分页索引

短期最建议先处理：

1. 清理 `audit_logs` 重复索引。
2. 补审计日志主列表索引。
3. 补文档目录/文件列表组合索引。
4. 分批补运行日志、升级、设备、文档传输等核心表组合索引。

长期再推进：

- 时间字段类型迁移。
- 游标分页。
- 异步导出。
- 全文搜索。
- 慢查询日志驱动的二次索引优化。
