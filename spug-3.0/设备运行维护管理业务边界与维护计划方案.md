# 设备运行维护管理业务边界与维护计划方案

**文档状态：** 讨论稿  
**编制日期：** 2026-10-07  
**适用范围：** 设备运行维护管理平台  
**本稿目的：** 在不扩展到采购、合同、资产、备件和报废管理的前提下，明确运行维护模块边界，并提出维护计划与逾期提醒的建设方案。

## 一、范围与产品定位

平台名称建议由“设备全生命周期管理”调整为“设备运行维护管理”。当前平台管理对象是**系统级运行维护事项**，不承担单台设备资产、序列号、备件库存和采购报废管理。

本平台关注以下闭环：

> 值班巡视与日常运行记录 → 发现异常 → 必要时转正式故障 → 处置进展 → 恢复并结案 → 形成重大事项履历。

周期性维护另有一条执行链：

> 维护计划 → 到期任务 → 实际维护 → 维护台账 → 复核 → 检修履历。

## 二、业务模块边界

| 模块 | 业务定位 | 主要记录 | 不负责的内容 |
|---|---|---|---|
| 系统档案 | 系统主数据和运行状态基线 | 系统名称、型号、地点、用途、厂家、使用单位、负责人、健康状态 | 单台设备资产、序列号、库存 |
| 日巡视 | 值班人员按固定表格完成整体巡视 | 值班日、值班人员、固定轮次、检查内容、结果、异常说明 | 维护计划、正式故障处置、单台设备资产履历 |
| 运行记录 | 即时记录日常运行情况和临时事件 | 发生时间、标题、情况描述、登记人、已采取措施、处理进展 | 固定轮次巡视、周期维护、正式故障结案 |
| 维护台账 | 记录已经执行的周月维护和季维护 | 实际执行日期、执行人、维护项目、结果、异常说明、现场处理内容、复核结果 | 维护计划生成、故障全过程处置 |
| 故障处置 | 对需要持续处理、恢复和结案的问题建立正式闭环 | 故障现象、影响程度、原因分析、处置进展、恢复确认、结案说明 | 普通运行留痕、周期维护计划 |
| 系统配置 | 维护系统参数及参数变更过程 | 参数定义、变更前后值、生效、验证、回退 | 软件版本升级过程 |
| 系统升级 | 管理软件或系统版本更新过程 | 升级内容、影响范围、风险、回退方案、执行步骤、升级状态 | 一般参数调整、采购合同 |
| 系统履历 | 重要运维事实的只读汇总 | 重大故障、系统更新、正式检修记录 | 所有运行记录和所有草稿的重复展示 |
| 维护计划（建议新增） | 定义何时应做什么维护，并生成待执行任务 | 周/月/季周期、适用范围、模板、计划窗口、任务状态、跳过原因 | 具体维护结果本身，结果仍由维护台账保存 |

### 2.1 日巡视、运行记录和维护台账的区分

三者不是按“是否有现场处理”区分。现有数据中可能存在现场处理或采取措施字段，但这些只是记录附加信息，不代表三者共享同一个业务流程。

实际区分口径如下：

- **日巡视：** 按值班日和固定轮次，对规定检查表逐项检查；一张表可以覆盖多个系统和设备，不需要逐条绑定系统或设备。
- **运行记录：** 发生了日常运行情况或临时事件时即时登记，时间由事件发生时间决定，不受固定轮次限制。
- **维护台账：** 按周、月、季等维护周期记录已经执行的计划性维护，时间由实际维护日期决定。

同一事项不得无理由在三个模块重复建单。推荐采用以下原则：

1. 日巡视和维护台账负责记录检查或维护结果。
2. 普通运行情况只登记运行记录，不自动转为故障。
3. 只有需要持续处理、影响系统运行或需要恢复确认的事项，才转为正式故障。
4. 转为故障后，后续处置、恢复和结案以故障记录为准，来源记录保留反向追溯关系。

## 三、事项转换规则




### 3.3 运行记录

运行记录分为两类：

- **日常运行：** 记录常规作业、操作结果或运行情况，登记完成后即可结束，不进入故障跟进流程。
- **异常事件：** 记录临时异常。可以直接保留为“已记录”，也可以追加处理进展进入“跟进中”，必要时转为正式故障。

转为故障后，运行记录只保留来源和转故障状态，正式处置过程、恢复确认和关闭均在故障模块完成。

## 四、故障处置进展设计建议

故障处置记录和运行记录处理进展暂时保留为两个对象，因为它们的上级事项和状态不同：

- 运行记录进展：运行事件的后续跟进；
- 故障处置进展：正式故障的排查、维修和恢复过程。

两者可以采用一致的填写结构：时间、处置人姓名、处置内容、附件、更正历史。暂不强行合并数据模型。

为提高厂家送修、外委维修等内容的可读性，故障处置进展建议增加可选分类：

| 分类 | 适用内容 |
|---|---|
| 检查分析 | 故障定位、测试、原因排查 |
| 临时措施 | 临时切换、旁路、重启、应急恢复 |
| 送厂家/外委 | 送修、厂家分析、外委处理 |
| 厂家反馈 | 厂家结论、维修建议、返修说明 |
| 返回测试 | 设备返回后的安装、测试和验证 |
| 持续观察 | 恢复后的观察和复测 |
| 其他 | 不适合以上分类的处置内容 |

分类是辅助查询字段，不改变追加式进展记录和故障状态机。

## 五、维护计划与周期任务方案

### 5.1 建设目标

现有周月维护和季维护台账已经能够记录“实际做了什么”，缺少的是“什么时候应该做、当前是否逾期”。维护计划模块用于补足计划侧，不替代维护台账。

### 5.2 计划定义

一条维护计划至少包含：

- 计划名称；
- 维护类型：周维护、月维护、季维护；
- 适用范围：全部系统或指定系统/站点；
- 使用的维护模板；
- 周期规则和计划窗口；
- 生效日期和停用日期；
- 是否需要复核；
- 备注。

计划本身不记录执行结果。执行结果必须落入周月或季维护台账。

### 5.3 任务生成

系统按计划周期生成维护任务。推荐采用“周期窗口 + 幂等键”方式：

- 周任务：按自然周生成；
- 月任务：按自然月生成；
- 季任务：按自然季度生成；
- 幂等键：计划 ID + 周期类型 + 周期起始日期；
- 同一计划同一周期只能生成一条有效任务；
- 已停用计划不再生成新任务，历史任务和历史台账保留。

生成时机可以采用每日一次的后台任务，也可以在用户进入维护首页时补偿生成。两者均应使用幂等创建，避免重复任务。

### 5.4 任务状态

建议状态如下：

| 状态 | 含义 |
|---|---|
| 待执行 | 已生成，尚未到计划窗口或尚未完成 |
| 进行中 | 已开始填写维护台账 |
| 已完成 | 已关联维护台账，且台账达到规定完成状态 |
| 已逾期 | 超过计划窗口仍未完成 |
| 已跳过 | 本周期明确不执行，必须填写原因 |
| 已取消 | 计划失效或周期被管理员取消，保留原因 |

“已逾期”是待执行任务的派生或流转状态，不能因为查看页面就自动伪造完成。完成必须以真实维护台账为依据。

### 5.5 任务与维护台账的关系

建议一条维护任务对应一张维护台账，但允许以下情况：

- 一张台账覆盖多个系统；
- 一张台账包含多个维护项目；
- 一个维护计划周期内按实际工作需要分批填写，但最终只能明确一个完成结果；
- 台账退回或作废时，任务不能继续保持“已完成”。

推荐完成判定：

1. 维护台账已提交；
2. 若该类型要求复核，则台账已复核通过；
3. 台账未被作废；
4. 台账的实际执行日期落在任务允许窗口内，或已填写补录原因。

### 5.6 逾期提醒

提醒对象是科室或租户，而不是个人账号，符合多人共用账号的实际情况。

建议提供：

- 维护首页待执行数量；
- 逾期数量和逾期天数；
- 按维护类型筛选；
- 按系统或适用范围筛选；
- 进入任务后直接创建或打开关联台账；
- 跳过时必须填写原因；
- 周期跨越后仍保留历史逾期任务，不自动删除。

提醒采用事件驱动或进入页面时刷新即可。维护计划属于低频业务，不需要高频轮询。

## 六、系统履历规则

系统履历定位为重要运维事实的只读汇总，不复制所有业务表。

### 6.1 纳入范围

1. **重大故障**：影响系统运行、造成降级或中断，或人工明确标记为重大；建议以“影响系统运行”为默认纳入口径。
2. **系统更新**：软件升级登记、升级完成、升级回退等关键节点。
3. **正式检修记录**：已完成并达到复核要求的周月维护、季维护台账。

### 6.2 不纳入范围

- 普通日常运行记录；
- 日巡视的正常明细；
- 维护台账草稿、退回或作废记录；
- 故障处置过程中的每一条普通进展；
- 普通配置值变化，除非明确标记为重要配置变更。

### 6.3 建议的履历节点

| 来源 | 建议节点 |
|---|---|
| 重大故障 | 故障发生、故障恢复确认、故障关闭、故障撤销 |
| 系统升级 | 升级登记、升级完成、升级回退 |
| 正式检修 | 检修完成、检修复核通过 |

### 6.4 “重大故障”的待确认口径

最终需要在产品上二选一：

- 自动口径：只要影响程度为降级、故障或中断，就进入履历；
- 人工口径：故障登记时增加“是否重大”，只有勾选后进入履历。

建议第一阶段采用自动口径，减少漏记；如果实际履历数量过多，再增加人工标记或分级规则。

## 七、模块状态与数据原则

### 7.1 状态责任

- 系统健康状态只由有效正式故障计算；
- 日巡视和维护台账的异常不直接改变系统健康状态；
- 运行记录的“跟进中”不等于系统故障；
- 故障关闭必须有恢复时间、恢复确认人和结案说明；
- 台账复核状态不等于故障恢复状态，两者不能互相替代。

### 7.2 历史可追溯

- 来源记录转故障后，来源记录保留；
- 故障、维护台账、升级和配置变更保存系统名称等历史快照；
- 履历只读生成，业务更正通过追加新节点或审计留痕表达；
- 共用账号场景下，业务表保留手工填写的实际人员姓名，登录账号只作为操作审计。

## 八、建议实施顺序

### 第一阶段：规则确认

1. 确认模块名称改为“设备运行维护管理”；
2. 确认事项转故障的统一判断条件；
3. 确认重大故障的履历口径；
4. 确认维护台账何时算完成；
5. 确认故障处置进展分类。

### 第二阶段：维护计划

1. 维护计划定义；
2. 周/月/季周期任务生成；
3. 任务与维护台账关联；
4. 待执行、逾期、跳过状态；
5. 首页统计和进入页面刷新；
6. 计划任务和生成逻辑的幂等测试。

### 第三阶段：履历收敛

1. 只保留重大故障、系统更新、正式检修三类主事项；
2. 明确维护台账复核通过后的履历生成时点；
3. 校验故障、升级、维护事项的来源跳转和权限；
4. 增加按系统、事项类型和时间范围的查询统计。

### 第四阶段：处置进展增强

1. 增加处置进展分类；
2. 保留自由文本作为详细说明；
3. 增加厂家送修、外委、返回测试等分类统计；
4. 根据实际使用量再决定是否抽取通用进展模型。

## 九、当前明确不纳入范围

本方案不建设以下内容：

- 采购、合同、资产卡片、序列号和报废；
- 备件库存、领用和采购申请；
- 工单转派、个人责任人和 SLA 验收；
- 厂家维修费用独立核算；
- 校准、计量和检测证书；
- 实时监控、告警阈值和遥测数据；
- 跨系统故障关联和级联影响；
- 单台设备级资产履历。

这些内容由其他系统承载，或暂不属于本平台运行维护阶段的目标。

## 十、待评审问题

以下问题在进入设计和开发前需要由业务方确认：

1. 周维护、月维护是否共用同一种维护计划模型，还是分别配置模板？
2. 维护任务完成是否必须等台账复核通过？
3. 维护任务允许提前多久执行，逾期后是否允许补录？
4. 跳过任务是否需要管理员权限，还是共用科室账号即可操作？
5. “重大故障”采用自动判断还是人工勾选？
6. 普通配置变更是否完全不进入系统履历，还是允许标记为重要变更？
7. 故障处置进展分类是否需要统计报表，还是只用于详情筛选？
