# 资料库模块代码质量报告

> 更新时间：2026-06-10  
> 审查范围：`spug_api/apps/document/`、`spug_api/tests/` 中资料库相关测试、`tests/` 中资料库相关测试、`spug_web/src/pages/document/`  
> 审查方式：静态代码审查 + 针对原报告问题逐项反查  

---

## 一、结论摘要

资料库模块已经不是一个小模块，当前后端非迁移/非缓存 Python 文件约 100 个，前端 JS 文件约 96 个，并包含上传、断点续传、合并、传输列表、回收站、搜索、预览、磁盘统计等多条业务链路。

模块整体可用，且已经有不少工程化痕迹：后端按 `views / services / libs / tasks` 拆分，前端上传核心拆出了状态机、队列、协调器和测试目录。但当前仍存在状态定义不一致、前端定时器泄漏、模块顶层 DOM 副作用、模型重复、约束不一致、历史备份文件残留等问题。

综合评价：**可维护性中等偏低，稳定性风险集中在状态流转和上传/清理链路，建议分阶段治理。**

## 二、总体评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | 3/5 | 后端分层基本清楚，前端上传核心有模块化改造；但 Public/Private 模型重复、Store 单例依赖顺序较脆弱 |
| 代码规范 | 3/5 | 命名整体可读，但存在函数内 import、裸 `Exception`、顶层 DOM 操作和旧备份文件 |

| 性能 | 3/5 | 已有分页、搜索限制、批量清理等优化；但全局 `ordering`、LIKE 递归搜索、部分长链路查询仍有成本 |

## 三、关键问题

### P0-1：传输状态定义不一致，可能导致运行时状态流转异常

证据：

- `spug_api/apps/document/constants.py` 中 `TransferStatus` 定义了 `MERGING`，但没有 `DOWNLOADING`
- `spug_api/apps/document/models.py` 中 `DocumentTransfer.TRANSFER_STATUS_CHOICES` 定义了 `DOWNLOADING`，但没有 `MERGING`
- `spug_api/apps/document/tasks/merge.py`、`views/upload/merge.py`、`views/upload/direct_merge.py`、`tasks/timeout_checker.py` 多处写入或查询 `MERGING`

影响：

- 数据库中会出现模型 choices 未声明的 `MERGING` 状态。
- 状态校验函数 `is_valid_status_transition()` 无法处理模型中存在的 `DOWNLOADING`。
- 传输列表、批量操作、超时清理、合并恢复等逻辑容易出现状态不可识别或非法转换。

结论：这是当前最明确的稳定性问题，建议优先修复。

---

### P0-2：上传核心存在未释放的 `setInterval`

证据：

- `spug_web/src/pages/document/stores/upload/core/index.js`
- `_initStateMachine()` 中直接调用 `setInterval()`，但没有保存返回值，也没有在销毁流程中清理。

影响：

- 页面多次挂载、热更新或 Store 重建后会累积定时器。
- 定时器继续引用旧的 `stateMachineManager`，造成内存泄漏和重复 cleanup。

结论：这是实质前端资源泄漏，应优先修复。

---

### P1-1：`Explorer/index.js` 模块顶层直接操作 DOM

证据：

- `spug_web/src/pages/document/Explorer/index.js` 文件末尾直接执行：
  - `document.createElement('style')`
  - `document.head.appendChild(style)`

影响：

- 热更新时可能重复插入样式。
- Jest/SSR/预渲染等没有 `document` 的环境会直接失败。
- 样式位置脱离 CSS Modules，维护成本变高。

结论：应改为 less/css 文件或组件生命周期内带幂等标识的注入。优先推荐移到样式文件。

---

### P1-2：Public/Private 模型重复严重

证据：

- `DocumentFolderPrivate` 与 `DocumentFolderPublic` 字段和方法高度重复。
- `DocumentFilePrivate` 与 `DocumentFilePublic` 字段和 `delete()` 逻辑高度重复。

影响：

- 删除、恢复、缩略图清理、待清理标记等逻辑需要两处同步修改。
- 历史注释中已有多处 `P0修复` 标记，说明该区域经历过紧急修复，重复逻辑会放大遗漏风险。

结论：这是架构债，不建议定为立即 P0，但应作为中期重构重点。

---

### P1-3：硬删除失败抛出裸 `Exception`，事务语义不清晰

证据：

- `DocumentFilePrivate.delete()`
- `DocumentFilePublic.delete()`
- 物理文件删除失败后先保存 `is_pending_clean` 等字段，再 `raise Exception(...)`

影响：

- 调用方无法精准捕获异常类型。
- 如果调用方外层包裹 `transaction.atomic()`，保存待清理标记和后续异常回滚之间的行为需要明确设计。
- 前端只能收到泛化删除失败，后端排查也缺少结构化异常类型。

结论：应定义模块级自定义异常，并明确调用方事务边界。

---

### P1-4：私有文件夹缺少同级同名唯一约束

证据：

- `DocumentFolderPublic` 有 `UniqueConstraint(fields=['name', 'parent'])`
- `DocumentFolderPrivate` 没有类似约束

影响：

- 同一用户/租户同一父目录下可能出现同名文件夹。
- 前端路径显示、移动/复制、恢复冲突处理会变复杂。

注意：

- 私有空间约束不能简单照抄公共空间。建议至少包含 `tenant_id`，并结合当前业务判断是否还需要 `created_by`。

---

### P1-5：全局 `ordering = ['-created_at']` 带来隐式查询成本

证据：

- `DocumentFolderPrivate`
- `DocumentFilePrivate`
- `DocumentFolderPublic`
- `DocumentFilePublic`
- `DocumentTransfer`

影响：

- 未显式排序的查询会默认带上排序。
- 对 `exists()`、部分关联查询、分页前计数和后台任务扫描不一定必要。

结论：不是立即故障，但建议逐步移除模型级默认排序，在列表接口显式排序。

---

### P1-6：Store 单例和 RootStore 注入方式较脆弱

证据：

- `spug_web/src/pages/document/stores/index.js` 中 `navigationStore`、`uploadUIStore` 是模块单例，`UploadCoreStore` 由 `RootStore` 创建。
- `navigation/index.js`、`upload/ui/index.js` 中存在从 `window.__ROOT_STORE__` 获取 rootStore 的兼容逻辑。

影响：

- 初始化顺序依赖模块加载顺序。
- 单元测试、热更新、多实例页面会更难隔离。

结论：短期可保留，长期建议由 `RootStore` 统一创建子 Store 并注入依赖。

---

### P1-7：权限错误响应格式仍不够统一

证据：

- `libs/document_decorators.py` 返回 `json_response(error=...)`
- 部分 views 自行返回 `json_response(error='...', code=403)` 或普通错误文本

影响：

- 前端需要兼容多种错误语义。
- 审计日志和用户提示不容易标准化。

结论：不是权限缺失，但属于接口一致性问题。

## 四、一般问题

### P2-1：`get_full_path()` 递归无循环保护

`DocumentFolderPrivate.get_full_path()` 和 `DocumentFolderPublic.get_full_path()` 递归向上拼路径。正常数据库树结构下没有问题，但如果历史数据或并发移动造成循环引用，会递归溢出。

建议改为迭代实现，并设置最大深度。

### P2-2：函数内 `import logging`

`DocumentFilePrivate.delete()` 和 `DocumentFilePublic.delete()` 内部导入 logging 并创建 logger。性能影响很小，但不符合常规风格，应移到模块顶部。

### P2-3：`AllObjectsManager` 与默认 Manager 等价

`AllObjectsManager.get_queryset()` 仅返回 `super().get_queryset()`，功能等价于默认 Manager。保留它可以表达语义，但建议补充注释，避免误解。

### P2-4：`UploadPanel.old.js`、`.bak`、`.backup` 文件残留

资料库前端目录中存在：

- `Explorer.js.bak`
- `UploadPanel.old.js`
- `recycle-bin/store.js.backup`

这些文件会干扰代码搜索和人工审查，也可能被错误引用。

### P2-5：`index.js` 使用 try/catch 包裹组件渲染

`spug_web/src/pages/document/index.js` 在函数组件体内包裹大段 try/catch，并直接渲染 `error.message`。这不是推荐的 React 错误处理方式，建议改为 Error Boundary。

### P2-6：搜索中保留 `QuerySet.extra()`

`views/search.py` 的 FULLTEXT helper 使用 `queryset.extra(where=[...], params=[...])`。当前参数走 `params`，不是典型 SQL 注入；但 `extra()` 是老接口，未来迁移和兼容性较差。

## 五、对原质量报告的修正

原报告有价值，但存在以下不准确点：

1. “无单元测试，仅有 locust 压测脚本”不准确。当前仓库存在多份资料库后端测试和前端上传状态机测试。
2. “后端约 40 文件 / 前端约 24 文件”不准确。当前实际规模明显更大，说明原报告漏扫了子目录、测试、回收站或上传核心文件。
3. “celery_lock Redis key 无过期时间”不符合当前代码。`RedisLock.acquire()` 默认 `timeout=600`，底层设置 `ex=timeout`。
4. “NavigationActions 未使用 @action”需要降级。常规调用路径经过 `NavigationStore` 的 `@action.bound` 代理，直接调用 `actions` 才有风险。
5. SQL 风险描述偏重。`search.py` 的 FULLTEXT helper 使用了参数化 `params`，不是直接拼接用户输入。
6. 修复示例中使用 `CANCELLED` 不符合当前代码。当前状态拼写是 `CANCELED`，不能直接替换。

## 六、建议优先级

### 第一阶段：稳定性修复

1. 统一 `TransferStatus`、`TRANSFER_STATUS_CHOICES` 和前端状态常量。
2. 修复 `UploadCoreStore` 的 `setInterval` 泄漏。
3. 移除 `Explorer/index.js` 的顶层 DOM 操作。
4. 为状态转换补充回归测试。

### 第二阶段：一致性和约束

1. 为私有文件夹增加合理唯一约束。
2. 定义硬删除失败自定义异常，明确事务行为。
3. 统一权限错误响应结构。
4. 清理前端备份文件。

### 第三阶段：架构治理

1. 抽象 Public/Private 共同基类或共同 Mixin。
2. 移除模型级默认 ordering，列表接口显式排序。
3. 重构 RootStore 依赖注入。
4. 将 `get_full_path()` 改为带深度保护的迭代实现。

---

## 七、总体判断

资料库模块当前的核心问题不是“完全缺少规范”，而是历史迭代后留下的状态常量分散、模型重复、前端单例和备份文件残留。短期应先修状态一致性和定时器泄漏，避免上传/合并链路继续积累隐性故障；中期再做模型抽象和 Store 初始化治理。
