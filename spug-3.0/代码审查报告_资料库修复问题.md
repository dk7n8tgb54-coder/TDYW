## 一、严重问题汇总（P0/P1）

### 🔴 P0-1: 断点续传验证逻辑存在严重缺陷

**文件**: `views/upload/validators.py` 第40-76行, `views/upload/chunk_checker.py` 第147-187行

**问题描述**:
`validate_transfer_record` 和 `validate_against_transfer` 方法存在以下问题：

```python
# 问题代码（validators.py:50-54）
transfer = DocumentTransfer.objects.filter(
    file_hash=file_hash,
    user=user,
    is_public=is_public
).first()  # ⚠️ 严重问题：使用.first()可能导致匹配到错误的记录
```

**具体问题**:
1. **多记录匹配问题**: 同一个用户上传同一文件多次时，`.first()`返回的是数据库中的任意一条（通常是第一条），可能不是最新的记录
2. **状态未过滤**: 查询没有限制状态，可能匹配到已完成或已失败的旧记录
3. **排序缺失**: 没有按`created_at`或`id`排序，导致行为不可预测
4. **租户隔离风险**: 查询条件中没有`tenant_id`，理论上存在跨租户风险（虽然user字段已隐含租户）

**修复建议**:
```python
# 修复后代码
transfer = DocumentTransfer.objects.filter(
    file_hash=file_hash,
    user=user,
    is_public=is_public,
    status__in=['PENDING', 'UPLOADING', 'PAUSED']  # 只匹配未完成的记录
).order_by('-created_at').first()  # 按创建时间倒序，取最新的
```

### 🔴 P0-2: 合并锁存在内存泄漏风险

**文件**: `views/upload/lock.py` 第19-21行, 第87-116行

**问题描述**:
```python
# 问题代码（lock.py:19-21）
_merge_locks = {}
_merge_locks_mutex = threading.Lock()

# 问题代码（lock.py:81-84）
def get_merge_lock(file_hash, is_public, tenant_id):
    with _merge_locks_mutex:
        if lock_key not in _merge_locks:
            _merge_locks[lock_key] = MergeLock()
        return _merge_locks[lock_key]  # ⚠️ 只创建不删除，内存泄漏！
```

**具体问题**:
1. **内存泄漏**: `_merge_locks`字典不断增长，每个不同的file_hash都会创建一个新锁，永远不会被删除
2. **无自动清理**: `cleanup_stale_locks`虽然存在，但没有被任何地方调用
3. **多进程问题**: 多进程部署时（如Gunicorn），每个进程有自己的锁字典，锁在进程间不共享

**修复建议**:
```python
# 1. 添加最大锁数量限制
MAX_LOCKS = 10000

def get_merge_lock(file_hash, is_public, tenant_id):
    with _merge_locks_mutex:
        # 清理最旧的锁
        if len(_merge_locks) > MAX_LOCKS:
            # 删除最久未使用的锁（需要记录最后使用时间）
            pass
        # ...

# 2. 更好的方案：使用Redis分布式锁（跨进程安全）
# 已在celery_lock.py中实现，应该统一使用
```

### 🔴 P0-3: 幂等性检查逻辑过于复杂且存在竞态条件

**文件**: `views/upload/merge.py` 第172-315行

**问题描述**:
`TransferChecker.check_idempotency`方法存在以下问题：

```python
# 问题代码（merge.py:236-240）
query = DocumentTransfer.objects.filter(
    file_hash=file_hash,
    status__in=[TransferStatus.MERGING.value, TransferStatus.COMPLETED.value],
    updated_at__gte=ten_minutes_ago  # 只查最近10分钟的记录
).order_by('-updated_at')
```

**具体问题**:
1. **时间窗口逻辑错误**: 10分钟限制过于武断，如果合并任务执行超过10分钟，前端查询会返回"未找到"
2. **count查询冗余**: 第243行先`query.count()`，后面又用`query.filter().first()`，实际上count的结果没有被充分利用
3. **日志过度**: 方法内有17处日志记录，过度日志影响性能
4. **查询次数过多**: 最多可能执行5次数据库查询，应该优化为1-2次
5. **租户过滤逻辑不完整**: 公共空间不过滤的逻辑正确，但实现方式不够清晰

**建议**: 简化逻辑，减少查询次数：
```python
@staticmethod
def check_idempotency(transfer_id, file_hash=None, is_public=None, user=None):
    from apps.document.models import DocumentTransfer
    
    # 1. 先查自己的记录（如果提供了transfer_id）
    if transfer_id:
        transfer = DocumentTransfer.objects.filter(
            id=transfer_id, user=user
        ).first()
        if transfer:
            if transfer.status == TransferStatus.COMPLETED.value:
                return {'status': 'completed', 'file_path': transfer.file_path}, None
            if transfer.status == TransferStatus.MERGING.value and transfer.celery_task_id:
                return {'status': 'merging', 'task_id': transfer.celery_task_id}, None
    
    # 2. 查其他用户的合并记录（通过file_hash）
    if file_hash and user:
        query = DocumentTransfer.objects.filter(
            file_hash=file_hash,
            status__in=[TransferStatus.MERGING.value, TransferStatus.COMPLETED.value]
        )
        if not is_public:
            query = query.filter(tenant_id=user.tenant_id)
        
        # 优先返回MERGING且有task_id的记录
        transfer = query.filter(
            status=TransferStatus.MERGING.value,
            celery_task_id__isnull=False
        ).first() or query.filter(
            status=TransferStatus.COMPLETED.value
        ).first()
        
        if transfer:
            status = 'merging' if transfer.status == TransferStatus.MERGING.value else 'completed'
            result = {'status': status}
            if transfer.celery_task_id:
                result['task_id'] = transfer.celery_task_id
            if transfer.file_path:
                result['file_path'] = transfer.file_path
            return result, None
    
    return None, None
```

## 七、结论

当前代码存在**3个P0级别**的严重问题，这些问题可能导致：
1. 断点续传功能不可靠
2. 内存泄漏（长期运行后）
3. 并发场景下的状态不一致

建议**暂停新功能开发**，优先修复上述问题，并进行代码重构以提高可维护性。
