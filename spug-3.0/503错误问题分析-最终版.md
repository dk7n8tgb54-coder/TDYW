## 二、问题根因分析（最终版）

### 2.1 503触发的完整链路

```
用户请求
    ↓
Nginx (连接池64)
    ↓
Gunicorn Worker (默认2-4个)
    ├── Worker耗尽 → 503 (最直接原因)
    └── Worker正常 → Django处理
            ↓
            调用Celery
            ├── Broker(Redis)无响应 → 请求阻塞 → HTTP超时
            └── Broker正常 → 任务入队
                    ↓
                    Celery Worker处理
                    ├── Worker并发不足 → 队列积压
                    └── 数据库连接池耗尽 → 任务失败
```

### 2.2 瓶颈优先级（最终版）

| 优先级 | 瓶颈 | 触发条件 | 503来源 |
|--------|------|----------|---------|
| 🔴 P0 | **Gunicorn Worker耗尽** | 并发请求 > worker数 | **直接来源** |
| 🔴 P0 | **Celery队列积压** | 批量任务过多 | 间接（HTTP超时） |
| 🔴 P0 | **数据库连接打满** | 并发连接 > max_connections | 直接+间接 |
| 🟠 P1 | **Nginx连接耗尽** | 大量长连接 | 直接来源 |
| 🟡 P2 | **Redis连接问题** | Broker不可达 | 请求阻塞 |

### 方案1: Gunicorn配置优化（异步Worker方案）

#### 配置A: 同步Worker（兼容性好，适合中小并发）

```bash

    -b 0.0.0.0:8000 \
    --workers=4 \
    --worker-class=sync \
    --max-requests=5000 \
    --max-requests-jitter=100 \
    --timeout=60 \
    --keep-alive=2 \
    --graceful-timeout=30
```

**适用场景**: 并发请求 < 50，服务器资源有限

#### 配置B: Gevent异步Worker（高并发推荐）

```bash
# 先安装依赖
pip install gevent

# /etc/supervisor/conf.d/spug.conf
[program:spug]
command=/path/to/venv/bin/gunicorn spug.wsgi:application \
    -b 0.0.0.0:8000 \
    --workers=4 \
    --worker-class=gevent \           # 异步Worker，单Worker可处理多个请求
    --worker-connections=1000 \       # 单Worker最大连接数
    --max-requests=5000 \
    --max-requests-jitter=100 \
    --timeout=60 \
    --keep-alive=2 \
    --graceful-timeout=30
```

**适用场景**: 并发请求 50-500，IO密集型业务

**Worker数计算公式**:
```
同步Worker: workers = 2 * CPU核心数 + 1
异步Worker: workers = CPU核心数 * 2  (worker-connections决定并发能力)

示例:
- 2核CPU: workers=4(同步) 或 workers=4 + worker-connections=1000(异步)
- 4核CPU: workers=6(同步) 或 workers=6 + worker-connections=1000(异步)
```

### 方案3: 后端批量任务优化（已修正事务问题）

```python
# apps/document/tasks/batch.py

@shared_task(
    bind=True,
    max_retries=3,
    default_retry_delay=30,
    queue='document.batch',
    time_limit=300,  # 硬超时5分钟
    soft_time_limit=240,  # 软超时4分钟
)
def batch_delete_transfers(self, transfer_ids, request_user_id, request_tenant_id):
    """
    异步批量删除传输记录 - 生产优化版（已修正事务问题）
    """
    from apps.document.models import DocumentTransfer
    from apps.document.constants import TransferStatus
    from django.db import transaction
    
    logger.info(f'[Celery] Batch delete start: count={len(transfer_ids)}')
    
    # 【优化1】批量查询，减少数据库往返
    transfers = list(DocumentTransfer.objects.filter(
        id__in=transfer_ids,
        tenant_id=request_tenant_id
    ).select_related())
    
    # 预分类
    deletable_states = {
        TransferStatus.COMPLETED.value,
        TransferStatus.FAILED.value,
        TransferStatus.CANCELED.value
    }
    
    deletable_transfers = []
    skipped_ids = []
    
    for transfer in transfers:
        if transfer.status in deletable_states:
            deletable_transfers.append(transfer)
        else:
            skipped_ids.append(transfer.id)
    
    # 【修正】文件清理在事务外，不占用数据库锁
    deleted_count = 0
    chunk_cleanup_results = []
    
    BATCH_SIZE = 10
    for i in range(0, len(deletable_transfers), BATCH_SIZE):
        batch = deletable_transfers[i:i+BATCH_SIZE]
        batch_ids = [t.id for t in batch]
        
        # 【修正】事务内只做数据库操作
        try:
            with transaction.atomic():
                DocumentTransfer.objects.filter(id__in=batch_ids).delete()
                deleted_count += len(batch)
        except Exception as e:
            logger.error(f'Batch delete error: {e}')
            # 降级：单条重试
            for transfer in batch:
                try:
                    with transaction.atomic():
                        transfer.delete()
                        deleted_count += 1
                except Exception as e2:
                    logger.error(f'Single delete failed: {transfer.id}, {e2}')
            continue
        
        # 【修正】事务外执行文件清理，不占用数据库锁
        for transfer in batch:
            if transfer.file_hash and transfer.total_chunks > 0:
                try:
                    _cleanup_transfer_chunks(transfer)
                    chunk_cleanup_results.append({'id': transfer.id, 'status': 'cleaned'})
                except Exception as e:
                    logger.warning(f'Chunk cleanup failed for {transfer.id}: {e}')
                    chunk_cleanup_results.append({'id': transfer.id, 'status': 'failed', 'error': str(e)})
    
    result = {
        'deleted': deleted_count,
        'skipped': len(skipped_ids),
        'total': len(transfer_ids),
        'chunk_cleaned': len([r for r in chunk_cleanup_results if r['status'] == 'cleaned']),
    }
    
    logger.info(f'[Celery] Batch delete completed: {result}')
    return result
```

**关键修正**:
1. **事务内**: 仅执行数据库操作（批量删除）
2. **事务外**: 执行文件清理（IO操作）
3. **避免**: 长时间占用数据库连接和行锁

```python
    try:

        active = inspector.active()

        if scheduled:
            for worker_tasks in scheduled.values():
                total_pending += len(worker_tasks)
        
        return {
            'status': 'ok',
            'pending_tasks': total_pending,
            'active_tasks': sum(len(t) for t in active.values()) if active else 0,

        }

                'status': 'ok',
                'usage_percent': round(usage, 2),
                'threads_connected': threads,
                'alert': usage > 80,  # 告警但不影响健康状态
            }
```

### 方案7: 前端指数退避重试

```javascript
// libs/http.js - 指数退避重试

import axios from 'axios';

const http = axios.create({
  baseURL: '/api/',
  timeout: 30000,
});

// 指数退避配置
const RETRY_CONFIG = {
  maxRetries: 3,
  initialDelay: 1000,      // 初始1秒
  maxDelay: 8000,          // 最大8秒
  retryStatusCodes: [503, 502, 504, 429],  // 429 Too Many Requests
  // 只重试幂等操作
  retryMethods: ['get', 'delete', 'head', 'options'],
  // 需要幂等性校验的POST操作
  idempotentPostUrls: [
    '/api/document/transfer/batch_delete/',
    '/api/document/transfer/batch_cancel/',
  ],
};

// 生成幂等键
function generateIdempotencyKey() {
  return `${Date.now()}-${Math.random().toString(36).substr(2, 9)}`;
}

http.interceptors.request.use(
  config => {
    // 为批量操作添加幂等键
    if (RETRY_CONFIG.idempotentPostUrls.some(url => config.url.includes(url))) {
      config.headers['X-Idempotency-Key'] = generateIdempotencyKey();
    }
    return config;
  }
);

http.interceptors.response.use(
  response => response.data,
  async error => {
    const { config, response } = error;
    
    if (!response) return Promise.reject(error);
    
    // 判断是否可重试
    const canRetry = (
      RETRY_CONFIG.retryStatusCodes.includes(response.status) &&
      (RETRY_CONFIG.retryMethods.includes(config.method) ||
       config.headers['X-Idempotency-Key'])  // 有幂等键的POST可重试
    );
    
    if (!canRetry) return Promise.reject(error);
    
    config.__retryCount = config.__retryCount || 0;
    
    if (config.__retryCount >= RETRY_CONFIG.maxRetries) {
      return Promise.reject(error);
    }
    
    config.__retryCount += 1;
    
    // 指数退避: delay = min(initialDelay * 2^retryCount, maxDelay)
    const delay = Math.min(
      RETRY_CONFIG.initialDelay * Math.pow(2, config.__retryCount - 1),
      RETRY_CONFIG.maxDelay
    );
    
    console.log(`[HTTP] ${response.status}错误，${delay}ms后第${config.__retryCount}次重试...`);
    
    await new Promise(resolve => setTimeout(resolve, delay));
    return http(config);
  }
);

export default http;
```

### 方案8: 批量操作用户级限流

```python
# apps/document/ratelimit.py

from functools import wraps
from django.core.cache import cache
from django.http import JsonResponse
import time

def rate_limit(key_func, rate='5/m', block=True):
    """
    用户级限流装饰器
    rate: '5/m' = 每分钟5次, '10/m' = 每分钟10次
    """
    def decorator(view_func):
        @wraps(view_func)
        def wrapper(request, *args, **kwargs):
            key = key_func(request)
            limit_key = f'ratelimit:{view_func.__name__}:{key}'
            
            # 解析rate
            count, period = rate.split('/')
            count = int(count)
            period_seconds = {'s': 1, 'm': 60, 'h': 3600, 'd': 86400}[period]
            
            # 获取当前计数
            now = time.time()
            window_start = now - period_seconds
            
            # 使用Redis有序集合存储请求时间戳
            pipe = cache.client.pipeline() if hasattr(cache, 'client') else None
            
            if block:
                current_count = cache.get(limit_key, 0)
                if current_count >= count:
                    return JsonResponse({
                        'error': 'Rate limit exceeded',
                        'retry_after': period_seconds,
                    }, status=429)
                cache.set(limit_key, current_count + 1, period_seconds)
            
            return view_func(request, *args, **kwargs)
        return wrapper
    return decorator
```

| 问题 | 原方案 | 修正方案 | 风险消除 |
