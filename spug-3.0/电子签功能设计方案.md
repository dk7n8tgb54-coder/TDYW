# 电子签功能设计方案

> 状态：待评审  
> 创建：2026-07-13  
> 作者：根据用户需求设计

## 一、需求与定位

### 1.1 业务诉求
- 第一期：部门日检查单（`CheckSheetDailySummary`）每日值班人员签字
- 第二期：科室值班日志（`DutyRecord`）签字
- 后续可能复用到其他业务场景

### 1.2 关键约束（已和用户确认）
| 约束 | 选择 | 说明 |
|---|---|---|
| 签字图来源 | **上传透明底 PNG 照片** | 用户手写签名后扫描/拍照去背景上传到个人中心，不做前端画板 |
| 法律效力 | **内部管理留痕级** | 内网不连公网，无法对接外部 CA（e签宝/契约锁）做实名认证与证书签发 |
| 部署环境 | **纯内网** | 禁止调用任何公网服务 |

### 1.3 法律效力说明（重要，须向用户讲清）

根据《电子签名法》第十三条，**可靠电子签名**须同时满足四要件：
1. 签名数据属签名人专有
2. 签署时仅签名人控制
3. 签署后对签名改动可被发现
4. 对数据电文改动可被发现

**纯内网 + 上传签字图** 无法满足第①②条（不能证明"这张图只属于这个人、且只被这个人控制"），因此**不构成法律意义上的可靠电子签名**。

但本方案能做到：
- **视觉留痕**：签字图渲染到检查单/PDF 上，相当于纸质签字的扫描件
- **行为留痕**：每次签字触发 `EvidenceEvent`（哈希链 + 操作人 ID + IP + 时间戳 + 业务快照）
- **不可抵赖性（内部级）**：签字图 hash 绑定到 `EvidenceEvent.object_snapshot`，事后若签字图被替换可被发现
- **可追溯性**：审计日志 + 证据包导出

**适用范围**：内部管理、复核追责、纪律检查。**不适用**：对外签署、司法诉讼主证据。

> 该定位与现有 `EvidenceEvent` 设计哲学一致——`external_ts_provider`/`external_ts_token` 字段注释明确"内网环境不实际接入"，本方案正好填满非 CA 路径的能力。

## 二、总体架构

### 2.1 设计原则
1. **复用 evidence 公共底座**——签字图本身是一张普通附件，落 `EvidenceAttachment` 表，`module='signature'`、`object_type='user_signature'`、`object_id=<user_id>`
2. **签名行为通过 EvidenceEvent 留痕**——每次签字动作写一条 `submit` 事件，快照含业务数据 hash + 签字图 attachment_id + 签字图 sha256
3. **签字图与业务数据绑定**——保存检查单时把签字图 hash 写入 `snapshot_hash` 计算输入，事后篡改任一方都可发现
4. **业务表只存引用**——`CheckSheetDailySummary` 新增 `signature_attachment_id` 字段指向签字图，不存图片本身
5. **向后兼容**——老数据无签字图也能正常显示文本姓名

## 三、数据模型设计

### 3.1 不新增独立签字模型

**理由**：签字图就是一张普通附件，行为留痕通过 `EvidenceEvent` 完成，没必要新建 `SignatureModel`。

签字图存储复用 `EvidenceAttachment`：
- `module='signature'`
- `object_type='user_signature'`  
- `object_id=<user_id>`（每个用户最多保留 1 张当前签字图，通过 `is_deleted` 软删历史）

## 四、后端接口设计

### 4.1 签字图管理（个人中心）

新增 `apps/signature/views.py`：

| 接口 | 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|---|
| 上传/替换签字图 | POST | `/api/signature/upload/` | 登录即可 | 上传 PNG，自动软删旧签字图 |
| 查询当前签字图 | GET | `/api/signature/current/` | 登录即可 | 返回当前生效签字图 + 预览 URL |
| 查询签字图历史 | GET | `/api/signature/history/` | 登录即可 | 列出所有上传过的签字图（含已删） |
| 删除签字图 | DELETE | `/api/signature/<id>/` | 登录即可 | 软删，需校验归属 |
| 内联预览签字图 | GET | `/api/signature/<id>/preview/` | preview_token 鉴权 | kkFileView 同款机制，浏览器内联展示 |

**上传校验**（`SignatureConfig`）：
```python
class SignatureConfig(AttachmentConfig):
    allowed_extensions = ('.png',)  # 仅 PNG，因透明背景需求
    max_size_mb = 2  # 签字图通常 < 100KB，2MB 足够
```

**上传流程**：
1. `AttachmentService.validate(file, SignatureConfig)` 校验扩展名和大小
2. 若用户已有当前签字图（`is_deleted=False`），先 `AttachmentService.soft_delete(...)` 软删
3. `AttachmentService.upload(file, user, module='signature', object_type='user_signature', object_id=str(user.id))`
4. 写 `EvidenceEvent`（`module='signature'`, `object_type='user_signature'`, `object_id=<user_id>`, `event_type='submit'`, `object_snapshot` 含 sha256）

### 4.2 检查单保存扩展（第一期）

**现有 `RecordListView.post` 已接收 `signatures` 参数**（`checksheet/views.py:160`），目前只用 `signatures.get('operator', '')`。

扩展 `signatures` 字段：
```python
signatures = {
    'operator': '张三',                     # 既有：文本姓名
    'signature_attachment_id': 123,         # 新增：签字图 attachment_id
    'signature_sha256': 'abc123...',        # 新增：签字图 hash（前端从 current 接口拿到）
}
```

后端保存逻辑：
```python
# apps/checksheet/views.py - RecordListView.post 扩展
sig_att_id = signatures.get('signature_attachment_id')
if sig_att_id:
    # 校验签字图确实属于当前用户
    att = EvidenceAttachment.objects.filter(
        pk=sig_att_id, module='signature',
        object_type='user_signature',
        object_id=str(request.user.id),
        is_deleted=False,
    ).first()
    if not att:
        return json_response(error='签字图无效或已过期，请重新上传')
    sig_att_id = att.id
    sig_sha256 = att.file_hash_sha256
else:
    sig_att_id = None
    sig_sha256 = ''

CheckSheetDailySummary.objects.update_or_create(
    year=year, month=month, day=int(day),
    defaults={
        'operator': signatures.get('operator', ''),
        'operator_user_id': operator_user_id,
        'operator_name_snapshot': operator_name,
        'signature_attachment_id': sig_att_id,
        'signature_signed_at': human_datetime() if sig_att_id else None,
        # ...其他既有字段
    }
)
```

### 4.3 签字行为证据事件

每次带签字图的保存，额外写一条 `EvidenceEvent`：

```python
record_evidence_event(
    tenant_id=tenant_id,
    module='checksheet',
    object_type='daily_signature',
    object_id=f'{submission.id}_{year}_{month}_{day}',
    event_type='submit',
    actor_user_id=operator_user_id,
    actor_username=user.username,
    actor_name=operator_name,
    actor_ip=get_request_real_ip(request),
    object_snapshot={
        'submission_id': submission.id,
        'project': project,
        'year': year, 'month': month, 'day': day,
        'operator_name_snapshot': operator_name,
        'signature_attachment_id': sig_att_id,
        'signature_file_name': att.file_name if sig_att_id else '',
        'signature_sha256': sig_sha256,
        'daily_summary_hash': '<当日所有记录的 hash>',
    },
    attachment_hashes=[{
        'attachment_id': sig_att_id,
        'sha256': sig_sha256,
        'file_name': att.file_name if sig_att_id else '',
    }] if sig_att_id else [],
    event_title=f'{project} {year}-{month}-{day} 签字',
)
```

**防篡改链路**：
- `object_snapshot.signature_sha256` 固化了"签字当时用的图"
- `object_snapshot.daily_summary_hash` 固化了"签字当时的业务数据"
- 事后若签字图被替换 → 新 sha256 ≠ 事件记录的 sha256 → 可发现
- 事后若业务数据被改 → 重新计算 hash ≠ 事件记录的 hash → 可发现

### 4.4 检查单查询返回签字图

`RecordListView.get` 返回的 `daily_summaries` 增加：
```python
daily_summaries[summary.day] = {
    'operator': summary.operator or '',
    'remark': summary.remark or '',
    'rectification': summary.rectification or '',

```

## 九、风险与权衡

### 9.1 已知风险
1. **签字图可被截图盗用**——内网环境，风险可控，但理论存在
2. **无法证明签字图归属**——没有 CA 实名认证，靠 `object_id=<user_id>` 后端强校验
3. **PDF 中签字图是图片**——可被 PS 替换，但 `EvidenceEvent.object_snapshot.signature_sha256` 提供比对依据

### 9.2 缓解措施
1. 上传签字图时写 `EvidenceEvent`（提交事件 + sha256），事后比对
2. 检查单保存时校验签字图归属当前用户（`object_id=user.id`）
3. PDF 导出审计日志记录导出人/时间
4. 证据包导出（`EvidencePackageView` 已存在）可一并打包签字图 sha256

### 9.3 不做的事
- ❌ 不做前端手写画板（YAGNI，用户已选上传方案）
- ❌ 不做 CA 对接（内网不可能）
- ❌ 不做签字图自动去背景（让用户自己处理，PS/在线工具均可）
- ❌ 不做签字图版本管理（仅保留当前 + 软删历史，足够）

## 十三、未来扩展：指纹验证（预研，不实施）

### 13.1 设计思路
保持签字图方案不变，未来加一层"签字前指纹验证"：
- 个人中心新增"指纹注册" Tab，调 WebAuthn API
- 检查单签字弹窗增加"指纹验证"按钮，验证通过才能完成签字
- EvidenceEvent.object_snapshot 增加 `webauthn_credential_id`（预留空字段）

### 13.2 技术选型：WebAuthn（推荐）
- 浏览器原生 API（`navigator.credentials.create` / `navigator.credentials.get`）
- Windows Hello 自带指纹模块支持，零驱动零中间件
- 内网可用（不需要联网，本地加密运算）
- HTTPS 部署即可（项目已支持）
- 拿不到指纹图像，但能拿到验签结果，对签字场景足够

### 13.3 兼容路径
- 本期签字图方案完全不动
- 未来增加 WebAuthn 时，EvidenceEvent 模型不改（用 object_snapshot 扩展字段）
- 没有指纹模块的设备可降级为 Windows PIN 签字（弱于指纹但强于纯签字图）

### 13.4 不采用 USB 指纹仪 + 厂商 SDK 方案的原因
- 每台电脑装驱动+中间件服务，运维负担重
- 跨厂家 SDK 不兼容，维护成本高
- WebAuthn 已能覆盖所有 Windows Hello 支持的指纹硬件，零适配工作

### 13.5 法律效力提升说明
纯签字图无法满足《电子签名法》第十三条第②条"签署时仅签名人控制"。
增加 WebAuthn 后，私钥由设备 TPM 安全区保管、签字时需生物验证，可视为满足第②条（但仍非 CA 颁发的可靠电子签名，仅作为内部管理增强）。
