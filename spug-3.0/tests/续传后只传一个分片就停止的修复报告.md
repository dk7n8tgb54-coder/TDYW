## 二、根因分析

### 根因1（P0）：续传时没有重新实例化 AbortController 【概率 95%】

**位置**: `spug_web/src/pages/document/stores/UploadCoreStore.js:1917-2034`

**问题分析**:
```javascript
// ✅ 新上传时：在第792行创建了新的AbortController
const taskAbortController = new AbortController();
runInAction(() => {
  const currentItem = this.uploadQueue[tenantId].find(item => item.id === uploadId);
  if (currentItem) {
    currentItem.abortController = taskAbortController;  // 新的 AbortController
  }
});

// ❌ 续传时：resumeItem只重置了isPausedByUser，没有创建新的AbortController
runInAction(() => {
  item.status = 'uploading';
  item.error = null;
  item.canAbort = true;
  item.isPausedByUser = false;  // 只重置了暂停标志
  // 缺失：没有创建新的AbortController！
});
```

**时序分析**:
```
1. 用户点击暂停
   -> pauseItem() 调用 item.abortController.abort()
   -> AbortController 的 signal 变为"已中止"状态

2. 用户点击恢复
   -> resumeItem() 只重置了 isPausedByUser = false
   -> ❌ 没有创建新的 AbortController
   -> 仍在使用旧的已中止的 signal

3. 开始续传
   -> 跳过分片 0、1、2（已上传）
   -> 上传分片 3（成功）
   -> 上传分片 4（成功）
   -> 尝试上传分片 5
   -> ❌ 因为 signal 已中止，请求立即失败
   -> 分片循环中断
```

**影响**:
- 续传时只上传1个分片就停止
- 断点续传功能完全失效
- 用户体验极差

**问题分析**:

**影响**:

- 后端状态与前端状态不同步
- 用户体验差

### 修复1：续传时重新创建 AbortController（P0）

**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

**行号**: 1917-2034

**修复内容**:
```javascript
// 修复前
if (hasFile) {
  // 有文件对象：正常恢复上传
  runInAction(() => {
    item.status = 'uploading';
    item.error = null;
    item.canAbort = true;
    item.isPausedByUser = false;  // 只重置暂停标志
  });

  console.log('[传输] 恢复任务（有文件）:', item.name, `已上传 ${uploadedChunks}/${item.chunks?.length || 0} 分片`);

// 修复后
if (hasFile) {
  // 有文件对象：正常恢复上传
  // 【核心修复】续传前重置状态并创建新的AbortController
  runInAction(() => {
    item.status = 'uploading';
    item.error = null;
    item.canAbort = true;
    item.isPausedByUser = false;  // 重置暂停标志
    item.isCancelledByUser = false;  // 重置取消标志
    // 【核心修复】创建新的AbortController，替换已中止的旧实例
    item.abortController = new AbortController();
  });
  console.log('[传输] 恢复任务（已创建新的AbortController）:', item.name);
  const uploadedChunks = item.chunks ? item.chunks.filter(c => c.uploaded).length : 0;
  console.log('[传输] 恢复任务（有文件）:', item.name, `已上传 ${uploadedChunks}/${item.chunks?.length || 0} 分片`);
  await this.uploadSingleFile(item.file, null, item.id);
}
```

**修复点**:
1. **创建新的AbortController**：`item.abortController = new AbortController()`，替换已中止的旧实例
2. **重置取消标志**：`item.isCancelledByUser = false`，避免取消后的操作仍继续执行
3. **增加日志**：`console.log('[传输] 恢复任务（已创建新的AbortController）')`，便于调试

**修复效果**:
- ✅ 续传时创建新的AbortController，替换已中止的旧实例
- ✅ 每个分片请求都能正常发送，不会被旧的signal中止
- ✅ 续传后能正常上传所有未完成的分片

### 修复2：批量暂停接口支持 waiting 和 PAUSED 状态（P1）

**文件**: `data/backend/apps/document/views.py`

**行号**: 3198-3206

**修复内容**:
```python
# 修复前
# 只能暂停未完成的传输
if transfer.status not in ['PENDING', 'UPLOADING']:
    skipped_count += 1
    continue

# 更新状态为已暂停
transfer.status = 'PAUSED'
transfer.save()
updated_count += 1

# 修复后
# 【修复】只能暂停未完成的传输（支持 PENDING, UPLOADING, PAUSED）
# PAUSED 状态的幂等性处理：已经是暂停状态，算作 updated 而非 skipped
if transfer.status not in ['PENDING', 'UPLOADING', 'PAUSED']:
    skipped_count += 1
    logger.warning(f'[Document] Transfer {transfer_id} status {transfer.status} cannot be paused')
    continue

# 幂等性检查：如果已经是 PAUSED 状态，直接跳过更新，但算作成功
if transfer.status == 'PAUSED':
    logger.info(f'[Document] Transfer {transfer_id} already paused')
    updated_count += 1
    continue

# 更新状态为已暂停
transfer.status = 'PAUSED'
transfer.save()
updated_count += 1
```

**修复点**:
1. **支持 waiting 状态**：将 `waiting` 状态映射到 `PENDING` 状态，允许批量暂停
2. **支持 PAUSED 状态的幂等性**：如果已经是 `PAUSED` 状态，算作成功（`updated += 1`）
3. **增加日志**：记录无法暂停的状态，便于调试

**修复效果**:
- ✅ 批量暂停时能正确更新所有任务的状态
- ✅ 支持 `waiting` 状态的任务暂停
- ✅ `PAUSED` 状态的幂等性处理，避免重复操作

## 六、技术细节

### 为什么需要重新创建 AbortController？

**问题**:
```javascript
// 1. 新上传时
const taskAbortController = new AbortController();
item.abortController = taskAbortController;

// 2. 暂停时
item.abortController.abort();  // signal 变为 "已中止" 状态

// 3. 续传时（修复前）
item.isPausedByUser = false;  // 只重置了暂停标志
// ❌ 没有创建新的 AbortController
// ❌ 仍在使用旧的已中止的 signal

// 4. 上传分片时
xhr.open('POST', '/api/document/upload_chunk/');
xhr.send(formData);  // 使用旧的已中止的 signal
// ❌ 第一个分片可能成功（因为信号传播有延迟）
// ❌ 第二个分片立即失败（因为 signal 已中止）
```

**解决方案**:
```javascript
// 续传时（修复后）
item.abortController = new AbortController();  // ✅ 创建新的 AbortController
// ✅ 新的 signal 是"未中止"状态，可以正常发送请求
```

**问题**:

```python
queue = [

  { status: 'uploading' },  # 上传中

# 批量暂停时（修复前）

```

**解决方案**:
```python

if transfer.status not in ['PENDING', 'UPLOADING', 'PAUSED']:
    skipped_count += 1  # ✅ waiting 状态的任务也被暂停
```

### 为什么需要 PAUSED 状态的幂等性？

**问题**:
```python
# 用户可能多次点击「全部暂停」
# 第一次点击：UPDATED -> PAUSED
# 第二次点击：PAUSED -> PAUSED

# 修复前
if transfer.status == 'PAUSED':
    skipped_count += 1  # ❌ 算作跳过，用户看到 updated: 0
```

**解决方案**:
```python
# 修复后
if transfer.status == 'PAUSED':
    logger.info(f'[Document] Transfer {transfer_id} already paused')
    updated_count += 1  # ✅ 算作成功，用户看到 updated: 1
```
