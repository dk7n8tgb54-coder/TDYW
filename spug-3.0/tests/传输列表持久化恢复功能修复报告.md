# 传输列表持久化恢复功能修复报告

**修复时间**: 2026-03-01
**修复人员**: AI Assistant
**问题等级**: P0（核心功能）

---

## 一、问题描述

### 核心现象
- 页面刷新后，传输列表完全清空
- 未完成的上传/下载记录消失
- 已创建 `DocumentTransfer` 表并持久化传输记录，但未生效

### 影响范围
- 所有用户（管理员/普通用户）
- 所有空间（公共空间/私有空间）
- 所有传输类型（上传/下载）

---

## 二、根因分析

### 根因 1（P0）：前端 API 调用方式错误 【概率 90%】

**位置**: `spug_web/src/pages/document/stores/UploadCoreStore.js:1798-1977`

**问题**:
- 使用原生 `fetch` 而非项目的 `http` 库
- 响应数据解析错误：`data.data` vs 直接 `data`
- 请求头处理可能不一致（X-Token 认证）

**影响**:
- API 调用可能失败或返回空数据
- 导致 `fetchTransfers` 无法正确获取后端记录

---

### 根因 2（P0）：恢复逻辑缺失关键字段同步 【概率 80%】

**位置**: `spug_web/src/pages/document/Explorer.js:146-222`

**问题**:
- 恢复的记录缺少 `fileHash` 字段，导致断点续传失效
- 恢复的记录 `file: null`，导致无法继续上传
- 未使用 `runInAction` 包裹状态更新，MobX 响应式失效

**影响**:
- 恢复后的记录无法继续上传
- 用户需重新选择文件，体验差

---

### 根因 3（P1）：后端 API 返回数据不完整 【概率 60%】

**位置**: `data/backend/apps/document/views.py:2637-2656`

**问题**:
- 返回数据缺少 `file_hash` 字段
- 前端无法获取文件哈希，断点续传失效

**影响**:
- 断点续传功能无法正常工作

---

### 根因 4（P1）：租户 ID 映射不一致 【概率 40%】

**位置**: `spug_web/src/pages/document/Explorer.js:172`

**问题**:
- `restoreTransfers` 未使用 `this.isPublic` 判断公共空间/私有空间
- 可能导致公共空间记录恢复到私有空间队列

**影响**:
- 租户隔离失效，数据泄露风险

---

## 三、修复方案

### 修复 1：统一 API 调用方式（使用 http 库）

**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

**修改内容**:
```javascript
// 修复前：使用原生 fetch
async fetchTransfers() {
  const response = await fetch('/api/document/transfers/', { ... });
  const data = await response.json();
  if (data.data) {
    return data.data;  // 错误：多了一层 .data
  }
  return [];
}

// 修复后：使用 http 库
async fetchTransfers() {
  try {
    const { http } = await import('libs');
    const data = await http.get('/api/document/transfers/');
    if (data && Array.isArray(data)) {
      console.log('[传输] 从后端恢复传输列表:', data.length, '条记录');
      return data;
    }
    return [];
  } catch (error) {
    console.error('[传输] 获取传输列表失败:', error);
    return [];
  }
}
```

**影响方法**:
- `fetchTransfers()` - 获取传输列表
- `createTransfer()` - 创建传输记录
- `updateTransferProgress()` - 更新进度
- `completeTransfer()` - 完成传输
- `cancelTransfer()` - 取消传输
- `deleteTransfer()` - 删除记录

**修改文件**: `UploadCoreStore.js`，行号 1798-1977，共修改 6 个方法

### 修复 2：完善恢复逻辑，同步 fileHash 字段

**文件**: `spug_web/src/pages/document/Explorer.js`

**修改内容**:
```javascript
// 修复前
uploadCoreStore.uploadQueue[tenantId].push({
  id: Date.now() + Math.random(),
  name: transfer.file_name,
  status: frontendStatus,
  percent: transfer.progress || 0,
  error: transfer.error_message || null,
  canAbort: false,
  fileSize: transfer.file_size,
  chunks: [],
  currentChunk: transfer.uploaded_chunks || 0,
  chunkCount: transfer.total_chunks || 0,
  tenantId: tenantId,
  transferId: transfer.id,
  file: null,  // ❌ 无法继续上传
});

// 修复后
runInAction(() => {  // ✓ 使用 runInAction 确保响应式
  uploadCoreStore.uploadQueue[tenantId].push({
    id: Date.now() + Math.random(),
    name: transfer.file_name,
    status: frontendStatus,
    percent: transfer.progress || 0,
    error: transfer.error_message || (frontendStatus === 'paused' ? '已暂停' : null),
    canAbort: false,
    fileSize: transfer.file_size,
    chunks: [],
    currentChunk: transfer.uploaded_chunks || 0,
    chunkCount: transfer.total_chunks || 0,
    tenantId: tenantId,
    transferId: transfer.id,
    fileHash: transfer.file_hash || null,  // ✓ 恢复文件哈希
    file: null,  // 文件对象无法恢复，用户需重新选择
  });
});
```

**新增内容**:
- 使用 `runInAction` 包裹状态更新
- 恢复 `fileHash` 字段（用于断点续传）
- 优化租户过滤逻辑（使用 `this.isPublic` 判断）

**修改文件**: `Explorer.js`，行号 146-222，共修改约 80 行

## 七、注意事项

### 1. 文件对象无法恢复
- 后端无法持久化 `File` 对象（浏览器安全限制）
- 用户需重新选择文件或手动继续上传
- 已有方案：点击"继续"按钮时，提示用户重新选择文件

### 2. 断点续传依赖 fileHash
- 恢复的记录必须包含 `fileHash`
- 后端 API 已返回 `file_hash` 字段
- 前端续传时使用该哈希查询已上传分片

### 3. 分片信息需重新查询
- 恢复时 `chunks` 数组为空
- 续传时调用 `/api/document/check_uploaded_chunks/` 查询
- 根据返回的 `uploaded_chunks` 重新初始化分片状态

### 4. 降级处理
- API 调用失败时，不影响页面其他功能
- 显示友好提示：`传输记录恢复失败，可手动重新上传`
- 记录日志便于排查问题
