## 测试工具介绍

本测试工具基于《多文件并发上传实现说明.md》文档开发，用于自动化验证多文件并发上传功能的各项特性。

### 包含的文件

| 文件 | 说明 |
|------|------|
| `test_multi_file_upload.js` | 核心测试脚本（可在浏览器或 Node.js 环境运行） |
| `test_multi_file_upload.html` | 测试工具的 HTML 界面（浏览器可视化测试） |
| `多文件上传测试指南.md` | 本文档（使用说明） |

### 测试覆盖范围

✅ **并发控制验证** - 验证最多 3 个文件同时上传
✅ **状态独立性验证** - 验证每个文件的进度和状态独立
✅ **暂停/继续验证** - 验证暂停和继续功能
✅ **进度节流验证** - 验证进度更新频率（预期 ≤ 5 次/秒）
✅ **资源清理验证** - 验证取消时清理 Worker 和网络请求

## 快速开始

### 方式一：使用 HTML 界面（推荐）

1. 在浏览器中打开 `tests/test_multi_file_upload.html`
2. 配置测试参数：
   - 文件数量：默认 5 个
   - 文件大小：默认 5MB
   - 预期并发数：默认 3
   - 超时时间：默认 30 秒
3. 点击"运行测试"按钮
4. 查看测试日志和结果

**注意：** 必须在 Spug 文档管理页面内打开此 HTML 文件，否则会找不到 `documentStore`。

### 方式二：在 Spug 页面控制台运行

1. 打开 Spug 文档管理页面
2. 按 F12 打开开发者工具，切换到 Console 标签
3. 复制 `test_multi_file_upload.js` 的内容到控制台
4. 运行以下代码：

```javascript
// 使用默认配置
const tester = new UploadTester();
await tester.runAll();
```

或自定义配置：

```javascript
// 自定义测试配置
TEST_CONFIG.fileCount = 10;
TEST_CONFIG.fileSize = 2;
const tester = new UploadTester();
await tester.runAll();
```

### 方式三：在 Node.js 环境运行（需要 Puppeteer）

```bash
cd tests
node test_multi_file_upload_node.js
```

## 测试项目说明

### 测试1：并发控制验证

**目的：** 验证最多 3 个文件同时上传

**测试步骤：**
1. 生成多个测试文件
2. 触发文件上传
3. 等待所有文件进入队列
4. 检查活跃上传数是否 ≤ 3
5. 检查等待队列是否存在

**预期结果：**
- ✅ 活跃上传数 ≤ 3
- ✅ 超过 3 个文件时，其余文件进入等待队列

**关键检查点：**
```javascript
// 检查活跃上传数
const activeUploads = documentStore.activeUploads;
assert(activeUploads <= 3, '活跃上传数不应超过 3');

// 检查等待队列
const waitingCount = queue.filter(item => item.status === 'waiting').length;
assert(waitingCount > 0, '应有文件在等待队列');
```

---

### 测试2：状态独立性验证

**目的：** 验证每个文件的进度和状态独立

**测试步骤：**
1. 等待上传开始
2. 检查每个文件的状态
3. 检查每个文件的进度

**预期结果：**
- ✅ 存在不同的状态（waiting, uploading, calculating 等）
- ✅ 每个文件的进度独立更新，互不干扰

**关键检查点：**
```javascript
// 检查状态多样性
const statuses = queue.map(item => item.status);
const uniqueStatuses = [...new Set(statuses)];
assert(uniqueStatuses.length > 1, '应有多种状态');

// 检查进度独立性
const percents = queue.map(item => item.percent);
const uniquePercents = [...new Set(percents)];
assert(uniquePercents.length > 1, '应有不同的进度值');
```

---

### 测试3：暂停/继续验证

**目的：** 验证暂停和继续功能

**测试步骤：**
1. 开始文件上传
2. 点击暂停所有
3. 检查文件状态是否变为 paused
4. 点击继续所有
5. 检查文件是否恢复上传

**预期结果：**
- ✅ 暂停后，所有正在上传的文件状态变为 paused
- ✅ 继续后，文件恢复上传状态

**关键检查点：**
```javascript
// 暂停测试
documentStore.pauseAll();
await sleep(1000);
const pausedCount = queue.filter(item => item.status === 'paused').length;
assert(pausedCount > 0, '应有文件进入暂停状态');

// 继续测试
documentStore.resumeAll();
await sleep(1000);
const uploadingCount = queue.filter(item => item.status === 'uploading').length;
assert(uploadingCount > 0, '应有文件恢复上传');
```

---

### 测试4：进度节流验证

**目的：** 验证进度更新频率（预期 ≤ 5 次/秒）

**测试步骤：**
1. 开始单个文件上传
2. 监控 2 秒内的进度更新次数
3. 计算每秒更新次数

**预期结果：**
- ✅ 每秒进度更新次数 ≤ 5 次（200ms 节流）

**关键检查点：**
```javascript
// 监控进度更新
let updateCount = 0;
const startTime = Date.now();

const checkInterval = setInterval(() => {
  if (item.percent !== originalPercent) {
    updateCount++;
  }
}, 100);

await sleep(2000);
clearInterval(checkInterval);

const updatesPerSecond = Math.round(updateCount / 2);
assert(updatesPerSecond <= 5, '每秒更新次数不应超过 5 次');
```

---

### 测试5：资源清理验证

**目的：** 验证取消时清理 Worker 和网络请求

**测试步骤：**
1. 开始文件上传
2. 点击取消所有
3. 检查活跃上传数是否归零
4. 检查 abortToken 是否被清理

**预期结果：**
- ✅ 取消后，活跃上传数归零
- ✅ 所有文件的 abortToken 被清理

**关键检查点：**
```javascript
// 取消上传
documentStore.cancelAll();
await sleep(500);

// 检查活跃上传数
const activeUploads = documentStore.activeUploads;
assert(activeUploads === 0, '活跃上传数应归零');

// 检查 abortToken 清理
const hasAbortToken = queue.some(item => item.abortToken !== null);
assert(!hasAbortToken, '所有 abortToken 应被清理');
```

## 测试脚本 API

### UploadTester 类

#### 方法

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `runAll()` | 运行所有测试 | Promise<TestResult[]> |

#### 示例

```javascript
// 创建测试实例
const tester = new UploadTester();
```

2. 网络连接不稳定
3. 服务器响应缓慢
4. 超时配置太短

**解决方案：**


   ```javascript
   TEST_CONFIG.fileSize = 2; // 减小到 2MB
   ```
3. 减少测试文件数量：
   ```javascript
   TEST_CONFIG.fileCount = 3; // 减少到 3 个文件
   ```
4. 添加超时重试机制：
   ```javascript
   async function retry(fn, maxRetries = 3, delay = 1000) {
     for (let i = 0; i < maxRetries; i++) {
       try {
         return await fn();
       } catch (error) {
         if (i === maxRetries - 1) throw error;
         await sleep(delay);
       }
     }
   }
   ```

**经验教训：**
- 测试配置应该可调整
- 提供合理的默认值

### 问题4：进度节流测试不准确

**问题描述：**
进度节流测试时，每秒更新次数超过预期（> 5 次），或者由于文件太小而无法准确测试。

**原因分析：**
1. 测试文件太小，上传速度太快，无法观察节流效果
2. 网络速度过慢，导致进度更新间隔大于节流阈值
3. 监控方式不正确，统计了所有状态变化而不仅仅是进度变化

**解决方案：**
1. 使用足够大的测试文件（至少 5MB）：
   ```javascript
   TEST_CONFIG.fileSize = 5; // 5MB
   ```
2. 延长监控时间：
   ```javascript
   const duration = 5000; // 监控 5 秒
   ```
3. 只统计实际的进度变化：
   ```javascript
   let lastPercent = item.percent;
   let updateCount = 0;

   const checkInterval = setInterval(() => {
     if (item.percent !== lastPercent) {
       updateCount++;
       lastPercent = item.percent;
     }
   }, 100);
   ```
4. 使用节流后的实际更新频率，而不是理论值：
   ```javascript
   const expectedMaxUpdates = Math.ceil(duration / 200); // 200ms 节流
   if (updateCount <= expectedMaxUpdates) {
     // 测试通过
   }
   ```

**经验教训：**
- 测试条件要符合实际情况
- 避免测试文件过小或过大
- 准确统计指标
- 考虑节流的实际实现

### 问题6：并发控制测试不稳定

**问题描述：**
并发控制测试时，有时活跃上传数超过预期，或者等待队列的文件数量不符合预期。

**原因分析：**
1. 检查时机不对，部分文件还在状态转换中
2. 竞态条件：文件完成上传的同时，新文件开始上传
3. 测试文件数量太少，无法触发并发限制

**解决方案：**
1. 增加稳定时间，等待状态稳定：
   ```javascript
   await sleep(2000); // 等待 2 秒让状态稳定
   ```
2. 增加测试文件数量，确保触发并发限制：
   ```javascript
   TEST_CONFIG.fileCount = 10; // 使用 10 个文件
   ```
3. 多次检查取平均值：
   ```javascript
   const measurements = [];
   for (let i = 0; i < 5; i++) {
     const activeUploads = documentStore.activeUploads;
     measurements.push(activeUploads);
     await sleep(500);
   }
   const avgActiveUploads = measurements.reduce((a, b) => a + b) / measurements.length;
   assert(avgActiveUploads <= 3, '平均活跃上传数不应超过 3');
   ```
4. 检查最大值而不是瞬时值：
   ```javascript
   let maxActiveUploads = 0;
   for (let i = 0; i < 10; i++) {
     maxActiveUploads = Math.max(maxActiveUploads, documentStore.activeUploads);
     await sleep(500);
   }
   assert(maxActiveUploads <= 3, '最大活跃上传数不应超过 3');
   ```

**经验教训：**
- 测试要考虑时序问题
- 等待状态稳定后再检查
- 使用多次采样提高可靠性
- 区分瞬时值和平均值
