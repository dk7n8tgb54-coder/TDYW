# 系统升级管理代码修复建议

## 检查范围

- 后端模型与迁移：`spug_api/apps/upgrade/models.py`、`models_checklist.py`、`models_template.py`、`migrations/0001_initial.py`
- 后端服务与接口：`spug_api/apps/upgrade/services/*`、`views/*`、`urls.py`、`exporters.py`
- 前端页面：`spug_web/src/pages/upgrade/*`
- 权限菜单与路由：`spug_web/src/pages/system/role/codes.js`、`spug_web/src/routes.js`
- 相关测试：`spug_api/tests/test_upgrade_unique_constraint.py`

## 总体结论

系统升级管理模块已经具备升级表单、统计报表、模板、步骤清单、日历视图和导出等基本能力，但当前设计中存在几类明显风险：

- 升级记录、清单、步骤之间没有使用数据库外键，删除主数据后容易留下孤儿步骤。
- 时间字段使用字符串保存，筛选、排序、统计都依赖字符串格式约定，长期维护成本高。
- 升级单号自动生成存在并发竞争，唯一约束只能兜底失败，不能保证用户体验。
- 前后端权限码表达不一致，统计、步骤操作、模板/清单管理的权限边界不够清晰。
- 前端日期控件、模拟同步按钮、附件上传入口等细节存在“看起来可用但实际不完整”的问题。
- 当前测试用例仍引用旧模块和旧字段，无法有效保护现有升级模块。

建议按 P0/P1/P2 分批修复，优先处理数据一致性、权限一致性和时间字段。

## P0：必须优先修复

### 1. 步骤与清单/升级记录使用整型 ID，缺少外键约束

**位置**

- `spug_api/apps/upgrade/models_checklist.py:57`
- `spug_api/apps/upgrade/models_checklist.py:89`
- `spug_api/apps/upgrade/services/record_service.py:175`

**问题**

`UpgradeChecklistStep.checklist_id`、`UpgradeRecordStep.upgrade_id`、`UpgradeRecordStep.checklist_id` 都是 `IntegerField`，不是 `ForeignKey`。

删除升级表单时，`RecordService.delete_record` 只执行 `record.delete()`，不会自动删除对应的 `UpgradeRecordStep`。删除清单时虽然服务层手动删除清单步骤，但这依赖调用路径；如果以后从其他路径删除清单，数据库不会帮忙保证一致性。

**影响**

- 删除升级表单后，`tdyw_upgrade_record_steps` 可能残留孤儿步骤。
- 清单或升级记录 ID 被复用或数据迁移后，整型关联容易指向错误对象。
- 统计和详情页可能读取到无主步骤，排查成本较高。

**建议**

- 将 `UpgradeChecklistStep.checklist_id` 改为 `ForeignKey(UpgradeChecklist, on_delete=models.CASCADE, related_name='steps')`。
- 将 `UpgradeRecordStep.upgrade_id` 改为 `ForeignKey(UpgradeRecord, on_delete=models.CASCADE, related_name='steps')`。
- `UpgradeRecordStep.checklist_id` 如果仅用于来源追踪，可改为可空外键 `source_checklist = ForeignKey(UpgradeChecklist, null=True, blank=True, on_delete=models.SET_NULL)`。
- 迁移前先清理孤儿步骤，再添加约束。
- 短期过渡方案：删除升级表单时在事务中先删除 `UpgradeRecordStep`，再删除主表。

**验证点**

- 删除升级表单后，对应步骤必须全部删除。
- 删除清单后，清单模板步骤必须全部删除，已应用到升级记录的实例步骤按产品定义保留或置空来源。
- 普通用户不能通过构造其他租户的 `upgrade_id` 访问或修改步骤。

### 2. 时间字段使用字符串，筛选和统计依赖格式约定

**位置**

- `spug_api/apps/upgrade/models.py:29`
- `spug_api/apps/upgrade/models.py:33`
- `spug_api/apps/upgrade/services/record_service.py:298`
- `spug_api/apps/upgrade/services/statistics_service.py:74`

**问题**

`upgrade_time`、`created_at`、`updated_at`、步骤的 `completed_at` 等字段大量使用 `CharField(max_length=20)` 保存时间。列表筛选通过字符串 `gte/lte` 比较，趋势统计通过 `DATE(upgrade_time)` 从字符串中截取日期。

**影响**

- 只要某条数据格式不是 `YYYY-MM-DD HH:mm:ss`，排序、筛选、统计都会出错。
- 数据库无法使用标准日期函数和日期索引优化查询。
- 时区、空值、日期范围边界都只能靠代码约定维护。

**建议**

- 将 `upgrade_time` 改为 `DateTimeField`。
- 将 `created_at`、`updated_at` 改为 `DateTimeField(auto_now_add=True/auto_now=True)` 或统一项目内的时间字段策略。
- 将 `completed_at` 改为 `DateTimeField(null=True, blank=True)`。
- 迁移时对历史字符串做格式解析，无法解析的数据单独记录并人工处理。
- 前端提交和展示统一使用 `YYYY-MM-DD HH:mm:ss`，但后端数据库字段保持日期类型。

**验证点**

- 日期范围筛选包含开始日期和结束日期当天的完整数据。
- 统计趋势按自然日期聚合准确。
- 错误格式历史数据不会导致迁移中断，迁移报告可追踪。

### 3. 升级单号生成存在并发重复风险

**位置**

- `spug_api/apps/upgrade/services/record_service.py:25`
- `spug_api/apps/upgrade/services/record_service.py:87`
- `spug_api/apps/upgrade/models.py:46`

**问题**

当前单号生成逻辑是查询当天已有最大序号，然后 `+1`。两个并发请求可能同时生成同一个 `UPG-YYYYMMDD-0001`。数据库唯一约束 `tenant_id + upgrade_no` 会阻止重复落库，但用户侧会得到创建失败。

**影响**

- 并发新建升级单时出现偶发失败。
- 前端 `next-no` 只是预览，不代表最终提交一定使用该单号。
- 如果用户打开多个新建弹窗，看到的单号可能相同。

**建议**

- 创建时保留数据库唯一约束，并捕获 `IntegrityError` 自动重试生成单号。
- 更稳妥方案：建立按 `tenant_id + date` 维度的序列表，在事务中 `select_for_update` 后递增。
- 前端明确把单号视为“预览单号”，最终以后端创建结果为准。

**验证点**

- 并发创建 20 个升级单时全部成功，且单号连续不重复。
- 同租户同日唯一，不同租户可独立编号。
- 手工传入重复单号时返回明确错误。

### 4. 权限码前后端不一致，统计权限可能失效

**位置**

- `spug_web/src/pages/system/role/codes.js:110`
- `spug_web/src/pages/upgrade/Statistics.js:62`
- `spug_api/apps/upgrade/views/statistics.py:13`
- `spug_web/src/routes.js`

**问题**

角色配置中定义了 `upgrade.statistics.view`，但统计页面和后端统计接口实际使用的是 `upgrade.upgrade.view`。这会导致“只授予统计报表权限”的角色无法访问统计，或者统计权限配置形同虚设。

步骤权限也存在语义不清：完成/跳过步骤使用 `upgrade.upgrade.edit`，重置和删除才使用 `step_reset/step_del`；手动添加步骤、应用清单使用 `upgrade.upgrade.add`，但业务语义更像编辑某个已有升级记录。

**影响**

- 权限配置与实际访问行为不一致，管理员难以理解。
- 用户可能有菜单权限但接口无权，或接口有权但菜单不可见。
- 步骤操作无法按“执行、重置、删除、清空”细粒度授权。

**建议**

- 统计页面、路由、后端接口统一使用 `upgrade.statistics.view`，或删除该权限点并全部归并到 `upgrade.upgrade.view`，二选一。
- 建议新增或统一步骤权限：
  - `upgrade.upgrade.step_view`
  - `upgrade.upgrade.step_add`
  - `upgrade.upgrade.step_execute`
  - `upgrade.upgrade.step_reset`
  - `upgrade.upgrade.step_del`
- 模板和清单管理如果面向管理员，建议拆出：
  - `upgrade.template.view/add/edit/del`
  - `upgrade.checklist.view/add/edit/del`
- 前端按钮显示与后端 `@auth` 保持完全一致。

**验证点**

- 只拥有统计权限的用户可以访问统计页和统计接口，但不能访问升级表单列表。
- 没有步骤删除权限时，直接请求删除接口应失败。
- 有步骤执行权限但无升级表单编辑权限时，可以完成/跳过步骤但不能编辑主表字段。

## P1：高优先级

### 5. 前端日期范围控件传入字符串数组

**位置**

- `spug_web/src/pages/upgrade/index.js:54`
- `spug_web/src/pages/upgrade/index.js:56`

**问题**

搜索区 `DatePicker.RangePicker` 的 `value` 使用 `[store.f_start_date, store.f_end_date]`，但 Ant Design DatePicker 通常期望 `moment` 对象数组。当前 store 中保存的是字符串。

**影响**

- 日期范围可能无法正常回显。
- 某些版本下可能出现运行时报错。
- 清空或切换筛选时，日历视图和列表视图状态容易不同步。

**建议**

- store 中可以继续保存字符串，但传给控件时转换为 `moment`：

```js
value={
  store.f_start_date && store.f_end_date
    ? [moment(store.f_start_date), moment(store.f_end_date)]
    : null
}
```

- `onChange` 中仍格式化为 `YYYY-MM-DD` 用于请求。
- 日历视图和列表视图共用筛选条件时，明确触发刷新策略。

**验证点**

- 选择日期范围后能正常回显。
- 清空日期范围后列表和日历都恢复全部数据。
- 切换列表/日历视图时筛选条件一致。

### 6. 默认模板和默认清单没有唯一约束

**位置**

- `spug_api/apps/upgrade/models_template.py:24`
- `spug_api/apps/upgrade/models_checklist.py:35`
- `spug_api/apps/upgrade/services/template_service.py:50`
- `spug_api/apps/upgrade/services/checklist_service.py:79`

**问题**

`is_default` 只是普通布尔字段。创建或更新模板/清单时，没有取消同租户下其他默认项，也没有数据库约束。

**影响**

- 同一租户可以有多个默认模板或默认清单。
- 前端排序会把多个默认项都置顶，用户不知道哪个才是真正默认。
- 后续如果实现“自动套用默认模板/清单”，会出现不确定行为。

**建议**

- 产品上明确“同租户最多一个默认模板、一个默认清单”。
- 服务层在事务内处理：
  - 当当前对象设为默认时，先把同租户其他对象 `is_default=False`。
- 如果数据库支持条件唯一索引，可增加 `tenant_id + is_default=True` 的唯一约束。

**验证点**

- 设置一个模板为默认后，其他模板自动取消默认。
- 多租户之间默认模板互不影响。
- 并发设置默认时最终只保留一个默认项。

### 7. 批量更新步骤状态会吞掉非法步骤 ID

**位置**

- `spug_api/apps/upgrade/services/step_service.py:194`
- `spug_api/apps/upgrade/services/step_service.py:211`

**问题**

`batch_update_status` 中如果某个 `step_id` 不存在或无权限，会直接 `continue`，接口仍返回成功。

**影响**

- 前端认为批量操作全部成功，但实际部分步骤没有更新。
- 越权或数据错误被悄悄吞掉，审计和排查困难。

**建议**

- 批量操作遇到无效步骤时返回错误，并回滚整个事务。
- 如果产品允许部分成功，应返回 `success_ids`、`failed_items`，前端明确提示。
- 对 `action` 做白名单校验，非法 action 不应静默忽略。

**验证点**

- 批量请求中包含不存在的步骤 ID 时，接口返回明确错误。
- 包含其他租户步骤 ID 时，接口不能更新任何数据。
- 非法 action 返回错误。

### 8. 模拟同步到设备履历按钮容易误导用户

**位置**

- `spug_web/src/pages/upgrade/RecordForm.js:181`

**问题**

详情页中“同步到设备履历”按钮只执行 `message.success('已模拟同步到设备履历模块')`，没有调用后端，也没有实际写入设备履历。

**影响**

- 用户会误以为升级记录已经同步到设备履历。
- 设备管理模块中可能看不到对应事件，造成业务数据不一致。

**建议**

- 若暂不支持同步，移除按钮或改为禁用状态并明确提示“暂未开放”。
- 若需要支持同步，新增后端接口，由后端根据升级记录创建设备履历事件。
- 同步接口必须根据当前用户、租户和升级记录 ID 重新查询数据，不能信任前端传入的记录详情。

**验证点**

- 点击同步后，设备履历中能看到对应事件。
- 重复点击不会生成重复事件，或有明确重复处理策略。
- 普通用户不能同步其他租户升级记录。

## P2：中优先级与维护性优化

### 9. `upgrade_no` 字段重复定义

**位置**

- `spug_api/apps/upgrade/models.py:24`
- `spug_api/apps/upgrade/models.py:25`

**问题**

`UpgradeRecord` 中连续定义了两次 `upgrade_no`。Django 最终会以后一次字段为准，但这属于明显代码质量问题。

**建议**

- 删除重复定义。
- 检查迁移文件是否与模型一致。

### 10. 附件上传入口与主业务模型脱节

**位置**

- `spug_api/apps/upgrade/views/upload.py:13`
- `spug_api/apps/upgrade/services/attachment_service.py:60`
- `spug_api/apps/upgrade/models.py`

**问题**

模块提供了附件上传接口，但 `UpgradeRecord` 没有附件字段，前端表单也未看到完整附件管理流程。

**影响**

- 上传后的 URL 没有稳定归属，容易成为孤儿文件。
- 附件清理函数没有被主流程调用。

**建议**

- 如果升级表单需要附件，新增附件模型或 JSON 字段，并在创建/编辑时保存附件列表。
- 如果暂不需要附件，移除接口或隐藏入口，避免无主文件堆积。
- 附件下载/预览也应补齐权限和路径安全校验。

### 11. 测试文件仍引用旧模块和旧字段

**位置**

- `spug_api/tests/test_upgrade_unique_constraint.py:15`
- `spug_api/tests/test_upgrade_unique_constraint.py:47`

**问题**

测试从 `apps.exec.models` 导入 `UpgradeRecord`，并使用旧字段 `plan_time`、`checklist`、`dependencies`、`issues`。当前升级模块已经迁移到 `apps.upgrade`，该测试无法有效验证现有代码。

**建议**

- 改为导入 `apps.upgrade.models.UpgradeRecord`。
- 按当前字段补齐测试数据：`upgrade_no`、`system`、`upgrade_type`、`version`、`upgrade_time`、`status`、`owner`、`created_at`、`created_by`、`tenant_id`。
- 增加并发创建单号测试、租户隔离测试、步骤级联删除测试、权限接口测试。

### 12. 统计接口权限和展示能力偏弱

**位置**

- `spug_api/apps/upgrade/services/statistics_service.py`
- `spug_web/src/pages/upgrade/Statistics.js`

**问题**

统计只提供总数、按类型、按系统、趋势表格。权限与统计权限码不一致的问题见 P0。展示层也只有表格，没有图表或状态维度。

**建议**

- 修复权限后，可补充按状态统计、按负责人统计、月度趋势。
- 大数据量下趋势查询应依赖日期字段和索引，避免对字符串做函数转换。
- 前端可使用项目已有图表组件或简洁表格，先保证数据准确。

## 建议实施顺序

1. 修复权限码一致性，保证菜单、按钮、后端接口权限统一。
2. 清理孤儿步骤，并为步骤/清单/升级记录建立外键或短期级联删除保护。
3. 修复升级单号并发生成，至少增加 `IntegrityError` 重试。
4. 规划时间字段迁移，把 `upgrade_time` 等核心字段改为日期类型。
5. 修复前端日期控件、默认模板/清单唯一性、批量步骤更新错误处理。
6. 处理同步设备履历、附件归属、过期测试文件。

## 回归测试建议

- 升级表单 CRUD：同租户唯一单号、不同租户同单号、编辑状态流转、删除级联步骤。
- 步骤清单：创建清单、添加步骤、应用到升级表单、删除清单后的行为。
- 步骤执行：完成、跳过、重置、删除、清空、批量操作，覆盖无权限和跨租户场景。
- 统计与导出：筛选条件一致，日期范围边界准确，导出结果与列表筛选一致。
- 权限：统计、模板、清单、步骤各权限点前后端一致。
- 并发：同租户同日并发创建升级单不重复、不失败。
