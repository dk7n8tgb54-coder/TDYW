# CRUD 系统可靠性工程实践指南

> 适用对象：数据量不大、增速平缓的内部业务型 CRUD 系统
> 核心优先级：**数据不丢 > 服务不瘫 > 故障快恢复 > 变更不翻车**

---

## 一、第一底线：数据可靠性（出问题就是生产事故）

CRUD 系统的本质是数据管理，数据丢失、错乱、不可逆是最严重的可靠事故，优先级远高于服务暂时不可用。

### 1.1 数据库约束——数据完整性的第一道防线

> **补充要点**：原文遗漏了数据库约束。事务保的是"多步操作的原子性"，约束保的是"单步操作的合法性"，两者互补缺一不可。

- **NOT NULL / UNIQUE / CHECK / FOREIGN KEY** 约束应在数据库层强制，不能仅靠应用层校验
- 绕过应用的直接 SQL 操作（运维脚本、数据修复）会绕过应用层校验，数据库约束是兜底
- 外键约束要配合 `ON DELETE` 策略（CASCADE / SET NULL / PROTECT）按业务语义选择
- 唯一约束防重复创建，是幂等性的数据库层保障

### 1.2 事务边界与数据一致性

这是数据错乱的头号诱因：核心写操作没加事务导致部分成功、部分失败；多表联动更新没有原子性保障。

**核心原则：**
- 所有涉及多步写操作的业务逻辑必须包裹在事务中
- 事务粒度尽量小，禁止在事务内做长时间阻塞的外部调用（如无限重试的 HTTP 请求）
  - 短超时的外部调用（快速检查类）可以容忍
  - 长耗时外部调用应移到事务外，用 **Transactional Outbox** 或 **Saga 模式** 保证最终一致性
- 禁止在事务里循环写入大批量数据，应分批提交

**隔离级别选择：**

| 隔离级别 | 适用场景 | 注意事项 |
|---|---|---|
| RR（Repeatable Read） | InnoDB 默认，低并发内部系统 | 间隙锁可能导致死锁，但幻读防护更完整 |
| RC（Read Committed） | 高并发系统，阿里/Facebook 等大量采用 | 并发更好，间隙锁少，锁竞争低 |

> **纠正**：不要盲目坚持 RR"不降级"。应理解 trade-off 按业务场景选择。低增速内部系统用 RR 足够且更安全；高并发场景 RC 往往更优。

**长事务的真正危害（纠正"引发脏读"的说法）：**
- 锁竞争：长时间持有行锁/间隙锁，阻塞其他事务
- undo log 膨胀：MVCC 旧版本堆积，影响性能
- 死锁概率上升：持有锁时间越长，交叉等待越容易
- 连接池耗尽：长事务占着连接不释放

> **纠正**：长事务在 RR/RC 隔离级别下**不会引发脏读**。脏读只发生在 READ UNCOMMITTED 隔离级别，InnoDB 默认 RR 根本不可能脏读。

### 1.3 幂等性设计

> **补充要点**：原文完全遗漏。CRUD 系统在重试场景下极易产生重复数据。

**典型故障场景：**
- 网络超时 → 用户重试 → 重复创建
- Celery 任务重试 → 重复执行副作用
- 前端防抖不完善 → 双击提交

**落地手段：**
- 核心写操作设计幂等键（业务唯一约束 + `INSERT ... ON DUPLICATE KEY UPDATE`）
- 或用唯一请求 ID（request_id）去重
- 异步任务用状态机控制：只有特定状态才允许执行，执行后原子更新状态
- DELETE 天然幂等；UPDATE 用绝对值而非增量（`SET count = 5` 而非 `SET count = count + 1`）

### 1.4 可验证的备份与恢复机制

这是系统的最后一道防线。绝大多数团队的备份都是"伪备份"——只备份不验证，真出问题时恢复失败。

**标准做法：**
- 定时全量备份 + 增量 binlog 备份
- 每月至少做一次完整的恢复演练，确认备份可用、恢复耗时可控
- 核心业务数据保留多份备份，避免单点存储损坏
- 备份文件做完整性校验（checksum / 试恢复）

**显式定义 RPO / RTO（补充）：**

> **补充要点**：原文说"恢复耗时可控"但没有量化目标。没有量化标准的"可控"是空话。

| 指标 | 含义 | 示例 |
|---|---|---|
| RPO（Recovery Point Objective） | 可接受的数据丢失量 | ≤ 1 小时（binlog 增量间隔） |
| RTO（Recovery Time Objective） | 可接受的恢复时间 | ≤ 30 分钟 |

有了量化目标，才能反推：备份频率要多高？是否需要主从热备？是否需要异地容灾？

### 1.5 防误操作与可追溯机制

内部 CRUD 系统超过一半的数据故障是人为误操作（误删、批量更新写错条件）。

**落地手段：**
- 核心业务表用逻辑删除替代物理删除
- 关键数据变更留痕：操作人、变更前后值、时间戳
- 高风险操作（批量删除、全表更新）增加二次校验与权限管控
- 数据库账号最小权限原则：应用账号无 DROP/TRUNCATE 权限

## 二、第二核心：基础稳定性（避免日常宕机）

大部分 CRUD 系统"不可用"，不是因为硬件故障，而是因为自身代码和数据库设计问题。

### 2.1 索引与慢查询治理

这是最常见的故障诱因：一条未走索引的慢 SQL 打满数据库 CPU，整个系统直接瘫痪，概率远高于服务器宕机。

**核心动作：**
- 所有业务查询上线前必须核对执行计划（EXPLAIN）
- 定期巡检慢查询日志，持续优化
- 禁止无边界查询（不带时间范围、不带筛选条件的全表列表/导出）
- **注意 DateTimeField 的 `__date` 过滤会绕过索引**（翻译成 `DATE(col)=...`），改用 `__gte` / `__lt` 范围查询
- 注意 `LIKE '%xxx'` 前缀通配无法走索引
- 复合索引遵循最左前缀原则

### 2.2 资源兜底与限流容错

避免单点压力拖垮整体：

- **数据库连接池**配置合理上限，防止连接被打满
  - 同时注意连接泄漏防护：确保连接在 finally 块中释放
  - Django 的 `CONN_MAX_AGE` 合理配置
- 批量导入、导出等重操作单独限流、异步化（Celery 队列隔离）
- 核心接口设置超时时间，避免请求堆积雪崩
- 导出操作设上限行数 + 异步生成，避免同步导出大表阻塞 worker

### 2.3 消除核心单点

- 应用服务至少双实例部署，单台宕机不影响服务
- 数据库至少主从架构，主库故障可快速切换到从库
- 对于资源受限的小型系统，如果无法做到双实例：
  - 确保有快速恢复流程（容器秒级重启 + 健康检查）
  - 主从至少做数据备份用途（异步复制 + 定期校验一致性）
  - 明确单点的 RTO，确保在可接受范围内

> **平衡提示**：原文同时说"双实例+主从"又说"不用追求分布式架构"，存在轻微矛盾。对于低增速内部系统，**好的备份 + 经过验证的恢复流程 > HA 架构**。优先把备份做实，再考虑高可用。

## 三、第三关键：可观测与应急能力（出问题能快速止损）

可靠性的后半段，是出问题后能不能快速发现、快速定位、快速恢复。

### 3.1 核心指标监控告警

必须覆盖三类指标：

**数据库层：**
- CPU 使用率、连接数、慢查询数量
- 主从延迟、磁盘空间
- InnoDB buffer pool 命中率、undo log 大小

**应用层：**
- 接口错误率（5xx 占比）、平均响应时间、P99 延迟
- 异常日志量突增告警
- Celery 队列堆积 / 任务失败率

**基础资源：**
- 服务器 CPU、内存、磁盘
- 磁盘 IO（对机械盘尤为重要）

告警阈值要合理，做到问题发生前预警、发生时第一时间通知，而不是等用户反馈。

### 3.2 可追溯的日志体系

- **错误日志**必须带完整上下文：请求参数、链路 ID（trace_id）、异常栈
- **数据操作日志**可定位到具体人、具体时间、具体变更内容（变更前后值）
- 日志分级：ERROR 触发告警，WARN 记录但观察，INFO 用于审计追溯
- 日志保留周期：操作审计日志 ≥ 180 天，错误日志 ≥ 30 天

### 3.3 容量规划与趋势监控

> **补充要点**：原文遗漏。"低增速"不等于"不增长"，等到磁盘满了才发现比慢查询打垮数据库更难恢复。

定期评估（至少每月一次）：
- 关键表的行数增长趋势
- 磁盘空间消耗速率
- 连接数峰值 / QPS 趋势
- 预估到达资源瓶颈的时间点

### 3.4 标准化应急预案

提前准备常见故障的处理流程（Runbook）：

| 故障类型 | 应急动作 |
|---|---|
| 数据库卡死 | 查 `SHOW PROCESSLIST` → 杀慢 SQL → 排查根因 |
| 数据误操作 | 从备份恢复 + binlog 回放到误操作前 |
| 版本上线出问题 | 一键回滚到上一版本 → 验证服务恢复 |
| 主库故障 | 切从库为主库 → 更新连接配置 → 重启应用 |
| 磁盘空间满 | 清理日志/临时文件 → 扩容 → 排查大文件 |

- 有预案和没预案，恢复时间差 10 倍以上
- 预案要定期演练，确保文档与实际环境一致

### 3.5 安全维度

> **补充要点**：原文完全没提安全。安全事件导致的数据丢失同样是可靠性事故。

- **SQL 注入防护**：参数化查询，禁止字符串拼接 SQL
- **最小权限原则**：应用账号只授予必要权限，无 DDL 权限
- **敏感数据加密**：密码哈希存储（bcrypt/argon2），敏感字段加密
- **访问控制**：RBAC 权限体系，越权访问防护
- **审计追溯**：关键操作留痕，可定位到人

## 四、第四重点：变更安全（人为故障是重灾区）

统计上，生产环境 70% 以上的故障来自变更：代码上线、数据库表结构修改、配置变更。

### 4.1 数据库变更规范

- **表结构修改（DDL）必须评估风险**
  - 大表变更使用在线 DDL 工具（pt-online-schema-change / gh-ost），避免锁表
  - MariaDB 不支持部分唯一索引，加唯一约束前先清洗重复数据
  - 改字段类型（如 CharField → DateField）先洗空串/非法值再迁移
- **所有变更 SQL 提前审核**，禁止无 WHERE 条件的 UPDATE/DELETE
- **变更前必须先备份对应表**
- **加字段优先选 nullable + default**，避免锁表和 NOT NULL 约束失败
- **拆步操作**：加字段 → 回填数据 → 查重 → 加约束，每步可独立回退
- **makemigrations 指定 app**，避免扫描全项目生成意外迁移文件

### 4.2 发布与回滚机制

- 代码发布支持一键回滚
- 核心功能变更小批量灰度验证
- 上线后持续观察 10~30 分钟监控指标，确认无异常才算发布完成
- 数据库迁移与代码发布分离：先执行迁移（向后兼容），再发布代码
- 配置变更纳入版本管理，变更可追溯、可回退

---

## 五、总结

对数据量不大、增速平缓的内部业务系统，完全不用追求分库分表、分布式架构——复杂度本身就会降低可靠性。

**把以下七件事做扎实，系统的可靠性就已经超过绝大多数同规模的 CRUD 系统：**

| 序号 | 基础事项 | 一句话总结 |
|---|---|---|
| 1 | 数据库约束 | NOT NULL / UNIQUE / FK 在数据库层强制，不只靠应用层 |
| 2 | 事务写对 | 多步写操作原子包裹，事务粒度小，隔离级别按场景选 |
| 3 | 幂等设计 | 重试不产生重复数据，状态机 + 唯一约束兜底 |
| 4 | 备份做实 | 全量 + binlog，定期演练，定义 RPO/RTO 量化目标 |
| 5 | 索引管好 | 上线核对 EXPLAIN，禁止无边界查询，定期巡检慢日志 |
| 6 | 监控配上 | DB + 应用 + 基础资源三层覆盖，容量趋势提前预警 |
| 7 | 变更走规范 | DDL 分步、SQL 审核、一键回滚、迁移与发布分离 |

**最终原则：简单 > 复杂，验证 > 假设，预防 > 恢复，量化 > 模糊。**
