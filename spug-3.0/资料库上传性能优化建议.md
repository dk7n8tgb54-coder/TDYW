# 资料库上传性能优化建议

## 背景结论

服务器内存为 8G 时，资料库 2-3 个账号同时上传变慢的主要风险点不在内存容量本身，而在上传请求并发、分片落盘、文件合并、缩略图生成以及状态更新共同压住 CPU 和磁盘 I/O。

建议优先优化以下 4 项：

1. 前端上传并发按服务器压力动态降级
2. 确认上传 API 独立部署
3. 控制合并 worker 并发
4. 缩略图生成改为异步任务

---

## 1. 前端并发按服务器压力动态降级

### 当前风险

当前前端资料库上传默认并发配置在：

- `spug_web/src/pages/document/stores/constants/upload.js`

当前逻辑大致为：

- 同时上传文件数：`MAX_CONCURRENT_UPLOADS = 3`
- 单文件分片并发：`MAX_CONCURRENT_CHUNKS = 3`

如果 3 个账号同时上传，理论上可能形成：

```text
3 个账号 * 3 个文件 * 3 个分片 = 27 个分片请求并发
```

这会放大后端落盘、Redis 更新、MySQL 状态更新和 Nginx/Gunicorn 连接压力。

### 修改建议

新增一个后端压力状态接口，前端上传前和上传过程中定期读取服务器压力，并动态调整上传并发。

建议接口：

```text
GET /api/document/upload_pressure/
```

返回示例：

```json
{
  "level": "normal",
  "max_concurrent_uploads": 3,
  "max_concurrent_chunks": 3,
  "disk_usage_percent": 62,
  "merge_queue_depth": 0,
  "cpu_load_hint": "normal"
}
```

建议分级：

| 压力等级 | 文件并发 | 分片并发 | 触发条件示例 |
|---|---:|---:|---|
| `normal` | 3 | 3 | 磁盘使用率低、合并队列为空 |
| `busy` | 2 | 2 | 合并队列有积压、磁盘 I/O 偏高 |
| `critical` | 1 | 1 | 磁盘使用率高、合并队列明显积压 |

前端需要把上传并发配置从静态常量改为运行时配置，例如：

- 页面初始化时拉取一次压力状态
- 每 10-30 秒刷新一次
- 上传失败、合并排队、接口响应慢时主动降级
- 状态恢复后不要立刻升高并发，建议延迟 1-3 分钟再恢复

### 推荐落地点

后端：

- `spug_api/apps/document/views/health.py` 或新增 `views/upload/pressure.py`
- `spug_api/apps/document/urls.py`

前端：

- `spug_web/src/pages/document/stores/constants/upload.js`
- `spug_web/src/pages/document/stores/upload/core/queue.js`
- `spug_web/src/pages/document/stores/upload/core/chunkUpload.js`

### 验证方式

使用 2-3 个账号同时上传大文件，观察：

- 前端并发是否会从 `3*3` 降到 `2*2` 或 `1*1`
- 普通资料库浏览接口是否不再明显卡顿
- 合并队列积压时是否停止继续放大上传压力

## 2. 确认上传 API 独立部署

### 当前风险

项目中已经有上传专用 API 脚本：

- `spug_api/tools/start-api-upload.sh`

Docker/Nginx 配置里也能看到上传接口代理到 `9003` 的设计：

- `docker/config/nginx.conf`
- `docker/config/supervisord.conf`

但需要确认生产环境是否真的启动了独立上传 API。否则上传落盘会和普通 API 请求混在同一组 Gunicorn worker 中，导致资料库浏览、查询、预览等普通接口被上传拖慢。

### 修改建议

生产部署必须保证至少有以下进程：

```text
spug-api          普通 API，监听 9001
spug-api-upload   上传专用 API，监听 9003
spug-ws           WebSocket，监听 9002
```

Nginx 中应将以下上传相关接口转发到 `9003`：

```text
/api/document/upload/
/api/document/upload_chunk/
/api/document/check_uploaded_chunks/
/api/document/merge_chunks/
/api/document/merge_status/
```

普通 API 仍转发到 `9001`。

### 推荐落地点

部署配置：

- `docker/config/supervisord.conf`
- `docker/config/nginx.conf`
- `config/dev/supervisor/conf.d/03a-spug-api-upload.conf`
- 生产服务器实际 supervisor 配置

### 运维检查命令

在服务器上检查：

```bash
supervisorctl status
```

应看到类似：

```text
spug-api                  RUNNING
spug-api-upload           RUNNING
spug-ws                   RUNNING
```

检查监听端口：

```bash
ss -lntp | grep -E '9001|9002|9003'
```

### 验证方式

同时上传大文件时访问普通资料库列表、搜索、预览：

- 如果普通 API 延迟明显降低，说明隔离生效
- 如果仍然卡顿，需要继续检查磁盘 I/O 和数据库连接压力

## 3. 控制合并 Worker 并发

### 当前风险

大文件分片上传完成后会进入 Celery 合并任务：

- `spug_api/apps/document/tasks/merge.py`

合并过程会：

1. 读取所有分片
2. 写入完整文件
3. 校验文件大小
4. 计算或比对 MD5
5. 创建文件记录
6. 清理分片目录

这是典型磁盘 I/O 密集任务。如果多个大文件同时合并，服务器会出现磁盘读写争抢。

当前合并 worker 启动脚本：

- `spug_api/tools/start-celery-merge.sh`

默认并发为：

```bash
CELERY_MERGE_CONCURRENCY=${CELERY_MERGE_CONCURRENCY:-4}
```

对 8G 内存服务器，如果磁盘不是高性能 NVMe，默认 4 个合并任务同时跑偏激进。

### 修改建议

把合并并发变成部署环境显式配置，不建议写死。

推荐生产环境初始值：

```bash
CELERY_MERGE_CONCURRENCY=1
```

如果压测确认磁盘 I/O 足够，再调整为：

```bash
CELERY_MERGE_CONCURRENCY=2
```

不建议 8G 小服务器默认使用 4。

### 进一步优化

可以增加合并队列深度监控：

- 队列为空：允许正常上传
- 队列积压 1-3 个：前端降级为 `2*2`
- 队列积压超过 3 个：前端降级为 `1*1`

这可以和第 1 项“动态并发降级”联动。

### 推荐落地点

- `spug_api/tools/start-celery-merge.sh`
- `docker/config/supervisord.conf`
- `config/dev/supervisor/conf.d/11-celery-merge.conf`
- 生产 supervisor 环境变量

### 验证方式

同时上传多个大文件，观察：

- 合并任务是否排队而不是同时全部跑满
- 普通 API 是否仍可流畅访问
- 磁盘 I/O 是否稳定
- Celery 队列是否没有长期积压

## 4. 缩略图生成改异步

### 当前风险

上传完成后会同步生成缩略图，相关代码：

- `spug_api/apps/document/services/file_upload_service.py`
- `spug_api/apps/document/tasks/merge.py`
- `spug_api/apps/document/services/thumbnail_service.py`

小文件普通上传时，请求线程中会调用：

```python
generate_thumbnail_for_file(...)
```

大文件分片合并完成后，Celery merge 任务中也会调用缩略图生成。

图片较大或多个图片并发上传时，Pillow 解码、缩放、保存会吃 CPU，并拉长上传完成耗时。

### 修改建议

将缩略图生成拆成独立 Celery 任务：

```text
document.thumbnail
```

上传或合并完成后只做两件事：

1. 创建文件记录
2. 投递缩略图生成任务

接口立即返回，不等待缩略图生成完成。

建议新增任务：

```python
@shared_task(queue='document.thumbnail')
def generate_document_thumbnail(file_id, is_public):
    ...
```

文件记录可以增加或复用状态字段：

```text
thumbnail_status: pending / processing / completed / failed
thumbnail_path
```

如果暂时不想加字段，也可以只异步生成并在失败时记录日志，不影响上传成功。

### 推荐落地点

新增：

- `spug_api/apps/document/tasks/thumbnail.py`

修改：

- `spug_api/apps/document/tasks/__init__.py`
- `spug_api/spug/settings.py` 中增加 Celery 路由
- `spug_api/apps/document/services/file_upload_service.py`
- `spug_api/apps/document/tasks/merge.py`
- supervisor 增加 `document.thumbnail` 专用 worker，或先由默认 Celery worker 消费

### 推荐 worker 并发

8G 服务器建议：

```bash
CELERY_THUMBNAIL_CONCURRENCY=1
```

图片上传多时可以提升到 2，但不建议和 merge worker 抢太多 CPU。

### 验证方式

上传图片后：

- 上传接口应快速返回
- 文件列表先显示默认图标或无缩略图
- 后台任务完成后刷新列表可看到缩略图
- 缩略图失败不影响文件上传成功

---

## 推荐实施顺序

1. 先确认生产环境是否启用了 `spug-api-upload` 和 `spug-celery-merge`
2. 将合并 worker 并发改为环境变量控制，并从 1 或 2 开始压测
3. 增加服务器压力接口，前端上传并发按压力动态降级
4. 缩略图生成改异步，避免上传请求和合并任务被图片处理拖慢

## 最终建议

8G 内存服务器上，资料库上传优化不要只看内存。真正需要控制的是：

- 同时上传的请求数量
- 同时落盘的分片数量
- 同时合并的大文件数量
- 同时执行的图片缩略图任务数量

建议以“上传隔离 + 合并限流 + 前端动态降级 + 缩略图异步”为主线推进。
