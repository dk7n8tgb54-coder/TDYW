# 审计日志完整准确简洁优化方案

## 一、目标

本方案用于优化当前项目的操作审计能力，使审计日志同时满足三个要求：

- 完整：关键安全行为、业务高风险行为、审计日志访问行为不漏记。
- 准确：动作类型、对象、结果、失败原因、租户归属准确，避免把失败记成成功、把导出记成创建。
- 简洁：一条审计只对应一个有审计价值的业务动作，detail 只保留摘要、差异、筛选条件和失败原因，不记录冗余请求体。

核心原则：

> 核心字段完整，detail 摘要化；高风险 GET 纳入，低价值读操作跳过。

## 二、当前现状

项目已经具备较好的审计基础：

- 已有 `apps.logs` 模块和 `AuditLog` 表。
- `AuditLogMiddleware` 已接入 Django 中间件。
- POST/PUT/PATCH/DELETE 写操作会自动记录审计。
- 登录成功、登录失败、登出已有单独审计。
- 审计导出动作本身已有手工记录。
- 已有敏感字段关键词过滤，避免 `password`、`token`、`secret`、`key` 等字段进入 `detail`。
- 已有 `request_id`、`user_agent`、`request_hash`、`response_hash`、`prev_hash`、`log_hash` 等证据闭环字段。

主要不足：

- 大量 GET 导出、下载、附件访问不会进入统一审计表。
- 部分 POST 导出会被中间件按 `create` 记录，动作分类不准。
- 审计日志查询本身被排除，不记录谁查看过审计日志。
- 默认 30 天物理删除审计日志，对合规追溯偏短。
- 哈希链有生成和校验函数，但缺少定时校验和告警闭环。
- `detail` 结构尚未统一，容易在不同模块间出现过多、过少或格式不一致。

## 三、记录边界

### 3.1 必须记录

以下行为必须进入统一 `AuditLog`：

| 类别 | 行为 | 说明 |
| --- | --- | --- |
| 认证 | 登录成功、登录失败、登出、账号锁定、MFA 失败 | 登录失败不得记录密码 |
| 权限 | 用户创建/编辑/删除、角色创建/编辑/删除、角色授权变更、租户变更 | 必须记录变更前后摘要 |
| 业务写操作 | 创建、修改、删除、作废、关闭、审批、驳回、纠正 | 记录对象 ID、名称、结果 |
| 数据流出 | Excel/PDF/ZIP 导出、附件下载、文件下载、批量下载 | GET 下载也必须记录 |
| 审计访问 | 审计日志查询、审计日志导出、哈希链校验 | 查询只记录条件摘要 |
| 系统配置 | 系统设置、推送配置、密钥配置、保留策略变更 | 敏感值只记录是否变更 |
| 异常安全事件 | 越权访问、租户隔离失败、非法路径、参数篡改 | 记录失败原因和来源 IP |

### 3.2 默认不记录

以下行为默认不进入统一审计，避免日志噪声：

- 普通列表查询。
- 普通详情查看。
- 下拉选项、字典、统计卡片等辅助读取接口。
- 健康检查、静态资源、轮询状态查询。
- 前端初始化配置读取。

例外：如果读取行为涉及敏感数据、审计数据、批量数据导出、附件内容或跨租户风险，应纳入审计。

## 四、统一字段规范

### 4.1 固定核心字段

`AuditLog` 每条记录应稳定包含：

| 字段 | 要求 |
| --- | --- |
| `created_at` | 服务端时间，使用统一时区 |
| `tenant_id` | 当前用户租户；未知登录失败可归入全局租户 |
| `user_id` | 未登录失败使用 `0` |
| `username` | 登录名或尝试登录名 |
| `action` | `create/update/delete/login/logout/export/import/approve/other` |
| `target_type` | 对象类型，如 `user`、`role`、`runlog`、`audit` |
| `target_id` | 对象主键，批量操作用逗号分隔或摘要 |
| `target_name` | 人类可读名称 |
| `is_success` | 真实业务结果，不只看 HTTP 状态码 |
| `ip` | 真实客户端 IP |
| `user_agent` | 客户端 UA，截断保存 |
| `request_id` | 单次请求唯一 ID |
| `detail` | 摘要 JSON，不放敏感原文 |
| `request_hash` | 基于脱敏 detail 的哈希 |
| `response_hash` | 响应体哈希；流式响应可为空 |
| `prev_hash` / `log_hash` | 按租户形成哈希链 |

### 4.2 detail 简洁规范

`detail` 只允许保存以下几类内容：

```json
{
  "changed": {
    "status": ["open", "closed"]
  },
  "filters": {
    "start_date": "2026-07-01",
    "end_date": "2026-07-07"
  },
  "count": 128,
  "error": "无权限访问该资源"
}
```

推荐结构：

| 场景 | detail 内容 |
| --- | --- |
| 创建 | 关键字段摘要，不保存完整表单 |
| 修改 | `changed`，只记录变更字段的前后值 |
| 删除 | 删除原因、是否软删、对象摘要 |
| 导出 | `filters`、`count`、`format`、文件名 |
| 下载 | 文件 ID、文件名、大小、是否公共空间 |
| 登录失败 | 失败原因、登录类型 |
| 权限变更 | 角色/权限变更前后摘要 |
| 配置变更 | 配置项名称、是否变更，不保存密钥原文 |

禁止写入：

- 密码、验证码、token、session、cookie。
- API key、private key、secret、push key、wx token。
- 完整请求头、完整响应体。
- 大字段正文、附件内容、二进制内容。
- 未脱敏的个人敏感信息。

## 五、动作分类规范

统一动作映射：

| 场景 | action |
| --- | --- |
| 新增对象 | `create` |
| 编辑对象 | `update` |
| 删除、软删、作废 | `delete` |
| 登录 | `login` |
| 登出 | `logout` |
| Excel/PDF/ZIP 导出 | `export` |
| 文件导入、批量导入 | `import` |
| 审批、通过、驳回 | `approve` |
| 其他无法归类动作 | `other` |

需要特别修正：

- POST `/runlog/export/pdf/` 应记录为 `export`，不能记录为 `create`。
- GET `/runlog/export/excel/` 应记录为 `export`。
- GET 附件下载、文件下载应记录为 `export` 或新增业务动作 `download`。若保持现有枚举简洁，建议统一归入 `export`，在 `detail.format` 中标记 `download`。

## 六、实现方案

### 6.1 新增审计工具函数

新增或扩展 `apps.logs.audit`：

- `record_audit_event(...)`：业务手工审计统一入口。
- `build_audit_detail(...)`：生成标准 detail。
- `sanitize_audit_detail(...)`：递归脱敏。
- `audit_export(...)`：用于 GET/POST 导出和下载。
- `audit_view_sensitive(...)`：用于审计日志查询等敏感查看。

建议参数：

```python
record_audit_event(
    request=request,
    action='export',
    target_type='runlog',
    target_id=None,
    target_name='运行日志 Excel 导出',
    detail={
        'filters': filters,
        'count': count,
        'format': 'excel',
    },
    is_success=True,
)
```

这样业务视图不用直接拼 `user_id`、`ip`、`tenant_id`，避免各模块风格不一致。

### 6.2 高风险 GET 白名单

中间件继续默认只记录写操作，避免噪声。

对 GET 不做全量记录，只通过显式白名单记录高风险行为：

- `/logs/audit/`：审计日志查询。
- `/logs/audit/export/`：审计日志导出。
- `/runlog/export/excel/`：运行日志 Excel 导出。
- `/device/device-resume/export/`：设备履历导出。
- `/fault/faultrecord/export/`：故障记录导出。
- `/interference/export/`：干扰记录导出。
- `/upgrade/records/export/`：升级记录导出。
- `/document/download/`：资料文件下载。
- `/document/folder/download/`：资料文件夹下载。
- `/document/folder/download/ready/`：异步打包文件下载。
- `/radio-license/attachments/<id>/download/`：无线电执照附件下载。
- `/upgrade/attachments/<id>/download/`：升级附件下载。

建议优先采用业务视图手工调用 `record_audit_event`，不要在中间件里硬解析所有 GET 细节。中间件负责兜底，业务视图负责准确。

### 6.3 修正导出动作误判

对已有 POST 导出接口增加显式审计：

- 运行日志 PDF 导出。
- 值班 PDF 导出。
- 检查表 PDF 导出。
- 设备履历 PDF 导出。

处理方式：

- 成功：`action='export'`，记录筛选条件、导出数量、格式。
- 失败：`action='export'`，`is_success=False`，记录失败原因。
- 避免中间件重复记录：可在 request 上设置 `_audit_handled = True`，中间件发现后跳过。

### 6.4 统一失败结果判断

保留当前中间件解析响应 JSON `error` 的逻辑。

补充统一规则：

- HTTP 状态码 `>= 400`：失败。
- JSON 响应存在非空 `error`：失败。
- 业务抛异常但被捕获返回 `json_response(error=...)`：失败。
- 流式响应成功创建并返回：成功。
- 文件不存在、无权限、路径非法：失败并记录 `error`。

### 6.5 递归脱敏

当前敏感字段过滤主要处理顶层字段。建议改成递归脱敏：

```json
{
  "old_password": "***",
  "profile": {
    "api_key": "***"
  }
}
```

脱敏策略：

- 字段名包含敏感关键词：值替换为 `***`。
- 超长字符串截断，如 500 字符。
- 列表最多保留前 20 项并附带总数。
- 字典最多保留白名单字段或前 N 项。

敏感关键词：

```text
password, token, secret, key, private, credential, captcha, cookie, session
```

### 6.6 留存和归档

当前默认 30 天物理删除偏短。建议改成配置化：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `AUDIT_RETENTION_DAYS` | 365 | 在线保留天数 |
| `AUDIT_ARCHIVE_ENABLED` | true | 是否归档 |
| `AUDIT_ARCHIVE_BEFORE_DELETE` | true | 删除前必须归档 |
| `AUDIT_CLEANUP_BATCH_SIZE` | 5000 | 批量清理大小 |

清理流程：

1. 查询超过保留期的日志。
2. 导出归档文件，包含日志 JSON、校验摘要、生成时间。
3. 计算归档文件 SHA256。
4. 写入一条 `target_type='audit'`、`action='export'` 的归档审计。
5. 归档成功后再批量删除在线数据。

如暂不实现归档，至少应把默认保留期改为 180 或 365 天。

### 6.7 哈希链校验

保留现有 `verify_hash_chain` 能力，并新增定时任务：

- 每日低峰按租户校验最近一天日志。
- 每周校验全量或抽样分段。
- 发现断链、单条 hash 不一致、缺失 prev_hash 时记录告警日志。
- 校验结果写入 `AuditLog`，例如：

```json
{
  "tenant_id": "tenant_a",
  "checked": 12345,
  "valid": true,
  "broken_at": null
}
```

### 6.8 前端展示优化

审计页面保持简洁：

- 列表默认展示：时间、用户、动作、对象、结果、IP。
- detail 默认折叠，只展示摘要。
- 失败记录高亮失败原因。
- 导出/下载类展示筛选条件和数量。
- 权限变更类展示前后差异。
- 哈希字段默认不展示，详情中可查看。

筛选项：

- 时间范围。
- 用户。
- 动作。
- 对象类型。
- 成功/失败。
- 关键字。
- request_id。

## 七、建议改造清单

### P0：准确性和漏记修复

- 新增统一手工审计入口 `record_audit_event`。
- 修正运行日志 PDF 导出被记为 `create` 的问题。
- 为 GET Excel/PDF/ZIP 导出补审计。
- 为文件下载、附件下载补审计。
- 为审计日志查询补审计。
- 增加 `_audit_handled` 机制，避免手工审计和中间件重复记录。

### P1：简洁化和一致性

- 统一 detail 结构。
- 增加递归脱敏。
- 修改中间件 detail 提取逻辑，只保存摘要字段。
- 对角色、权限、用户编辑记录 changed diff。
- 对导出/下载记录 filters、count、format。

### P2：可信和合规增强

- 审计保留期配置化，默认 365 天。
- 删除前归档。
- 新增哈希链定时校验任务。
- 增加校验失败告警。
- 前端增加 request_id 查询和 detail 折叠展示。

## 八、验收标准

### 8.1 完整性验收

- 登录成功、登录失败、登出均有审计。
- 用户、角色、权限变更均有审计。
- 创建、修改、删除、审批、作废均有审计。
- Excel/PDF/ZIP 导出均有审计。
- 文件和附件下载均有审计。
- 审计日志查询和导出均有审计。
- 普通列表查询不会产生审计噪声。

### 8.2 准确性验收

- 业务失败不会显示为成功。
- 导出不会显示为创建。
- 删除目标能记录 `target_id`。
- 多租户用户只能看到本租户审计。
- 未知账号登录失败按全局策略记录。
- 手工审计和中间件不会重复记同一动作。

### 8.3 简洁性验收

- detail 不包含完整请求体。
- detail 不包含密码、token、secret、key 等敏感值。
- 修改类 detail 只展示 changed diff。
- 导出类 detail 只展示 filters、count、format。
- 单条审计日志能在列表中快速理解动作含义。

### 8.4 可信性验收

- 新增审计日志均有 `request_id`。
- 新增审计日志均有 `log_hash`。
- 同租户日志 `prev_hash` 能连续校验。
- 定时清理不会直接删除未归档数据。
- 审计日志导出自身会产生审计记录。

## 九、推荐实施顺序

1. 先做 P0，解决漏记和动作误判。
2. 再做 detail 结构和递归脱敏，控制日志体积和敏感信息风险。
3. 最后做留存归档、哈希链校验和前端展示增强。

这样可以先保证审计可用，再逐步把它做得干净、可信、好查。

## 十、给编程 AI 的执行任务单

本节用于直接交给负责编码的 AI 或开发人员执行。执行时必须保持小步提交，优先完成 P0，不要一次性重构全部审计体系。

### 10.1 执行总要求

- 不改变现有 `AuditLog` 表的核心字段，优先复用现有 `save_audit_log`。
- 不全量审计 GET，只审计高风险 GET。
- 不把完整请求体写入 `detail`。
- 不记录密码、验证码、token、secret、key、cookie、session 等敏感值。
- 每个业务动作最多生成一条审计日志，避免中间件和手工审计重复。
- 所有新增审计都必须携带 `tenant_id`、`ip`、`user_agent`、`request_id`。

### 10.2 第一步：扩展审计工具函数

目标文件：

- `spug_api/apps/logs/audit.py`
- `spug_api/apps/logs/middleware.py`

新增函数：

```python
def sanitize_audit_detail(value, max_string_length=500, max_list_items=20):
    """递归脱敏并压缩 detail。"""


def record_audit_event(request, action, target_type, target_id=None,
                       target_name=None, detail=None, is_success=True,
                       error=None):
    """业务视图手工审计统一入口。"""
```

实现要求：

- `record_audit_event` 内部调用现有 `save_audit_log`。
- 从 `request.user` 读取 `user_id`、`username`、`tenant_id`。
- 使用现有 `_extract_user_agent(request)`。
- 使用 `get_request_real_ip(request.headers)` 获取 IP。
- 使用 `request._audit_request_id`，不存在时允许为空。
- 如果传入 `error`，合并到 `detail.error`，并设置 `is_success=False`。
- 写入成功后设置 `request._audit_handled = True`。
- `sanitize_audit_detail` 必须递归处理 `dict`、`list`、`tuple`、字符串。
- 敏感字段用 `***` 替代，不是删除字段。

修改中间件：

- 在 `AuditLogMiddleware._record_audit` 开头增加判断：

```python
if getattr(request, '_audit_handled', False):
    return
```

验收：

- 手工调用 `record_audit_event` 后，中间件不再重复记录同一请求。
- 嵌套字段中的 `api_key`、`old_password`、`token` 会被替换为 `***`。

### 10.4 第三步：补齐 GET 导出审计

目标文件：

- `spug_api/apps/runlog/exporters.py`
- `spug_api/apps/device/exporters.py`
- `spug_api/apps/fault/exporters.py`
- `spug_api/apps/interference/exporters.py`

改动要求：

- 在导出成功返回响应前调用 `record_audit_event`。

```json
{
  "format": "excel",

  "count": 123
```

- 如果导出失败或无数据，记录失败审计。
