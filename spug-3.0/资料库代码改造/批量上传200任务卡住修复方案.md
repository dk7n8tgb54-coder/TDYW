# 资料库批量上传 200 任务卡住修复方案

## 一、问题现象

批量上传大量任务时，例如一次上传 870 个文件，上传流程在约第 200 个任务附近停止继续调度。

同时可能出现以下现象：

- 后续任务停留在等待状态，不再继续上传。
- 传输列表点击无响应或响应明显变慢。
- 浏览器控制台可能出现状态机创建失败、空对象调用或相关前端异常。

## 二、初步结论

当前问题不是后端“最多只能上传 200 个文件”的业务限制，而是前端上传状态管理存在 200 个状态机实例上限。

涉及两个容易混淆的配置：

| 配置 | 文件 | 作用 | 是否会阻止上传 |
| --- | --- | --- | --- |
| `MAX_DISPLAY_COUNT = 200` | `spug_web/src/pages/document/stores/constants/upload.js` | 传输列表显示数量限制 | 理论上不应阻止上传 |
| `MAX_MACHINES = 200` | `spug_web/src/pages/document/stores/upload/core/StateMachineManager.js` | 上传状态机实例数量上限 | 会影响上传调度 |

真正高风险的是 `StateMachineManager.MAX_MACHINES = 200`。

## 三、根因分析

### 1. 状态机数量存在硬上限

文件：

```text
spug_web/src/pages/document/stores/upload/core/StateMachineManager.js
```

当前代码中存在：

```js
static MAX_MACHINES = 200;
```

当 `this.machines.size >= 200` 时，`create(uploadId, context)` 会尝试清理已完成任务。如果清理后仍然达到上限，则返回 `null`。

### 2. 调用方没有完整处理 `create()` 返回 `null`

文件：

```text
spug_web/src/pages/document/stores/upload/core/coordinators/FileUploadCoordinator.js
spug_web/src/pages/document/stores/upload/core/coordinators/UploadCoordinator.js
```

部分调用点只调用：

```js
this.core.stateMachineManager.create(uploadId, context);
```

但没有判断是否创建成功。

如果超过 200 后 `create()` 返回 `null`，任务虽然可能已经进入前端队列，但没有对应状态机，后续调度无法启动该任务。

### 3. 上传调度依赖状态机存在

文件：

```text
spug_web/src/pages/document/stores/upload/core/coordinators/UploadCoordinator.js
```

调度逻辑会筛选 waiting 任务：

```js
const sm = this.core.stateMachineManager?.get(item.id);
return sm && sm.canTransition('START');
```

这意味着没有状态机的任务即使在队列中，也不会被启动。

### 4. 传输列表无响应可能由前端异常触发

如果某些路径在 `create()` 返回 `null` 后继续执行：

```js
stateMachine.addListener(...)
```

则会触发空对象异常，导致上传模块局部失效，表现为传输列表点击无响应或 UI 卡住。

## 四、修复目标

修复后需要满足：

- 支持一次性选择 800、1000 甚至更多任务进入队列。
- 任务不会因为第 200 个状态机上限停止调度。
- 前端不会因为状态机创建失败导致 UI 卡死。
- 上传并发数仍然受控，例如保持 `MAX_CONCURRENT_UPLOADS = 3`。
- 任务完成、失败、取消后能及时释放状态机，避免内存持续增长。

## 五、推荐修复方案

### 方案原则

不要把“队列任务数”和“状态机实例数”绑定。

队列可以包含大量任务，但状态机只应该服务于当前正在调度、正在上传、暂停、失败重试等需要状态流转的任务。

### 阶段 1：短期止血

短期目标是避免第 200 个任务后前端直接卡死。

#### 1. 提高状态机临时上限

将：

```js
static MAX_MACHINES = 200;
```

临时调整为：

```js
static MAX_MACHINES = 1000;
```

或：

```js
static MAX_MACHINES = 2000;
```

说明：

- 这是临时止血，不是最终生产级方案。
- 单纯调大上限仍然会增加前端内存压力。
- 如果用户一次上传超过新上限，问题仍可能复现。

#### 2. 所有 `create()` 调用点必须判空

示例：

```js
const stateMachine = this.core.stateMachineManager.create(uploadId, context);

if (!stateMachine) {
  this.core.queueStore.updateUploadItem(uploadId, {
    status: 'waiting',
    error: '上传任务初始化失败，等待后续重试',
  });
  return;
}
```

如果后续有：

```js
stateMachine.addListener(...)
```

必须放在判空之后。

#### 3. 添加清晰日志

当状态机创建失败时记录：

```js
console.error('[Upload] 状态机创建失败', {
  uploadId,
  machineCount: this.core.stateMachineManager.size(),
  queueLength: this.core.queueStore.getQueueLength(tenantId),
  activeUploads: this.core.activeUploads,
});
```

### 阶段 2：生产级修复

生产级方案是状态机懒创建。

#### 1. 入队时不立即创建状态机

当前逻辑是：

1. 文件入队。
2. 立即创建状态机。
3. 等待调度启动。

建议改成：

1. 文件入队，状态为 `waiting`。
2. 不立即创建状态机。
3. 调度器准备启动该任务时，再确保状态机存在。
4. 任务完成、失败、取消后及时释放状态机。

#### 2. 新增 `ensureStateMachine(item)` 方法

建议在 `UploadCoordinator` 或独立工具中新增：

```js
ensureStateMachine(item) {
  let stateMachine = this.core.stateMachineManager?.get(item.id);
  if (stateMachine) {
    return stateMachine;
  }

  stateMachine = this.core.stateMachineManager?.create(item.id, {
    queueStore: this.core.queueStore,
    transferStore: this.core.transferStore,
    md5Store: this.core.md5Store,
    file: item.file,
    folderId: item.folderId,
    item,
  });

  if (!stateMachine) {
    console.error('[UploadCoordinator] 创建状态机失败', {
      uploadId: item.id,
      name: item.name,
      machineCount: this.core.stateMachineManager?.size?.(),
    });
    return null;
  }

  return stateMachine;
}
```

#### 3. 修改 `startWaiting()` 调度逻辑

原逻辑会排除没有状态机的 waiting 任务。

应改为：

```js
const waitingItems = queue.filter(item => item.status === 'waiting');

for (const item of waitingItems) {
  if (startedCount >= availableSlots) {
    break;
  }

  const stateMachine = this.ensureStateMachine(item);
  if (!stateMachine) {
    continue;
  }

  if (stateMachine.canTransition('START')) {
    stateMachine.transition('START');
    startedCount++;
  }
}
```

这样第 201 个之后的 waiting 任务不会因为入队阶段没有状态机而永远无法启动。

#### 4. 从入队逻辑移除批量创建状态机

文件：

```text
spug_web/src/pages/document/stores/upload/core/coordinators/FileUploadCoordinator.js
```

在 `_processBatch()` 和 `_processUniform()` 中，入队时不再立即创建状态机。

保留：

```js
this.core.queueStore.addToQueue(item, tenantId);
```

移除或改造：

```js
this.core.stateMachineManager.create(uploadId, context);
```

状态机创建统一交给调度器。

#### 5. 完成、失败、取消后释放状态机

在状态变成终态后调用：

```js
this.core.stateMachineManager.remove(uploadId);
```

终态包括：

```js
completed
error
cancelled
```

建议在 `StateChangeHandler` 中统一处理，而不是散落在多个上传路径中。

伪代码：

```js
if (['completed', 'error', 'cancelled'].includes(toState)) {
  setTimeout(() => {
    this.core.stateMachineManager?.remove(uploadId);
  }, 0);
}
```

如果 UI 需要短时间读取历史状态，可以延迟 30 到 60 秒后释放。

#### 6. 保留定时清理作为兜底

`StateMachineManager.cleanup()` 可以继续保留，但它只能作为兜底，不应该成为主要释放机制。

## 六、关键文件改动清单

| 文件 | 改动 |
| --- | --- |
| `spug_web/src/pages/document/stores/upload/core/StateMachineManager.js` | 调整上限、增强日志、保留清理机制 |
| `spug_web/src/pages/document/stores/upload/core/coordinators/FileUploadCoordinator.js` | 入队时不再批量创建状态机 |
| `spug_web/src/pages/document/stores/upload/core/coordinators/UploadCoordinator.js` | 新增 `ensureStateMachine()`，调度时懒创建状态机 |
| `spug_web/src/pages/document/stores/upload/core/lifecycle/StateChangeHandler.js` | 终态后释放状态机 |
| `spug_web/src/pages/document/stores/constants/upload.js` | 明确 `MAX_DISPLAY_COUNT` 只用于显示，不参与调度 |

## 七、兼容性注意事项

### 1. 暂停和恢复

如果任务已经有状态机，暂停和恢复沿用原状态机。

如果任务处于 `waiting` 且没有状态机，恢复时通过 `ensureStateMachine()` 创建即可。

### 2. 失败重试

失败任务如果需要支持重试，需要确认状态机是否已释放。

建议规则：

- 失败后如果允许立即重试，可以保留状态机一段时间。
- 如果用户手动重试时状态机已被释放，则重新创建。

### 3. 传输列表显示

`MAX_DISPLAY_COUNT` 只允许影响渲染数量，不允许影响上传队列或调度队列。

如果发现有代码使用 `MAX_DISPLAY_COUNT` 截断真实队列，应改为只截断显示数组。

## 八、测试建议

### 1. 单元测试

新增或调整测试：

- `StateMachineManager.create()` 超过上限返回 `null` 时调用方不崩溃。
- `UploadCoordinator.ensureStateMachine()` 能为 waiting 任务创建状态机。
- 没有状态机的 waiting 任务可以被调度启动。
- 终态任务会释放状态机。

### 2. 集成测试

构造 870 个模拟文件：

- 所有文件可以进入队列。
- 活跃上传数不超过 `MAX_CONCURRENT_UPLOADS`。
- 已完成任务释放状态机。
- 队列能从第 1 个持续调度到最后 1 个。

### 3. 浏览器手工验证

验证场景：

- 一次上传 870 个小文件。
- 一次上传 870 个混合大小文件。
- 上传过程中打开、关闭、点击传输列表。
- 暂停全部、恢复全部。
- 取消部分任务。
- 网络中断后恢复。

## 九、验收标准

修复完成后，应满足：

- 一次上传 870 个任务不会在第 200 个停止。
- 浏览器控制台没有 `Cannot read properties of null` 或状态机空对象异常。
- 传输列表可以正常打开、滚动、点击。
- 上传并发数保持受控。
- 状态机数量不会随着上传总数无限增长。
- 完成、失败、取消任务能正确释放资源。

## 十、推荐实施顺序

1. 给所有 `stateMachineManager.create()` 调用点补判空。
2. 临时提高 `MAX_MACHINES`，快速解除第 200 个任务卡死问题。
3. 在 `UploadCoordinator` 中新增 `ensureStateMachine()`。
4. 从 `FileUploadCoordinator` 入队流程中移除批量创建状态机。
5. 修改 `startWaiting()`，调度时懒创建状态机。
6. 在 `StateChangeHandler` 中处理终态释放。
7. 补充 870 个任务的集成测试和浏览器验证。

## 十一、最终建议

短期可以通过提高 `MAX_MACHINES` 和补判空止血，但生产级修复必须采用“队列无限制、状态机懒创建、终态及时释放”的设计。

这样才能支持 870 个、1000 个甚至更多任务，同时避免前端内存、状态机数量和 UI 响应性一起失控。
