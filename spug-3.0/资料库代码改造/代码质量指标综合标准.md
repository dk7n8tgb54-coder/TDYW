# 代码质量指标综合标准

## 一、基础规模指标

### 1.1 文件规模
| 指标 | 建议值 | 最大值 | 说明 |
|------|--------|--------|------|
| 文件行数 | <500行 | 1000行 | 超过需拆分模块 |
| 函数/方法数 | <20个 | 30个 | 保持单一职责 |
| 类定义行数 | <400行 | 600行 | 考虑拆分子类 |

### 1.2 函数/方法规模
| 指标 | 建议值 | 最大值 | 说明 |
|------|--------|--------|------|
| 函数行数 | <50行 | 200行 | 超过需提取子函数 |
| 参数数量 | <4个 | 6个 | 考虑使用对象封装 |
| 圈复杂度 | <10 | 15 | 条件分支过多需重构 |
| 嵌套深度 | <4层 | 5层 | 避免过深嵌套 |

## 二、命名规范指标

### 2.1 命名一致性
| 类型 | Python规范 | JavaScript规范 | 示例 |
|------|-----------|----------------|------|
| 类名 | PascalCase | PascalCase | `UploadController`, `StateMachine` |
| 函数/方法 | snake_case | camelCase | `process_upload`, `processUpload` |
| 变量 | snake_case | camelCase | `file_name`, `fileName` |
| 常量 | UPPER_SNAKE_CASE | UPPER_SNAKE_CASE | `MAX_FILE_SIZE` |
| 私有属性 | _leading_underscore | _leadingUnderscore | `_internal_state` |
| 模块/文件 | snake_case | camelCase | `upload_service.py`, `uploadService.js` |

### 2.2 命名语义化
- **动词+名词**形式：`validateInput`, `processFile`, `handleError`
- **布尔变量**使用is/has/should前缀：`isValid`, `hasPermission`, `shouldRetry`
- **集合变量**使用复数形式：`users`, `fileList`, `transferIds`
- **避免缩写**：使用`configuration`而非`config`（局部变量除外）

## 三、代码结构指标

### 3.1 单一职责原则 (SRP)
| 检查项 | 标准 | 反例 |
|--------|------|------|
| 类职责数量 | 1个主要职责 | 同时处理上传+下载+删除 |
| 函数职责数量 | 只做一件事 | 既验证又处理又保存 |
| 代码耦合度 | 低耦合 | 直接操作多个不相关模块 |

### 3.2 代码组织
```
推荐文件结构：
├── constants/          # 常量定义
├── models/            # 数据模型
├── services/          # 业务逻辑
├── controllers/       # 请求处理
├── utils/             # 工具函数
├── validators/        # 验证逻辑
├── exceptions/        # 自定义异常
└── tests/             # 测试文件
```

### 3.3 导入规范
| 检查项 | 标准 | 示例 |
|--------|------|------|
| 标准库导入 | 放在最顶部 | `import os`, `import json` |
| 第三方库导入 | 放在标准库之后 | `import django`, `import axios` |
| 本地模块导入 | 放在最后 | `from .models import File` |
| 循环导入 | 禁止 | A导入B，B又导入A |

## 四、错误处理指标

### 4.1 异常处理规范
| 检查项 | 建议 | 禁止 |
|--------|------|------|
| 异常捕获 | 捕获具体异常类型 | 裸`except:`或`except Exception:` |
| 异常日志 | 必须记录异常信息 | 静默捕获异常 |
| 错误信息 | 返回用户友好的消息 | 暴露内部错误详情 |
| 资源清理 | 使用try-finally或上下文管理器 | 不关闭文件/连接 |

### 4.2 错误处理代码比例
- **理想比例**：错误处理代码占总代码的 10-20%
- **警告阈值**：<5% 或 >30%
- **检查方式**：统计try-except-finally块数量

## 五、状态管理指标

### 5.1 状态转换规范
| 检查项 | 标准 | 说明 |
|--------|------|------|
| 状态定义 | 使用枚举而非字符串 | 避免拼写错误 |
| 状态转换验证 | 必须验证转换合法性 | 防止非法状态跳转 |
| 终态保护 | 终态不可再转换 | COMPLETED/FAILED/CANCELLED |
| 状态同步 | 前后端状态一致 | 状态变更需同步 |

### 5.2 状态机实现检查清单
- [ ] 所有状态都有明确定义
- [ ] 所有转换都有规则约束
- [ ] 终态任务有保护措施
- [ ] 批量操作有统一的状态检查
- [ ] 状态转换有日志记录

## 六、安全性指标

### 6.1 输入验证
| 检查项 | 标准 | 风险 |
|--------|------|------|
| 用户输入验证 | 必须验证 | SQL注入、XSS |
| 文件上传验证 | 验证类型、大小 | 上传恶意文件 |
| ID参数验证 | 验证存在性和权限 | 越权访问 |
| SQL参数绑定 | 使用ORM或参数化查询 | SQL注入 |

### 6.2 权限控制
| 检查项 | 标准 | 示例 |
|--------|------|------|
| 租户隔离 | 每个查询都带租户过滤 | `.filter(tenant_id=request.tenant_id)` |
| 用户权限 | 检查用户是否有操作权限 | `@permission_required` |
| 资源归属 | 验证资源属于当前用户/租户 | 删除前检查所有权 |

### 6.3 敏感信息保护
| 检查项 | 标准 | 禁止 |
|--------|------|------|
| 密码存储 | 必须加密/哈希 | 明文存储 |
| 密钥管理 | 使用环境变量或密钥管理系统 | 硬编码密钥 |
| 日志脱敏 | 敏感信息打码 | 日志中打印密码、token |
| 错误信息 | 对外返回通用错误 | 暴露堆栈跟踪 |

## 七、性能指标

### 7.1 数据库性能
| 指标 | 建议值 | 警告值 | 危险值 |
|------|--------|--------|--------|
| 单次查询返回记录数 | <100条 | 100-1000条 | >1000条 |
| 关联查询深度 | <3层 | 3-4层 | >4层 |
| N+1查询 | 禁止 | - | - |
| 查询耗时 | <100ms | 100-500ms | >500ms |

### 7.2 前端性能
| 指标 | 建议值 | 警告值 | 危险值 |
|------|--------|--------|--------|
| 组件渲染时间 | <16ms | 16-50ms | >50ms |
| 首屏加载时间 | <1s | 1-3s | >3s |
| 状态更新频率 | <60次/秒 | 60-120次/秒 | >120次/秒 |
| 内存占用增长 | 稳定 | 缓慢增长 | 快速增长 |

### 7.3 资源使用
| 检查项 | 标准 |
|--------|------|
| 数据库连接池 | 合理配置，及时释放 |
| 文件句柄 | 使用上下文管理器确保关闭 |
| 内存缓存 | 设置过期时间，避免无限增长 |
| 定时器/监听器 | 组件销毁时清理 |

## 八、可维护性指标

### 8.1 代码注释
| 检查项 | 标准 | 示例 |
|--------|------|------|
| 模块/类注释 | 必须说明职责 | `"""处理文件上传的核心类"""` |
| 公共函数注释 | 必须说明参数/返回值 | docstring格式 |
| 复杂逻辑注释 | 说明"为什么"而非"做什么" | `# 使用乐观锁防止并发覆盖` |
| 注释比例 | 10-20% | 每10行代码1-2行注释 |

### 8.2 代码重复
| 指标 | 标准 | 工具 |
|------|------|------|
| 代码重复率 | <5% | SonarQube, CodeClimate |
| 重复块行数 | 禁止>10行的重复 | - |
| 重复次数 | 相同逻辑出现>3次需提取 | - |

### 8.3 测试覆盖
| 指标 | 建议值 | 最低值 |
|------|--------|--------|
| 单元测试覆盖率 | >80% | 60% |
| 核心业务逻辑 | 100%覆盖 | 90% |
| 状态转换逻辑 | 100%覆盖 | 100% |
| 安全相关代码 | 100%覆盖 | 100% |

## 九、可读性指标

### 9.1 代码格式
| 检查项 | Python | JavaScript |
|--------|--------|------------|
| 缩进 | 4个空格 | 2个空格 |
| 行长度 | <100字符 | <100字符 |
| 空行使用 | 类/函数间2行，逻辑块间1行 | 同Python |
| 引号使用 | 字符串用单引号，docstring用三双引号 | 单引号 |

### 9.2 代码表达力
| 检查项 | 好的示例 | 差的示例 |
|--------|----------|----------|
| 布尔判断 | `if is_valid:` | `if is_valid == True:` |
| 空值判断 | `if not items:` | `if len(items) == 0:` |
| 条件表达式 | `max_size = user_max or DEFAULT_MAX` | 多行if-else |
| 列表推导 | `[f for f in files if f.valid]` | 循环append |

## 十、依赖管理指标

### 10.1 依赖数量
| 类型 | 建议 | 警告 |
|------|------|------|
| 生产依赖 | 精简，只引入必要依赖 | >50个包 |
| 开发依赖 | 分离开发/测试依赖 | 混入生产依赖 |
| 依赖深度 | 避免过深的嵌套依赖 | 深度>5 |

### 10.2 依赖安全
| 检查项 | 工具 | 频率 |
|--------|------|------|
| 漏洞扫描 | `safety check` (Python), `npm audit` | 每次构建 |
| 过期依赖检查 | `pip list --outdated`, `npm outdated` | 每周 |
| 许可证合规 | `pip-licenses`, `license-checker` | 每月 |

## 十一、综合评价体系

### 11.1 质量等级
| 等级 | 分数 | 说明 |
|------|------|------|
| A (优秀) | 90-100 | 符合所有建议指标，偶有小问题 |
| B (良好) | 80-89 | 符合核心指标，部分建议指标未达标 |
| C (合格) | 70-79 | 符合最低要求，有明显改进空间 |
| D (需改进) | 60-69 | 存在多个问题，需要重构 |
| F (不合格) | <60 | 严重问题，必须立即修复 |

### 11.2 评分权重
| 维度 | 权重 | 说明 |
|------|------|------|
| 正确性/安全性 | 30% | 功能正确，无安全漏洞 |
| 可维护性 | 25% | 易于理解和修改 |
| 性能 | 20% | 响应快速，资源高效 |
| 可读性 | 15% | 代码清晰，注释充分 |
| 测试覆盖 | 10% | 有充分的自动化测试 |
