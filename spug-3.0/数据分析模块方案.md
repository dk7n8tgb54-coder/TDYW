# 数据分析模块实施方案

> 状态：已按当前仓库代码复核，本文是实现基线。执行时以当前工作区代码为准，并保留已有未提交修改。

## 1. 审阅结论

原方案的总体方向可行：新建只读聚合 app、复用现有业务表、前端使用 `antd` + `bizcharts`、增加独立权限。但原稿不足以直接实施，以下问题必须先修正。

| 原方案问题 | 仓库事实 | 修正决定 |
|---|---|---|
| 故障“未闭合数、处理时效、故障类型”没有定义 | `FaultRecord` 没有状态、关闭时间、故障类型字段 | MVP 改为故障记录数、故障等级、所属系统、故障件状态；不伪造闭环和时效指标 |
| 设备“分类统计、在用数”没有字段依据 | `DeviceResume` 没有设备分类和“在用”字段，只有 `device_model`、`manufacturer`、`use_unit` 和 5 种 `current_status` | 展示真实状态分布、型号、厂家、使用单位；不把“正常”改名为“在用” |
| 升级“设备覆盖率”没有数据关系 | `UpgradeRecord` 只有系统、类型、计划时间、状态等字段，没有设备关联或目标设备数 | MVP 删除设备覆盖率，改为状态分布和完成率 |
| 菜单只绑定 `overview` 权限 | 用户可能只有其他分析页权限 | 菜单和页面外层使用 5 个查看权限的 OR 表达式，Tab 按权限动态生成，默认打开第一个有权 Tab |
| “复用现有统计 View”边界不清 | 干扰统计是 View；升级已有 `StatisticsService`，且现有升级统计未显式排除软删除 | 不在后端内部调用 View/HTTP；新模块直接聚合，必要时复用纯函数/Service 思路，但必须显式排除软删除 |
| 日期只有参数名，没有边界语义和校验 | 四个模块使用不同 DateTimeField，现有代码也存在 `23:59:59` 写法 | 统一严格 `YYYY-MM-DD`，使用半开区间 `[start 00:00:00, end+1day 00:00:00)`，限制跨度并返回明确错误 |
| 缓存只写“按租户” | 超级管理员/全局管理员按现有 `apply_tenant_filter` 可看全租户；若只用 `tenant_id` 会有缓存串数风险 | 缓存键加入可见范围 `all` 或 `tenant:<id>`、接口名、日期范围和版本 |
| 缺少响应结构、空数据、异常和测试约定 | 执行者需要自行猜测 | 本文补齐统一响应、各接口字段、前端状态和验收标准 |

## 2. 目标与范围

### 2.1 本期目标

- 建成一个可使用的“数据分析”主菜单页面。
- 提供总览、故障、干扰、设备、升级 5 个只读分析页。
- 所有统计由后端完成，前端只负责筛选和展示。
- 权限、租户隔离、软删除、日期边界、缓存隔离均有自动化测试。
- 桌面端和移动端均可正常查看，不出现溢出、遮挡或空白图表。

### 2.2 非目标

- 不新增业务表、model 或 migration。
- 不修改四个来源模块的业务数据，不提供 CRUD、导出、下钻明细或自定义报表。
- 不实现故障处置时效、故障闭环率、设备分类、升级设备覆盖率。这些指标缺少可靠字段，后续应先改造来源数据模型。
- 不重写现有 `/api/interference/statistics/` 和 `/api/upgrade/statistics/`，避免影响旧页面。

## 4. 数据口径

### 4.1 通用规则

1. 所有查询先构造业务 QuerySet，再调用一次 `apply_tenant_filter(queryset, request.user)`，后续聚合只基于该 QuerySet。
2. 所有来源表都排除 `is_deleted=True`。即使模型默认 manager 已过滤，也要让代码意图明确。
3. 日期参数必须同时提供或同时省略；格式严格为 `YYYY-MM-DD`。
4. 默认范围为“今天往前 364 天至今天”，共 365 个自然日；允许最大范围为 366 天。
5. 所有 DateTimeField 使用 `__gte=start_dt`、`__lt=end_dt + 1 day`，不使用 `__date`、`__startswith` 或字符串拼接 `23:59:59`。
6. 趋势统一按月返回，覆盖请求范围涉及的每个月；没有数据的月份也返回 `count: 0`。
7. 比例统一保留 1 位小数；分母为 0 时返回 `0.0`。
8. 分组字段为空字符串或 NULL 时统一显示“未填写”。高基数字段只返回前 10 项，其余合并为“其他”。
9. API 只返回聚合结果，不返回业务记录、人员姓名、故障现象、处置过程等明细或敏感文本。

### 4.2 来源字段

| 分析主题 | 模型 | 时间字段 | 核心维度 | 明确排除 |
|---|---|---|---|---|
| 设备 | `apps.device.models.DeviceResume` | `created_at` 仅用于新增趋势 | `current_status`、`device_model`、`manufacturer`、`use_unit` | `is_deleted=True` |
| 故障记录 | `apps.fault.models.FaultRecord` | `fault_date` | `fault_level`、`system_name` | `is_deleted=True` |
| 故障件 | `apps.fault.models.FaultPart` | `fault_date` | `status`、`system_name` | `is_deleted=True` |
| 干扰 | `apps.interference.models.Interference` | `datetime` | `frequency`、`interference_type`、`status`、`report_dept`、`is_reported` | `is_deleted=True` |
| 升级 | `apps.upgrade.models.UpgradeRecord` | `upgrade_time` | `status`、`upgrade_type`、`system` | `is_deleted=True` |

### 4.3 特殊口径

- 设备状态是当前快照，不受日期范围影响；“本期新增设备”及新增趋势才使用 `created_at` 日期范围。
- 设备状态必须使用模型常量对应的 5 个值：正常、故障、维修中、停用、报废。
- 故障件“已归档”指 `status == '正常归档'`；“未归档”指本期故障件中其他状态。
- 干扰“已上报”沿用当前字段口径 `is_reported == '是'`；同时单独返回结构化 `status` 分布，不混合推导两个字段。
- 升级状态必须使用 `UpgradeStatus`：处理中、已完成、已回退。完成率为 `已完成数量 / 本期升级记录总数 * 100`。
- 日期字段为 NULL 的记录不进入本期统计和趋势；设备当前快照统计不受此规则影响。

## 5. 后端设计

### 5.1 目录结构

```text
spug_api/apps/data_analysis/
├── __init__.py
├── apps.py
├── urls.py
├── views.py
├── services/
│   ├── __init__.py
│   ├── common.py          # 日期校验、范围过滤、分组格式化、月份补零
│   ├── cache.py           # 可见范围感知的缓存键与容错
│   ├── overview.py
│   ├── fault.py
│   ├── interference.py
│   ├── device.py
│   └── upgrade.py
└── tests.py
```

该 app 不创建 `models.py` 和 `migrations/`。View 只负责权限、参数解析、缓存编排和 `json_response`；ORM 聚合放在 service 中。

### 5.2 注册

- 在 `spug_api/spug/settings.py` 的 `INSTALLED_APPS` 增量加入 `'apps.data_analysis'`。
- 在 `spug_api/spug/urls.py` 增量加入：

```python
path('data-analysis/', include('apps.data_analysis.urls')),
```

说明：Django 测试客户端路径是 `/data-analysis/...`，浏览器请求路径是 `/api/data-analysis/...`。

### 5.3 API 与权限

| 浏览器请求 | Django 路径 | 后端权限 |
|---|---|---|
| `GET /api/data-analysis/overview/` | `/data-analysis/overview/` | `data_analysis.overview.view` |
| `GET /api/data-analysis/fault/` | `/data-analysis/fault/` | `data_analysis.fault.view` |
| `GET /api/data-analysis/interference/` | `/data-analysis/interference/` | `data_analysis.interference.view` |
| `GET /api/data-analysis/device/` | `/data-analysis/device/` | `data_analysis.device.view` |
| `GET /api/data-analysis/upgrade/` | `/data-analysis/upgrade/` | `data_analysis.upgrade.view` |

每个 View 使用现有 `@auth(...)`。这些新权限是独立的“聚合数据查看权”，不要求用户同时拥有来源模块的明细查看权；角色管理员应按这一含义授权。总览权限会暴露四类数据的聚合数量，但不会暴露明细。

### 5.4 查询参数与错误

所有接口只接受：

```text
start_date=YYYY-MM-DD
end_date=YYYY-MM-DD
```

校验失败时遵循项目现有协议，以 HTTP 200 返回 `json_response(error='...')`。错误至少覆盖：只传一个参数、格式错误、开始日期晚于结束日期、跨度超过 366 天。不要将解析异常或数据库异常原文返回前端。

### 5.5 缓存

- TTL：60 秒。
- 缓存键格式：`data_analysis:v1:<endpoint>:<scope>:<start>:<end>`。
- `scope` 必须与 `apply_tenant_filter` 的实际可见范围一致：超级管理员或全局管理员使用 `all`，普通用户使用 `tenant:<tenant_id>`。
- 权限校验必须先于缓存读取，避免权限撤销后仍读取缓存。
- Redis 读取或写入失败时记录 warning 并回退到实时查询，不能让统计页因缓存故障不可用。
- 缓存允许最多 60 秒的数据延迟；前端刷新仍遵循该 TTL，不提供无约束的强制绕过参数。

### 5.6 性能约束

- 使用数据库 `Count`、条件聚合、`values(...).annotate(...)`，禁止把全量模型加载到 Python 再计数。
- 对同一模型只调用一次 `apply_tenant_filter`，避免其内部审计计数被重复触发。
- 趋势优先一次 `TruncMonth` 聚合后在 Python 对缺失月份补零，禁止按天或按月循环发起 N 次查询。
- 不新增索引或 migration；现有来源表已有主要的 `tenant_id + 时间/状态` 索引。若实测慢，先记录 `EXPLAIN`，另立索引变更任务。
- 任一接口不得产生 N+1 查询，且返回体不随原始记录数量线性增长。

## 6. 响应契约

### 6.1 公共结构

成功响应仍由 `json_response(data)` 包裹。`data` 内统一包含：

```json
{
  "meta": {
    "start_date": "2025-08-04",
    "end_date": "2026-08-03",
    "timezone": "Asia/Shanghai",
    "generated_at": "2026-08-03 23:00:00"
  },
  "summary": {},
  "trends": {},
  "distributions": {}
}
```

通用数组结构：

```json
{
  "distribution": [{"name": "A", "count": 12, "percent": 60.0}],
  "monthly_trend": [{"month": "2026-01", "count": 0}]
}
```

字段名必须固定，不因空数据而省略。空数据返回零值和空数组；月份趋势仍按所选范围补零。

### 6.2 总览 `overview`

`summary`：

- `device_total_snapshot`
- `device_normal_snapshot`
- `device_fault_snapshot`
- `fault_record_count`
- `interference_record_count`
- `upgrade_record_count`
- `upgrade_completed_count`
- `upgrade_completion_rate`

`trends`：`fault_monthly`、`interference_monthly`、`upgrade_monthly`。

### 6.3 故障分析 `fault`

`summary`：`record_count`、`part_count`、`archived_part_count`、`unarchived_part_count`、`archive_rate`。

`trends`：`record_monthly`、`part_monthly`。

`distributions`：`record_by_level`、`record_by_system`、`part_by_status`、`part_by_system`。

### 6.4 干扰分析 `interference`

`summary`：`record_count`、`reported_count`、`unreported_count`、`report_rate`。

`trends`：`record_monthly`。

`distributions`：`by_type`、`by_frequency`、`by_status`、`by_report_department`。

### 6.5 设备分析 `device`

`summary`：`total_snapshot`、`normal_snapshot`、`fault_snapshot`、`repairing_snapshot`、`disabled_snapshot`、`scrapped_snapshot`、`created_in_period`。

`trends`：`created_monthly`。

`distributions`：`by_status`、`by_model`、`by_manufacturer`、`by_use_unit`。

### 6.6 升级分析 `upgrade`

`summary`：`record_count`、`in_progress_count`、`completed_count`、`rolled_back_count`、`completion_rate`。

`trends`：`record_monthly`。

`distributions`：`by_status`、`by_type`、`by_system`。

公共组件只抽取实际重复的指标网格、分布图和趋势图，不建设通用报表引擎。

### 7.2 路由和页面权限

菜单权限必须是全部 Tab 权限的 OR：

```js
const DATA_ANALYSIS_AUTH = 'data_analysis.overview.view|data_analysis.fault.view|data_analysis.interference.view|data_analysis.device.view|data_analysis.upgrade.view';
```

将该字符串用于 `routes.js` 的数据分析路由和页面最外层 `AuthDiv`。Tab 配置中逐项使用 `hasPermission` 过滤；默认激活第一个有权限的 Tab，不能硬编码 `overview`。无权 Tab 不渲染，也不请求对应 API。

在 `codes.js` 增量加入：

```js
{
  key: 'data_analysis',
  label: '数据分析',
  pages: [
    {key: 'overview', label: '总览看板', perms: [{key: 'view', label: '查看总览'}]},
    {key: 'fault', label: '故障分析', perms: [{key: 'view', label: '查看故障分析'}]},
    {key: 'interference', label: '干扰分析', perms: [{key: 'view', label: '查看干扰分析'}]},
    {key: 'device', label: '设备分析', perms: [{key: 'view', label: '查看设备分析'}]},
    {key: 'upgrade', label: '升级分析', perms: [{key: 'view', label: '查看升级分析'}]}
  ]
}
```

### 7.3 页面交互

- 顶部依次为 Breadcrumb、页面标题/刷新时间、全局日期范围和刷新按钮、Tabs。
- 默认日期与后端一致：今天往前 364 天至今天；RangePicker 禁止选择未来日期和超过 366 天的范围。
- 首次进入只请求当前 Tab；切换 Tab 时按需请求。日期确认或点击刷新后只刷新当前 Tab，已加载的其他 Tab 标记为过期，切回时再请求。
- 每个 Tab 独立维护 `data`、`loading`、`error` 和请求序号；较早请求后返回时不得覆盖新日期请求的数据。
- 加载时保留稳定布局并显示 Spin/Skeleton；失败时显示可重试的 Alert；无数据时图表区域显示 Empty，不能显示空白画布。
- API 错误已有全局 message，页面仍需保留错误态和重试入口。

### 7.4 展示要求

- 使用现有 `bizcharts` 3.5 API，不升级依赖，不引入第二套图表库。
- 指标使用响应式 `Row/Col + Statistic`；图表使用未嵌套的同级 Card，圆角不超过现有设计。
- 趋势图用折线图；低基数分布用柱状图或环图；高基数 Top 10 用横向条形图。
- 图表容器设置稳定高度和 `autoFit`，Tooltip 显示原始数量及百分比。
- 在设备页明确标注“当前状态快照”，避免用户误以为受日期筛选影响。
- 使用 `xs/sm/lg` 栅格保证 375px 手机、768px 平板和常见桌面宽度无横向溢出、文字遮挡或按钮挤压。

### 7.5 MobX 约束

- 遵循仓库 MobX 5 的 `@observable` / `@action` 风格，不使用当前版本不存在的 MobX 6 API。
- `store.js` 统一封装 5 个 `/api/data-analysis/.../` 请求和按 Tab 缓存状态。
- 页面卸载或重新进入时不得残留上一个用户的不可见 Tab 数据；权限判断始终使用当前 `hasPermission` 结果。

## 8. 实施顺序

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| P0 | 公共日期、分组、缓存工具及其单元测试 | 参数边界、月份补零、百分比、缓存 scope 测试通过 |
| P1 | 后端 5 个接口及权限/租户/软删除测试 | 所有 API 契约测试通过，空数据稳定 |
| P2 | 前端入口、权限 Tab、全局日期和 store | 不同权限组合进入正确 Tab，只请求有权接口 |
| P3 | 总览与 4 个专题页图表 | 指标与接口一致，加载/失败/空状态完整 |
| P4 | 全量验证与文档回填 | 后端测试、前端测试/构建、桌面与移动端人工或浏览器验证通过 |

## 10. 测试与验收

### 10.1 后端自动化测试

至少覆盖：

1. 5 个接口各自的有权成功和无权拒绝。
2. 普通用户只能统计自己租户；普通租户之间不串数。
3. 按现有产品规则，超级管理员和全局管理员可统计全租户。
4. 缓存键区分 `all` 与 `tenant:<id>`，不能用相同 `tenant_id` 造成权限范围碰撞。
5. 所有软删除数据均不计入。
6. 起止日均包含，范围外和日期 NULL 的记录排除。
7. 参数缺半边、非法日期、反向日期、超过 366 天均返回稳定错误。
8. 空库时字段完整、计数和比例为 0、趋势月份补零。
9. 各状态、分组、Top 10 + 其他、完成率和归档率口径正确。
10. Redis 异常时回退实时查询。

## 11. 上线与回退

- 本模块无数据库迁移，部署顺序可先后端再前端。
- 上线后为角色显式分配新的 `data_analysis.*.view` 权限；未授权用户不会看到菜单。
- 观察 5 个接口的耗时、数据库慢查询和 Redis 异常日志。若 60 秒缓存下仍慢，再基于 `EXPLAIN` 评估索引。
- 回退时移除前端菜单/页面入口和后端 URL/app 注册即可；不会影响来源数据。
