# 资料库上传模块重构方案

## 重构日期
2026-06-06

## 一、目标与原则

### 1.1 重构目标
解决 P0 双轨制架构问题，统一"普通上传"和"文件夹上传"两条并行的代码路径，消除技术债务。

### 1.2 工程原则（指导本次重构）
- **SOLID**：单一职责、开闭原则、依赖倒置
- **关注点分离**：UI 层、协调层、领域层、基础设施层清晰分层
- **渐进式重构**：每次改动不破坏现有功能，可以分阶段合并
- **测试驱动**：先写测试验证领域规则，再实现
- **YAGNI**：只实现当前需要的功能，不做过度抽象

### 1.3 不做什么
- ❌ 不引入新框架/库
- ❌ 不做"全面重写"（风险太大）
- ❌ 不强行追求"完美架构"（架构是演进出来的）

---

## 二、当前问题诊断

### 2.1 双轨制架构（P0）
```
普通上传：FileUploadCoordinator → StateMachine → upload
文件夹上传：FolderUploadStore → 直接调用 uploadFileToFolder
```

### 2.2 已识别的具体问题
| ID | 等级 | 位置 | 问题 |
|----|------|------|------|
| P1-1 | 🔴 高 | `core/index.js:370-392` | `destroy()` 未调用 `folderUploadStore.destroy()`，事件监听器泄漏 |
| P1-2 | 🔴 高 | `folderUpload.js:178-179` | `_initUploadState` 无条件重置 `isPaused/isCancelled`，暂停按钮失效 |
| P1-3 | 🟡 中 | `folderUpload.js:230` | 双重 rootStore 访问链，引用关系脆弱 |
| P2-1 | 🟡 中 | `folderUpload.js:444` | 进度按文件数计算，不按字节加权 |
| P2-2 | 🟡 中 | `folderUpload.js:567` 行 | 单一类承担 8+ 职责，违反 SRP |
| P2-3 | 🟢 低 | `uploadFileToFolder:241` | 重复创建传输记录风险（与 Coordinator 重复） |
| P0-1 | 🔴 高 | 整体架构 | 双轨制，行为不一致 |

## 三、重构方案

### 3.1 总体策略

**分三个阶段，每阶段独立可发布**：

```
阶段 1（立即）：修复 3 个 P1 风险（最小改动，最大安全收益）
    ↓
阶段 2（短期）：拆分 FolderUploadStore，按职责分离
    ↓
阶段 3（中期）：引入 UploadBatch 抽象（如果阶段 2 暴露有这个必要）
```

**关键决策**：不直接做阶段 3，先看阶段 1+2 之后的代码是否仍然需要抽象层。

#### 修复 1.2：暂停失效
**文件**: `spug_web/src/pages/document/stores/upload/core/folderUpload.js`

**当前** (第 178-179 行):
```javascript

this.rootStore.isCancelled = false;
```

**问题**: 每次文件夹选择都重置全局暂停标志，覆盖用户的"全部暂停"操作。

**修复**: **不重置全局标志**。改为在循环内检查局部状态。
```javascript
// 移除无条件重置
// this.rootStore.isPaused = false;  // ❌ 删除
// this.rootStore.isCancelled = false;  // ❌ 删除
```

**注意**: 旧逻辑重置是为确保新批次上传能开始。改为：上传开始后由 `UploadCoordinator` 自然启动（已有机制），无需手动重置全局标志。

#### 修复 1.3：双重 rootStore 访问
**文件**: `folderUpload.js` 第 230 行

**当前**:

**问题**: `this.rootStore` 已是 `uploadCoreStore`，再访问 `rootStore` 是它的 rootStore。依赖 `uploadCoreStore.rootStore` 字段赋值时序。

**修复**: 改用 NavigationStore 的代理方法（如有）或添加安全检查
```javascript
// 在 UploadCoreStore 中添加清晰的代理方法
getUploadTargetFolderId() {  // 已有，见 core/index.js:265
  return this.rootStore.navigationStore?.getUploadTargetFolderId?.() || null;
}
```

实际已经存在，folderUpload 调用方式可简化为：
```javascript

const isPublic = this.rootStore.rootStore?.navigationStore?.isPublic;
```

### 3.3 阶段 2：拆分 FolderUploadStore（3-5 天）

```
    ├── FolderUploadBatchFactory（构造上传批次）
```


#### 步骤 2.2：复用 FileUploadCoordinator
**关键决策**: 不创建新的 `BatchExecutor` 抽象层。

**原因**（YAGNI）:
- 当前 `FileUploadCoordinator.processUploadQueue(files, folderId)` 只支持统一 `folderId`
- 文件夹上传需要每个文件有自己的 `targetFolderId`
- **直接修改 processUploadQueue 接受 `items: [{file, folderId}]`** 比创建新抽象更简单

**修改**: `FileUploadCoordinator.js:71`

```javascript
// 之前
async processUploadQueue(files, folderId) { ... }

// 之后（保持向后兼容）
async processUploadQueue(files, folderId = null) {
  // 检测是否为新格式
  if (Array.isArray(files) && files.length > 0 && files[0]?.file) {
    // 新格式：[{file, folderId}, ...]
    return this._processBatch(files);
  }
  // 老格式：files, folderId（普通上传）
  return this._processUniform(files, folderId);
}

async _processBatch(items) {
  // items: [{file, folderId, folderPath?}, ...]
  // 复用现有逻辑，但每个 item 有自己的 folderId
}

async _processUniform(files, folderId) {
  // 现有逻辑
}
```

## 四、风险评估

### 4.1 阶段 1 风险（低）
- `destroy()` 修复是单纯的资源清理，不影响功能
- `isPaused` 重置删除需要测试"上传中暂停"场景
- `getUploadTargetFolderId` 已有相同实现，简化调用是安全的

### 4.2 阶段 2 风险（中）
- `FileUploadCoordinator.processUploadQueue` 接口扩展需要兼容老调用方
- 文件夹上传的行为可能与 Coordinator 默认行为有微妙差异
- 需要大量回归测试

### 4.3 缓解措施
- **每阶段独立 PR**，不合并到主分支前充分测试
- **保留老代码路径**（feature flag），可快速回滚
- **逐步灰度**：先 10% 用户使用新代码，观察 1 周

## 八、总结

本次重构采用 **"渐进式 + 实用主义"** 策略：

1. **阶段 1 立即修复 P1 风险**（内存泄漏、暂停失效、双重 rootStore 访问）
2. **阶段 2 拆分职责**，让 `FolderUploadStore` 变薄
3. **阶段 3 按需引入抽象层**，避免 YAGNI

**核心原则**：
- 不追求"完美架构"，追求"够用、可演化"
- 每次改动独立可发布
- 代码可读性优先于 DRY
- 测试驱动 + 回归验证
