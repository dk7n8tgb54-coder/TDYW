## 登录安全设计

登录接口位于 `spug_api/apps/account/views.py` 的 `login()` 函数，已实现多层防护，**不需要额外添加静态图验证码**。

### 现有防护层

| 防护层 | 机制 | 位置 |
|------|------|------|
| **IP 限流** | 30 次/小时/IP，防止分布式暴力破解 | `views.py:441-445` |
| **用户锁定** | 5 次/15 分钟后锁定，防止针对性攻击 | `views.py:447-453, 468-478` |
| **强密码策略** | 至少 8 位，必须包含数字+小写+大写+特殊字符 | `views.py:117-119, 171-173` |
| **审计日志** | 登录失败写审计日志 + 登录历史，含 IP/UA | `views.py:483-513` |

### 安全性测算

- 用户级限流：5 次/15 分钟 = 一天最多 480 次尝试
- 强密码空间：8 位（数字+大小写+特殊字符）≈ \(62^8 \approx 2 \times 10^{14}\)
- 按当前限流速度暴力破解所需时间：约 \(4 \times 10^{11}\) 天

**结论**：在现有 IP 限流 + 用户锁定 + 强密码 + 审计的组合下，暴力破解不可行，防护强度已超过静态图验证码。

### 为什么不加静态图验证码

1. **OCR 识别率高**：普通静态图验证码对现代 OCR 几乎无防护，只能挡最原始的脚本
2. **每次都加伤体验**：内网运维平台用户登录频率不低，每次输验证码是纯摩擦
3. **挡不住撞库**：撞库使用真实密码字典，验证码挡不住——限流+锁定才挡得住
4. **可被人工打码绕过**：低成本打码平台 1 分钱一条
5. **项目是内网部署**（docker-compose），不在静态图验证码适用的"公网暴露无 WAF"场景

### 现有 captcha 字段的说明

登录接口已接受 `captcha` 参数并校验 `{username}:code` 缓存（`views.py:433, 466, 517-528`），前端 `login/index.js` 也有"获取验证码"输入框。但这是 **MFA（邮件/推送验证码）的残留代码**，不是图片验证码：
- 前端是"获取验证码"按钮 + 倒计时 + MailOutlined 图标，对应邮件/推送验证码
- 后端 `views.py:534` 明确写着"推送服务已移除，MFA认证不可用"
- 这段代码当前处于废弃状态

### 如果未来真要加验证码

推荐**按需验证码**（失败 N 次后才要求）优于"每次都加"。后端基础设施已就绪，缺的只是：
1. 一个生成验证码图片的接口
2. 前端在 `user_fails >= 3` 时展示验证码
3. 后端在 `user_fails >= 3` 时强制校验 captcha

但当前限流已经够用，按 YAGNI 原则不预先做。如果未来限流被证明不够用，再考虑按需验证码或滑块/行为验证。
