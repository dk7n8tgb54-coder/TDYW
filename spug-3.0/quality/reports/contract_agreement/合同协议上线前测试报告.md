### DEF-01 [P1·阻断] 附件接口缺少模块归属校验，同租户跨模块越权（下载/删除/预览）

- **端点**：`GET /api/contract-agreement/attachments/{id}/download/`、`DELETE /api/contract-agreement/attachments/?id=`、`GET /api/contract-agreement/attachments/{id}/preview-url/`
- **复现**：持有 `contract_agreement.attachment.download`（或 delete）权限的普通用户，将 URL 中附件 ID 替换为同租户其他模块（如 upgrade 台账、radio_license 执照）的附件 ID。
  - 操作者：qa_full（普通用户，admin 租户，仅有合同协议权限）；目标：upgrade 模块附件（同租户）。
  - 实际结果：下载返回 200 + 文件流（`application/octet-stream`）；删除返回成功且附件被软删除；preview-url 可为其他模块附件生成预览令牌。
  - 预期结果：返回业务错误「附件不存在或无权限访问」，且不得产生任何副作用。
- **根因**：`views.py:429/475/446` 调用 `AttachmentService.download_response/soft_delete/get_preview_url` 时未按 `module='contract_agreement'` 过滤；`attachment_service.py:302-304` 只按租户过滤。对照正确实现：`coop_task/views.py:981` 先按 `module=ATTACHMENT_MODULE` 过滤再放行。
- **影响范围**：附件 ID 为自增整数，可枚举。拥有合同附件权限的用户可读取/删除同租户内任意模块的附件（执照、批复、规章、升级记录等）。**radio_license、interference 模块存在同类问题（超出本模块范围，建议另立工单）**。
- **证据**：`test_cross_module_attachment_access_rejected`、`test_cross_module_attachment_delete_rejected`（stable_contract，FAIL）；跨租户附件访问/删除用例通过（租户隔离本身正常）。
- **[2026-09-03 已修复]** ①radio_license（执照+批复，用户修复，`_get_license/approval_attachment_for_user` 归属校验 + 删除前快照，42 项附件测试验证）；②contract_agreement 三入口增加 `_get_contract_attachment_for_user`（下载/删除复用校验结果，审计不再无差别重查）；③interference 三入口增加 `_get_interference_attachment_for_user`（附件行级校验，兼容临时 UUID 上传模式；顺带修复删除后查询必为 None 的证据事件死代码）。home/announcement 复核确认自带模块过滤，无需修改。共性规则与范式已沉淀至 `spug_api/AGENTS.md`「附件接口归属校验（防跨模块越权）」，interference 新增 5 项归属校验稳定契约用例。

### DEF-02 [P1·阻断] 编辑接口信任客户端伪造的 responsible_user_name

- **端点**：`POST /api/contract-agreement/`（携带 id 走编辑分支）
- **复现**：对已有合同（责任人 qa_full）提交 `{"id": <pk>, "responsible_user_name": "伪造姓名"}`（不传 responsible_user_id）。
  - 操作者：qa_full（有编辑权限，admin 租户）。实际结果：200 成功，数据库 `responsible_user_name` 变为「伪造姓名」。预期结果：保持原值（姓名只能由服务端根据 responsible_user_id 回填）。
- **根因**：`views.py:288-291` 仅在 `responsible_user_id is not None` 时校验回填，但 `views.py:293-295` 的 `update_data` 无条件采纳客户端传入的 `responsible_user_name`。创建路径已正确回填（`views.py:87`）。
- **影响范围**：列表/详情/提醒弹窗展示的责任人姓名可被任意伪造，误导追责与提醒触达（提醒按 `responsible_user_id` 过滤，姓名展示不一致）。任务要求「responsible_user_name 必须由服务端根据真实用户信息回填，不能信任客户端伪造值」。
- **证据**：`test_partial_edit_must_not_forge_responsible_user_name`（FAIL）；`test_responsible_user_name_is_server_filled`（创建路径，PASS）。
- **[2026-09-03 已修复]** 编辑路径的 `update_data` 不再采纳客户端传入的 `responsible_user_name`，仅当 `responsible_user_id` 校验通过后写入 `_validate_and_fill_responsible_user` 回填的服务端值。测试复测通过。

### DEF-03 [P1·阻断] 即将到期（未过期）合同的提醒无法确认处理，每日反复弹出

- **端点**：`GET /api/contract-agreement/reminders/popup/` + `POST /api/contract-agreement/reminders/ack/`
- **复现**：创建 `valid_end_date = 今天+15 天`、责任人为当前用户的合同。弹窗接口返回该合同（`remind_type=expiring_daily`）；点击「已处理」调用 ack。
  - 操作者：qa_full（admin 租户，合同责任人）。实际结果：ack 返回 `{"acked": false, "message": "当前合同无需提醒"}`，未落确认记录；刷新后提醒再次弹出（E2E CA012 实测：Expected 0, Received 1）。预期结果：`acked: true`，落 `ContractAgreementReminderAck`，此后不再弹出。
- **根因**：`views.py:551-553` 仅在 `calculate_agreement_status` 为 `expired`（已过截止日）时才写确认记录，而弹窗按 60 天窗口返回未过期合同（`views.py:500-503`）；`tasks.py:38-40` 在未过期时恒返回 `normal`。前端 `ContractAgreementReminderNotification.js:101` 对 `acked:false` 无感知（`finally` 直接关通知），用户以为已处理。
- **影响范围**：到期提醒功能对「即将到期」这一主场景完全失效——60 天窗口内每天登录都会重新弹出，且「今日不再提醒」仅本地当日生效。已过期合同（days_left<0）的确认路径正常（幂等、续期失效逻辑均通过）。
- **证据**：`test_ack_expiring_contract_within_threshold`（FAIL）；E2E CA012（FAIL，截图 `e2e-artifacts/*CA012*/`）。
- **[2026-09-03 已修复]** 经产品确认两态为错误设计（合同协议应对齐执照/批复的三态，见第九节），三态改造后 ack 的 `status == 'normal'` 门槛逻辑未改动即自然修复；上述测试与 E2E CA012 复测通过。

### DEF-04 [P2] 局部编辑静默重置 has_fee / fee_detail / remark

- **端点**：`POST /api/contract-agreement/`（编辑分支）
- **复现**：对 `has_fee=true, fee_amount=6666, fee_detail='原明细', remark='原备注'` 的合同提交 `{"id": <pk>, "remark": "只改备注"}`。
  - 实际结果：`has_fee` 被重置为 `false`，`fee_detail` 被清空（remark 更新为目标值）。预期结果：仅 remark 变更，其余字段保持原值。
- **根因**：`views.py:233-239` 中 `has_fee` 默认 `False`、`fee_detail`/`remark` 默认 `''`（非 None），`views.py:293` 按「非 None 即更新」组装 `update_data`，与 `_post_edit` 注释声明的「只更新传入的非 None 字段」契约冲突。
- **影响范围**：当前前端表单为全量提交，UI 路径不受影响；但 API 契约层面的部分更新会导致调用方静默丢失费用信息（数据完整性风险）。
- **证据**：`test_partial_edit_must_not_reset_fee_fields`（FAIL）；`test_edit_full_payload_preserves_fee`（全量提交，PASS）。
- **[2026-09-03 已修复]** `has_fee`/`fee_detail`/`remark` 的 JsonParser 默认值改为 None（未传即不更新），显式传空串/False 仍可清空。测试复测通过。

### DEF-05 [P2] 超长字段无服务端校验，触发未处理异常（HTTP 500 + 告警）

- **端点**：`POST /api/contract-agreement/`（新增）
- **复现**：分别提交 `contract_name` >200 字、`contract_no` >100 字、`signing_party` >500 字（数据库列宽分别为 varchar(200)/(100)/(500)，sql_mode 为 STRICT_TRANS_TABLES）。
  - 实际结果：未处理异常，响应 `{"error": "服务器内部错误，请联系管理员"}`，且触发 `[ALERT][ERROR] API 异常` 告警（日志可证）。预期结果：返回字段级业务错误（如「合同名称不能超过 200 字」）。
- **根因**：`_validate_form`（`views.py:120-167`）无长度校验，直接落库触发 DataError。
- **影响范围**：用户粘贴超长文本即触发 500 与告警噪音；错误文案无法定位字段。三字段均复现。
- **证据**：`test_create_overlong_fields_rejected`（FAIL）；`logs/backend_tests_*.log` 中 `Unhandled exception on POST /contract-agreement/` + `ERROR [ALERT][ERROR] API 异常` 记录。
- **[2026-09-03 已修复]** 新增 `FIELD_LENGTH_LIMITS`（200/100/500，与列宽对齐）+ `_validate_field_lengths`，创建与编辑双路径前置校验，返回字段级业务错误。测试复测通过（无告警触发、无 1406 暴露）。

### DEF-06 [P2] 列表 status 过滤口径与展示口径不一致

- **端点**：`GET /api/contract-agreement/?status=expired`
- **复现**：合同创建时截止日期在未来（DB `status=normal`），随后时间越过截止日期但每日 8:10 的 Celery 扫描尚未执行。此时列表展示该合同为「已关闭」（实时计算，`views.py:98/106-108`），但 `status=expired` 过滤查不到它（按 DB 列过滤，`views.py:194-195`）。
  - 实际结果：`status=expired` 过滤命中 {已扫描的过期合同}，漏掉未扫描的。预期结果：与展示口径一致，命中全部已到期合同。
- **影响范围**：每日扫描前的最长窗口内（最长约 24 小时），「已关闭」筛选结果不完整，用户以为无过期合同。
- **证据**：`test_status_filter_matches_computed_status`（FAIL）；`test_filter_status_normal_and_expired`（扫描后口径，PASS）。
- **[2026-09-03 已修复]** 列表 status 过滤已改为按 `valid_to` 实时范围过滤（范式同批复 `_apply_approval_status_filter`，不再依赖 Celery 落库的 status 列），`test_status_filter_matches_computed_status` 复测通过。

### DEF-07 [P3] 前端同一错误弹出两次提示

- **场景**：新建合同触发业务错误（如 30 秒幂等拒绝）时，`libs/http.js` 拦截器 `showErrorOnce` 已弹出「操作过于频繁，请勿重复提交相同合同」，`Form.js:64-66` 的 `catch` 中 `e.message` 为 undefined（reject 的是字符串），再弹「操作失败，请稍后重试」。
