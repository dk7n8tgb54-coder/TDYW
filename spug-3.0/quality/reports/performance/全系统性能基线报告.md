### 2.2 冷缓存 vs 热缓存

| 端点 | 冷缓存 (ms) | 热缓存平均 (ms) | 缓存效果 |

**观察**：
- `data_analysis` 和 `notices` 显示明显的缓存效果（~48% 提升），符合 60 秒 Redis 缓存设计
- `navigation` 冷热缓存差异不大，可能已使用 Django 内存缓存或查询本身就很快
- `account_users` 即使热缓存也较慢（57.6ms），可能存在 N+1 查询或 JOIN 过多

## 六、环境异常说明

以下因素可能影响测试结果，不应归咎于应用：

1. **CONN_MAX_AGE=0**：每个请求新建数据库连接，实际生产环境可能使用连接池
2. **dev 数据库数据量**：dev 环境数据量可能小于生产环境
3. **Docker 资源限制**：容器 CPU/内存限制可能影响性能
4. **WSL 网络层**：WSL → Windows 网络转发可能增加延迟
5. **单请求探测**：无并发，无法发现并发相关问题

## 七、结论与建议

### 7.1 当前状态

- 系统在单请求场景下响应迅速（大部分 <25ms）
- 缓存机制有效（data_analysis 冷热缓存差异 48%）
- 两个端点需要路径修正（doc_files, faults）
- alerts 端点存在周期性慢请求，需进一步调查
- account_users 端点比其他列表慢 3x，可能需要查询优化

### 7.2 建议

1. **建立独立测试环境**：创建 test_spug 数据库，安装 Locust，执行完整负载测试
2. **调查 alerts 慢请求**：检查是否与 Beat 任务（check_disk_usage, check_db_status）竞争
3. **优化 account_users 查询**：检查是否存在 N+1，添加 select_related
4. **修正端点路径**：faults 路径应为 /api/fault/faultrecord/
5. **在独立环境中执行峰值和持续测试**：建立真实基线后设定阈值
6. **启用慢查询日志**：在测试环境中开启 MariaDB slow_query_log
7. **监控 Redis 命中率**：在负载测试时监控缓存效果
