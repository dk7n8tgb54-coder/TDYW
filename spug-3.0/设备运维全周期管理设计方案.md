# 设备运维全周期管理设计方案

> 编写日期：2026-07-10  
> 模块名称：设备运维全周期管理  
> 推荐英文模块名：device_lifecycle 或在现有 `device` 模块下扩展  
> 参照模块：设备履历、故障管理、检查单、合同协议、公共附件能力

## 一、结论

建议将“设备运维全周期管理”建设为现有设备管理能力的升级版，而不是完全另起一个孤立模块。

现有项目已经有 `DeviceResume` 设备档案、`DeviceEvent` 设备履历事件、故障管理、检查单、附件、导出、审计日志等基础能力。首期应保留现有设备台账入口，在其下扩展采购入库、安装调试、日常巡检、故障处理、维修保养、报废注销六类生命周期业务，最终形成：

```text
设备管理
  - 设备台账
  - 采购入库
  - 安装调试
  - 巡检计划
  - 巡检任务
  - 故障报修
  - 维修保养
  - 报废注销
  - 设备履历
```

整体设计应坚持三个原则：

1. 设备台账只保存设备当前基础信息和当前状态。
2. 采购、安装、巡检、故障、保养、报废等过程数据保存到独立业务表。
3. 所有关键业务动作同步写入设备履历事件，支持单台设备全生命周期追溯。

## 二、建设目标

本模块面向运维单位、管制部门、部门负责人、技术委员会、上级审批人员等角色，覆盖设备从采购入库到报废归档的完整过程。

建设目标包括：

- 建立统一设备台账，形成唯一设备编号和状态流转。
- 支持采购合同、质检报告、安装图片、调试报告、保养报告、技术鉴定报告等附件归档。
- 支持 Excel 批量导入和单条手动录入。
- 支持安装调试、验收审核、故障派单、结案确认、报废审批等流程。
- 支持巡检计划、巡检任务、扫码打卡、运行参数采集、异常分级预警。
- 支持保养计划、保养执行、下次保养提醒。
- 支持设备履历时间线、状态变更记录、责任人追踪、导出归档。

## 三、业务边界

### 3.1 首期纳入范围

| 业务环节 | 首期能力 | 说明 |
|---|---|---|
| 采购入库 | 台账录入、批量导入、附件、编号生成、状态变更 | 入库后状态为待安装 |
| 安装调试 | 安装记录、调试记录、图片和报告上传、验收申请、审核 | 审核通过后状态为正常运行 |
| 日常巡检 | 计划配置、任务生成、扫码打卡、参数录入、异常预警 | 支持 PC 和移动端表单 |
| 故障处理 | 报修、派单、维修过程、配件更换、结案确认 | 流程闭环后更新状态和故障台账 |
| 维修保养 | 保养计划、实施记录、报告上传、下次提醒 | 覆盖定期保养和专项保养 |
| 报废注销 | 报废申请、鉴定、审批、处置方式、归档 | 报废后设备不可再发起常规运维 |

### 3.2 不建议首期过度扩展

以下能力建议作为二期或三期建设：

- 复杂备件库存管理。
- 维修费用核算和财务对账。
- 设备 IoT 自动采集和实时监控大屏。
- 离线移动端巡检缓存。
- 电子签章和正式公文流转。
- 与外部资产管理系统双向同步。

## 四、设备状态设计

现有设备状态为“正常、故障、维修中、停用、报废”。全周期管理需要更细的过程状态，建议增加一个独立字段 `lifecycle_status`，避免直接破坏现有 `current_status` 的兼容逻辑。

### 4.1 状态枚举

| 状态编码 | 状态名称 | 触发场景 |
|---|---|---|
| `pending_install` | 待安装 | 采购入库完成 |
| `installing` | 安装调试中 | 开始安装或调试 |
| `acceptance_pending` | 待验收 | 调试合格后提交验收 |
| `running` | 正常运行 | 验收审核通过 |
| `fault` | 故障 | 故障报修或巡检异常确认为故障 |
| `repairing` | 维修中 | 运维单位接单并派工 |
| `maintenance` | 保养中 | 开始保养任务 |
| `stopped` | 停用 | 人工停用或长期不可用 |
| `scrap_pending` | 报废审批中 | 提交报废申请 |
| `scrapped` | 已报废 | 报废审批完成 |

### 4.2 与现有状态兼容

建议保留现有 `DeviceResume.current_status`，用于列表快速筛选和兼容旧页面；新增 `lifecycle_status` 表示更细的生命周期状态。

映射关系如下：

| `lifecycle_status` | `current_status` |
|---|---|
| `pending_install`、`installing`、`acceptance_pending` | 停用 |
| `running` | 正常 |
| `fault` | 故障 |
| `repairing`、`maintenance` | 维修中 |
| `stopped` | 停用 |
| `scrap_pending`、`scrapped` | 报废 |

页面展示时优先展示 `lifecycle_status_display`，旧导出或旧统计仍可使用 `current_status_text`。

### 4.3 状态流转

```text
采购入库
  -> 待安装
  -> 安装调试中
  -> 待验收
  -> 正常运行
  -> 故障 / 维修中 / 保养中 / 停用
  -> 正常运行
  -> 报废审批中
  -> 已报废
```

状态流转必须由业务动作触发，不建议允许用户直接在设备编辑表单里随意修改生命周期状态。

## 五、功能设计

### 5.1 采购入库

采购入库用于建立设备初始档案，是生命周期起点。

功能点：

- 支持单条录入和 Excel 批量导入。
- 录入设备名称、型号、规格、供应商、采购日期、技术参数、采购金额、质保期限等信息。
- 上传采购合同、质检报告、到货验收单等附件。
- 系统生成唯一设备编号。
- 入库完成后自动创建设备台账，状态更新为“待安装”。
- 自动写入设备履历事件“采购入库”。

设备编号建议规则：

```text
设备类型编码 + 年月 + 4 位流水号
示例：RAD-202607-0001
```

编号规则需要支持配置，至少包含：

- 前缀。
- 年月格式。
- 流水号长度。
- 是否按设备类型分组递增。

Excel 导入策略：

- 提供标准模板下载。
- 导入前执行字段校验、重复编号校验、枚举值校验。
- 导入结果返回成功数、失败数、失败行号和失败原因。
- 导入成功的数据统一写入设备履历。

### 5.2 安装调试

安装调试用于记录设备从入库到可运行的现场过程。

功能点：

- 记录安装位置，精确到空管区域、机房、机柜、机位。
- 记录安装时间、安装单位、调试人员、调试步骤、调试结果。
- 支持移动端拍照上传现场安装图片。
- 支持上传调试报告。
- 调试合格后提交验收申请。
- 部门负责人审核通过后，设备状态更新为“正常运行”。
- 审核驳回后退回安装调试环节，补充整改说明。

验收流程：

```text
安装人员提交验收申请
  -> 部门负责人审核
  -> 审核通过：设备状态=正常运行
  -> 审核驳回：设备状态=安装调试中
```

验收记录需要保留审核人、审核时间、审核意见和附件快照。

### 5.3 日常巡检

日常巡检用于按照设备类型和区域生成周期性任务。

功能点：

- 预设巡检计划，支持每日、每周、每月。
- 支持按设备类型、设备区域、设备级别配置巡检频次。
- 支持配置巡检项目模板，例如电压、信号强度、外观状态、环境温湿度、线缆连接状态。
- 系统按计划生成巡检任务。
- 巡检人员通过 PC 或移动端接收任务。
- 到现场后扫码打卡，确认巡检地点。
- 录入运行参数、外观状态、异常情况、现场图片。
- 巡检记录自动关联设备台账和设备履历。
- 异常情况实时上报并触发分级预警。

异常等级：

| 等级 | 编码 | 处理建议 |
|---|---|---|
| 一般 | `normal` | 记录异常，通知设备负责人 |
| 重要 | `important` | 通知设备负责人和部门负责人，可转故障 |
| 紧急 | `urgent` | 立即推送负责人，建议自动生成故障报修 |

巡检异常闭环建议：

```text
巡检发现异常
  -> 选择异常等级
  -> 一般：生成异常记录，责任人确认
  -> 重要/紧急：生成预警，可一键转故障报修
  -> 处理完成后关闭异常
```

扫码打卡建议：

- 每台设备生成二维码，内容包含设备 ID、设备编号、租户 ID 防篡改签名。
- 移动端扫码后打开巡检填报页面。
- 后端校验当前任务是否包含该设备。
- 可选记录 GPS 或机房区域，但不强依赖定位。

### 5.4 故障处理

故障处理用于从报修到维修闭环。

功能点：

- 管制部门或运维人员发起故障报修。
- 填写故障设备编号、故障描述、影响范围、紧急程度、发现时间。
- 支持上传故障现场图片。
- 运维单位接收派单。
- 分配维修人员。
- 记录故障排查过程、原因分析、解决方案。
- 记录更换配件型号、数量、序列号。
- 维修完成后提交结案申请。
- 报修方确认无误后流程闭环。
- 系统自动更新设备状态和故障台账。

故障流程：

```text
故障报修
  -> 待派单
  -> 已派单
  -> 维修中
  -> 待确认
  -> 已结案
```

设备状态联动：

| 故障单状态 | 设备状态 |
|---|---|
| 待派单、已派单 | 故障 |
| 维修中 | 维修中 |
| 已结案且报修方确认 | 正常运行 |

若故障无法修复，可从故障单发起报废申请，进入报废注销流程。

### 5.5 维修保养

维修保养用于周期性维护和专项维护。

功能点：

- 制定设备保养计划。
- 保养类型包括定期保养和专项保养。
- 配置保养周期、保养项目、责任人、提前提醒天数。
- 系统生成保养任务和到期提醒。
- 保养实施后录入保养时间、保养人员、保养内容、检测数据。
- 上传保养报告和相关凭证。
- 保养完成后更新设备维护记录。
- 自动生成下次保养提醒。

保养计划字段建议：

| 字段 | 说明 |
|---|---|
| 保养计划名称 | 如“导航设备季度保养” |
| 适用设备范围 | 按设备类型、区域或指定设备 |
| 保养类型 | 定期保养、专项保养 |
| 周期 | 每月、每季度、每半年、每年、自定义天数 |
| 保养项目 | 可复用模板 |
| 责任人 | 默认处理人 |
| 提前提醒天数 | 默认 7 天 |
| 是否启用 | 停用后不再生成任务 |

保养完成后应写入设备履历事件“维修保养”，并保存下次计划时间。

### 5.6 报废注销

报废注销用于处理达到使用年限或无法修复的设备。

功能点：

- 运维单位提交报废申请。
- 填写报废原因、设备现状、无法修复说明、建议处置方式。
- 上传技术鉴定报告、报废原因说明等附件。
- 经部门审核、技术委员会鉴定、上级审批后完成注销。
- 记录处置方式：回收、销毁。
- 设备状态更新为“已报废”。
- 历史运维数据保留归档。
- 已报废设备不可再创建巡检、故障、保养任务。

报废流程：

```text
报废申请
  -> 部门审核
  -> 技术委员会鉴定
  -> 上级审批
  -> 处置登记
  -> 已报废
```

已报废设备的数据处理规则：

- 不允许物理删除设备台账。
- 不允许删除历史巡检、故障、保养、报废附件。
- 列表默认隐藏已报废设备，但提供筛选入口。
- 设备履历仍可查看和导出。

## 六、数据模型设计

### 6.1 设备主表扩展

在现有 `tdyw_device_resume` 基础上建议增加以下字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `lifecycle_status` | varchar(30) | 是 | 生命周期状态 |
| `device_type` | varchar(50) | 否 | 设备类型 |
| `specification` | varchar(200) | 否 | 规格 |
| `supplier` | varchar(200) | 否 | 供应商 |
| `purchase_date` | varchar(20) | 否 | 采购日期 |
| `warranty_end_date` | varchar(20) | 否 | 质保截止日期 |
| `technical_params` | text/json | 否 | 技术参数 |
| `asset_source` | varchar(50) | 否 | 资产来源 |
| `area` | varchar(100) | 否 | 空管区域 |
| `room` | varchar(100) | 否 | 机房 |
| `cabinet` | varchar(100) | 否 | 机柜 |
| `position_code` | varchar(100) | 否 | 机位或安装点位 |
| `last_inspection_at` | varchar(20) | 否 | 最近巡检时间 |
| `last_maintenance_at` | varchar(20) | 否 | 最近保养时间 |
| `next_maintenance_at` | varchar(20) | 否 | 下次保养时间 |

如果不希望一次性改动设备主表过大，也可将采购、安装等扩展信息放入专项表，仅在主表保留 `lifecycle_status`、`device_type`、`area`、`room` 等高频查询字段。

### 6.2 采购入库表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 主键 |
| `tenant_id` | int/string | 是 | 租户 ID |
| `device_resume_id` | int | 是 | 关联设备 |
| `device_sn` | varchar(50) | 是 | 设备编号快照 |
| `device_name` | varchar(100) | 是 | 设备名称 |
| `device_model` | varchar(100) | 是 | 型号 |
| `specification` | varchar(200) | 否 | 规格 |
| `supplier` | varchar(200) | 否 | 供应商 |
| `purchase_date` | varchar(20) | 是 | 采购日期 |
| `technical_params` | text/json | 否 | 技术参数 |
| `inbound_status` | varchar(30) | 是 | 入库状态 |
| `remark` | text | 否 | 备注 |
| `created_at` | varchar(20) | 是 | 创建时间 |
| `created_by` | FK | 是 | 创建人 |

### 6.3 安装调试表

建议新增 `DeviceInstallationRecord`，表名 `tdyw_device_installation_record`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `device_resume_id` | int | 是 | 关联设备 |
| `area` | varchar(100) | 是 | 空管区域 |
| `room` | varchar(100) | 是 | 机房 |
| `install_location` | varchar(200) | 是 | 详细安装位置 |
| `install_time` | varchar(20) | 是 | 安装时间 |

### 6.4 巡检相关表

建议拆分为计划、任务、记录、参数明细四类表。

```text
DeviceInspectionPlan
DeviceInspectionTask
DeviceInspectionRecord
DeviceInspectionMetric
```

`DeviceInspectionPlan` 用于计划配置：

| 字段 | 说明 |
|---|---|
| `plan_name` | 计划名称 |
| `frequency_type` | 每日、每周、每月 |
| `device_scope_type` | 设备类型、区域、指定设备 |
| `device_scope_value` | 范围配置 |
| `inspection_items` | 巡检项目 JSON |
| `responsible_user_ids` | 巡检人员 |
| `enabled` | 是否启用 |

`DeviceInspectionTask` 用于周期任务：

| 字段 | 说明 |
|---|---|
| `plan_id` | 来源计划 |
| `task_date` | 巡检日期 |
| `task_status` | 待巡检、巡检中、已完成、已逾期 |
| `assigned_user_id` | 执行人 |
| `total_device_count` | 应巡检设备数 |
| `completed_device_count` | 已巡检设备数 |

`DeviceInspectionRecord` 用于单台设备巡检记录：

| 字段 | 说明 |
|---|---|
| `task_id` | 关联任务 |
| `device_resume_id` | 关联设备 |
| `checkin_type` | PC、扫码、移动端 |
| `checkin_at` | 打卡时间 |
| `appearance_status` | 外观状态 |
| `abnormal_level` | 无、一般、重要、紧急 |
| `abnormal_desc` | 异常描述 |
| `record_status` | 正常、异常待处理、已处理 |

`DeviceInspectionMetric` 用于保存电压、信号强度等参数：

| 字段 | 说明 |
|---|---|
| `record_id` | 巡检记录 |
| `metric_key` | 参数编码 |
| `metric_name` | 参数名称 |
| `metric_value` | 参数值 |
| `metric_unit` | 单位 |
| `is_abnormal` | 是否异常 |

### 6.5 故障工单表

现有 `FaultRecord` 字段偏简单，建议新增面向流程的 `DeviceFaultTicket`，表名 `tdyw_device_fault_ticket`。旧故障记录可保留，后续逐步迁移。

| 字段 | 类型 | 必填 | 说明 |

## 九、预警与提醒设计

需要统一建设“设备运维提醒”能力，覆盖巡检异常、故障紧急程度、保养到期、报废审批待办。

提醒类型：

| 类型 | 触发条件 | 接收人 |
|---|---|---|
| 巡检任务提醒 | 任务生成或临近截止 | 巡检人员 |
| 巡检逾期提醒 | 超过计划时间未完成 | 巡检人员、部门负责人 |
| 巡检异常预警 | 异常等级为一般、重要、紧急 | 设备负责人、部门负责人 |
| 故障派单提醒 | 新故障报修 | 运维单位负责人 |
| 故障结案确认 | 维修人员提交结案 | 报修方 |
| 保养到期提醒 | 距下次保养日期小于提醒天数 | 责任人 |
| 报废审批提醒 | 流程进入待审核节点 | 对应审核人 |

预警推送首期可先支持站内消息、菜单角标、弹窗提醒；如项目已有企业微信、短信、邮件能力，再扩展外部推送。

## 十七、验收标准

### 17.1 功能验收

- 采购入库后能生成唯一设备编号，并自动创建设备台账。
- 设备入库后状态为待安装。
- 安装调试提交验收后，负责人审核通过能将状态更新为正常运行。
- 巡检计划能按周期生成任务。
- 巡检人员能扫码进入巡检表单并提交参数。
- 巡检异常能触发一般、重要、紧急三级预警。
- 故障报修能完成派单、维修、结案、报修方确认。
- 保养计划能生成任务并提醒下次保养。
- 报废申请能完成多级审批并将设备状态更新为已报废。
- 单台设备履历能展示完整时间线。

### 17.2 数据验收

- 所有生命周期业务记录均带 `tenant_id`。
- 所有关联设备的数据均能回到设备详情页查询。
- 关键状态流转均写入设备履历和流程日志。
- 附件能预览、下载，并与业务记录正确关联。
- 已报废设备历史数据可查，不参与常规任务生成。

### 17.3 权限验收

- 普通运维人员不能执行报废最终审批。
- 管制部门用户只能确认自己发起或自己部门相关的故障。
- 巡检人员只能看到分配给自己的巡检任务。
- 部门负责人能看到待自己审核的验收和报废申请。
- 无导出权限的用户不能导出设备履历。

## 十八、风险与建议

### 18.1 主要风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 状态过多导致混乱 | 同一设备可能同时有故障、保养、报废审批 | 使用 `lifecycle_status` 表示主状态，未闭环工单用统计字段展示 |
| 业务表过多 | 六类业务都建表，开发量较大 | 分阶段建设，先完成采购、安装、巡检主链路 |
| 移动端范围膨胀 | 移动端可能被要求接近完整 App | 首期只做扫码巡检和拍照上传 |
| 审批流程变复杂 | 报废审批可能因组织调整变化 | 使用轻量流程日志，节点枚举可配置 |
| 旧故障模块兼容 | 现有 `FaultRecord` 与新故障工单可能重复 | 新工单作为设备生命周期入口，旧模块逐步迁移或作为历史查询 |

### 18.2 推荐落地策略

第一版优先打通“采购入库 -> 安装验收 -> 正常运行 -> 巡检 -> 故障/保养 -> 履历”的主链路。报废注销虽然重要，但可以在主链路稳定后再上线，避免一次性把流程、权限、附件、提醒全部压到同一个版本。

如果担心修改现有 `DeviceEvent.event_type` 的整数枚举影响旧代码，可新增字符串字段 `event_biz_type`，旧 `event_type` 暂时保持兼容。
