# 系统升级管理模块 — 边界条件遗漏清单

> 用途：供另一 Agent 针对"当前代码未覆盖的边界逻辑"做定向修复。
> 范围：仅列出**缺失的边界条件 / 异常输入 / 极端场景**，不提供修复代码或实现方案。
> 现状确认（避免误报）：
> - 附件清理链路 `delete_record → soft_delete_by_object` 中 `object_id` 已被统一 `str()` 归一化，类型一致，**非遗漏**。
> - `UpgradeStatus` 实际只有 3 态（处理中 / 已完成 / 已回退），**不存在"已暂停"枚举**；`pause/resume` 仅落时间线日志，不映射主状态（见 A5）。

---

## A. 状态流转引擎（`services/status_log_service.py`）

| 编号 | 位置 | 边界情况 | 预期行为 | 触发条件 |
|---|---|---|---|---|
| A1 | `update_record` editable 含 `status` + `validate_update` | 直接编辑 `status` 字段**绕过事件溯源引擎**，不写状态日志，导致主状态与时间线（StatusLog）不一致 | 状态变更统一经 `add_log` 落地；若允许直接编辑，应自动补一条对应 StatusLog，保证 timeline 与 status 一致 | `PUT /api/upgrade/records/{id}/` 带 `status` |
| A2 | `delete_log` → `_recompute_main_status` | 删除一条日志后重算**仅看最后一条 complete/rollback**，未重算派生 `current_index`，也未与步骤完成度联动；可能呈现"已回退/已完成"但所有步骤尚未完成 | 删除日志后应按剩余日志重算 `current_index`，并重驱动步骤联动 / 主状态 | 撤销 / 删除某条状态日志（标准接口） |
| A3 | `add_log` rollback 分支 `_compute_current_index` | 回退目标 `target_idx > current_index`（回退到"尚未到达/当前之后"的节点）时：`current_index` 不变，但 `_resolve_to_status` 仍把主状态翻为 `已回退` —— 静默 no-op + 状态翻转 | 校验回退目标须位于当前进度之前（或此前已到达的节点），否则返回错误 | 处于 start/backup 阶段时，回退到 full_release/observe |
| A4 | `_next_event_seq` + `_persist_log` | `event_seq` 读 max+1 与写入不在同一原子约束下；同一升级单高并发 `add_log` 可能得到相同 `event_seq`，破坏时间线顺序 | 唯一约束 + 冲突重试，或 `select_for_update` / 数据库序列保证序号唯一有序 | 同一升级单并发写入多条状态日志 |
| A5 | 常量 `UpgradeStatus` + `ACTION_TO_MAIN_STATUS` | `pause/resume` 动作不映射主状态、无 `paused` 枚举；"暂停"只是时间线备注，无法阻止暂停期间继续推进状态 | 明确暂停态，或在流程引擎中禁止非 `resume` 动作在 `pause` 之后生效 | 记录 `pause` 后仍可 `complete`/`rollback`/`full_release` |

## B. 升级单 CRUD / 编号 / 筛选（`services/record_service.py` + `views/record/*`）

| 编号 | 位置 | 边界情况 | 预期行为 | 触发条件 |
|---|---|---|---|---|
| B1 | `generate_upgrade_no` | 单号"先查后插"非原子；同日并发创建可能生成相同 `UPG-YYYYMMDD-XXXX` | 唯一约束 + 重试，或数据库序列 | 同一天高并发创建 |
| B2 | `generate_upgrade_no` `next_seq:04d` | 当日序号 > 9999 时输出 5 位，破坏格式（不报错） | 位数溢出保护 / 显式报错 | 单日创建 >9999 单（极端） |
| B3 | `create_record` + `validate_create` | 手工传入 `upgrade_no` 缺格式正则校验；唯一性校验在并发下仍可能竞态 | 格式正则 + 唯一约束 | `POST` 带畸形单号 |
| B4 | `update_record` `upgrade_time` 分支 | `upgrade_time` 无 `strftime` 属性时原样入库（'abc' 也可存） | 日期格式校验 | `PUT` 传非日期字符串 |
| B5 | `_apply_filters` + `get_list` | 日期范围依赖 CharField **字典序**比较；空串/格式不一致记录导致过滤不可靠；且**只传一端日期被静默忽略**（须两端齐全才生效） | 统一日期类型或规范化后比较；单端日期应生效或明确报错 | 仅传 `start_date`；或存在历史脏数据 |
| B6 | `get_list` 分页 | `page`/`page_size` 未校验：负数 page → 切片异常/空；超大 `page_size` → 全表加载；非整数类型可能 500 | 范围 + 类型校验（含上限） | `GET ?page=-1` 或 `page_size=100000` |
| B7 | `update_record` editable 字段 | `system`/`owner` 为任意自由文本，无枚举/存在性校验（仅 `status`/`upgrade_type` 受部分校验） | 参考数据完整性校验（`system` 应在系统字典内） | `PUT` 传 `system='随便'` |
| B8 | `VALID_STATUS_TRANSITIONS` + A1 | 该常量定义了允许的转换集合，但与流程引擎顺序脱节；直接编辑 `status` 时只受此表约束，可从任意态直接跳到 `已回退`，绕开流程顺序 | 状态转换应与流程引擎一致、统一入口 | 见 A1 |

## C. 步骤子模块（`services/step_service.py` + `models_checklist.py`）

| 编号 | 位置 | 边界情况 | 预期行为 | 触发条件 |
|---|---|---|---|---|
| C1 | `_check_and_update_record_status` | `status==已回退` 且某已完成步骤被 `reset` 为 pending 时，主状态保持不变，与步骤完成度不一致（逻辑仅在 `==COMPLETED` 时回退） | 主状态与步骤完成度应双向一致（回退态下新增 pending 也应反映） | 已回退单 reset 一个已完成步骤 |
| C2 | `clear_record_steps` | 清空步骤后不回退"已完成"主状态（`total==0` 时直接 return；调用处也未联动） | 清空步骤应把主状态回退到处理中（或保留但明确语义） | 清空某"已完成"单的全部步骤 |
| C3 | `batch_update_status` | 对全部无效 `step_id` 静默 `continue` 并返回 `None`，无错误反馈；调用方传入的 id 全错时接口返回成功但零变更 | 至少返回"无有效步骤"或计数 | 传入错误 / 他人 `step_id` 列表 |
| C4 | `apply_to_record` | 重复调用会**累积重复步骤**（每次 `max_seq+1` 追加，无幂等 / 去重 / 已实例化标记） | 记录是否已实例化 / 按 `checklist_id` 去重 | 对同一单多次 `apply` 同一方案 |
| C5 | 步骤自动完成 vs 状态日志 | 步骤全完成会自动把主状态置 `已完成`；状态日志同样可把主状态置 `已完成`/`已回退`。两路径并存，可能出现"步骤全完成 → 被 rollback 翻为已回退 → 又因步骤变化翻回"的乒乓 | 明确主状态唯一权威来源（建议状态日志 + 显式步骤完成 gate） | 步骤全完成后又加 `rollback` 日志 |

## D. 方案子模块（`services/plan_service.py`）

| 编号 | 位置 | 边界情况 | 预期行为 | 触发条件 |
|---|---|---|---|---|
| D1 | `update_plan` vs `apply_to_record` | 编辑方案步骤（整体替换）**不回灌已实例化的升级单步骤**（`checklist_id` 存方案 id），旧单仍是旧步骤 | 方案变更时提示 / 同步 / 标记受影响实例 | apply 后修改方案再观察旧单 |
| D2 | `reorder_steps` | 入参不完整 / 含重复 id：只更新传入 id 顺序，其余保留旧 sequence（部分乱序）；重复 id 被赋同样 sequence | 要求完整步骤集合 + 唯一性校验 | 前端只传部分步骤 / 重复传同一 id |
| D3 | `create_plan`/`update_plan` `is_default` | `is_default` 允许多个方案同时为真，无唯一性约束；仅展示排序优先 | 单一默认约束，或明确允许多默认 | 把多个方案都设为默认 |

## E. 删除与数据完整性（`services/record_service.py` → `delete_record`）

| 编号 | 位置 | 边界情况 | 预期行为 | 触发条件 |
|---|---|---|---|---|
| E1 | `delete_record` | 删除升级单**不清理** `UpgradeStatusLog` 与 `UpgradeRecordStep` 子表，产生孤儿记录（仍引用已删 `upgrade_id`） | 删除时级联 / 显式清理子表（或软删联动） | `DELETE` 升级单后查 logs/steps 表 |
| E2 | 全局核心操作 | 升级单的 create/update/delete/add_log/step/plan 普遍**缺 AuditLog 审计**（与系统其它模块不一致），操作不可追溯 | 补齐关键操作审计 | 审计需求 / 合规排查 |
