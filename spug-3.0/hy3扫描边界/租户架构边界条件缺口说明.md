## A. 写入隔离 / 自动注入（tenant_base_model.py + tenant_middleware.py）

### GAP-01 超级管理员写入不归属任何租户
- **模块 / 位置**：`tenant_middleware.auto_set_tenant` / `TenantMiddleware.process_request`
- **缺失的边界条件**：超管请求创建 `TenantModelMixin` 记录时线程局部 tenant 为 None，pre_save 信号不注入 tenant_id，记录 tenant_id 落为空串。
- **描述**：`TenantMiddleware` 对 `is_supper` 用户 `set_current_tenant(None)`；`auto_set_tenant` 仅在 `current_tenant` 为真且 `instance.tenant_id` 为空时填充，故超管写入租户化模型得到 `tenant_id=""`。普通用户按 `Q(tenant_id=自身)` 过滤，永远看不到这些空串记录（孤儿数据）；超管则因不过滤可见。
- **预期行为**：超管写入要么明确归属某个租户，要么标记为"全局/平台级"（如 tenant_id 为特定保留值），不应产生空串孤儿。
- **触发条件**：超管通过接口/后台直接创建业务记录，且未显式调用 `set_instance_tenant` / `assign_tenant_id`。

### GAP-02 后台任务 / Celery / Shell 无租户上下文
- **模块 / 位置**：`tenant_middleware.get_current_tenant` / `TenantModelManager.get_queryset`
- **缺失的边界条件**：请求线程之外 `get_current_tenant()` 为 None，`TenantModelManager.get_queryset` 返回未过滤全集，且写入不注入 tenant_id。
- **描述**：租户隔离完全依赖每请求中间件设定线程局部。Celery 任务、management command、Django shell 复用线程局部时可能为 None 或残留上一请求值，导致隔离失效或数据串租户。
- **预期行为**：后台任务必须有显式租户上下文（入参/任务路由注入），否则应报错而非静默返回全集或写空 tenant_id。
- **触发条件**：Celery 定时/异步任务、运维脚本、管理命令中查询或写入租户化模型。

### GAP-03 模型层无写入防御（可越租户写入）
- **模块 / 位置**：`tenant_middleware.auto_set_tenant`
- **缺失的边界条件**：信号仅在 tenant_id 为空时填充；若视图/序列化器已显式置为其他租户值，信号不覆盖。
- **描述**：写入隔离仅靠"自动填空"，没有"强制纠正为当前用户租户"的防御。非超管若能在请求体带 tenant_id 并经 `update_by_dict` 写入，可把数据写进非本租户。
- **预期行为**：非超管写入时，模型层/信号应将 tenant_id 强制收敛为当前用户租户并拒绝越租户值（防御纵深）。
- **触发条件**：某业务视图在 body 接受 tenant_id 且未对非超管剥离即 `update_by_dict` / 直接 `save`。

### GAP-04 新旧两套租户基类语义不一致
- **模块 / 位置**：`tenant_middleware.TenantModel` / `TenantManager`（旧实现）
- **缺失的边界条件**：旧 `TenantModel` / `TenantManager` 默认 `tenant_id="default"`，新 `TenantModelMixin` / `TenantModelManager` 默认 `""`，两实现并存。
- **描述**：默认字符串 `"default"` 与 `""` 语义不同，若仍有模型继承旧抽象基类，其隔离行为（过滤值、写入默认值）与统一方案不一致，且容易与新方案混淆。
- **预期行为**：统一为一套租户基类与默认 tenant_id 约定，移除或显式标注旧实现。
- **触发条件**：任何仍继承旧 `TenantModel` 的模型被迁移/查询。

## B. 线程局部生命周期（tenant_middleware.py）

### GAP-05 认证短路导致线程局部租户泄漏
- **模块 / 位置**：`TenantMiddleware.process_request` / `process_response`
- **缺失的边界条件**：`AuthenticationMiddleware` 返回 401 响应时，`TenantMiddleware.process_request` 不执行，其 `process_response` 也不被调用，`clear_tenant()` 不触发。
- **描述**：Django 中若上层中间件 `process_request` 提前返回响应，下层中间件 `process_request` / `process_response` 均不执行。于是上一次请求在该线程设置的 tenant 未被清除，被同一线程后续请求复用。
- **预期行为**：每次请求结束（含认证失败短路）必须清除线程局部租户。
- **触发条件**：带无效/缺失 token 的请求使 `AuthenticationMiddleware` 返回 401 后，同一线程处理后续请求。

### GAP-06 无请求上下文读取到旧租户值
- **模块 / 位置**：`tenant_middleware.get_current_tenant`
- **缺失的边界条件**：`get_current_tenant()` 在请求生命周期外返回残留值，无"无上下文"哨兵。
- **描述**：同 GAP-02/05 的读取侧：非请求线程或泄漏场景下，`get_current_tenant()` 返回上一请求租户，导致误过滤或误不过滤。
- **预期行为**：应区分"已设定"与"未设定"，无上下文时显式报错而非复用旧值。
- **触发条件**：线程局部被上一请求污染后的任意读操作。

## C. 读取过滤（tenant_utils.apply_tenant_filter / check_tenant_unique_name）

### GAP-07 严格模式超管 tenant_id 回退 "admin"
- **模块 / 位置**：`tenant_utils.apply_tenant_filter`（strict_mode 分支）
- **缺失的边界条件**：`strict_mode=True` 时超管按 `getattr(tenant_id, "admin")` 过滤，但超管 tenant_id 通常为 None。
- **描述**：资料库公共空间等 strict_mode 场景期望超管也按租户隔离，但用 `"admin"` 兜底会过滤 `Q(tenant_id="admin")`，与超管实际归属不符，可能看到 admin 租户数据或空集。
- **预期行为**：严格模式下超管应基于其真实归属或显式拒绝，不应静默回退 `"admin"`。
- **触发条件**：超管访问 `strict_mode=True` 的接口（如资料库公共空间）。

### GAP-08 普通用户 tenant_id 为空/None 静默错误过滤
- **模块 / 位置**：`tenant_utils.apply_tenant_filter`（普通用户分支）
- **缺失的边界条件**：`getattr(tenant_id, "admin")`；用户 tenant_id 为 `""` 或 None（数据损坏）时过滤 `Q(tenant_id="admin")` 或 `Q(tenant_id="")`。
- **描述**：tenant_id 缺失的用户不会收到错误，而是被过滤到错误租户或空集（功能"假性失灵"），难以排查。
- **预期行为**：tenant_id 缺失应明确报错而非静默错误过滤。
- **触发条件**：tenant_id 为空的普通用户发起查询。

### GAP-09 越权拦截告警基于已过滤集合，恒失效
- **模块 / 位置**：`tenant_utils.apply_tenant_filter`（越权告警）
- **缺失的边界条件**：WARNING "潜在越权拦截"比较 count_before / count_after，但传入 queryset 已被 `TenantModelManager` 预过滤。
- **描述**：因管理器已预加租户条件，count_before 与 count_after 多为同一租户集合，告警基本恒为 0 或无意义；且超管分支提前 return 不计数，使该安全监控形同虚设。
- **预期行为**：告警应基于未过滤基线计数，或移除该不可靠告警。
- **触发条件**：所有走模型管理器的过滤调用。

### GAP-10 公共空间同名校验忽略 system_scope 维度
- **模块 / 位置**：`tenant_utils.check_tenant_unique_name`
- **缺失的边界条件**：`is_public=True` 时完全不应用租户过滤，也未按 `system_folder` / 党建维度区分。
- **描述**：公共空间文件名唯一性只按 name+folder 判定；跨 scope（党建区 vs 普通区）同 folder 同名文件会出现"已存在"误判或允许冲突，与二维隔离模型不一致。
- **预期行为**：公共空间同名检查应将 `system_scope` 纳入唯一性维度。
- **触发条件**：党建区与普通区存在同 folder 同名文件的创建/重命名。

## D. 存量数据租户化迁移（tenant_utils.migrate_existing_data）

### GAP-11 迁移模型硬编码且不全
- **模块 / 位置**：`tenant_utils.migrate_existing_data`
- **缺失的边界条件**：仅迁移 6 个模型（RunLog / FaultRecord / FaultPart / Interference / UpgradeRecord / DutyRecord）。
- **描述**：通过 import 硬编码模型列表，新增的 `TenantModelMixin` 模型若 tenant_id 为空不会被迁移，成为孤儿数据，与"自动发现"的设计意图相悖。
- **预期行为**：基于 `get_tenant_models()` 自动发现所有租户模型并迁移。
- **触发条件**：首次/补数据迁移后查询其他 app（文档/证据等）的历史数据。

### GAP-12 无 created_by 或 created_by 无租户 → 永久孤儿
- **模块 / 位置**：`tenant_utils.migrate_existing_data`
- **缺失的边界条件**：记录 `created_by=None` 或 `created_by.tenant_id` 为空时，tenant_id 保持空串，无兜底/告警。
- **描述**：迁移依赖 `created_by.tenant_id` 回溯租户；历史脏数据缺少该关联时记录永久 `tenant_id=""`，既无默认归属也无告警。
- **预期行为**：应有默认归属策略或对无法判定租户的记录明确告警。
- **触发条件**：`created_by` 缺失/为空的历史记录参与迁移。

### GAP-13 迁移逐条 save 无事务包裹
- **模块 / 位置**：`tenant_utils.migrate_existing_data`
- **缺失的边界条件**：循环中对每条 record 调用 `record.save()`，无 atomic 包裹。
- **描述**：迁移中途若 DB 异常，部分记录已迁移、部分未迁移，产生不一致且不幂等。
- **预期行为**：整体置于事务中，保证原子性。
- **触发条件**：迁移过程中数据库抛出异常。

## E. 认证 / 令牌（libs/middleware.py AuthenticationMiddleware）

### GAP-14 last_ip 为空 + 启用 IP 绑定时永久登录失败
- **模块 / 位置**：`middleware.AuthenticationMiddleware._authenticate_x_token`
- **缺失的边界条件**：IP 绑定开启且 `user.last_ip` 为 None/空时，`x_real_ip == user.last_ip` 恒 False。
- **描述**：首次登录或 `last_ip` 被清空后启用 IP 绑定，所有登录尝试因 IP 不匹配被拒，用户被永久锁死，无"首次绑定"逻辑。
- **预期行为**：`last_ip` 为空应允许登录并写入当前 IP，或提供首次绑定豁免。
- **触发条件**：新用户 / `last_ip` 被清空后平台启用 IP 绑定。

### GAP-15 preview_token 未校验 user.tenant_id 与 token.tenant_id 一致
- **模块 / 位置**：`middleware.AuthenticationMiddleware._authenticate_preview_token`
- **缺失的边界条件**：仅按 `token_data["user_id"]` 取用户，未比对 token 绑定的 tenant_id。
- **描述**：若用户租户发生变更，旧预览令牌仍可能解析出该用户并放行，与令牌绑定的租户上下文不一致。
- **预期行为**：应校验 token 绑定 tenant_id 与用户当前 tenant_id 一致。
- **触发条件**：用户租户变更后仍使用此前签发的预览令牌。

### GAP-16 每次认证请求 user.save() 全量写放大
- **模块 / 位置**：`middleware.AuthenticationMiddleware._authenticate_x_token`
- **缺失的边界条件**：刷新 `token_expired` 时对完整 User 执行 `save()`，触发 pre_save 信号。
- **描述**：每个需认证的请求都会写整行 user 并触发 `auto_set_tenant` 等信号，高并发下产生不必要写放大与行锁竞争。
- **预期行为**：仅更新 `token_expired` 等必要字段（update 单字段）。
- **触发条件**：每个携带有效 x-token 的请求。

## F. 租户 CRUD（apps/account/views.py TenantView）

### GAP-17 删除租户不清理业务数据
- **模块 / 位置**：`account.views.TenantView.delete`
- **缺失的边界条件**：仅检查 `User.objects.filter(tenant_id=...).exists()`，未检查/未级联业务记录。
- **描述**：`tenant_id` 为普通 CharField（无外键），删除租户后其文件/文件夹/日志/附件等业务数据悬挂为孤儿，且后续查询按 tenant_id 仍可命中这些悬挂数据。
- **预期行为**：删除前应校验无业务数据，或提供级联/归档处理。
- **触发条件**：删除一个无用户但存在业务数据的租户。

### GAP-18 可删除/创建保留租户标识
- **模块 / 位置**：`account.views.TenantView.post` / `delete`
- **缺失的边界条件**：未禁止删除 `"admin"` 等引导租户，也未禁止创建 `id="admin"` / `"default"` 等保留名。
- **描述**：`User.tenant_id` 默认 `"admin"`；若创建 `id="admin"` 的 Tenant 行，引导用户会被并入该新建租户，造成身份混淆；删除 admin 租户亦无保护。
- **预期行为**：保留租户名黑名单，禁止创建/删除引导租户。
- **触发条件**：创建 `id="admin"` 的租户 / 删除 admin 租户。

### GAP-19 租户停用无下游影响控制
- **模块 / 位置**：`account.views.TenantView.patch`
- **缺失的边界条件**：可 `is_active=False` 一个仍有用户的租户，无一致性约束。
- **描述**：停用有用户的租户后，这些用户仍可登录且数据可见，缺乏"停用即限制"的明确语义。
- **预期行为**：明确停用语义：阻止登录或直接拒绝停用有活跃用户的租户。
- **触发条件**：停用一个仍有用户的租户。

## G. 用户租户变更（apps/account/views.py UserView）

### GAP-20 修改用户租户只迁移 6 个硬编码模型
- **模块 / 位置**：`account.views.UserView._migrate_user_tenant`
- **缺失的边界条件**：`_migrate_user_tenant` 调用 `migrate_existing_data`，仅迁移 `created_by` 关联的 6 模型。
- **描述**：超管把用户从租户 A 改到 B 时，文档/证据/其他租户化数据不随迁，且依赖 `created_by` 字段存在；迁移后用户历史数据孤儿化。
- **预期行为**：迁移该用户全部租户化数据，而非仅 6 个模型。
- **触发条件**：超管把用户从租户 A 改到租户 B。

### GAP-21 超管隐式租户用 username 跳过格式校验
- **模块 / 位置**：`account.views.UserView._resolve_tenant_id`
- **缺失的边界条件**：`form.tenant_id` 为空时直接用 username 作 tenant_id，未走 `validate_tenant_id`。
- **描述**：`TenantView.post` 对显式 tenant_id 做 `TENANT_ID_PATTERN` 校验，但用户创建路径在超管不填 tenant_id 时用 username 兜底，含 `@` / `.` / 空格等特殊字符的 username 会成为非法租户标识。
- **预期行为**：隐式租户同样执行 `TENANT_ID_PATTERN` 校验（或规范化）。
- **触发条件**：超管创建用户时不填 tenant_id，且 username 含 `@` / `.` / 空格等字符。

## H. 角色委派边界（apps/account/role_permissions.py + RoleView）

### GAP-22 租户级 is_system 角色无约束
- **模块 / 位置**：`account.views.RoleView._normalize_role_fields`
- **缺失的边界条件**：普通管理员强制 `is_system=False`；但超管可创建 `tenant_id` 非空且 `is_system=True` 的角色。
- **描述**：`is_system` 语义上应为平台级（`tenant_id=None`），但超管路径未禁止"租户内系统角色"，产生语义矛盾数据。
- **预期行为**：`is_system=True` 必须要求 `tenant_id=None`（平台级）。
- **触发条件**：超管创建"租户内系统角色"。

### GAP-23 同租户角色重名无校验
- **模块 / 位置**：`account.views.RoleView.post`
- **缺失的边界条件**：Role 创建未检查同租户内 name 唯一。
- **描述**：同一租户可重复创建同名角色，造成管理歧义与下拉选择混淆。
- **预期行为**：同租户内角色 name 唯一约束。
- **触发条件**：同一租户重复创建同名角色。

### GAP-24 全局管理员角色可授予租户用户且无额外约束
- **模块 / 位置**：`account.role_permissions.validate_assignable_role_ids`
- **缺失的边界条件**：超管将 global-admin 角色授予任意租户用户时显式允许（`is_global_admin` 被排除出冲突检查）。
- **描述**：该租户用户将获得全局可见性；若其原管理员误操作，缺乏额外保护/审计，存在权限放大顾虑。
- **预期行为**：明确是否允许并加相应约束与审计。
- **触发条件**：超管把全局管理员角色赋给租户普通用户。

### GAP-25 target_tenant_id 不存在时无校验
- **模块 / 位置**：`account.role_permissions.get_assignable_roles_for_target`
- **缺失的边界条件**：对伪造/不存在的 tenant_id 不报错，仅返回空租户角色集。
- **描述**：前端传不存在的 tenant_id 时静默返回（可能为空），调用方难以发现租户不存在。
- **预期行为**：校验 `target_tenant_id` 对应的租户存在。
- **触发条件**：前端/接口传不存在的 tenant_id。

## I. 文档二维隔离（apps/document/services/system_scope_validators.py）

### GAP-26 file_obj=None 时党建 scope 校验跳过
- **模块 / 位置**：`system_scope_validators.validate_file_source_scope`
- **缺失的边界条件**：`file_obj` 为 None 时只校验 context，不校验文件实际 scope。
- **描述**：党建模式若调用方未取文件并传 file_obj，则只做了 context 校验，文件实际是否在党建 scope 未验证，仅靠普通模式反向隔离兜底。
- **预期行为**：要求调用方必须传 file_obj，或在视图层强制取文件并校验 scope。
- **触发条件**：调用方传 `file_obj=None` 的党建文件操作。

### GAP-27 unknown code 两种路径处理不一致
- **模块 / 位置**：`system_scope_validators.normalize_context` vs `validate_document_context`
- **缺失的边界条件**：`normalize_context` 对未知 `system_folder` 抛 `ValueError`；主校验链可能静默当作普通模式。
- **描述**：两路径对未知编码行为分歧：一处报错、一处放行为普通模式，易引发维护混乱与潜在绕过误解。
- **预期行为**：统一 unknown-code 处理（均拒绝或均规范化）。
- **触发条件**：传入拼错的 `system_folder` 编码。

### GAP-28 验证器不校验 tenant_id（双维度依赖调用方）
- **模块 / 位置**：`system_scope_validators`（整体）
- **缺失的边界条件**：`system_scope` 校验假设 tenant 已隔离，自身不校验 tenant_id。
- **描述**：若某视图只做 scope 校验而漏掉 `apply_tenant_filter`，跨租户仍可泄露；两维度需同时生效但无代码层强制组合。
- **预期行为**：文档化并强制双维度同时生效，或提供统一入口组合校验。
- **触发条件**：遗漏 tenant 过滤的资料库视图。

## J. 通用 / 审计 / 管理器使用

### GAP-29 系统动作审计 tenant_id 缺失
- **模块 / 位置**：`apps/account/views.py login` / `logout` / `handle_login_record`
- **缺失的边界条件**：审计日志 tenant_id 取 `getattr(user, "tenant_id", "default")`；无 user 时归 `"default"`。
- **描述**：Celery/系统级动作无 user 上下文，审计归 `"default"`，跨租户审计可见性不一致，租户管理员可能看不到本租户系统动作。
- **预期行为**：系统动作应明确归属租户或做隔离。
- **触发条件**：系统级/后台任务写审计日志。

### GAP-30 使用未过滤管理器却忘记 apply_tenant_filter
- **模块 / 位置**：各业务视图（使用 `all_objects` / 非 `TenantModelManager`）
- **缺失的边界条件**：`all_objects`（旧 `TenantManager` 提供的非过滤管理器）或自定义 Manager 若未显式过滤，隔离完全失效。
- **描述**：部分视图为超管便利使用 `all_objects`，若漏掉 `apply_tenant_filter` 则跨租户数据全量暴露；需逐个审计调用点。
- **预期行为**：审计所有 `all_objects` / 未过滤管理器调用点，确保显式 tenant 过滤。
- **触发条件**：使用 `all_objects` 的业务视图。
