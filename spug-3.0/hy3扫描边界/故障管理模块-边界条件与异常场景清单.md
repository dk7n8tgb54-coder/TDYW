# 故障管理模块 — 边界条件与异常场景清单

> 仅列当前代码遗漏的边界逻辑，未含修复方案，供 Agent 针对性修复。
> 覆盖范围：故障处置记录（FaultRecord）、故障件（FaultPart）的后端视图、模型、导出与前端页面。

## 二、逐条明细

### B01 列表接口无分页（GET）
- **区域**：输入/查询边界
- **描述**：`FaultRecordView.get` 与 `FaultPartView.get` 均通过 `apply_tenant_filter` 后直接 `[x.to_view() for x in records]` 返回全部记录，未做分页、未限制返回条数，也未提供 page/limit 参数。
- **预期行为**：大数据量时应分页返回或限制单页/单请求上限，避免响应体过大、前端内存暴涨与序列化开销过高。
- **触发条件**：单租户故障记录/故障件数量达到数百至数千条时，列表接口返回完整集合。

### B02 日期字段格式不一致
- **区域**：数据格式边界
- **描述**：前端始终以 `YYYY-MM-DD` 提交日期；但后端状态机在故障件状态变为"送修/运回测试/正常归档"且对应日期为空时，写入 `human_datetime()`（格式 `YYYY-MM-DD HH:MM:SS`）。因此 `fault_sent_date` / `test_return_date` / `archive_date` 可能同时包含两种格式字符串，与 `date` / `fault_date` 的纯日期格式不一致。
- **预期行为**：统一日期格式（建议模型改用 DateField，或自动填充也仅取 `YYYY-MM-DD`）；避免同一字段出现两种格式，防止排序、导出、前端回显解析出现偏差。
- **触发条件**：在故障件表单中将状态改为送修/运回测试/正常归档且未手填对应日期，后端自动写入带时分秒的值。

### B03 故障件状态回退遗留陈旧日期
- **区域**：状态机边界
- **描述**：后端仅在状态"前进"到送修/运回测试/正常归档且目标日期为空时自动填充；编辑时将状态从"正常归档"改回"故障"时，`archive_date` 不会被清除，仍保留旧归档日期；同理送修→故障不会清除 `fault_sent_date`。状态机只处理"前进填充"，不处理"回退清理"。
- **预期行为**：状态变更时应按状态机清理不再适用的日期字段（如退出"正常归档"应清空 `archive_date`），避免脏数据。
- **触发条件**：编辑已有故障件，将状态调低（如正常归档→故障）后保存。

### B04 status / fault_level 无后端枚举白名单
- **区域**：输入校验边界
- **描述**：`FaultPartView` 的 `status` 与 `FaultRecordView` 的 `fault_level` 在后端仅做 `required=False`（编辑）或 `required=True`（创建），无任何取值白名单校验。API 接受任意字符串。前端虽用 Select 限定选项，但直接调用接口可传入非法值。
- **预期行为**：后端应强制枚举白名单（`status` ∈ {故障,送修,运回测试,正常归档}；`fault_level` ∈ {A,B,C}），拒绝非法取值。
- **触发条件**：直接 POST 接口传入 `status="未知状态"` 或 `fault_level="Z"`。

### B05 编辑清空字段与未传字段语义不清
- **区域**：输入校验边界
- **描述**：编辑路径 `update_data = {k: v for k,v in form.items() if v is not None and k!="id"}`。用户清空字段提交空串 `""` 会被写入（覆盖原值）；而完全不传该字段则为 `None` 被忽略（保留原值）。前端编辑必传全部字段，故"清空"等价于"置空串"。
- **预期行为**：明确空串与未传的差异语义；若需允许显式置空，应一致处理；否则需防止误清空关键业务字段。
- **触发条件**：编辑表单中将某业务字段清空后保存。

### B06 日期合法性与顺序未校验
- **区域**：输入校验边界
- **描述**：`fault_date` / `date` / `fault_sent_date` 等均为 CharField，后端未校验是否为合法日期、是否未来日期，也未校验业务逻辑顺序（如归档日期不应早于故障日期、送修日期不应早于故障日期）。
- **预期行为**：校验日期格式合法性与基本业务顺序，拒绝非法或逻辑矛盾的时间输入。
- **触发条件**：提交 `fault_date="2026-13-45"`、未来日期，或归档日期早于故障日期。

### B07 业务字段无唯一约束，可重复录入
- **区域**：数据一致性边界
- **描述**：`FaultRecord` 与 `FaultPart` 模型未定义 `unique_together` 或唯一索引。相同系统/设备/日期的故障记录或故障件可被重复创建，无去重提示。
- **预期行为**：依据业务需要增加适当唯一约束或存在性校验（如 `system_name + device_code + fault_date` 组合），或在提交前提示重复。
- **触发条件**：重复提交内容相同的故障处置记录或故障件。

### B08 编辑丢失更新（并发竞态）
- **区域**：并发竞态边界
- **描述**：编辑使用 `FaultRecord.objects.filter(pk=id).update(**update_data)` 直接覆盖，无版本号/乐观锁比对，也无 `select_for_update` 悲观锁。两个用户同时编辑同一记录时，后提交者无条件覆盖先提交者。
- **预期行为**：引入乐观锁（如更新时比对 `updated_at`）或悲观锁，避免并发编辑相互覆盖。
- **触发条件**：同一记录被两名用户几乎同时打开并保存。

### B09 超长文本/特殊字符无校验
- **区域**：输入校验边界
- **描述**：`fault_phenomenon` / `handling_process` 为 TextField 无长度上限；CharField 字段（`max_length=100/50`）由 ORM 截断但不显式报错。超大文本或异常字符直接入库，导出 Excel 时可能影响排版与性能。
- **预期行为**：对大文本设置合理上限，对异常输入字符做校验/过滤，并在超限时返回明确错误。
- **触发条件**：提交极长故障现象/处置过程文本。

### B10 列表/详情响应暴露内部字段
- **区域**：信息暴露边界
- **描述**：`to_view()` 直接返回 `to_dict()`，包含 `tenant_id`、`created_by_id`、`updated_by_id`、`created_at` 等内部/实现字段。前端仅使用业务字段，内部字段对调用方可见。
- **预期行为**：序列化时剔除内部/敏感字段，仅返回业务字段；如需展示创建人，应单独映射显示名而非原始外键 id。
- **触发条件**：查看列表或详情接口响应。

### B11 故障件仅前端导出且无行数上限
- **区域**：导出边界
- **描述**：故障处置记录走后端 openpyxl 导出（含 `check_export_limit` 10000 上限），而故障件仅在前端用 XLSX 客户端导出，无行数保护、无后端筛选一致性校验。海量数据时浏览器内存生成 XLSX 可能卡死。
- **预期行为**：故障件导出也应受行数保护（或后端化），并与列表筛选语义保持一致。
- **触发条件**：故障件数量过万时点击导出。

### B12 列表与导出筛选口径不一致
- **区域**：导出边界
- **描述**：record 列表前端用 `includes` 模糊匹配；后端导出用 `icontains`（等价）。但列表不接受 `start_date`/`end_date` 范围参数，导出却接受；导出日期范围按字符串 `gte`/`lte` 比较，若 `fault_date` 混入时分秒则范围判断可能出现偏差（本模块 `fault_date` 为纯日期，风险较低，但口径不对称本身即是隐患）。
- **预期行为**：列表与导出的筛选参数集合与比较口径完全一致，避免"看到的数据"与"导出的数据"范围不同。
- **触发条件**：同时使用日期范围导出与列表查看，或切换不同筛选条件。

### B13 record 编辑权限键错误（功能失效）
- **区域**：权限/前端边界
- **描述**：`record/Form.js` 第 56 行使用 `hasPermission("exec.faultrecord.edit")`，而真实权限码为 `fault.faultrecord.edit`（codes.js 与后端 `@auth` 均为 `fault.*`）。导致 `hasPermission` 恒为 false，打开已有记录时 `viewMode` 被强制为真，编辑按钮失效，既有记录永远以只读详情打开。
- **预期行为**：权限码应改为 `fault.faultrecord.edit`，使既有记录的编辑表单可正常进入。
- **触发条件**：打开并查看/编辑任意"已有"故障处置记录（非新建）。

### B14 故障件操作按钮缺权限门控
- **区域**：权限/前端边界
- **描述**：故障件列表的删除/编辑按钮未使用 `AuthButton` / `hasPermission` 按 `fault.faultpart.*` 权限码显隐；record 编辑因 B13 实际也等同于无门控。后端 `@auth` 会拦截越权请求，但 UI 仍展示可点击按钮，体验与权限模型不一致。
- **预期行为**：新增/编辑/删除等操作按钮应按对应权限码显隐，与后端鉴权保持一致。
- **触发条件**：无对应权限的用户进入故障件/故障记录列表，仍可见操作按钮。

### B15 part 提交失败无 loading 恢复
- **区域**：前端健壮性边界
- **描述**：`part/store.js` 的 `handleSubmit` 使用 `.then(...)` 但无失败回调；当后端返回错误（如权限拒绝、校验失败）时，表单 `confirmLoading` 不会恢复，UI 卡在加载态。`record/Form.js` 的 `handleSubmit` 有失败回调，但 part 缺失。
- **预期行为**：提交失败分支应恢复 loading 状态并给出错误提示。
- **触发条件**：提交故障件时后端返回错误响应。

### B16 删除无二次确认、无批量删除
- **区域**：前端健壮性边界
- **描述**：列表删除直接调用接口，缺少 `Modal.confirm` 二次确认（取决于 Table 实现）；不支持批量选择删除。误点删除不可挽回（后端为物理删除）。
- **预期行为**：删除前增加二次确认；按需提供批量删除能力。
- **触发条件**：误点击删除按钮。

### B17 系统名称动态添加无去重、不持久化
- **区域**：前端健壮性边界
- **描述**：`record/Form.js` 与 `part/Form.js` 的"添加系统名称"直接 push 到本地 `systemNames` 数组，不校验重复，也不持久化到后端；刷新页面后自定义名称丢失，且可重复添加同一名称。
- **预期行为**：添加时去重；可选系统名称应从后端字典拉取并持久化。
- **触发条件**：重复添加同名系统；或刷新页面后自定义系统名称消失。

### B18 连续打开不同记录表单可能串数据
- **区域**：前端健壮性边界
- **描述**：`record/Form.js` 用 `useEffect([])` 仅在挂载时基于 `S.record` 判定 `viewMode`；若 `store.record` 在关闭弹窗时未清空，再次打开不同类型记录（如先编辑后新建）可能复用上一次数据或错误判定 `viewMode`。`part/Form.js` 用 `useEffect([form])` 在 `formVisible` 变化时 `setFieldsValue`，相对稳健，但仍依赖 `store.record` 被正确重置。
- **预期行为**：每次打开弹窗都基于当前 record 完整初始化，关闭时清空 `store.record`。
- **触发条件**：连续打开"编辑已有"→"新建"或不同记录。

### B19 列表无加载失败/空数据态
- **区域**：前端健壮性边界
- **描述**：`store.fetchRecords` 仅在 `finally` 关闭 `isFetching`，无错误态与空数据提示；请求失败或数据为空时用户无明确反馈。
- **预期行为**：增加请求失败错误态与空数据占位提示，必要时提供重试。
- **触发条件**：列表接口请求失败，或当前租户无数据。

### B20 非预期日期格式导致 moment 解析异常
- **区域**：前端健壮性边界
- **描述**：`part/Form.js` 对非空日期字段执行 `moment(value)` 转换为 DatePicker 值。代码对空串 `""` 已做 `if` 跳过（安全），但若后端写入非预期格式（如 `0000-00-00`、仅含时分秒等），`moment` 产生 Invalid Date，DatePicker 可能显示异常或报错。该风险与 B02（格式混杂）直接相关。
- **预期行为**：对日期字段做格式校验与容错，解析失败时使用安全默认值或提示。
- **触发条件**：某日期字段被写入非 `YYYY-MM-DD` / `YYYY-MM-DD HH:MM:SS` 格式时打开编辑。

## 三、移交建议（仅供 Agent 参考）

- **高优**：B13（编辑权限键错误，功能失效）应最先修复。
- **中优**：B01 / B02 / B03 / B04 / B11 涉及数据正确性、性能与状态机完整性，建议第二批处理。
- **低优**：其余为健壮性/一致性增强，可在迭代中逐步补齐。
- 修复时请保持向后兼容，勿破坏现有接口契约（字段名、响应结构）。
- 涉及数据库的字段类型/约束变更（B02/B07）需配套 migration，并评估存量数据清洗。
