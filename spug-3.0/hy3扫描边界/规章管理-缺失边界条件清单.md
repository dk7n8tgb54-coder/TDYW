# 规章管理模块 · 缺失边界条件清单（待修复）

> 用途：本文档仅梳理**当前代码中尚未覆盖的边界条件、异常输入与极端场景**，供另一 Agent 进行针对性修复。
> 范围：后端 `spug_api/apps/regulation/`（models / views / storage / urls），前端仅作为背景参考。
> 约定：不提供修复代码，只描述"缺失什么 / 触发条件 / 预期应如何处理"。严重度 `高/中/低` 为相对评估。

## A. 租户隔离（最高优先，需先确认前提）

### A-01　规章/分类/附件无任何租户隔离
- **描述**：`RegulationCategory`、`Regulation`、`RegulationAttachment` 均无 `tenant_id` 字段；所有列表/详情/树接口用 `objects.all()`，跨租户数据完全互通。
- **触发条件**：系统以多租户模式部署时，任一租户用户可读取/操作其他租户创建的规章与附件（只要有对应权限码）。
- **预期行为**：数据按 `tenant_id` 隔离（与 `evidence` 模块一致），每张表带 `tenant_id` 且查询默认加过滤。
- **当前行为**：无隔离。
- **位置**：`models.py:20/49/92`；`views.py` 各 `objects.all()/filter(...)`。
- **严重度**：高（前提确认后定）。

## B. 输入校验缺失

### B-01　字段最大长度未在 API 层校验（静默截断）
- **描述**：`title(255)`、`rule_no(100)`、`RegulationCategory.name(100)`、`RegulationAttachment.original_name(255)`、`file_path(500)` 等字段超长时，API 未拦截。Django `Model.create` 不做 `max_length` 强制校验，MySQL 会静默截断或报错。
- **触发条件**：提交超长标题/编号/文件名。
- **预期行为**：超长即返回明确错误（如"标题不能超过 255 个字符"）。
- **当前行为**：可能被截断或 500。
- **位置**：`RegulationCreateView` / `RegulationDetailView.put` / `CategoryListCreateView.post` / `CategoryDetailView.put`。
- **严重度**：中。

### B-02　更新时允许置空必填字段（空字符串）
- **描述**：编辑规章时 `title` 传入 `''` 会被 `_apply_plain_fields` 接受（`val is not None` 且 `'' != None`），生成空标题；编辑分类时 `name` 同理可置空。
- **触发条件**：PUT 规章传 `{"title":""}`；PUT 分类传 `{"name":""}`。
- **预期行为**：必填字段不允许清空，返回"XX 不能为空"。
- **当前行为**：置空成功，前端树/列表出现空白节点。
- **位置**：`views.py:469`（`_apply_plain_fields`）、`views.py:255`（`CategoryDetailView.put`）。
- **严重度**：中。

### B-03　`rule_no` 未做唯一性校验
- **描述**：`rule_no` 仅 `db_index=True` 非 `unique`。创建/编辑允许与其它规章重复。
- **触发条件**：两条规章使用相同编号。
- **预期行为**：业务上编号应唯一（至少租户内唯一），重复时报错。
- **当前行为**：允许重复，列表按编号检索会出现歧义。
- **位置**：`RegulationCreateView.post`、`RegulationDetailView.put`。
- **严重度**：中。

### B-04　分类 `name` / `code` 未做同级唯一性校验
- **描述**：同一父节点下可创建同名分类；`code` 可重复。
- **触发条件**：在相同父分类下重复建同名节点。
- **预期行为**：同级 `name` 唯一（按需 `code` 唯一）。
- **当前行为**：允许重复，左侧树出现同名分支。
- **位置**：`CategoryListCreateView.post`。
- **严重度**：低。

### B-05　列表筛选的日期参数未解析校验
- **描述**：`RegulationListView` 的 `effective_start`/`effective_end` 直接以**原始字符串**传入 `effective_date__gte/lte`，而创建/编辑接口使用 `_parse_date` 严格解析。前后不一致。
- **触发条件**：列表传 `effective_start=2024/01/01`（非 ISO）或 `effective_start=abc`。
- **预期行为**：与写入保持一致，非法格式返回明确错误；合法则按日期比较。
- **当前行为**：SQLite/严格模式下可能 500；MySQL 下非 ISO 格式静默返回错误结果。
- **位置**：`views.py:361-364`。
- **严重度**：中。

### B-06　`sort_order` 未做范围/合法性约束
- **描述**：分类与附件的 `sort_order` 接受任意整数（含负数、超大值）。
- **触发条件**：上传附件传 `sort_order=-999` 或极大值。
- **预期行为**：限制为非负合理区间（或至少非负）。
- **当前行为**：原样存储。
- **位置**：`RegulationAttachmentUploadView.post:674`。
- **严重度**：低。

## C. 业务规则缺失

### C-01　日期业务逻辑未校验（生效日期早于发布日期）
- **描述**：`publish_date` 与 `effective_date` 无先后关系校验。
- **触发条件**：`effective_date < publish_date`。
- **预期行为**：按需校验"生效日期不早于发布日期"（若产品有此约束）。
- **当前行为**：任意组合均可保存。
- **位置**：`RegulationCreateView.post`、`RegulationDetailView.put`（`_apply_date_fields`）。
- **严重度**：低（取决于业务要求）。

### C-02　状态仅有 active/retired，无反向/其它流转保护
- **描述**：`retire` 可将 active→retired；但无 retired→active 恢复入口，也无其它状态。属于设计取舍，但若产品需"恢复"则缺失。
- **触发条件**：废止后希望重新生效。
- **预期行为**：如有恢复需求，应提供反向接口或说明不可逆。
- **当前行为**：废止后只能再调 retire（返回"已废止"），无法恢复。
- **位置**：`RegulationRetireView.post`。
- **严重度**：低（确认设计意图）。

## D. 文件 / 存储边界

### D-01　允许上传空文件（0 字节）
- **描述**：上传仅校验 `file.size > MAX_FILE_SIZE`，未校验 `file.size == 0`。
- **触发条件**：上传 0 字节文件。
- **预期行为**：拒绝空文件，返回"文件内容为空"。
- **当前行为**：空文件被正常存储并生成附件记录。
- **位置**：`RegulationAttachmentUploadView.post:659-666`。
- **严重度**：中。

### D-02　上传失败（DB 异常）后遗留孤儿物理文件
- **描述**：上传流程**先写磁盘文件**（`save_upload_file`），**再在 `@transaction.atomic` 内** `RegulationAttachment.objects.create`。文件 I/O 不在 DB 事务回滚范围内。若 DB 写入抛异常（含唯一约束、连接中断等），磁盘文件不会被清理。
- **触发条件**：文件写盘成功后、DB 创建失败（含并发唯一冲突、DB 故障）。
- **预期行为**：写盘与建记录应保证原子性（如先建记录占占位、再写盘；或失败时清理已写文件）。
- **当前行为**：磁盘残留孤儿文件，无记录。
- **位置**：`views.py:687`（`save_upload_file`）早于 `views.py:690`（`create`）。
- **严重度**：中。

### D-03　删除规章时未清理"已软删除"附件的物理文件
- **描述**：`RegulationDetailView.delete` 仅遍历 `attachments.filter(is_deleted=False)` 做物理清理；随后 `regulation.delete()` 触发 FK `CASCADE` 删除**所有**附件行（含已 `is_deleted=True` 的）。那些早已软删的附件其物理文件不在循环内，永不被清理。
- **触发条件**：先软删某附件（物理文件已删或仍在）→ 再删除该规章。
- **预期行为**：删除规章时应清理其下所有附件（含已软删）的物理文件，避免孤儿文件。
- **当前行为**：已软删附件的物理文件（若此前清理失败或残留）成为孤儿。
- **位置**：`views.py:572`（仅 `is_deleted=False`）、`views.py:582`（`regulation.delete()` 级联）。
- **严重度**：中。

### D-04　单规章附件数量 / 总大小无配额限制
- **描述**：上传接口无"每规章附件数上限""单规章总大小上限"校验。
- **触发条件**：对单规章连续上传大量/超大附件。
- **预期行为**：设置合理配额并超限拒绝。
- **当前行为**：无限制，磁盘可被占满。
- **位置**：`RegulationAttachmentUploadView.post`。
- **严重度**：中。

### D-05　文件扩展名与真实内容不一致（MIME 嗅探缺失）
- **描述**：仅按扩展名白名单放行，不校验文件真实类型。扩展名伪造（如把可执行/脚本改名 `.pdf`）可绕过。
- **触发条件**：上传扩展名在白名单但内容非所声称类型的文件。
- **预期行为**：按需做 Magic/MIME 校验或病毒扫描（内网环境可评估必要性）。
- **当前行为**：仅扩展名校验。
- **位置**：`storage.py:31`（`ALLOWED_EXTENSIONS`）、`views.py:670`。
- **严重度**：低（内网可酌情）。

### D-06　上传过程磁盘写满 / I/O 错误未捕获
- **描述**：`save_upload_file` 中的 `open()/write()` 若抛 `OSError`（磁盘满、权限不足），异常未被捕获，直接 500，且可能留下半截文件（见 D-02）。
- **触发条件**：磁盘空间不足或目录无写权限。
- **预期行为**：捕获 I/O 异常，回滚并返回友好错误，清理半成品文件。
- **当前行为**：未捕获，500 + 孤儿半截文件。
- **位置**：`storage.py:155`（`save_upload_file`）。
- **严重度**：中。

### D-07　`file_hash`（MD5）计算后从未被使用
- **描述**：上传计算并存储 `file_hash`，但下载/预览均未做完整性校验，也未做去重。该字段为"死数据"。
- **触发条件**：任何下载。
- **预期行为**：要么用于下载时完整性比对，要么用于相同内容去重；否则应明确是否保留。
- **当前行为**：仅存储，无消费逻辑。
- **位置**：`storage.py:162`、`models.py:108`。
- **严重度**：低（设计取舍，记录备查）。

## E. 删除 / 清理边界

### E-01　删除规章为硬删除，无恢复机制
- **描述**：`Regulation.delete()` 直接级联删除附件行，无软删除、无回收站。
- **触发条件**：误删规章。
- **预期行为**：若产品需防误删，应提供软删除 + 恢复；否则应在前端二次确认（当前已有 `Modal.confirm`）。
- **当前行为**：不可逆物理删除。
- **位置**：`RegulationDetailView.delete`。
- **严重度**：低（确认设计意图）。

### E-02　分类删除竞态（并发）
- **描述**：`CategoryDetailView.delete` 先查"无子分类/无规章"再删；两个并发删除请求可能都通过检查后重复删除（后者报"分类不存在"）。影响较小。
- **触发条件**：同一分类并发删除。
- **预期行为**：删除应幂等或加行锁。
- **当前行为**：第二次删除返回"分类不存在"。
- **位置**：`views.py:292`。
- **严重度**：低。

## F. 权限 / 安全边界

### F-01　预览令牌未绑定请求用户（可被任意用户重放）
- **描述**：`preview-url` 生成的 `preview_token` 含 `user_id`，但 `preview-file` 视图仅校验 `attachment_id`、模块/对象绑定与时效，**不校验当前请求用户与令牌 `user_id` 一致**。令牌在 300s 内可被任何能拿到 URL 的人使用。
- **触发条件**：令牌泄露（如共享链接、日志）后，有效期内他人可预览该附件。
- **预期行为**：视安全需要，校验令牌 `user_id` 与当前用户一致（或接受"持令牌即可预览"的设计并明确）。
- **当前行为**：仅时效 + 附件绑定校验。
- **位置**：`views.py:846`（`RegulationAttachmentPreviewFileView.get`）。
- **严重度**：低（内网可酌情）。

### F-02　下载 / 预览无频率限制
- **描述**：`download` / `preview-url` / `preview-file` 无速率/频次限制，可被批量刷取占用带宽与 kkFileView 资源。
- **触发条件**：脚本循环请求下载。
- **预期行为**：按需加限流。
- **当前行为**：无限制。
- **位置**：`RegulationAttachmentDownloadView` / `PreviewUrlView` / `PreviewFileView`。
- **严重度**：低。

### F-03　`inline` 参数大小写敏感
- **描述**：`request.GET.get('inline') in ('1','true','True')`，传入 `TRUE`/`yes` 不被识别为 inline。
- **触发条件**：前端传 `inline=TRUE`。
- **预期行为**：大小写不敏感解析布尔参数。
- **当前行为**：仅限三种写法。
- **位置**：`views.py:738`。
- **严重度**：低。

## G. 并发 / 事务边界

### G-01　上传写盘与 DB 记录非原子（见 D-02）
- 已并入 **D-02**，此处不重复。

### G-02　分类 `is_leaf` 维护依赖"先查后改"非原子
- **描述**：新建子分类时先 `get(parent)` 再 `parent.is_leaf=False` 保存；并发建子分类可能出现竞争（极端情况下 `is_leaf` 状态不一致）。

- **预期行为**：用 `update` 或 `select_for_update` 保证一致性。
- **当前行为**：先读后写，弱一致。
- **位置**：`views.py:220-227`。
- **严重度**：低。

## H. 审计 / 可观测性

### H-01　预览文件访问无审计日志
- **描述**：`download` 有 `record_audit_event('download_attachment')`，但 `preview-file`（实际文件读取）无审计。预览是主要阅文途径，缺失会低估访问量。
- **触发条件**：通过预览查看附件。
- **预期行为**：预览读取也应记审计（或明确不记）。
- **当前行为**：仅 `preview-url` 获取动作记审计，文件实际流出未记。
- **位置**：`RegulationAttachmentPreviewFileView.get`（无 `record_audit_event`）。
- **严重度**：低。

### H-02　`Regulation` 缺少 `created_by` / `created_at`
- **描述**：模型仅有 `updated_by` / `updated_at`，无创建人/创建时间字段（仅审计日志留存）。
- **触发条件**：需要追溯"谁在何时创建"。
- **预期行为**：补充创建人/时间字段或确认审计日志足够。
- **当前行为**：仅 updated 字段 + 审计日志。
- **位置**：`models.py:73-74`。
- **严重度**：低。
