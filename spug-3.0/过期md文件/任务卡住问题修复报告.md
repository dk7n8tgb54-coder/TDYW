# 任务卡住pending状态问题修复报告（最终版）

## 问题现象

上传文件后，任务一直卡在 `pending` 状态，状态在 `pending` 和 `scheduled` 之间反复切换：

```
[传输] 合并状态查询成功: {status: 'pending', job_id: '171c5f9defff4af89b237a02c229339b_1772551553', ...}
[传输] 合并状态查询成功: {status: 'scheduled', job_id: '171c5f9defff4af89b237a02c229339b_1772551553', ...}
```

## 根本原因分析

### 核心问题：多进程调度器实例冲突

系统使用了**两个不同的调度器初始化路径**，导致任务提交到错误的调度器实例：

#### 初始化路径1：`apps/document/apps.py` (错误)
```python
class DocumentConfig(AppConfig):
    def ready(self):
        # 每个 Gunicorn worker 都会调用此方法
        start_scheduler()
```

问题：
- Gunicorn 配置：`-w 2`（2个worker进程）
- 每个worker都有自己的进程空间
- **每个worker都初始化了自己的调度器实例**
- 但调度器任务存储在 Redis 中，多个实例竞争同一个存储

#### 初始化路径2：`spug/wsgi.py` (正确)
```python
def initialize_scheduler():
    # 使用文件锁确保只有一个worker初始化调度器
    fcntl.flock(lock_file, fcntl.LOCK_EX | fcntl.LOCK_NB)
    # 只有第一个worker能执行到这里
    start_scheduler()
```

正确点：
- 使用文件锁确保单实例
- 只有一个worker持有调度器实例

### 问题复现流程

```
1. Gunicorn 启动，创建2个worker进程
2. Worker 1:
   - apps.py: 初始化调度器A（在worker 1进程中）
   - wsgi.py: 获得文件锁，初始化调度器B（在worker 1进程中）
3. Worker 2:
   - apps.py: 初始化调度器C（在worker 2进程中）
   - wsgi.py: 文件锁被占用，跳过初始化
```

任务提交时：
```
4. 请求到达 worker 1
   - scheduler.get_scheduler() 返回 调度器A（全局变量）
   - 提交任务到 调度器A（未运行）
5. 调度器B 在运行，但没有收到任务
6. 任务永远卡在 pending
```

日志证据：
```
[INFO] [APScheduler] Scheduler running state: False
[INFO] [APScheduler] Merge job submitted successfully
```

### 次要问题：job_id生成不一致（已在之前修复）

`merge_task.py:45` 行的 job_id 生成逻辑与调度器传入的 job_id 不一致。

## 修复方案

### 修复1：禁用 apps.py 中的调度器初始化

**文件**：`data/backend/apps/document/apps.py`

```python
def ready(self):
    """
    Django应用启动时的初始化逻辑

    注意：APScheduler 调度器已在 wsgi.py 中通过文件锁方式初始化
    这里不再重复初始化，避免多实例问题
    """
    logger.info('[DocumentConfig] ready() method called')

    # APScheduler 由 wsgi.py 初始化（使用文件锁确保单实例）
    # 这里跳过调度器初始化，避免多进程场景下的多实例问题
    logger.info('[DocumentConfig] Skipping APScheduler initialization (handled by wsgi.py)')

    return
```

**修复说明**：
- 移除 apps.py 中的调度器初始化逻辑
- 只保留 wsgi.py 中的单实例初始化
- 避免多个调度器实例竞争

### 修复2：增强提交任务时的日志

**文件**：`data/backend/apps/document/libs/scheduler.py`

```python
def submit_merge_job(job_id, job_data):
    logger.info(f'[APScheduler] submit_merge_job called: job_id={job_id}')
    job_data['job_id'] = job_id

    scheduler = get_scheduler()
    logger.info(f'[APScheduler] Scheduler instance: {scheduler}')
    logger.info(f'[APScheduler] Scheduler running state: {scheduler.running}')

    if not scheduler.running:
        logger.error(f'[APScheduler] ERROR: Scheduler is not running!')
        raise RuntimeError(f'Scheduler is not running')

    try:
        logger.info(f'[APScheduler] About to add job to scheduler: {job_id}')
        scheduler.add_job(...)
        logger.info(f'[APScheduler] Merge job submitted successfully')
        logger.info(f'[APScheduler] Total jobs in scheduler: {len(scheduler.get_jobs())}')
    except Exception as e:
        logger.error(f'[APScheduler] Failed to submit merge job: {e}', exc_info=True)
        raise
```

**修复说明**：
- 添加调度器实例和状态日志
- 提交任务前检查调度器是否运行
- 记录任务总数，便于调试

### 修复3：清理卡住的任务文件

```bash
docker exec spug rm -f /data/spug/spug_api/storage/document_merge_tasks/*.task
```

## 技术细节

### 为什么 Gunicorn 多worker会导致问题？

Gunicorn 的多worker模式：
```
Gunicorn master process
  ├─ Worker 1 (进程1)
  │   ├─ apps.py: 初始化调度器A（未运行）
  │   └─ wsgi.py: 初始化调度器B（运行中）
  │
  └─ Worker 2 (进程2)
      ├─ apps.py: 初始化调度器C（未运行）
      └─ wsgi.py: 跳过初始化（锁被占用）
```

每个进程有独立的内存空间，Python 的全局变量 `_scheduler` 在不同进程中互不影响。

### 为什么文件锁能解决这个问题？

wsgi.py 中的文件锁机制：
```python
fcntl.flock(lock_file, fcntl.LOCK_EX | fcntl.LOCK_NB)
```

- `LOCK_EX`：排他锁
- `LOCK_NB`：非阻塞模式
- 第一个获取锁的worker初始化调度器
- 其他worker获取锁失败，跳过初始化

### 为什么任务提交到错误的调度器？

`scheduler.py` 中的单例模式：
```python
_scheduler = None

def get_scheduler():
    global _scheduler
    if _scheduler is None:
        _scheduler = init_scheduler()  # 创建新实例
    return _scheduler
```

问题：
- 每个 worker 进程都有独立的 `_scheduler` 变量
- `apps.py` 中初始化的实例赋值给 worker 1 的 `_scheduler`
- `wsgi.py` 中初始化的实例也赋值给 worker 1 的 `_scheduler`（覆盖了）
- `submit_merge_job` 调用 `get_scheduler()` 返回哪个实例取决于初始化顺序

### 为什么调度器状态是 False？

```python
[INFO] [APScheduler] Scheduler running state: False
[INFO] [APScheduler] Merge job submitted successfully
```

因为调用的调度器实例是 `apps.py` 初始化的那个（未运行），而 `wsgi.py` 初始化的实例（运行中）没有收到任务。

## 结论

问题根源是 **Gunicorn 多worker 模式下，apps.py 和 wsgi.py 分别初始化了不同的调度器实例**，导致任务提交到未运行的实例。

修复方案：**禁用 apps.py 中的调度器初始化，只使用 wsgi.py 中受文件锁保护的单实例**。

修复后，调度器将在唯一的 worker 进程中运行，任务能正确提交和执行。
