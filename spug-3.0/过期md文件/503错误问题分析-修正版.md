**修正时间**: 2026-03-31  
**修正依据**: 生产环境最佳实践审查反馈

## 一、原方案问题与修正

### 1.1 遗漏的关键瓶颈

| 遗漏项 | 影响 | 修正方案 |
|--------|------|----------|
| **WSGI/Gunicorn进程数不足** | 503的直接诱因之一 | 补充Gunicorn优化配置 |
| **队列混用风险** | 批量任务阻塞核心业务 | 队列隔离 |
| **暴力重启Celery** | 任务丢失、数据不一致 | 优雅停机 |

### 1.2 需要废弃的反模式

| 原方案 | 问题 | 修正 |
|--------|------|------|
| 前端拆分批量为单条请求 | 请求量暴增，加重503 | **保持批量接口，后端统一处理** |
| `PREFETCH_MULTIPLIER=4` | 长任务阻塞、内存堆积 | **保持为1** |
| `select_for_update(nowait=True)` | 直接抛异常，失败率高 | **使用`skip_locked`或移除** |
| 固定2s重试503 | 请求雪崩 | **指数退避+幂等校验** |
| 循环内`sleep(0.5)` | 执行极慢，队列积压 | **批量SQL优化** |

## 二、问题根因分析（修正版）

### 2.1 503触发的真实链路

```
用户发起批量删除请求
    ↓
Nginx接收请求
    ↓
Gunicorn/WSGI处理
    └── 如果worker进程耗尽（默认可能只有2-4个）
        └── 返回503 Service Unavailable
    └── 如果worker正常
        └── 转发给Django
            ↓
            调用Celery任务
            └── 如果Celery队列积压
                └── 任务等待执行
                └── HTTP超时（30s）
                    └── 前端显示超时错误
```

### 2.2 三大瓶颈（按优先级）

| 优先级 | 瓶颈 | 当前状态 | 影响 |
|--------|------|----------|------|
| 🔴 P0 | **WSGI进程不足** | 未检查 | 最直接的503来源 |
| 🔴 P0 | **Celery并发低** | -c 4 | 队列积压 |
| 🟠 P1 | **数据库连接** | CONN_MAX_AGE=0 | 连接开销大 |

## 三、生产级解决方案

### 方案1: Gunicorn配置优化（立即实施）

**检查当前配置**:
```bash
# 查看Gunicorn进程数
ps aux | grep gunicorn

# 查看启动命令
cat /path/to/gunicorn_start.sh
```

**优化配置**:
```bash
# 启动脚本（supervisor配置）
# /etc/supervisor/conf.d/spug.conf

[program:spug]
command=/path/to/venv/bin/gunicorn spug.wsgi:application \
    -b 0.0.0.0:8000 \
    --workers=4 \                    # 2*CPU+1，4核CPU配4-6个worker
    --worker-class=sync \            # 同步worker，适合Django
    --worker-connections=1000 \      # 每个worker的连接数
    --max-requests=5000 \            # 处理5000请求后重启，防内存泄漏
    --max-requests-jitter=100 \      # 随机抖动，避免同时重启
    --timeout=60 \                   # 60秒超时
    --keep-alive=2 \                 # 保持连接2秒
    --graceful-timeout=30            # 优雅停机30秒
```

**为什么重要**:
- Gunicorn是Django的入口，worker不足直接导致503
- 4个worker可以处理4个并发HTTP请求
- 超过4个并发请求时，Nginx会返回503

### 方案3: 后端批量任务优化

**优化目标**:
- 减少数据库锁竞争
- 提高批量处理效率
- 避免任务阻塞

```python
# apps/document/tasks/batch.py

@shared_task(
    bind=True,
    max_retries=3,
    default_retry_delay=30,
    queue='document.batch',
    # 不要全局rate_limit，避免业务不可用
)
def batch_delete_transfers(self, transfer_ids, request_user_id, request_tenant_id):
    """
    异步批量删除传输记录 - 生产优化版
    """
    from apps.document.models import DocumentTransfer
    from apps.document.constants import TransferStatus
    from django.db import transaction
    
    logger.info(f'[Celery] Batch delete start: count={len(transfer_ids)}')
    
    # 【优化1】先批量查询，减少数据库往返
    transfers = DocumentTransfer.objects.filter(
        id__in=transfer_ids,
        tenant_id=request_tenant_id
    ).select_related()
    
    # 预分类，减少循环内判断
    deletable_ids = []
    deletable_transfers = []
    skipped_ids = []
    
    deletable_states = {
        TransferStatus.COMPLETED.value,
        TransferStatus.FAILED.value,
        TransferStatus.CANCELED.value
    }
    
    for transfer in transfers:
        if transfer.status in deletable_states:
            deletable_ids.append(transfer.id)
            deletable_transfers.append(transfer)
        else:
            skipped_ids.append(transfer.id)
    
    # 【优化2】批量删除，减少事务开销
    deleted_count = 0
    chunk_cleaned_ids = []
    
    # 分批处理，每批10个，平衡性能与锁竞争
    BATCH_SIZE = 10
    for i in range(0, len(deletable_transfers), BATCH_SIZE):
        batch = deletable_transfers[i:i+BATCH_SIZE]
        batch_ids = [t.id for t in batch]
        
        try:
            with transaction.atomic():
                # 【优化3】批量删除，而非循环单条
                # 先删文件记录
                DocumentTransfer.objects.filter(
                    id__in=batch_ids
                ).delete()
                
                deleted_count += len(batch)
                
                # 批量清理分片（事务外）
                for transfer in batch:
                    if transfer.file_hash and transfer.total_chunks > 0:
                        try:
                            _cleanup_transfer_chunks(transfer)
                            chunk_cleaned_ids.append(transfer.id)
                        except Exception as e:
                            logger.warning(f'Chunk cleanup failed: {e}')
                            # 不阻止删除流程
                
        except Exception as e:
            logger.error(f'Batch delete error: {e}')
            # 单条重试（降级策略）
            for transfer in batch:
                try:
                    with transaction.atomic():
                        transfer.delete()
                        deleted_count += 1
                except Exception as e2:
                    logger.error(f'Single delete failed: {transfer.id}, {e2}')
    
    result = {
        'deleted': deleted_count,
        'skipped': len(skipped_ids),
        'total': len(transfer_ids),
        'chunk_cleaned': len(chunk_cleaned_ids),
    }
    
    logger.info(f'[Celery] Batch delete completed: {result}')
    return result
```

**关键优化点**:
1. **批量查询**: 一次查询所有记录，减少N+1问题
2. **预分类**: 循环外判断状态，减少锁持有时间
3. **批量删除**: 使用`filter().delete()`，单条SQL删除多条
4. **无nowait**: 避免直接抛异常，降低失败率
5. **无sleep**: 提高执行效率

### 方案4: 前端优化（保持批量接口）

**核心原则**: 前端发送1个批量请求，后端统一处理

```javascript
// stores/upload/core/transfer.js - 修正版

/**
 * 批量删除传输记录 - 生产优化版
 * @param {Array<number>} transferIds - 传输ID列表
 */
async batchDeleteTransfers(transferIds) {
  if (!transferIds || transferIds.length === 0) {
    return { success: true, deleted: 0 };
  }

  // 【优化】一次性发送批量请求，不拆分
  // 后端使用Celery异步处理
  try {
    const result = await http.post('/api/document/transfer/batch_delete/', {
      transfer_ids: transferIds
    });
    
    // 返回Celery任务ID，可轮询状态
    if (result.task_id) {
      message.loading(`已提交批量删除任务 (${transferIds.length}个)，正在处理...`, 2);
      
      // 可选：轮询任务状态
      await this.pollTaskStatus(result.task_id);
      
      return {
        success: true,
        taskId: result.task_id,
        message: '批量删除任务已完成'
      };
    }
    
    return result;
  } catch (error) {
    // 错误处理
    console.error('Batch delete failed:', error);
    message.error(error.message || '批量删除失败');
    throw error;
  }
}

/**
 * 轮询Celery任务状态
 */
async pollTaskStatus(taskId, maxAttempts = 30) {
  const { http } = await import('libs');
  
  for (let i = 0; i < maxAttempts; i++) {
    await new Promise(resolve => setTimeout(resolve, 2000)); // 2秒间隔
    
    try {
      const status = await http.get(`/api/celery/task_status/?task_id=${taskId}`);
      
      if (status.state === 'SUCCESS') {
        return status.result;
      }
      if (status.state === 'FAILURE') {
        throw new Error(status.error || '任务执行失败');
      }
      // PENDING/PROGRESS继续轮询
    } catch (e) {
      // 轮询失败继续
    }
  }
  
  // 超时，但任务可能仍在执行
  return { pending: true };
}
```

### 方案5: 指数退避重试机制

```javascript
// libs/http.js - 修正版

import axios from 'axios';

const http = axios.create({
  baseURL: '/api/',
  timeout: 30000,
});

// 指数退避配置
const RETRY_CONFIG = {
  maxRetries: 3,
  initialDelay: 1000,      // 初始1秒
  maxDelay: 8000,          // 最大8秒
  retryStatusCodes: [503, 502, 504],
  // 只重试幂等操作（GET、DELETE、幂等POST）
  retryMethods: ['get', 'delete', 'head', 'options'],
};

http.interceptors.response.use(
  response => response.data,
  async error => {
    const { config, response } = error;
    
    // 判断是否可重试
    if (!response || !RETRY_CONFIG.retryStatusCodes.includes(response.status)) {
      return Promise.reject(error);
    }
    
    // 非幂等方法不重试（避免重复操作）
    if (!RETRY_CONFIG.retryMethods.includes(config.method)) {
      return Promise.reject(error);
    }
    
    config.__retryCount = config.__retryCount || 0;
    
    if (config.__retryCount >= RETRY_CONFIG.maxRetries) {
      return Promise.reject(error);
    }
    
    config.__retryCount += 1;
    
    // 指数退避计算: delay = min(initialDelay * 2^retryCount, maxDelay)
    const delay = Math.min(
      RETRY_CONFIG.initialDelay * Math.pow(2, config.__retryCount - 1),
      RETRY_CONFIG.maxDelay
    );
    
    console.log(`[HTTP] ${response.status}错误，${delay}ms后第${config.__retryCount}次重试...`);
    
    await new Promise(resolve => setTimeout(resolve, delay));
    return http(config);
  }
);

export default http;
```

### 方案7: 监控告警（生产落地）

```python
# apps/document/monitoring.py

from celery import current_app as celery_app
from django.db import connection
import logging

logger = logging.getLogger(__name__)

def check_system_health():
    """系统健康检查 - 可集成到Prometheus或定期任务"""
    health = {
        'celery': check_celery_health(),
        'database': check_database_health(),
        'timestamp': timezone.now().isoformat(),
    }
    
    # 记录到日志，供ELK/日志系统分析
    logger.info(f'[HealthCheck] {health}')
    
    return health

def check_celery_health():
    """检查Celery状态"""
    try:
        inspector = celery_app.control.inspect()
        active = inspector.active()
        scheduled = inspector.scheduled()
        
        # 统计各队列任务数
        queue_stats = {}
        total_active = 0
        
        if active:
            for worker, tasks in active.items():
                count = len(tasks)
                total_active += count
                queue_stats[worker] = count
        
        # 告警阈值
        alerts = []
        if total_active > 50:  # 积压过多
            alerts.append(f'Celery任务积压: {total_active}')
        
        return {
            'status': 'ok',
            'active_tasks': total_active,
            'scheduled_tasks': len(scheduled) if scheduled else 0,
            'queue_stats': queue_stats,
            'alerts': alerts,
        }
    except Exception as e:
        return {
            'status': 'error',
            'error': str(e),
        }

def check_database_health():
    """检查数据库状态"""
    try:
        with connection.cursor() as cursor:
            # MySQL连接数
            cursor.execute("SHOW STATUS LIKE 'Threads_connected'")
            threads_connected = int(cursor.fetchone()[1])
            
            cursor.execute("SHOW VARIABLES LIKE 'max_connections'")
            max_connections = int(cursor.fetchone()[1])
            
            usage_percent = (threads_connected / max_connections) * 100
            
            # 告警阈值
            alerts = []
            if usage_percent > 80:
                alerts.append(f'数据库连接使用率过高: {usage_percent:.1f}%')
            
            return {
                'status': 'ok',
                'threads_connected': threads_connected,
                'max_connections': max_connections,
                'usage_percent': round(usage_percent, 2),
                'alerts': alerts,
            }
    except Exception as e:
        return {
            'status': 'error',
            'error': str(e),
        }

# 集成到Django Admin或API
from django.http import JsonResponse

def health_check_api(request):
    """健康检查API"""
    health = check_system_health()
    
    # 如果有告警，返回503状态码
    has_alerts = any(
        h.get('alerts') for h in [health['celery'], health['database']]
    )
    
    status_code = 503 if has_alerts else 200
    return JsonResponse(health, status=status_code)
```
