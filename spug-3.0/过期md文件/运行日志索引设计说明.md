# 运行日志模块索引设计说明

## 概述

运行日志模块包含两个核心复合索引，针对多租户场景下的查询特点进行优化设计，确保租户隔离、查询高效。

---

## 索引1: `idx_runlog_tenant_status_severity`

### 定义
```sql
INDEX idx_runlog_tenant_status_severity (tenant_id, status, severity)
```

### 用途
支持**状态和级别过滤**的查询，用于统计接口和筛选功能。

### 典型查询场景
```python
# 1. 查询某个租户下的"处理中"事件
logs = RunLog.objects.filter(
    tenant_id='admin',
    status='in_progress'
)

# 2. 查询某个租户下的"P0紧急"事件
logs = RunLog.objects.filter(
    tenant_id='admin',
    severity='P0'
)

# 3. 统计查询（聚合）
logs.aggregate(
    in_progress_count=Count('id', filter=Q(status='in_progress')),
    p0_count=Count('id', filter=Q(severity='P0'))
)
```

### 索引工作原理
复合索引遵循**最左前缀原则**，可以高效支持以下查询：

| 查询条件 | 是否使用索引 | 说明 |
|---------|------------|------|
| `WHERE tenant_id = 'admin' AND status = 'in_progress'` | ✅ 完全使用 | (tenant_id, status) 匹配索引前两列 |
| `WHERE tenant_id = 'admin' AND severity = 'P0'` | ⚠️ 部分使用 | 只使用tenant_id列 |
| `WHERE tenant_id = 'admin' AND status = 'in_progress' AND severity = 'P0'` | ✅ 完全使用 | 三列都匹配 |
| `WHERE status = 'in_progress'` | ❌ 不使用 | 缺少最左列tenant_id（租户过滤必须） |

### 为什么这样设计？
- **tenant_id在最左侧**：所有查询都必须有租户过滤（安全要求），这样索引最高效
- **status和severity**：统计接口需要频繁按状态和级别聚合

## 索引2: `idx_runlog_tenant_created`

### 定义
```sql
INDEX idx_runlog_tenant_created (tenant_id, created_at)
```

### 用途
支持**时间范围查询**和**列表排序**。

### 典型查询场景
```python
# 1. 列表查询（按时间倒序）
logs = RunLog.objects.filter(
    tenant_id='admin'
).order_by('-created_at', '-id')

# 2. 日期筛选
logs = RunLog.objects.filter(
    tenant_id='admin',
    created_at__startswith='2026-03-19'  # 或使用 range 查询
)

# 3. 日期范围查询
logs = RunLog.objects.filter(
    tenant_id='admin',
    created_at__gte=start_date,
    created_at__lte=end_date
)

# 4. 分页查询
logs = logs[start_index:end_index]
```

### 索引工作原理
这是一个**复合索引**，可以：
1. 快速定位到特定租户的数据
2. 按created_at排序（支持ORDER BY）
3. 支持时间范围过滤

### 优化效果对比

**没有索引时：**
```sql
-- 全表扫描，然后排序
EXPLAIN: type=ALL, Using filesort
rows=3000
```

**有索引时：**
```sql
-- 索引扫描，避免排序
EXPLAIN: type=range, Using index
rows=20 (分页查询)
```

## 两个索引的协同工作

在实际查询中，这两个索引分别处理不同的查询类型：

| 查询类型 | 使用的索引 | 示例 |
|---------|-----------|------|
| 列表查询 | `idx_runlog_tenant_created` | `GET /api/runlog/` |
| 状态筛选 | `idx_runlog_tenant_status_severity` | `WHERE status='in_progress'` |
| 级别筛选 | `idx_runlog_tenant_status_severity` | `WHERE severity='P0'` |
| 统计聚合 | `idx_runlog_tenant_status_severity` | `statistics`接口 |
| 日期范围 | `idx_runlog_tenant_created` | `WHERE created_at__range=(...)` |

---

## 索引设计原则

1. **最左前缀原则**：tenant_id必须在最左侧，因为所有查询都要租户过滤
2. **查询覆盖**：索引列覆盖常用的WHERE、ORDER BY条件
3. **避免冗余**：不创建太多索引（每个索引都会增加写入成本）
4. **区分度优先**：tenant_id区分度高，放在前面效率最好

这两个索引是针对运行日志模块的**特定查询模式**设计的，已经覆盖了90%以上的查询场景。

## 注意事项

1. **租户过滤必须**：所有查询都必须包含tenant_id条件，否则索引无法生效
2. **索引维护**：数据量大时，索引会增加写入开销，建议定期优化表
3. **监控索引使用**：使用EXPLAIN分析慢查询，确保索引被正确使用
4. **数据归档**：建议定期归档历史数据，保持表数据量在合理范围（<10000条）
