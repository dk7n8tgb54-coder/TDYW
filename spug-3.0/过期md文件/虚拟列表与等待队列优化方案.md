# 虚拟列表与等待队列优化方案

## 问题背景

当前系统同时存在两个控制机制：

1. **`MAX_DISPLAY_COUNT` (30个)**：限制传输列表显示的任务数量
2. **虚拟列表**：解决大批量任务的前端渲染性能问题

这两个机制产生了**功能重叠**，需要进行职责分离和优化。

## 当前架构分析

### 现有流程

```
用户添加文件
    ↓
判断当前显示队列数量 >= MAX_DISPLAY_COUNT (30)
    ↓
    ├── 是 → 放入 pendingDisplayQueue（等待显示队列）
    ↓
    └── 否 → 加入显示队列，开始上传
                ↓
         任务完成/删除后，从 pendingDisplayQueue 补充
```

### 存在的问题

| 问题 | 说明 |
|------|------|
| **功能耦合** | `MAX_DISPLAY_COUNT` 同时承担"显示限制"和"并发控制"两个职责 |
| **用户体验差** | 用户上传100个文件，只看到30个，其余在"等待中" |
| **虚拟列表价值未充分利用** | 虚拟列表支持1000+流畅渲染，但用户仍被限制看到30个 |

## 优化方案

### 核心思想

**职责分离**：
- **虚拟列表**：负责前端渲染性能（支持1000+任务流畅显示）
- **后端并发控制**：限制同时上传的文件数量（保护服务器资源）
- **取消显示限制**：让用户能看到所有任务状态

### 架构调整

```
┌─────────────────────────────────────────────────────────────┐
│                         用户上传文件                          │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  显示层（虚拟列表）                                            │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  所有任务都显示（1000+ 也能流畅渲染）                       │ │
│  │  状态：waiting / calculating / uploading / completed...  │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  调度层（并发控制）                                            │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  最多同时处理 MAX_CONCURRENT_UPLOADS (3个) 个上传任务      │ │
│  │  其他任务保持 waiting 状态，不占用服务器资源                │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  后端服务                                                      │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  同时处理的请求数 <= 3，服务器资源得到保护                  │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

## 实施步骤

### 步骤1：调整常量配置

**文件**：`spug_web/src/pages/document/stores/constants/upload.js`

```javascript
export const UPLOAD_CONSTANTS = {
  // ... 其他常量
  
  // 调整前：30个（兼顾渲染和并发）
  // 调整后：100个（虚拟列表支持1000+渲染，不再受显示限制）
  MAX_DISPLAY_COUNT: 100,
  
  // 真正的并发控制 - 同时上传的任务数
  MAX_CONCURRENT_UPLOADS: 3,  // 保持3个并发上传
  
  // 虚拟列表配置（已实施）
  VIRTUAL_LIST: {
    ITEM_HEIGHT: 80,
    OVERSCAN_COUNT: 5,
    LIST_MAX_HEIGHT: 400,
    LIST_MIN_HEIGHT: 100,
    FALLBACK_THRESHOLD: 50,  // 低于50个使用原生渲染
  },

```

### 步骤2：修改队列调度逻辑

**文件**：`spug_web/src/pages/document/stores/upload/core/queue.js`

**调整前**：超过30个就放入等待队列
```javascript
addToQueue(item, tenantId) {
  const currentQueue = this.uploadQueue[tenantId] || [];
  
  // 问题：这里限制了显示数量
  if (currentQueue.length >= UPLOAD_CONSTANTS.MAX_DISPLAY_COUNT) {
    this.addToPendingDisplayQueue(item);
    return;
  }
  
  // ... 加入队列
}
```

**调整后**：根据后端并发控制决定是否等待
```javascript
addToQueue(item, tenantId) {
  // 所有任务都加入显示队列（虚拟列表支持1000+）
  if (!this.uploadQueue[tenantId]) {
    this.uploadQueue[tenantId] = [];
  }
  this.uploadQueue[tenantId].push(item);
  
  // 并发控制：检查当前活跃上传数
  const activeCount = this.getActiveUploadCount(tenantId);
  if (activeCount >= UPLOAD_CONSTANTS.MAX_CONCURRENT_UPLOADS) {
    // 标记为 waiting 状态，等待调度
    item.status = 'waiting';
  } else {
    // 可以立即开始上传
    this.startUpload(item);
  }
}

/**
 * 获取当前正在上传的任务数
 */
getActiveUploadCount(tenantId) {
  const queue = this.uploadQueue[tenantId] || [];
  return queue.filter(item => 
    ['calculating', 'uploading', 'merging'].includes(item.status)
  ).length;
}

/**
 * 当一个任务完成时，调度下一个 waiting 任务
 */
scheduleNextUpload(tenantId) {
  const queue = this.uploadQueue[tenantId] || [];
  const waitingItem = queue.find(item => item.status === 'waiting');
  
  if (waitingItem) {
    this.startUpload(waitingItem);
  }
}
```

**UploadPanel.js 同步修改**：

### 步骤4：完善状态流转

```
用户添加文件
    ↓
加入显示队列（所有用户都可见）
    ↓
检查并发数 < MAX_CONCURRENT_UPLOADS ?
    ↓
    ├── 是 → status = 'calculating' → 开始MD5计算 → uploading → completed
    ↓
    └── 否 → status = 'waiting'（用户可见，显示"等待中"）
                  ↓
         当前有任务完成
                  ↓
         自动调度：waiting → calculating → uploading → completed
```

## 预期效果

### 性能对比

| 场景 | 调整前 | 调整后 | 改进 |
|------|--------|--------|------|
| 上传100个文件 | 显示30个，70个在等待队列 | 显示全部100个 | ✅ 用户可见性提升 |
| DOM节点数 | ~900个（30个 × 30节点） | ~900个（虚拟列表） | ✅ 渲染性能不变 |
| 服务器并发 | 30个（过大） | 3个（合理） | ✅ 服务器压力降低 |
| 用户体验 | 不知道任务状态 | 实时看到所有任务 | ✅ 体验提升 |

### 关键指标

| 指标 | 目标值 |
|------|--------|
| 最大显示任务数 | 无限制（虚拟列表支持1000+） |
| 同时上传任务数 | 3个（可配置） |
| 页面滚动帧率 | 60fps |
| 内存占用 | < 100MB（1000个任务） |

## 风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 大量任务同时 waiting 占用内存 | 低 | 任务对象本身占用很小，1000个约几MB |
| 用户同时开始大量上传导致服务器压力 | 低 | 并发控制限制为3个，不受影响 |
| 虚拟列表在大数量下的稳定性 | 低 | react-window 成熟稳定，已广泛验证 |

## 回滚方案

如果出现问题，可以快速回滚：

1. 恢复 `MAX_DISPLAY_COUNT: 30`
2. 恢复 `pendingDisplayQueue` 相关代码
3. 恢复 `UploadPanel.js` 的显示逻辑

## 总结

通过将**显示限制**与**并发控制**分离：

- ✅ **前端**：虚拟列表提供无限显示能力，用户能看到所有任务
- ✅ **后端**：精确的并发控制（3个），保护服务器资源
- ✅ **体验**：实时状态可见，减少用户焦虑
- ✅ **性能**：DOM节点数保持稳定，不随任务数增加

这个方案充分发挥了虚拟列表的优势，同时保持了系统的稳定性。
