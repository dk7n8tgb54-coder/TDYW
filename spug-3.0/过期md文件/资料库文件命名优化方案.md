# 资料库文件命名优化方案

**日期**: 2026-03-14  
**涉及模块**: 资料库（Document）文件上传、复制、移动功能

---

## 一、现状分析

### 1.1 当前问题

当前文件命名方案将所有信息（原始文件名、用户ID、时间戳、随机串）都塞入物理文件名，导致：

```
84-【哑铃】第11周，周三，臀腿+核心，围度突破2023-06-02_15_1773480302_8d09d33e.mp4
└─────────────────────────────────────────────────────────────────────────┘
                    超长物理文件名（78字符）
```

**问题清单**:

| 问题 | 影响 |
|-----|------|
| 文件名过长 | 超出某些文件系统限制（如FAT32的255字节） |
| 可读性差 | 用户从文件名无法识别内容 |
| 信息冗余 | 用户ID、时间戳对物理存储无意义 |
| 路径过长 | Windows路径超过260字符时出错 |
| 编码问题 | 中文+特殊符号在某些系统兼容性差 |

### 1.2 当前三层命名现状

| 层级 | 当前实现 | 示例 |
|-----|---------|------|
| **前端显示** (display_name) | 可为null，从物理名解析 | `84-【哑铃】..._15_1773480302_8d09d33e.mp4` |
| **数据库name** | 物理文件名 | `84-【哑铃】..._15_1773480302_8d09d33e.mp4` |
| **物理文件** (file_path) | 带hash的随机名 | `storage/.../84-【哑铃】..._15_1773480302_8d09d33e.mp4` |

**核心问题**: 三层都使用物理文件名，没有分离逻辑。

## 二、工程最佳实践

### 2.1 业界标准方案

参考主流云存储（AWS S3、阿里云OSS、腾讯云COS）的设计：

```
┌─────────────────────────────────────────┐
│  前端显示层  │  原始文件名 (用户友好)      │
│  display_name │ "哑铃-臀腿训练.mp4"        │
├─────────────────────────────────────────┤
│  数据库层   │  逻辑文件名 (可识别+唯一)    │
│  name       │ "哑铃-臀腿训练_001.mp4"      │
├─────────────────────────────────────────┤
│  物理存储层  │  随机唯一名 (防冲突)        │
│  file_path  │ "1773480302_8d09d33e.mp4"   │
└─────────────────────────────────────────┘
```

### 2.2 分层职责

| 层级 | 职责 | 命名原则 |
|-----|------|---------|
| **display_name** | 用户界面展示 | 保留原始文件名，最友好 |
| **name** | 数据库索引、API交互 | 原始文件名+序号，解决同名 |
| **file_path** | 物理存储定位 | 纯随机串，最短、唯一 |

### 2.3 命名规范对比

| 方案 | 物理文件名长度 | 可读性 | 唯一性保障 |
|-----|--------------|-------|-----------|
| **当前方案** | 60-100字符 | 差 | hash+timestamp+random |
| **优化方案** | 20-30字符 | 无（不需要） | timestamp+random8 |
| **业界标准** | 16-32字符 | 无 | UUID或随机串 |

## 三、优化方案设计

### 3.1 新命名规范

#### 物理文件名（最短化）

```python
# 新规范: 时间戳(10位) + 随机串(8位) + 扩展名
physical_name = f"{timestamp}_{random8}{ext}"
# 示例: 1773480302_8d09d33e.mp4 (27字符)

# 旧规范对比
old_name = f"{file_base}_{user_id}_{timestamp}_{random8}{ext}"
# 示例: 84-【哑铃】..._15_1773480302_8d09d33e.mp4 (78字符)
```

**优势**:
- 长度减少60%+
- 无中文/特殊字符，跨平台兼容
- 时间戳+8位随机足够唯一（碰撞概率<1/10^12）

#### 数据库name（可读+唯一）

```python
# 新规范: 原始文件名 + 3位序号（解决同名冲突）
logical_name = f"{original_name}_{counter:03d}{ext}"
# 示例: 哑铃-臀腿训练_001.mp4

# 无冲突时无序号
logical_name = f"{original_name}{ext}"
# 示例: 哑铃-臀腿训练.mp4
```

**优势**:
- 保留原始文件名可读性
- 3位序号处理99.9%冲突场景
- 数据库查询友好（可索引）

#### display_name（用户友好）

```python
# 纯原始文件名（无序号）
display_name = f"{original_name}{ext}"
# 示例: 哑铃-臀腿训练.mp4
```

**优势**:
- 用户看到最自然的名字
- 同名时前端可额外标识

### 3.2 完整示例

| 场景 | display_name | name | file_path |
|-----|-------------|------|-----------|
| **首次上传** | `哑铃-臀腿训练.mp4` | `哑铃-臀腿训练.mp4` | `1773480302_8d09d33e.mp4` |
| **同名上传** | `哑铃-臀腿训练.mp4` | `哑铃-臀腿训练_001.mp4` | `1773480303_a1b2c3d4.mp4` |
| **复制文件** | `哑铃-臀腿训练.mp4` | `哑铃-臀腿训练_002.mp4` | `1773480304_e5f6g7h8.mp4` |
| **移动冲突** | `哑铃-臀腿训练.mp4` | `哑铃-臀腿训练_003.mp4` | `1773480302_8d09d33e.mp4` |

### 3.3 存储路径结构

```
storage/
├── documents/
│   ├── public/                    # 公共空间
│   │   ├── 1773480302_8d09d33e.mp4
│   │   └── 1773480303_a1b2c3d4.pdf
│   └── tenant_1/                  # 私有空间（按租户）
│       ├── folder_10/
│       │   ├── 1773480304_e5f6g7h8.docx
│       │   └── 1773480305_i9j0k1l2.xlsx
│       └── 1773480306_m3n4o5p6.jpg
```

**优势**:
- 物理文件名短，路径总长度可控
- 目录结构清晰（按租户/文件夹）
- 便于直接浏览存储目录

## 四、实施计划

### 4.1 修改范围

| 文件 | 修改内容 | 优先级 |
|-----|---------|--------|
| `upload.py` | 修改物理文件名生成逻辑 | P0 |
| `file.py` | 修改复制时的文件名生成 | P0 |
| `folder.py` | 修改复制时的文件名生成 | P0 |
| `merge.py` | 确保合并后文件名符合规范 | P1 |

### 4.2 代码变更示例

#### upload.py 修改

```python
# 修改前
file_base = file_hash[:8]  # 取hash前8位
timestamp = int(time.time())
random_suffix = uuid.uuid4().hex[:8]
unique_name = f"{file_base}_{request.user.id}_{timestamp}_{random_suffix}{file_ext}"

# 修改后（简化物理名）
timestamp = int(time.time())
random_suffix = uuid.uuid4().hex[:8]
physical_name = f"{timestamp}_{random_suffix}{file_ext}"

# name使用原始文件名+序号（由数据库唯一性检查生成）
logical_name = generate_unique_name(FileModel, original_name, folder, user)

# display_name使用纯原始文件名
display_name = original_name
```

#### file.py 复制修改

```python
# 修改前
unique_name = f"copy_{file.id}_{request.user.id}_{timestamp}_{random_suffix}{file_ext}"

# 修改后
physical_name = f"{timestamp}_{random_suffix}{file_ext}"
logical_name = generate_unique_name(FileModel, original_display_name, target_folder, user)
display_name = original_display_name
```

### 4.3 兼容性策略

| 方案 | 说明 |
|-----|------|
| **历史数据** | 保持现状，不迁移（功能正常） |
| **新上传** | 采用新命名规范 |
| **过渡期** | 支持新旧两种命名解析 |
| **完全切换** | 6个月后废弃旧规范支持 |

### 4.4 风险评估

| 风险 | 等级 | 缓解措施 |
|-----|------|---------|
| 历史文件无法识别 | 低 | display_name已存储，不受影响 |
| 外部系统依赖物理名 | 中 | 检查是否有直接访问物理路径的外部系统 |
| 用户习惯路径 | 低 | 用户不直接接触物理路径 |
| 数据迁移成本 | 低 | 不迁移历史数据 |

## 六、决策建议

### 推荐方案

**采用"新文件新规范，旧文件不迁移"的渐进式方案**

理由：
1. 风险可控，不影响现有功能
2. 实施成本低，无需数据迁移
3. 长期收益明显，符合工程最佳实践
