# 资料库前后端适配修复方案

## 问题分析

### 1. 登录问题（已解决）
- **原因**: `localhost` 被解析为 IPv6 (`::1`)，但 Docker Desktop 的 IPv6 端口映射有问题
- **解决**: 修改 `setupProxy.js` 中的 `localhost` 为 `127.0.0.1`

### 2. 资料库前后端不适配问题

#### 2.1 问题描述
后端已从 APScheduler 迁移到 Celery，但前端代码仍使用旧的 `merge_task_id` 方式查询合并状态，可能导致：
1. 合并状态查询失败
2. 文件上传后状态无法正确更新
3. 断点续传功能异常

#### 2.2 当前代码状态

**后端 (Celery改造后)**:
- `merge_chunks` 接口返回两个ID：
  - `task_id`: 新的 Celery 任务ID（推荐）
  - `merge_task_id`: 兼容旧的ID
- `merge_status` 接口支持两种参数：
  - `task_id`: 直接查询 Celery 任务状态
  - `merge_task_id`: 从任务文件读取 `task_id` 后查询

**前端 (未适配)**:
- 只保存了 `merge_task_id`
- `pollMergeStatus` 只传 `merge_task_id` 参数
- 没有利用 Celery 的 `task_id` 直接查询

#### 2.3 潜在问题
1. **性能问题**: 使用 `merge_task_id` 需要先从文件读取 `task_id`，多一次IO操作
2. **可靠性问题**: 如果任务文件损坏或不存在，状态查询会失败
3. **状态映射问题**: Celery 状态 (`PENDING/STARTED/PROGRESS/SUCCESS/FAILURE`) 需要正确映射到前端状态

## 修复方案

### 方案一：前端适配 Celery（推荐）

修改前端代码，保存并使用 `task_id` 直接查询 Celery 任务状态。

#### 修改点 1: 保存 `task_id`
**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

在调用 `merge_chunks` 后，同时保存 `task_id` 和 `merge_task_id`：

```javascript
// 第 1021-1023 行
const mergeResult = await http.post('/api/document/merge_chunks/', { ... });

// 保存两个ID
const mergeTaskId = mergeResult.merge_task_id;
const celeryTaskId = mergeResult.task_id;  // 【新增】保存 Celery 任务ID

// 存储到 item 中供后续使用
runInAction(() => {
  const currentItem = this.uploadQueue[tenantId].find(item => item.id === uploadId);
  if (currentItem) {
    currentItem.status = 'merging';
    currentItem.error = '合并中';
    currentItem.mergeTaskId = mergeTaskId;      // 保留旧的
    currentItem.celeryTaskId = celeryTaskId;    // 【新增】保存新的
  }
});
```

#### 修改点 2: 修改 `pollMergeStatus` 使用 `task_id`
**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

修改 `pollMergeStatus` 方法，优先使用 `task_id`：

```javascript
// 第 1118 行
async pollMergeStatus(mergeTaskId, celeryTaskId = null) {  // 【修改】增加 celeryTaskId 参数
  const { http } = await import('libs');
  let startTime = Date.now();
  let consecutiveErrors = 0;
  const MAX_CONSECUTIVE_ERRORS = 5;

  while (true) {
    const elapsed = (Date.now() - startTime) / 1000;
    if (elapsed > UploadConstants.MERGE_MAX_POLLING_TIME) {
      throw new Error('合并超时');
    }

    try {
      // 【修改】优先使用 celeryTaskId 查询
      const params = celeryTaskId 
        ? { task_id: celeryTaskId }           // 使用 Celery 任务ID
        : { merge_task_id: mergeTaskId };     // 兼容旧方式
        
      const status = await http.get('/api/document/merge_status/', {
        params,
        timeout: 10000
      });
      // ... 后续逻辑不变
    }
  }
}
```

#### 修改点 4: 后端 `check_uploaded_chunks` 接口返回 `task_id`
**文件**: `spug_api/apps/document/views/upload.py`

在 `CheckUploadedChunksView` 中，如果存在合并任务，也返回 `task_id`：

```python
# 第 633-640 行
return json_response({
    'exists': True,
    'uploaded_chunks': uploaded_chunks,
    'count': len(uploaded_chunks),
    'message': f'找到 {len(uploaded_chunks)} 个已上传分片',
    'merge_status': merge_status,
    'merge_task_id': merge_task_id,
    'task_id': task_id,  # 【新增】返回 Celery 任务ID
})
```

需要在读取任务文件时获取 `task_id`：
```python
# 第 617-630 行，在读取 merge_status 文件时
task_id = None  # 【新增】
if os.path.exists(status_file):
    try:
        with open(status_file, 'r') as f:
            merge_status = f.read().strip()
            # 同时读取任务文件获取 task_id
            if merge_task_id:
                merge_task_file = os.path.join(...)

```

### 方案二：后端增强兼容性（备选）

如果前端改动较大，可以优化后端的 `merge_task_id` 兼容逻辑：

1. **缓存优化**: 将 `merge_task_id` -> `task_id` 的映射缓存到 Redis，避免每次都读文件
2. **状态预读**: 在读取任务文件时，同时读取 Celery 状态并缓存
3. **容错增强**: 如果任务文件不存在，尝试从 Celery 任务队列中查找

## 备注

- 方案一（前端适配）是长期推荐方案，性能更好
- 如果前端改动困难，可以先实施方案二（后端优化）作为过渡
- 最终目标是完全迁移到 Celery，废弃 `merge_task_id` 兼容层
