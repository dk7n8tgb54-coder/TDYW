## 1. 背景与目标

### 1.1 当前问题

当前资料库文件存储存在以下问题：

1. **命名冲突风险**: 同一文件夹下同名文件上传时处理逻辑复杂
2. **物理文件管理困难**: 无法直接从物理路径识别文件归属
3. **迁移和备份复杂**: 文件分散存储，难以按租户/用户进行归档
4. **安全风险**: 物理文件名与逻辑文件名关联性弱，存在被篡改风险

### 1.2 设计目标

1. **唯一性**: 确保每个文件的物理存储路径全局唯一
2. **可读性**: 从物理路径可直接识别文件归属（租户/用户/空间）
3. **扩展性**: 支持未来分表、分库、分布式存储
4. **安全性**: 防止物理文件被越权访问或篡改
5. **兼容性**: 平滑迁移现有数据，不影响业务

### 1.3 核心设计原则

#### 1.3.1 职责分离原则
- **物理存储层**: 只负责文件的字节存储，不关心文件内容语义
- **元数据层**: 数据库是文件元数据的唯一权威来源
- **业务层**: 负责权限控制、文件命名、分类展示

#### 1.3.2 物理文件名中性原则
- 物理文件名**不包含**业务语义（如原始文件名、上传者信息）
- 物理文件名**仅包含**技术属性（时间戳、随机串、内容哈希）
- 目的: 防止敏感信息泄露，保持文件名简洁稳定

#### 1.3.3 元数据唯一权威原则
- 文件归属、逻辑名称、权限信息**仅以数据库为准**
- 文件系统路径仅用于**物理隔离**，不用于业务查询
- 备份恢复时**必须**同时恢复数据库和文件系统

## 2. 存储架构设计

### 2.1 目录结构

```
/data/spug/documents/
├── {tenant_id}/                          # 租户ID（第一级分区）
│   ├── private/                          # 私密空间
│   │   ├── users/                        # 按用户分区
│   │   │   ├── {user_id}/                # 用户ID
│   │   │   │   ├── files/                # 独立文件（无文件夹）
│   │   │   │   │   └── {date}/           # 按日期分目录（避免单目录文件过多）
│   │   │   │   │       └── {physical_name}
│   │   │   │   └── folders/              # 文件夹内容
│   │   │   │       └── {folder_id}/      # 文件夹ID
│   │   │   │           └── {physical_name}
│   │   └── temp/                         # 临时文件（上传中）
│   │       └── {date}/
│   │           └── {upload_id}_{chunk_index}.tmp
│   └── public/                           # 公共空间
│       ├── files/                        # 独立文件（注意：不包含user_id，见设计说明）
│       │   └── {date}/
│       │       └── {physical_name}
│       └── folders/                      # 文件夹内容
│           └── {folder_id}/
│               └── {physical_name}
├── shared/                               # 共享文件（跨租户）
│   └── {share_token}/
│       └── {physical_name}
└── recycle/                              # 回收站物理文件暂存
    └── {date}/
        └── {file_id}_{physical_name}
```

### 2.2 物理文件名格式

#### 2.2.1 标准文件

```
{timestamp}_{random}_{hash_suffix}.{ext}
```

- **timestamp**: 毫秒级时间戳 (13位数字)
- **random**: 6位随机字符（小写字母+数字）
- **hash_suffix**: 文件内容MD5前8位
- **ext**: 原始文件扩展名

**示例**: `1711523456789_a3x9k2_m7n4p8q9.pdf`

#### 2.2.2 分片临时文件

```
{upload_id}_{chunk_index:04d}.chunk
```

**示例**: `upload_abc123_0001.chunk`

#### 2.2.3 合并后的临时文件

```
{upload_id}_merged.tmp
```

## 3. 关键设计决策说明

### 3.1 公共空间不包含user_id的决策

**决策**: 公共空间路径保持 `{tenant_id}/public/...`，不增加 `{user_id}` 层级

**理由**:
1. **公共空间强调共享属性**: 公共空间的文件是租户内共享资源，不应强调个人归属
2. **权限模型一致性**: 公共空间访问权限基于角色，而非文件上传者
3. **避免信息冗余**: 上传者信息已存储在数据库 `created_by` 字段，无需在路径中重复
4. **用户变更不影响路径**: 如果用户被删除或修改，路径保持不变，避免级联变更

**归属查询方式**: 通过数据库 `created_by` 字段查询，而非文件系统路径

### 3.2 物理文件名不包含逻辑名称的决策

**决策**: 物理文件名保持 `{timestamp}_{random}_{hash_suffix}.{ext}` 格式，不包含原始文件名信息

**理由**:
1. **文件名长度限制**: Windows(260字符)、Linux(255字符)，增加缩略名可能超限
2. **中文处理复杂性**: 中文文件名需要转拼音或编码，增加系统复杂度
3. **敏感信息保护**: 物理文件名中不应暴露业务敏感信息
4. **单一职责**: 物理存储层只负责存储字节，文件名语义由业务层维护

**快速查找方式**: 备份时同时备份数据库，通过数据库查询 `display_name`

### 3.3 不采用元数据文件(.meta.json)的决策

**决策**: 不生成额外的元数据文件，元数据唯一存储在数据库中

**理由**:
1. **一致性维护成本**: 文件移动、删除、重命名时都需要同步更新元数据文件
2. **并发竞争风险**: 多进程/线程同时操作可能导致元数据文件损坏
3. **数据冗余风险**: 元数据文件与数据库内容可能不一致
4. **备份复杂度**: 元数据文件本身也需要备份，增加备份复杂度

**推荐方案**: 数据库定期备份 + 文件系统备份，恢复时通过数据库关联

### 4.2 路径生成规则

```python
def generate_file_path(tenant_id, space_type, user_id, folder_id, physical_name):
    """
    生成文件存储路径
    """
    date_str = datetime.now().strftime('%Y/%m')
    
    if space_type == 'private':
        if folder_id:
            # 文件夹内文件
            return f"{tenant_id}/private/users/{user_id}/folders/{folder_id}/{physical_name}"
        else:
            # 独立文件，按日期分目录
            return f"{tenant_id}/private/users/{user_id}/files/{date_str}/{physical_name}"
    else:  # public
        if folder_id:
            return f"{tenant_id}/public/folders/{folder_id}/{physical_name}"
        else:
            return f"{tenant_id}/public/files/{date_str}/{physical_name}"
```

## 5. 关键流程设计

### 5.1 上传流程

```
1. 前端发起上传请求
   ↓
2. 后端生成 upload_id 和存储路径
   - 生成 physical_name: {timestamp}_{random}_{hash_suffix}.{ext}
   - 生成 file_path: {tenant_id}/{space}/users/{user_id}/...
   ↓
3. 返回 upload_id 和分片上传配置给前端
   ↓
4. 前端分片上传（直接上传到存储目录的 temp 子目录）
   - 临时文件: {tenant_id}/temp/{date}/{upload_id}_{chunk_index}.chunk
   ↓
5. 所有分片上传完成后，后端合并文件
   - 合并到目标路径
   - 计算完整文件 MD5
   - 校验 hash_suffix 是否匹配
   ↓
6. 清理临时分片文件
   ↓
7. 写入数据库记录
```

### 5.2 下载流程

```
1. 用户请求下载文件
   ↓
2. 权限校验（租户隔离 + 用户权限）
   ↓
3. 从数据库获取 file_path
   ↓
4. 构造完整物理路径: {STORAGE_ROOT}/{file_path}
   ↓
5. 返回文件流或重定向URL
```

### 5.3 移动/复制流程

```
方案A: 物理移动（同租户内）
- 实际移动物理文件到新路径
- 更新数据库 file_path

方案B: 逻辑引用（跨租户复制）
- 生成新的 physical_name
- 复制物理文件到新路径
- 插入新数据库记录
```

### 5.4 删除流程

```
软删除:
- 标记数据库 is_deleted = true
- 文件保留在原地

硬删除（回收站清理）:
- 删除物理文件
- 删除数据库记录
- 记录审计日志
```

## 6. 命名规则详解

### 6.1 物理文件名生成

```python
def generate_physical_name(original_filename, file_content_hash=None):
    """
    生成物理文件名
    
    Args:
        original_filename: 原始文件名（用于获取扩展名）
        file_content_hash: 文件内容MD5（可选，用于校验）
    
    Returns:
        物理文件名，如: "1711523456789_a3x9k2_m7n4p8q9.pdf"
    """
    timestamp = int(time.time() * 1000)  # 13位毫秒时间戳
    random_str = ''.join(random.choices(string.ascii_lowercase + string.digits, k=6))
    hash_suffix = file_content_hash[:8] if file_content_hash else '00000000'
    ext = os.path.splitext(original_filename)[1].lower()
    
    return f"{timestamp}_{random_str}_{hash_suffix}{ext}"
```

### 6.2 文件名冲突处理

由于物理文件名包含时间戳和随机字符串，冲突概率极低（1/36^6 ≈ 1/2.1亿）。

如检测到冲突（理论上几乎不可能）：
1. 重新生成 random_str
2. 重试最多3次
3. 如仍冲突，抛出异常

### 6.3 特殊字符处理

- 原始文件名中的特殊字符在 `display_name` 中保留
- `physical_name` 只保留小写字母、数字、下划线、点和连字符
- 非法字符替换为下划线

## 7. 安全设计

### 7.1 路径遍历防护

```python
def validate_path_component(component):
    """
    验证路径组件，防止路径遍历攻击
    """
    if '..' in component or '/' in component or '\\' in component:
        raise ValueError(f"Invalid path component: {component}")
    return component
```

### 7.2 租户隔离

- 物理路径第一级必须是 tenant_id
- 服务层严格校验用户只能访问自己租户的路径
- 超级管理员也只能访问自己租户下的私密文件

### 7.3 文件完整性校验

- 上传时计算 MD5，存储到 file_hash 字段
- 物理文件名包含 hash_suffix，可快速比对
- 定期任务扫描校验文件完整性

### 8.1 现有数据迁移

#### 阶段1: 存量数据迁移（离线）

```python
# 迁移脚本逻辑
def migrate_existing_files():
    for file in DocumentFilePrivate.objects.all():
        # 1. 生成新的物理文件名
        new_physical_name = generate_physical_name(file.name, file.file_hash)
        
        # 2. 生成新的存储路径
        new_file_path = generate_file_path(
            tenant_id=file.tenant_id,
            space_type='private',
            user_id=file.created_by_id,
            folder_id=file.folder_id,
            physical_name=new_physical_name
        )
        
        # 3. 创建目标目录
        os.makedirs(os.path.dirname(new_file_path), exist_ok=True)
        
        # 4. 移动物理文件
        old_full_path = os.path.join(STORAGE_ROOT, file.file_path)
        new_full_path = os.path.join(STORAGE_ROOT, new_file_path)
        shutil.move(old_full_path, new_full_path)
        
        # 5. 更新数据库
        file.physical_name = new_physical_name
        file.file_path = new_file_path
        file.save()
```

- 所有新操作使用新规则

## 9. 备份与恢复策略

### 9.1 备份策略设计原则

基于**职责分离原则**，备份策略遵循以下原则：
1. **数据库是元数据的唯一权威来源**，文件系统仅存储字节
2. **必须同时备份**数据库和文件系统，缺一不可
3. **备份时间点一致性**，确保数据库记录与物理文件匹配

### 9.2 备份内容

| 组件 | 备份内容 | 备份频率 | 保留周期 |
|------|----------|----------|----------|
| 数据库 | 文件元数据、权限信息、目录结构 | 每日全量 + 实时binlog | 30天 |
| 文件系统 | 物理文件（按租户分区） | 每日增量 | 30天 |

### 9.3 备份方式

#### 9.3.1 数据库备份
```bash
# MySQL备份示例
mysqldump -u root -p spug_db --tables document_documentfileprivate \
  document_documentfilepublic > backup_$(date +%Y%m%d).sql

# Binlog增量备份（用于时间点恢复）
mysqlbinlog --read-from-remote-server --raw --stop-never mysql-bin.000001
```

#### 9.3.2 文件系统备份
```bash
# 按租户ID增量备份（使用rsync）
rsync -av --link-dest=/backup/spug/current /data/spug/documents/{tenant_id}/ \
  /backup/spug/incremental/$(date +%Y%m%d)/

# 生成文件清单用于校验
find /data/spug/documents -type f -exec md5sum {} \; > file_manifest_$(date +%Y%m%d).txt
```

### 9.4 恢复流程

#### 场景1: 数据库损坏，文件系统完好
```
1. 恢复数据库到最近备份点
2. 校验数据库记录中的 file_hash 与物理文件是否匹配
3. 如有不匹配，以物理文件为准更新数据库记录
```

#### 场景2: 文件系统损坏，数据库完好
```
1. 从备份恢复文件系统
2. 校验物理文件的 MD5 与数据库 file_hash 是否匹配
3. 缺失的文件标记为 is_deleted = true，通知用户重新上传
```

#### 场景3: 完全灾难恢复
```
1. 恢复数据库到目标时间点
2. 恢复文件系统到相同时间点
3. 运行一致性校验脚本，生成差异报告
4. 处理不一致的文件（缺失或哈希不匹配）
```

### 9.5 一致性校验脚本

```python
# scripts/verify_backup_consistency.py

def verify_consistency():
    """校验数据库与物理文件一致性"""
    inconsistencies = []
    
    # 1. 检查数据库记录对应的物理文件是否存在
    for file_record in DocumentFilePrivate.objects.filter(is_deleted=False):
        full_path = os.path.join(STORAGE_ROOT, file_record.file_path)
        if not os.path.exists(full_path):
            inconsistencies.append({
                'type': 'missing_physical',
                'file_id': file_record.id,
                'file_path': file_record.file_path
            })
            continue
        
        # 2. 校验文件哈希
        actual_hash = calculate_md5(full_path)
        if actual_hash != file_record.file_hash:
            inconsistencies.append({
                'type': 'hash_mismatch',
                'file_id': file_record.id,
                'expected_hash': file_record.file_hash,
                'actual_hash': actual_hash
            })
    
    # 3. 检查物理文件是否有数据库记录
    for root, dirs, files in os.walk(STORAGE_ROOT):
        for filename in files:
            # 跳过临时文件
            if filename.endswith('.tmp') or filename.endswith('.chunk'):
                continue
            
            relative_path = os.path.relpath(os.path.join(root, filename), STORAGE_ROOT)
            if not DocumentFilePrivate.objects.filter(file_path=relative_path).exists():
                inconsistencies.append({
                    'type': 'orphan_file',
                    'file_path': relative_path
                })
    
    return inconsistencies
```

### 9.6 快速查找指南（备份场景）

**场景**: 需要从备份中查找某个用户的特定文件

**推荐流程**:
```
1. 恢复数据库备份到临时实例
2. 通过SQL查询定位文件:
   SELECT file_path, display_name, physical_name 
   FROM document_documentfileprivate 
   WHERE created_by = {user_id} 
   AND display_name LIKE '%关键词%'
   
3. 根据返回的 file_path 在文件系统备份中定位物理文件
4. 恢复所需文件
```

**不推荐**: 直接遍历文件系统查找（效率低，无法识别文件内容）

#### 10.2.1 路径生成器

```python
# apps/document/libs/storage/path_generator.py

import os
import random
import string
import hashlib
from datetime import datetime
from django.conf import settings


class PathGenerator:
    """文件路径生成器"""
    
    STORAGE_ROOT = settings.DOCUMENT_STORAGE_PATH
    
    @classmethod
    def generate_physical_name(cls, original_filename, file_hash=None):
        """生成物理文件名"""
        timestamp = int(datetime.now().timestamp() * 1000)
        random_str = ''.join(random.choices(string.ascii_lowercase + string.digits, k=6))
        hash_suffix = file_hash[:8] if file_hash else '00000000'
        ext = os.path.splitext(original_filename)[1].lower()
        return f"{timestamp}_{random_str}_{hash_suffix}{ext}"
    
    @classmethod
    def generate_file_path(cls, tenant_id, space_type, user_id, folder_id, 
                          physical_name, is_private=True):
        """生成文件存储路径"""
        date_str = datetime.now().strftime('%Y/%m')
        
        if is_private:
            if folder_id:
                return f"{tenant_id}/private/users/{user_id}/folders/{folder_id}/{physical_name}"
            else:
                return f"{tenant_id}/private/users/{user_id}/files/{date_str}/{physical_name}"
        else:
            if folder_id:
                return f"{tenant_id}/public/folders/{folder_id}/{physical_name}"
            else:
                return f"{tenant_id}/public/files/{date_str}/{physical_name}"
    
    @classmethod
    def get_temp_path(cls, tenant_id, upload_id, chunk_index=None):
        """获取临时文件路径"""
        date_str = datetime.now().strftime('%Y/%m/%d')
        if chunk_index is not None:
            return f"{tenant_id}/temp/{date_str}/{upload_id}_{chunk_index:04d}.chunk"
        return f"{tenant_id}/temp/{date_str}/{upload_id}_merged.tmp"
    
    @classmethod
    def get_full_path(cls, relative_path):
        """获取完整物理路径"""
        return os.path.join(cls.STORAGE_ROOT, relative_path)
```

```python
# 修改后的文件保存逻辑
def save_uploaded_file(uploaded_file, tenant_id, user_id, folder_id=None, 
                       space_type='private'):
    """
    保存上传的文件
    
    Args:
        uploaded_file: 上传的文件对象
        tenant_id: 租户ID
        user_id: 用户ID
        folder_id: 文件夹ID（可选）
        space_type: 空间类型（private/public）
    
    Returns:
        dict: 包含 physical_name, file_path, file_hash
    """
    # 1. 计算文件哈希
    file_hash = calculate_md5(uploaded_file)
    
    # 2. 生成物理文件名
    physical_name = PathGenerator.generate_physical_name(
        uploaded_file.name, 
        file_hash
    )
    
    # 3. 生成存储路径
    file_path = PathGenerator.generate_file_path(
        tenant_id=tenant_id,
        space_type=space_type,
        user_id=user_id,
        folder_id=folder_id,
        physical_name=physical_name,
        is_private=(space_type == 'private')
    )
    
    # 4. 创建目录
    full_path = PathGenerator.get_full_path(file_path)
    os.makedirs(os.path.dirname(full_path), exist_ok=True)
    
    # 5. 保存文件
    with open(full_path, 'wb') as f:
        for chunk in uploaded_file.chunks():
            f.write(chunk)
    
    # 6. 返回信息
    return {
        'physical_name': physical_name,
        'file_path': file_path,
        'file_hash': file_hash,
        'file_size': uploaded_file.size,
    }
```

```python
def cleanup_temp_files():

    temp_dirs = glob.glob(f"{STORAGE_ROOT}/*/temp/*/*/*")
```

### 12.3 替代方案对比分析

针对审查意见中提出的其他方案，在此进行对比分析：

| 方案 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| 公共空间路径增加user_id | 可直接识别上传者 | 违背公共空间共享属性；用户变更导致路径不一致 | **拒绝** |
| 物理文件名增加缩略名 | 便于人工识别 | 文件名长度风险；中文处理复杂；暴露敏感信息 | **拒绝** |
| 元数据文件(.meta.json) | 离线可查看文件信息 | 一致性维护成本高；并发风险；数据冗余 | **拒绝** |
| 纯数据库存储元数据 | 单一权威源；查询效率高 | 备份时必须同时备份数据库 | **采纳** |

**核心原则**: 物理存储层保持简单中性，所有业务语义由数据库维护。
