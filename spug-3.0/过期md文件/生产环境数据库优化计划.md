# 生产环境数据库优化计划

## 一、开发环境与生产环境配置对比

### 1.1 数据库核心参数对比

| 参数名 | 开发环境 | 生产环境 | 差异分析 |
|--------|----------|----------|----------|
| **innodb_buffer_pool_size** | **3G** ✅ | **512M** ❌ | 生产环境严重偏低，仅为开发环境的17% |
| **innodb_log_file_size** | **128M** ✅ | **64M** ⚠️ | 生产环境偏小，大事务时性能受限 |
| **max_connections** | 500 | 800 | 生产环境更高，但需配合连接池优化 |
| **innodb_lock_wait_timeout** | 120秒 | 300秒 | 生产环境更宽松，适合大表迁移 |
| **innodb_read_io_threads** | **8** ✅ | 默认(4) ❌ | 生产环境未优化I/O线程 |
| **innodb_write_io_threads** | **8** ✅ | 默认(4) ❌ | 生产环境未优化I/O线程 |
| **数据库镜像** | MariaDB 10.8.2 | 自定义镜像 | 版本差异不大 |
| **容器内存限制** | 无限制 | 8GB | 生产环境有明确限制 |

### 1.2 配置问题总结

```
生产环境 8GB 内存分配现状：
├─ innodb_buffer_pool_size: 512MB (6.4%)  ❌ 严重不足
├─ 其他MySQL开销: ~1GB
├─ 操作系统: ~512MB
└─ 剩余: ~6GB 未充分利用

理想分配（8GB内存）：
├─ innodb_buffer_pool_size: 6GB (75%)    ✅ 推荐
├─ 其他MySQL开销: ~1GB
├─ 操作系统: ~512MB
└─ 缓冲: 512MB
```

## 二、后端代码配置现状分析

### 2.1 当前数据库连接配置

**文件**: `spug_api/spug/settings.py`

```python
DATABASES = {
    'default': {
        'ATOMIC_REQUESTS': True,
        'ENGINE': 'django.db.backends.mysql',
        'NAME': os.environ.get('MYSQL_DATABASE'),
        'USER': os.environ.get('MYSQL_USER'),
        'PASSWORD': os.environ.get('MYSQL_PASSWORD'),
        'HOST': os.environ.get('MYSQL_HOST'),
        'PORT': os.environ.get('MYSQL_PORT'),
        'CONN_MAX_AGE': 0,  # 禁用连接池
    }
}
```

### 2.2 存在的问题

| 问题 | 当前值 | 影响 |
|------|--------|------|
| **CONN_MAX_AGE** | 0（禁用连接池） | 每个请求都新建/关闭连接，开销大 |
| **无连接池大小限制** | - | 可能超出MySQL max_connections限制 |
| **无连接超时配置** | - | 网络波动时连接挂起，资源不释放 |
| **无数据库读写分离** | - | 所有压力集中在主库 |

**重启步骤**:

#### 2.2 添加数据库连接池监控

**文件**: `spug_api/apps/document/views/health.py`（新增健康检查项）

```python
# 添加数据库连接状态检查
def check_database_connections():
    from django.db import connection
    with connection.cursor() as cursor:
        cursor.execute("SHOW STATUS LIKE 'Threads_connected'")
        threads_connected = cursor.fetchone()[1]
        
        cursor.execute("SHOW STATUS LIKE 'Max_used_connections'")
        max_used = cursor.fetchone()[1]
        
    return {
        'threads_connected': threads_connected,
        'max_used_connections': max_used,
        'utilization': f"{int(threads_connected)/800*100:.1f}%"
    }
```

## 四、参数匹配关系

### 4.1 MySQL vs Django 参数匹配表

| MySQL 参数 | 值 | Django 参数 | 建议值 | 匹配关系 |
|------------|-----|-------------|--------|----------|
| max_connections | 800 | CONN_MAX_AGE | 300 | 连接保持时间应 < wait_timeout |
| wait_timeout | 300 | CONN_MAX_AGE | 300 | Django保持时间 ≤ MySQL超时时间 |
| innodb_lock_wait_timeout | 300 | read_timeout | 30 | Django超时 < MySQL锁超时 |
| max_allowed_packet | 默认 | OPTIONS['max_allowed_packet'] | 64M | 应保持一致 |

### 4.2 连接数计算

```
总连接数需求 = 
    Gunicorn workers × 每个worker连接数 + 
    Celery workers × 每个worker连接数 + 
    后台任务连接数

示例:
    4 Gunicorn workers × 10 = 40
    2 Celery workers × 5 = 10
    后台任务 = 10
    预留 = 20
    ------------------------
    总计 = 80

max_connections=800 完全够用，甚至可以降低到 200-300
```
