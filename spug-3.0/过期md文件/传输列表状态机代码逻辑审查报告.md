## 二、详细问题分析

### C-01: `history` 检查逻辑错误

**代码位置**: `UploadStateMachine.js:449`

```javascript
shouldResumeWaiting() {
  const item = this.getItem();
  if (!item?.file) {
    return true;
  }
  // 问题：history 是对象数组，不是字符串数组
  const wasWaiting = this.history.includes('waiting') ||  // ❌ 错误
                     (item?.status === 'waiting');
  // ...
}
```

**问题分析**:
`this.history` 是对象数组，每项为 `{ from, to, event, timestamp, payload }`，使用 `includes('waiting')` 永远返回 `false`。

**修复建议**:
```javascript
shouldResumeWaiting() {
  const item = this.getItem();
  if (!item?.file) {
    return true;
  }
  // 正确：检查 history 中是否有 from 或 to 为 waiting 的记录
  const wasWaiting = this.history.some(h => h.from === 'waiting' || h.to === 'waiting') ||
                     (item?.status === 'waiting');
  // ...
}
```

### C-02: `batchResume` 并发控制缺陷

**代码位置**: `StateMachineManager.js:204`

```javascript
batchResume(maxConcurrent = 3, getActiveCount = null) {
  // ...
  const activeCount = getActiveCount ? getActiveCount() : 0;
  const availableSlots = Math.max(0, maxConcurrent - activeCount);
  // ...
  this.machines.forEach((machine, uploadId) => {
    if (resumedCount >= availableSlots) return; // ❌ 只检查数量，不检查类型
    // waiting -> calculating 也占用并发槽位？
    // 实际上传开始时才应该占用槽位
  });
}
```

**问题分析**:
1. `availableSlots` 计算时 `activeCount` 可能不包含即将进入 `uploading` 的任务
2. waiting -> calculating 转换也占用恢复配额，但此时实际并发未增加

**修复建议**:
```javascript
batchResume(maxConcurrent = 3, getActiveCount = null) {
  const activeCount = getActiveCount ? getActiveCount() : 0;
  // 计算真正占用并发槽位的数量（uploading + merging）
  let uploadingCount = 0;
  this.machines.forEach(m => {
    if (m.isInState('uploading') || m.isInState('merging')) uploadingCount++;
  });
  const availableSlots = Math.max(0, maxConcurrent - uploadingCount);
  // ...
}
```

### C-03: `onCalculatingEntry` 错误处理后状态未重置

**代码位置**: `UploadStateMachine.js:332`

```javascript
onCalculatingEntry() {
  const item = this.getItem();
  if (!item?.file) {
    // 触发错误状态转换
    this.transition('ERROR', { error: '请重新选择文件' });  // ❌ 问题
    return;
  }
  // ...
}
```

**问题分析**:
1. 在 entry 钩子中调用 `transition` 可能导致嵌套状态转换
2. 错误状态转换后，`calculating` 的 exit 钩子可能执行也可能不执行，取决于实现
3. MD5计算任务可能仍在后台运行

**修复建议**:
```javascript
onCalculatingEntry() {
  const item = this.getItem();
  if (!item?.file) {
    // 延迟执行错误转换，避免在 entry 中直接转换
    setTimeout(() => {
      this.transition('ERROR', { error: '请重新选择文件' });
    }, 0);
    return;
  }
  // 启动MD5计算
  this.startMD5Calculation();
}
```

### H-01: `paused` 状态 RESUME 事件顺序问题

**代码位置**: `UploadStateMachine.js:59`

```javascript
paused: {
  transitions: [
    { event: 'RESUME', target: 'waiting', guard: this.shouldResumeWaiting },    // 第1条
    { event: 'RESUME', target: 'calculating', guard: this.shouldRecalculateMD5 }, // 第2条
    { event: 'RESUME', target: 'uploading', guard: this.shouldResumeUpload },   // 第3条
  ]
}
```

**问题分析**:
守卫条件的优先级顺序有问题。当满足多个条件时（如没有 file 但有 fileHash），会选择第一条匹配的。

**当前逻辑问题**:
- 没有 File 但有 fileHash：应该去 uploading，但可能去 waiting
- 有 File 但没有 fileHash：应该去 calculating，但可能去 waiting

**建议优先级**:
1. `shouldResumeWaiting` - 只有当没有 File 时才返回 true
2. `shouldRecalculateMD5` - 有 File 但没有 fileHash
3. `shouldResumeUpload` - 有 File 且有 fileHash

**当前实现已修复此问题**，但需要确保守卫条件互斥。

### H-02: `schedulePendingUploadsRecovery` 并发竞争

**代码位置**: `index.js:306`

```javascript
schedulePendingUploadsRecovery() {
  const checkAndResumeNext = () => {
    // ...
    if (pausedMachines.length > 0 && this.activeUploads < UPLOAD_CONSTANTS.MAX_CONCURRENT_UPLOADS) {
      // ❌ 问题：检查时有槽位，但恢复时槽位可能已被占用
      const { machine, uploadId } = pausedMachines[0];
      if (machine.canTransition(eventName)) {
        machine.transition(eventName);
        // 此时并发数增加，但其他恢复可能也在检查
      }
    }
  };
  setTimeout(checkAndResumeNext, 100);
}
```

**问题分析**:
1. `activeUploads` 检查和 `transition` 调用之间有时间差
2. 多个任务几乎同时完成时，可能同时触发恢复，导致并发超限

**修复建议**:
使用原子操作或锁机制：
```javascript
schedulePendingUploadsRecovery() {
  if (this._isRecovering) return; // 防止并发恢复
  this._isRecovering = true;
  
  const checkAndResumeNext = () => {
    try {
      if (this.isPaused || this.isCancelled) return;
      // ... 恢复逻辑
    } finally {
      this._isRecovering = false;
    }
  };
  setTimeout(checkAndResumeNext, 100);
}
```

## 三、架构建议

### 3.1 状态机与业务逻辑解耦

当前 `onStateUploading` 和 `onStateCalculating` 直接包含业务逻辑，违反了状态机只管理状态的职责。

**建议架构**:
```javascript
// 状态机只负责状态流转
stateMachine.on('state:uploading', ({ uploadId, fromState }) => {
  // UploadCoreStore 订阅事件并执行业务逻辑
  this.executeUpload(uploadId, fromState);
});
```

### 3.2 统一并发控制

当前并发控制分散在多处：
- `batchResume` 中的 `availableSlots` 检查
- `processPendingUploads` 中的 `activeUploads` 检查
- `onStateUploading` 中的 `while` 循环等待

**建议**:
使用统一的并发控制器：
```javascript
class ConcurrencyController {
  constructor(maxConcurrent) {
    this.maxConcurrent = maxConcurrent;
    this.running = 0;
    this.queue = [];
  }
  
  async acquire() {
    if (this.running < this.maxConcurrent) {
      this.running++;
      return;
    }
    return new Promise(resolve => this.queue.push(resolve));
  }
  
  release() {
    this.running--;
    if (this.queue.length > 0) {
      const next = this.queue.shift();
      this.running++;
      next();
    }
  }
}
```

### 3.3 状态持久化

当前状态机状态只保存在内存中，页面刷新后丢失。

**建议**:
- 使用 `localStorage` 或 `IndexedDB` 持久化状态机状态
- 页面加载时恢复状态机

## 六、总结

状态机实现整体良好，主要问题集中在：

1. **数据类型错误**: `history.includes('waiting')` 是严重逻辑错误
2. **并发控制漏洞**: 多处并发检查可能不一致
3. **状态定义不完整**: 缺少 `cancelled` 状态
4. **架构耦合**: 业务逻辑与状态机耦合过紧

建议优先修复 C-01、C-03 和 H-03，这些问题可能导致状态机行为异常。并发控制问题需要系统性地解决，建议设计统一的并发控制器。
