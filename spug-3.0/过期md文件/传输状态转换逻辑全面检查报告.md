# 传输状态转换逻辑全面检查报告

## 检查范围

- 前端状态机与同步逻辑：
  - `spug_web/src/pages/document/stores/upload/core/UploadStateMachine.js`
  - `spug_web/src/pages/document/stores/upload/core/StateMachineManager.js`
  - `spug_web/src/pages/document/stores/upload/core/index.js`
  - `spug_web/src/pages/document/stores/upload/core/transfer.js`
- 后端状态规则与接口：
  - `spug_api/apps/document/constants.py`
  - `spug_api/apps/document/views/transfer/status.py`
  - `spug_api/apps/document/views/transfer/cancel.py`
  - `spug_api/apps/document/views/transfer/batch.py`
  - `spug_api/apps/document/views/upload/merge.py`

## 总体结论

当前状态转换逻辑仍存在**前后端规则不一致**与**幂等处理掩盖问题**两类核心风险。  
这些问题会在“批量/单条混合操作 + 暂停/恢复/取消并发点击 + 合并阶段”场景下放大，表现为：

- 仍可能出现“无效状态转换”告警；
- 前端以为成功、后端实际拒绝；
- 取消任务被错误映射成失败；
- 合并态的边界行为不稳定。

---

## 关键问题（按严重度）

### P0 - 取消状态值拼写不一致，可能导致取消状态同步失败

- 位置：`UploadStateMachine.js`
- 现象：前端 `onCancelledEntry()` 调用 `updateTransferStatus('CANCELLED')`（双 L），后端枚举是 `CANCELED`（单 L）。
- 风险：
  - 后端会把该值判定为无效状态值；
  - 取消态可能未成功落库；
  - 前端局部显示 `cancelled`，后端实际不是 `CANCELED`，造成状态漂移。

---

### P0 - 前端把“后端非法转换”当成功处理，掩盖真实问题

- 位置：`transfer.js` 的 `updateTransferStatus()`
- 现象：当后端返回“无效的状态转换”时，前端直接 `return { ignored: true }`，流程继续。
- 风险：
  - UI/状态机会继续推进，造成“前端已暂停/已恢复，后端未变化”；
  - 问题被吞掉，难以定位根因；
  - 后续批量操作会在错误基础上叠加。

---

### P1 - 后端“统一状态规则”与“实际接口实现”不一致

- 规则来源：`constants.py` 中 `ALLOWED_STATUS_TRANSITIONS`
- 实际实现分散在多个视图中，且有“绕过统一校验”的逻辑：
  - `TransferCompleteView` 未使用统一规则，允许范围与 `ALLOWED_STATUS_TRANSITIONS` 不完全一致；
  - `TransferCancelView` 也是独立判断；
  - `upload/merge.py` 直接把 `UPLOADING/PAUSED -> MERGING`，同样不走统一校验。
- 风险：
  - “同一状态转换”在不同入口结论不同；
  - 单条接口、批量接口、上传流程接口行为不一致。

---

### P1 - 取消状态在前端回读时被映射为 `error`

- 位置：`index.js` 的 `mapBackendStatus()`
- 现象：`CANCELED -> error`，而前端状态机已引入 `cancelled` 终态。
- 风险：
  - 取消任务会被当成失败任务处理；
  - 可能出现在“可重试/可恢复”判断中被误操作；
  - 与终态过滤（`cancelled`）逻辑不一致。

---

### P1 - 批量暂停接口含“不可达幂等分支”

- 位置：`transfer/batch.py` 的 `TransferBatchPauseView`
- 现象：
  - 查询只筛选 `PENDING/UPLOADING`；
  - 循环里又判断 `if transfer.status == PAUSED`，该分支理论不可达。
- 风险：
  - 代码语义混乱，维护者容易误判“已处理 PAUSED 幂等”；
  - 后续改动更容易引入分支遗漏。

---

### P2 - 批量恢复与状态机恢复语义不完全对齐

- 位置：
  - 前端 `StateMachineManager.batchResume()`
  - 后端 `TransferBatchResumeView`
- 现象：
  - 前端恢复是事件驱动（`START/RESUME`），包含 waiting/calc/uploading 分支；
  - 后端批量恢复只处理 `PAUSED -> UPLOADING`。
- 风险：
  - 前端“恢复成功计数”与后端“实际更新条数”可能不一致；
  - 形成“前端认为已恢复，后端仍未恢复”的感知偏差。

---

## 当前逻辑中已改善项（确认有效）

- 前端已避免将 `waiting` 持续回写为后端 `PENDING`，可显著减少 `UPLOADING/PAUSED -> PENDING`。
- 后端规则已允许 `PENDING -> PAUSED`，与前端“waiting 可暂停”基本对齐。

---

## 建议修复顺序（务实版）

1. **先修 P0**
   - 统一取消状态值为 `CANCELED`（前端所有上报点、常量、映射统一）。
   - `updateTransferStatus()` 不再把“非法转换”当成功，至少打强告警并返回失败态给调用方处理。
2. **再修 P1**
   - 统一后端状态校验入口：`status.py` / `cancel.py` / `merge.py` 尽量都走 `is_valid_status_transition`。
   - `mapBackendStatus()` 将 `CANCELED` 映射为 `cancelled`，避免取消被误识别为失败。
3. **最后修 P2**
   - 对齐批量恢复的“前端成功定义”与“后端更新定义”；
   - 增加前后端对账日志，输出 `{transfer_id, frontend_state, backend_state}`。

---

## 建议回归用例（必须覆盖）

1. 单条：`waiting -> pause -> resume -> pause`
2. 单条：`uploading -> pause -> resume -> cancel`
3. 批量：混合 `PENDING/UPLOADING/PAUSED/MERGING` 后执行 pause/resume/cancel
4. 合并中：触发 cancel 与 pause，确认被拒绝或按预期处理
5. 前后端对账：每次操作后拉取 `transfer list` 与前端状态机状态比对

---

## 一句话总结

当前不是“单点 bug”，而是“状态定义、状态映射、接口幂等策略”三层未完全统一；  
建议先处理 P0（取消状态拼写 + 错误吞掉），再做规则统一，问题会明显收敛。
