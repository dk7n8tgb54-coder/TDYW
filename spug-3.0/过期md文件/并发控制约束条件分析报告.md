# 资料库模块并发控制约束条件分析报告

## 执行摘要

通过对代码库的全面审查，发现并发控制机制存在**多层但不严谨**的问题。虽然实现了多种锁机制（Redis分布式锁、线程锁、数据库行锁），但存在**锁粒度不一致、锁超时配置不合理、缺乏统一的死锁处理策略**等关键缺陷。

**风险等级：中高风险**
- 可能导致重复合并文件
- 可能出现竞态条件导致状态不一致
- 极端情况下可能引发内存泄漏

---

## 1. 当前并发控制机制概览

### 1.1 锁机制类型统计

| 锁类型 | 实现位置 | 使用场景 | 问题数量 |
|--------|----------|----------|----------|
| Redis分布式锁 | `celery_lock.py` | Celery任务间互斥 | 3个 |
| 线程级内存锁 | `lock.py` | 单进程内线程互斥 | 4个 |

## 2. 关键问题分析

### 2.1 【P0级】锁超时时间不一致

**问题描述：**
不同层级的锁超时时间配置不统一，可能导致"持有短锁等待长锁"的死锁场景。

**具体配置：**
```python
# celery_lock.py - Redis分布式锁
REDIS_LOCK_TIMEOUT_SECONDS = 900  # 15分钟

# lock.py - 线程级MergeLock  
MERGE_LOCK_TIMEOUT = 300  # 5分钟 (constants.py)
DEFAULT_MERGE_LOCK_TIMEOUT = 300  # 5分钟

# tasks/merge.py - Celery任务超时
CELERY_SOFT_TIME_LIMIT_SECONDS = 600  # 10分钟
CELERY_HARD_TIME_LIMIT_SECONDS = 900  # 15分钟
```

**风险分析：**
1. Redis锁超时(15min) > Celery硬超时(15min) - 临界状态
2. 线程锁超时(5min) < Celery软超时(10min) - 线程锁可能提前释放
3. 当线程锁超时后，同Worker的新线程可能获取锁，但Redis锁仍被原任务持有

**建议修复：**
```python
# 统一超时策略：底层锁 > 上层锁
REDIS_LOCK_TIMEOUT = 1200          # 20分钟 (最底层，最长)
CELERY_HARD_TIME_LIMIT = 900       # 15分钟 (中间层)  
CELERY_SOFT_TIME_LIMIT = 600       # 10分钟
THREAD_LOCK_TIMEOUT = 300          # 5分钟 (最上层，最短)

# 确保：REDIS_TIMEOUT > CELERY_HARD > CELERY_SOFT > THREAD_TIMEOUT
```

### 2.2 【P0级】缺乏跨层锁协调机制

**问题描述：**
Redis锁和线程锁是独立管理的，没有建立"谁持有谁释放"的关联关系。

**代码分析：**
```python
# celery_lock.py
@with_distributed_lock("merge_lock:{file_hash}", timeout=900)
def merge_file_chunks(self, job_data):
    # 获取了Redis锁
    ...
    # 在任务内部又获取线程锁
    lock = get_merge_lock(file_hash, is_public, tenant_id)
    if not lock.acquire(timeout=300):
        # 问题：Redis锁仍被持有，但线程锁获取失败
        # 任务会重试，但Redis锁未释放可能导致死锁
```

**风险场景：**
```
Worker-A                    Worker-B
  │                           │
  ├─获取Redis锁(15min)        │
  │                           │
  ├─尝试获取线程锁            │
  │  (失败，因其他线程持有)   │
  │                           │
  ├─任务重试(30s后)           │
  │                           │
  │                           ├─尝试获取Redis锁
  │                           │  (失败，被Worker-A持有)
  │                           │
  │◄──────────────────────────┤ 死锁：双方互相等待
```

**建议修复：**
1. 实施"单层锁策略"：Celery任务只使用Redis锁，不额外使用线程锁
2. 或建立锁层级：获取上层锁之前必须先获取下层锁
3. 添加锁持有标识，记录哪个任务持有哪把锁

### 2.3 【P1级】select_for_update 范围不一致

**问题描述：**
不同场景下数据库行锁的使用范围不一致，可能导致并发修改。

**问题场景1：批量操作缺乏行锁**
```python
# views/transfer/batch.py
@transaction.atomic
def post(self, request):
    # 查询时没有使用 select_for_update
    all_transfers = DocumentTransfer.objects.filter(id__in=transfer_ids)
    ...
    for transfer in permitted_transfers:
        # 循环内单条修改，但查询时未加锁
        transfer.status = TransferStatus.PAUSED.value
        transfer.save()
```

**问题场景2：先查询后加锁存在时间窗口**
```python
# tasks/timeout_checker.py
# 先查询
stale_tasks = DocumentTransfer.objects.filter(
    status=TransferStatus.MERGING.value,
    updated_at__lt=cutoff_time
).select_related('user')

for task in stale_tasks:
    # 后加锁 - 存在竞态条件窗口
    with transaction.atomic():
        locked_task = DocumentTransfer.objects.select_for_update().get(
            id=task.id,
            status=TransferStatus.MERGING.value
        )
```

**风险分析：**
- 批量操作时，同一条记录可能被多个请求同时修改
- 在"查询"和"加锁"之间，记录状态可能被其他会话改变

**建议修复：**
```python
# 批量操作时使用 select_for_update
with transaction.atomic():
    transfers = DocumentTransfer.objects.select_for_update().filter(
        id__in=transfer_ids,
        user=request.user
    )
    for transfer in transfers:
        transfer.status = new_status
        transfer.save()
```

### 2.4 【P1级】Redis锁缺乏续期机制

**问题描述：**
Redis锁使用固定超时时间，对于长时间运行的任务可能提前过期。

**代码分析：**
```python
def acquire(self, lock_key, timeout=600):
    # 固定超时，无续期
    acquired = self.redis.set(lock_key, "locked", nx=True, ex=timeout)
    return acquired
```

**风险场景：**
1. 大文件合并耗时超过15分钟
2. Redis锁自动过期
3. 另一个Worker获取到相同锁，开始重复合并
4. 原任务完成后清理分片，可能导致新任务失败

**建议修复：**
```python
class RedisLock:
    def acquire_with_renewal(self, lock_key, timeout=600, renewal_interval=60):
        """获取带自动续期的锁"""
        acquired = self.acquire(lock_key, timeout)
        if acquired:
            # 启动续期线程
            self._start_renewal_thread(lock_key, renewal_interval, timeout)
        return acquired
    
    def _start_renewal_thread(self, lock_key, interval, timeout):
        """后台线程定期续期"""
        def renew():
            while self.is_locked(lock_key):
                time.sleep(interval)
                self.redis.expire(lock_key, timeout)
        
        threading.Thread(target=renew, daemon=True).start()
```

### 2.5 【P2级】MergeLock内存锁上限风险

**问题描述：**
虽然设置了最大锁数量(MAX_LOCKS=5000)，但清理策略可能清理正在使用的锁。

**代码分析：**
```python
MAX_LOCKS = 5000

def _cleanup_oldest_locks(count=100):
    for key, lock_obj in list(_merge_locks.items()):
        if not lock_obj.is_locked():  # 只清理未锁定的
            keys_to_remove.append(key)
```

**潜在问题：**
1. 如果短时间内有大量文件(>5000)需要合并
2. LRU策略会清理最久未使用的锁
3. 被清理的锁对象可能还在被某个线程引用
4. 可能导致KeyError或内存访问错误

**建议修复：**
1. 增加软限制和硬限制
2. 清理前检查是否有活跃任务
3. 添加锁对象引用计数

### 2.6 【P2级】幂等性检查与锁顺序不一致

**问题描述：**
幂等性检查和锁获取的顺序可能导致竞态条件。

**代码分析：**
```python
# views/transfer/batch.py
def post(self, request):
    # 1. 先检查幂等性
    cached_result = idempotency_checker.check(form.idempotent_key)
    if cached_result:
        return json_response(data=cached_result)
    
    # 2. 后提交Celery任务
    task = batch_cancel_transfers.delay(...)
    
    # 3. 最后缓存结果
    idempotency_checker.cache(response_data)
```

**风险：**
- 两个相同请求同时到达，都通过了幂等性检查
- 都会提交Celery任务，导致重复执行
- 虽然任务内部有锁，但资源已被重复消耗

**建议修复：**
```python
# 使用"先获取锁再检查"的模式
with idempotency_lock(idempotent_key):
    cached_result = idempotency_checker.check(form.idempotent_key)
    if cached_result:
        return json_response(data=cached_result)
    
    task = batch_cancel_transfers.delay(...)
    idempotency_checker.cache(response_data)
```

## 3. 并发控制最佳实践对比

### 3.1 当前实现 vs 最佳实践

| 维度 | 当前实现 | 最佳实践 | 差距 |
|------|----------|----------|------|
| 锁超时 | 各层独立配置 | 统一协调，层级递减 | 中 |
| 死锁检测 | 无 | 锁等待超时+死锁图检测 | 高 |
| 锁续期 | 无 | 看门狗自动续期 | 中 |
| 锁粒度 | 文件级 | 文件级+任务级 | 低 |
| 幂等性 | Redis缓存 | 数据库唯一索引 | 中 |
| 监控告警 | 仅日志 |  metrics + 告警 | 高 |

### 3.2 推荐架构

```
┌─────────────────────────────────────────────────────────┐
│  应用层（幂等性控制）                                     │
│  ┌─────────────────────────────────────────────────┐   │
│  │  数据库唯一索引 (idempotent_key)                 │   │
│  │  插入成功=首次请求，插入失败=重复请求              │   │
│  └─────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────┤
│  服务层（分布式锁）                                       │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Redis RedLock (支持续期+看门狗)                 │   │
│  │  锁粒度：file_hash + tenant_id                   │   │
│  │  超时：任务预估时间 * 2                          │   │
│  └─────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────┤
│  数据层（数据库控制）                                     │
│  ┌─────────────────────────────────────────────────┐   │
│  │  select_for_update (nowait=true)                │   │
│  │  获取锁失败立即返回，不阻塞                       │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

## 6. 结论

当前资料库模块的并发控制机制**存在但不严谨**，主要体现在：

1. **锁层级之间缺乏协调** - 可能导致死锁和重复执行
2. **超时配置不合理** - 锁可能在任务完成前过期
3. **数据库锁使用不完整** - 批量操作存在竞态条件
4. **缺乏监控和自愈机制** - 问题发现和处理滞后
