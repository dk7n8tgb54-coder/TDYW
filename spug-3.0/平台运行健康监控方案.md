# 平台运行健康监控方案

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-06 |
| 状态 | 方案评审中（未实施，未改任何代码） |
| 修订 | 2026-09-06：采样与落库解耦，改为每分钟外部探活、每 5 分钟聚合落库；运行指标默认保留 30 天；补充 Nginx 完整请求指标和日志持久化要求 |
| 目标 | 在平台内回答"最近几天运行得稳不稳定"，可回看历史 |
| 实施落点 | 指标模型/API/页面放现有 `alert` 应用；请求日志改 Nginx 配置；外部探活放容器外（不新建 Django app） |

---

## 1. 背景与目标

目前平台对"有没有当场爆炸"已有覆盖（异常告警、磁盘/DB 巡检、容器 healthcheck），但**没有可回看的运行指标历史**，无法回答：

- 昨天有没有人访问？系统有没有偷偷出错？
- 昨天下午接口慢不慢？慢了多少？
- 这两天容器/Celery 有没有崩过、崩了多久？
- Celery 任务失败频率是在变高吗？

本方案补齐"结构化运行日志 + 聚合指标历史 + 外部探活 + 健康视图"这一块，设计原则：**日志用于追因、指标用于判断、探活用于证明可用；聚合而非请求流水入库；不引入 Prometheus/Grafana/Loki 等新观测栈；采集失败不影响业务**。

## 2. 现状盘点

### 2.1 已覆盖（不重复建设）

| 能力 | 现有实现 |
|---|---|
| 未处理异常告警 | `spug_api/libs/middleware.py` `HandleExceptionMiddleware` → `send_alert` |
| Celery 任务失败告警 | `spug_api/spug/celery.py` 全局 `@task_failure` 钩子 → `send_alert` |
| 磁盘巡检 + 满盘趋势预测 | `apps/alert/tasks.py` `check_disk_space`（每 10 分钟，`libs/trend.py`） |
| DB 指标巡检 | `apps/alert/tasks.py` `collect_db_metrics`（每 5 分钟，仅当前值缓存，无历史） |
| 依赖连通性 | `/api/document/health/`（DB/Redis/存储检查），docker-compose healthcheck 在用，但无历史记录 |
| 进程存活 | supervisor autorestart + 容器 `restart: unless-stopped` |
| 业务操作审计 | `apps/logs/` AuditLog（哈希链 + 90 天清理），与本方案无关，不动 |
| 请求访问日志 | Nginx/Gunicorn 已记录请求；Gunicorn 有耗时，Nginx 暂无上游耗时和统一 request_id |

### 2.2 缺失（本方案补齐）

- 无可查询的请求量、服务端错误率、网关错误率、慢请求率和延迟分布历史。
- Nginx 访问日志未持久化到独立卷，当前格式也不能直接分析上游状态和耗时。
- Celery 任务只有失败才留痕（体现为 Alert 行），无执行统计历史。
- DB 指标只存当前值缓存，无历史可回看（磁盘已有 7 天趋势，见 2.1），回看不了"昨天 DB 压力大不大"。
- 现有 Docker healthcheck 位于 `tdyw` 容器内部且不保存结果，不能证明用户访问链路过去是否可用。
- 无任何"近 48 小时稳定性 + 按天汇总"视图。

## 3. 方案选型

| 方案 | 内容 | 结论 |
|---|---|---|
| A | 零代码：每天看告警中心页 + healthcheck | 只能回答"报没报警"，否决 |
| **B（选定）** | 结构化运行日志 + 1 分钟外部探活 + 5 分钟聚合指标 + 健康视图 | 覆盖真实需求八九成，不引入完整观测栈 |
| C | Prometheus + Grafana（+Loki）外部观测栈 | 效果上限最高（带外监控、p95、全层覆盖），留作升级路径 |

**选 B 的理由**：本平台是小型内网单体，真实故障模式（崩溃重启、磁盘满、DB 耗尽、接口变慢、任务失败）都能被"现有告警 + 指标历史"覆盖；C 的核心优势（带外监控、分位数、多服务覆盖）在此规模下收益有限，而永久运维负担（多容器、PromQL/Grafana 维护）是实打实的。

**升级到 C 的触发条件**（出现任意一条再议）：
1. 出现 B 回答不了的排障需求：按接口/按 worker 细分延迟、日志与指标对齐分析。
2. 平台从单体拆成多个服务。
3. 需要正式的可用率/SLA 汇报指标。

届时可停止 B 的轻量采集并迁移到标准指标系统，现有历史数据仍可作为迁移前基线。

## 4. 总体设计

```
请求 ──► Nginx 结构化 access log（逐请求写文件，不逐请求写数据库）
          └─ time / request_id / method / uri / status / upstream_status
             request_time / upstream_response_time / bytes

Django HTTP 200 + error ──► 单独累计 business_error
未处理异常 / Celery 失败 ──► 复用现有 Alert，并累计对应错误数

独立于 tdyw 的探活任务（每 1 分钟）──► 请求 /api/document/health/
          ├─ 持久化 timestamp / success / status / duration_ms
          └─ 连续失败和恢复时产生健康事件；不把缺样本误判为正常

collect_db_metrics（既有，每 5 分钟）──► 当前值缓存 + 带窗口时间的短期快照

Celery beat（每 5 分钟）──► flush_run_metrics
          ├─ 聚合上一个完整 5 分钟窗口的访问日志、探活、错误和 DB 指标
          ├─ 幂等 upsert MariaDB run_metrics 一行
          └─ 延迟执行时允许补算遗漏窗口

Celery beat（每天）──► cleanup_run_metrics（默认保留 30 天）

管理员 ──► GET /api/alert/run-metrics/（只读，复用 system.alert.view 权限）
          └─ 运维管理 → 告警页新增"平台健康"Tab：48h 曲线 + 按天汇总 + 不可用/未知区间
```

核心组成部分：**持久化结构化访问日志、一张 5 分钟指标表、一条容器外探活链路、一个只读接口、一个前端 Tab、清理与数据完整性检查**。

## 5. 详细设计

### 5.1 数据模型（`apps/alert` 内新增）

```python
class RunMetric(models.Model):
    """运行指标，每个完整的 5 分钟窗口一行。"""
    class Meta:
        db_table = 'run_metrics'

    bucket_start = models.DateTimeField(unique=True, verbose_name='窗口起点')
    request_count = models.IntegerField(default=0, verbose_name='请求数')
    client_error_count = models.IntegerField(default=0, verbose_name='4xx 次数')
    app_server_error_count = models.IntegerField(default=0, verbose_name='Django 5xx 次数')
    gateway_error_count = models.IntegerField(default=0, verbose_name='502/503/504 次数')
    business_error_count = models.IntegerField(default=0, verbose_name='HTTP 200 业务失败次数')
    slow_count = models.IntegerField(default=0, verbose_name='慢请求数')
    total_ms = models.BigIntegerField(default=0, verbose_name='总耗时(ms)')
    max_ms = models.IntegerField(default=0, verbose_name='最大耗时(ms)')
    latency_le_200 = models.IntegerField(default=0)
    latency_le_500 = models.IntegerField(default=0)
    latency_le_1000 = models.IntegerField(default=0)
    latency_le_3000 = models.IntegerField(default=0)
    latency_gt_3000 = models.IntegerField(default=0)
    celery_fail_count = models.IntegerField(default=0, verbose_name='Celery 失败数')
    probe_count = models.IntegerField(default=0, verbose_name='探活次数')
    probe_success_count = models.IntegerField(default=0, verbose_name='探活成功次数')
    probe_total_ms = models.BigIntegerField(default=0, verbose_name='探活总耗时(ms)')
    probe_max_ms = models.IntegerField(default=0, verbose_name='探活最大耗时(ms)')
    db_threads_connected = models.IntegerField(null=True, verbose_name='DB 连接数')
    db_slow_queries = models.BigIntegerField(null=True, verbose_name='DB 慢查询累计值')
    created_at = models.DateTimeField(auto_now_add=True)
```

- 平均耗时 = `total_ms / request_count`，不单独存列。
- 延迟桶用于估算 p95，避免平均值掩盖少量慢请求，也避免最大值被单个异常请求放大。
- 普通 API 慢请求阈值初始设为 1000ms；上传、下载、预览路径单独统计或排除，不与普通 API 共用阈值。
- 4xx 仅作为参考，不进入平台稳定性错误率；`business_error_count` 也单独展示，只有明确标记为系统异常的业务错误才进入稳定性判断。
- `probe_count=0` 表示监控数据缺失，健康状态必须显示“未知”；`probe_success_count < probe_count` 才表示实际探活失败。
- `db_threads_connected`/`db_slow_queries` 允许 NULL：NULL 表示该窗口没有 DB 采集数据，避免写 0 造成误读。`db_slow_queries` 是累计值，计算增量时必须识别数据库重启后的计数器归零。
- 按纪律：`makemigrations alert` 指定 app；无 CharField；一功能一 migration。

### 5.2 采集挂点一：Nginx 结构化访问日志

- Nginx 是用户请求入口，由它记录请求量、状态和耗时，才能覆盖请求尚未到达 Django 时产生的 502/503/504。
- access log 使用 JSON Lines 或其他可严格解析的结构化格式，至少记录：时间、request_id、method、`$uri`、status、upstream_status、request_time、upstream_response_time、bytes。
- 使用 `$uri`，禁止记录带查询串的 `$request`/`$request_uri`；禁止记录 Token、Cookie、请求正文和响应正文。
- `/api/document/health/`、静态资源、WebSocket、普通 API、上传/下载/预览请求应分类，健康检查流量不能污染业务请求量，长文件请求不能污染普通 API 延迟。
- `/var/log/nginx` 必须持久化，按天和大小双重轮转，原始访问日志默认保留 14 天。聚合任务应能跨轮转文件读取，并用窗口唯一键保证重算不重复。

### 5.3 采集挂点二：Django 业务错误与异常

- 本项目 HTTP 200 + `{"error": "..."}` 不能按 HTTP 状态判定，应单独累计为 `business_error_count`，但预期参数校验失败不能直接算平台不稳定。
- `HandleExceptionMiddleware` 产生的未处理异常继续通过现有 `send_alert` 留痕，并计入系统错误；现有告警内容和脱敏逻辑不变。
- 如使用 Redis 暂存低频错误计数，一次 pipeline/Lua 完成并设置短超时；Redis 异常时只记录降级日志，不得阻塞或改变业务响应。

### 5.4 采集挂点三：外部探活（每分钟采样）

- 探活每分钟一次是为了缩短故障发现时间，并不代表每分钟都写一行数据库。5 分钟窗口内通常只有 5 个小样本，聚合后随指标一起落一行。
- 探活必须位于 `tdyw` 容器之外，优先放在独立运维节点；没有独立节点时至少放在宿主机定时任务中。容器内 Celery 心跳不能证明 Nginx/Gunicorn 和用户访问链路可用。
- 原始探活结果写入容器外持久化文件，至少保留 30 天；平台恢复后可补算停机窗口。连续失败达到告警阈值时立即通知，恢复时记录恢复时间。
- 单点部署下，如果宿主机和探活任务同时停止，只能标记为“监控数据缺失/未知”，不能宣称平台正常或精确计算 SLA。

### 5.5 五分钟聚合落库任务

- `flush_run_metrics` 每 5 分钟聚合上一个完整窗口：Nginx access log、探活样本、业务错误暂存值、现有 Alert/Celery 失败和带时间戳的 DB 指标快照。
- 使用 `bucket_start` 唯一键进行幂等 upsert；任务延迟或短时失败后，应从最后成功窗口开始补算，不能直接跳过并伪装成零值。
- 没有业务流量时仍写请求数为 0 的窗口；没有探活样本时 `probe_count=0`，该窗口状态为“未知”。指标行是否存在不再被当作 Web 存活证明。
- 任务注册进 `apps/alert/celery_beat_schedule.py` 的 `ALERT_BEAT_SCHEDULE`。Celery 失败继续复用现有 `@task_failure` 处理器和告警逻辑。

### 5.6 健康判定与告警

- 外部探活连续失败 3 次（约 3 分钟）触发不可用告警；单次失败只显示黄色波动，避免网络瞬断误报。恢复后记录实际失败和恢复时间。
- 5xx/网关错误率、慢请求率、近似 p95、Celery 失败和 DB/磁盘指标分别判断，不用一个总分掩盖具体问题。
- 初始阈值仅作为试运行值，先采集 7 至 14 天基线再确认。阈值修改必须人工评审，系统不得为了显示绿色自动放宽阈值。
- 聚合任务缺失、探活样本缺失、日志不可读分别显示“数据缺失”，不等同于平台故障，也不等同于平台正常。

### 5.7 只读查询接口

- `GET /api/alert/run-metrics/?hours=48`：返回 5 分钟序列，包括请求量、服务端/网关/业务错误、慢请求率、平均/最大/近似 p95、探活成功率、Celery 失败和 DB 指标。
- `GET /api/alert/run-metrics/summary/?days=7`：按天聚合请求量、系统错误、慢请求、不可用窗口和未知窗口。
- 视图放 `apps/alert/views/`，只读，无写副作用。

### 5.8 前端页面

- 位置：`spug_web/src/pages/system/alert/` 告警页内新增 **"平台健康" Tab**（运维管理菜单，路由不变），不新建页面/路由。
- 内容：
  - 近 48 小时曲线（请求量、错误率、耗时、探活、DB 连接数，仿现有"磁盘使用趋势"图模式）；
  - 近 7 天每日汇总卡片；
  - 实际不可用时段红色高亮，监控数据缺失时段灰色高亮，两者不能混淆。
- 按需加载（进 Tab 才请求），不加常驻轮询；组件测试放同目录 `__tests__/`。

### 5.9 保留与清理策略

- `cleanup_run_metrics` 每天一次，默认物理删除 30 天前的 5 分钟运行指标；30 天约 8640 行，足够回答最近两天、近一周和近月趋势。
- Nginx 原始访问日志默认保留 14 天并设置总大小上限；原始探活日志默认保留 30 天。
- `AuditLog` 的 90 天保留不变。审计日志用于追责和合规，运行指标用于近期运维判断，两者没有必要使用同一保留期。
- 保留期使用受控配置，允许在 7 至 90 天范围内人工调整；只有出现月度对比、季度容量分析或正式 SLA 需求时，才考虑将运行指标延长到 90 天或增加按日汇总表。

### 5.10 频率与保留期结论

| 数据 | 采样/写入频率 | 默认保留 | 原因 |
|---|---|---|---|
| 外部探活 | 每 1 分钟采样 | 原始记录 30 天 | 采样频率决定故障发现速度；连续 3 次失败可在约 3 分钟内告警 |
| Nginx 访问日志 | 每请求顺序写文件 | 14 天 + 总大小上限 | 用于追查具体请求，不进入业务数据库 |
| 运行聚合指标 | 每 5 分钟 1 行 | 30 天 | 足够看近 48 小时、近一周和近月趋势，并与现有 DB 指标周期对齐 |
| 审计日志 | 按业务操作写入 | 维持现有 90 天 | 用于追责和合规，不属于运行监控指标 |

一分钟落库在技术上并不算大：30 天约 43200 行，90 天约 129600 行。但它会增加 5 倍写入和图表点数，而当前目标只要求判断最近两天是否稳定。5 分钟窗口仍保留请求总数、错误数、最大耗时和延迟桶，不会丢失错误事件，只把时间定位精度从 1 分钟降低到 5 分钟；故障发现速度仍由每分钟外部探活保证。

90 天运行指标在容量上也不算大，但当前没有季度趋势或正式 SLA 需求，长期保留没有明确收益。默认 30 天更符合最小建设原则；以后出现月度同比、季度容量规划或 SLA 审计需求，再由管理员显式延长，而不是一开始按审计日志的 90 天机械设置。

## 6. 关键设计决策

| 决策 | 理由 |
|---|---|
| 1 分钟探活、5 分钟聚合 | 探活频率决定发现故障的速度，落库频率决定图表粒度和数据库写入量，两者不应绑定 |
| 请求指标以 Nginx 为主 | 覆盖 Django 之前的 502/503/504，且不在每个请求中增加数据库或多次 Redis 写入 |
| flush 任务放 Celery beat | 聚合工作脱离请求进程，按完整窗口幂等计算；任务缺失只表示监控数据缺失，不能充当 Web 心跳 |
| 外部探活独立于 tdyw | Celery、Redis 和 Gunicorn 位于同一容器时，内部心跳不能证明用户访问链路可用 |
| 落 MariaDB 而非只存 Redis | Redis 与应用同容器，重启即丢；`tdyw-db` 是独立容器，崩溃前后数据可留存 |
| Redis 只暂存低频补充计数 | Gunicorn 多 worker 不能用进程内存汇总；仅业务错误等 Nginx 无法识别的指标需要 Redis，且采集必须 fail-open |
| DB 指标历史复用 `collect_db_metrics`，不重复查询 | 采集任务除维持现有当前值缓存外，再写入带窗口时间且 TTL 不少于 15 分钟的快照；flush 按窗口读取，避免两个 5 分钟任务的执行先后和 300 秒缓存过期造成误缺失 |
| 未知与不可用分开 | 没有探活样本是监控缺失；有样本且失败才是不可用，禁止用零值掩盖 |
| 权限复用 `system.alert.view` | 与告警页同权限，免新增权限码、免动 `page_perms` 缓存版本号；如未来要独立权限再按 `<app>.<model>.<action>` 增补 |
| 运行指标默认保留 30 天 | 当前目标是近 48 小时和近月趋势；90 天审计保留策略不应机械套用到运行指标 |
| 实现放现有 `alert` app | 复用 send_alert、beat 合并、权限与运维菜单，避免新 app 样板成本 |

## 7. 开销评估

- **每请求**：Nginx 本来就写 access log，只增加少量结构化字段；成功请求不增加数据库写入。日志真实开销需在试运行中测量，不预先承诺“微秒级”。
- **每分钟**：外部探活 1 次，全天 1440 次；原始记录很小且在容器外顺序追加。
- **每 5 分钟**：1 次窗口聚合 + 1 次幂等 upsert，全天 288 行；与现有 DB 指标采集周期一致。
- **查询**：近 48 小时最多 576 个窗口，30 天最多 8640 个窗口，单列时间索引足够。
- **存储**：聚合表的体量很小；真正需要限制的是逐请求 Nginx 原始日志，因此必须同时设置保留天数和总大小上限。

## 8. 已知盲区（接受并记录）

1. 外部探活若部署在同一宿主机，宿主机整体宕机时探活也会中断，只能得到“未知”；需要正式 SLA 时必须部署到独立节点。
2. `/api/document/health/` 覆盖 Nginx → Django → DB/Redis/存储检查，不覆盖 WebSocket 的长期连接质量、kkFileView 实际转换成功率和完整业务事务。
3. 5 分钟窗口可能稀释持续不足一分钟的尖峰；通过最大耗时、延迟桶和 14 天原始访问日志保留排查能力。需要严格分钟级 SLA 时再切换为 1 分钟窗口。
4. 现有 HTTP 200 + error 没有统一错误分类码，初期只能将业务失败作为参考指标；未建立“预期校验错误/系统错误”分类前，不能把它全部计入稳定性错误率。
5. 从日志补算指标必须正确处理轮转边界、重复执行和延迟窗口；解析失败时标记数据缺失，禁止写入虚假的零值。
6. MariaDB 宕机期间聚合任务无法落库，需依靠容器外原始探活日志和持久化 Nginx 日志在恢复后补算。

## 10. 明确不做的事

- 不做每请求流水日志表。
- 不做精确 p95/p99 原始样本存储；仅用固定延迟桶估算趋势，不做 APM 链路追踪。

- 不改动现有审计日志语义和 90 天保留策略。
