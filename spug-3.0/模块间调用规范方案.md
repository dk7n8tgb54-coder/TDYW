# 模块间调用规范方案

## 1. 背景

当前项目中存在一个模块需要使用另一个模块数据的场景，例如：

- 值班日志模块引入运行日志信息
- 值班日志模块引入干扰记录信息
- 后续可能出现故障管理、系统升级、设备履历等模块之间相互调用

如果调用方直接引入其他模块的 `models.py` 并直接查询数据库，会导致模块之间耦合过重。被调用模块一旦调整字段、表结构、过滤逻辑或权限规则，调用方也容易受到影响。

因此需要建立统一的模块间调用规范。

## 2. 总体原则

模块之间通过公开服务接口通信，不直接依赖对方内部实现。

核心规则：

> 跨模块调用只能调用对方公开的 `services.py` 接口；不要直接查询对方模型，不要调用对方视图，不要依赖对方内部实现。

## 3. 推荐目录结构

每个业务模块可以按需增加 `services.py`，用于暴露给其他模块调用的稳定接口。

```text
apps/
  duty/
    models.py
    views.py
    services.py
    import_services.py

  runlog/
    models.py
    views.py
    services.py

  interference/
    models.py
    views.py
    services.py
```

说明：

- `models.py`：只定义本模块数据模型
- `views.py`：只处理 HTTP 请求、参数解析、响应返回
- `services.py`：封装本模块对外提供的业务能力
- `import_services.py`：当某个模块需要聚合多个模块数据时，可单独放聚合逻辑

## 4. 调用规则

### 4.1 查询其他模块数据

调用方不要直接引入对方模型。

不推荐：

```python
from apps.runlog.models import RunLog, RunLogUpdate

logs = RunLog.objects.filter(...)
```

推荐：

```python
from apps.runlog.services import get_duty_import_items

items = get_duty_import_items(target_date, request.user)
```

被调用模块负责处理自己的查询逻辑、租户过滤、字段映射和数据格式。

### 4.2 修改其他模块数据

调用方不要直接更新对方模型。

不推荐：

```python
from apps.runlog.models import RunLog

RunLog.objects.filter(id=runlog_id).update(status='closed')
```

推荐：

```python
from apps.runlog.services import close_runlog

close_runlog(runlog_id, request.user, reason)
```

这样运行日志模块可以在 `close_runlog` 内部统一处理权限、状态校验、更新时间、操作记录等逻辑。

### 4.3 通知类场景

如果一个模块只是要通知其他模块“发生了某件事”，可以后续引入事件机制。

适合事件的场景：

- 干扰记录创建后，自动生成运行日志
- 系统升级完成后，自动写入操作审计
- 故障关闭后，通知统计模块刷新缓存

不适合事件的场景：

- 页面需要按日期立即查询其他模块数据
- 调用方需要同步拿到返回结果

例如“值班日志按日期引入运行日志和干扰记录”属于同步查询场景，应使用 `services.py`，不需要事件机制。

## 5. 当前值班日志引入方案

当前值班日志模块需要引入运行日志和干扰记录，建议改成三层结构：

```text
apps/runlog/services.py
  get_duty_import_items(date, user)

apps/interference/services.py
  get_duty_import_items(date, user)

apps/duty/import_services.py
  get_import_records(date, user)
```

### 5.1 运行日志模块提供接口

```python
# apps/runlog/services.py

def get_duty_import_items(date, user):
    """
    获取指定日期可引入值班日志的运行日志动态。
    返回值班日志模块需要的摘要数据，不暴露 RunLog / RunLogUpdate 模型对象。
    """
    ...
    return [
        {
            'id': 'runlog_1',
            'source': 'runlog',
            'title': '事件标题',
            'sequence': 1,
            'recorder': '记录人',
            'content': '动态内容',
        }
    ]
```

### 5.2 干扰记录模块提供接口

```python
# apps/interference/services.py

def get_duty_import_items(date, user):
    """
    获取指定日期可引入值班日志的干扰记录。
    返回值班日志模块需要的摘要数据，不暴露 Interference 模型对象。
    """
    ...
    return [
        {
            'id': 'interference_1',
            'source': 'interference',
            'title': '干扰类型 - 频率',
            'sub_title': '上报部门',
            'content': '干扰现象',
        }
    ]
```

### 5.3 值班日志模块负责聚合

```python
# apps/duty/import_services.py

from apps.runlog.services import get_duty_import_items as get_runlog_items
from apps.interference.services import get_duty_import_items as get_interference_items


def get_import_records(date, user):
    return {
        'date': date,
        'runlog': get_runlog_items(date, user),
        'interference': get_interference_items(date, user),
    }
```

### 5.4 视图层保持简单

```python
# apps/duty/views.py

class DutyImportView(View):
    @auth('duty.duty.view')
    def get(self, request):
        from datetime import datetime
        from apps.duty.import_services import get_import_records

        date_str = request.GET.get('date')
        target_date = date_str if date_str else datetime.now().strftime('%Y-%m-%d')

        return json_response(get_import_records(target_date, request.user))
```

## 6. 数据返回规范

跨模块接口不要返回 Django Model 对象，应该返回普通字典、列表或明确的 DTO 结构。

推荐返回：

```python
{
    'id': 'runlog_1',
    'source': 'runlog',
    'title': '标题',
    'content': '内容',
}
```

不推荐返回：

```python
RunLog(...)
Interference(...)
```

原因：

- 调用方不应该知道被调用模块的字段细节
- 避免调用方继续访问模型内部属性
- 便于后续调整数据库结构
- 便于后续改成缓存、远程接口或事件来源

## 7. 公共能力放置规则

公共技术能力可以放到 `libs/`。

适合放 `libs/`：

- 租户过滤工具
- 时间格式工具
- 导出工具
- 权限辅助工具
- 通用响应格式工具

不适合放 `libs/`：

- 运行日志如何组装给值班日志
- 干扰记录如何转换成值班日志引入项
- 故障记录如何关闭
- 系统升级如何流转状态

业务规则应该留在对应业务模块的 `services.py` 中。

## 8. 后续扩展方式

如果后续值班日志还需要引入故障记录、系统升级、设备履历等模块，只需要让对应模块提供同名或类似接口。

例如：

```text
apps/fault/services.py
  get_duty_import_items(date, user)

apps/system_upgrade/services.py
  get_duty_import_items(date, user)

apps/device_lifecycle/services.py
  get_duty_import_items(date, user)
```

然后在 `apps/duty/import_services.py` 中聚合：

```python
def get_import_records(date, user):
    return {
        'date': date,
        'runlog': get_runlog_items(date, user),
        'interference': get_interference_items(date, user),
        'fault': get_fault_items(date, user),
        'system_upgrade': get_system_upgrade_items(date, user),
        'device_lifecycle': get_device_lifecycle_items(date, user),
    }
```

## 9. 迁移步骤建议

建议分阶段落地，避免一次性改动过大。

### 第一阶段：值班日志引入改造

- 新增 `apps/runlog/services.py`
- 新增 `apps/interference/services.py`
- 新增 `apps/duty/import_services.py`
- 将 `DutyImportView` 中直接查询 `RunLog / RunLogUpdate / Interference` 的逻辑迁移到服务层

### 第二阶段：新功能按规范开发

- 新模块对外提供能力时，优先写 `services.py`
- 调用方只能调用服务接口
- Code Review 时检查是否存在跨模块直接 import model 的情况

### 第三阶段：清理历史耦合

- 搜索 `from apps.xxx.models import`
- 判断是否属于跨模块调用
- 逐步迁移到对应模块的 `services.py`

## 10. Code Review 检查项

后续评审模块间调用时，可以重点检查：

- 是否直接引入了其他业务模块的 `models.py`
- 是否直接调用了其他业务模块的 `views.py`
- 是否绕过了对方模块的权限、租户过滤、状态校验
- 跨模块接口是否返回了 Model 对象
- 服务接口返回的数据结构是否稳定、清晰、够用
- 公共工具和业务规则是否混放到了 `libs/`

## 11. 结论

项目后续统一采用以下规范：

> 模块内部的数据模型和业务细节由本模块自己维护；其他模块如需使用，只能通过该模块公开的 `services.py` 接口获取或操作。

这套方案可以降低模块耦合，减少后续字段调整、业务规则变化带来的连锁修改，也方便后期扩展更多模块间协作。
