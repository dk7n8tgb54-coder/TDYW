- 本次 views.py / models.py / index.js 被整体转成 CRLF（HEAD 版本为纯 LF），违反 AGENTS.md 行尾规范
- 修复：`fs.writeFileSync(f, c.replace(/\r\n/g,'\n'))` 内容不动只改行尾

- git 的 "LF will be replaced by CRLF" warning 是仓库 autocrlf 配置的正常提示，与文件本身行尾无关

## 追加 1：自然排序修复（同日，用户反馈数字字典序问题）
- 现象：`文件11,文件12,文件2` —— 字典序逐位比较，用户期望 `文件2,文件11,文件12`
- 修复：`useSorting.js` compareValues 的 `localeCompare(b, 'zh-CN', { numeric: true })`（一行改动，两处方向分支）
- **行为验证**（node 脚本实测）：`文件2,文件3,文件4,文件11,文件12` ✓；混合场景 `2026年第3季度 < 2026年第12季度`、`第2号批复 < 第11号批复`、`a2.txt < a10.txt` ✓
- 本次编辑未破坏 LF 行尾（CRLF:0）
- **局限（已向用户说明）**：仅作用于前端单页内排序；后端 MariaDB 无法原生自然排序，超一页的目录页间边界仍是字典序。彻底方案是 sort_key 补零列 + 写入路径维护（多处改动），按 YAGNI 暂不做
- 相关：Windows 资源管理器默认自然排序（StrCmpLogicalW），网盘多为字典序

## 追加 3：文件夹/文件分组恢复（同日，用户反馈混排）
- **现象**：自然排序生效后文件夹和文件混在一起。原因：`compareWithFolderPriority` 原本只在 **size 列**做文件夹优先，名称排序无分组逻辑；此前"看起来分组"只是后端返回顺序（文件夹在前）未被重排
- **修复**：`a.isFolder !== b.isFolder` 时文件夹恒返回 -1（不随 order 方向变化），适用于所有列。原 size 列降序时文件夹在后的行为统一为恒在前（Windows/OneDrive/百度网盘惯例）
- **行为实测**（模拟 6 条混合数据）：名称升序 `[D]2026报告 [D]法规汇编 [F]文件2 [F]文件3 [F]文件11 [F]文件12` —— 分组+自然排序同时正确；降序/大小/时间列文件夹均恒在前
- 教训：**前端重排开启后，所有"依赖后端顺序"的隐式展示效果都会失效**（分组、置顶等），必须在排序器里显式重建

## 追加 4：文件夹树/选择器自然排序统一修复（同日，用户反馈树没改好）

- **行为实测**：树同级 `2026报告,法规汇编,文件夹2,文件夹11,文件夹12` ✓；列表 `[D]分组 [F]文件2,文件11,文件12` ✓
