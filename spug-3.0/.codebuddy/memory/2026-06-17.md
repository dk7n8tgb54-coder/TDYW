5. `constants/upload.js` — `MAX_DISPLAY_COUNT` 注释明确仅显示用途
6. `upload/core/controls/ItemOperationController.js` — `resumeItem` 懒创建重建；`cancelItem`/`removeItem` 显式释放

### 设计外必要补充

### 编译错误修复（10:28 用户反馈）
- **问题**：3 处 `this.core.stateMachineManager?.remove(id)` 作为独立语句触发 ESLint `no-unused-expressions`
  - `ItemOperationController.js` 284 行（cancelItem）
  - `ItemOperationController.js` 372 行（removeItem）
  - `StateChangeHandler.js` 89 行（终态释放）
- **原因**：可选链 `a?.b()` 作为独立语句时整个表达式值未使用，触发规则；文件内其他 `?.` 都是右侧赋值（`const x = a?.b`），不触发

- **教训**：CRA 默认 ESLint 不允许 `?.` 独立语句；在状态机释放这种"fire-and-forget"场景应优先用 `if` 显式判断

### 第二轮修复：1003 任务卡住（11:13 用户反馈）
- **现象**：用户测试发现一次最多上传 1003 个，剩余全部 waiting（1003 ≈ MAX_MACHINES=1000 + 3 并发）
- **根因**：`startWaiting` 用 `activeUploads` 计数器判断并发，但该计数器**只在 uploading 状态增减**（`handleUploadingState:incrementActiveUploads`），`calculating` 状态（大文件异步算 MD5 期间）不占计数器
- **连锁反应**：大文件 calculating 期间 activeUploads=0 → startWaiting 误判有空闲槽位 → 持续调度新任务 → 状态机数量爆炸到 MAX_MACHINES 上限 → 第 1001 个 ensureStateMachine 返回 null → 永久 waiting
- **代码与注释不一致**：原注释写"calculating + uploading"，但实际代码只统计了 uploading
- **修复**：`startWaiting` 的 `activeCount` 改为直接从队列统计 `calculating + uploading` 状态任务数（`queue.filter`），不再依赖 `activeUploads` 计数器；`merging` 不占槽位
- **教训**：并发计数器如果只覆盖部分状态，调度入口必须用队列实际状态统计而非计数器；注释与代码不一致是 bug 的高发区

### 第三轮修复：保护阈值彻底降级为运行时资源限制（12:50 用户反馈）

用户指出第二轮修复只是把硬上限从 200 抬到 1000，"单次上传无数量限制"核心设计未完成。按用户方案做 5 处深度加固：

**1. `StateMachineManager.js`**：`MAX_MACHINES` → `MAX_ACTIVE_MACHINES`（语义明确为保护阈值）
- `create()` 达到阈值时：原 `cleanup(0)`（只清终态）→ 新 `_aggressiveCleanup()`（清终态 + orphan）
- orphan = 队列中已不存在的非终态状态机（如任务被删除但状态机未释放）
- 清理后仍超才拒绝创建，日志带 `{size, uploadId, cleaned}` 便于排查
- 新增 `_aggressiveCleanup()` 方法：遍历 machines，终态直接删；非终态查 `machine.context.queueStore.findUploadItemInCurrentTenant`，找不到则删

**2. `FileUploadCoordinator.js`**：确认 `_processBatch`/`_processUniform` 入队路径无 create 调用（全局仅 `UploadCoordinator.ensureStateMachine` 一处 create），仅更新 2 处注释常量名

**3. `UploadCoordinator.startWaiting` 重写调度循环**：
- 新增 `canPrepareStart(item)` 预检：`status==='waiting' && file && !isPausedByUser && !isCancelledByUser`
- 创建前先预检，避免创建无法 START 的状态机堆积
- `ensureStateMachine` 返回 null 时 **break**（而非 continue）：避免一轮扫爆所有 waiting，等待终态释放后 `processPending` 重试
- `canTransition('START')` 失败立即 `remove(item.id)`：避免堆积
- `transition('START')` 失败也立即 `remove(item.id)`

**4. `StateChangeHandler.js` 终态释放闭环**：终态 `setTimeout(0)` 释放状态机后立即 `uploadCoordinator.processPending()`，让 waiting 任务顶上来，形成"完成-释放-调度"闭环（之前只释放不调度，依赖其他触发点）

**5. `constants/upload.js`**：`MAX_DISPLAY_COUNT: 200` 保持不变，确认仅 UI 用途（不参与 queue 截断/waitingItems 截断/调度/入队限制）

**目标架构**：
- 上传队列：可有 1000/5000/10000 个 waiting 任务（无上限）
- 状态机：只为即将运行/正在运行/暂停/短期错误重试任务存在（稳定在并发数左右）
- 并发数：始终由 `MAX_CONCURRENT_UPLOADS=3` 控制
- 终态：completed/error/cancelled 后释放 + 触发调度

### 第四轮修复：remove 误删运行中状态机（13:30 用户反馈"依旧1003"）

**根因（上一轮引入的 bug）**：我在 startWaiting 里加了 `canTransition('START')` 失败立即 `remove(item.id)` 的逻辑。但状态机可能已在运行（calculating/uploading），只是 item.status 因时序窗口仍是 'waiting'。remove 会**误删正在运行的状态机** → 上传中断 → processPending 又创建新状态机 → 新状态机也被 remove → 每轮 processPending 都删除+创建 → 状态机数量爆炸到 MAX_ACTIVE_MACHINES(1000) → 第 1001 个 ensureStateMachine 返回 null → 永久 waiting

**关键代码路径分析**：
1. `transition('START')` 内部（UploadStateMachine.js:196）：`currentState = toState` 在 entry 钩子**之前**同步更新
2. entry 钩子（onCalculatingEntry:410）→ `actions.updateItem` → EventBus emit STATUS_CHANGE → StoreEventAdapter.handleStatusChange → `queueStore.updateUploadItem`（全部同步）
3. `notifyListeners`（UploadStateMachine.js:331-336）用 `queueMicrotask` **异步**通知 listener（StateChangeHandler.handle）
4. 所以 transition('START') 返回时 item.status 已被同步更新为 'calculating'，但 StateChangeHandler.handle 还在 microtask 队列里

**修复**：
1. **activeCount 改用状态机 currentState 统计**（新增 `StateMachineManager.countByStates(['calculating','uploading'])`），不依赖 item.status 的 EventBus 更新时序，直接读 `machine.getState()`（transition 内同步更新的 currentState）
2. **去掉所有 remove 逻辑**：`canTransition('START')` 失败只 `continue`，不 remove（状态机可能正在运行，remove 会误删）
3. **已有状态机不在 waiting 状态时直接 skip**：`sm.get(item.id)` 返回已有的，如果 `getState() !== 'waiting'`，说明已被调度过，直接 continue

**教训**：
- 不要在调度循环里 remove 状态机——状态机可能正在运行，remove 会导致上传中断 + 状态机数量爆炸
- 并发槽位统计要用状态机 currentState（唯一可靠的真相源），不要用 item.status（依赖 EventBus→StoreEventAdapter 更新链，有时序风险）
- `transition()` 内部 currentState 同步更新在 entry 钩子之前，notifyListeners 是 queueMicrotask 异步

### 第六轮：根因定位 + 修复"只能上传3个"（14:05 用户提供日志）

**日志关键证据**：
- `activeUploads` 正确递减 3→2→1→0
- 但 `countByStates(['calculating','uploading'])` 一直停在 3，状态机总数也停在 3
- 我加的 `transition 失败` 日志一条都没出现 → **transition 根本没被尝试**

**根因**：`fileUpload.js` 的 `uploadFileNormal`（小文件上传）成功后只更新了 `item.status='completed'`，但**从未调用 `stateMachine.transition('UPLOAD_COMPLETE')`**。状态机永远卡在 `uploading`，`countByStates` 永远返回 3，后续任务无法启动。

对比 `chunkUpload.js:258` 大文件路径在分片上传完成后有 `stateMachine.transition('UPLOAD_COMPLETE')`。小文件路径漏了。

**修复（3 处）**：
1. `fileUpload.js` `uploadFileNormal` 成功路径：加 `transition('UPLOAD_COMPLETE')`（guard `isNormalUpload` 检查 `totalChunks<=1` → 转到 `completed`）
2. `fileUpload.js` `uploadFileToFolder` 小文件成功路径：同样加 `transition('UPLOAD_COMPLETE')`
3. `UploadLifecycle.js` `onCompleted`：移除 `decrementActiveUploads()`（`handleUploadingState` finally 块已统一递减，避免双重递减）

**双重递减分析**：
- `handleUploadingState` finally 块在 `startUpload` 返回后递减（覆盖成功/失败/异常）
- `onCompleted` 在状态机到达 `completed` 时触发（小文件直通 / 大文件 merging→completed）
- 两者都会执行 → 双重递减 → 移除 `onCompleted` 中的递减
- 错误路径：`handleUploadingState` catch 调 `transition('ERROR')` → `onError`（不含递减），finally 仍递减 ✓

**guard 机制确认**：状态机的 `isNormalUpload()` 方法从 `context.queueStore` 查找 item，不依赖 payload，小文件 `totalChunks=1` → guard 通过 → `uploading→completed`
