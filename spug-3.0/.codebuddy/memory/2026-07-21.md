## locust 上传 401 风暴根因与修复（已改代码 locustfile/_common.py）

kkFileView 预览压测出现 ~17% 上传请求 401（"验证失败，请重新登录"），查询列表 0%。
**根因**：非服务端 bug，是压测 harness 的 Token 池竞态。Spug 每次登录都 `access_token=uuid4().hex` 让旧 token 立即失效（TOKEN_TTL=8h，非过期）。`_common.py` 的 `login_shared`/`_refresh` 在 `_token_pool_lock` **外**调 `_do_login`，同一共享账号的多个并发线程各自登录，N 次登录刷掉前 N-1 个 token → 401 级联 → 耗尽 3 次重试被记为失败。上传是 on_start 首个请求故中招，查询在 token 自愈后才跑故 0%。
**修复**：新增 `_account_locks`（每账号一把锁）+ `_obtain_token()`（adopt-or-relogin + 按账号串行登录），`login_shared`/`_refresh`/`refresh_token` 全部走它，保证同一账号同一时刻只真登一次、其余 adopt 最新 token，从根消除竞态。`py_compile` 通过，lint 仅预存 locust 未装告警。

**device 压测复现与验证（同日下午）**：用户跑 `locustfile_device.py` 报 ~10% 401 + `加载设备列表失败: 'str' object has no attribute 'get'`。在 `tdyw` 容器内用 urllib + 50 线程并发 5 账号复现：修复前 1602/2000 请求 401；把 `_obtain_token` 的「按账号串行登录+adopt」算法搬进复现脚本后 **401→0/2000、解析错误 0**。
**关键因果**：`'str' object has no attribute 'get'` 是 401 风暴的**次生现象**——列表接口 401 时返回 `{"data":"","error":"验证失败..."}`，旧版 `load_existing_devices` 用 `result['data']['data']`/非防御式 `.get('data').get('data')` 对空串 `""` 调 `.get('data')` 才崩。当前磁盘版 `load_existing_devices`（isinstance 守卫 + `if not isinstance(device, dict): continue`）已防御，故该报错不会再现。
**结论**：根因就是 401 风暴（即上午修的 `_common.py` 竞态），device 脚本本身无需改；用户那次失败用的是修复前的旧 `_common.py`（`_common.py` 工作区未提交修改）。**用当前工作区代码重跑即可**。`修复时间不能早于故障时间` 是履历事件的业务校验（预期内），非 bug。

## locust device 脚本"只建设备没建事件"根因 = 响应解析 bug（已修）

用户反馈 device 压测只建了设备履历表单、没给每个设备建事件。排查后发现**事件创建逻辑本来就有**（`prepare_test_data` 给每个设备建 3-8 个事件 + `create_event` task），但被两处**响应解析 bug** 废掉：
- 后端 `json_response` 把单对象包成 `{"data": {...含id}}`、列表包成 `{"data": [...]}`，且 `to_dict` 确认输出包含主键 `id`。

**修复**：所有 id 解析改为 `(result.get('data') or {}).get('id')`；列表解析改为 `result.get('data') or []`。`py_compile` 通过。
**系统性隐患（待办，本次未改其他脚本）**：其余 locust 脚本同样存在响应解析不匹配：

## 压测 device 脚本：401 风暴根因修复 + 列表解析修复（重要，可复用）

**现象**：locust device 跑 40~50 并发实测 ~10.77% 请求失败，全部 401；日志 `加载设备列表失败: 'str' object has no attribute 'get'`。

**根因1（401 风暴，核心）**：`locustfile/_common.py` 的 `TokenSharedHttpUser._refresh()` 原实现每次 401 都直接 `refresh_token`（重新登录）。而认证中间件 `libs/middleware.py._authenticate_x_token` 用 `User.objects.filter(access_token=access_token)` 校验，登录会写入**新** access_token 使旧 token 不再匹配 DB → 立即失效。5 个账号被 50 并发用户共享（每账号~10 用户），任一用户刷新 → 同账号其他 9 用户 token 集体失效 → 集体 401 → 集体刷新 → 死循环（实测 4774 次重新登录）。

**修复1（adopt-or-relogin）**：重写 `_refresh`：
- 先查 `_token_pool[username]` 是否已有比 `self.token` 更新的 token（别人刚刷新过）→ 直接采用，不重新登录；
- 仅当池中 token 与自身一致（说明确实过期、无人刷新）才在 `_token_pool_lock` 内串行重新登录；
- 串行保证同一账号每次过期最多一次登录。实测应使 401 失败趋近于 0（首次 401 被 `with resp: resp.success()` 掩盖，重试用新 token 成功）。
- **结论性教训**：压测 token 池设计里，"登录/刷新使旧 token 失效"与"多用户共享同账号 token"本质冲突，必须用 adopt 而非重登来消除震荡；或干脆 1 账号配 1 并发用户（需服务器多建账号，本项目仅 ~38 账号未采用）。

**根因2（列表解析）**：`locustfile_device.py` 的 `load_existing_devices()` 用 `result.get('data') or []` 当设备列表遍历，但实际部署返回 `result['data']` 是字典（如 `{"records":[...]}` 或 `{"data":[...]}`），遍历到字符串 key → `device.get` 报错 → 非首用户 `test_device_ids` 为空 → 跳过详情/事件等任务。

**修复2（兼容多种结构）**：改为先取 `data = result.get('data')`；若是 dict 则取 `.get('data') or .get('records')`；非 list 兜底 `[]`；循环内跳过非 dict 元素。同样模式适用于 interference/runlog 等脚本列表解析（已知 interference 用 `result['data']['records']` 实为 `result['data']`=列表，属同类隐患，待统一审计）。

**附带调整**：每个设备履历事件数 `prepare_test_data` 从 `random.randint(3,8)` → `(10,20)` → 最终 `(20,40)`（用户嫌少逐步加）。

**验证**：read_lints 仅 basedpyright 环境噪音（locust 未装 + params 字典类型推断误报），无真实语法错误；未跑容器压测（用户自行跑）。

## interference 压测 [FAIL] 0.52% 根因 + 修复

**现象**：`locustfile_interference.py` 单跑 50 并发 5min → 7493 req / 39 fail (0.52%) → [FAIL]。错误明细：38× HTTP 401（列表 11 / 创建 8 / 获取记录ID 16 / 统计 2 / 更新 1），2× 业务「记录不存在或无权限」（更新 1 + 删除 1）。
