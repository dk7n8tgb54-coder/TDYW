## 修复登录页 import 相对路径错误（构建失败）

### 现象
Docker frontend-builder 构建报错：
```
./src/pages/login/index.js
Cannot find file '../routes' in './src/pages/login'.
```

### 根因
2026-07-26 给工作台菜单加 auth 时，在 `spug_web/src/pages/login/index.js` 引入 `routes` 写成了 `import routes from '../routes'`，少了一层。

## 文件夹树单击节点同时展开子文件夹

### 需求
当前单击文件夹节点只触发右侧文件列表显示下一级（文件+子文件夹），文件夹树本身不展开。用户希望单击节点时**树本身也展开显示其子文件夹**。

### 改动
`spug_web/src/pages/document/FolderTree.js` 的 `handleSelect`：
- 三个分支（system-root / private-root|public-root / 普通节点）末尾分别追加 `this._expandNodeOnSelect(node.key)`
- 新增 `_expandNodeOnSelect(key)` 方法：未展开且非叶子 → 把 key 加入 `expandedKeys`；antd Tree 检测到 `children=undefined` 会自动触发 `onLoadData` 按需加载子文件夹
- 新增 `_findNodeInData(nodes, key)` 递归查找节点（用于读 `isLeaf`）

### 设计决策
1. **不实现 toggle**：单击已展开节点保持展开，不折叠。折叠仍由展开三角专门负责——避免误折叠丢失视野
2. **叶子节点跳过**：`isLeaf===true` 不展开（无子文件夹，展开也无意义）
3. **根节点也支持**：虽然根节点初始已展开，但统一处理逻辑（保持一致性）
4. **不重复展开**：`expandedKeys.includes(key)` 已展开则 `return null`（setState 返回 null 表示无变化，React 跳过 rerender）

### 验证
- read_lints：0 错误
- @babel/parser：OK

### 关键技术点
- antd Tree 受控展开：`expandedKeys={state.expandedKeys}` + `onExpand` setState
- children=undefined + expandedKeys 包含 key → antd 自动调用 `loadData`（即 `onLoadData`）按需加载
- React `setState((prev) => null)` 是合法的"无变化"信号，不会触发 rerender

## 备份恢复：党建文件夹"跑到文档管理下当子文件夹"根因排查

### 现象
用户第一次 production 恢复（老镜像）后，党建模块文件夹出现在文档管理树里当子文件夹；删容器换最新镜像重建再恢复，正常。

### 结论（已读源码确认）
**恢复脚本无罪。** `backups/restore_fileset_chain.py` 只做文件 tar 拷贝 + SHA256 校验，完全不懂文件夹层级；目录树父子关系只在 DB 的 `document_folder_public.parent_id`，由逻辑 dump 忠实还原。恢复脚本零干预目录树。

### 真正机制
- 党建隔离是**代码层**隔离，不是结构层：`document_folder_public` 表里党建根目录就是普通一行，`system_folder_service.py` 的 `exclude_system_folder_scope()`/`exclude_system_file_scope()` 在查询时把党建子树从普通文档库藏起来（`folder/views.py:108/125/181` 等）；`init_document_system_folders` 命令确保党建是 `parent=None` 顶层系统根。
- 老镜像代码缺/错这套隔离逻辑 → 党建渲染进文档管理；新镜像有 → 正常。两次恢复同一备份集（数据完全一致），差异只在镜像代码 → 典型**代码版本不匹配**特征。
- 入口 `docker/config/entrypoint.sh:23` 每次启动跑 `init_document_system_folders`（幂等），新镜像自动修复顶层绑定。

### 教训
- "同备份、老镜像错/新镜像对"= 代码版本问题信号，不是备份/恢复缺陷；无老镜像代码不能 100% 坐实，但可高置信排除恢复脚本。
- 备份脚本只忠实还原备份时刻的库；若那一刻数据本身有错位（如党建 parent 非 NULL），新代码靠 exclude 藏住它——数据层可能仍残留孤儿文件夹，需 SQL 核实现状（`SELECT ... WHERE name='党建工作'` 查 parent_id/重复行）。
- 党建系统目录重构迁移链：`0009_document_system_folder`→`0010_transfer_system_folder`→`0011_rename_party_building_documents`(code 从 industry_rules/party_building 改为 party_building_documents)→`0012_system_folder_unique_folder`。

## BorgBackup 一致性备份恢复方案文档

### 需求
用户已在 Linux 安装 borgbackup（离线 deb 包在 `e:\TDYW\borgbackup_deb\`），要求结合 `backups/` 现有 backup_set 方法的思路，在 borgbackup 文件夹写一个 borg + 数据库的一致性备份恢复 md 方案。

### 产物
新增 `borgbackup/borgbackup_一致性备份恢复方案.md`（15 节，约 500 行）。

### 核心设计（对齐现有 backup_set 哲学）
1. **一致性停写窗口复用**：freeze app（停 ingress→beat→worker→tdyw 容器，DB 保持运行靠 single-transaction）→ dump → borg create。Borg 不跨过冻结逻辑。
2. **绝对禁止 borg 直接备份运行中 `/var/lib/mysql`**（InnoDB 不一致），DB 必须用 mariadb-dump --single-transaction。
3. **不打包 tar 中间层**：borg 直接吃 documents/media volume 的宿主机 mountpoint（`docker volume inspect -f '{{.Mountpoint}}'`），享受文件级+块级去重；tar 头部元数据会破坏去重。
4. **密码只走 0600 cnf**：DB 凭据复用 `tdyw_backup.cnf`/`tdyw_restore.cnf`；borg passphrase 写 `/etc/tdyw-backup/borg.env`（0600），`source` 进环境变量，不进 argv。
5. **原子发布 + trap 失败保护**：失败 archive 立即 `borg delete`；与 backup_set 共享 `.backup.lock` 互斥。
6. **GFS 保留**：`borg prune --keep-within=2d --keep-daily=7 --keep-weekly=4 --keep-monthly=6`；prune 后需 `borg compact` 才回收空间。
7. **完整性校验分级**：每次备份后 `borg check --repository-only`（秒级）；每周 `borg check --verify-data`（检测位腐烂，tar 方案做不到）。
8. **异地 3-2-1**：直接向 SSH 远程 repo `borg create`（只传去重增量块）；passphrase + key 离线保存。

### 与现有方案关系
- 互补共存渐进迁移：阶段1并行（tar 全量 + borg 去重归档），阶段2 drill 通过后停 tar cron 只留 borg。不一次性删历史 tar 集。

### 关键技术点
- `borg extract` 会还原原始绝对 mountpoint 路径树，**不能在 `/` 下直接 extract**（中途失败污染原数据），需 extract 到临时根再 `rsync --delete` 替换。
- DB 逻辑恢复用 `borg extract --stdout <dump> | gunzip | mariadb`（流式，不落地大文件）。
- 加密模式推荐 `repokey-blake2`（密钥在 repo 内，异地恢复只需 repo+passphrase）。
- borg 1.2 与 1.4 仓库格式不兼容，异地端版本必须 ≥ 本地端。

### 方案经多轮讨论定稿重写（覆盖初版部分判断）

用户补充场景：内网 Linux 单机 Docker、RAID1 两块 300G 剩 166G、38 人 CRUD、DB+文件均 volume、有 U 盘 + 老 PC 可作异地。经 4 轮讨论后**重写** `borgbackup/borgbackup_一致性备份恢复方案.md`，初版以下判断**作废/修正**：

1. **mariabackup 日常砍掉**：38 人小库（几 GB），逻辑 dump 足够，物理备份是过度设计。仅 mariadump。
2. **tar 不作每日并行**：纯 borg 无重大缺陷，双跑两套是维护负担。tar 降为季度 `borg export-tar` 手动导出（异构冗余，nice-to-have）。
3. **加密分级**（非一刀切）：本地 repo `--encryption=none`（同机加密不防勒索、收益≈0）；U 盘 + 老 PC repo 必须 `repokey-blake2`（离开机房防外泄）。
4. **3-2-1 凑齐**：本地 RAID1 repo + U 盘（export-tar 导出，物理带离）+ 老 PC（每日 `borg create ssh:` 去重增量推送）。老 PC 位置决定等级：机房内=异机级，另一地点=真异地级。
5. **补 RAID1 scrub**（初版缺）：`echo check > /sys/block/md0/md/sync_action` 每月 cron，位腐烂第一道防线，比 borg verify-data 更基础。
6. **verify-data 降为月度**（初版是每周，对 38 人系统过频）。
7. **远程推送在 restore_application 之后**：先解冻恢复生产，再后台推老 PC，缩短停机窗口。

**之前初版"异地 SSH 是空中楼阁"判断作废**——有老 PC 后异地 SSH 落地了。之前"必须长期并行 tar"判断作废——纯 borg 可作终态。

**U 盘不建 borg repo**（随机写伤盘+慢），用 `borg export-tar` 导 tar，顺序写友好且任何机器可读。U 盘小则只导 dump（最关键最小）。
