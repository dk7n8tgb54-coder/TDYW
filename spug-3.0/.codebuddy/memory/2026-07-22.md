### 2. BigAutoField 升级（关键教训）
**改动**：
- `settings.py`：DEFAULT_AUTO_FIELD = BigAutoField
- 6 个 apps.py：regulation/document/radio_license/interference/device/contract_agreement
- `document/models.py:649`：显式 `id = models.AutoField` → `BigAutoField`（DocumentTransfer 模型，显式定义不受 default_auto_field 影响）
- 生成 18 个 alter id 迁移文件（AutoField→BigAutoField）

**踩坑与纠正**：
1. 改 default_auto_field 会触发**所有老表** alter id 迁移（不止新表），Django 会生成 AlterField id 迁移
2. migrate 失败：MariaDB 错误 1833 "Cannot change column 'id': used in a foreign key constraint"——被外键引用的主键列不能直接 ALTER
3. **错误做法**（我走的弯路）：写脚本给 18 个迁移文件批量加 RunSQL SET FOREIGN_KEY_CHECKS——过度复杂
4. **正确做法**：migrate 前 Django 连接 `SET FOREIGN_KEY_CHECKS=0`（会话级，migrate 全程同一连接），不需要动迁移文件
5. 用户删库重建 + FK_CHECKS=0 migrate：57 张业务表 id 全部升级 bigint ✓

**遗留**：
- 12 张 int 表是 Django auth/celery/contenttypes 内置 app（不归项目管，数据量极小，保持 int）
- git restore 还原老迁移文件时引入行尾符变化（LF↔CRLF），git diff 噪音大但不影响功能

### 教训总结
1. **改 default_auto_field 影响所有表**，不是只影响新表——Django 会为所有已有模型生成 alter id 迁移
2. **MariaDB alter 主键列撞外键**：解法是 migrate 前 SET FOREIGN_KEY_CHECKS=0（会话级），不要写脚本改迁移文件
3. **进生产前是改主键类型唯一无痛窗口**：空表 ALTER 秒级，进生产后改有锁表风险
4. **用户质疑"为什么要脚本/不用正常方式"时立即反思**：migrate with FK_CHECKS=0 是正常方式，写脚本批量改迁移文件是绕路
5. **grep 'AutoField' 会误匹配 BigAutoField**：精确匹配用 `grep 'models\.AutoField('`

  - `CharField(max_length=20, default=human_datetime)` → `DateTimeField(auto_now_add=True)`（created_at）
  - `CharField(max_length=20, null=True)` → `DateTimeField(null=True, blank=True)`（可空时间）

- **前端兼容性已验证通过**：后端 `DateTimeEncoder`（libs/utils.py:114）把 datetime 序列化为 `strftime('%Y-%m-%d %H:%M:%S')`，与原 human_datetime 格式完全一致，JSON 输出零变化，前端无需任何改动
