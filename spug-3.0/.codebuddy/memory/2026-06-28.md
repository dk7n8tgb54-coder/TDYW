## P1 修复：设备软删除后仍可见 + 编号无法复用

**问题**：删除设备（is_deleted=True 软删除）后，列表/详情/下拉/导出仍显示该设备；同编号也无法重新新增。

**根因**：device 模块删除逻辑已改为软删除（views.py delete 设 is_deleted=True），但 DeviceResume 用 TenantModelManager 不过滤 is_deleted，所有业务查询用 `objects.all()` 含已删除记录；且 DB 唯一约束 uniq_device_resume_tenant_sn 阻止复用已软删除编号。

**方案**（对齐 document 模块 SoftDeletedManager 既有模式）：
1. models.py：新增 `SoftDeleteTenantManager(TenantModelManager)`，get_queryset 自动 filter(is_deleted=False)；DeviceResume 改 `objects=SoftDeleteTenantManager()`（业务默认过滤）+ `all_objects=TenantModelManager()`（审计/证据全量）。
2. views.py 证据包视图：objects→all_objects（审计需查看已删除设备，保持证据链完整）。
3. views.py 新增逻辑重写为"恢复重建"：①未删除记录查重→报错；②仅有软删除记录→恢复并更新数据（保留原 ID，证据事件/审计日志不脱链）；③都无→新建。
   - 其余业务查询点（列表/详情/下拉/编辑/删除/事件关联/PDF导出/Excel导出）无需逐个改，由 objects 管理器自动过滤，防止未来回归。

**验证**：read_lints 0 错误；docker py_compile 3 文件 exit 0；Django shell 验证 objects SQL 含 `WHERE is_deleted=False`、all_objects 无此过滤。

**关键经验**：DB=MySQL 不支持部分唯一索引，故"复用软删除编号"不能靠改唯一约束，而用"恢复重建"（复用原 ID）既允许复用又保持证据链——这是软删除为证据闭环服务的正确语义。

### migration 字段定义一致性教训

手写 migration 时 CharField 的 `blank=True` 必须与 model 严格一致，否则 Django 会生成"Alter field" 假 migration：
- model 中 `CharField(default='', blank=True, ...)` → migration 必须也带 `blank=True`
- model 中 `CharField(default='', ...)`（无 blank） → migration 不能带 `blank=True`
- IntegerField 的 `blank=True` 对应 null=True 的字段，CharField 的 blank 是独立的表单验证标志

本次修正了 4 个字段：interference 的 report_channel/report_no/void_reason 和 radio_license 的 delete_reason（model 有 blank=True，migration 漏写）。

### P0-3 索引命中问题修复（v2 方案）

**问题**：初版组合索引字段顺序为 `[tenant_id, is_deleted, parent_id, -created_at, -id]`，EXPLAIN 显示优化器选了旧的外键单列索引 `[parent_id]`，导致 `Using filesort`。用户质疑"不是没命中吗？"后深入诊断。

**诊断过程**：
1. ANALYZE TABLE 后优化器仍选旧外键索引 → 不是统计信息问题
2. IGNORE INDEX 旧外键索引后组合索引命中、filesort 消失 → 组合索引设计正确，但被旧索引干扰
3. CASCADE 删除路径 `WHERE parent_id=?` 依赖旧外键索引 → 不能直接删除旧索引（组合索引前缀是 tenant_id，无法服务纯 parent_id 查询）

**根因**：组合索引前缀 `[tenant_id, is_deleted, ...]` 无法服务 CASCADE 删除的 `WHERE parent_id=?`，所以旧外键索引必须保留；但旧索引存在时优化器偏好它（key_len 短），产生 filesort。

**v2 方案**：调整组合索引字段顺序，把 `parent_id`/`folder_id` 放最前：
- 私有文件夹：`[parent_id, tenant_id, is_deleted, -created_at, -id]`
- 私有文件：`[folder_id, tenant_id, is_deleted, -created_at, -id]`
- 公共文件夹：`[parent_id, is_deleted, -created_at, -id]`
- 公共文件：`[folder_id, is_deleted, -created_at, -id]`

**v2 优势**：
1. 完整索引覆盖列表查询（过滤+排序），无 filesort
2. 左前缀 `[parent_id]`/`[folder_id]` 服务 CASCADE 删除，无全表扫描
3. 一个索引服务两种查询路径，无冗余

**验证结果（v2 落地后）**：
- 列表查询：4 表全部命中组合索引，**无 filesort**
- CASCADE 路径：4 表全部命中组合索引左前缀，`type=ref`，**无全表扫描**
- 优化器自由选择（无 FORCE/IGNORE），全部正确命中

**教训**：
1. **组合索引字段顺序必须考虑所有查询路径**：不能只看列表查询，还要看 ForeignKey CASCADE 删除路径。把外键字段放最前，左前缀可服务 CASCADE。
2. **用户质疑时要深入验证**：初版我说"数据量小优化器没选"，用户反问后才发现是字段顺序问题。应主动用 ANALYZE + IGNORE INDEX + FORCE INDEX 多维度验证，而非用"数据量小"搪塞。
3. **临时索引必须清理**：诊断时创建的 v2 临时索引（CREATE INDEX）第一次清理脚本没执行成功（输出为空），导致残留。后续要确认清理结果。
4. **migrate 回滚后重跑**：`migrate document 0006` 可回滚 0007，修改 0007 后重新 `migrate document` 即可重跑，无需删迁移文件。

1. **CharField→DateTimeField 迁移必须先扫描空字符串**：NULL 在 ALTER 时安全，但空字符串 `''` 会导致转换失败。迁移前用 `STR_TO_DATE` 统计 NULL/空串/合法/非法分布。
2. **RunPython 清洗要放在 AlterField 之前**：此时字段仍是 varchar，`filter(col='')` 能正确匹配。
3. **`migrate app1 app2` 语法错误**：第二个参数是迁移名不是 app 名，需分别 `migrate logs` + `migrate runlog`。
4. **容器内无 mysql 客户端**：`tdyw-test` 容器没装 mysql cli，需通过 Django ORM 查询表结构和数据。

## P2 修复：检查表模板管理分页导致超过 50 条不可见

**问题**：模板数量超过 50 时，模板管理表格只加载前 50 条，表格自身的客户端分页只能在这 50 条内翻页，后续模板完全不可见。

**根因**：后端 `TemplateView.get`（views.py:287）默认分页 `page_size=50`；前端 `store.js fetchTemplates` 不传 page/page_size，也不消费后端返回的 total/page/page_size 做服务端分页——拿到的是被截断的前 50 条，前端表格的客户端分页只能在这 50 条里翻。

**修复**（对齐 bug 报告建议"模板量可控，接口明确返回全量并移除分页"）：仅改后端 `TemplateView.get`，移除分页逻辑，返回全量模板（按 created_at 排序，与同文件 `ProjectListView` 不分页返回全量项目名的模式一致）。响应体从 `{templates, total, page, page_size}` 简化为 `{templates}`。

**前端无需改动**：`store.js:36` `this.templates = res.templates || []` 直接消费全量；`TemplateTable.js` 客户端分页在拿到全量后自然正确工作。

**验证**：
- read_lints：0 错误
- docker `python -m py_compile apps/checksheet/views.py`：OK
- 全局搜索确认仅 store.js 调用该接口，且不依赖 total/page/page_size 字段、不传 page 参数

**教训**：前端"假分页"（客户端分页）+ 后端"真分页"（服务端截断）混用时，若前端不把服务端分页参数串起来，就会出现"只能在前 N 条里翻页"的隐性 bug。要么前端实现完整服务端分页，要么后端返回全量交由前端客户端分页——二选一，不能各做一半。模板这种数量可控的场景，后者更简单可靠。
