## 资料库（document）三个 Bug 修复

### Bug1: "替换"失败后仍上传新文件
- **根因**: `FileUploadCoordinator.js` 的 `executeConflictResolution` 用 `Promise.all` 删除旧文件，catch 块调用 `message.error` 但 HTTP 拦截器已调用过，导致重复弹窗；且 `e.message` 为 undefined（reject 值是 string 不是 Error），显示"未知错误"
- **修复**: 逐个 delete 包装 try/catch 转为结果对象，reject 不再重复弹窗，resolve 但含 `{error:...}` 才补充提示，全部成功才入队上传
- **文件**: `FileUploadCoordinator.js`

### Bug2: "保留两者"上传报 MySQL 1062
- **根因**: `naming_utils.py` 的 `generate_unique_logical_name` 用 `name__startswith=f"{clean_original}_"` 查询，但精确名 `f"{clean_original}{ext}"`（如 `foo.txt`）不以 `foo_` 开头，永远查不到，导致返回已存在的 name -> 1062
- **修复1**: 增加独立的 `FileModel.objects.filter(name=exact_pattern).exists()` 检查
- **修复2**: `generate_file_names` 的 `display_name` 当逻辑名有序号时同步带序号，确保"保留两者"两个文件 display_name 可区分
- **修复3**: `FileUploadService.upload()` 添加 IntegrityError 重试（3 次）+ 物理文件清理
- **修复4**: `tasks/merge.py` 的 `_create_file_instance` 添加 IntegrityError 重试（3 次）
- **文件**: `naming_utils.py`, `file_upload_service.py`, `tasks/merge.py`

### Bug3: 重命名重复弹出 3 条提示
- **根因**: 三层各弹一次：HTTP 拦截器 -> `handleRename` catch -> `confirmRename` catch
- **修复**: `handleRename` 移除所有 `message.error`/`message.success`，仅做 HTTP 调用 + 刷新；`confirmRename` 作为通知唯一所有者，成功弹一次 success，失败不弹（拦截器已弹），不调用 `cancelRename`（保留编辑态）
- **文件**: `useFileOperations.js`, `Explorer/index.js`

## Bug #8 排查报告：页面自动跳回根目录、路径重复叠加

### 已确认根因（2 个）
1. **`enterFolder()` 无条件 push 不检查重复**（actions.js L22）
   - `this.store.path.push({ id: folderId, name: folderName })` 不检查 `folderId === currentFolderId`
   - 连续两次 `enterFolder(同一 folderId)` 会产生 `[{A}, {A}]` 重复路径
   - `selectFolder()` 替换路径、`enterFolder()` 追加路径，格式不一致
2. **`clearSystemFolder()` 清空所有导航状态**（actions.js L252-254）
   - 党建模式切回普通模式时调用 `clearSystemFolder()`，清空 path/currentFolderId/selectedFolderId
   - `navigationStore` 是单例，普通/党建共享，模式切换带入过期状态
   - `document/index.js` L77-81：非党建模式检测到残留 systemFolder 也会调用 clearSystemFolder

### 排除的猜测
- 请求失败/旧请求晚返回：`enterFolder` 是纯前端状态变更，不依赖 API 响应，不会自动回退
- 双击事件：`handleRowDoubleClick` 不调用 `enterFolder`，只有单击触发
- URL sync：`syncToUrl` 在每次导航后自动调用，URL 始终反映最新状态

### 诊断测试：16/16 pass（已删除临时文件）

## Bug #9 排查报告：移动后未迁移物理文件，删除原文件夹导致文件丢失

### 完整数据丢失调用链
1. 文件 F 在文件夹 A：DB `folder_id=A`, `file_path=storage/.../folder-A/F.ext`
2. `FileMoveView._move_file()` 更新 `folder=B` + `name`，`save(update_fields=['folder','name','updated_at'])`
3. **不更新** `file_path`/`thumbnail_path`/`physical_name`，**不移动物理文件**
4. 删除 A：`_delete_folder(A)` 中 `folder.files.all()` 查不到 F（F.folder_id 已是 B）
5. `PhysicalFolderCleaner.delete(A)` 对 `storage/.../folder-A/` 执行 `shutil.rmtree()`
6. F 的物理文件被删除，但 DB 记录仍在（folder=B），`file_path` 指向已不存在的路径
7. 下载/预览 F → **文件不存在，数据丢失**

### 诊断测试结果：26/26 pass（已删除临时文件）
- T1: 移动后 folder_id=B 但 file_path 仍指向 folder-A ✅
- T2: 删除 A 后物理文件被 rmtree 删除，DB 记录仍存在但 file_path 失效 ✅ **数据丢失已复现**
- T3: 路径生成使用 `folder-{id}` 格式 ✅
- T4: 文件夹移动只更新 parent，folder_id 不变，物理目录无需移动 ✅
- T5: `_move_file` 的 `update_fields` 不包含 `file_path`/`thumbnail_path`/`physical_name` ✅
- T6: `cleanup_parent_dirs_safe` 会删除收集到的父目录 ✅
- T7: `FileMoveView` 只在同空间内移动 ✅

### 哪些移动会丢文件
| 移动类型 | 物理目录变化 | 当前是否迁移物理文件 | 是否丢文件 |
|---|---|---|---|
| 文件跨 folderId 移动 | 是（folder-A -> folder-B） | **否** | **是** |
| 文件夹改 parent | 否（folder-{id} 不变） | 不需要 | 否 |
| 文件到根目录 | 是（folder-A -> 根目录） | **否** | **是** |
| 根目录文件到文件夹 | 是（根 -> folder-B） | **否** | **是** |
