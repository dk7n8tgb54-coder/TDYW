## 幂等命中file_path不同步导致StatusSynchronizer失败

### 问题
反复上传相同文件时，第1个成功，第2/3个失败。错误：`文件上传未成功（文件记录未创建）`

### 根因
1. 用户上传"测试2.mp4" -> MERGE_CHUNKS 端点 `check_idempotency` 按 `file_hash` 找到旧记录（已COMPLETED + file_path）
2. 返回 `{status: 'completed', file_path: '...'}` 给前端
3. 前端进入 `completed` 状态 -> `StatusSynchronizer` 同步 COMPLETED 到**新**传输记录
4. `TransferCompletionService.complete()` 检查新传输记录的 `file_path` -> 空 -> 拒绝

### 修复
`merge.py` L705: 幂等命中 `completed` 时，用旧记录的 `file_path` 把当前传输记录也设为 COMPLETED：
```python
TransferCompletionService.complete(current_transfer, file_path=result.get('file_path'), source='idempotent_file_hash')
```

### 教训
幂等检查返回旧记录状态时，必须同步更新新记录的关键字段（file_path），否则后续同步会失败。

## 同file_hash并发上传竞态条件修复

### 问题

### 根因（竞态）
1. File A 进入 MERGING 状态，`celery_task_id` 已设

## N7-LOCK 深度验证（内存锁非分布式）

### 验证结论：问题真实，但后果被高估

**事实确认（全部为真）**：
1. `lock.py:40` `_merge_locks = OrderedDict()` + `lock.py:58` `threading.Lock()` - 纯进程内存锁
2. `gunicorn.conf.py:49` `workers = get_cpu_limit()` + `:57` `preload_app = False` - 多 Worker 独立内存空间
3. `merge.py:718-742` `FileMergeChunksView.post()` 使用 `get_merge_lock()` + `acquire()`/`release()`
4. 每个 Worker 有独立 `_merge_locks` 字典，并发请求落在不同 Worker 上各自获取不同 MergeLock，互不阻塞

**但"文件损坏"后果不成立**，存在三层防御：
1. **视图层 DB 行锁**：`_lookup_by_transfer_id` 用 `select_for_update()`（同 transfer_id 场景跨进程安全）
2. **Celery 层 Redis 分布式锁**：`tasks/merge.py:867-872` `RedisLock.acquire()` 防止实际文件合并并发
3. **Celery 幂等检查**：第二个任务获取 Redis 锁后发现 COMPLETED 直接返回

**真实风险窗口**：同 `file_hash` 不同 `transfer_id` 并发命中不同 Worker -> `_lookup_by_file_hash` 无 `select_for_update` -> 两个请求都通过幂等检查 -> 两个 Celery 任务提交 -> Redis 锁串行化 -> 第二个任务发现已完成提前返回

**实际后果**：浪费 Celery 任务提交 + `.merge_status` 竞态写（同路径覆盖，无害），**不会文件损坏**

**修复建议**：将 `merge.py:718` 的 `get_merge_lock` 替换为已有 `RedisLock`（`celery_lock.py`），统一分布式锁，代价低

## 干扰模块附件功能（复用 evidence.AttachmentService + 新建阶段上传）

### 背景
用户要求给干扰记录加上附件功能，复用公共附件组件（evidence.AttachmentService），参考无线电台执照做法，但要求**新建阶段就能上传附件**（radio_license 仅在详情页管理附件）。

### 设计：临时 UUID 桥接
- 新建表单打开时前端生成临时 UUID（`temp-{timestamp}-{random}`）
- 上传附件时用临时 UUID 作为 `object_id`，后端跳过记录存在性校验
- 保存记录时前端传递 `attachment_temp_id`，后端创建记录后批量 `UPDATE object_id = record.id WHERE object_id = temp_id`

### 改动清单（3 文件，+217/-14 行）
| 文件 | 改动 |
|---|---|
| `apps/interference/views.py` | 新增 `AttachmentListView`（支持数字 ID + 临时 UUID）、`AttachmentDownloadView`、`AttachmentPreviewUrlView`、`AttachmentPreviewFileView`、`AttachmentDeleteView`；`InterferenceView.post()` 创建分支增加 `attachment_temp_id` 参数 + 附件关联逻辑 |
| `apps/interference/urls.py` | 新增 5 个附件 URL 模式，`(?P<pk>[\w-]+)/attachments/` 同时匹配数字 ID 和临时 UUID |
| `spug_web/src/pages/interference/Form.js` | 新增 `tempId` state + `AttachmentManager` 组件嵌入新建/编辑/查看三种模式；`handleSubmit` 传递 `attachment_temp_id`；查看模式增加"编辑"按钮 |

### 关键技术点
1. **临时 ID 模式**：`pk.isdigit()` 判断是否为数字 ID，非数字（临时 UUID）跳过记录存在性校验
2. **权限复用**：上传用 `interference.interference.add|edit`，删除用 `interference.interference.edit|del`，列表/下载/预览用 `interference.interference.view`（无需新增权限码）
3. **URL 模式**：`(?P<pk>[\w-]+)/attachments/` 放在最后，不与 `export/$`、`statistics/$` 等冲突（它们不以 `/attachments/` 结尾）
4. **附件关联**：`EvidenceAttachment.objects.filter(object_id=temp_id).update(object_id=str(record.id))`，在事务外执行（附件关联失败不应回滚记录创建）
