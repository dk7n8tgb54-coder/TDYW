## 升级工作台状态时间线与标准流程参考进度优化

**背景**：标准流程参考条用 `statusLogs.some(action)` 判断节点完成，导致历史出现过就永久点亮，回退时不跟随退回。回退只记录 action=rollback，不记录回退到哪个阶段。

**目标**：让参考进度能前进/后退，回退记录目标节点，有稳定排序，普通推进校验前置顺序，保留受控补录能力。

   - `is_override`（BooleanField，补录/跳步标记）
   - Meta ordering 从 `('-created_at', '-id')` 改为 `('-event_seq', '-id')`

1. **event_seq 而非 created_at 排序**：created_at 是字符串，比较不稳定；event_seq 是整数递增，同一 upgrade_id 内唯一

4. **删除日志重算主表 status**：找剩余日志中最后一条 complete/rollback 决定状态，无则回退到"处理中"
5. **后端与前端逻辑一致**：`_compute_current_index` 和 `computeFlowState` 用相同算法

## 完成语义改造 + 回退语义修正（第二轮）

**背景**：用户要求明确语义——状态时间线动作代表"该阶段已完成/该里程碑已达成"，不是"刚开始做"。蓝色右三角由系统自动推算，不需要用户手动记录。回退语义需要修正：rollback 到 target 表示 target 需要重做（变为 current），不是 target 仍为 completed。

### 文案统一为"完成"语义

| action | 旧 label | 新 label |
|---|---|---|
| start | 开始升级 | 升级启动 |
| backup | 备份 | 备份完成 |
| gray_release | 灰度发布 | 灰度发布完成 |
| test | 升级测试 | 升级测试完成 |
| test_pass | 测试通过 | 测试通过（不变） |
| full_release | 全量发布 | 全量发布完成 |
| observe | 上线观察期 | 观察完成 |
| complete | 完成 | 升级完成 |

**注意**：`UPGRADE_PHASES`（步骤阶段标签）保持不变（开始升级/备份/灰度发布/...），因为步骤代表"正在做的阶段"，状态时间线代表"已完成的里程碑"。

### 回退语义修正（核心变更）

**旧逻辑**：`rollback to X` → `currentIndex = X` → X 仍为 completed，X+1 为 current
**新逻辑**：`rollback to X` → `currentIndex = X - 1` → X 变为 current（需重做），X 之前仍为 completed

```js
// shared.js computeFlowState + status_log_service._compute_current_index
if (targetIdx <= currentIndex) {
  currentIndex = targetIdx - 1;  // target becomes current (needs redo)
}
```

**边界**：
- `targetIdx <= currentIndex` 才生效（不能回退到未完成的节点）
- rollback to start (idx=0) → currentIndex=-1，start 变为 current
- 回退后重做 target → 正常推进，currentIndex 恢复

### 改动文件

1. **models_status_log.py**：ACTION_CHOICES 12 个 label 改为完成语义 + 注释/docstring 更新
2. **constants.py**：新增 `FLOW_NODE_LABELS`（8 个主线节点完成语义 label）
3. **services/status_log_service.py**：
   - import 改 `FLOW_NODE_LABELS`（替代 `PHASE_LABEL_MAP`）
   - `_compute_current_index` 回退逻辑改 `target_idx - 1`
   - `to_view` / `add_log` / `get_rollback_targets` 用 `FLOW_NODE_LABELS`
4. **shared.js**：
   - `STANDARD_FLOW` 8 个 label 改为完成语义
   - `computeFlowState` 回退逻辑改 `targetIdx - 1`
5. **migrations/0009_status_log_action_labels.py**：Django 自动生成的 AlterField（choices 变更）

### 验收场景验证（11 个全通过）

| 场景 | 结果 |
|---|---|
| 无记录 → start=current, rest=pending | ✓ |
| start → start=completed, backup=current | ✓ |
| start+backup → start+backup=completed, gray=current | ✓ |

### 关键设计决策

1. **UPGRADE_PHASES 与 FLOW_NODE_LABELS 分离**：步骤阶段标签保持"正在做"语义（备份/灰度发布），状态时间线标签用"已完成"语义（备份完成/灰度发布完成）。两套 label 服务不同场景。
2. **choices 变更需要 migration**：Django 检测到 ACTION_CHOICES 的 choices 文本变更会生成 AlterField 迁移（虽然不改 DB schema，但 Django 仍记录）。
3. **回退后重做**：rollback 到 backup 后，重新记录 backup → currentIndex 从 0 恢复到 1，gray_release 从 rolled_back 变回 current。流程自然恢复。

## 修复：删除系统候选项后下拉不立即消失

**根因**：`SystemSelect` 是普通函数组件，直接读 `store.systems`（mobx observable），但**未用 `observer` 包裹**，store 变化时组件不会重渲染。`fetchSystems()` 更新了 store 但 SystemSelect 感知不到，只有重新触发渲染（输入/刷新）才反映新状态。

**修复（2 文件）**：

1. **`components/SystemSelect.js`**：
   - 用 `observer` 包裹（`export default observer(SystemSelect)`），响应 store.systems 变化
   - `handleRemove`：删除成功后**乐观更新** `store.removeSystem(name)` 立即从本地移除，UI 即时刷新；再异步 `fetchFilterOptions` 同步列表筛选数据源
   - `handleAdd`：新增成功后**乐观更新** `store.addSystem(...)` 立即追加；再异步 `fetchFilterOptions`
   - 移除当前选中项时：`onChange(undefined)` 清空 + `message.warning('当前选中的系统已被移除，请重新选择')`

2. **`store.js`** 新增两个乐观更新方法：
   - `removeSystem(name)`：`this.systems = this.systems.filter(s => s.name !== name)`
   - `addSystem(system)`：去重后追加

**关键教训**：
- mobx observable 必须用 `observer` 包裹组件才能响应变化，普通函数组件直接读 observable 不会重渲染
- 乐观更新 > 等待 fetch 返回：先改本地 state/store 让 UI 即时反馈，再异步同步后端
- `useMemo` 依赖 `systemNames`（由 systems 派生），systems 变化时 systemNames 重新计算，existed 自动更新

## 代码门禁修复第二轮（add_log 复杂度仍超标 17→7）

**问题**：第一轮抽出 `_validate_flow` 后，门禁报告 `add_log` 复杂度仍 17（限 15）。复杂度主要来自：to_status 的 if/else、try/except、重复两次的 `target_main_status and target_main_status != from_status` 判断、以及 create() 内多个 `or` 默认值。

**做法**：再抽两个辅助方法：

1. `_resolve_to_status(action, from_status) -> (to_status, target_main_status, needs_update)`：
   - 用 `needs_update = bool(target_main_status) and target_main_status != from_status` 合并原来的 if/else + 重复判断
   - `to_status = target_main_status if needs_update else from_status`

2. `_persist_log(*, upgrade_id, user, action, remark, target_action, is_override, from_status, to_status, target_main_status, needs_update, record) -> (log, error)`：
   - 承接原 try/except + transaction.atomic + create + 主表联动 + logger.info/error
   - 内部用 `if needs_update` 替代重复的 `target_main_status and ... != from_status`

add_log 末尾简化为：
```python
to_status, target_main_status, needs_update = StatusLogService._resolve_to_status(action, record.status)
return StatusLogService._persist_log(upgrade_id=..., ..., record=record)
```

**结果**：add_log 仅剩 5 个线性校验分支（~复杂度 7）；_persist_log ~6；_resolve_to_status ~2，均在限内。

**验证**：Docker py_compile PY_COMPILE_OK。

**教训（迭代降复杂度）**：
- 单次抽取可能不够——第一轮抽走顺序校验后，剩余的 to_status 计算 + 事务块仍贡献大量分支（`and` 链 + try/except + 重复条件）
- 降复杂度的有效粒度：把"计算结果 + 判断是否需要副作用"抽成一个返回多值元组的小函数（_resolve_to_status），把"执行副作用 + 异常处理"抽成一个带关键字参数的持久化函数（_persist_log），主函数变成纯编排
- 重复的布尔条件（`target_main_status and target_main_status != from_status` 出现两次）应计算一次存变量（needs_update）复用

### 设计决策

1. **轮询生命周期由组件控制**：pressureManager 实例长驻 coreStore，但 startPolling/stopPolling 由 DocumentIndex useEffect 控制——只在资料库页面活跃时轮询，离开停止。不在 constructor 启动（避免页面未打开就轮询）。
2. **降级不中断已运行任务**：startWaiting 只控制"启动新 waiting 任务"，已 calculating/uploading 的不受影响。满足"已上传分片不强制中断"。
3. **升级保守防抖**：连续 3 次 normal 才恢复高并发，避免频繁抖动。
4. **拉取失败不阻断**：refreshNow catch 后保持当前等级，下次轮询重试。
5. **压力是服务器全局**：merge_queue_depth 跨租户统计（物理机共享），但接口仍需 `document.document.view` 权限（避免匿名访问）。

### ⚠️ 修复：类名错误导致 Celery 全线崩溃（21:45）

**根因**：`pressure.py` 误用 `from ..models import TransferRecord`，但实际模型类名是 **`DocumentTransfer`**（`db_table='tdyw_document_transfer'`，类名≠表名）。`ImportError` 导致 `urls.py` 加载失败 → Celery worker 启动时加载 Django apps 崩溃 → supervisor 日志显示所有 celery 进程 "exited: ... (exit status 1; not expected)" 反复重启。

**为什么 py_compile 没发现**：`python -m py_compile` 只检查语法，不解析 import。import 类名错误是运行时 ImportError，必须用 `django.setup()` 后实际 import 才能暴露。

**修复**：`pressure.py` 两处 `TransferRecord` → `DocumentTransfer`（import 行 + `_get_merge_queue_depth` 调用行）。

**验证**：`DJANGO_SETTINGS_MODULE=spug.settings python -c "django.setup(); from apps.document.views.pressure import UploadPressureView; from apps.document import urls"` 输出 `IMPORT_OK`。

**教训**：
1. **py_compile ≠ import 检查**：新增 view 引用模型时，必须用 `django.setup()` 后实际 import 验证，不能只靠 py_compile
2. **类名≠表名**：`db_table` 可任意命名，类名才是 import 的依据。`tdyw_document_transfer` 对应的类是 `DocumentTransfer`，不能凭表名猜类名
3. **Celery 全线崩溃优先怀疑 import 链**：supervisor 显示多个 celery 进程同时 "exit status 1; not expected" 循环重启，通常是某个 app 的 urls/models/tasks import 失败，而不是单个 task 的 bug
4. **PowerShell 命令行双引号会被吃掉**：`python -c "import django"` 在 PowerShell→docker exec bash 链路中双引号被破坏成 `import` 单词。解决：验证脚本写到 .py 文件再执行，或 bash 内层用单引号
