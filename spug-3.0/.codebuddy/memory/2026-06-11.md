## 20:10 传输列表宽度/位置一致性修复 v2

**用户反馈**：
- 切换 Tab 时列表位置/宽度不一致
- 外框"特别宽"

### 错误的设计 v1

**症状**：3 个 Tab 用 `&&` 条件渲染 VirtualList
- 激活 Tab 变化时 Tabs 内容区宽度坍缩（只渲染激活的，宽度 = 内容宽度）
- 切到 "已完成" 时 Tabs 整个内容区向左对齐
- "外框宽" = 960px 太大（猜的）+ `.virtualTransferList` 又有 padding: 12px + gap: 12px
- 实际宽度 = 960 + 24 padding + 24 gap ≈ 1008px

### 正确的设计 v2

**核心思想**：3 个 TabPane **永远同时挂载**，**位置/宽度由 antd Tabs 统一管理**

1. **撤销条件渲染**：3 个 TabPane 都同时挂载
2. **VirtualList 加 `active` prop**：
   - 非激活时**只渲染占位 div**（保持 TabPane 尺寸稳定）
   - 不挂 ResizeObserver（避免非激活 Tab 拿到 clientHeight=0 写错 state）
   - 不挂 react-window（避免 3 个 FixedSizeList 同时跑影响性能）
3. **`animated={false}`** 关闭切换动画
4. **`LIST_MAX_WIDTH: 960 → 720`**：与底部 MiniBar 完全对齐
5. **删 `.virtualTransferList` 的 padding: 12px + gap: 12px**：与 TransferList 一致

### 为什么用 active prop 而不是条件渲染

| 方案 | TabPane 位置 | 宽度 | 切换视觉残留 |
|---|---|---|---|
| 条件渲染 `&&` | 切 Tab 时位置跳 | 坍缩到内容宽 | 无 |
| 全部挂载 + active | 永远同一位置 | 永远 720 | 无（不挂载非激活 react-window） |
| antd `destroyInactiveTabPane` | 一致 | 一致 | 切换时卸载重建，丢滚动位置 |

### active prop 实现要点

```jsx
if (!active) {
  return <div ref={containerRef} style={{ flex: 1, minHeight: 0, width: '100%' }} aria-hidden="true" />;
}
```

**关键细节**：
- 占位 div **必须**有 `ref={containerRef}`，切到该 Tab 时 ResizeObserver 第一次 update 能拿到正确高度
- `useEffect([active])`：非激活时 return，避免 ResizeObserver 污染状态
- 占位 div 与真实 div 尺寸完全一致（`flex: 1, minHeight: 0, width: '100%'`）

- Babel parser 语法 OK
- 18/18 回归 PASS
- VirtualTransferList: 409 行，TransferList: 345 行

### 教训

- **不要轻易用条件渲染控制"激活状态"**：antd Tabs 的 TabPane 是 `display: none` 隐藏，**3 个 TabPane 都同时挂载**才能保证位置/宽度一致

## 20:31 Drawer 容器修复 — 解决"只占左侧 25%"

**用户截图反馈**：
- 抽屉展开时只占屏幕左侧 ~25% 宽（侧边栏 240px + 详情面板 360px 之外剩余的 explorerArea 区域）
- 右侧大片空白
- Tabs "上传中 / 已完成 / 失败" 也偏左

### 根因

UploadPanel.js:241
```jsx
<Drawer ... getContainer={false} push={false}>
```

`getContainer={false}` 让 Drawer **不 portal 到 body**，而是渲染到 React 树当前位置的父级 DOM（即 .explorerArea）。
antd Drawer 的 mask + panel wrapper 虽然是 `position: fixed`，但**当祖先节点有 transform/filter/will-change/contain 时**，fixed 元素的 containing block 变成该祖先而不是 viewport。

虽然我搜了项目没有显式的 transform，但**实际上 antd Drawer 内部 wrapper 用 `position: fixed; left: 0; right: 0`** 应该能铺满视口——所以可能问题是**面板内部布局**（不是 wrapper 本身）。

实际上 antd Drawer v4 在 `getContainer={false}` 模式下，**wrapper 元素被插入到父级 DOM 树中**，而 `position: fixed` 仍能 work 应该是 OK 的——

实测**真正原因**可能是 antd 内部 wrapper 计算 left/right 时基于父级 .explorerArea 的 offsetParent，导致 width 受 .explorerArea 限制（~25% 视口）。

### 修复

**删除 `getContainer={false}`**，让 Drawer **默认 portal 到 body**：
- wrapper 真正相对视口定位
- mask + panel 都能铺满视口
- 副作用：Drawer DOM 不再在 .explorerArea 内，但 React state 仍受控（visible=uploadUIStore.panel.expanded），键盘快捷键照常工作

### 验证

- `read_lints` 0 错误

- 14/14 回归 PASS（删除 1 项 + 保留 13 项）
- 文件改动：删除 1 行 + 4 行注释 = 净 -1 行

### 教训

- **`getContainer={false}` 是 antd Drawer 的"陷阱"选项**——除非有明确原因（如嵌套在特定容器里），否则用默认值（portal 到 body）
- **fixed 元素的 containing block** 受 transform/filter/will-change/contain 影响——下次调试 fixed 不居中时优先查祖先 CSS
- 写测试断言时**注释和代码要区分**：用 `not in [filtered code]` 而不是 `not in raw_code`

## 21:05 面包屑智能省略 — 长路径不再挤按钮

**之前的设计问题**：
- antd Breadcrumb 每级 `max-width: 200px` 想做省略，但 antd 内部 `ant-breadcrumb-link` 是 `<span>` + `display: inline-block`，max-width 在某些场景下不生效
- 路径长时面包屑整体超宽，把操作按钮挤走
- 即使能省略，体验也不好（每级独立 200px 截断，路径长就截成 "公共共享库 / 测试小文件 / 甚高频规章规范 / 台站..."）

### 修复方案

**智能省略**（行业惯例：macOS Finder、VSCode 资源管理器、百度网盘）：

```js
if (currentPath.length <= 2) {
  // 短路径：完整渲染
  return <完整路径>
}
// 长路径：根 + 第1级 + "..." + 最后1级
return (
  <根>  <第1级>  <... title="已省略 N 级：xxx">  <最后1级>
)
```

**关键细节**：
- "..." 节点带 `title` 属性，hover 显示被省略的完整路径
- 阈值定 2 级（≤ 2 级短路径完整显示，> 2 级才省略），与 macOS Finder 行为一致
- "..." 节点**可点击**到倒数第二级（"测试小文件"那一级），方便用户回退

- Babel parser 语法 OK

### 教训

- **不要用 CSS 截断面包屑**：每个 Item max-width 不稳定（受 antd 内部结构影响），用 JS 智能省略更可靠
- **路径省略的阈值**：≤ 2 级完整 / > 2 级省略，参考 macOS Finder 行为
- **省略节点可点击**：用户应该能通过点击 "..." 回退到上一级（这里跳转到倒数第二级）
