## 索引与慢查询风险修复（P0-P3 全部完成）

### Django 4.2 `__year`/`__month` SQL 生成行为（验证确认）

| 查询写法 | 实际 SQL | 绕过索引？ |
|:---|:---|:---:|
| `__year=2025` | `duty_date BETWEEN '2025-01-01' AND '2025-12-31'` | 否 |
| `__month=6` | `EXTRACT(MONTH FROM duty_date) = 6` | **是** |
| `__gte/__lt` | `duty_date >= '2025-06-01' AND duty_date < '2025-07-01'` | 否 |

- Django 4.2 已将 `__year` 优化为 BETWEEN（不再生成 `YEAR()` 函数）
- `__month` 仍生成 `EXTRACT(MONTH FROM ...)` 函数调用，是绕过索引的真正原因
- `__gte/__lt` 半开区间同时消除 EXTRACT 和 BETWEEN 闭区间，最稳妥
- 含 OR 可见性条件的完整查询 EXPLAIN 确认仍走 `duty_log_date_idx` 索引（`type=range`）

## 监控告警体系审计（CRUD 指南 3.1 节）

### 审计范围
对照 CRUD 系统可靠性工程实践指南 3.1 节三层指标（数据库层/应用层/基础资源），全面排查项目监控告警现状。

### 现状总结：只有"被动查看"能力，完全没有"主动告警"能力

| 层级 | 已有 | 缺失 |
|:---|:---|:---|
| 数据库层 | `DatabasePoolStatusView`(连接数查询,无告警) | CPU/慢查询/缓冲池命中率/undo log |
| 应用层 | Docker healthcheck(仅 SELECT 1) | 5xx 错误率/响应时间/异常突增/Celery 队列堆积/任务失败率 |
| 基础资源 | `DiskUsageView`(手动查询,无告警) | CPU/内存/磁盘 IO(机械盘关键!) |
| 告警机制 | **完全没有**(无邮件/webhook/钉钉) | 全部缺失 |

### 关键发现
1. **Celery 无 task_failure 信号处理**：17 个 @shared_task 失败后只记 Celery 内部日志，不触发应用层告警
2. **异常中间件只捕获不告警**：`HandleExceptionMiddleware` 捕获未处理异常后只写日志，不通知任何人
3. **健康检查太浅**：不检查 Redis(Celery broker+缓存全依赖)、不检查存储目录、不检查 Celery worker
4. **无 MySQL slow_query_log**：`docker/config/mysqlnew.cnf` 未配置慢查询日志
5. **无 trace_id 贯穿**：`AuditLogMiddleware` 有 request_id 但 `HandleExceptionMiddleware` 不复用
6. **磁盘监控不覆盖 chunks 目录**：上传分片可能撑爆磁盘
7. **Gunicorn 无响应时间统计**：access log 有 `%(D)s` 字段但无人解析

### 建议路线（P0→P3）
- **P0(2天)**: `libs/alert.py` 告警通道 + Celery task_failure 信号 + 异常中间件告警 + 磁盘空间 Beat 任务
- **P1(2天)**: 增强健康检查(Redis+存储) + MySQL slow_query_log + DB 指标采集 Beat
- **P2(1.5天)**: 请求指标中间件(5xx率/响应时间) + Celery 队列堆积监控
- **P3(2.5天)**: ERROR 日志突增检测 + trace_id 贯穿 + 指标聚合端点(Prometheus 准备)
