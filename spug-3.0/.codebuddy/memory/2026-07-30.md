## 索引与慢查询风险修复（P0-P3 全部完成）

### Django 4.2 `__year`/`__month` SQL 生成行为（验证确认）

| 查询写法 | 实际 SQL | 绕过索引？ |
|:---|:---|:---:|
| `__year=2025` | `duty_date BETWEEN '2025-01-01' AND '2025-12-31'` | 否 |
| `__month=6` | `EXTRACT(MONTH FROM duty_date) = 6` | **是** |
| `__gte/__lt` | `duty_date >= '2025-06-01' AND duty_date < '2025-07-01'` | 否 |

- Django 4.2 已将 `__year` 优化为 BETWEEN（不再生成 `YEAR()` 函数）
- `__month` 仍生成 `EXTRACT(MONTH FROM ...)` 函数调用，是绕过索引的真正原因
- `__gte/__lt` 半开区间同时消除 EXTRACT 和 BETWEEN 闭区间，最稳妥
- 含 OR 可见性条件的完整查询 EXPLAIN 确认仍走 `duty_log_date_idx` 索引（`type=range`）

## 监控告警体系审计（CRUD 指南 3.1 节）

### 审计范围
对照 CRUD 系统可靠性工程实践指南 3.1 节三层指标（数据库层/应用层/基础资源），全面排查项目监控告警现状。

### 现状总结：只有"被动查看"能力，完全没有"主动告警"能力

| 层级 | 已有 | 缺失 |
|:---|:---|:---|
| 数据库层 | `DatabasePoolStatusView`(连接数查询,无告警) | CPU/慢查询/缓冲池命中率/undo log |
| 应用层 | Docker healthcheck(仅 SELECT 1) | 5xx 错误率/响应时间/异常突增/Celery 队列堆积/任务失败率 |
| 基础资源 | `DiskUsageView`(手动查询,无告警) | CPU/内存/磁盘 IO(机械盘关键!) |
| 告警机制 | **完全没有**(无邮件/webhook/钉钉) | 全部缺失 |

### 关键发现
1. **Celery 无 task_failure 信号处理**：17 个 @shared_task 失败后只记 Celery 内部日志，不触发应用层告警
2. **异常中间件只捕获不告警**：`HandleExceptionMiddleware` 捕获未处理异常后只写日志，不通知任何人
3. **健康检查太浅**：不检查 Redis(Celery broker+缓存全依赖)、不检查存储目录、不检查 Celery worker
4. **无 MySQL slow_query_log**：`docker/config/mysqlnew.cnf` 未配置慢查询日志
5. **无 trace_id 贯穿**：`AuditLogMiddleware` 有 request_id 但 `HandleExceptionMiddleware` 不复用
6. **磁盘监控不覆盖 chunks 目录**：上传分片可能撑爆磁盘

## binlog 纳入 borg 备份

### 背景
用户发现每日凌晨 2:00 borg 全量备份只能恢复到备份时刻，无法恢复到"上一分钟"。讨论后确认：
- binlog 记录所有 DB 变更，但只存在 Docker volume 中，未纳入 borg 备份
- binlog 7 天后自动过期
- binlog 纳入备份可实现 PITR（按时间点恢复）

### 讨论过程
1. 最初提出"每 5 分钟 borg create 小 archive"方案 -> 用户质疑 archive 太多（一天 288 个）
2. 改为"每 5 分钟 cp 到 staging 目录" -> 用户觉得还是麻烦
3. 最终方案：**只在每日 borg 备份时顺带复制 binlog 文件**，不增加额外 cron
4. 用户问"binlog 存了所有变更，还需要备份数据库吗" -> 解释 binlog 是增量不是全量，需要全量备份做起点
5. 用户问"什么情况下需要恢复" -> 主要场景：人为误操作（DROP TABLE/DELETE 没 WHERE），不是系统崩溃

### 最终方案
**只改 `borg_backup_set_create.sh`，不增加 cron、不增加 staging 目录**

流程：
```
freeze_application
backup_database_logical（mariadb-dump）
archive_binlog:
  1. SHOW MASTER STATUS -> 记录 binlog_file + binlog_pos
  2. FLUSH BINARY LOGS -> 轮转当前 binlog（变为已完成）
  3. cp 已完成 binlog 文件到临时目录
build_manifest（含 binlog 位点）
borg create（dump + documents + media + binlog + manifest）
```

### 修改文件
1. `borgbackup/borg_backup_set_create.sh`：
   - 新增 `MYSQL_DATA_VOLUME` 变量（默认 `docker_tdyw-mysql-data`）
   - 新增 `BINLOG_DIR/BINLOG_FILE/BINLOG_POS` 状态变量
   - 新增 `archive_binlog()` 函数（~50 行）
   - `build_manifest()` 加入 `binlog_file/binlog_pos/binlog_files_archived` 字段
   - `borg_create_local()` 和 `borg_push_remote()` 加入 `${BINLOG_DIR}` 参数
   - `main()` 流程在 `backup_database_logical` 后调用 `archive_binlog`
   - 头注释、环境变量说明、`print_plan` 更新

2. `borgbackup/borgbackup_一致性备份恢复方案.md`：
   - 一致性原理流程加入 binlog 归档
   - 备份流程加入 archive_binlog 步骤
   - borg create 代码片段更新（local + remote）
   - 新增 5.6 节：PITR 手动恢复操作步骤

### 关键设计决策
- **不用 `--master-data=2`**：避免 RELOAD/REPLICATION CLIENT 权限问题，改为单独 SHOW MASTER STATUS 记录到 manifest
- **FLUSH BINARY LOGS 在 dump 之后**：dump 完成后轮转，确保 binlog 文件包含 dump 期间的变更
- **不自动重放**：恢复脚本不改，PITR 手动操作（低频场景不值得自动化）
- **RPO**：Docker volume 完好 = 实时（直接从 volume 读 binlog）；volume 损坏 = 上次备份点

### 技术注意
- `mariadb-binlog` 需加 `--no-defaults`（否则报 `unknown variable 'default-character-set=utf8mb4'`）
- 文件中的 Unicode 箭头 `->`（U+2192）不是 ASCII `->`，编辑时需注意
- `${BINLOG_DIR:+...}` 语法：变量为空时不展开，避免 borg create 报空路径

## 数据质量巡检命令

### 背景
用户问"代码 bug 污染数据什么时候发现"，讨论后确认防护手段是数据库约束 + 定期巡检，不是靠备份。用户要求实现。

### 实现
新增 `apps/home/management/commands/data_quality_check.py`（~300 行）

**6 项检查（全部用 raw SQL，不依赖 ORM 管理器）**：
1. `soft_delete_orphans` - 软删除孤儿：子记录指向已软删除父记录
   - DocumentFilePrivate -> DocumentFolderPrivate
   - DocumentFilePublic -> DocumentFolderPublic
   - UpgradeRecordStep -> UpgradeRecord（IntegerField 非 FK）
2. `file_db_consistency` - DB 有记录但磁盘文件不存在（采样 500 条）
3. `unique_key_consistency` - DocumentFolder 的 unique_key 与 is_deleted 不匹配
   - 注意：DocumentFile 没有此字段，只检查 Folder
4. `deleted_suffix` - UpgradeRecord 软删除后 upgrade_no 缺 `__deleted_` 后缀
5. `pending_clean_files` - is_pending_clean=True（物理删除失败卡住）
6. `tenant_isolation` - DocumentFilePrivate 与 Folder 的 tenant_id 不一致

**用法**：
```bash
python manage.py data_quality_check           # 全量巡检
python manage.py data_quality_check --json    # JSON 输出
python manage.py data_quality_check --check pending_clean_files  # 单项
python manage.py data_quality_check --no-alert  # 不发告警
python manage.py data_quality_check --file-sample 100  # 限制采样
```

**关键技术决策**：
- **用 raw SQL 不用 ORM**：`DocumentFilePrivate.all_objects.values_list('tenant_id')` 报 `Cannot resolve keyword 'tenant_id'`（原因不明，可能是管理器继承问题），改用 raw SQL 彻底避免
- **表名差异**：`UpgradeRecord` 的表名是 `tdyw_upgrade_records`（不是 `upgrade_upgrade_record`），`UpgradeRecordStep` 是 `tdyw_upgrade_record_steps`
- **公共空间无 tenant_id**：`DocumentFilePublic` / `DocumentFolderPublic` 没有 `tenant_id` 字段（公共空间无租户隔离），SQL 需条件包含/排除
- **`--check` 参数匹配**：方法名有 `check_` 前缀，需 `.replace('check_', '', 1)` strip 后比较
- 告警走 `libs/alert.send_alert()`，level='warning'
- 建议每周运行一次（Celery Beat 或 cron）

### 后续完善
- 文件一致性检查从资料库扩展到全模块（4 张表）：
  - `tdyw_document_file_private`（file_path 绝对路径）
  - `tdyw_document_file_public`（file_path 绝对路径）
  - `tdyw_evidence_attachments`（file_path 相对 MEDIA_ROOT，覆盖 evidence/upgrade/fault/device/signature）
  - `tdyw_regulation_attachment`（file_path 相对 BASE_DIR/storage/documents/）
- 各表 name 列名不同：document 用 `name`，evidence 用 `file_name`，regulation 用 `original_name`
- `Regulation` 主表无 `is_deleted`（用 `status='retired'`），FK CASCADE 已在 DB 层处理，不需要软删除孤儿检查
- 采样从 86 增到 90 条（开发环境），全量通过

### 关键实现细节

- **竞态修复**：store 维护 `_formRequestId`/`_signRequestId` 计数器，每次 showForm/showSign 递增，异步回调比对序号丢弃过期响应；Form 用 `_editId`/`_editVersion` 实例变量固定提交目标，不从 store.formRecord 实时读取
- **幂等修复**：`sign_draft` 在 `record.status != STATUS_DRAFT` 分支中，先检查 `request_id` 是否匹配已有 `SignatureUsage`（字段 `signer_user_id` 不是 `actor_id`），匹配则返回已签记录
- **约束修复**：CharField 用 `Q(field='') | Q(field__isnull=True)` 兼容空串和 NULL；migration 0011 含 RunPython 清理存量 DRAFT 记录的 CharField 残留
- **响应体修复**：列表去掉 `duty_record` 字段，保留 `duty_record_summary`；编辑通过 showForm 调详情接口获取全文
