### 关键技术教训
1. **Docker 容器不热加载 .py 文件**：修改后端代码后必须重启容器（tdyw-test）才能看到变化
2. **Django 4.2 request.FILES 只为 POST 解析**：PUT/PATCH 的 multipart 需手动 `request.parse_file_upload(META, BytesIO(request.body))`
3. **不能先访问 request.FILES 再手动解析**：首次访问 FILES 触发 _load_post_and_files 锁定 upload_handlers，之后 parse_file_upload 抛 AttributeError。应检查 `getattr(request, '_files', None)` 避免触发
4. **Django 4.2 Client.put 默认 content_type=application/octet-stream**（不是 MULTIPART_CONTENT！），且传 dict+MULTIPART_CONTENT 时编码不完整（文件内容丢失）。测试中需手动 `encode_multipart(BOUNDARY, data)` 构造 bytes body

## 批量去除 Python 源文件 UTF-8 BOM

lint 报告 21 个 `.py` 文件首行 `invalid non-printable character U+FEFF`（UTF-8 BOM）。涉及 `apps/document` 和 `apps/regulation` 两个 app。

PowerShell 一行命令扫描并去除 BOM（保留其余字节不变）：
```powershell
Get-ChildItem -Path 'e:\TDYW\spug-3.0\spug_api' -Recurse -Filter *.py | ForEach-Object {
    $b=[System.IO.File]::ReadAllBytes($_.FullName)
    if($b.Length -ge 3 -and $b[0]-eq0xEF -and $b[1]-eq0xBB -and $b[2]-eq0xBF){
        [System.IO.File]::WriteAllBytes($_.FullName,$b[3..($b.Length-1)])
        Write-Output $_.FullName
    }
}
```

被截断未列出的第 21 个文件是 `apps/document/management/commands/init_document_system_folders.py`。

验证流程：
1. 二次扫描确认 `NO_BOM_REMAINING`
2. `python -m compileall -q apps/document apps/regulation` 全部通过
3. `read_lints` 抽样 models.py / urls.py 无错误

教训：编辑器/工具保存 .py 时若默认带 BOM，会触发 Python 语法错误。项目应统一 UTF-8 无 BOM 编码。

## regulation/views.py put 方法复杂度治理

`RegulationDetailView.put`（原 444 行）圈复杂度 20（限制 15）。四块字段处理（普通/分类/日期/状态）嵌套大量分支。

重构手法：按字段类型抽 4 个 applier 方法，统一签名 `(self, regulation, form) -> (error, changed_partial)`：
- `_apply_plain_fields`：title/rule_no/issuing_authority/biz_type（rule_no strip+非空）

逻辑等价性：处理顺序（plain→category→date→status）、error 即时返回、changed 累积、`changed or {'summary':'无变更'}` 全部保留。put 复杂度降至约 7，各 applier 均 ≤7。

## 党建文档逻辑隔离加固 — 搜索隔离补充修复

**背景**：党建文档逻辑隔离加固主体已完成（system_scope_validators 统一校验 + document_auth fail-closed + preview_token 绑定 system_folder + transfer 作用域闭环 + migration 0012 唯一约束 + 33 个 IDOR 测试）。但搜索接口 `FolderSearchView` 仍有 3 个跨作用域泄漏漏洞。

**漏洞 1 — 党建搜索递归排除自身后代**：
`_get_descendant_folder_ids` 在 BFS 递归子目录时无条件调用 `exclude_system_folder_scope`，党建模式下会把党建根目录的所有后代排除掉，导致党建搜索搜不到任何子目录/文件。
修复：增加 `system_folder` 参数，党建模式（`is_party_scope`）不调用 `exclude_system_folder_scope`，普通模式继续排除。

**漏洞 2 — 党建搜索混入普通根层文件**：
`files_query` 无条件加 `Q(folder_id=None) | Q(folder_id__in=...)`，党建搜索时会把公共根层文件（folder_id=None 的普通文件）混入结果。
修复：只有"原始 folder_id 为空的全库搜索 + 非党建模式"才加 `Q(folder_id=None)`；党建模式和指定目录搜索只用 `folder_id__in=folder_ids_to_search`。
关键：保存 `original_folder_id`（在 `_validate_search_scope` 规范化前），因为党建模式空 folder_id 会被规范化为党建根目录 ID。

**漏洞 3 — 前端未显式传 system_folder**：
`SearchBox.js` 只传 is_public/folderId，依赖 Axios 自动注入 system_folder，不是唯一作用域来源。
修复：SearchBox 增加 `systemFolderCode` prop 显式传给后端；DocumentIndex 党建模式传 `PARTY_BUILDING_DOCUMENTS_CODE`，普通模式传 null。

**测试**：新增 `SearchIsolationTest` 类 10 个请求级测试到 `test_document_scope_isolation.py`：
- 普通搜索不返回党建根/子目录/文件
- 普通搜索返回普通文件 + 根层文件
- 党建搜索不返回普通根层/子目录/文件
- 党建搜索返回多级子目录深层文件（pb_subsub/pb_deep_file）
- 党建搜索不混入根层文件
- 指定普通子目录搜索不混入根层文件
- 普通上下文传党建 folder_id 被拒绝
- 非法 system_folder 被拒绝
- 私有模式携带 system_folder 被拒绝

## 权限缓存失效缺失排查（只读，未改代码）

**现象**：普通账号（林杰等）登录后除公告管理/部门值班日志外全部"权限拒绝"，主菜单只剩工作台/数据分析/部门值班日志；管理员登录后等待片刻其他账号自动恢复。

**根因定位**：`page_perms` 权限缓存（`perms_{user.id}`，Redis，TTL 默认 300s）的失效机制存在缺口。
- `apps/account/models.py:44-56` `page_perms` 属性：`if data:` 非空集合直接短路返回，**不再重算**；`set_perms_cache()` 无参写空集合触发重算。
- **唯一未触发失效的权限变更路径 = 迁移 `document/migrations/0011_rename_party_building_documents.py` 的 `_rename_role_permissions`（123-140 行）**：它遍历并改写**所有角色**的 `role.page_perms`（把 `document.industry_rule` 重命名为 `document.party_building_document`），但**没有调用 `role.clear_perms_cache()`**。全库 grep migrations 仅此一处改 `role.page_perms`。
- 所有 API 变更路径（用户增改 `views.py:157/185`、角色 post `374`、角色 patch `461-463`）都调了 `set_perms_cache`/`clear_perms_cache`。
- `clear_perms_cache` 失效逻辑是**后加的**：`git log -S clear_perms_cache` 显示首次出现于 `e50a6fbc`（"增加了审计系统..."），后在 `0b12a0e1`（"解决用户角色委派权限问题"）完善。即在此之前所有 API 角色/权限变更都不失效。

**机制解释**：`if data:` 短路使任何非空（即便残缺）缓存值被视为权威，直到 300s TTL 过期才重算 → 解释了"瞬态 + 管理员登录（等待超过 TTL）后自愈"。迁移 0011 仅重命名 document 键，理论上只影响资料库模块；多位普通账号"多模块同时被拒"说明各自缓存是更早一次未失效的残缺/陈旧集合（部署/角色分配发生在失效逻辑就位前），被短路长期滞留。

**未做**：未修复。修复方向候选——迁移 0011 补 `role.clear_perms_cache()`；`page_perms` 改为显式 `cache.delete`（真失效）或缓存里带角色版本/校验和，而非依赖"空集合→重算"隐式约定。

## 签名文件丢失排查（重要教训）

现象：修改签名代码并重启容器后，已配置签名的物理文件全部消失，DB 记录完好（is_deleted=False，审计 success=True），签名预览/签署因文件不存在而失效。

根因（与代码无关）：`dev/docker-compose.yml` 新增了 `tdyw-media:/data/spug/spug_api/media` named volume，遮盖了 bind mount `/mnt/e/TDYW/spug-3.0/spug_api:/data/spug/spug_api` 的 media 子目录。签名文件写进 named volume，存在 `dev_tdyw-media` 和 `docker_tdyw-media` 两套独立 volume（曾用不同 compose 项目名 dev/docker 启动），切换/重建时数据丢失。同样问题影响 `tdyw-documents`/`tdyw-document-chunks`/`tdyw-logs`。

修复方向：移除这 4 个 named volume 挂载，让 media/storage/logs 走 bind mount 到宿主机（持久、可见、可备份）。签名文件已永久丢失，需重新上传。注意：删挂载前若 tdyw-documents 里有资料库文件需先迁移，否则会重演丢失。
