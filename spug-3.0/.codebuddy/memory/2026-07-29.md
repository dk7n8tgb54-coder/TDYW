## 数据库性能审计 + 7 项修复

### 审计背景
用户问"单表 100 万是否必须分区"。先澄清：100 万分区是误导，InnoDB B+树 1000 万行无压力。然后系统性扫描代码库 5 维度：索引设计/慢查询/深度分页/无缓存统计/锁冲突。

### 7 项修复（9 文件 +110/-38 行，2 个 migration）

**#1 `__date` 绕过索引（严重）**
- Django `__date` -> `DATE(col) = ...`，B-tree 索引失效，强制全表扫描
- 修复：`home/views.py`、`runlog/statistics_service.py`、`runlog/views.py`、`runlog/exporters.py`
- 改为 `__gte`/`__lt` + datetime 范围
- `values('created_at__date')` GROUP BY 保留（queryset 已由 __gte/__lt 过滤，DATE() 作用于小结果集）

**#2 `__startswith` 在 DateTimeField 上绕过索引（严重）**
- `col LIKE '2026-07-29%'` 对 DATETIME 列需隐式类型转换，大概率不走索引
- 修复：`home/views.py`（5 处）、`duty/import_services.py`、`upgrade/views_old.py`
- 改为 `__gte`/`__lt` + datetime 范围
- CharField 上的 `__startswith` 不受影响（如 upgrade_no、file_name、name），是正常的前缀匹配

**#3 FaultRecord/FaultPart 零索引（高）**
- 两个模型 Meta.indexes 完全为空，默认列表查询每次 filesort
- 修复：`fault/models.py` 加 `[tenant_id, '-fault_date', '-id']` 和 `[tenant_id, '-date', '-id']`
- migration: `fault/0005`

**#4 RunLog 缺默认分页索引（中）**
- 有 `[tenant_id, status]` 和 `[tenant_id, severity]` 但缺 `[tenant_id, -created_at, -id]`
- 修复：`runlog/models.py` 加一行 index
- migration: `runlog/0013`

**#5 audit_logs `__icontains` 限制搜索范围（中）**
- `LIKE '%keyword%'` 无法走索引，三重 OR 更慢
- 修复：`logs/views.py` 无时间范围时默认限制最近 90 天
- 查询和导出两个视图都加了

**#6 Dashboard 零缓存统计（中）**
- `home/views.py:get_statistic` 每次打开首页 ~15 个查询，无缓存
- 修复：加 Redis 缓存（60s TTL，按租户分键 `dashboard:{tenant_id}`）

**#7 RunLogUpdate 冗余索引（低）**
- `[runlog_id]` 单列索引与 `[tenant_id, runlog_id]` 重复（TenantModelManager 总带 tenant_id）
- 修复：`runlog/models.py` 移除 `[runlog_id]`
- migration: `runlog/0013`（同 #4）

### 核心教训
- **分区的决策基于数据生命周期和查询模式，不是行数阈值**
- **`__date`/`__startswith` 在 DateTimeField 上绕过索引**是 Django 最常见的性能陷阱
