## 索引与慢查询风险排查（依据 CRUD 系统可靠性指南 2.1 节）

### 排查范围
- 全项目 13 个 app 的 models.py Meta.indexes + views.py/services.py 查询模式
- 重点排查：`__icontains` 在 DateTimeField/TextField 上、`__year/__month` 绕过索引、`.extra(DATE())` 函数绕过索引、复合索引最左前缀违反、无界查询

### EXPLAIN 验证结果（14 个测试）

| 编号 | 级别 | 位置 | EXPLAIN 结论 |
|:---:|:---:|:---|:---:|
| R1 | 高 | `fault/exporters.py:46` `fault_date__icontains` 在 DateTimeField | PARTIAL（索引仅 tenant_id，CAST+LIKE 做 Using where） |
| R2 | **严重** | `department_duty_log/services.py:302` `duty_date__year+__month` | **CONFIRMED**（type=ALL, key=NULL） |
| R2-对照 | - | `__gte/__lt` 正确写法 | **CONFIRMED**（仍全表扫描！复合索引最左前缀违反） |
| R3 | 高 | `upgrade/statistics_service.py:82` `.extra(DATE(upgrade_time))` | PARTIAL（Using temporary + filesort） |
| R4a-d | 中 | runlog/interference/device/logs `__icontains` 无索引 CharField | PARTIAL（索引仅 tenant_id） |
| R5 | 中 | `fault/views.py:20` 分页前无界 DISTINCT | PARTIAL |
| R6/R10 | 中 | runlog/device 证据包无界审计日志查询 | PARTIAL |
| R9 | **严重** | `department_duty_log/services.py:335` TextField `__icontains` | **CONFIRMED**（type=ALL, key=NULL） |
| R11 | **严重** | `DepartmentDutyLog` 复合索引 `(status, deleted_at, duty_date)` 最左前缀违反 | **CONFIRMED** |

### 关键发现
1. **DepartmentDutyLog 索引设计严重缺陷**：复合索引 `(status, deleted_at, duty_date)` 最左列是 status，但大多数查询直接按 duty_date 过滤，导致索引完全不可用。即使改用 `__gte/__lt` 也是全表扫描。
2. **R1 icontains vs range 对比**：`icontains` → `type=ref + Using where`，`__gte/__lt` → `type=range`（更高效）
3. **R3 extra(DATE()) 产生 Using temporary + Using filesort**：GROUP BY DATE(col) 需要临时表+排序
4. **PARTIAL 的原因**：大多数查询有 `tenant_id` 过滤，索引首位是 tenant_id 所以走了索引，但目标列的过滤条件仍做 Using where 逐行扫描

### 修复优先级
- P0: R2+R11 DepartmentDutyLog 新增 duty_date 独立索引 + 改 `__year/__month` 为 `__gte/__lt`
- P1: R1 fault/exporters.py 改 icontains 为日期范围；R3 statistics_service.py 改 extra(DATE()) 为按日期循环
- P2: R6/R10 证据包增加日期范围；R5 系统名称下拉加 Redis 缓存
- P3: R4a-d 高频搜索字段评估全文索引；R7/R9 增加结果行数上限
