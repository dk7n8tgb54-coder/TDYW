## 评审《平台运行健康监控方案》（未实施，仅评审）

结论：方案 B（平台内分钟级聚合 + 健康视图）方向成立，但有 2 个 P0 前提性错误 + 4 个 P1 实现缺陷，需改后再实施。

### 实测确认的关键事实（长期有效）

1. **Celery Beat 用的是 DatabaseScheduler，不是 settings 的 CELERY_BEAT_SCHEDULE**
   - `spug_api/tools/start-celery-beat.sh`：`celery -A spug beat -l info --scheduler django_celery_beat.schedulers:DatabaseScheduler`
   - 因此 `settings.CELERY_BEAT_SCHEDULE` / 各模块 `*_BEAT_SCHEDULE` **不会自动生效**，必须写 `PeriodicTask` 表
   - 实测 dev 库：PeriodicTask 21 条 / IntervalSchedule 3 / CrontabSchedule 14，均为**人工维护**（spug_api 全仓 grep `PeriodicTask` 零命中，无任何 get_or_create 初始化代码）
   - 当前 last_run_at 为 None 的 4 条（疑似从未执行）：`logs-verify-audit-hash-chain`、`run-data-quality-check`、`cleanup-old-alerts`（每天 03:00）、`coop-task-cleanup-expired-attachments`

2. **中间件顺序导致 4xx 漏计**：`MIDDLEWARE` 中 AuthenticationMiddleware(2) / OriginCheckMiddleware(3) 的 `process_request` 直接返回 response 时，其后中间件（HandleExceptionMiddleware 在 6）的 `process_response` **不会执行** → 401/403 全部漏计。要计全量必须把新计数中间件放 MIDDLEWARE **首位**（响应阶段最后执行）。

3. **5xx 恒为 0**：`libs/utils.py:85 json_response` 返回 `HttpResponse`（无 status）→ 200；`HandleExceptionMiddleware.process_exception` 兜底也是 200。且 `HandleExceptionMiddleware` **没有 process_response**，方案说的"现有请求收尾处"不存在。

4. **healthcheck 污染**：`docker/docker-compose.yml:58-63` 每 30s 打 `/api/document/health/` → 2880 次/天，会淹没请求量与慢请求指标，必须硬排除。

5. Redis 在 tdyw 容器内（supervisord `[program:redis]`），与 api 同容器 → 重启即丢，方案"落 MariaDB"的理由成立。
