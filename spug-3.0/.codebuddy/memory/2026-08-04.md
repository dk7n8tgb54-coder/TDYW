## 浏览器 HTTPS 证书不安全修复

**现象**：浏览器访问 `https://192.168.40.118` 报"不安全"，在 Windows 安装 CA 证书后仍不生效。

**根因**：`spug.crt` 只包含终端证书，未拼接 CA 证书链。nginx 只发送终端证书给浏览器，浏览器找不到签发者（CA）就无法验证。与容器内 CA 信任无关，是服务器端证书链不完整。

**修复**：`cat ca.crt >> spug.crt`，将 CA 根证书追加到终端证书后形成完整链。nginx reload 后发送 2 个证书（终端 + CA）。备份在 `spug.crt.bak`。

**教训**：自签名证书的 `ssl_certificate` 文件必须包含完整证书链（终端证书 + CA 证书），不能只有终端证书。

## 生产环境 MySQL InnoDB 损坏

**现象**：生产服务器 MySQL 容器无法启动，日志 `InnoDB: Missing FILE_CREATE before FILE_CHECKPOINT for tablespace 416 / Data structure corruption`。

**根因**：OOM killer 杀了 kkFileView（java），内存压力导致 MySQL 也没来得及刷盘就被容器停止/重建，InnoDB redo log 与数据文件不一致。

**修复**：
1. 删除损坏数据卷，重建空 MySQL 容器
2. 用 `backup_set_restore.sh --mode production` 恢复
3. `docker-compose.yml` 中 `tdyw-db` 加 `stop_grace_period: 60s`（默认 10 秒不够 2G buffer pool 刷盘）

**根本原因**：8G 服务器运行 3 容器（tdyw 2G + tdyw-db 3G + kkfileview 1.5G = 6.5G），几乎没有内存余量。

## backup_set_create.sh 定时备份 cron 配置审计

**用户原写法（错误）**：
```
0 2 * * * cd /opt/docker/backups && BACKUP_CLIENT_CNF=/etc/... && ./backup_set_create.sh && BACKUP_ROOT=/data/... >> /var/log/... 2>&1
```

**两个致命错误**：
1. **环境变量用 `&&` 连接不传子进程**：`VAR=value && command` 是两条独立命令，`VAR=value` 只在当前 shell 赋值且不 export，`./script` 是子进程读不到。正确写法是"赋值前缀"：`VAR=value ./script`。项目官方示例在 `backups/tdyw-backup.cron.example:4`。
2. **缺少 `DRY_RUN=NO`**：脚本默认 `DRY_RUN=YES`（`backup_set_create.sh:107`），主流程在 `:698-701` 直接 return，不会真正停服务/备份/归档。用户的 cron 实际上每天只跑一次 dry-run 前置检查。

**正确写法**：
```
0 2 * * * cd /opt/docker/backups && BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf BACKUP_ROOT=/data/backups/tdyw/backup_sets DRY_RUN=NO ./backup_set_create.sh >> /var/log/tdyw-backup/backup_set_daily.log 2>&1
```

**部署检查清单**：辅助脚本齐全（mariabackup_backup.sh / create_fileset_snapshot.py / create_backup_set_manifest.py / select_retention_chains.py，脚本通过 SCRIPT_DIR 定位）、日志目录存在、cnf 0600 可读、cron 用户有 docker 权限、先手动 dry-run 验证再上 cron。

**教训**：shell 变量赋值语法 `A=B && cmd` vs `A=B cmd` 区别要牢记；部署定时备份后务必确认日志里出现 `Backup set published atomically` 而非 `DRY_RUN complete`。

**wrapper 脚本（分行方案）**：crontab 不支持反斜杠续行，一条任务必须写在一行。已创建 `backups/backup_set_daily_cron.sh` 模板（含 `export PATH` 防 cron 环境 PATH 极简），但**用户最终未采用**，改用一行 cron 方式。

**用户最终选择（一行 cron）**：
```
0 2 * * * cd /opt/docker/backups && BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf BACKUP_ROOT=/data/backups/tdyw/backup_sets DRY_RUN=NO ./backup_set_create.sh >> /var/log/tdyw-backup/backup_set_daily.log 2>&1
```

**cron 测试三步**：① dry-run 手动验证（默认 DRY_RUN=YES，不停服务）；② 完整备份低峰期跑（DRY_RUN=NO 会 docker stop tdyw，业务中断）；③ cron 调度测试临时去掉 DRY_RUN=NO + cron 改 `*/2 * * * *` 看日志，确认调度和 PATH。
**最大风险**：cron 环境 PATH 极简（仅 /usr/bin:/bin），docker 若在 /usr/local/bin 会报 `docker is required`，需在 crontab 顶部加 `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`。
**成功标志**：日志出现 `Backup set published atomically`，而非 `DRY_RUN complete`。

**手动完整备份验证通过（2026-08-04 18:32）**：

## 公告发布权限修复（is_global_admin 硬编码 -> 权限码）

**现象**：用户反馈"其他账号给了发布公告权限，能打开页面但显示权限拒绝"。

**根因**：`apps/home/announcement.py` 的 `ensure_announcement_admin(user)` 硬编码只检查 `is_supper`/`is_global_admin`，与 `codes.js` 定义的 `home.announcement.{view,add,edit,delete,publish,withdraw}` 6 个权限码完全脱节。前端 `AuthDiv`/`hasPermission` 按权限码控制菜单和按钮显示，所以"能进页面但接口被拒"。

**修复**：把 `ensure_announcement_admin` 改为 `ensure_announcement_perm(user, code)`，内部调 `user.has_perms(['home.announcement.<code>'])`（has_perms 内部 is_supper 自动放行）。各接口按语义传对应 code：
- 列表/详情/部门列表/附件列表/附件下载预览（管理端通道）-> `view`
- 新增/编辑（POST admin/）-> 先解析 form，按 `form.id` 区分 `add`/`edit`
- 删除公告/删除附件 -> `delete`
- 发布 -> `publish`；撤回 -> `withdraw`
- 上传附件 -> `edit`

**验证**：py_compile OK + lint 0 错误。前端无需改动（已全用 hasPermission）。

**教训**：权限模型必须前后端统一走权限码体系，后端禁用 `is_supper`/`is_global_admin` 硬门槛做业务功能拦截（超管放行由 `has_perms` 内部处理即可）。同类风险：其它模块若有 `ensure_xxx_admin` 类硬编码函数需排查。
