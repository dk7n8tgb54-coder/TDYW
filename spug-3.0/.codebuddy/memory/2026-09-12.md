### 关键发现
1. **coop_task / interference 是多 object_type 共用同一组端点**：
   - coop_task：`delivery` + `item_template` → 传 `att.object_type`，并先白名单校验。
   - interference：`interference` + `bridge_interference` + `air_interference` 共用
     `/interference/attachments/<pk>/download|preview-url` 与 `attachments/?id=` 删除。
     原 `_get_interference_attachment_for_user` 硬编码 `object_type == 'interference'`，
     导致 bridge/air 附件根本无法下载（`test_bridge_interference.test_download` 在 HEAD 即失败）。
     修复：views.py 定义 `ATTACHMENT_OBJECT_TYPES` 集合 + `BRIDGE/AIR_OBJECT_TYPE` 常量，
     business_views.py 改为从 views 导入（避免重复定义与循环导入）。
2. ⚠️ **测试坑：`HttpResponse.close()`（含 FileResponse）会发送 `request_finished` 信号**，
   Django 的接收器会重置/关闭 DB 连接，把 `TestCase` 的 atomic 块标记 `needs_rollback`，
   导致**后续所有用例**在 setUp 报
   `TransactionManagementError: An error occurred in the current transaction`。
   排查手段：打印 `django.db.connection.needs_rollback`（本项目别的 gives: after_close=True）。
   正确做法：只关闭 `resp._closable_objects`，不要调 `resp.close()`。
3. `tdyw-test` 容器期间多次整体重启（redis/mysql 断连），会造成大面积伪失败；
   跑测试前应先确认 `docker exec tdyw-test redis-cli ping` 为 PONG，必要时
   `supervisorctl start redis` 并重试。
