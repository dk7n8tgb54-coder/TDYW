# 2026-07-31 工作日志

## 脚本拆分：build.sh + deploy_prod.sh（2026-08-02）

### 背景
用户实际部署流程是"开发机构建镜像 -> 拷贝 tar 到生产 -> 生产加载部署"，原 deploy.sh 假设同一台机器构建+部署，不适用。

### 新增脚本

**1. `docker/scripts/build.sh`（开发机用）**
- git 检查 -> Django check -> 迁移检查 -> docker build -> docker save
- 输出：`/mnt/e/TDYW/dyw-server/tdyw_YYYYMMDD-N.tar`
- 用法：`wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/build.sh'`

**2. `docker/scripts/deploy_prod.sh`（生产服务器用）**
- docker load -> 保存旧版本 -> 更新 compose -> 重启 -> 90s 健康检查 -> 失败自动回滚
- 用法：`bash deploy_prod.sh tdyw_20260802-123.tar`
- 前提：rollback.sh 和 post_deploy_watch.sh 也在同目录

### 脚本分工
| 脚本 | 运行位置 | 功能 |
|---|---|---|
| build.sh | 开发机 | 构建 + 导出 tar |
| deploy_prod.sh | 生产服务器 | 加载 tar + 部署 + 健康检查 + 回滚 |
| deploy.sh | 开发机（本地测试用） | 构建 + 部署一条龙 |
| rollback.sh | 任意 | 回滚到上个镜像 |
| post_deploy_watch.sh | 任意 | 发布后 5min 监控 |

## 磁盘趋势预警功能（§3.3 容量规划）

### 背景
用户指出 `apps/alert` 模块只有"当前快照超阈值"型告警，没有趋势预测。磁盘 89% 时不告警，等到 91% 才告。要求做磁盘趋势预测 + 测试验证 + 前端趋势图表展示。

### 新增/修改文件

**后端（4 文件）：**
1. **新增 `libs/trend.py`**（~100 行）- 趋势计算工具

   - `get_trend(name, window_hours)` - 读窗口内历史数据

2. **修改 `apps/alert/tasks.py`** - `check_disk_space` 增加趋势逻辑

### 顺带修复的 bug
`libs/alert.py` 的 `_push_to_cache` 用 `cache.lpush`/`cache.ltrim` -> Django cache 抽象层不暴露这些 Redis 原生命令，改用 `django_redis.get_redis_connection()`。这是 alert 模块加入后从未测试过的预先存在 bug。

### 关键技术决策
- **`django_redis.get_redis_connection()` 而非 `cache.zadd`** - Django cache 抽象层不暴露 Redis 原生命令（zadd/zrangebyscore/lpush/ltrim）
- **ZSet member 格式 `{timestamp}:{value}`** - 保证唯一性
- **预测窗口 72h** - 留足人工介入时间
- **最低 12 个数据点** - 避免 2h 内冷启动误报

## SSL 证书 SAN IP 不匹配问题

### 问题
用户在客户端安装了 `certs/ca/ca.crt` 后访问 `https://192.168.40.118` 仍显示"不安全"。

### 根因
- 服务器证书 `certs/prod/spug.crt` 的 SAN 只包含 `IP:192.168.1.49`
- 实际服务器 IP 是 `192.168.40.118`（`.env` ALLOWED_HOSTS）
- `setup-ca.sh` 第 18 行默认 `IP_ADDR=${2:-"192.168.1.49"}`，生成证书时未传正确 IP
- 浏览器发现访问的 IP 不在证书 SAN 列表 -> 即使 CA 已信任也报不安全

### docker-compose.yml 挂载确认正常
- `./certs/prod:/etc/nginx/ssl:ro` -> nginx `ssl_certificate /etc/nginx/ssl/spug.crt` 正确
- `./certs/ca/ca.crt:/data/spug/spug_web/build/ca.crt:ro` -> 供客户端下载，正确

### 修复方案
无需重新生成 CA（客户端不用重装），只用现有 CA 重新签发服务器证书：
1. 生成新 key + CSR（CN=tdyw.jc）
2. 创建 cert.ext，SAN 加入 `IP.1 = 192.168.40.118`（和旧的 192.168.1.49）
3. `openssl x509 -req` 用 ca/ca.crt + ca/ca.key 签发
4. `docker restart tdyw`

发布回滚脚本（deploy.sh/rollback.sh）的回滚能力有边界：如果迁移不可逆，回滚镜像也没用。需要制定 Expand-Contract 规范确保迁移可安全回滚。

### 核心内容
- **3 阶段模式**：EXPAND（加字段/表/索引，向后兼容）-> DEPLOY（发新代码，双写过渡，可回滚）-> CONTRACT（删旧字段，延后做，不可回滚）
- **4 种禁止模式**：删字段+同次删代码 / 改字段类型+同次改代码 / 加NOT NULL无default / 删唯一约束+同次删去重逻辑
- **6 种常见场景方案**：删字段 / 改字段类型 / 加NOT NULL / 加唯一约束 / 改字段名 / 删表
- **与 deploy.sh 集成**：EXPAND 迁移单独执行 -> DEPLOY 用 deploy.sh -> CONTRACT 迁移单独执行
- **回滚能力矩阵**：阶段1可回滚迁移+镜像 / 阶段2只回滚镜像（安全）/ 阶段3不可回滚
- **真实案例**：upgrade_no 移除、document 软删除字段移除（均为违反 Expand-Contract 的反例）

### 关键设计决策
1. 加字段（nullable+default）可直接发布，无需 Expand-Contract
2. 破坏性变更（删字段/改类型/改名/删表/加NOT NULL/删约束）必须用 Expand-Contract
3. 加唯一约束/CHECK约束需先清洗数据再加约束
4. CONTRACT 阶段应在观察期（1-2天）后执行
5. 双写代码示例：保存时同时写新旧字段，读取时优先新字段 fallback 旧字段

## Expand-Contract 策略调整（2026-08-02）

### 决策
从"所有迁移都走三步 Expand-Contract"改为"日常不分离，破坏性才手动分离"。

### 理由
- 95% 的迁移是加法（加字段/加表/加索引），与旧代码兼容，entrypoint.sh 自动 migrate 即可
- 只有 5% 是破坏性的（删字段/改类型/删表），需要手动两步
- 分离的代价（3 步流程 + 认知负担 + 改 entrypoint）远大于收益

### 最终方案
- **日常发布**：`deploy.sh` -> entrypoint 自动 migrate -> 健康检查 -> 监控（一条命令）
- **破坏性迁移**：手动两步
  - 第 1 步：删代码引用不删字段，用 deploy.sh 发布
  - 第 2 步：观察 1-2 天后，手动 `docker exec tdyw python manage.py migrate <app>`
- deploy.sh 迁移检查自动扫描破坏性操作并警告
- 不改 entrypoint.sh，不加 --phase 参数

- 文件重命名：`数据库迁移与发布分离规范.md` -> `发布安全与回滚规范.md`

## 脚本验证与 Bug 修复（2026-08-02）

### 验证结果：发现并修复 8 个 bug

| # | 文件 | 行 | Bug | 修复 |
|---|---|---|---|---|
| 1 | deploy.sh | L118 | `grep` 管道在 `pipefail` 下无匹配时退出码 1 -> `set -e` 退出脚本 | 加 `|| true` |
| 2 | deploy.sh | L123 | grep 模式 `AlterField` 重复 | 删除重复 |
| 3 | deploy.sh | L132 | `read -r` 在非交互模式（`wsl bash -c`）下 stdin 为空 -> `set -e` 退出 | 改为 `read -r < /dev/tty || true` |
| 4 | rollback.sh | L82-89 | `fatal` 调用 `exit 1`，后面 `if` 块是死代码 | 改为 `echo` + `exit 1` |
| 5 | rollback.sh | L152 | 回滚后更新 `.last_deployed_image` 为坏镜像 -> 二次回滚滚到坏镜像 | 不更新，保持原值 |
| 6 | watch.sh | L79 | `|| echo 0` 与 `grep -c` 输出 "0" 叠加 -> "0\n0" -> 整数比较报错 | 改为 `|| true` |
| 7 | watch.sh | L82 | 同上 | 同上 |
| 8 | watch.sh | L85-88 | `df` 失败时 DISK_PCT 为空字符串 -> `[ "" -gt 90 ]` 报错 | 加 `DISK_PCT=${DISK_PCT:-0}` |

### 根因分析
- **Bug 1/3/4**: `set -euo pipefail` 对非零退出码零容忍，但很多命令（grep/read）在"无匹配/无输入"时返回 1 是正常的，不是错误
- **Bug 6/7**: `grep -c` 无匹配时退出码 1 + stdout "0"，`|| echo 0` 额外输出 "0" -> 变量值 "0\n0"
- **Bug 5**: 回滚后再回滚的场景未考虑，.last_deployed_image 指向坏镜像
- **Bug 8**: WSL 环境下 `/var/lib/docker` 路径可能不存在，`df` 无输出

### 改动
在 deploy.sh 的 Django check 之后、构建镜像之前，新增迁移待执行检查：
1. `showmigrations --list` 检查待执行迁移数量
2. 如果有待执行迁移，列出迁移列表
3. `grep -rl` 扫描迁移文件中的破坏性操作（RemoveField/AlterField/DeleteModel/RemoveIndex/AlterUniqueTogether）
4. 如果发现破坏性操作，提示可能属于 CONTRACT 阶段，需用户确认才继续
5. 无待执行迁移时打印 OK

### 技术细节
- `grep -c` 无匹配时退出码为 1，与 `set -e` 冲突 -> 用 `|| true` 而非 `|| echo "0"`
- grep pattern 用单引号 `'\[ \]'` 避免转义问题
