## 无线电台执照提醒弹窗重构：执照中心模型

**问题**：弹窗 days_left 不随 valid_to/日期变化（读快照），content 拼死，作废/去重逻辑复杂。

**根因**：RadioLicenseReminder 表混合了派生数据、通知事件、用户确认状态三个概念。

**方案**：执照中心模型——派生数据不存储，状态与事件分离，续期失效靠数据本身。

### 新增 LicenseReminderAck 表

```
LicenseReminderAck
  - license_id        ← 外键
  - user_id           ← 确认用户
  - ack_valid_to      ← 确认时的 valid_to（续期后自动失效）
  - tenant_id, created_at
  UNIQUE(tenant_id, license_id, user_id, ack_valid_to)
```

**弹窗判断**：license.status IN (expiring, expired) AND NOT EXISTS ack WHERE (license_id, user_id, ack_valid_to=license.valid_to)
**续期失效**：license.valid_to 变化 → 旧 ack 的 ack_valid_to ≠ 新 valid_to → 自动失效

### 修改文件（7 个）

1. `models.py`：新增 LicenseReminderAck；RadioLicenseReminder 注释降级为历史日志
2. `migrations/0005_add_reminder_ack.py`：建表 + 数据迁移（历史 is_handled=True → ack，反推 ack_valid_to = remind_date + days_left）
3. `views.py`：
   - 新增 `ReminderPopupView`：实时查 license + 排除 ack，days_left 实时算
   - 新增 `ReminderAckView`：写 ack（IntegrityError 幂等）
   - `ReminderHandleView` 保留兼容：handle action 同步写 ack
   - 删除编辑流程里"作废旧提醒"逻辑（ack 自动失效）
4. `urls.py`：注册 `reminders/popup/` 和 `reminders/ack/`
5. `tasks.py`：`scan_single_license` 只更新 license.status，删除 `_generate_reminder`/`_has_handled_in_current_cycle`/`_get_receiver`
6. `ReminderNotification.js`：改用 `/reminders/popup/` 接口，去重 key 从 reminder.id 改 license_id，content 前端拼
7. `ReminderList.js`：已处理按钮改调 `/reminders/ack/` {license_id}

### Django 2.2 兼容性教训

- `UniqueConstraint` 必须放 `Meta.constraints`，不能放 `indexes`（否则 `_check_indexes` 报 `AttributeError: 'UniqueConstraint' object has no attribute 'fields_orders'`）
- `indexes` 里外键字段用实际字段名 `license`，不能用 `license_id`（报 `models.E012 nonexistent field`）

### 验证结果

- lint 0 错误，py_compile 语法 OK
- migration 执行成功：1 条历史 is_handled=True 迁移到 ack 表
- ack 表结构确认：UNIQUE 约束 + 索引正确
- 重启 spug-api + spug-celery-radio-license + spug-celery-beat

### 设计原则

1. **派生数据不存储** — days_left 是 valid_to 的函数，存就失真
2. **状态与事件分离** — ack 是状态（会变），reminder 是事件（只增）
3. **单一真相源** — valid_to 唯一，其他都从它派生
4. **续期失效靠数据本身** — ack_valid_to 字段，不需反推/作废

## 资料库上传并发槽位口径统一（方案 7.2）

**任务**：按《资料库并发上传与状态机修复方案.md》7.2 节，统一前端上传并发调度口径，消除 `activeUploads` 与状态机计数两套口径并存的问题。

### 修改前的问题

`StateChangeHandler.handleUploadingState()` 使用 `while (activeUploads >= MAX_CONCURRENT_UPLOADS)` 等待槽位 + 手工 `increment/decrement`，而 `UploadCoordinator.startWaiting()` 使用 `countByStates(['calculating','uploading'])`。两套口径不一致会导致卡槽、超发、暂停/取消/失败后槽位泄漏。

### 修改的文件（6 个源文件 + 1 个测试）

1. **`lifecycle/StateChangeHandler.js`**（核心改造）：
   - 删除 `while (activeUploads >= MAX)` 等槽循环
   - 删除所有 `incrementActiveUploads()` / `decrementActiveUploads()` 调用（共 5 处）
   - 保留上传业务执行和错误处理
   - 保留 finally 中的 `processPending()` 作为防御性兜底
   - 槽位释放由状态机状态自然变化实现（uploading→merging/completed/error 后 countByStates 不再统计）

2. **`coordinators/RecoveryCoordinator.js`**：
   - `this.core.activeUploads < MAX` → `stateMachineManager.countByStates(['calculating','uploading']) < MAX`

3. **`controls/DebounceController.js`**：
   - `() => coreStore.activeUploads` → `() => coreStore.stateMachineManager.countByStates(['calculating','uploading'])`

4. **`queue.js`**：`activeUploads` 字段 + `increment/decrement` 方法标注 `@deprecated`
5. **`index.js`**：`get activeUploads()` 代理属性标注 `@deprecated`
6. **`controls/QueueOperationController.js`**：`activeUploads = 0` 标注 `@deprecated`（防御性保留）

### activeUploads 保留策略

- **保留字段和方法**，标注 `@deprecated`
- **不参与调度决策**（已从所有调度逻辑中移除）
- **仅作为兼容 UI/调试指标**
- 值不再被业务递增递减（`increment/decrement` 不再被调用）
- `QueueOperationController.cancelAll` 中的 `= 0` 保留为防御性清零
