1. **E2E 登录会轮换 access_token**：`apiLogin` 后再用之前建的 API 上下文会报

9. PowerShell `| head`、`grep "(...)"`、`{{.X}}` 等内层引号/括号会被吃掉 →

# 2026-09-02 晚：数据质量巡查 503 修复

## 现象
前端「数据质量巡查」页面（`/maintenance/data-quality`）加载后报 `请求失败: 503 Service Unavailable`。

## 根因链（实测确认）
1. `GET /api/alert/data-quality/`（`apps/alert/views.py` DataQualityCheckView）**同步**执行
   `call_command('data_quality_check')`，容器内实测耗时 **~16.4s**（文件存在性采样重）
2. 前端 dev 代理 `spug_web/src/setupProxy.js` 通用 `/api` 路由设了 `proxyTimeout: 10000`（10s 兜底）
3. 10s 后 http-proxy-middleware 触发 timeout → `onError` 返回 **503**；
   容器 nginx access log 对应记录为 **499**（对端断开）——日志与推断完全吻合

## 修复
- `setupProxy.js` 在通用 `/api` 代理**之前**新增专用路由 `/api/alert/data-quality`，
  `proxyTimeout/timeout = 130000`（与 axios 默认 120s 对齐略留余量），复用 noKeepAliveAgent
- 通用 `/api` 的 10s 快速失败兜底保留不动（最小修改）
- **用户需重启 `npm start`** setupProxy 是 dev server 启动时加载的

## 顺带确认（无需修改）
- `[Celery] xxx tasks imported successfully` 等 print 在 `spug/celery.py` 模块导入时执行（启动一次），
  不会污染 View 内 `call_command(stdout=StringIO())` 捕获的结果；CLI 直跑 manage.py 才会混入
- 该路径若直连容器 nginx（localhost:8080）则 proxy_read_timeout=600s，不受影响
- 巡检命令本身正常返回：6 项检查 / 107 个问题 / 1 项执行失败（数据内容，非本次 503 问题）

## 经验
- nginx access log 的 **499** = 客户端（或中间代理）在响应前断开，是排查「前端报 503/超时但后端查无异常」的关键信号
- 同步重接口 + 前端代理超时兜底是常见冲突点：给慢接口单开更长超时的代理路由，别动全局兜底
