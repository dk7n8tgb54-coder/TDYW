## 资料库大文件上传：磁盘 IO 打满 / 11M/s 上限排查

用户原报：上传大文件「计算 MD5 + 合并」会把磁盘打满。经排查纠正为**打满磁盘 IO（读写带宽），不是磁盘空间（容量）**。

### 合并阶段（IO 重灾区）
- 合并逻辑已是**单遍**（已优化）：`apps/document/tasks/merge.py` `_copy_chunk` 边读分片(.part)边写完整文件边算 MD5，**不会读两遍**。
- IO 打满根因：`document.merge` 队列 worker 默认并发 **2**（`tools/start-celery-merge.sh` `CELERY_MERGE_CONCURRENCY=2`；`docker/config/supervisord.conf` 也设 2）。合并是「读全部分片 + 写完整文件」纯 IO 流，且分片目录与最终 `documents` 目录**同处 storage 盘** → 读写互抢带宽，多文件并发时 IO 叠加打满。
- 缓解方向（待用户确认再做）：合并串行化（并发降 1）、合并 IO 限速（token-bucket，锚点 merge.py 243-249 while 循环）、分片与最终目录分盘。

### 上传速度 11M/s 上限
- 用户发现上传最高 11M/s，问应用代码层是否有限速。
- 结论：**应用代码层无任何上传限速**：
  - 前端 `chunkUpload.js` 串行 POST 分片，无 sleep/节流（仅进度刷新节流）；`CHUNK_SIZE=32MB`、`MAX_CONCURRENT_UPLOADS=3`（stores/constants/upload.js:179/183）
  - Nginx `upload_chunk` location **无 `limit_rate` / `limit_req`**，`client_max_body_size 0`（docker/config/nginx.conf）
  - Django settings 无 throttle 中间件；Gunicorn `gevent` 异步（gunicorn.conf.py:19）
- 11M/s 来自**网络带宽**，不是磁盘。用户实测 storage 盘顺序写 **82.2MB/s**（容器内 `dd ... oflag=direct bs=1M count=200`），远高于 11MB/s → 排除磁盘写吞吐为上传瓶颈。
- 验证命令：容器内 `dd if=/dev/zero of=/data/spug/spug_api/storage/document_chunks/_ddtest bs=1M count=200 oflag=direct`（WSL 内 `docker exec tdyw bash -c '...'`）。注：WSL2 下 Docker 卷真实路径在 `docker-desktop-data` 发行版，跨发行版访问失真，故进容器测最准。
- **两个独立瓶颈，勿混淆**：
  1. 上传 11M/s = 网络带宽上限（代码无能为力，除非升级带宽/就近接入/压缩）。
  2. 合并打满磁盘 IO = 本地纯 IO（无网络参与），`document.merge` 并发 2 + 分片与 documents 同盘，读写总量逼近 82MB/s 上限 → 仍可能打满，同期其他 IO 变慢。治理方案（串行化/限速/分盘）对合并仍对症。
- 写放大优化（/tmp 中转）优先级因磁盘不慢而下降，但仍是合理的代码层改进。

### 可优化的写放大（代码层能做）
- 分片 32MB 远大于 Django 默认 `FILE_UPLOAD_MAX_MEMORY_SIZE=2.5MB` → Django 先把整个分片缓冲到 `/tmp`，再被视图读到 chunk 目录落盘，**单分片写两遍磁盘**（写放大）。若 `/tmp` 与 storage 同盘，上传更慢且加重 IO。
- 优化：上传视图改为**流式直写**（直接读 request 流写 chunk 目标文件，跳过 /tmp 中转），可把上传写 IO 减半。

### 反思
- 用户连续纠正方向：先是从「磁盘空间」纠正为「磁盘 IO」，后是问「11M/s 是否代码限速」→ 查实无代码限速，来自底层。每次都应先确认根因再下结论，避免凭"看起来像 X"就给方案。

### 网络环境确认 + 离线测速方案（用户提供）
- 网络拓扑：公司内网，服务器在机房接内网交换机，终端经服务器 IP 访问（通常千兆≈125MB/s）。**内网千兆下 11M/s 反常 → 不是物理带宽上限**，更可能是**网关/安全设备对单 TCP 连接限速**（11M/s≈100Mbps 常见阀值）。
- 应用层已查无显式限速：前端 XHR 串行分片无节流、Nginx 无 `limit_rate`/`limit_conn`、上传 gunicorn 服务无带宽限制。
- 关键洞察：前端**单文件分片是串行的**（`chunkUpload.js:167` for+await），单文件全程只走 1 条连接 → 若网关单连接限速 11M，单文件死卡 11M。代码层对症解法是**单文件内分片并发上传（多连接叠加带宽）**，比"流式直写"更对症。
- 终端无 Python（离线）：改用 Windows 自带 `curl.exe` + `fsutil file createnew` 造文件，服务器 `python3 -c` 起 HTTP 接收端（端口 9999，绕过 Nginx 直连）测单连接带宽，隔离"网关限速 vs 应用层"。待用户跑出 `RECV MB/s` 再定方向。
- ⚠️ 测速命令坑：`curl -T` 默认发 **PUT**，会命中 nginx 405（Django 拒 PUT）或 python 9999 的 501（只写 do_POST）。**必须用 `curl.exe -X POST --data-binary @file` 上传**才能测出速度。SSL renegotiation 警告无害，加 `-k` 忽略。
- 备选：iperf3 静态二进制（iperf.fr）U盘/scp 拷离线服务器，零依赖免安装。

## 合并 IO 优化实施（方案 1+3+4）

用户确认生产为**单块机械盘**，`chunks`/`documents`/`media` 同盘（`/dev/sdd`，ext4，IO 调度器 `none`）。多用户并发上传时，上传随机写（分片落盘）与合并顺序读写抢同一磁头 → 寻道打满。ionice 在 `none` 调度器下无效。

### 已实施（3 文件 4 处改动，py_compile + bash -n 验证通过）
1. **merge worker 并发 2→1**：`docker/config/supervisord.conf:154` `CELERY_MERGE_CONCURRENCY` + `tools/start-celery-merge.sh` 默认值 `${...:-1}`。合并串行，只留 1 路顺序 IO 抢盘。
2. **合并写缓冲 8MB→16MB**：`apps/document/tasks/merge.py:43` `FILE_COPY_BUFFER_SIZE`。减少 write 系统调用次数。
3. **fallocate 预分配目标文件**：`merge.py` `ChunkMerger._preallocate_target_file`（新增方法），`merge_chunks` open 后调用。`os.posix_fallocate` 物理预分配防 ext4 碎片；ENOSPC 抛出，ENOSYS/EINVAL 回退 ftruncate，再失败跳过。

### 未实施（评估后搁置）
- token-bucket 限速：`none` 调度器下无法做真"比例"，只能绝对值近似，阈值难定；与降并发叠加致合并过慢。若 1+3+4 不够，优先 cgroup `io.max`（不侵入代码）。
- 前端分片并发 3→2：影响用户体验，最后手段。
- chunks 独立磁盘：根治，需硬件。

### 死代码（已清理）
- `tasks/merge_helpers.py`、`tasks/merge_utils.py` 是 1MB 缓冲旧副本，无人调用（主路径是 merge.py 的 ChunkMerger）。已删除，`manage.py check` 通过（唯一 warning 是 pre-existing 的 `DocumentSystemFolder.folder` W342，与本次无关），import 链完好。

### 生效方式
重启 merge worker：`docker exec tdyw supervisorctl restart spug-celery-merge`（tdyw 无 bind mount，需先 docker cp 三个文件进容器）。实测 `iostat -xm 2 10 /dev/sdX` 看 `await`/`%util`。
