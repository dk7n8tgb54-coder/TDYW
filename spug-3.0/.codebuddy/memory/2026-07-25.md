## 资料库"我的文件"私密空间：超管可见所有账号文件

**需求**：资料库-文档管理-"我的文件"私密空间，当前按租户隔离。希望超级管理员能看到所有账号的文件，其他账号保持隔离不变。

**隔离机制澄清**（探索后确认）：
- 私密空间（is_public=False）隔离靠 `apply_tenant_filter(qs, user, strict_mode=True)`，按 `tenant_id` 过滤
- 模型有 `created_by` 字段但查询未用它过滤；`unique_key=MD5(tenant_id:created_by_id:name:parent_id)` 允许同租户多用户各有同名文件夹
- `strict_mode=True` 时原逻辑：超管也按自己的 tenant_id 过滤（只看本租户）
- 用户部署实际是"每账号一租户"，故按 tenant_id 过滤 ≈ 按账号隔离

**改动**（2 文件）：
- `libs/tenant_utils.py` `apply_tenant_filter`：strict_mode=True 且 `is_supper` 时，返回原 queryset（不按 tenant_id 过滤）。影响 document 模块所有 strict_mode 调用点（列表/搜索/预览/下载/移动/复制/重命名），超管均可跨账号访问
- `apps/document/views/folder/views.py` `_annotate_has_children`：第 244-247 行原硬编码 `children_qs.filter(tenant_id=tenant_id)`，加 `if not is_supper:` 条件，否则超管看到的文件夹 has_children 错误为 False（因为子目录按超管 tenant_id 过滤看不到其他租户的）

**未改动**（保持隔离）：
- 普通用户 strict_mode=True/False 行为完全不变
- `tasks/pack.py` / `tasks/merge.py` / `upload/merge.py` / `transfer/list.py` 等硬编码 tenant_id 的地方是 Celery 后台任务/传输列表，不在"我的文件"浏览路径，不改
- 上传时 `set_instance_tenant` 仍按超管 tenant_id='admin' 归属，其他租户用户看不到超管上传的文件

**验证**：lint 0 错误；py_compile OK；临时脚本用 SimpleNamespace mock 3 个用户（超管/userA/userB）+ DocumentFolderPrivate queryset，5 个测试全通过：
1. 超管 strict=True → WHERE 无 tenant_id 过滤 ✓
2. 普通用户A strict=True → WHERE 含 tenant_a ✓
3. 普通用户B strict=True → WHERE 含 tenant_b ✓
4. 超管 strict=False → WHERE 无 tenant_id 过滤（原有行为）✓
5. 普通用户A strict=False → WHERE 含 tenant_a（原有行为）✓

**经验**：
- Django `str(qs.query)` 含 SELECT 字段列表，列名 `tenant_id` 会出现；判断 WHERE 是否过滤要用 `'tenant_id` ='` 模式（带反引号闭合+等号），不能简单 `'tenant_id' in sql`
- `apply_tenant_filter` 的 strict_mode 设计意图就是"私密空间"，超管在此放开跨租户符合语义
- `_annotate_has_children` 硬编码 tenant_id 过滤未走 apply_tenant_filter，改隔离逻辑时必须同步检查所有硬编码过滤点

## 架构咨询：9 模块删除是否改逻辑删除

**问题**：部门值班日志/无线电台执照/台站频率批复/合同协议/设备履历/系统升级/故障/干扰/值班日志 这些模块删除功能是否需改逻辑删除？

**调查结论**：**不需要大规模改逻辑删除**。资料库回收站是本项目已有的失败先例（2026-06-23 完全移除），带来跨租户漏洞/重复代码/N+1/unique 冲突/查询过滤负担/UI 维护成本。模型层保留 is_deleted 字段但不再被业务设置。

**各模块现状分类**：
- 已实现逻辑删除（标杆）：`device` 设备档案（SoftDeleteTenantManager + all_objects + 编号恢复重建）
- 已有逻辑删除（仅草稿）+ 作废机制：`department_duty_log`（草稿软删，已签走 voided 作废）
- 已有作废机制替代删除：`interference`（draft→...→voided 状态机）
- 不可删除：`logs` 审计日志（哈希链防篡改，无删除接口）
- 纯物理删除：`radio_license`(执照/批复)、`contract_agreement`、`upgrade`、`fault`、`duty`

**真正该做的 3 件事（与逻辑删除无关，已核实代码）**：
1. 修 `upgrade` 孤儿数据 bug（高优）：`delete_record`(record_service.py:162-201) 只软删附件 + `record.delete()` 物理删主表，但子表 `UpgradeStatusLog.upgrade_id` 是 **IntegerField 不是外键**(models_status_log.py:76)，DB 不级联，留孤儿（UpgradeRecordStep 同理）。后果：时间线查询异常/统计失真/id 复用串台/存储堆积。解法：删主表前级联清理子表
2. 补删除 AuditLog（中优）：radio_license/upgrade/fault/duty 删除未写审计日志。后果：误删/恶意删除无据可查，合规追溯断链（非运行时错误，是留痕缺失）
3. `interference` 删除限制缺失（高优，最危险）：docstring(views.py:251) 声称"仅 draft/voided 可删"，但代码注释(views.py:261) 明确写"状态流转功能已暂停：删除不再受 status 限制"，实际无任何 status 校验直接 `record.delete()`。**docstring 撒谎**比"没限制"更糟——维护者以为有限制实际没有。后果：任意状态干扰记录可被物理删除，证据链断裂，合规/执法取证无据。解法：要么恢复 status 限制，要么至少修正 docstring 不再误导
