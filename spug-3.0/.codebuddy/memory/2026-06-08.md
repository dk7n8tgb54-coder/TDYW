## 关键教训（来自本会话）

1. **不要凭时间顺序下因果结论**：M9/M6 时间在 FATAL 之后 ≠ M9/M6 导致 FATAL
2. **改完代码必须验证代码真的进了运行环境**：git status + 容器 grep 双向验证
3. **用户质疑"是不是你改的"时，要做反向验证**：去查容器里实际跑的代码、git log 里所有出现位置
4. **stash 是隐形炸弹**：用 stash 而不提交，等于改了一堆代码但环境完全不知道
5. **修复要 1) 写代码 2) 验证代码进了运行目录 3) 提交 4) 重启服务** — 缺一不可
6. **PowerShell 工具调用陷阱**：
   - `&&` 和 `;` 在某些情况下被 PowerShell 吞
   - `>` 重定向会变成 `Out-File E:\dev\null`
   - `cd` 后工作目录被 PowerShell 吞，导致 git 看不到修改
   - 解决方案：把命令写在 `bash -c '...'` 或 `powershell -Command '...'`，**用单引号**
7. **replace_in_file 多次相同 old_str 失败**：用 Python 脚本批量替换（独立 .py 文件，测试完删除）
8. **PowerShell 环境 git 工作目录漂移**：`pwd` 返回 IDE 视角（`E:/TDYW/spug-3.0`），但 `git rev-parse --show-toplevel` 返回 git 视角（`E:/TDYW`）。这是因为 `E:/TDYW/.git` 是 git 根，spug-3.0 是子目录。**git 视角看到所有路径都带 `spug-3.0/` 前缀**。
9. **修复前先扫调用方**：扫 `completeTransfer` 9 个调用方后，发现 5 个已有 try-catch（部分能处理抛错，部分是空 catch），3 个无 try-catch（底层抛错会冒泡到上层 catch 块被处理），1 个 `updateTransferProgress` 完全没人用
