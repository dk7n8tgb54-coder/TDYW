**关键配置来源**（已核对）：

- `docker/docker-compose.yml`：容器名 `tdyw-db-test`，数据目录 `/var/lib/mysql`

**产出文件**：`backups/mariadb_backup.sh`

**脚本设计要点**：
1. 三种模式：`dump`（逻辑备份）/ `physical`（物理热备份）/ `all`（默认，两者都做）
2. 自动从 `docker/.env` 读取 `MYSQL_ROOT_PASSWORD` 和 `MYSQL_DATABASE`，读不到回退到脚本默认值
3. mariadb-dump 参数：`--single-transaction --routines --triggers --events --hex-blob --quick --default-character-set=utf8mb4`，输出 gzip 压缩为 `.sql.gz`
4. mariabackup：容器内 `--backup --target-dir=/tmp/...`，校验 `xtrabackup_checkpoints` 存在，再用 `tar czf - ` 直接流式输出到宿主机（省去 docker cp）
5. 备份完整性校验：dump 做 `gzip -t` 校验；physical 检查 checkpoints 文件 + 非空
6. 清理策略：dump 保留 30 天，physical 保留 7 天（物理备份文件大）
7. `set -euo pipefail` + `umask 027`（备份含敏感数据，限制权限）
8. 日志同时输出控制台和 `backup.log`

**与旧脚本差异**：
- 旧 `backups/backup.sh` 用的是过时配置（容器 `spug-db`、库名 `spug`、密码 `spug.cc`），与当前 docker 配置不符
- 新脚本配置完全对齐当前 `docker-compose.yml`，并支持从 .env 自动加载密码

**待用户注意**：

## 环境变量覆盖支持 + 生产部署方案

**需求**：用户确认备份应直接输出到生产宿主机 Linux（而非容器内 + volume 映射），并要求脚本支持环境变量覆盖路径。

**决策依据**：当前脚本架构本就是「宿主机执行 `docker exec`，备份流式输出到宿主机文件」（`docker exec | gzip > 宿主机文件`），备份文件从未进容器，volume 映射是多余环节。行业惯例也是备份落宿主机独立磁盘。

**变更**（两个脚本均改）：
- `BACKUP_DIR` / `LOG_FILE` 改为 `${VAR:-默认值}` 形式，支持环境变量覆盖
- `KEEP_DAYS` 同样支持环境变量覆盖
- 默认值仍是脚本相对路径（开发/测试场景），生产用环境变量设绝对路径
- 头部注释补充环境变量说明 + 生产 crontab 示例

**生产部署方式**：
```bash
# crontab 中直接用环境变量指定输出路径
0 2 * * *   BACKUP_DIR=/data/backups/mariadb/dump /opt/backups/mariadb_dump_backup.sh
0 3 * * 0   BACKUP_DIR=/data/backups/mariadb/physical /opt/backups/mariabackup_backup.sh
```

## 资料库文件增量备份脚本

**需求**：用户确认 mariadb-dump / mariabackup 都是全量备份，要求为资料库文件（`tdyw-documents` 卷 → 容器内 `/data/spug/spug_api/storage/documents`）做增量备份。

**存储结构调研**（code-explorer 子代理结果）：
- 资料库文件按 `public/folder-{id}/` 和 `private/user-{uid}/folder-{id}/` 组织
- 物理文件名含毫秒时间戳：`原始名_1719456789012_a3b2c1.ext`
- 缩略图存在同目录 `thumbnails/` 子目录下
- `document_chunks` / `document_merge_tasks` 是上传临时数据，合并后自动清理，无需备份
- 文档模型有 `is_deleted` 软删除 + `created_at`/`updated_at` 字段
- documents 卷挂在**应用容器**（tdyw-test）上，不是 db 容器

**产出文件**：`backups/documents_incremental_backup.sh`

**增量策略**：基于文件 mtime 的时间戳增量（find -newer）
- 首次运行或无标记文件 → 自动全量备份
- 后续运行 → `find -newer <标记文件>` 只备份变动文件
- 每次成功后更新标记文件（`BACKUP_DIR/.last_backup_marker`）作为下次基准
- 可用 `./documents_incremental_backup.sh full` 强制全量

**技术实现要点**：
- `find -type f -printf '%P\n'` 生成相对路径文件列表
- 文件列表 `docker cp` 到容器，用 `tar -T <list>` 精确打包
- `tar -C ${DOCUMENTS_PATH}` 保证包内是相对路径，恢复时直接解压到 documents 目录
- 标记文件经 `docker cp` 拷到容器内做 `find -newer` 基准，用完即删
- 无变动文件时跳过打包但仍更新标记（避免下次扫描窗口累积过大）

**与数据库备份的配合**：
- mariadb-dump（每天全量，30天）+ mariabackup（每周全量，7天）+ documents 增量（每天，90天）
- 恢复顺序：先恢复数据库 → 再解压文件备份到 storage/documents/

**环境变量覆盖**：BACKUP_DIR / LOG_FILE / KEEP_DAYS / APP_CONTAINER

**验证**：Git Bash `bash -n` 语法检查 `exit=0`。Docker Desktop 未运行，未做容器内实测。
