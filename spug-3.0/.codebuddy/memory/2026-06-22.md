## 资料库并发上传修复方案 5.2：合并时同步计算 MD5

**任务**：依据 `资料库并发上传与状态机修复方案.md` 第 5.2 节，实施 P0-2 修复。

**目标**：合并写入时同步 `md5.update(data)`，合并完直接得到 MD5，`verify_file_md5` 直接比对，省掉合并后的二次全量读盘。

**修改文件**：`spug_api/apps/document/tasks/merge.py`（4 处改动）

1. 顶部新增 `import hashlib`
2. `ChunkMerger` 类：
   - `__init__` 新增 `self.merged_md5 = None`
   - `merge_chunks`：全量 MD5 文件初始化 `hashlib.md5()`，sv1_ 抽样 MD5 跳过计算；合并完 `self.merged_md5 = md5_hash.hexdigest()`
   - `_copy_chunk`：用等价于 `shutil.copyfileobj` 的手动 read/write 循环替换，write 后立即 `md5_hash.update(data)`
3. `FileVerifier.verify_file_md5`：签名改为 `verify_file_md5(self, merged_md5=None)`，优先用合并期 MD5 比对，`merged_md5 is None` 时回退到 `calculate_file_md5` 全量读盘
4. `MergePipeline._merge_and_verify`：调用改为 `verify_file_md5(merged_md5=self.merger.merged_md5)`

**关键正确性保证**：`hashlib.md5().update()` 是流式的，分段 update 与一次 update 结果一致，所以合并期用 8MB 缓冲 update 与 `calculate_file_md5` 用 1MB update 结果相同。容器内单元测试验证通过（全量 MD5 一致 + sv1_ 跳过）。

**向后兼容**：`execute(get_models, create_instance, get_mime_type, calculate_file_md5)` 外部签名不变，`calculate_file_md5` 参数在 pipeline 内部不再使用但保留，避免破坏 `merge_file_chunks` 的延迟导入链。

**未触动**：`merge_utils.py:112` 的独立 `verify_file_md5` 函数不在合并流程链路，未改动。

**生产环境部署排查（重要经验）**
- 问题：用户反馈"提醒记录里还是只有 45/7 天固定节点"
- 根因：docker cp 复制新代码到容器文件系统后，**Python 进程（celery/gunicorn）加载的还是旧模块**（进程启动时加载进内存，后续改文件不自动重载）
- 修复步骤：
  1. 用 pymysql 脚本清理旧分级提醒记录（expiring_45/30/15/7/1）
  2. `supervisorctl restart spug-celery-radio-license spug-celery-beat spug-api` 重启进程加载新代码
  3. 手动触发 `scan_radio_license_expiration.apply().get()` 全量扫描，立即生成今日 expiring_daily 提醒
- 结果：6 张即将到期执照 status 全部更新为 expiring，3 张有有效责任人的执照生成 expiring_daily 提醒（3 张因责任人禁用/为空/伪ID 跳过，warning 日志正确）
- 追加修复：`scan_radio_license_expiration` 的 `updated_count` 统计 bug（scan_single_license 会更新 license_obj.status，需在调用前保存旧值）

**关键教训**：docker cp 修改容器内文件后，**必须重启相关 Python 进程**才能让新代码生效。文件系统更新 ≠ 进程内存更新。
