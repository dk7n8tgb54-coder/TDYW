# 附件功能公共化设计方案

> 修订日期：2026-07-10
> 适用范围：后续多个业务模块统一接入附件上传、列表、下载、删除、在线预览能力
> 核心要求：附件文件可通过 kkFileView 在线预览；物理文件保存到 `/data/spug/spug_api/media` 下以模块英文名命名的子目录

## 一、目标

多个业务模块都需要附件能力时，不建议每个模块各写一套上传、下载、删除、预览逻辑。推荐建设一套公共附件能力：

1. **后端统一底座**：统一附件表、统一保存、统一校验、统一下载、统一预览 URL 生成。
2. **前端统一组件**：统一上传按钮、附件列表、下载、删除、预览入口。
3. **模块只做配置**：各模块只声明模块英文名、业务对象类型、权限码、文件限制、业务对象存在性校验。
4. **物理路径统一规范**：文件统一落在 `/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}`。
5. **在线预览统一接入 kkFileView**：所有可预览附件通过 kkFileView 打开，不把长期登录 token 暴露给 kkFileView。

## 二、总体设计

### 2.1 推荐架构

```text
业务模块页面
  -> 公共 AttachmentManager 组件
     -> 列表 / 上传 / 下载 / 删除 / 获取预览地址
        -> 模块薄接口或通用附件接口
           -> AttachmentService
              -> EvidenceAttachment / Attachment 表
              -> /data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
              -> kkFileView preview_token 下载端点
```

### 2.2 职责划分

| 层级 | 职责 | 不应承担的职责 |
|---|---|---|
| 业务模块 | 提供 `module`、`object_type`、`object_id`、权限码、业务对象存在性校验 | 不直接处理文件保存、路径拼接、kkFileView URL 拼装 |
| 公共后端服务 | 校验、保存、入库、列表、下载、删除、生成预览地址 | 不硬编码某个业务模块的权限 |
| 公共前端组件 | 上传、列表、预览、下载、删除、状态展示 | 不硬编码某个模块接口路径 |
| kkFileView | 渲染 Office/PDF/图片/文本等可预览文件 | 不参与业务权限判断 |

## 三、数据模型

### 3.1 表结构建议

当前项目已有 `EvidenceAttachment` 通用附件表，可优先复用。如果后续希望摆脱 evidence 语义，也可以迁移为独立的 `Attachment` 表，但字段结构保持一致。

| 字段 | 说明 |
|---|---|
| `id` | 附件主键 |
| `tenant_id` | 租户 ID |
| `module` | 模块英文名，如 `upgrade`、`runlog`、`interference` |
| `object_type` | 业务对象类型，如 `record`、`order`、`task` |
| `object_id` | 业务对象 ID，统一按字符串保存 |
| `file_name` | 原始文件名 |
| `file_path` | 相对 `MEDIA_ROOT` 的文件路径，如 `upgrade/1/202607/record_123/a.docx` |
| `file_size` | 文件大小，单位 byte |
| `file_ext` | 文件扩展名，小写，含点 |
| `file_hash_sha256` | 文件 SHA256 |
| `uploaded_by_id` | 上传人 ID |
| `uploaded_by_name` | 上传人姓名快照 |
| `uploaded_at` | 上传时间 |
| `is_deleted` | 软删除标记 |
| `deleted_by_id` | 删除人 ID |
| `deleted_by_name` | 删除人姓名快照 |
| `deleted_at` | 删除时间 |
| `delete_reason` | 删除原因 |

### 3.2 推荐索引

| 索引 | 字段 | 用途 |
|---|---|---|
| `att_obj_idx` | `tenant_id, module, object_type, object_id, is_deleted` | 查询某个业务对象下的附件 |
| `att_module_idx` | `tenant_id, module, is_deleted` | 模块级统计或清理 |
| `att_sha256_idx` | `file_hash_sha256` | 文件完整性校验、去重扩展 |

## 四、物理文件存储规范

### 4.1 根目录

附件物理文件必须保存在：

```text
/data/spug/spug_api/media
```

Django 配置建议显式支持环境变量，生产默认值指向该目录：

```python
MEDIA_ROOT = os.environ.get('MEDIA_ROOT', '/data/spug/spug_api/media')
MEDIA_URL = '/media/'
```

如果本地开发仍希望使用项目目录下的 `spug_api/media`，可以通过 `.env` 或启动环境覆盖 `MEDIA_ROOT`。

### 4.2 模块子目录

每个模块必须使用模块英文名作为 `MEDIA_ROOT` 下的一级目录，模块目录下再按租户 ID、年月、业务对象分层：

```text
/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
```

示例：

```text
/data/spug/spug_api/media/upgrade/
/data/spug/spug_api/media/runlog/
/data/spug/spug_api/media/interference/
/data/spug/spug_api/media/radio_license/
```

### 4.3 推荐完整路径

为了避免单目录文件过多，并便于排查问题，推荐路径结构：

```text
/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
```

其中 `tenant_id` 使用租户的序号原值，例如 `1`、`2`，不额外加 `tenant_` 前缀。

示例：

```text
/data/spug/spug_api/media/upgrade/1/202607/record_123/升级说明.docx
```

数据库中的 `file_path` 保存相对路径：

```text
upgrade/1/202607/record_123/升级说明.docx
```

### 4.4 路径安全规则

1. `module` 只允许英文、数字、下划线、中划线：`^[A-Za-z0-9_-]+$`。
2. `tenant_id` 只允许租户序号值，建议按数字字符串处理并做路径段清洗。
3. `yyyyMM` 固定为 6 位年月，例如 `202607`。
4. 文件名必须使用 `os.path.basename` 清洗，移除 `..`、`/`、`\`、`\x00`。
5. 保存前使用 `os.makedirs(save_dir, exist_ok=True)` 创建目录。
6. 下载、预览、删除物理文件前必须使用 `realpath` 校验目标文件仍在 `MEDIA_ROOT` 内。
7. 同名文件自动追加序号或 UUID 后缀，避免覆盖旧文件。

## 五、后端设计

### 5.1 模块附件配置

每个模块声明一个附件配置：

```python
AttachmentConfig(
    module='upgrade',
    object_type='record',
    allowed_extensions=('.pdf', '.doc', '.docx', '.xls', '.xlsx', '.png', '.jpg', '.zip'),
    max_size_mb=500,
    upload_perm='upgrade.upgrade.add',
    view_perm='upgrade.upgrade.view',
    delete_perm='upgrade.upgrade.add',
)
```

其中 `module` 必须等于物理一级目录名，即文件会落到：

```text
/data/spug/spug_api/media/upgrade/...
```

### 5.2 AttachmentService 接口

公共服务建议提供以下方法：

| 方法 | 说明 |
|---|---|
| `validate(file, config)` | 校验扩展名和大小 |
| `save_file(file, user, config, object_type, object_id)` | 保存到 `/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}` |
| `upload(file, user, module, object_type, object_id, config)` | 上传并写入附件表 |
| `list(user, module, object_type, object_id)` | 查询业务对象附件列表 |
| `download_response(user, attachment_id)` | 下载附件 |
| `preview_file_response(preview_token, attachment_id)` | 给 kkFileView 回调用的文件流接口 |
| `get_preview_url(user, attachment_id)` | 生成 kkFileView 在线预览 URL |
| `soft_delete(user, attachment_id, delete_file=False)` | 软删除附件，可选物理删除 |
| `soft_delete_by_object(user, module, object_type, object_id)` | 业务对象删除时批量软删除附件 |

### 5.3 HTTP 接口

推荐每个模块保留薄接口，原因是当前项目权限体系多使用固定权限装饰器，各模块权限码不同。薄接口只做权限和业务对象校验，文件处理全部转调公共服务。

以 `upgrade` 为例：

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/upgrade/records/<id>/attachments/` | `GET` | 附件列表 |
| `/api/upgrade/records/<id>/attachments/` | `POST` | 上传附件 |
| `/api/upgrade/attachments/<attachment_id>/download/` | `GET` | 下载附件 |
| `/api/upgrade/attachments/<attachment_id>/preview-url/` | `GET` | 获取 kkFileView 预览地址 |
| `/api/upgrade/attachments/<attachment_id>/preview-file/` | `GET` | kkFileView 回调读取文件流 |
| `/api/upgrade/attachments/` | `DELETE` | 删除附件 |

各模块接口可以不同，但前端公共组件通过 props 传入 URL，不硬编码模块路径。

### 5.4 上传流程

```text
前端选择文件
  -> 前端校验大小、扩展名
  -> POST 模块上传接口
  -> 模块接口校验权限和业务对象存在
  -> AttachmentService.validate
  -> 保存到 /data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
  -> 计算 SHA256
  -> 写入附件表
  -> 返回附件元数据
```

### 5.5 下载流程

```text
前端点击下载
  -> GET download 接口
  -> 校验登录态、权限、租户、附件归属
  -> 校验物理路径在 MEDIA_ROOT 内
  -> FileResponse 流式返回
```

下载接口可以继续使用当前项目支持的 `x-token` GET 参数，便于浏览器 `<a>` 标签下载。

## 六、kkFileView 在线预览设计

### 6.1 配置项

项目中已有 kkFileView 配置，附件能力继续复用：

```python
KKFILEVIEW_API_URL = os.environ.get('KKFILEVIEW_API_URL', '')
KKFILEVIEW_SERVER_URL = os.environ.get('KKFILEVIEW_SERVER_URL', '')
```

含义：

| 配置 | 说明 |
|---|---|
| `KKFILEVIEW_API_URL` | 浏览器访问 kkFileView 的地址，例如 `http://your-server:8012` 或 `/kkfileview` |
| `KKFILEVIEW_SERVER_URL` | kkFileView 服务访问 Spug API 的地址，例如 Docker 内网 `http://spug-api:80` |

### 6.2 预览流程

```text
用户点击“预览”
  -> 前端请求 /preview-url/
  -> 后端校验用户权限、租户、附件归属
  -> 后端生成短时效 preview_token
  -> 后端构造 kkFileView 可访问的文件下载 URL
  -> 后端将文件 URL + fullfilename 整体 base64 编码
  -> 返回 kkFileView /onlinePreview?url=<base64> 地址
  -> 前端 iframe/modal 打开预览地址
  -> kkFileView 回调 /preview-file/?preview_token=...
  -> 后端校验 preview_token 后流式返回附件
```

### 6.3 预览 URL 拼装规则

kkFileView 3.x 通常要求 `url` 参数使用 base64 编码。源文件 URL 不带真实文件扩展名时，需要把 `fullfilename` 拼到源文件 URL 中，再整体 base64：

```python
file_url = (
    f'{KKFILEVIEW_SERVER_URL}/api/upgrade/attachments/{attachment_id}/preview-file/'
    f'?preview_token={preview_token}'
    f'&fullfilename={quote(file_name)}'
)
encoded_url = base64.b64encode(file_url.encode('utf-8')).decode('utf-8')
preview_url = f'{KKFILEVIEW_API_URL}/onlinePreview?url={encoded_url}'
```

注意：`fullfilename` 应拼在源文件 URL 上，一起参与 base64 编码，不建议作为 `onlinePreview` 的独立参数。

### 6.4 preview_token 安全设计

不要把用户长期登录 `x-token` 直接暴露给 kkFileView。建议复用或抽取 document 模块现有的短时效预览令牌工具。

令牌建议绑定：

| 绑定项 | 作用 |
|---|---|
| `attachment_id` | 限制令牌只能访问指定附件 |
| `user_id` | 标识发起预览的用户 |
| `tenant_id` | 防止跨租户访问 |
| `module` | 防止跨模块复用 |
| `object_type` / `object_id` | 防止令牌被换目标对象使用 |
| `exp` / timestamp | 短时效，建议 5 分钟 |

校验失败时，`preview-file` 接口返回 403 或业务错误，不返回物理路径。

### 6.5 kkFileView 回调接口

`preview-file` 接口只服务 kkFileView 文件拉取：

1. 接收 `preview_token`。
2. 校验 token 是否过期。
3. 校验 token 中的 `attachment_id` 与 URL 中的附件 ID 一致。
4. 校验附件未软删除。
5. 校验附件租户、模块、业务对象信息与 token 一致。
6. 校验物理文件路径在 `MEDIA_ROOT` 内。
7. 使用 `FileResponse` 返回文件流，`Content-Disposition` 建议为 `inline`。

由于 kkFileView 从服务端回调，来源 IP 可能不是用户浏览器 IP，IP 绑定检查需要排除该接口路径。例如：

```python
IP_CHECK_EXCLUDES = (
    '/document/preview/',
    '/upgrade/attachments/',  # 实际实现时建议精确到 preview-file 路由
)
```

更推荐在中间件中支持精确匹配：

```text
/api/*/attachments/*/preview-file/
```

安全边界仍由 `preview_token` 保证。

### 6.6 可预览类型

kkFileView 能否预览取决于服务版本和部署配置。附件公共组件应按扩展名显示“预览”按钮，但后端必须二次判断。

推荐默认开放：

```text
.doc .docx .xls .xlsx .ppt .pptx .pdf .txt .md .csv
.jpg .jpeg .png .gif .bmp .webp
```

压缩包、安装包、二进制包默认只允许下载，不显示预览：

```text
.zip .rar .7z .exe .msi .deb .rpm .iso
```

如果业务要求“所有附件都走 kkFileView 尝试预览”，也可以保留预览按钮，但后端对不支持类型返回“该文件类型不支持在线预览”。

## 七、前端公共组件设计

### 7.1 组件能力

公共组件建议命名为 `AttachmentManager`，能力包括：

1. 附件列表展示。
2. 上传附件。
3. 下载附件。
4. 删除附件。
5. 在线预览附件。
6. 上传进度、上传中状态、失败提示。
7. 只读模式。
8. 权限控制。
9. 附件数量回调，用于 Tab 标题显示数量。

### 7.2 Props 建议

| Prop | 说明 |
|---|---|
| `module` | 模块英文名 |
| `objectType` | 业务对象类型 |
| `recordId` / `objectId` | 业务对象 ID |
| `listUrl` | 列表接口 |
| `uploadUrl` | 上传接口 |
| `deleteUrl` | 删除接口 |
| `downloadUrlPrefix` | 下载接口前缀 |
| `previewUrlPrefix` | 预览地址接口前缀 |
| `readOnly` | 只读模式 |
| `uploadPerm` | 上传权限码 |
| `deletePerm` | 删除权限码 |
| `previewPerm` | 预览权限码，通常同查看权限 |
| `maxFileSize` | 单文件大小限制 |
| `accept` | 文件选择器允许类型 |
| `previewableExtensions` | 前端显示预览按钮的扩展名列表 |
| `onCountChange` | 附件数量变化回调 |

### 7.3 交互建议

1. 文件名点击默认预览；如果不可预览，则下载。
2. 操作列提供“预览 / 下载 / 删除”。
3. 预览使用 Modal + iframe 打开 kkFileView URL。
4. 获取预览地址失败时提示具体原因，例如“kkFileView 未配置”或“该文件类型不支持在线预览”。
5. 上传成功后局部刷新列表，不刷新整个业务表单。

### 7.4 调用示例

```jsx
<AttachmentManager
  module="upgrade"
  objectType="record"
  recordId={record.id}
  listUrl={`/api/upgrade/records/${record.id}/attachments/`}
  uploadUrl={`/api/upgrade/records/${record.id}/attachments/`}
  deleteUrl="/api/upgrade/attachments/"
  downloadUrlPrefix="/api/upgrade/attachments/"
  previewUrlPrefix="/api/upgrade/attachments/"
  readOnly={viewMode}
  uploadPerm="upgrade.upgrade.add"
  deletePerm="upgrade.upgrade.add"
  previewPerm="upgrade.upgrade.view"
  maxFileSize={500}
  accept=".pdf,.doc,.docx,.xls,.xlsx,.ppt,.pptx,.txt,.md,.csv,.jpg,.jpeg,.png,.zip,.rar,.7z"
  onCountChange={setAttachmentCount}
/>
```

### 7.5 列表页附件数量入口

除详情页/表单页内的附件管理区外，各业务模块列表页应统一支持“附件数量”展示，类似当前无线电执照列表中显示该执照有几个附件的能力。

设计目标：

1. 用户在列表页即可判断某条业务记录是否已有附件。
2. 不需要进入详情页才能发现附件数量。
3. 各模块列表的展示方式统一，减少每个模块单独写附件数量逻辑。

推荐展示方式：

```text
附件列
  无附件：显示 -
  有附件：显示 paperclip 图标 + 数量徽标，例如 📎 3
```

前端建议抽一个轻量展示组件，例如 `AttachmentCountBadge`：

```jsx
<AttachmentCountBadge
  count={record.attachment_count}
  onClick={() => openDetail(record, { activePanel: 'attachments' })}
/>
```

该组件只负责展示数量和触发跳转，不负责上传、下载、删除。真正的附件管理仍由详情页里的 `AttachmentManager` 完成。

后端列表接口建议统一返回：

```json
{
  "id": 88,
  "name": "xxx",
  "attachment_count": 3
}
```

`attachment_count` 应从通用附件表按以下条件统计：

```text
tenant_id = 当前租户
module = 当前模块英文名
object_type = 当前业务对象类型
object_id = 当前业务对象 ID
is_deleted = false
```

无线电执照模块示例：

```text
module = radio_license
object_type = license
object_id = license.id
```

对应物理路径仍是：

```text
/data/spug/spug_api/media/radio_license/{tenant_id}/{yyyyMM}/license_{license_id}/{file_name}
```

交互建议：

1. 点击附件数量时，打开该条业务记录详情页并定位到附件区域。
2. 如果页面使用抽屉或弹窗详情，则默认展开附件面板。
3. 如果当前用户没有查看附件权限，则不显示可点击状态，只显示数量或隐藏附件列。
4. 列表页不要加载完整附件列表，只返回数量，避免列表接口变重。

## 八、模块接入流程

### 8.1 后端接入

1. 在模块常量中定义模块英文名：

```python
ATTACHMENT_MODULE = 'upgrade'
ATTACHMENT_OBJECT_TYPE = 'record'
```

2. 定义附件配置：

```python
UpgradeAttachmentConfig = AttachmentConfig(
    module=ATTACHMENT_MODULE,
    object_type=ATTACHMENT_OBJECT_TYPE,
    allowed_extensions=ATTACHMENT_ALLOWED_EXTENSIONS,
    max_size_mb=500,
)
```

3. 新增模块薄接口，完成权限和业务对象存在性校验。
4. 调用公共 `AttachmentService.upload/list/download_response/get_preview_url/soft_delete`。
5. 业务对象删除时调用 `soft_delete_by_object`。

### 8.2 前端接入

1. 在业务表单或详情页引入 `AttachmentManager`。
2. 传入模块接口 URL、权限码、限制配置。
3. 如果业务对象未保存，隐藏附件区或提示“保存后可上传附件”。

### 8.3 部署接入

1. 确认 API 容器内存在目录：

```text
/data/spug/spug_api/media
```

2. 确认 API 进程对目录有读写权限。
3. 确认该目录持久化挂载，避免容器重建后附件丢失。
4. 配置 kkFileView：

```text
KKFILEVIEW_API_URL=http://your-server:8012
KKFILEVIEW_SERVER_URL=http://spug-api:80
```

5. 确认 kkFileView 容器可以访问 `KKFILEVIEW_SERVER_URL`。

## 九、当前代码改造建议

当前项目已经有一些可复用基础：

| 现有能力 | 建议 |
|---|---|
| `spug_api/apps/evidence/attachment_service.py` | 继续作为公共附件服务底座，但保存路径要强制调整为 `{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}` |

| `spug_api/spug/settings.py` | `MEDIA_ROOT` 支持生产默认 `/data/spug/spug_api/media` 或环境变量覆盖 |

### 9.1 开发阶段处理原则

当前仍处于开发阶段，尚未产生需要保留的真实附件数据，因此本次公共化改造**不需要考虑历史附件文件迁移、旧物理路径兼容、旧附件下载兼容**。

处理原则：

1. 以新公共附件方案为准，直接调整表结构、接口、组件和物理路径。
2. 已存在的旧附件实现只作为参考，不作为兼容边界。
3. 旧附件表、旧附件模型、旧附件组件、旧附件接口如与公共方案冲突，应删除或改造，不保留双轨实现。
4. 不需要编写历史文件搬迁脚本。
5. 不需要保留旧上传路径或旧附件 URL 的兼容逻辑。
6. 不需要为了兼容旧数据保留旧字段；字段设计以公共附件模型当前需要为准。
7. 如果旧代码里有半成品接入痕迹，应清理或改造为标准公共附件接入方式。
8. Django migration 可以按开发阶段策略整理：若数据库尚未正式投产，可删除旧附件表相关迁移或新增删除迁移，最终保证模型与数据库结构一致即可。

公共化改造时允许直接处理的对象包括：

| 类型 | 处理方式 |
|---|---|
| 独立附件表 | 删除或停止使用，统一迁移到通用附件表设计 |
| 独立附件模型 | 删除或改为业务扩展模型，不再保存重复文件字段 |
| 独立前端附件组件 | 删除或改造成调用 `AttachmentManager` |
| 独立上传/下载/删除接口 | 改造成模块薄接口，转调 `AttachmentService` |
| 旧物理路径常量 | 改为 `{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}` |
| 旧权限码 | 可保留业务权限语义，但接入公共组件 props 和模块薄接口 |

### 9.2 无线电执照附件改造建议

无线电执照当前是独立附件实现：前端使用 `radioLicense/AttachmentList.js`，后端使用 `RadioLicenseAttachment` 独立表和 `radio_license/views.py` 中的独立上传、下载、删除逻辑。由于开发阶段没有真实附件数据，建议直接迁移到公共附件能力。

目标结构：

```text
无线电执照页面
  -> 公共 AttachmentManager
     -> radio_license 薄接口
        -> AttachmentService
           -> EvidenceAttachment / Attachment 通用表
           -> /data/spug/spug_api/media/radio_license/{tenant_id}/{yyyyMM}/license_{license_id}/{file_name}
```

改造建议：

1. 前端废弃 `radioLicense/AttachmentList.js`，改为直接使用公共 `AttachmentManager`。
2. 后端废弃 `RadioLicenseAttachment` 独立附件表思路，附件记录写入通用附件表。
3. `radio_license` 模块只保留薄接口，负责执照存在性校验、租户校验、权限校验，然后转调 `AttachmentService`。
4. `attachment_type` 如仍有业务价值，可优先作为公共附件的扩展元数据处理；如果暂时不需要，可不保留。
5. 新上传文件统一保存到：

```text
/data/spug/spug_api/media/radio_license/{tenant_id}/{yyyyMM}/license_{license_id}/{file_name}
```

示例：

```text
/data/spug/spug_api/media/radio_license/1/202607/license_88/执照扫描件.pdf
```

因为没有历史附件数据，本模块不需要保留旧路径：

```text
radio_license/attachments/{yyyyMM}/{file_name}
```

也不需要从 `RadioLicenseAttachment` 向通用附件表迁移数据。

### 9.3 无线电执照提醒功能保留与删除边界

无线电执照模块当前存在两类提醒能力：

1. 到期提醒弹窗：全局组件实时查询即将到期/已过期执照，并弹出提醒。
2. 主菜单红色数字：左侧菜单显示即将到期/已过期执照数量。

这两类能力需要保留。

保留项：

| 能力 | 保留原因 | 说明 |
|---|---|---|
| 到期提醒弹窗 | 用户需要及时知道执照即将到期或已过期 | 保留实时查询接口和全局弹窗组件 |
| `LicenseReminderAck` | 用于记录用户对某张执照当前有效期周期的“已处理”确认 | 保留，避免同一执照在同一有效期内反复弹窗 |
| 主菜单红色数字 | 用于在菜单上提示待关注执照数量 | 保留 badge/红点统计接口 |

删除项：

| 能力 | 处理方式 | 说明 |
|---|---|---|
| `RadioLicenseReminder` 历史日志表 | 删除或停用 | 不再保留“提醒记录”历史日志 |
| `ReminderList` 前端提醒记录列表 | 删除 | 详情页不再展示“提醒记录”表格 |
| `/reminders/` 提醒历史列表接口 | 删除 | 不再提供历史提醒查询 |
| `/reminders/handle/` 历史提醒已读/已处理接口 | 删除 | “已处理”统一走 `LicenseReminderAck` |
| 详情页“提醒记录”区块 | 删除 | 保留到期弹窗和菜单红色数字即可 |

保留后的提醒模型：

```text
定时任务 / 实时查询
  -> 更新或判断 RadioLicense.status、valid_to、days_left
  -> ReminderPopupView 实时返回当前用户负责的到期执照
  -> 前端 ReminderNotification 弹窗提示
  -> 用户点击“已处理”
  -> 写入 LicenseReminderAck
  -> 同一 license_id + user_id + ack_valid_to 周期内不再弹窗
```

主菜单红色数字仍按实时数据统计，不依赖 `RadioLicenseReminder` 历史日志：

```text
当前租户下 valid_to <= today + 阈值天数的执照数量
或按 expiring / expired 状态统计
```

需要重点调整：

1. `AttachmentConfig.upload_dir` 不再使用通用 `attachments`，而是直接使用模块英文名。
2. `AttachmentService.save_file` 默认路径改为：

```text
{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
```

3. `AttachmentManager` 新增在线预览入口。
4. 每个模块新增 `preview-url` 和 `preview-file` 接口。
5. 预览接口统一使用短时效 `preview_token`，不使用长期 `x-token`。

## 十、安全与边界

### 10.1 权限

1. 列表、下载、预览使用模块查看权限。
2. 上传、删除使用模块编辑或新增权限。
3. 后端必须校验业务对象存在，并且属于当前租户。
4. 不能只依赖前端隐藏按钮。

### 10.2 文件类型

1. 前端 `accept` 只做体验优化。
2. 后端必须按扩展名白名单校验。
3. 如需更强安全，可增加 MIME 或魔数检测，但不要只相信浏览器传来的 `content_type`。

### 10.3 大文件

1. 上传使用 `file.chunks()` 流式写入。
2. 下载和预览使用 `FileResponse` 流式返回。
3. 前后端都设置单文件大小上限。
4. 超过 500MB 或需要断点续传时，再考虑复用 document 模块的分片上传能力。

### 10.4 删除策略

默认建议软删除数据库记录，不立即删除物理文件，便于审计和恢复。

如果业务要求节省磁盘，可以增加 `delete_file=True` 策略，但必须先校验物理路径安全，再删除物理文件，最后软删除数据库记录。

## 十一、验收标准

1. 任一模块上传附件后，数据库记录中的 `module` 等于模块英文名。
2. 物理文件真实路径符合：

```text
/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}
```

3. 附件列表能显示文件名、大小、上传人、上传时间。
4. 下载接口能正确下载中文文件名附件。
5. 支持类型的文件点击“预览”后能打开 kkFileView。
6. kkFileView 回调文件流时使用短时效 `preview_token`，不暴露长期登录 token。
7. 用户不能访问其他租户、其他模块、其他业务对象的附件。
8. 删除业务对象时，其附件被联动软删除。
9. 不支持预览的文件给出明确提示，不影响下载。
10. 未配置 kkFileView 时，上传、下载、删除仍可正常使用，预览提示管理员配置服务。

## 十二、建议实施顺序

1. 调整公共 `AttachmentService` 的路径规则，确保落盘到 `/data/spug/spug_api/media/{module}/{tenant_id}/{yyyyMM}/{object_type}_{object_id}/{file_name}`。
2. 抽取通用 preview token 和 kkFileView URL 生成工具。
3. 为一个模块先接入完整链路：上传、列表、下载、删除、预览。
4. 扩展 `AttachmentManager` 的预览能力。
5. 将第二个模块接入，验证配置化程度是否足够。
6. 再批量推广到其他模块。

先用一个模块打通完整闭环，再扩展到多个模块，能避免公共组件过早抽象，又能保证后续接入成本低。
