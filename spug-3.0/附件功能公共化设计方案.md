# 附件功能公共化设计方案

> 建立日期：2026-06-30
> 状态：已实施（upgrade 模块已接入，radio_license 保持独立实现）

## 一、背景与问题

### 1.1 历史现状

项目原有三套附件实现并存，相互割裂：

| 位置 | 实现 | 完整度 | 问题 |
|---|---|---|---|
| `apps/evidence/models.py` 的 `EvidenceAttachment` | 通用表（`module+object_type+object_id` 多态关联，SHA256 + 软删除） | 表结构最完整 | 有表无 HTTP 接口，只是服务库 |
| `apps/radio_license` 的 `RadioLicenseAttachment` | 独立表 + 完整视图（list/upload/download/delete） | 中等 | 与 evidence 表字段 90% 重复，又是一套 |
| `apps/upgrade` 的旧 `AttachmentService` | 只返回 URL 字符串 | 最简陋 | 无独立附件表、无哈希、无软删除、无审计；且 `ATTACHMENT_ALLOWED_TYPES` 只允许图片，升级包根本传不上去 |

前端同样零散：`radioLicense/AttachmentList.js`、`runlog/Form.js`、`upgrade/Form_old.js` 各写各的，没有公共附件组件。

### 1.2 核心问题

"前端公共组件 + 后端各建表"是**错误的中间态**——前端以为后端统一了，后端其实没统一。每新增一个模块就要复制一份附件表 + 一份 service，技术债持续累积。

## 二、设计目标

1. **后端统一底座**：附件数据集中存一张通用表，各模块通过 `module/object_type/object_id` 关联
2. **前端公共组件**：一处实现，各模块调用，UI 交互统一
3. **向后兼容**：radio_license 已有独立实现保持不动，不破坏现有功能
4. **各模块自治**：权限码、文件类型限制、业务对象存在性校验由各模块自己负责

## 三、架构设计

### 3.1 整体架构

```
┌─────────────────────────────────────────────────┐
│  前端 components/AttachmentManager.js（公共）    │
│  - 上传/下载/删除/列表 UI                        │
│  - 路径、权限码全参数化                          │
└──────────────────┬──────────────────────────────┘
                   │ HTTP
┌──────────────────▼──────────────────────────────┐
│  各模块桥接视图（如 upgrade/views/upload.py）    │
│  职责：                                          │
│  1. 校验业务对象存在（UpgradeRecord 是否存在）   │
│  2. 校验模块权限码（upgrade.upgrade.view/.add）  │
│  3. 转调 evidence.AttachmentService              │
└──────────────────┬──────────────────────────────┘
                   │ 函数调用
┌──────────────────▼──────────────────────────────┐
│  evidence/attachment_service.py（通用服务）      │
│  - upload / list / download_response             │
│  - soft_delete / soft_delete_by_object           │
│  - AttachmentConfig 配置类（各模块可自定义）     │
└──────────────────┬──────────────────────────────┘
                   │ ORM
┌──────────────────▼──────────────────────────────┐
│  EvidenceAttachment 表（通用，多态关联）         │
│  tdyw_evidence_attachments                       │
│  - module + object_type + object_id              │
│  - file_name / file_path / file_size / file_ext  │
│  - file_hash_sha256                              │
│  - uploaded_by_id / uploaded_by_name             │
│  - is_deleted / deleted_by_id / deleted_at       │
└─────────────────────────────────────────────────┘
```

### 3.2 关键设计决策

#### 决策 1：复用 EvidenceAttachment 通用表，不在各模块建独立附件表

**理由**：`EvidenceAttachment` 本就是为跨业务模块共用设计，表注释明说"各业务模块可直接复用本表"。字段完整（SHA256、软删除、上传人快照、租户隔离），无需新建。

**关联方式**：多态关联
- `module`：业务模块标识（如 `upgrade`、`device`、`interference`）
- `object_type`：对象类型（如 `record`、`license`、`fault`）
- `object_id`：业务对象 ID（字符串存储，兼容各种 ID 类型）

#### 决策 2：evidence 只补 service，不补 views/urls

**理由**：evidence 是通用底座，**无法感知各模块的权限码**。比如 upgrade 用 `upgrade.upgrade.view`，radio_license 用 `radio_license.attachment.upload`，device 可能用 `device.device.view`。如果 evidence 提供通用 HTTP 视图，权限码无法统一处理。

**方案**：各模块写薄薄的桥接视图，负责：
1. 校验业务对象存在（evidence 不知道 upgrade 的 UpgradeRecord 是否存在）
2. 校验模块权限码（`@auth('upgrade.upgrade.view')`）
3. 转调 `evidence.AttachmentService` 完成实际文件操作

#### 决策 3：radio_license 保持独立实现

**理由**：
- radio_license 的 `RadioLicenseAttachment` 有 `attachment_type` 业务字段（license/permit/approval/other），迁到通用表会丢语义
- 向后兼容，增量改进 > 大爆炸式重写
- radio_license 已有完整证据事件写入逻辑，强行迁移风险大于收益

#### 决策 4：普通上传兜底，暂不复用 document 模块的分片上传体系

**理由**：
- 升级包大小不确定，先用普通上传 + 长超时（10 分钟）+ 500MB 限制兜底
- 分片上传体系复杂（状态机、断点续传、合并轮询），YAGNI 原则下不过早引入
- 未来如确有大文件需求，可再接入 document 模块的分片上传

## 四、后端实现

### 4.1 通用服务：`apps/evidence/attachment_service.py`

#### AttachmentConfig 配置类

各模块可自定义实例，控制文件类型、大小上限、存储子目录：

```python
@dataclass
class AttachmentConfig:
    allowed_extensions: tuple = ('.zip', '.rar', '.7z', '.exe', '.msi', ...)
    max_size_mb: int = 500
    upload_dir: str = 'attachments'  # MEDIA_ROOT 下的子目录

DefaultAttachmentConfig = AttachmentConfig()
```

#### AttachmentService 核心接口

| 方法 | 用途 | 关键逻辑 |
|---|---|---|
| `validate(file, config)` | 校验文件类型与大小 | 扩展名白名单（比 content_type 更可靠） |
| `save_file(file, config)` | 保存文件到磁盘 | 文件名清洗防路径穿越 + 重名自动加序号 |
| `upload(file, user, module, object_type, object_id, config)` | 上传并入库 | 落盘 + 计算 SHA256 + 写 EvidenceAttachment |
| `list(user, module, object_type, object_id)` | 获取附件列表 | 租户过滤 + 软删除过滤 + 时间倒序 |
| `download_response(user, attachment_id)` | 获取下载响应 | 路径安全检查 + 流式下载 + 中文文件名编码 |
| `soft_delete(user, attachment_id, reason)` | 软删除单个附件 | 标记 is_deleted，保留物理文件作为证据 |
| `soft_delete_by_object(user, module, object_type, object_id, reason)` | 批量软删除某业务对象下所有附件 | 用于业务对象删除时联动 |

#### 安全措施

| 风险 | 防护措施 |
|---|---|
| 路径穿越攻击 | `os.path.basename` + 替换 `..` `/` `\` `\x00`；下载时 `os.path.realpath` 校验是否在 MEDIA_ROOT 内 |
| 文件名冲突 | 重名自动加序号：`xxx.zip` → `xxx_1.zip` |
| 大文件内存占用 | `file.chunks()` 流式写入；SHA256 流式读取（8KB 缓冲） |
| 越权访问 | 所有查询走 `apply_tenant_filter`；下载/删除额外校验关联业务对象存在 |
| 中文文件名乱码 | `Content-Disposition` 同时提供 `filename="..."` 和 `filename*=UTF-8''...` |

### 4.2 桥接视图模板：`apps/upgrade/views/upload.py`

各模块复制此文件作为模板，修改 3 处即可：

```python
# 1. 模块标识
MODULE = 'upgrade'
OBJECT_TYPE = 'record'

# 2. 附件配置（复用各模块 constants.py 的配置）
UpgradeAttachmentConfig = AttachmentConfig(
    allowed_extensions=tuple(ATTACHMENT_ALLOWED_EXTENSIONS),
    max_size_mb=ATTACHMENT_MAX_SIZE_MB,
    upload_dir=ATTACHMENT_UPLOAD_DIR,
)

# 3. 权限码（装饰器）
@auth('upgrade.upgrade.view')  # 各模块替换为自己的权限码
def get(self, request, record_id):
    ...

# 4. 业务对象存在性校验（各模块实现自己的 _get_record）
def _get_record(record_id, user):
    return apply_tenant_filter(
        UpgradeRecord.objects.filter(pk=record_id), user
    ).first()
```

#### 视图清单

| 视图 | 方法 | 权限 | 路由 |
|---|---|---|---|
| `AttachmentListView` | GET / POST | `.view` / `.edit` | `records/<int:record_id>/attachments/` |
| `AttachmentDownloadView` | GET | `.view` | `attachments/<int:pk>/download/` |
| `AttachmentDeleteView` | DELETE | `.edit` | `attachments/` |
| `AttachmentUploadView`（旧版兼容） | POST | `.add` | `upload/` |

### 4.3 业务对象删除联动

业务对象删除时，需联动软删除其下所有附件。在 `record_service.py` 的 `delete_record` 中：

```python
@staticmethod
def delete_record(record_id, user):
    from apps.evidence.attachment_service import AttachmentService
    ...
    with transaction.atomic():
        # 软删除关联附件（evidence 通用表，通过 module/object_type/object_id 关联）
        AttachmentService.soft_delete_by_object(
            user=user,
            module='upgrade',
            object_type='record',
            object_id=record_id,
            reason='升级表单已删除',
        )
        record.delete()
```

## 五、前端实现

### 5.1 公共组件：`components/AttachmentManager.js`

#### 设计原则

- **路径全参数化**：`listUrl`/`uploadUrl`/`deleteUrl`/`downloadUrlPrefix` 由调用方传入，组件不硬编码任何模块
- **权限码参数化**：`uploadPerm`/`deletePerm` 由调用方传入，复用项目 `hasPermission` 体系
- **下载鉴权**：走 `x-token` GET 参数（项目中间件支持）
- **大文件兜底**：`timeout: 600000`（10 分钟）
- **前端预校验**：上传前校验文件大小，避免大文件传到后端才被拒

#### Props 清单

| Prop | 类型 | 说明 |
|---|---|---|
| `module` | string | 业务模块标识（用于日志） |
| `recordId` | number/string | 业务对象 ID（未创建时传空，组件自动隐藏） |
| `listUrl` | string | 列表接口 URL |
| `uploadUrl` | string | 上传接口 URL |
| `deleteUrl` | string | 删除接口 URL（`?id=` 拼参） |
| `downloadUrlPrefix` | string | 下载接口前缀（拼 `${id}/download/?x-token=`） |
| `readOnly` | bool | 只读模式隐藏上传/删除 |
| `uploadPerm` | string | 上传权限码（空则不校验） |
| `deletePerm` | string | 删除权限码（空则不校验） |
| `maxFileSize` | number | 最大文件大小（MB），前端预校验 |
| `accept` | string | 文件选择器 accept 属性 |
| `onCountChange` | func | 附件数量变化回调（用于 Tab 标题显示计数） |

#### 字段约定

组件默认展示以下字段（与 evidence 表对齐）：

| 前端字段 | 后端字段 | 说明 |
|---|---|---|
| `file_name` | `file_name` | 原始文件名 |
| `file_size` | `file_size` | 文件大小（字节） |
| `uploaded_by_name` | `uploaded_by_name` | 上传人姓名快照 |
| `created_at` | `uploaded_at` | 上传时间（service.list 中映射） |

### 5.2 调用示例

```jsx
import { AttachmentManager } from 'components';

<TabPane tab={`附件 (${attachmentCount})`} key="attachments">
  <AttachmentManager
    module="upgrade"
    recordId={store.record.id}
    listUrl={`/api/upgrade/records/${store.record.id}/attachments/`}
    uploadUrl={`/api/upgrade/records/${store.record.id}/attachments/`}
    deleteUrl="/api/upgrade/attachments/"
    downloadUrlPrefix="/api/upgrade/attachments/"
    readOnly={!hasPermission('upgrade.upgrade.add')}
    uploadPerm="upgrade.upgrade.add"
    deletePerm="upgrade.upgrade.add"
    maxFileSize={500}
    onCountChange={setAttachmentCount}
  />
</TabPane>
```

## 八、后续模块加附件的标准流程

### 8.1 后端（4 步）

1. **复制桥接视图**：以 `apps/upgrade/views/upload.py` 为模板，复制到新模块
2. **修改 3 处**：
   - `MODULE` / `OBJECT_TYPE` 改为新模块标识
   - `XxxAttachmentConfig = AttachmentConfig(...)` 复用新模块 constants 配置
   - 权限码装饰器改为新模块权限码
3. **实现业务对象存在性校验**：`_get_record` 改为查询新模块的业务模型
4. **业务对象删除联动**：在新模块的 delete_service 中调用 `AttachmentService.soft_delete_by_object(module=..., object_type=..., object_id=...)`

**无需新建附件表、无需新建 service**——全部复用 evidence 通用底座。

### 8.2 前端（1 步）

```jsx
import { AttachmentManager } from 'components';

<AttachmentManager
  module="新模块标识"
  recordId={业务对象ID}
  listUrl={`/api/新模块/records/${id}/attachments/`}
  uploadUrl={`/api/新模块/records/${id}/attachments/`}
  deleteUrl="/api/新模块/attachments/"
  downloadUrlPrefix="/api/新模块/attachments/"
  readOnly={只读模式}
  uploadPerm="新模块.权限码"
  deletePerm="新模块.权限码"
  maxFileSize={500}
  onCountChange={setCount}
/>
```

### 8.3 数据库

无需新建表、无需新建 migration——附件数据写入 `tdyw_evidence_attachments`，通过 `module/object_type/object_id` 关联。

## 九、技术要点与踩坑记录

### 9.1 migration 里 human_datetime 的引用路径

migration 文件里引用 `human_datetime` 的正确路径是 `libs.utils.human_datetime`，不是 `libs.mixins.human_datetime`。

**原因**：`libs/mixins.py` 只有 `from .utils import json_response`，没有 re-export `human_datetime`。但 `libs/__init__.py` 的 `from .utils import *` 会把 `human_datetime` 导入 `libs` 命名空间，所以 `from libs import human_datetime` 可以工作，但 `libs.mixins.human_datetime` 不行。

### 9.2 AlterModelOptions 的参数名

Django 2.2 的 `AlterModelOptions` 第一个参数是 `name`，不是 `model_name`。

```python
# ✗ 错误
migrations.AlterModelOptions(model_name='upgradetemplate', options={...})

# ✓ 正确
migrations.AlterModelOptions(name='upgradetemplate', options={...})
```

### 9.3 PowerShell 下 Docker 命令的引号问题

Windows PowerShell 下 `docker exec bash -c "..."` 内层双引号会触发 EOF 错误，必须用单引号：

```powershell
# ✗ 错误（PowerShell 会破坏内层双引号）
docker exec tdyw-test bash -c "python -c 'import django'"

# ✓ 正确
docker exec tdyw-test bash -c 'python manage.py shell -c "..."'
```

复杂脚本建议写到临时 .py 文件，`docker exec` 执行文件，避免引号嵌套问题。

### 9.4 下载鉴权方式

下载接口不能用 `X-Token` 请求头（浏览器 `<a>` 标签点击无法设置请求头），改用 `x-token` GET 参数：

```js
const url = `${downloadUrlPrefix}${att.id}/download/?x-token=${X_TOKEN}`;
```

项目中间件已支持此鉴权方式（与 radio_license 模块一致）。
