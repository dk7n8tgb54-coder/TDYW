# 账号表单可分配角色下拉优化方案

## 背景

角色委派权限修复后，后端已经对 `role_ids` 做了强校验，普通管理员即使构造请求提交不可分配角色，也会被拒绝。

但当前还有一个体验问题：普通管理员在创建或编辑子账号时，角色下拉框仍可能看到全部角色，包括：

- 超级管理员创建的平台级角色。
- 系统角色。
- 全局管理员角色。
- 其他租户角色。
- 当前账号无权分配的角色。

这些角色虽然最终会被后端拒绝，但展示在下拉框里会造成混淆。用户会以为自己可以选择，提交后又失败，体验不清晰，也容易让管理员误解权限边界。

## 修复目标

账号表单里的“角色”下拉框只展示当前操作者可以分配给目标账号的角色。

安全边界仍以后端 `validate_assignable_role_ids()` 为准，前端过滤只用于提升体验，不能替代后端校验。

## 关键概念区分

本次补充修复需要区分两个列表：

1. 角色管理列表

   表示当前用户可以查看或管理哪些角色。

2. 账号表单角色下拉

   表示当前用户可以把哪些角色分配给目标账号。

这两个概念不应长期混用。角色管理页可以有自己的列表逻辑，账号表单应该使用“可分配角色”逻辑。

## 推荐方案

新增一个专用接口：

```text
GET /api/account/role/assignable/
```

该接口只服务于账号创建/编辑表单中的角色下拉。

### 请求参数

```text
tenant_id 可选
```

用途：

- 超级管理员创建或编辑账号时，账号可能选择不同租户，因此需要根据目标账号租户返回可分配角色。
- 普通管理员不需要传 `tenant_id`，即使传了也应被后端忽略。

示例：

```text
GET /api/account/role/assignable/
GET /api/account/role/assignable/?tenant_id=tenant_a
```

## 返回规则

### 普通管理员

只返回当前管理员可分配的普通租户角色：

```python
Role.objects.filter(
    tenant_id=request.user.tenant_id,
    is_system=False,
    is_global_admin=False,
)
```

普通管理员不可看到：

- 平台级角色。
- 系统角色。
- 全局管理员角色。
- 其他租户角色。

### 超级管理员

超级管理员需要根据目标账号租户返回角色。

如果传入 `tenant_id`：

```text
返回：
- 平台级角色 tenant_id is null
- 全局管理员角色
- tenant_id == 目标 tenant_id 的租户角色
```

如果没有传入 `tenant_id`：

```text
返回：
- 平台级角色 tenant_id is null
- 全局管理员角色
```

不建议在未选择目标租户时返回全部租户角色，否则超管创建账号时仍可能误选其他租户角色。

## 后端实现建议

在 `role_permissions.py` 中增加：

```python
def get_assignable_roles_for_target(operator, target_tenant_id=None):
    from django.db.models import Q
    from apps.account.models import Role

    if not operator.is_supper:
        return Role.objects.filter(
            tenant_id=operator.tenant_id,
            is_system=False,
            is_global_admin=False,
        )

    queryset = Role.objects.filter(
        Q(tenant_id__isnull=True) | Q(is_global_admin=True)
    )

    if target_tenant_id:
        queryset = queryset | Role.objects.filter(tenant_id=target_tenant_id)

    return queryset.distinct()
```

注意：

- 普通管理员传入的 `target_tenant_id` 不参与计算。
- 超级管理员未选择租户时，不返回所有租户角色。
- 全局管理员角色虽然通常也是平台级角色，但保留 `is_global_admin=True` 条件可以兼容历史数据。

## 接口实现建议

可以在 `RoleView` 中增加静态方法或单独 View：

```python
@staticmethod
def assignable(request):
    target_tenant_id = request.GET.get('tenant_id')
    roles = get_assignable_roles_for_target(request.user, target_tenant_id)
    return json_response(roles)
```

并在 `spug_api/apps/account/urls.py` 中新增路由：

```python
re_path(r'^role/assignable/$', RoleView.assignable),
```

需要确保该接口仍受账号/角色相关权限保护。建议至少要求用户具备账号查看或账号新增/编辑权限。若当前路由机制统一走 `AdminView.dispatch`，单独静态方法需要注意不要绕过权限校验。

更稳的做法是新增一个 `AssignableRoleView(AdminView)`：

```python
class AssignableRoleView(AdminView):
    PERM_MAP = {
        'GET': 'system.account.view',
    }

    def get(self, request):
        target_tenant_id = request.GET.get('tenant_id')
        roles = get_assignable_roles_for_target(request.user, target_tenant_id)
        return json_response(roles)
```

然后配置：

```python
re_path(r'^role/assignable/$', AssignableRoleView.as_view()),
```

## 前端实现建议

修改账号表单：

```text
spug_web/src/pages/system/account/Form.js
```

账号表单角色下拉不要再直接使用角色管理页的 `rStore.records`，改为单独维护 `assignableRoles` 状态。

普通管理员：

```text
打开账号表单时调用：
GET /api/account/role/assignable/
```

超级管理员：

```text
打开账号表单时，如果已有 tenant_id：
GET /api/account/role/assignable/?tenant_id=<tenant_id>

新建账号时，如果用户选择或切换 tenant_id：
重新拉取可分配角色。
```

当超级管理员切换目标租户后：

- 重新请求可分配角色。
- 清空当前已选 `role_ids`，或过滤掉不再可分配的角色。
- 避免保留上一个租户的角色选择。

## 前端交互建议

账号表单角色下拉的提示文案建议调整为：

```text
仅显示当前账号可分配给该用户的角色
```

超级管理员未选择租户时，角色下拉可展示平台级角色和全局管理员角色，也可以提示：

```text
选择所属租户后可分配该租户角色
```

普通管理员不需要看到任何平台级、系统、全局、其他租户角色。

## 为什么不只在前端过滤

不建议只在前端按 `tenant_id/is_system/is_global_admin` 过滤，因为：

- 前端数据可能来自缓存。
- 用户可以直接构造请求。
- 超级管理员目标租户切换时，前端容易漏处理。
- 后端已经有统一权限逻辑，应复用后端结果。

正确做法是：

```text
后端提供可分配角色接口
前端使用该接口展示
用户提交时后端再次校验 role_ids
```

## 与现有后端校验的关系

该接口只是体验优化，不替代以下已有安全校验：

- `validate_assignable_role_ids()`
- 普通管理员只可分配本租户普通角色。
- 超级管理员不可把其他租户角色分配给目标租户账号。
- 不存在的角色 ID 必须被拒绝。
- 全局管理员角色必须保持平台级系统角色不变量。

即使前端展示正确，提交时仍必须保留后端校验。

## 推荐测试用例

### 普通管理员

1. 打开新建账号表单，只看到本租户普通角色。
2. 不看到平台级角色。
3. 不看到系统角色。
4. 不看到全局管理员角色。
5. 不看到其他租户角色。
6. 直接构造请求提交不可分配角色，后端仍拒绝。

### 超级管理员

1. 未选择目标租户时，只看到平台级角色和全局管理员角色。
2. 选择租户 A 后，看到平台级角色、全局管理员角色、租户 A 角色。
3. 切换到租户 B 后，租户 A 角色不再显示。
4. 切换租户后，已选的租户 A 角色被清空或过滤。
5. 直接构造请求把租户 A 角色分配给租户 B 用户，后端仍拒绝。

## 结论

普通管理员账号表单下拉展示全部角色会造成明显混淆，建议修复。

推荐新增 `GET /api/account/role/assignable/` 专用接口，让账号表单只展示当前操作者对目标账号可分配的角色。这样既不影响角色管理页，又能让账号创建/编辑体验和后端权限边界保持一致。
