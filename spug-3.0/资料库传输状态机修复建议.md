# 资料库传输列表状态机修复建议

更新时间：2026-06-27

## 背景

资料库上传/传输列表目前同时存在两套状态：

- 前端上传项状态：`waiting`、`calculating`、`uploading`、`paused`、`merging`、`completed`、`error`、`cancelled`
- 后端传输记录状态：`PENDING`、`UPLOADING`、`DOWNLOADING`、`PAUSED`、`MERGING`、`COMPLETED`、`FAILED`、`CANCELED`

前端主要通过 `UploadStateMachine` 管状态流转，但部分单个操作和批量操作仍会绕过状态机直接改 `item.status`。这会造成传输列表显示、按钮可用性、后端传输记录状态三者不一致。

## 刚才已修复的内容

### 1. 批量取消显示状态从 `error` 改为 `cancelled`

文件：

- `spug_web/src/pages/document/stores/upload/core/controls/QueueOperationController.js`

原问题：

- `cancelAll()` 批量取消时直接把前端任务写成：
  - `status: 'error'`
  - `error: '已取消'`
- 但状态机正式的取消终态是 `cancelled`，后端对应 `CANCELED`。
- 这会让用户主动取消的任务显示为“上传失败”，并且失败/取消语义混在一起。

已改为：

- `status: 'cancelled'`
- `error: '已取消'`
- `errorCode: 'CANCELLED'`
- `percent: 0`

预期效果：

- 用户主动取消进入“已取消”语义。
- 传输列表失败 Tab 仍可展示取消项，但状态文本不再误导为“上传失败”。

### 2. 合并中任务不再显示“暂停”按钮

文件：

- `spug_web/src/pages/document/components/TransferItem.js`

原问题：

- UI 中 `canPause` 包含 `merging`。
- 但 `UploadStateMachine` 的 `merging` 状态没有 `PAUSE` 转换。
- 用户点“暂停”会无效，体验像按钮坏了。

已改为：

- `canPause` 只包含 `waiting`、`calculating`、`uploading`。

预期效果：

- 合并中只允许取消，不再暴露无效暂停操作。

### 3. 虚拟传输列表的“全部暂停”按钮排除不可暂停任务

文件：

- `spug_web/src/pages/document/components/VirtualTransferList.js`

原问题：

- 虚拟列表用 `uploadingList.length - pausedCount` 判断是否显示“全部暂停”。
- 如果列表里只有 `merging`，仍会显示“全部暂停”，但批量暂停实际会跳过 `merging`。

已改为：

- 通过 `ACTIVE_STATUSES` + `PENDING_STATUSES` 计算可暂停数量。
- `merging` 虽然仍在 active 状态集合中，但后续建议还需要进一步拆分“占用槽位状态”和“可暂停状态”，见下文。

注意：

- 当前修复降低了误显示概率，但 `ACTIVE_STATUSES` 仍包含 `merging`，语义不够精准，建议继续抽出专门的 `PAUSEABLE_STATUSES`。

### 4. 修复终态同步后端可能被提前跳过的问题

文件：

- `spug_web/src/pages/document/stores/upload/core/sync/StatusSynchronizer.js`

原问题：

- `syncStateToBackend()` 中如果发现 `item.status` 已经是终态，会直接 return。
- 状态机进入 `completed`、`error`、`cancelled` 时，`item.status` 可能已经被 entry/action 更新为终态。
- 结果是后端状态同步可能被提前跳过，后端还停在 `UPLOADING` 或 `MERGING`。

已改为：

- 如果当前 item 已是终态，只阻止“非终态回退同步”。
- 终态自身仍允许同步到后端：
  - `completed` -> `COMPLETED`
  - `error` -> `FAILED`
  - `cancelled` -> `CANCELED`

预期效果：

- 前端进入终态后，后端传输记录也能正确落到终态。
- 避免刷新页面后任务又被后端旧状态拉回“上传中/合并中”。

### 5. 已补充的测试草稿

文件：

- `spug_web/src/pages/document/stores/upload/core/__tests__/StateMachineManager.test.js`
- `spug_web/src/pages/document/stores/upload/core/__tests__/StatusSynchronizer.test.js`

已补充覆盖：

- 批量取消后状态应为 `cancelled`。
- 批量暂停应跳过 `merging`。
- `StatusSynchronizer` 对 `completed`、`cancelled` 终态仍会同步后端。
- 已终态时不允许同步回非终态。

注意：

- 测试命令刚开始执行时被中断，还没有完成验证。

## 仍建议继续修复的内容

### P0. 抽出统一的前端状态集合，避免状态含义混用

当前 `upload-core-constants.js` 里：

- `ACTIVE_STATUSES` 包含 `calculating`、`uploading`、`merging`
- 但业务上：
  - 并发槽位只应统计 `calculating`、`uploading`
  - 可暂停状态应是 `waiting`、`calculating`、`uploading`
  - 进行中展示可包含 `waiting`、`calculating`、`uploading`、`paused`、`merging`

建议新增：

```js
export const SLOT_OCCUPYING_STATUSES = Object.freeze([
  UPLOAD_STATUS.CALCULATING,
  UPLOAD_STATUS.UPLOADING,
]);

export const PAUSEABLE_STATUSES = Object.freeze([
  UPLOAD_STATUS.WAITING,
  UPLOAD_STATUS.CALCULATING,
  UPLOAD_STATUS.UPLOADING,
]);

export const DISPLAY_UPLOADING_STATUSES = Object.freeze([
  UPLOAD_STATUS.WAITING,
  UPLOAD_STATUS.CALCULATING,
  UPLOAD_STATUS.UPLOADING,
  UPLOAD_STATUS.PAUSED,
  UPLOAD_STATUS.MERGING,
]);
```

然后替换各处硬编码数组，重点检查：

- `TransferItem.js`
- `TransferList.js`
- `VirtualTransferList.js`
- `UploadPanel.js`
- `UploadCoreStore.activeCount`
- `UploadCoordinator.startWaiting()`
- `DebounceController.resumeAll()`
- `StateMachineManager.batchPause()`

### P0. 单个取消 `cancelItem()` 仍绕过状态机直接移除 UI

文件：

- `spug_web/src/pages/document/stores/upload/core/controls/ItemOperationController.js`

现状：

- `cancelItem()` 会：
  - bump operation version
  - 直接从前端队列移除
  - 移除状态机
  - 异步调用后端取消接口

优点：

- UI 立即消失，用户体验快。

风险：

- 不经过 `UploadStateMachine.transition('CANCEL')`。
- 传输列表里看不到 `cancelled` 终态记录。
- 如果后端取消失败，前端已经移除了任务，后续排查困难。

建议：

- 对单个取消区分两类操作：
  - “取消并保留记录”：走状态机 `CANCEL`，显示 `cancelled`。
  - “删除/移除记录”：走 `removeItem()`。
- 如果产品希望取消后直接消失，则文案应叫“移除/取消并移除”，并确保后端失败有日志或轻提示。

### P0. `StatusSynchronizer` 与 `StoreEventAdapter` 可能重复同步后端

当前同步链路至少有两条：

- `StateChangeHandler.handle()` 调 `statusSynchronizer.syncStateToBackend()`
- `UploadStateMachine` entry 中 `actions.updateTransferStatus()` 触发 `StoreEventAdapter.handleTransferStatusUpdate()`

风险：

- 同一状态可能同步两次。
- `_lastSyncStatusMap` 只在 `StatusSynchronizer` 内部去重，挡不住 `StoreEventAdapter` 的重复调用。
- 某些失败情况下，一条链路失败另一条成功，日志会变得混乱。

建议：

- 保留一条权威同步链路，推荐保留 `StatusSynchronizer.syncStateToBackend()`。
- 移除或降级 `UploadStateMachine` entry 里的 `actions.updateTransferStatus()`。
- 如果暂时不敢动大，可以让 `StoreEventAdapter.handleTransferStatusUpdate()` 也共用同一个去重器。

### P1. 合并失败后的 `_directMerge()` 仍绕过状态机

文件：

- `spug_web/src/pages/document/stores/upload/core/controls/ItemOperationController.js`

现状：

- `_directMerge()` 成功提交后直接写：
  - `item.state = 'merging'`
  - `item.status = 'merging'`
  - `item.progress = 99`

风险：

- 状态机可能仍在 `error` 或新建后的 `waiting`。
- `countByStates()`、终态释放、后端同步可能都和 UI 不一致。

建议：

- 把“合并失败重试”建成状态机合法路径。
- 最小修法：
  - 重建/获取状态机后，不直接写 `item.status`。
  - 引入一个事件，例如 `RETRY_MERGE` 或复用 `RESUME` 后通过 guard 进入 `merging`。
- 如果短期不改，至少在 `_directMerge()` 后同步状态机状态或明确释放旧状态机，避免 UI 与状态机长期分裂。

### P1. 批量恢复只恢复已存在状态机的任务，可能漏掉等待队列

文件：

- `spug_web/src/pages/document/stores/upload/core/StateMachineManager.js`
- `spug_web/src/pages/document/stores/upload/core/controls/DebounceController.js`

现状：

- `batchResume()` 遍历的是 `this.machines`。
- 但当前设计是“懒创建状态机”，大量 waiting 任务可能还没有状态机。

风险：

- 批量恢复只能恢复已经创建过状态机的任务。
- 没有状态机的 waiting/paused 任务可能需要依赖 `UploadCoordinator.startWaiting()` 另行调度。

建议：

- `resumeAll()` 不要只依赖 `stateMachineManager.batchResume()`。
- 对当前队列中 `paused/waiting` 的 item 做一轮扫描：
  - `paused` 且有状态机：走状态机 `RESUME`
  - `waiting` 且无状态机：交给 `uploadCoordinator.startWaiting()`
- 后端批量恢复只同步真正恢复成功或准备恢复的 transferIds。

### P1. 后端批量暂停/恢复的状态统计要和前端保持一致

文件：

- `spug_api/apps/document/views/transfer/batch.py`

观察：

- 后端 `TransferBatchPauseView` 对已暂停记录也计入 `updated_count`。
- 前端可能把“已是目标状态”当成成功，这本身没错，但统计文案容易误导。

建议：

- 返回结构区分：
  - `updated_ids`
  - `already_ids`
  - `skipped_ids`
- 前端提示使用更准确的文案，例如“已处理 X 个，其中 Y 个原本已暂停”。

### P2. 清空失败/取消任务建议统一删除接口语义

文件：

- `spug_web/src/pages/document/UploadPanel.js`
- `spug_web/src/pages/document/stores/upload/core/transfer.js`

观察：

- `UploadPanel` 已经直接调用 `batchDeleteTransfers()` 清空完成/失败/取消。
- `TransferStore.clearCompletedTransfers()` 仍调用了批量取消接口，语义错误。

建议：

- 删除 `clearCompletedTransfers()`，如果无人调用。
- 或改成安全 no-op，并注释说明后端暂无“清理已完成”专用接口。

### 手工回归场景

1. 单个小文件上传成功：
   - 前端：`waiting -> calculating -> uploading -> completed`
   - 后端：`PENDING/UPLOADING -> COMPLETED`

2. 单个大文件上传成功：
   - 前端：`waiting -> calculating -> uploading -> merging -> completed`
   - 后端：`PENDING/UPLOADING -> MERGING -> COMPLETED`

3. 单个上传中暂停/恢复：
   - 前端暂停后显示 `paused`
   - 后端为 `PAUSED`
   - 恢复后回到 `uploading`

4. 合并中任务：
   - 不显示暂停按钮
   - 可取消或等待完成

5. 单个取消：
   - 根据产品语义确认是“取消并保留记录”还是“取消并移除记录”
   - 如果保留记录，应显示 `cancelled`
   - 后端应为 `CANCELED`

6. 批量取消：
   - 前端所有受影响任务显示 `cancelled`
   - 后端批量取消任务完成后为 `CANCELED`

7. 刷新页面后状态校正：
   - completed/error/cancelled 不应被后端旧状态拉回 uploading/merging
