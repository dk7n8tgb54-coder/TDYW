# 制度管理模块设计方案

> 状态：多文件制度已实施（2026-10-29 落地，迁移 0003）；文件生命周期与保留策略已实施（2026-10-29，迁移 0004）；文件分工已实施（2026-10-29，迁移 0005）——分工单位从"章节"改为"整份制度文件"，独立的"章节分工"页签取消，旧章节记录只读保留供人工核对。**发布后修订状态已实施（2026-10-30，迁移 0006）**：修订进行中成为显式持久状态，发布成功结束本轮修订但保留工作副本，无内容/结构变化拒绝重复发布，支持批量文件分工。ONLYOFFICE 已在开发环境接入，两份真实样本的保存链路已验收，复杂 `.docx` 的浏览器显示保真仍未通过。制度管理暂不迁移到生产环境，保留策略的自动物理清理未启用（仅显式预检/执行入口）。

## 1. 目标与边界

制度管理用于管理部门及科室的规章制度和手册，支持跨部门参与编制、上传、在线查看、在线编辑、变更记录、发布和历史版本查阅。一个制度可以包含一份或多份 Word 文件；制度名称、编号、类别、文件名称、顺序和数量均为业务数据，由有权限的管理员维护，不是代码中的固定清单。下文沿用现有模型名称“手册”（`Manual`）表示一项制度容器，并不限定它只能有一份文件。

初始可录入以下手册：

- 部门管理手册、部门应急救援手册；
- 各科室操作手册、各科室应急手册；
- SMS 手册，初步按部门手册设计，最终归属逐本确认。

现有“规章管理”侧重规章台账、分类和附件，不具备手册正文的草稿与版本语义。制度管理已作为独立业务模块开发，与规章管理并列；不把 Word 手册当作规章记录的普通附件来覆盖更新。kkFileView 承担只读预览，不是在线编辑器。

## 2. 已确认的业务事实

1. 每个科室只有一个账号，且各科室账号拥有独立的 `tenant_id`。
2. 部门有多位领导，各自有账号，领导账号的 `tenant_id` 不相同。
3. 本部门的科室之间可以相互查看手册；部分手册可能邀请其他部门共同编制。
4. 每本手册的编辑需要密码，以防止其他科室修改。
5. 同一制度可能由多人分工，参与者也可能属于不同部门；同一制度可有一份或多份 Word 文件。不同文件可以由不同参与者分别编制；同一份 Word 首期仍只允许一个可写会话。
6. SMS 手册大致属于部门手册，不能在未确认时固定为科室手册。
7. 编辑、发布若由同一科室账号完成，不构成独立审批；首期不设计形式上的审批状态。

手册的业务归属、查看授权、编辑授权是三件事。具体授权通过现有角色体系与手册配置决定，不按用户和手册的 `tenant_id` 是否相同来放行。不得为了本模块改变现有账号的租户归属，因为租户同时影响其他业务模块。

## 3. 手册归属与访问规则

可以完全使用角色做制度管理的查看、编制和发布授权，不需要用 `tenant_id` 判断访问范围。每本手册的名称、编号、类别及“部门/科室”归属都是可维护的业务数据；归属用于分类和责任说明，不自动授予权限。查看、编制、发布分别关联角色，账号获得哪些角色由管理员配置。代码只实现通用校验规则，不硬编码手册名称、科室、部门、账号或角色名称。新增手册不应要求修改代码或发布版本。

| 手册类别 | 业务归属 | 建议的角色配置 |
| --- | --- | --- |
| 科室操作/应急手册 | 对应科室 | 关联该科室查看角色和编制角色；角色与账号的对应关系由管理员配置 |
| 部门管理/应急救援手册 | 对应部门 | 关联部门查看角色、一个或多个编制角色；可包含领导角色和跨部门参与角色 |
| SMS 手册 | 暂按部门归属 | 与部门手册同一规则，最终归属逐本确认 |

- 推荐为制度管理使用平台级角色，由超级管理员将角色分配给相应账号。这样不同租户的领导可以拥有同一个部门编制角色，手册不必理解账号租户。科室之间需要权限差异时，配置不同科室的制度角色；跨部门协作时，把参与账号授予该手册关联的角色，或授予专门的协作角色。
- 当前项目中的普通角色受租户范围约束，平台级角色可跨租户分配。制度管理应复用现有角色授权能力并在后台校验角色 ID；不能按角色显示名称匹配，也不能把“角色名称含某科室名”当作授权规则。
- 默认查看范围是本部门的授权角色。跨部门参与者通过该手册的明确角色授权查看草稿；是否允许合作部门查看最终发布版也应逐本配置，不能因参与编制而自动公开给整个外部部门。
- 编制角色允许修改草稿，发布角色允许使版本生效；二者可以授予同一账号，但不伪称独立审批。草稿与未发布修订只对本手册获得相应授权的账号可见。
- 后端在列表、详情、文件列表、预览、下载、编辑配置、保存回调和发布等入口分别校验操作权限、文件所属制度及制度关联角色。不能把“有页面权限”“知道密码”或“前端显示按钮”单独视为编辑授权。
- 角色删除、账号调岗、手册移交或撤销授权后，应立即停止相关账号的新编辑和发布；历史操作人及版本记录不改写。

建议的编辑判定为：账号有效且具有模块编辑权限，账号拥有该手册允许的编制角色，并且本次编辑会话通过该手册密码验证。其他科室即使知道密码，只要没有该手册的编制角色，也不能编辑。管理员重置密码和调整角色关联需有单独管理权限并留痕。

## 4. 编辑密码与会话

- 密码按手册独立设置，数据库只保存经过 Django 密码哈希器处理的值，不保存明文，也不在接口或日志中回传。
- 输入制度密码只用于开启短时编辑会话；目标结构中会话绑定制度、具体文件、账号、该文件草稿修订号及有效期。保存操作仍重新校验账号角色、制度授权、文件归属及会话有效性。
- 单写锁以文件为单位：同一文件同一时刻仅一个可写会话；同一制度的不同文件可由不同账号并行编辑。文件排序、移除、发布和整套回退仍需制度级串行校验，避免与进行中的保存交错。
- 密码验证需限制失败尝试；密码重置、手册移交或撤销编辑权后，既有编辑会话失效。
- 仅查看已发布版本不要求编辑密码。密码遗失由有管理权限的账号重置，重置不改变历史版本。
- 科室共用一个账号意味着审计只能确认“哪个科室账号操作”，不能确认科室内具体人员；使用个人账号的领导与跨部门参与者可记录实际账号。

## 5. 文档与版本流程

多文件结构已按本节目标实施（迁移 0003）：制度容器 `Manual` + 稳定文件条目 `ManualFile` + 文件各自草稿 `ManualDraft` + 整套不可变发布版本 `ManualVersion`/`ManualVersionFile`。`ManualOriginal` 的多条记录是同一制度文件可更换的候选来源（"初始来源"历史），不是可同时发布的多份文件。

| 对象 | 主要内容 |
| --- | --- |
| 制度容器 `Manual` | 名称、编号、类别、业务归属、查看/编制/发布角色、状态、当前发布版本、编辑密码哈希 |
| 制度文件 `ManualFile`（拟新增） | 稳定 ID、所属制度、显示名称、排序、文件状态；即使改名或移除也不复用 ID |
| 文件原稿与草稿（拟调整） | 原稿保留上传文件与来源；每个文件至多一个当前工作草稿，含路径、哈希、基准发布版本、最后保存人/时间和独立修订号 |
| 文件编辑会话（拟调整） | 绑定制度文件、账号、模式、有效期与修订号；同一文件单写，不能与另一编辑模式同时写 |
| 制度发布版本 `ManualVersion` + 文件快照（拟调整） | 版本号、变更说明、发布人/时间、生效状态；每版有完整、有序的文件清单及各文件独立不可变路径、哈希和名称 |
| 文件分工（2026-10-29，替代章节分工） | 分工单位=整份制度文件：每份文件至多一名负责人与一段分工说明（字段在 `ManualFile` 上，结构上不存在互相冲突的多条当前分工）；负责人完成编制后可"提交编制"（记录草稿修订号与时间）；不单独授予超过制度角色的编辑权，不隔离同一文件内部章节 |
| 旧章节分工 `ManualChapter`（遗留只读） | 旧记录只关联制度、无法按章节名称猜测所属文件，人工核对完成前保留可读；全部写接口已关闭 |
| 操作记录 | 制度与可选文件 ID、文件修订号、操作账号、文件增删/改名/排序、分工/提交编制、保存、发布及版本号 |

目标流程：建立制度并配置角色/密码 -> 按需新增一份或多份文件（上传原稿，新增时可指定负责人与分工说明）-> 分别建立和编辑各文件草稿 -> 负责人完成编制后在文件清单"提交编制"（记录提交时的草稿修订号与时间）-> 发布人核对完整文件清单与顺序、各文件负责人与提交状态后，填写整套变更说明一次发布整套制度。一个文件时仍走同一流程，不强迫创建多个文件。不同文件可以同时编制；同一文件仍单写。文件分工记录责任，不声称能在同一份 Word 内强制限制每人只能改自己章节。

发布时以制度行锁固定文件清单与顺序，并核对各文件草稿修订号、哈希和编辑会话状态；仍在编辑、待同步、转换失败或缺少有效草稿的文件不能悄悄跳过。先为本版每份文件制作独立不可变快照，全部成功后才在同一数据库事务中写入版本及其文件快照、切换当前版本并记录审计；中途失败清理新文件，保留旧生效版和原草稿。物理文件不受数据库回滚保护，必须显式补偿。未修改的文件也要进入本次完整清单，可复用不可变文件内容，但不得引用会被覆盖或清理的草稿。发布后新增、移除、改名或重排文件只影响下一版草稿，不改变任何历史清单。

**修订状态与发布轮次（2026-10-30，迁移 0006）**：区分四个概念，互不混淆——

| 概念 | 语义 | 载体 |
| --- | --- | --- |
| 初始来源 | 最初上传的原始文件（候选来源，可更换） | `ManualOriginal` 记录，永不覆盖 |
| 草稿工作副本 | 每份未移除文件持续保留的一份可编辑工作文件 | `ManualDraft`（发布后保留，不删除） |
| 进行中的修订 | 显式持久状态 `ManualFile.revision_open`，绝不凭哈希相等推断 | 文件条目字段，默认 True |
| 发布快照 | 某版整套不可变文件清单 | `ManualVersion`/`ManualVersionFile` |

- 修订开启：新文件创建即为进行中；「开始修订」（`POST files/<fid>/revision/start/`，编制角色）是真实状态动作；任何草稿内容变更（保存/恢复/回退/原稿重建）都经 `_create_draft_record` 把文件置回进行中；废止当前版本后全部启用文件回到进行中。
- 修订结束：仅整套发布成功时对本次发布清单内文件关闭；发布失败（预检拒绝/快照制作失败/落库复核失败）不触碰修订状态、草稿与旧生效版本。
- 工作副本健康时的「开始修订」原样复用现有工作副本，绝不再复制生效快照；工作副本缺失、损坏或与当前生效基线不一致时返回 `needs_repair`（reason=draft_missing/draft_corrupt/baseline_mismatch + 恢复提示），前端明确提示并经 `confirm_repair` 二次确认后从当前生效版本快照修复，绝不静默改用初始来源，也绝不静默覆盖可能含未发布修改的工作副本。
- 发布收尾（同一事务内）：发布清单内文件修订关闭、清除"提交编制"交接记录（提交随本版发布被消费）、草稿 `base_version` 指向新版本并解除 `source_original` 引用（来源历史由 ManualOriginal 记录与操作记录承载）；已结束的旧引用不再无期限保护历史原稿/版本。移除文件与整套回退同样解除退出文件休眠草稿的基线/来源引用。
- 无意义发布拒绝：已有生效版本且无内容变化（哈希）、无新增/移除/改名/排序时，发布预检 `can_publish=false` 且发布端 `publish_whole_set` 明确拒绝——两处口径一致（`version_compare.has_pending_publish_changes`），首次发布（无生效版本）除外。修订开启但内容未变不构成发布理由。
- 存量迁移（0006）保守回填：AddField 默认全量"修订进行中"，仅对「存在于当前生效版本快照 + 草稿哈希一致 + 无活跃编辑会话」的文件翻转为已结束；其余（含草稿缺失、哈希不一致、有活跃会话）保持进行中，不丢失可能尚未发布的修改或编辑会话。

“移除文件”是从当前待发布清单移除并保留稳定 ID、原稿和历史版本引用，不直接删除被历史版本引用的物理文件；最后一份文件不能被移除后仍允许发布空制度。整套回退以某个历史版本的有序文件清单重建一套新草稿，不覆盖现有发布版；重发时产生更大的新版本号。下载可逐份进行，也可按版本导出 ZIP（含清单、文件名冲突处理与哈希）；ZIP 是派生下载件，不是新的发布版本。不自动合并 Word 文件，避免样式、目录和编号变化。若将来需要多人实时编辑同一份 Word，再单独评估协同能力。

“变更记录”至少提供两种视图：发布版本列表展示整套文件清单、顺序、每份文件的快照、变更说明与发布人；操作记录展示何时由哪个账号对哪个文件进行了保存、增删、改名、排序等动作及对应修订号。编辑器的自动保存可能非常频繁，不宜将每次按键当作业务版本；草稿修订不等于发布版本。科室共用账号的人员级归因限制仍然存在。

首期不设置“同一账号编辑后再审批”的流程。若将来要求独立复核，需要另行指定不同账号和明确的审核责任，届时再增加审批状态。

## 6. Word 在线编辑方案

在线编辑采用私有部署的 ONLYOFFICE Docs（2026-10-27 确认并接入）；kkFileView 继续承担只读预览。二者的鉴权和文件入口严格分离：预览走 `*/attachments/<kind>-<id>/preview-file/` + 短时效 preview_token；编辑走 `attachments/oo-editor-file/`（editor_token 自认证）与 `attachments/oo-editor-callback/`（官方 JSON 回调协议 + JWT），并在 `AUTHENTICATION_EXCLUDES` 登记豁免中间件认证、由视图独立校验。

现有单主文件实现的保护语义（不得误认为已经支持多文件）：

- 编辑配置（`draft/editor-config/`）在有效编辑会话内签发，含按修订号生成的 document.key（`oo-<manual>-r<rev>-<rand>`）与 JWT 签名的完整 config；未配置服务时返回 `editor_available=false` 前端降级。
- `.doc` 原稿永不改动：首次编辑前经 LibreOffice headless 转出 `.docx` 工作副本；转换失败可预览/下载并明确提示。
- 回调校验链：JWT（HS256，恒时比较，拒绝 alg 降级）→ JWT 载荷为权威回调体 → `users` 数组归属账号 → 手册编制角色 + 活跃编辑会话 + 手册未归档 → 回调 key 必须等于会话当前签发 key（迟到回调与旧编辑实例被拒；同会话重开编辑器即轮换 key）→ 内容哈希幂等（重复回调不虚增修订号）→ 保存前行锁复核修订号。
- 回调文件下载仅允许 DS 自身主机白名单（`ONLYOFFICE_ALLOWED_URL_HOSTS`），禁止任意 URL 取回；文件大小受限。
- 部署：docker compose 提供 `onlyoffice` 服务（JWT_ENABLED）与制度文件持久化卷；浏览器经 nginx `/onlyoffice/` 同源代理（CSP 无需放行外部源），DS 回源走 compose 网络 `http://tdyw`。`ONLYOFFICE_JWT_SECRET` 未配置时整体降级，不影响其他功能。

多文件改造须把文件稳定 ID 纳入编辑配置、取文件令牌、document.key、编辑会话、回调及草稿修订号的绑定；回调必须核对“账号 + 制度 + 文件 + 当前会话 + 文件修订号 + 当前 key”，不能只按制度 ID 找一份草稿。不同文件可以分别签发 key，但同一文件的旧实例回调仍须拒绝；WPS 客户端试点若后续接入，也与 ONLYOFFICE 共享同一文件级单写占用。预览令牌和下载接口同样绑定文件快照或当前草稿，不允许改文件 ID 后读取别的制度。`.doc` 原稿逐文件独立保留，转换为 `.docx` 工作副本，不改写原稿；转换失败只阻止该文件建立可编辑草稿和整套发布，不妨碍其他文件查看。

真实样本已验证打开、保存、重开和下载链路，但复杂 Word 原生 `.docx` 的 ONLYOFFICE 浏览器显示仍存在字体、页眉及表格文字异常；`.doc` 转换往返也出现分页差异。多文件模型不会修复版式兼容性。继续用真实脱敏样本对照字体、页眉页脚、表格和分页，不把文件同步成功等同于版式验收通过。生产环境暂不迁移制度管理。

## 7. 页面与配置入口

- 手册列表：按类别、科室、名称、编号、状态筛选；显示归属、当前生效版本与整套工作状态（含"修订进行中"独立状态，已生效手册显示"已生效/无未发布修改"）。
- 手册详情：默认以当前生效文件为主。发布成功后整套摘要显示"已生效（vN），无未发布修改"，不再并排展示生效版本/草稿版本对照；有进行中的修订或待发布结构变化时明确展示对应状态。默认页签为"文件清单"，日常清单保持简单——顺序/文件名/大小/负责人/状态/编制提交/主要操作；修订号、工作副本来源与版本比较放草稿工作台详情与"变更记录"。行操作按修订状态显示「开始修订」（真实状态动作）或「继续编辑」（直接复用工作副本）。历史版本可查看当时的清单、文件、变更说明和操作记录。
- 草稿文件页（草稿工作台）：新增（可选指定负责人）/改名/排序/移除文件，逐份显示原稿、草稿修订号、最后保存人、负责人、编辑占用和同步状态；一次只打开选中的文件编辑页。单文件制度无需额外文件夹层级。
- 编辑页：具备编制角色的账号经制度密码验证后打开选中文件草稿；显示该文件的保存状态和修订号。不同文件的占用状态相互独立。
- 发布操作：由具备发布角色的账号预览整套待发布文件——重点展示实际变化文件（新增/修改/移除/受阻），未修改文件以数量汇总并可展开核对完整清单；逐行含负责人与提交编制状态；确认各文件均已保存并填写变更说明后一次发布整套制度，成功后整套生效；失败时不得显示发布成功。整套状态无待发布变化时（首发除外）发布入口弱化且确认禁用，服务端同样拒绝。
- 管理入口：动态新增和维护手册名称、编号、类别与业务归属，配置查看/编制/发布角色关联、文件分工（文件级负责人，支持勾选多份文件批量指定/清空）、密码设置与重置，以及手册停用或归档。

发布版查看权限与草稿编辑权限在页面和接口均需独立控制。前端请求沿用项目 HTTP 业务错误约定，避免同一错误重复弹窗。

## 9. 现有数据迁移与实施顺序

现有库的 `ManualDraft`、`ManualVersion`、`ManualEditSession` 都以制度为直接父对象。升级前须确认迁移脚本在隔离数据库上能处理当前真实数据形态；不能删除旧表后重建，也不能把多条 `ManualOriginal` 自动解释为同一制度下的多份正式文件。

1. 先新增文件条目及版本文件快照表，保留现有表与接口。为每个已有制度创建一个稳定的“主文件”条目；其当前草稿对应这一文件。历史 `ManualVersion` 每版的一份文件映射成该版的一条文件快照，保留旧版本号、时间、发布人、说明、路径和哈希；旧原稿先保留为该主文件的候选来源，不据原稿数量推断正式文件数量。名称从已有草稿/版本文件名取值，无法确定时标记待人工核对，不能编造对应关系。
2. 先做可重跑的数据回填和迁移校验：逐制度核对文件条目、每版文件快照数、版本号、当前版本指针、文件存在性及 SHA256；失败即停止切流，原始记录和文件仍可按旧路径读取。既有活跃会话在切流前须完成保存或安全失效，不能跨新旧协议复用。
3. 然后增加文件级服务/API 和前端页面，先让单文件制度经新路径完整读写，再开放新增第二份文件。ONLYOFFICE 的 key、令牌、回调、单写与迟到回调校验须同步升级；原有单文件入口在过渡期委托唯一文件或明确拒绝多文件制度，不能默默选第一份。
4. 最后启用整套发布、历史回退、整套下载与操作记录。切流期间保留旧数据与可逆映射，回滚仅在尚未产生多文件发布版本时可回到旧写入逻辑；出现多文件草稿或版本后，旧模型无法完整表达，回滚应停止写入、保留数据并使用前向修复，不得丢弃新增文件。

阶段实施只在开发和隔离测试数据库验证；制度管理生产迁移继续延后。实施时另行确认生产延迟上线开关已通过启动、路由和迁移计划验证，不因本文设计修改而触发部署。

## 10. 多文件改造验收点

1. 拥有本部门查看角色的账号能查看获授权的已发布手册；未获授权的部门外账号不能查看。
2. 科室手册只允许配置的编制角色通过密码后编辑；其他科室即使知道密码也不能编辑，账号租户不单独决定权限。
3. 不同租户的领导账号只要获得部门手册配置的编制角色，就能通过密码参与编辑；跨部门参与者仅访问明确授权的手册与草稿。
4. 单文件制度仍能完整编辑和发布；多文件制度可按用户配置的顺序逐份编辑、预览和下载，不同文件可由不同账号并行编辑，同一文件只允许一个可写会话。
5. 发布得到一份完整、有序、不可变的文件清单；任一文件仍在编辑、未同步、无有效草稿或快照失败时，旧生效版保持不变，历史文件不被覆盖。文件移除、改名、排序与整套回退只影响新草稿及后续版本。
6. 密码重置、授权撤销、不同制度文件 ID 冒用、编辑回调失败、旧回调迟到及修订冲突时，不会使未经授权或过时的内容进入草稿或生效版。
7. 操作记录能关联账号、制度、具体文件和修订号，发布记录能关联完整版本；科室共用账号的人员级归因限制在界面与管理制度中说明。
8. 存量单文件制度、原稿及历史版本迁移前后数量、归属、文件哈希和下载结果一致；旧接口在过渡期不误操作多文件制度。

后续实现测试应执行真实 API、数据库、文件存储与编辑回调路径；后端测试按项目要求在 Docker 隔离测试数据库内运行。

## 11. 文件生命周期与保留策略（2026-10-29 已实现）

原稿与发布版本的物理文件按保留策略管理；记录行与元数据永久保留。实现位于 `retention_services.py`（候选评估/预检/执行），路由为 `cleanup/preview/`（只读预检）与 `cleanup/execute/`（可控执行），门控 `institution.manual.config`；不新增权限码。**自动物理清理不启用**——没有定时任务，清理只能经显式端点触发，且未配置保留期限（`INSTITUTION_VERSION_RETENTION_DAYS`，默认 0）时执行整体拒绝。

### 11.1 初始原稿的语义与恢复

- 初始原稿只用于首次建立草稿，或用户明确选择"从原始上传文件重建草稿"（高级操作：发布过版本须 confirm 二次确认、丢弃草稿须编辑密码、有活跃编辑会话一律拒绝）。正常编辑直接继续当前草稿，绝不重新创建覆盖。
- 无草稿时按严格优先级恢复：① 已有草稿拒绝覆盖；② 优先从当前生效版本中该文件的快照恢复；③ 仅该制度从未发布过版本时，才默认从原稿创建。当前版本不含该文件、已废止或来源原稿已清理时，明确展示可用处理方式（`draft_recovery` 提示字段），不静默回到原稿。
- 发布版本是当时整套实际生效文件的不可变快照；当前版本用于日常查阅，历史版本用于核查及在文件仍可用时整套回退。

### 11.2 初始来源页面与上传交互

- 制度详情默认页签为"文件清单"（由"当前生效文件"与"草稿工作区"两页签合并；2026-10-30 起日常清单简化为 顺序/文件名/大小/负责人/状态/编制提交/主要操作——状态列由服务端内容关系与修订状态合并为一句可懂短语，修订号、工作副本来源与版本比较放草稿工作台与变更记录；负责人列点击即可分工，勾选多份文件可批量分工；预览/下载/开始修订/继续编辑按权限提供，草稿工作台仍是唯一编辑页面）；版本与发布保留整套历史，发布入口位于详情头部整套待发布状态旁（受阻文件提供处理入口，受阻或无变化时禁用确认按钮，后端仍权威校验）；文件变更记录支持按具体文件查看（含已移除文件，下拉取自 originals-overview 全集）。
- "初始来源"为次要页签，无逐文件选择下拉：一次聚合请求（`originals-overview/`）返回全部制度文件，每份一行（文件名、最初原稿的上传人与时间、首次进入的发布版本、直接预览/下载），多条原稿记录在该行展开历史（区分"最初原稿"与"后续来源"，已清理记录仅存元数据）。
- "新增制度文件"（批量，每个上传文件各建一份制度文件）与"为已有文件更换来源"（按行受控操作，确认目标文件与对草稿的影响，上传新原稿记录、不改当前草稿）严格分开。
- "从原始上传文件重建草稿"展示替换风险与二次确认；原稿已清理时禁用并解释；零文件手册仍可在该页签首次上传。

### 11.3 原稿保留

- 保护边界 = 该文件**首次进入成功发布的版本**；在此之前原稿本体永久保留。首次发布并经过 `INSTITUTION_ORIGINAL_CLEAN_BUFFER_DAYS` 缓冲期后，原稿本体才可成为清理候选。
- 清理前逐项核对：草稿来源引用（草稿仍以该原稿为 `source_original` 时阻止）、文件共享路径引用、活跃编辑会话；不能删除仍被使用或无法确认归属的文件。
- 已清理原稿保留名称、上传人、时间、哈希与清理时间等元数据（`ManualOriginal.cleaned_at`），预览、下载与重建入口关闭并明确解释。

### 11.4 发布版本保留

- 当前生效版本及整套文件永久受保护；`is_effective=False` 仅表示不是当前生效版，绝不据此判断可删除。重要版本可设长期保留标记（`ManualVersion.long_term_protected`，`versions/<vid>/protect/`，发布域权限）；近期历史版本按 `INSTITUTION_VERSION_RECENT_KEEP_COUNT`（数量）与保留期限（天数）保护。
- 较早版本只有超过期限、未受保护且没有业务引用（无草稿以其为 `base_version`）才成为清理候选。多文件版本按整套判定与清理；部分快照删除失败时整版标为 partial（不可完整使用）、记录失败并允许重试，不显示为可完整回退。
- 清理后保留版本号、发布人/时间、变更说明与快照行（`ManualVersionFile.cleaned_at`，含哈希），明确标记"文件已按保留策略清理"，关闭该版本的预览、下载与回退。删除物理文件前核对 ManualVersion 旧兼容镜像列与 ManualVersionFile 的同路径引用及跨版本/草稿共享引用，防止重复删除或误删。

### 11.5 预检与执行

- 预检（`GET cleanup/preview/`）完全只读：列出候选制度、版本、文件、大小、候选原因和阻止条件，不写数据库或磁盘；预检不是执行凭证，执行前逐项重新核对。
- 执行（`POST cleanup/execute/`，可带 `manual_id` 限定单本制度）可控、幂等：重新核对权限、归属、期限、引用与物理路径，逐文件记录成功/失败，失败留下可重试状态，不伪装成功；操作与审计留痕。
- 只在开发环境测试副本上验证删除；不清理生产或真实手册文件。整套 ZIP 导出、章节级 Word 隔离等能力仍属未实现项。

## 13. 文件分工与提交编制（2026-10-29 已实现，迁移 0005）

旧"章节分工"（`ManualChapter`，只关联制度）让用户维护与文件无法对应的章节记录，已由"文件分工"替代：分工单位是整份制度文件，每份文件至多一名负责人与一段分工说明。

### 13.1 指定、改派与未分配

- 字段就在 `ManualFile` 上（owner/owner_name/assign_note/assigned_at/assigned_by），结构上不存在"同一文件多条互相冲突的当前分工"；负责人为空即"未分配"，前端明确显示。
- 新增文件时即可指定（`files/create` 的可选 `owner_id`/`note` 字段，草稿工作台新增文件弹窗提供入口）；之后经 `POST manuals/<pk>/files/<fid>/assignment/` 改派或清空（owner_id 必须显式携带，null=清空）。
- **批量分工（2026-10-30）**：`POST manuals/<pk>/files/batch-assignment/`（file_ids 非空整数列表 + owner_id 显式携带 + note 统一说明）——逐文件校验归属，任一文件不属于 URL 中的制度即整批拒绝（全成功或全失败，绝不部分生效）；事务内逐文件复用单文件分工实现，每份文件写一条 `file_assign` 操作记录（batch 标记）并记一条模块审计事件。前端在文件清单勾选多份文件后批量指定/清空，明确展示已选数量与作用范围；筛选、刷新、切换制度后不保留旧勾选。
- **改派或清空负责人即重置提交编制记录（2026-10-30）**：owner 变化时同步清除 `submission_revision/submitted_at/submitted_by`——提交是负责人向发布者的一次交接，负责人变更后旧交接不再有效（回到"未提交"）；负责人未变（仅修改分工说明）时保留提交。历史交接保留在操作记录中。
- 分工接口权限=模块 draft_edit 权限 +（管理权限或手册编制角色）；每个请求先校验文件确属 URL 中的制度。
- **指定负责人不自动授予查看或编辑权限**：编辑仍要求模块权限 + 该制度编制角色 + 密码会话；同一文件单写、不同文件可并行的会话规则不变。负责人身份只是责任标记，所有写接口由后端逐接口校验文件归属与操作权限，前端按钮隐藏不能替代校验。
- 负责人与分工说明对清单可见者下发（`files/` 行内 `assignment`，含服务端判定的 `is_mine`）；编制者可按"只看我负责的文件"筛选。文件清单页签的分工入口在负责人列（有分工权限者点击姓名/「未分配」直接编辑，无权限者只读），操作列不再有独立的「文件分工」链接。

### 13.2 提交编制

- 负责人完成编制后执行 `POST manuals/<pk>/files/<fid>/submit/`：后端记录提交时的草稿修订号（`submission_revision`）与时间（`submitted_at`/`submitted_by`），作为明确的交接信息。放行口径=文件负责人 或 管理权限 或 手册编制角色（负责人不要求持有编制角色——提交是状态交接而非编辑操作）。
- 拒绝条件：手册已归档、无有效草稿（记录缺失/路径非法/物理文件缺失）、该文件仍有活跃编辑会话。可重复提交（以最新修订号覆盖）。
- **提交状态为计算式判定**：`submission_revision == 当前草稿 revision` 且草稿有效=已提交（submitted）；草稿再次保存、原稿重建、版本回退或恢复都会推进修订号，提交状态随即失效（stale），绝不继续显示"已完成"。不依赖任何写路径记得"清除提交"。
- **交接记录的显式失效（2026-10-30）**：三类事件会直接清除提交记录（回到"未提交"，非 stale）——① 改派或清空负责人（旧负责人的交接不再有效）；② 整套发布成功（提交随本版发布被消费，绝不误显示为下一轮的待交接）；③ 配套的负责人字段落库路径。历史交接保留在操作记录中。
- **第一阶段不新增发布阻断条件**：`publish_whole_set` 的整套发布校验保持不变，提交与否、是否负责人都不影响发布；`publish-preview/` 各分组行（除 removed）携带负责人与提交状态，仅供发布者核对（`ManualChapter` 时代的旧发布校验也未受影响）。
- 发布者核对整套制度时，在发布确认窗口逐行看到 各文件负责人、提交状态、草稿与生效版差异及编辑占用（受阻行同样带负责人）。

### 13.3 旧章节记录的过渡处理（待人工迁移）

- 旧 `ManualChapter` 表与记录**一律未删除、未改写**：旧记录只关联制度、无法按章节名称猜测所属文件，不做自动映射。
- `GET manuals/<pk>/chapters/` 继续开放（遗留只读清单）；新增/编辑/删除/进度全部写接口返回明确业务错误。
- 前端独立的"章节分工"顶层页签已取消；存在历史记录时，文件清单页签底部只读过渡展示（说明改为按文件重新指定负责人，核对完成前记录保留）。
- 人工核对完成后的旧记录清理（确认无人需要后再删行或归档表）属后续运维操作，不在本期实现。
