# 制度管理模块设计方案

> 状态：方案讨论稿。本文记录截至 2026-10-27 已确认的业务规则与建议实现，不代表功能已开发或 Office 编辑服务已选型。

## 1. 目标与边界

制度管理用于管理部门及科室的 Word 手册，支持跨部门参与编制、上传、在线查看、在线编辑、变更记录、发布和历史版本查阅。手册名称、编号、类别和数量均为业务数据，由有权限的管理员在页面新增、编辑、停用或归档；本文列举的名称仅为初始示例，不是代码中的固定清单。

初始可录入以下手册：

- 部门管理手册、部门应急救援手册；
- 各科室操作手册、各科室应急手册；
- SMS 手册，初步按部门手册设计，最终归属逐本确认。

现有“规章管理”侧重规章台账、分类和附件，不具备手册正文的草稿与版本语义。制度管理建议作为独立业务模块，与规章管理并列展示；不把 Word 手册当作规章记录的普通附件来覆盖更新。现有 kkFileView 可以继续承担只读预览，但它不是在线编辑器。

## 2. 已确认的业务事实

1. 每个科室只有一个账号，且各科室账号拥有独立的 `tenant_id`。
2. 部门有多位领导，各自有账号，领导账号的 `tenant_id` 不相同。
3. 本部门的科室之间可以相互查看手册；部分手册可能邀请其他部门共同编制。
4. 每本手册的编辑需要密码，以防止其他科室修改。
5. 同一本手册可能由多人按章节或部分分工，参与者也可能属于不同部门。此前确认的是不需要多人同时编辑同一份 Word；是否要求各章节并行编制仍待确认。
6. SMS 手册大致属于部门手册，不能在未确认时固定为科室手册。
7. 编辑、发布若由同一科室账号完成，不构成独立审批；首期不设计形式上的审批状态。

手册的业务归属、查看授权、编辑授权是三件事。具体授权通过现有角色体系与手册配置决定，不按用户和手册的 `tenant_id` 是否相同来放行。不得为了本模块改变现有账号的租户归属，因为租户同时影响其他业务模块。

## 3. 手册归属与访问规则

可以完全使用角色做制度管理的查看、编制和发布授权，不需要用 `tenant_id` 判断访问范围。每本手册的名称、编号、类别及“部门/科室”归属都是可维护的业务数据；归属用于分类和责任说明，不自动授予权限。查看、编制、发布分别关联角色，账号获得哪些角色由管理员配置。代码只实现通用校验规则，不硬编码手册名称、科室、部门、账号或角色名称。新增手册不应要求修改代码或发布版本。

| 手册类别 | 业务归属 | 建议的角色配置 |
| --- | --- | --- |
| 科室操作/应急手册 | 对应科室 | 关联该科室查看角色和编制角色；角色与账号的对应关系由管理员配置 |
| 部门管理/应急救援手册 | 对应部门 | 关联部门查看角色、一个或多个编制角色；可包含领导角色和跨部门参与角色 |
| SMS 手册 | 暂按部门归属 | 与部门手册同一规则，最终归属逐本确认 |

- 推荐为制度管理使用平台级角色，由超级管理员将角色分配给相应账号。这样不同租户的领导可以拥有同一个部门编制角色，手册不必理解账号租户。科室之间需要权限差异时，配置不同科室的制度角色；跨部门协作时，把参与账号授予该手册关联的角色，或授予专门的协作角色。
- 当前项目中的普通角色受租户范围约束，平台级角色可跨租户分配。制度管理应复用现有角色授权能力并在后台校验角色 ID；不能按角色显示名称匹配，也不能把“角色名称含某科室名”当作授权规则。
- 默认查看范围是本部门的授权角色。跨部门参与者通过该手册的明确角色授权查看草稿；是否允许合作部门查看最终发布版也应逐本配置，不能因参与编制而自动公开给整个外部部门。
- 编制角色允许修改草稿，发布角色允许使版本生效；二者可以授予同一账号，但不伪称独立审批。草稿与未发布修订只对本手册获得相应授权的账号可见。
- 后端在列表、详情、预览、下载、编辑配置、保存回调和发布等入口分别校验操作权限和手册角色关联。不能把“有页面权限”“知道密码”或“前端显示按钮”单独视为编辑授权。
- 角色删除、账号调岗、手册移交或撤销授权后，应立即停止相关账号的新编辑和发布；历史操作人及版本记录不改写。

建议的编辑判定为：账号有效且具有模块编辑权限，账号拥有该手册允许的编制角色，并且本次编辑会话通过该手册密码验证。其他科室即使知道密码，只要没有该手册的编制角色，也不能编辑。管理员重置密码和调整角色关联需有单独管理权限并留痕。

## 4. 编辑密码与会话

- 密码按手册独立设置，数据库只保存经过 Django 密码哈希器处理的值，不保存明文，也不在接口或日志中回传。
- 输入密码只用于开启短时编辑会话；会话绑定手册、账号、草稿和有效期。保存操作仍重新校验账号角色、手册授权及会话有效性。
- 密码验证需限制失败尝试；密码重置、手册移交或撤销编辑权后，既有编辑会话失效。
- 仅查看已发布版本不要求编辑密码。密码遗失由有管理权限的账号重置，重置不改变历史版本。
- 科室共用一个账号意味着审计只能确认“哪个科室账号操作”，不能确认科室内具体人员；使用个人账号的领导与跨部门参与者可记录实际账号。

## 5. 文档与版本流程

建议采用“手册主记录 + 当前草稿 + 不可变发布版本”的结构：

| 对象 | 主要内容 |
| --- | --- |
| 手册 | 可编辑的名称、编号、类别、业务归属类型和单位标识、查看/编制/发布角色关联、状态、当前发布版本、编辑密码哈希 |
| 草稿 | 工作文件、基于哪个发布版本创建、最后保存人和时间、编辑修订序号 |
| 章节分工 | 手册、章节或部分名称、负责人账号、参与角色、进度与提交记录；不单独授予超过手册角色的编辑权 |
| 发布版本 | 版本号、独立存储的 Word 文件、文件哈希、变更说明、发布人、发布时间、生效状态 |
| 操作记录 | 创建、上传、进入编辑、保存草稿、重置密码、调整授权、发布、废止、下载等事件及操作账号 |

推荐流程：上传原稿并建立手册 -> 配置角色和章节分工 -> 创建或继续草稿 -> 参与者编辑所负责内容并保存 -> 填写变更说明 -> 具有发布角色的账号确认发布 -> 新版成为当前生效版。首期以一份主 Word 草稿为准，允许多人先后参与，但同一时间只由一个有效会话写入；章节分工记录责任，不声称能在同一份 Word 内强制限制每人只能改自己章节。已发布版本不能原地覆盖；回退旧版时，以旧版为来源创建新草稿，再发布一个新版本，保留完整时间线。废止只改变生效状态，不清除历史文件。

如业务需要各人同时编制不同章节，可为章节暂存独立草稿文件，由指定整编人合入主 Word 后发布；自动合并 Word 章节可能破坏样式、目录和编号，不能未经样本验证就作为首期能力承诺。若要求多人实时编辑同一份 Word，则需另行验证编辑服务的协作能力与冲突处理，并调整当前单写会话规则。

“变更记录”至少提供两种视图：发布版本列表，展示各版内容、变更说明与发布人；操作记录，展示何时由哪个账号进行了什么动作。编辑器的自动保存可能非常频繁，不宜将每次按键当作业务版本；可以按一次完成的编辑会话形成草稿检查点，但首期发布版本必须完整留存。

首期不设置“同一账号编辑后再审批”的流程。若将来要求独立复核，需要另行指定不同账号和明确的审核责任，届时再增加审批状态。

## 6. Word 在线编辑方案

技术候选为私有部署的 ONLYOFFICE Docs，并先用真实手册验证功能、部署条件和许可。它承担编辑；现有 kkFileView 继续承担只读预览。二者的鉴权和文件入口不能混用。

- 接受 `.doc` 和 `.docx` 上传，原稿永久保留。`.doc` 在首次编辑前转换为 `.docx` 工作副本，不覆盖原稿；转换失败时仍允许预览、下载并提示不能在线编辑。
- 对复杂表格、页眉页脚、目录、域、批注、修订痕迹、字体和分页，用实际样本比较转换前后与编辑保存后的效果，再确定是否可用及是否需要限制某些格式。
- 编辑服务获取文件和回传保存结果时，使用绑定手册、草稿、账号及有效期的服务端授权；回调还须校验编辑服务签名、目标草稿和修订序号，防止伪造或过期回调覆盖新内容。
- 首期多人可先后参与同一手册，但同一时间只有一个可写编辑会话；仍须处理不同账号、同账号多标签页和迟到回调，使用草稿修订序号阻止旧内容覆盖新内容。章节并行编制或实时协作的需求明确后，再决定是否扩展编辑模式。
- 文件先落入受控存储，再更新数据库指针；数据库失败或文件失败都要有补偿与清理。发布版文件独立且不可变，不能指向仍会被自动保存改写的草稿文件。

正式选型前须验证编辑服务与本项目 Docker、Nginx、HTTPS、文件体积和内网部署的兼容性，并确认实际部署所需许可。未验证前不承诺 `.doc` 编辑保真或 Word 修订痕迹的完整保留。

## 7. 页面与配置入口

- 手册列表：按类别、科室、名称、编号、状态筛选；显示归属和当前生效版本。
- 手册详情：默认显示已发布版，提供预览、历史版本、变更说明和操作记录。
- 编辑页：具备编制角色的账号经密码验证后打开草稿；显示保存状态、当前草稿修订和返回详情入口。
- 章节分工：指定负责人、查看参与进度和提交记录；首期分工不等于 Word 正文的段落级权限。
- 发布操作：由具备发布角色的账号填写变更说明并确认，使新版本生效；失败时不得显示发布成功。
- 管理入口：动态新增和维护手册名称、编号、类别与业务归属，配置查看/编制/发布角色关联、章节分工、密码设置与重置，以及手册停用或归档。

发布版查看权限与草稿编辑权限在页面和接口均需独立控制。前端请求沿用项目 HTTP 业务错误约定，避免同一错误重复弹窗。

## 8. 与现有项目的边界

| 范围 | 现状 | 制度管理建议 |
| --- | --- | --- |
| `spug_web/src/pages/regulation/` + `spug_api/apps/regulation/` | 规章分类、台账、附件、预览与审计 | 保留原职责，不直接承担手册正文版本 |
| `spug_web/src/pages/document/` + `spug_api/apps/document/` | 资料库文件管理与预览 | 可参考文件与预览实践，不让资料库普通文件覆盖手册发布版 |
| `spug_api/apps/account/` | 账号、租户、角色与权限 | 使用现有平台级角色授权查看、编制和发布，不改变账号租户；租户字段不参与制度访问判断 |
| `spug_api/apps/logs/` | 操作审计 | 记录制度操作；不可替代不可变的 Word 发布版本 |
| `docker/` | kkFileView 预览 | 在线编辑服务需单独部署与验证 |

实现时再决定制度管理的具体 app、路由和表名；新增权限码须同时落到后端校验、前端路由及角色配置。项目全局规则要求业务模型具备 `tenant_id` 字段，这是数据模型约定；制度管理仍可完全以角色进行业务授权，不使用 `tenant_id` 推导手册归属、可见范围或编辑权。若模型采用租户感知 Manager，制度管理查询需显式绕过其默认租户过滤，并在每个 API 上按手册关联角色授权；不能无条件放开到全平台。

## 9. 建议的首期验收点

1. 拥有本部门查看角色的账号能查看获授权的已发布手册；未获授权的部门外账号不能查看。
2. 科室手册只允许配置的编制角色通过密码后编辑；其他科室即使知道密码也不能编辑，账号租户不单独决定权限。
3. 不同租户的领导账号只要获得部门手册配置的编制角色，就能通过密码参与编辑；跨部门参与者仅访问明确授权的手册与草稿。
4. 草稿保存、发布与回退均不会改写历史发布文件；每个版本可以单独预览和下载。
5. 密码重置、授权撤销、编辑服务回调失败及旧回调迟到时，不会使未经授权或过时的内容成为生效版。
6. 多名参与者能在同一本手册下记录章节分工并先后提交修改；没有发布角色的编制者不能发布。
7. 审计能关联账号、手册、操作和版本；科室共用账号的人员级归因限制在界面与管理制度中说明。

后续实现测试应执行真实 API、数据库、文件存储与编辑回调路径；后端测试按项目要求在 Docker 隔离测试数据库内运行。

## 10. 待验证与待决定

- SMS 手册大致归属部门；逐本确认是否存在例外，无需再验证跨部门共同编制是否可能，该场景已纳入方案。
- 手册业务归属单位标识的数据来源，以及查看、编制和发布角色由谁维护；跨部门参与者是否同时可查看发布版。
- 制度管理平台级角色由谁维护、如何命名和分配；建议角色由超级管理员维护并授予各部门账号。
- 多人分工时是否需要并行编辑不同章节，还是先后编辑主 Word 即可；是否需要章节文件暂存与指定整编人。
- 实际 Word 样本的格式兼容性、文件大小、字体依赖与编辑服务许可。
- 草稿检查点的保留数量和期限；发布版本与审计记录的长期保留要求。

上述事项在实施前确认。本文不将未验证的现状、许可条件或个人级审计能力写成既定事实。
