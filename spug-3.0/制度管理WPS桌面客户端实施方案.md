# 制度管理 WPS 桌面客户端实施方案

> 状态：实施方案，尚未开发桌面客户端。以 2026-10-28 工作区内的制度管理实现为依据；本文中的桌面接口和目录均为拟新增内容，不代表已经可用。

## 1. 目标与范围

- 保留现有 React 网页版、ONLYOFFICE 在线编辑和 kkFileView 预览。桌面客户端是 Windows 试验入口，先在一台开发终端验证本机 WPS 编辑和自动回传。
- 用户在制度管理中取得手册编辑资格，客户端打开本机 WPS；WPS 保存后，客户端把工作文件上传到服务器。只有服务器确认并返回新的草稿修订号，界面才显示“已同步”。
- 草稿保存产生 `ManualDraft.revision` 和操作记录；只有现有发布流程才产生不可变 `ManualVersion` 和发布说明。客户端不得把每次 WPS 保存称为“发布新版本”。
- 首期只做单机试点和单本手册单写，不承诺多人实时协同、离线编辑后自动合并、WPS 与 Word 的完全版式一致，也不替换生产系统入口。

## 2. 现状与复用边界

| 现有能力 | 位置 | 客户端处理 |
|---|---|---|
| 手册角色、编辑密码、单写会话 | `spug_api/apps/institution/services.py`、`views_draft.py` | 复用服务端判定；账号租户不作为手册授权条件 |
| 当前草稿、修订号、哈希、保存记录 | `ManualDraft`、`save_draft_file` | 复用草稿存储和修订号并发保护，增加客户端同步协议 |
| 手工下载和 multipart 上传 | `draft/download/`、`draft/save/` | 可用于早期联调；不足以处理断线重试、重复请求与同步状态确认 |
| ONLYOFFICE 编辑和保存回调 | `editor-config/`、`oo-editor-callback/` | 保留；WPS 路线不得借用 ONLYOFFICE 回调 JWT 或文档 key |
| 已发布版与操作记录 | `ManualVersion`、`ManualOperationLog` | 沿用发布及查询页面，不直接修改已发布文件 |

当前 `.doc` 原稿在创建草稿时由 LibreOffice 转为 `.docx` 工作副本，原稿不改动；现有 `draft/save/` 仅接受 `.docx`。因此试点的 WPS 编辑对象是 `.docx` 草稿，即使手册最初上传的是 `.doc`。要保留 `.doc` 编辑格式，需要另行评估，不能在试点中暗中改写原稿或改变格式约定。

现有编辑会话有效期为两小时，保存时续期；长时间没有成功保存可能过期。客户端需在服务器验证当前账号、角色和会话后续租，并在过期前明确提示。现有“同账号多标签复用会话”还不足以区分 WPS 与 ONLYOFFICE：新增 WPS 编辑前，服务端应明确编辑模式和占用关系；切换模式须确认前一编辑器已完成保存，不能轮换 ONLYOFFICE key 后丢弃未回传内容。

## 3. 架构与目录

```text
Windows 终端
  Electron 桌面客户端（承载现有网页 + 受限本机编辑能力）
    └─ WPS 打开本地受控工作副本 → 监听稳定写入 → 同步队列
            ↕ 内网 HTTPS，账号认证 + 手册编辑会话
现有 Django 制度管理 API → 草稿文件、修订号、操作记录、发布版
```

- 拟新增源码目录：项目根目录 `desktop/`，与 `spug_web/`、`spug_api/` 并列。建议包含 Electron 主进程、preload、WPS 适配器、同步队列、安装打包配置及自身测试；不在 `spug_web/` 内直接放 Node 文件系统和进程启动代码。
- 首期客户端加载同一内网服务器提供的现有 React 页面，不复制一套业务前端。桌面专属的“使用 WPS 编辑”和同步状态可通过受限 preload 能力接入制度管理页面；普通浏览器仍显示现有 ONLYOFFICE/手工上传路径。具体桥接接口在实施时确定，不能把任意 IPC 暴露给远端页面。
- 安装包是构建产物，放 `desktop/dist/` 并忽略 Git；安装位置由 Windows 安装器决定，与源码目录无关。本地工作副本和恢复元数据放在当前 Windows 用户的 `%LOCALAPPDATA%/TDYW/WpsEdits/` 下，按服务器、账号、手册及会话隔离；该目录不在仓库和同步盘内。安装包不能内置业务文件或密钥。
- 服务端不安装 WPS；WPS 运行在终端。客户端只连接已有内网系统，不依赖公网或 WPS 365 云服务。

## 4. 一次编辑的状态与数据流

1. 用户在客户端登录现有平台并进入手册草稿页，选择“使用 WPS 编辑”。服务端重新校验页面权限、手册编制角色、编辑密码、手册状态以及单写占用；权限判断不信任客户端。
2. 服务端签发或确认绑定账号、手册、模式和当前修订号的 WPS 编辑会话。客户端下载草稿文件到受控目录，校验长度和 SHA256，再用该终端实际可用的 WPS 启动方式打开。若 WPS 未安装或打开失败，保留网页编辑路径并给出明确状态。
3. 本地副本进入“编辑中”。WPS 保存时可能先写临时文件再重命名；客户端监听目录变化并做防抖，等待目标文件可稳定读取、大小和摘要连续一致后才排队上传。以摘要区别真正变更和 WPS 重复写入。不能靠进程退出或单次文件事件判断保存完成。
4. 上传包含会话凭证、手册、基准修订号、文件 SHA256 和幂等请求标识。服务端再次校验账号、角色、会话、模式、文件类型/大小/内容和当前修订号；在行锁内比较并保存为新草稿，记录操作与审计，返回新修订号和服务器哈希。必要时以单独的同步结果查询接口处理“服务器已保存但响应丢失”。
5. 客户端核对服务端返回的修订号和哈希后，才将该摘要标记为“已同步”；WPS 后续再次保存时，以最新修订号继续上传。若服务端已更新而本地又发生修改，必须按顺序排队，不能并发上传同一本手册的多个快照。
6. 用户执行“结束编辑”时，先等待同步队列清空，再由服务端结束会话。若仍有未同步内容，阻止静默结束并显示重试或保留副本的选择。退出客户端、WPS 异常结束或断网后，保留待同步副本与最小恢复元数据；下次启动先复核服务端修订号，不自动覆盖服务器文件。

客户端状态至少区分：准备中、编辑中、待同步、同步中、已同步、同步失败（仅本机）、会话失效、版本冲突。状态文案应基于服务端确认，而不是文件监听事件。若账号撤权或密码重置，停止自动上传并保留本地副本供管理员按制度处理；不得以旧令牌绕过服务端授权。

## 5. 服务端拟新增契约

在 `spug_api/apps/institution/` 内增加 WPS 桌面编辑服务与少量端点，具体 URL 和字段以实现时的 API 契约为准：

| 操作 | 必要语义 |
|---|---|
| 开始 WPS 编辑 | 校验密码、权限、单写占用；返回模式绑定的会话、草稿修订号、哈希、文件名和有效期 |
| 下载 WPS 工作文件 | 只允许持有本手册有效 WPS 会话者取当前草稿；返回实际文件哈希与长度 |
| 续租与查询状态 | 重新校验账号和授权；返回服务端修订号、哈希、会话状态；避免盲目延长已撤权会话 |
| 上传保存 | multipart 文件 + 基准修订号 + 内容摘要 + 幂等标识；成功返回服务器修订号和哈希，失败给出可区分的会话失效、冲突、文件无效等原因 |
| 查询同步结果 | 按同账号、同手册、同会话的幂等标识查询已确认保存结果，解决响应丢失后的安全重试 |
| 结束 WPS 编辑 | 幂等释放会话；服务端不能凭客户端宣称“已保存”，客户端先核对待同步状态 |

会话隔离需防同一账号同时用 ONLYOFFICE 和 WPS 写同一草稿。现有 `start_edit_session` 对同账号会复用会话，实施时必须补充模式占用和切换规则，并覆盖同账号多标签、不同账号、客户端重启及到期恢复。若会话过期而本地有修改，重新验证密码后只能在服务器修订号仍等于本地基准时续传；否则进入冲突处理，不自动覆盖。旧 `draft/save/` 路径及 ONLYOFFICE 回调须继续正常工作。

服务端继续沿用角色授权、不以 `tenant_id` 判断手册访问。文件先落盘，数据库事务内校验修订号并更新草稿及审计，失败清理新文件；发布版绝不原地覆盖。上传幂等应以服务端记录的请求标识和结果实现，不能只靠前端比较 SHA256；同内容重复请求不得产生新修订号。不能通过公开文件 URL、共享盘路径或 ONLYOFFICE 回调接口绕过授权。

## 6. 客户端实现要点

- Electron 保持 `contextIsolation`，关闭 `nodeIntegration`，启用沙箱；preload 仅暴露制度管理所需的有限操作，IPC 校验来源、手册 ID、路径与参数。限制导航到配置的内网源；下载、外链和新窗口走明确策略。不得关闭 TLS 证书校验。
- 验证目标终端上 WPS 的安装路径、文件关联、命令行打开方式和保存行为后再实现适配器；不要硬编码单一安装路径或假定一定能收到“文档关闭”事件。首期以明确的“结束编辑”操作收尾。
- 本地文件只允许位于客户端受控目录，不接受网页传入任意路径。启动 WPS 时只打开已校验的工作副本；临时锁文件、自动恢复文件与真正的目标文档区分处理。
- 客户端需要单实例/重复窗口策略和进程崩溃后的恢复扫描。待同步副本不得因退出、卸载、清缓存或登录切换而静默删除；已确认同步的副本按约定期限清理。恢复记录避免保存账号密码或长期服务端令牌。
- 打包、安装、更新和签名在试点时分别验证。内网无更新源时可先人工安装试验包，但需固定 Electron 版本并记录发布包校验值。桌面环境与浏览器的登录会话、Cookie、上传下载、打印、ONLYOFFICE iframe/代理和证书都要做回归检查。

## 7. 分阶段实施与验收

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| 0. 终端能力验证 | 在一台 Windows 开发机确认 WPS 版本、`.docx` 打开方式、保存写入模式、字体环境 | 能以测试副本在 WPS 中保存并检测真实文件变化；不具备则记录阻碍和替代路线 |
| 1. 服务端同步契约 | 会话模式、续租、幂等上传、冲突和结果查询；Docker 隔离库行为测试 | 权限、单写、过期、撤权、重复上传、响应丢失、冲突均由真实请求验证 |
| 2. 客户端最小闭环 | `desktop/` 可安装试验客户端，制度管理入口、WPS 启动、稳定写入检测、同步状态和本地恢复 | 测试手册可打开、保存、自动回传、关闭重开；服务器草稿修订与操作记录正确 |
| 3. 故障与兼容回归 | 断网/重连、进程异常、登录切换、WPS 多次保存；网页版和 ONLYOFFICE 回归 | 未同步修改可恢复，旧请求不覆盖新草稿；网页版原功能继续可用 |
| 4. 真实手册版式评估 | 脱敏 `.doc` 来源与复杂 `.docx` 的 WPS 往返、PDF 对照 | 字体、页眉页脚、分页差异逐项记录；格式验收与同步验收分开判定 |

试点使用开发环境和测试手册副本，不修改正式原稿或生产数据。后端测试遵守项目规定，在 Docker 内以隔离测试数据库跑真实请求及文件副作用；前端/客户端测试验证实际状态流转与请求。无法执行的 WPS 实测或 Word/WPS 版式对照明确标为 `NOT_RUN`/`BLOCKED`，不能以模拟事件代替通过。

## 8. 试点通过标准与后续决策

两类来源手册（`.doc` 转换后的工作草稿、原生 `.docx` 草稿）都应完成：密码与角色验证、WPS 打开、连续多次保存、自动上传、服务端修订号与哈希核对、关闭重开、操作记录查询。还需验证断网后保留本地修改并重试、会话过期或撤权时拒绝旧上传、冲突时不覆盖服务端、同一手册 WPS 与 ONLYOFFICE 不并发写入。

只有以上链路在真实终端通过，才决定是否推广桌面客户端。若以后采用“网页版 + 本地助手”，可复用服务端同步契约及 WPS 文件同步核心，重新实现唤起和用户界面；试点不要求现在迁移所有用户。

## 9. 待试验确认

- 目标终端 WPS 的具体版本、安装方式、文件关联与实际写入行为。
- 内网客户端分发与更新方式、Windows 安装权限及代码签名要求。
- 已同步本地副本的保留期限，以及故障副本由谁清理和如何交接。
- 真实手册的授权字体和版式基准；同步成功不等于文档版式验收通过。
