# 规章管理独立附件设计方案

## 1. 背景与结论

当前规章管理模块的附件通过资料库中的 `DocumentFilePublic` 进行关联，并且范围绑定到了 `industry_rules` 系统目录。这个设计不适合当前业务边界：

- 党务档案用于存放党建材料，不应承载行业/业务规章文件。
- 文档管理是通用资料库，若规章附件直接关联通用文档，会导致文件归属、权限、删除、归档边界不清。
- 规章原文、修订稿、废止依据等附件属于规章台账的一部分，应由规章管理模块闭环维护。

建议采用：**规章管理单独附件表 + 单独上传/下载/删除接口**。

资料库模块可以继续作为通用文档库存在，但规章附件不再依赖资料库业务目录，也不再引用党务档案文件。

## 2. 设计原则

1. **业务归属清晰**
   规章元数据和规章附件均归规章管理模块管理。

2. **权限独立**
   规章附件权限只使用规章管理权限码，不依赖 `document.document.*` 或 `document.industry_rule.*`。

3. **物理存储卷可复用，业务模型不复用**
   规章附件可以复用资料库所在的 Docker volume / 存储根目录，便于备份、容量规划和迁移；但必须使用独立的 `regulation/` 子目录，不要复用资料库的文件表、目录表和业务权限。

4. **附件生命周期跟随规章**
   删除规章时，可软删除或级联清理附件记录；文件物理清理应有失败补偿机制。

5. **默认支持主附件**
   一条规章可有多个附件，但最多一个主附件。

## 3. 数据模型设计

### 3.1 新增模型：RegulationAttachment

当前 `RegulationAttachment` 关联 `document.DocumentFilePublic`。建议重构为独立附件表。

```python
class RegulationAttachment(models.Model):
    regulation = models.ForeignKey(
        Regulation,
        on_delete=models.CASCADE,
        related_name='attachments',
        verbose_name='所属规章',
    )

    original_name = models.CharField(max_length=255, verbose_name='原始文件名')
    stored_name = models.CharField(max_length=255, verbose_name='存储文件名')
    file_path = models.CharField(max_length=500, verbose_name='文件路径')
    file_size = models.BigIntegerField(default=0, verbose_name='文件大小')
    file_type = models.CharField(max_length=100, blank=True, default='', verbose_name='文件类型')
    file_hash = models.CharField(max_length=64, blank=True, default='', db_index=True, verbose_name='文件哈希')

    is_primary = models.BooleanField(default=False, verbose_name='是否主附件')
    sort_order = models.IntegerField(default=0, verbose_name='排序')

    uploaded_by = models.ForeignKey(User, null=True, on_delete=models.SET_NULL, related_name='+', verbose_name='上传人')
    uploaded_at = models.CharField(max_length=20, default=human_datetime, verbose_name='上传时间')

    is_deleted = models.BooleanField(default=False, db_index=True, verbose_name='是否删除')
    deleted_by = models.ForeignKey(User, null=True, blank=True, on_delete=models.SET_NULL, related_name='+', verbose_name='删除人')
    deleted_at = models.CharField(max_length=20, null=True, blank=True, verbose_name='删除时间')

    class Meta:
        db_table = 'tdyw_regulation_attachment'
        ordering = ['-is_primary', 'sort_order', '-id']
        indexes = [
            models.Index(fields=['regulation', 'is_deleted', '-is_primary', 'sort_order'], name='reg_att_list_idx'),
        ]
```

### 3.2 主附件唯一性

业务层在设置主附件时执行：

```python
RegulationAttachment.objects.filter(
    regulation=regulation,
    is_deleted=False,
).exclude(id=attachment.id).update(is_primary=False)
attachment.is_primary = True
attachment.save(update_fields=['is_primary'])
```

如果数据库支持条件唯一索引，可增加“同一规章仅一个未删除主附件”的数据库约束；如果 MariaDB 版本不支持部分索引，则以事务内业务逻辑保障。

## 4. 文件存储设计

规章附件文件较多，建议复用资料库当前使用的 Docker volume：

```text
tdyw-documents:/data/spug/spug_api/storage/documents
```

也就是说，规章附件和资料库文件可以在**同一个物理存储卷/存储根目录**下，便于统一备份和扩容。但规章附件必须使用独立业务子目录，不能混入资料库文件目录结构。

建议规章附件存储目录：

```text
/data/spug/spug_api/storage/documents/regulation/{regulation_id}/{yyyy}/{mm}/{uuid_filename}
```

示例：

```text
/data/spug/spug_api/storage/documents/regulation/1024/2026/07/6f4c9e1b3c0f4e5a9d8a.pdf
```

要求：

- 数据库建议只存相对路径，例如 `regulation/1024/2026/07/6f4c9e1b3c0f4e5a9d8a.pdf`，运行时再与配置的存储根目录拼接。
- 存储根目录应通过配置项管理，例如 `DOCUMENT_STORAGE_ROOT=/data/spug/spug_api/storage/documents` 或复用项目现有资料库存储根配置。
- 规章模块只能读写 `DOCUMENT_STORAGE_ROOT/regulation/` 下的文件。
- 删除文件前必须校验最终路径仍位于 `DOCUMENT_STORAGE_ROOT/regulation/` 内，避免误删资料库或其他模块文件。
- 如果资料库存在清理无引用文件、回收站清理、缩略图生成等后台任务，必须排除 `regulation/` 子目录，避免误扫规章附件。
- 存储文件名使用 UUID，避免用户文件名导致路径冲突。
- 原始文件名只用于展示和下载响应。
- 文件扩展名从原始文件名安全提取，禁止路径穿越字符。
- 上传时计算 `file_size`、`file_type`、可选 `file_hash`。
- 删除建议先软删除记录，再异步或补偿清理物理文件。

## 5. API 设计

### 5.1 附件列表

```http
GET /api/regulation/<id>/attachments/
权限：document.regulation.view
```

返回：

```json
[
  {
    "id": 1,
    "file_name": "空中交通管理规定.pdf",
    "file_size": 204800,
    "file_type": "pdf",
    "is_primary": true,
    "uploaded_by": "管理员",
    "uploaded_at": "2026-07-16 10:30:00"
  }
]
```

### 5.2 上传附件

```http
POST /api/regulation/<id>/attachments/upload/
Content-Type: multipart/form-data
权限：document.regulation.upload
```

参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | file | 是 | 附件文件 |
| is_primary | bool | 否 | 是否设为主附件 |
| sort_order | int | 否 | 排序 |

校验：

- 规章必须存在。
- 文件不能为空。
- 文件大小不得超过系统配置上限。
- 文件类型应使用白名单，例如 `pdf/doc/docx/xls/xlsx/png/jpg`，具体按业务决定。
- 如果 `is_primary=true`，同事务内取消该规章其他主附件。

### 5.3 下载附件

```http
GET /api/regulation/<id>/attachments/<att_id>/download/
权限：document.regulation.download 或 document.regulation.view
```

建议使用独立 `download` 权限。如果业务认为能查看规章就能下载原文，也可以使用 `view`。

校验：

- 附件必须属于当前规章。
- 附件未删除。
- 物理文件存在。

### 5.4 删除附件

```http
DELETE /api/regulation/<id>/attachments/<att_id>/
权限：document.regulation.upload 或 document.regulation.delete
```

建议使用 `document.regulation.upload` 表示“维护附件”。如果希望删除附件更敏感，可新增 `document.regulation.attachment_delete`。

删除策略：

- 默认软删除附件记录。
- 记录 `deleted_by`、`deleted_at`。
- 物理文件清理可同步尝试，失败则记录待清理状态或日志。

### 5.5 设置主附件

```http
POST /api/regulation/<id>/attachments/<att_id>/primary/
权限：document.regulation.upload
```

行为：

- 附件必须属于当前规章。
- 附件未删除。
- 同事务内取消其他主附件。
- 当前附件设为主附件。

## 6. 前端设计

### 6.1 规章详情页

附件区域提供：

- 附件列表
- 上传附件按钮
- 下载按钮
- 设为主附件按钮
- 删除/取消附件按钮

不再提供“输入资料库文件 ID”。

### 6.2 新建/编辑规章

建议先保存规章元数据，再进入详情页上传附件。原因：

- 附件存储路径需要 `regulation_id`。
- 可以避免“表单未保存但文件已上传”的孤儿文件。

如需在新建弹窗中直接上传，应增加临时上传 token 和最终绑定逻辑，但复杂度更高，不建议第一版实现。

### 6.3 权限展示

前端按钮按以下权限控制：

| 功能 | 权限 |
|---|---|
| 查看附件列表 | `document.regulation.view` |
| 上传附件 | `document.regulation.upload` |
| 设置主附件 | `document.regulation.upload` |
| 删除附件 | `document.regulation.upload` 或新增删除权限 |
| 下载附件 | `document.regulation.download` |

## 7. 迁移方案

当前已有数据如果已经使用 `DocumentFilePublic` 关联，需要决定是否迁移。

### 7.1 无历史数据或可丢弃测试数据

直接改表结构：

- 删除 `document_file` 外键。
- 增加独立附件字段。
- 调整接口和前端。

### 7.2 有历史数据需要保留

建议分两步：

1. 新建独立附件表，例如 `tdyw_regulation_file_attachment`，不要直接复用旧表。
2. 编写迁移脚本：
   - 遍历旧 `RegulationAttachment`。
   - 读取关联 `DocumentFilePublic` 的文件元数据。
   - 将物理文件复制到 `/data/spug/spug_api/storage/documents/regulation/...`。
   - 写入新附件记录。
   - 保留旧表一段时间作为回滚依据。

迁移完成并确认后，再删除旧关联表或废弃旧字段。

## 8. 需要同步修复的问题

以下问题不包含租户隔离，因为规章管理按当前业务应是全局共享数据。

### 8.1 权限码命名空间不一致

问题：

- 角色管理中“资料库 -> 规章管理”生成的权限码是 `document.regulation.*`。
- 原规章页面和后端接口使用 `regulation.regulation.*`。
- 导致角色已授权后，普通用户仍看不到菜单或接口被拒绝。

处理建议：

- 前端路由、页面 `AuthDiv/AuthButton`、后端 `@auth` 统一使用 `document.regulation.*`。
- 写操作不要再叠加超管硬判断，按角色权限控制。

当前状态：

- 已在代码中完成对齐。

### 8.2 `require_supper` 与角色权限冲突

问题：

- 角色管理里有新增、编辑、删除、附件、分类管理权限。
- 后端写接口又额外要求 `is_supper=True`。
- 普通角色即使被授权，也无法实际操作。

处理建议：

- 删除规章模块写接口上的 `require_supper`。
- 保留 `@auth('document.regulation.xxx')` 作为唯一权限来源。

当前状态：

- 已在代码中去掉规章模块活动接口里的超管硬拦截。

### 8.3 现有“设为主附件”功能前后端不匹配

问题：

- 后端 `POST /attach/` 只支持新增关联，不支持把已有关联设置为主附件。
- 前端 `handleSetPrimary(record.file_id)` 把 `file_id` 当作附件关联 ID 使用。
- catch 分支里调用 `DELETE /attach/<att_id>/` 时传错 ID，可能失败或误操作。

处理建议：

- 新增独立接口：`POST /attachments/<att_id>/primary/`。
- 前端传 `record.id`，即附件记录 ID。
- 后端事务内取消其他主附件，再设置当前附件为主附件。

### 8.4 日期字段缺少后端格式校验

问题：

- `publish_date`、`effective_date`、`repeal_date` 直接接收字符串并写入 `DateField`。
- 非法日期可能导致 500 或数据库异常。

处理建议：

- 后端统一解析日期。
- 允许空字符串转 `None`。
- 非法格式返回明确错误，例如“日期格式必须为 YYYY-MM-DD”。

建议辅助函数：

```python
def parse_date_or_error(value, field_name):
    if not value:
        return None, None
    try:
        return datetime.datetime.strptime(value, '%Y-%m-%d').date(), None
    except ValueError:
        return None, f'{field_name}格式必须为 YYYY-MM-DD'
```

### 8.5 `category_id` 缺少存在性校验

问题：

- 创建/编辑规章时直接写 `category_id`。
- 如果传入不存在的分类 ID，可能触发数据库外键错误。

处理建议：

- 后端在写入前校验分类存在。
- 如果只允许选择叶子分类，应同时校验 `is_leaf=True`。

### 8.6 分类树 `is_leaf` 维护不完整

问题：

- 新增子分类时会把父分类设为 `is_leaf=False`。
- 删除最后一个子分类后，没有把父分类恢复为 `is_leaf=True`。
- 前端还允许手动修改 `is_leaf`，容易造成树结构和表单可选项不一致。

处理建议：

- `is_leaf` 不建议作为用户可编辑字段。
- 可以改为后端根据是否存在子节点动态计算。
- 如果保留字段，则新增/删除/移动分类时必须统一维护。

### 8.7 附件交互不应手输文件 ID

问题：

- 当前前端要求用户输入资料库文件 ID。
- 这暴露了内部实现细节，体验差，也容易误关联。

处理建议：

- 独立附件方案下改为直接上传。
- 如果保留关联模式，也应使用文件选择器，而不是手输 ID。

## 9. 推荐实施顺序

1. 新增或重构规章独立附件模型。
2. 新增独立附件上传、下载、删除、设主附件接口。
3. 前端移除资料库文件 ID 输入，改为规章详情内上传附件。
4. 修复日期和分类后端校验。
5. 修复分类树 `is_leaf` 维护逻辑。
6. 如果有旧附件关联数据，执行迁移脚本。
7. 删除旧的资料库关联逻辑和 `industry_rules` 范围校验依赖。

## 10. 最终目标

规章管理模块应形成独立闭环：

```text
规章台账
  ├── 基础信息：编号、名称、分类、发文单位、状态、日期
  ├── 附件文件：原文、修订稿、废止依据
  ├── 权限控制：document.regulation.*
  └── 审计日志：新增、编辑、删除、上传、下载、设主附件
```

资料库继续承担通用文档管理职责；党务档案只承担党建材料管理职责；规章管理独立管理规章文件，避免业务边界混淆。
