# 账号签名图片公共能力设计方案

> 状态：待评审  
> 创建日期：2026-07-17  
> 适用项目：Spug 3.0  
> 本文范围：仅设计方案，不包含代码实现

## 一、需求背景

系统需要提供一项账号级公共能力：

- 每个账号最多配置一张当前生效的手写签名图片；
- 签名图片只能由超级管理员上传、替换或停用；
- 普通用户不能自行上传、替换或删除自己的签名图片；
- 检查单、值班日志、审批单等业务模块可以调用该能力完成签名展示和签署；
- 用户更换签名图片后，历史业务记录仍必须展示签署当时使用的旧版本；
- 签名图片的赋予、替换、停用和每次实际使用都必须可审计、可追溯。

本功能属于内部管理系统中的“手写签名图片留痕”，不等同于通过 CA 证书、可信时间戳和实名认证形成的可靠电子签名。它适合内部确认、审批留痕和责任追溯，不应直接宣称具备对外合同签署或司法意义上的可靠电子签名效力。

## 二、目标与非目标

### 2.1 建设目标

1. 在账号管理中由超级管理员统一维护签名图片。
2. 建立稳定的签名公共服务，业务模块不直接读取账号表或附件表。
3. 签署时固化签名图片版本、文件哈希、签署人和业务数据摘要。
4. 签名图片替换不影响历史记录，停用后不能用于新的签署。
5. 所有敏感操作以后端权限判断为准，并写入操作审计。
6. 支持后续逐步接入检查单、值班日志、审批和 PDF 导出等场景。

### 2.2 本期不做

- 不提供普通用户自行上传签名图片的入口；
- 不提供浏览器手写画板；
- 不提供自动抠图、自动美化或第三方图片处理服务；
- 不接入 CA、短信认证、人脸识别或外部可信时间戳；
- 不允许定时任务或业务模块在用户无感知的情况下自动代签；
- 不将签名图片作为公开静态文件暴露在 `/media/` URL 下。

## 三、核心业务规则

### 3.1 签名的两个阶段

本方案必须区分“赋予签名图片”和“实际签署”两个动作：

| 阶段 | 操作人 | 含义 | 是否形成业务签署记录 |
|---|---|---|---|
| 赋予 | 超级管理员 | 给账号配置一张可用的签名图片 | 否 |
| 实际签署 | 账号本人 | 在具体业务模块中确认使用签名 | 是 |

超级管理员上传图片，只代表该图片被配置给目标账号，并不代表目标账号已经同意或签署任何业务数据。

### 3.2 当前签名与历史签名

- 一个账号在任意时刻最多只有一个当前生效签名；
- 替换签名时生成新版本，不覆盖旧文件；
- 当前签名只用于后续新签署；
- 历史业务记录固定引用签署时的版本，不跟随当前签名变化；
- 停用签名后不能发起新签署，但历史记录和历史图片仍可按权限查看；
- 删除账号时不物理删除已被使用的签名文件。

### 3.3 实际签署要求

业务模块调用签名能力时必须同时满足：

1. 当前请求用户已登录且账号有效；
2. 签署人必须是当前请求用户，不接受前端任意传入其他 `user_id`；
3. 目标账号存在当前生效签名；
4. 当前用户拥有业务模块自身的编辑、提交或审批权限；
5. 前端显示待签业务摘要和签名预览，由用户明确点击“确认签署”；
6. 后端重新读取当前签名并完成签署，不能信任前端提交的图片地址、哈希或版本号；
7. 签署记录与业务数据应在同一事务中提交，任一失败则整体回滚。

如业务确实存在“代签”需求，应另行设计委托关系、有效期、代签标识和审批流程，不能复用本期普通签署接口隐式实现。

## 四、总体架构

```text
系统管理 / 账号管理
  -> 超级管理员上传、替换、停用签名
     -> AccountSignatureService
        -> AttachmentService（文件校验、存储、哈希）
        -> AccountSignature（账号当前签名绑定）
        -> EvidenceAttachment（每个图片版本的附件元数据）
        -> AuditLog（赋予、替换、停用操作审计）

业务模块
  -> 用户打开签署确认框
     -> SignatureService.get_my_current_signature()
  -> 用户确认签署
     -> 业务模块校验业务权限与状态
     -> SignatureService.apply_signature()
        -> SignatureUsage（不可变的签署快照）
        -> EvidenceEvent（证据事件，可选但推荐）
     -> 业务模块保存 signature_usage_id
```

### 4.1 模块边界

建议在后端新增独立公共模块：

```text
spug_api/apps/signature/
  __init__.py
  apps.py
  models.py
  services.py
  admin_views.py
  user_views.py
  urls.py
  migrations/
  tests/
```

职责划分：

| 组件 | 职责 |
|---|---|
| `admin_views.py` | 解析超级管理员的 HTTP 请求，调用管理服务 |
| `user_views.py` | 查询本人签名、获取预览令牌，不提供写操作 |
| `services.py` | 对业务模块公开稳定的查询、签署、渲染接口 |
| `models.py` | 保存账号当前绑定和每次签署快照 |
| `AttachmentService` | 复用现有附件校验、磁盘存储、SHA256 和安全路径能力 |
| `AuditLog` | 记录管理员赋予、替换、停用等操作 |
| `EvidenceEvent` | 记录实际签署时的业务快照和防篡改信息 |

业务模块只允许调用 `apps.signature.services` 暴露的方法，不直接查询 `AccountSignature` 或 `EvidenceAttachment`，符合现有模块间调用规范。

## 五、数据模型设计

### 5.1 账号当前签名表 `AccountSignature`

该表表达“账号当前被赋予哪一版签名”，每个账号最多一条记录。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BigAutoField | 主键 |
| `tenant_id` | CharField(50), index | 目标账号所属租户快照 |
| `user_id` | BigIntegerField, unique | 目标账号 ID，一账号一条绑定记录 |
| `current_attachment_id` | BigIntegerField, null | 当前签名对应的 `EvidenceAttachment.id` |
| `version` | PositiveIntegerField | 当前版本号，从 1 递增 |
| `status` | CharField(20) | `active` 或 `disabled` |
| `assigned_by_id` | BigIntegerField | 最近一次赋予/替换的超级管理员 ID |
| `assigned_by_name` | CharField(100) | 管理员姓名快照 |
| `assigned_at` | CharField(20) | 最近一次赋予/替换时间 |
| `disabled_by_id` | BigIntegerField, null | 停用操作人 ID |
| `disabled_by_name` | CharField(100), null | 停用操作人姓名快照 |
| `disabled_at` | CharField(20), null | 停用时间 |
| `remark` | CharField(255), blank | 管理备注，不返回给普通业务页面 |
| `created_at` | CharField(20) | 创建时间 |
| `updated_at` | CharField(20) | 更新时间 |

建议约束和索引：

- 唯一约束：`user_id`；
- 普通索引：`(tenant_id, status)`；
- 应用层校验 `AccountSignature.tenant_id == User.tenant_id`；
- `current_attachment_id` 可使用逻辑外键，保持与项目现有附件模型的低耦合方式；
- 更新时使用 `transaction.atomic()` 和 `select_for_update()` 防止并发替换产生错误版本号。

不建议直接给 `User` 表增加 `signature_path` 或二进制字段。签名涉及版本、停用、哈希和管理员审计，直接塞进账号表会使账号模型承担不属于它的文件生命周期职责。

### 5.2 签名图片版本

每次上传都在现有 `EvidenceAttachment` 中新增一条不可覆盖的附件记录：

```text
module       = account_signature
object_type  = user_signature
object_id    = <目标用户 ID>
tenant_id    = <目标用户 tenant_id>
```

附件表已有的文件名、路径、大小、扩展名、SHA256、上传人和上传时间可以作为版本元数据。`AccountSignature.current_attachment_id` 指向当前版本，查询同一 `object_id` 下的附件即可查看历史版本。

重要规则：

- 替换签名时不覆盖旧物理文件；
- 旧版本不做普通软删除，避免历史签署无法展示；
- 未被任何 `SignatureUsage` 引用的误传版本，可由专门的清理流程处理；
- 已被签署记录引用的版本永久禁止物理删除；
- 附件的 `tenant_id` 必须使用目标账号的租户，而不是上传操作人的租户。

现有 `AttachmentService.upload()` 默认从上传人读取 `tenant_id`。由于超级管理员可能给其他租户账号配置签名，实现时建议为该公共方法增加向后兼容的关键字参数 `owner_tenant_id=None`：为空时保持原逻辑，有值时由可信服务层传入目标账号租户。HTTP 接口不得允许客户端直接控制该参数。

### 5.3 签署使用表 `SignatureUsage`

该表保存每一次实际使用签名的不可变快照，解决“当前签名替换后历史业务仍能还原”的问题。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BigAutoField | 签署使用记录 ID |
| `tenant_id` | CharField(50), index | 签署业务所属租户 |
| `module` | CharField(50) | 调用模块，如 `checksheet`、`duty` |
| `object_type` | CharField(50) | 业务对象类型，如 `daily_summary` |
| `object_id` | CharField(100) | 业务对象 ID |
| `scene_code` | CharField(50) | 签署位置，如 `operator`、`reviewer`、`approver` |
| `signer_user_id` | BigIntegerField | 签署账号 ID |
| `signer_username` | CharField(100) | 登录名快照 |
| `signer_name` | CharField(100) | 显示姓名快照 |
| `signature_attachment_id` | BigIntegerField | 签署时使用的附件版本 ID |
| `signature_version` | PositiveIntegerField | 签署时账号签名版本号 |
| `signature_sha256` | CharField(64) | 签名文件哈希快照 |
| `business_snapshot_hash` | CharField(64) | 待签业务数据的规范化 SHA256 |
| `business_snapshot` | JSONField/TextField | 最小必要业务摘要，避免保存敏感全文 |
| `signed_at` | CharField(20) | 服务器签署时间 |
| `signer_ip` | CharField(50) | 请求来源 IP |
| `request_id` | CharField(64), index | 请求追踪 ID/幂等键 |
| `evidence_event_id` | BigIntegerField, null | 对应证据事件 ID |

建议索引：

- `(tenant_id, module, object_type, object_id)`：按业务对象查询签名；
- `(tenant_id, signer_user_id, signed_at)`：按签署人追溯；
- `request_id` 唯一或与场景组成唯一约束，用于防止重复点击生成两次签署；
- `(signature_attachment_id)`：判断某版本是否已经被业务使用。

`SignatureUsage` 创建后禁止普通更新和删除。业务撤回、作废或重新签署时，应新增“撤回/作废”证据事件或生成新的使用记录，而不是修改旧快照。

### 5.4 业务表如何关联

单签名场景建议业务表增加：

```python
signature_usage_id = models.BigIntegerField(null=True, blank=True)
```

多角色签名场景可以增加多个语义字段，例如：

```python
operator_signature_usage_id = models.BigIntegerField(null=True, blank=True)
reviewer_signature_usage_id = models.BigIntegerField(null=True, blank=True)
```

如果同一业务对象签名数量不固定，则业务表不必增加多个字段，通过 `SignatureUsage(module, object_type, object_id, scene_code)` 查询。具体选择由业务模块的数据稳定性和查询频率决定。

业务表不得只保存 `user_id` 或当前 `attachment_id`，否则签名替换后无法证明当时使用的是哪一版图片。

## 六、后端公共服务设计

### 6.1 管理服务

```python
assign_signature(operator, target_user_id, image_file, remark='')
replace_signature(operator, target_user_id, image_file, remark='')
disable_signature(operator, target_user_id, reason)
get_signature_admin_detail(operator, target_user_id)
list_signature_versions(operator, target_user_id)
```

共同要求：

- 第一行即校验 `operator.is_supper is True`；
- 目标账号必须存在且未逻辑删除；
- 以目标账号租户保存附件；
- 赋予/替换必须在数据库事务中更新当前指针和版本号；
- 先成功保存新附件，再更新当前指针；数据库失败时清理本次新建且未被引用的物理文件；
- 每个动作写操作审计，记录操作人、目标账号、旧版本、新版本、哈希、原因、IP 和请求 ID；
- 审计信息中不记录文件二进制内容。

`assign_signature` 和 `replace_signature` 可以在内部复用同一实现，但对外保留清晰语义：无签名时赋予，有签名时替换。也可以只提供一个 `set_signature` 服务，由服务根据当前状态确定审计动作。

### 6.2 业务模块公开服务

```python
get_current_signature_for_user(user_id, tenant_id)
get_my_current_signature(user)
apply_signature(
    actor,
    module,
    object_type,
    object_id,
    scene_code,
    business_snapshot,
    request_id,
)
get_usage(usage_id, requester)
get_usages_for_object(requester, module, object_type, object_id)
get_signature_image_for_render(usage_id, requester)
```

返回普通字典或 DTO，不向调用模块返回 Django Model 对象。例如：

```python
{
    'available': True,
    'user_id': 42,
    'version': 3,
    'attachment_id': 126,
    'sha256': '...',
    'preview_url': '/api/signature/preview/126/?token=...',
}
```

`apply_signature()` 是唯一允许生成正式签署记录的公共入口，内部完成：

1. 校验模块名、对象类型和场景码是否在注册白名单内；
2. 从 `actor` 确定签署人，不接受调用方另传签署人 ID；
3. 锁定并读取签署人的当前有效签名；
4. 从附件表重新读取真实 SHA256，不信任前端值；
5. 对规范化后的业务快照计算 SHA256；
6. 创建不可变的 `SignatureUsage`；
7. 创建 `EvidenceEvent`，快照中记录使用记录 ID、图片哈希和业务哈希；
8. 返回 `usage_id`、签署人快照、版本和签署时间。

业务权限、对象存在性和业务状态由调用模块在调用前校验；签名服务负责账号签名的真实性、租户一致性、版本固化和留痕。二者应放在同一 `transaction.atomic()` 中完成。

### 6.3 调用场景注册

为了防止任意模块拼接字符串调用签名，建议维护显式注册表：

```python
SIGNATURE_SCENES = {
    ('checksheet', 'daily_summary', 'operator'),
    ('duty', 'duty_record', 'operator'),
    ('approval', 'request', 'approver'),
}
```

新增调用模块时必须同时提交：

- 场景注册；
- 业务权限校验；
- 待签内容摘要定义；
- 签署后是否允许修改、撤回和重签的规则；
- 页面展示与导出规则；
- 单元测试和集成测试。

## 七、HTTP 接口设计

### 7.1 超级管理员接口

建议放在现有账号管理域下，便于从账号列表操作：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/account/user/<user_id>/signature/` | 仅超级管理员 | 查询目标账号当前签名及历史摘要 |
| POST | `/api/account/user/<user_id>/signature/` | 仅超级管理员 | 首次赋予签名图片 |
| PUT | `/api/account/user/<user_id>/signature/` | 仅超级管理员 | 替换并生成新版本 |
| PATCH | `/api/account/user/<user_id>/signature/status/` | 仅超级管理员 | 停用或重新启用当前签名 |
| GET | `/api/account/user/<user_id>/signature/history/` | 仅超级管理员 | 分页查看版本和管理记录 |

不建议提供普通 DELETE 物理删除接口。管理界面的“移除签名”应实现为停用，保证历史可追溯。

### 7.2 普通用户接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/signature/mine/` | 登录用户 | 查询本人是否有当前有效签名 |
| GET | `/api/signature/preview/<attachment_id>/` | 短期签名令牌 | 返回图片流，仅允许查看本人或有权业务记录的签名 |

普通用户接口不提供 POST、PUT、PATCH、DELETE。

### 7.3 业务签署接口

业务模块继续使用自己的提交接口，例如：

```text
POST /api/checksheet/daily-summary/<id>/sign/
POST /api/duty/record/<id>/sign/
```

业务前端只提交确认信息和幂等键：

```json
{
  "confirm": true,
  "request_id": "7dce9f2d-..."
}
```

不要由前端提交 `signer_user_id`、图片路径、附件 ID、版本号或 SHA256。后端应从认证用户和签名服务中获取这些信息。

## 八、图片校验与存储

### 8.1 上传规范

第一期建议统一为 PNG：

| 项目 | 规则 |
|---|---|
| 扩展名 | 仅 `.png` |
| MIME | 必须为 `image/png`，但不能只信任请求头 |
| 文件大小 | 最大 2 MB |
| 图片尺寸 | 宽高均在 100～2000 像素之间 |
| 解码校验 | 使用 Pillow 实际解码并执行 `verify()` |
| 标准化 | 服务端重新编码为 PNG，剥离元数据和潜在附加内容 |
| 背景 | 推荐透明背景；不强制自动抠图 |
| 文件名 | 使用服务端生成的 UUID 文件名，原文件名只作为元数据 |

仅检查扩展名不足以保证安全。重新解码和编码可以减少伪造图片、畸形文件、脚本混入和超大像素图片带来的风险。

### 8.2 推荐显示规格

- 管理端预览区域：约 `320 x 120 px`，使用 `object-fit: contain`；
- 业务表格签名：固定高度 `32～48 px`，宽度自适应且有最大值；
- PDF/Word 导出：按固定签名框等比缩放，禁止拉伸变形；
- 图片组件必须预留固定尺寸，加载成功或失败都不能导致表格布局跳动。

### 8.3 物理路径

沿用现有附件目录规范：

```text
{MEDIA_ROOT}/account_signature/{target_tenant_id}/{yyyyMM}/user_signature_{user_id}/{uuid}.png
```

示例：

```text
/data/spug/spug_api/media/account_signature/tenant_a/202607/user_signature_42/8f31....png
```

数据库只保存相对 `MEDIA_ROOT` 的路径。所有读取必须经过路径归一化检查，确保最终路径仍在 `MEDIA_ROOT` 下。

## 九、权限与租户隔离

### 9.1 权限矩阵

| 能力 | 超级管理员 | 账号本人 | 其他普通用户 | 业务模块 |
|---|---:|---:|---:|---:|
| 给账号赋予签名 | 是 | 否 | 否 | 否 |
| 替换/停用签名 | 是 | 否 | 否 | 否 |
| 查看管理备注和版本历史 | 是 | 否 | 否 | 否 |
| 查看本人当前签名 | 是 | 是 | 否 | 否 |
| 在本人有权限的业务中签署 | 可作为本人签署 | 是 | 是 | 发起服务调用 |
| 查看历史业务中的签名 | 按业务权限 | 按业务权限 | 按业务权限 | 按业务权限获取 |
| 获取签名物理路径 | 否 | 否 | 否 | 仅服务端渲染服务可获取文件流 |

项目中超级管理员字段为 `User.is_supper`，后端必须直接校验该字段。不能只依赖前端隐藏按钮，也不建议把“签名赋予”开放给普通管理员角色，因为手写签名图片属于高敏感身份资产。

### 9.2 租户规则

- 签名记录和附件的 `tenant_id` 一律取目标账号租户；
- 签署业务的租户必须与签署人租户一致，除非以后有明确的跨租户业务规则；
- 超级管理员可跨租户管理，但每次操作必须记录目标租户；
- 普通用户查询本人签名时同时按 `user_id` 和 `tenant_id` 过滤；
- 业务查询签名使用记录时先经过业务模块权限检查，再按租户过滤；
- 错误响应不泄露其他租户是否存在某账号或某附件。

## 十、审计与证据留痕

### 10.1 管理操作审计

以下动作必须调用现有 `save_audit_log`：

- 首次赋予签名；
- 替换签名；
- 停用签名；
- 重新启用签名；
- 查看或下载签名历史原图（如后续开放）。

审计快照至少包含：

```json
{
  "target_user_id": 42,
  "target_username": "zhangsan",
  "target_tenant_id": "tenant_a",
  "old_attachment_id": 120,
  "old_version": 2,
  "old_sha256": "...",
  "new_attachment_id": 126,
  "new_version": 3,
  "new_sha256": "...",
  "reason": "签名更新"
}
```

审计日志不保存图片 Base64、物理绝对路径或预览令牌。

### 10.2 实际签署证据事件

每次正式签署推荐创建 `EvidenceEvent`：

```json
{
  "signature_usage_id": 901,
  "signer_user_id": 42,
  "signer_name": "张三",
  "signature_attachment_id": 126,
  "signature_version": 3,
  "signature_sha256": "...",
  "business_snapshot_hash": "...",
  "module": "checksheet",
  "object_type": "daily_summary",
  "object_id": "2026-07-17-01",
  "scene_code": "operator"
}
```

这样可以分别发现：

- 图片文件被替换或损坏；
- 业务数据在签署后被修改；
- 签署记录与实际业务对象解绑；
- 同一请求被重复提交。

## 十一、前端交互设计

### 11.1 账号管理列表

在 `spug_web/src/pages/system/account/` 的账号列表中增加“签名状态”列：

- 已配置：显示小型签名预览和“已配置”状态；
- 未配置：显示“未配置”；
- 已停用：显示“已停用”；
- 操作列增加签名图标按钮，悬停提示“管理签名”；
- 该列和按钮仅超级管理员可见。

### 11.2 管理签名弹窗

弹窗包含：

- 目标账号、姓名和所属租户，只读展示；
- 当前签名预览、版本号、赋予人和赋予时间；
- 上传/替换按钮；
- 停用或重新启用按钮；
- 管理备注输入；
- 历史版本列表，默认折叠或分页展示；
- 替换前二次确认，明确提示“只影响后续签署，不影响历史记录”。

上传后先显示本地预览，管理员确认后才提交。前端校验只用于体验，后端仍需执行完整校验。

### 11.3 普通用户侧

个人中心可以只读展示“我的签名”：

- 已配置时显示当前图片和版本；
- 未配置时显示“尚未由超级管理员配置签名”；
- 不显示上传、替换、删除按钮；
- 不显示管理员备注或历史版本。

该入口不是第一期必需项。业务签署弹窗也可以直接提示签名状态。

### 11.4 业务签署确认框

确认框至少显示：

- 当前签署人姓名；
- 当前签名图片预览；
- 待签业务对象的关键摘要；
- “确认签署”主按钮和“取消”按钮；
- 无签名时禁用确认按钮，提示联系超级管理员配置；
- 图片加载失败时禁止签署，不能只显示姓名后继续提交；
- 提交期间按钮进入加载状态，结合 `request_id` 防止重复提交。

页面不应展示“本功能如何工作”等说明性大段文字，必要风险提示放在确认动作附近并保持简洁。

## 十二、业务模块接入规范

### 12.1 标准接入流程

```text
1. 用户打开业务签署弹窗
2. 前端查询本人当前签名并预览
3. 用户确认签署
4. 业务接口校验对象存在、租户、状态和用户权限
5. 服务端生成规范化业务快照
6. 调用 SignatureService.apply_signature(...)
7. 返回 SignatureUsage.id
8. 业务对象保存该 usage_id，并进入已签署状态
9. 返回签署人、签署时间和签名预览信息
```

### 12.2 业务快照规范

每个模块必须定义稳定的待签数据结构：

- 字段按固定规则排序；
- 日期、时间、空值、布尔值采用统一格式；
- 排除展示顺序、临时 URL、更新时间等非业务字段；
- JSON 使用 UTF-8 和固定分隔符序列化后计算 SHA256；
- 对敏感内容可只保存哈希和最小摘要，不在签名表复制完整正文。

### 12.3 签署后的修改

业务模块必须明确下列策略之一：

1. **锁定策略（推荐）**：签署后禁止修改关键字段，修改前必须撤回签名；
2. **自动失效策略**：关键字段变化后原签名显示“已失效”，要求重新签署；
3. **版本策略**：业务数据形成新版本，旧版本和旧签名继续保留。

不能在已签署业务数据被修改后继续把原签名显示为有效。

### 12.4 显示与导出

- 页面和导出均按 `SignatureUsage.signature_attachment_id` 读取历史版本；
- 不允许按签署人 ID读取其“当前签名”来渲染历史单据；
- 图片读取失败时显示“签名文件异常”，同时保留签署人、时间、版本和哈希；
- PDF/Word 导出在服务端通过 `get_signature_image_for_render()` 获取受控文件流；
- 导出文件可附带签署人、签署时间和签名版本等文本信息，避免只靠图片识别责任人。

## 十三、异常与并发处理

| 场景 | 处理方式 |
|---|---|
| 两名超级管理员同时替换同一账号签名 | 锁定 `AccountSignature`，后提交者基于新版本继续递增或返回冲突 |
| 上传文件成功但数据库提交失败 | 清理本次未引用的新文件，记录错误日志 |
| 替换签名时用户正在签署 | `apply_signature` 在事务内锁定当前绑定；最终使用某个完整版本，不出现半更新状态 |
| 用户重复点击确认 | 通过 `request_id` 幂等返回同一 `SignatureUsage` |
| 当前签名已停用 | 返回明确业务错误，不创建使用记录 |
| 账号已禁用或已删除 | 禁止新签署，历史记录继续可查 |
| 历史图片丢失或哈希不一致 | 不静默回退到当前签名，标记异常并记录安全日志 |
| 业务保存失败 | 同一事务回滚 `SignatureUsage` 和 `EvidenceEvent` |

## 十四、测试方案

### 14.1 后端单元测试

- 只有 `is_supper=True` 可以赋予、替换和停用；
- 普通管理员即使拥有账号编辑权限也不能管理签名；
- 跨租户赋予时附件归属目标账号租户；
- 非 PNG、伪造 MIME、损坏 PNG、超大文件和超大像素图片被拒绝；
- 替换后版本号递增，旧附件仍存在；
- 停用后查询本人返回不可用，历史使用仍可读取；
- `apply_signature` 不能为其他用户签署；
- 客户端伪造附件 ID、SHA256 或用户 ID 不影响服务端最终数据；
- 相同 `request_id` 不会生成重复签署；
- 签署使用记录创建后不能修改或删除；
- 文件哈希或业务快照哈希不一致时能识别异常。

### 14.2 接口测试

- 管理端五类接口的鉴权、参数错误和正常流程；
- 普通用户只能查看本人当前签名；
- 预览令牌过期、越权、附件不匹配时拒绝访问；
- 已删除账号、停用账号、停用签名均不能新签署；
- 审计日志字段完整且不含图片内容和绝对路径。

### 14.3 前端测试

- 账号列表签名状态展示正确；
- 非超级管理员看不到签名管理入口；
- 上传预览、替换确认、停用和重新启用交互正确；
- 签署弹窗在无签名、图片失败、提交中和提交成功状态下布局稳定；
- 小屏幕和常用桌面分辨率下文字、按钮和图片不重叠；
- 历史业务记录在签名替换后仍显示旧版本；
- 导出文件中的签名比例正确、不拉伸、不裁切。

### 14.4 数据一致性测试

- `AccountSignature.current_attachment_id` 必须指向相同用户和租户的附件；
- `SignatureUsage.signature_sha256` 与实际历史文件一致；
- `SignatureUsage.business_snapshot_hash` 可由规范化快照重算；
- 已被 `SignatureUsage` 引用的附件无法物理删除；
- 定期检查孤立附件、失效当前指针和跨租户错误引用。

### 第二阶段：签名公共调用能力

- 新增不可变 `SignatureUsage`；

### 第三阶段：首个业务模块接入

- 定义业务快照；
- 业务表关联 `signature_usage_id`；
- 明确签署后的锁定、撤回和重签规则；
- 页面详情和 PDF/Word 导出显示历史签名；
- 完成端到端测试后再推广到其他模块。

## 十六、验收标准

满足以下条件可认为公共能力验收通过：

1. 超级管理员能给任意有效账号赋予一张签名图片；
2. 普通用户和普通管理员不能上传、替换、停用任何签名；
3. 跨租户配置时数据归属正确且无越权读取；
4. 替换签名后，新业务使用新版本，历史业务仍使用旧版本；
5. 停用后无法新签署，但历史签名仍可查看和导出；
6. 每次赋予、替换、停用和实际签署都有完整审计记录；
7. 实际签署记录包含签名版本、图片哈希、业务哈希、签署人、时间和 IP；
8. 前端不能通过伪造用户 ID、附件 ID 或哈希实现代签；
9. 图片不通过公开静态 URL 暴露，预览访问经过鉴权或短期令牌；
10. 业务数据在签署后发生变化时，系统能够阻止修改或明确标记原签名失效。

## 十七、最终建议

本功能应作为独立的账号签名公共模块建设，而不是在每个业务模块中各自增加一套图片上传逻辑。推荐采用以下最小闭环：

```text
超级管理员集中赋予
  + 账号当前签名绑定
  + 附件不可覆盖版本
  + 用户明确确认签署
  + SignatureUsage 固化历史版本
  + AuditLog / EvidenceEvent 全程留痕
```

其中最关键的两条设计底线是：

1. “管理员给账号配置图片”不等于“管理员替账号完成签署”；
2. 历史业务永远读取签署时固化的图片版本，不能读取账号当前签名。

只要守住这两条边界，后续各模块就可以在不复制文件管理、权限和审计逻辑的前提下，稳定复用签名能力。
