# 资料库备份还原一致性修复方案

## 一、问题现象

资料库使用备份文件还原后，前端仍然显示部分文件；但点击预览、下载或打开时提示“文件不存在”。

实际情况是：这些文件的数据库记录仍然存在，但对应的物理文件已经不在 `storage/documents` 目录中。

## 二、根因分析

资料库文件由两部分组成：

1. 数据库元数据  
   存储文件名、大小、类型、所属文件夹、上传人、物理路径等信息。

2. 磁盘物理文件  
   存储在容器内 `/data/spug/spug_api/storage/documents`，Docker 中对应 `tdyw-documents` volume。

当前列表接口只查询数据库记录，不检查物理文件是否存在：

- `spug_api/apps/document/views/folder/views.py`
  - 根目录文件查询：`FileModel.objects.filter(folder__isnull=True)`
  - 指定文件夹文件查询：`FileModel.objects.filter(folder_id=folder_id)`

而预览、下载接口会检查物理文件：

- `spug_api/apps/document/views/file/download.py`
  - `os.path.exists(file.file_path)`

- `spug_api/apps/document/views/file/preview.py`
  - `os.path.exists(file.file_path)`

所以当数据库和文件卷不一致时，就会出现：

```text
列表可见 -> 打开时报文件不存在
```

部署配置中，数据库卷和资料库文件卷也是分开的：

- 数据库：`tdyw-mysql-data` 或 `mysql-data`
- 资料库文件：`tdyw-documents`

如果只恢复数据库，或恢复文件卷时没有清空旧数据/没有完整恢复，就会产生这种不一致。

## 三、问题性质

这是一个需要修复的 bug，准确说是“备份还原一致性缺陷”。

它不是前端缓存问题，也不是权限问题，而是资料库元数据和物理文件生命周期没有在备份还原流程中保持一致。

影响包括：

- 用户看到不可用文件，体验差。
- 批量下载、预览、Office 预览会失败。
- 运维无法直观看出哪些文件是真实可用的。
- 长期积累后，资料库数据可信度下降。

## 四、修复原则

不建议在文件列表接口中逐条执行 `os.path.exists()`。

原因：

- 文件列表是高频接口。
- 每页最多可能返回较多文件。
- 逐条访问磁盘会增加 I/O 压力。
- 文件越多，列表接口越慢。
- Docker volume 或网络存储场景下性能更不可控。

推荐修复方向是：

1. 备份时同时备份数据库和 `tdyw-documents` 文件卷。
2. 还原时同时还原数据库和 `tdyw-documents` 文件卷。
3. 还原后执行一次资料库一致性校验任务。
4. 对缺失物理文件的数据库记录进行标记或清理。

## 五、推荐修复方案

### 方案 A：修复备份/还原流程

这是首要修复。

备份必须包含：

```text
数据库 SQL
资料库文件卷 tdyw-documents
资料库分片卷 tdyw-document-chunks，可选
媒体附件卷 tdyw-media，按实际模块需要
```

还原时必须遵循：

1. 停止业务容器，避免还原过程中继续上传文件。
2. 恢复数据库。
3. 清空目标环境的 `tdyw-documents` 文件卷。
4. 恢复备份中的资料库文件。
5. 启动业务容器。
6. 执行资料库一致性校验。
7. 清除缓存。

关键点：还原文件卷前应该先清空目标资料库文件目录，否则旧文件可能残留；只恢复数据库则一定会出现缺失物理文件。

### 方案 B：新增资料库一致性校验命令

新增 Django management command，例如：

```text
spug_api/apps/document/management/commands/check_document_consistency.py
```

建议能力：

```bash
python manage.py check_document_consistency --dry-run
python manage.py check_document_consistency --mark-deleted
python manage.py check_document_consistency --hard-delete-records
```

默认使用 `--dry-run`，只输出问题，不修改数据。

扫描范围：

- `DocumentFilePrivate`
- `DocumentFilePublic`

检查内容：

- `file_path` 是否为空。
- `file_path` 是否在 `storage/documents` 安全目录下。
- `file_path` 对应物理文件是否存在。
- `thumbnail_path` 如果存在，缩略图是否存在。

处理策略：

1. 物理文件缺失，但数据库记录存在  
   推荐默认软删除：`is_deleted=True`，保留审计余地。

2. 缩略图缺失，但原文件存在  
   不删除文件记录，只清空 `thumbnail_path` 或等待重新生成缩略图。

3. 路径不安全  
   标记为异常，优先人工确认，不自动删除物理文件。

4. 数据库记录已软删除但物理文件存在  
   可交给现有清理任务或单独增加回收站清理策略。

### 方案 C：还原完成后自动执行一致性校验

如果项目后续提供自动还原脚本，应在还原脚本最后增加：

```bash
python manage.py check_document_consistency --dry-run
```

确认输出无异常后，再执行：

```bash
python manage.py check_document_consistency --mark-deleted
```

如果是生产环境，建议先导出异常清单，让管理员确认后再执行清理。

### 方案 D：前端增加异常提示，作为辅助优化

后端列表接口可以选择额外返回文件状态字段，但不建议每次实时检查磁盘。

更合适的方式是：

- 一致性校验任务发现缺失文件后，将记录标记为异常或软删除。
- 前端列表默认不显示已软删除文件。
- 管理员可在“资料库健康检查”或“系统维护”页面查看异常文件清单。

如果要新增字段，建议命名：

```text
physical_status
```

可选值：

```text
OK
MISSING
UNSAFE_PATH
UNKNOWN
```

但该字段应由离线校验任务维护，不应由列表接口逐次计算。

## 六、落地步骤

### 第一步：补充备份规范

更新部署和备份文档，明确资料库备份不是只备份 SQL。

必须同时备份：

```text
tdyw-mysql-data
tdyw-documents
```

如使用开发环境，则对应：

```text
mysql-data
tdyw-documents
```

### 第二步：新增一致性校验命令

实现一个只面向运维使用的 Django 命令。

建议输出格式：

```text
space,file_id,file_name,file_path,status,reason
private,123,xxx.docx,/data/spug/spug_api/storage/documents/private/user-1/xxx.docx,MISSING,file not found
public,456,yyy.pdf,/data/spug/spug_api/storage/documents/public/yyy.pdf,OK,
```

### 第三步：先 dry-run 验证

在测试环境执行：

```bash
python manage.py check_document_consistency --dry-run
```

确认异常数量和用户反馈一致。

### 第四步：执行软删除清理

确认无误后执行：

```bash
python manage.py check_document_consistency --mark-deleted
```

软删除后，资料库列表将不再显示这些缺失物理文件的记录。

### 第五步：补充回归测试

需要覆盖：

- 正常文件存在时不处理。
- 物理文件缺失时 dry-run 只报告，不修改。
- 物理文件缺失时 mark-deleted 会软删除记录。
- 公共空间和私有空间都能扫描。
- 非法路径不会被自动删除。
- 缩略图缺失不会误删原文件记录。

## 七、临时处置方案

如果当前生产环境已经出现幽灵文件，推荐临时处理流程：

1. 先完整备份当前数据库。
2. 执行一致性检查脚本，只生成缺失文件清单。
3. 人工确认这些文件确实不需要恢复。
4. 将缺失文件对应记录软删除。
5. 刷新资料库前端确认文件不再显示。

不建议直接手工删除数据库记录。

原因：

- 可能影响回收站逻辑。
- 可能影响审计追踪。
- 可能破坏外键关系。
- 误删后不容易恢复。

## 八、验收标准

修复完成后应满足：

1. 只恢复数据库但未恢复文件卷时，系统能通过一致性校验发现缺失文件。
2. 执行软删除清理后，前端资料库列表不再显示缺失物理文件。
3. 正常文件仍可预览、下载。
4. 公共空间、私有空间均不受影响。
5. 备份还原文档明确要求数据库和资料库文件卷一起备份、一起恢复。

## 九、最终建议

优先级建议定为 P1。

推荐按下面顺序修复：

1. 先补备份/还原文档，避免继续产生新问题。
2. 再加资料库一致性校验命令，用于清理历史脏数据。
3. 最后考虑在系统维护页增加可视化检查入口。

不建议把主要修复放在前端，也不建议在文件列表接口里实时检查磁盘。最稳妥的修复点是备份还原流程和后端一致性校验任务。

## 十、脚本层修复重点补充

结合当前项目结构，本问题的优先修复点应放在 `backups` 目录中的资料库文件备份/还原脚本：

- `backups/documents_incremental_backup.sh`
- `backups/documents_restore.sh`

前面提到的 Django 一致性校验命令适合作为还原后的兜底检查，但不应作为第一修复点。第一修复点应该是保证资料库文件备份本身完整、还原顺序正确、还原后可校验。

### 10.1 `documents_incremental_backup.sh` 的风险

当前增量备份基于 `mtime`：

```bash
find "${DOCUMENTS_PATH}" -type f -newer "${CONTAINER_MARKER}"
```

这会遗漏部分真实需要备份的文件。

典型风险场景：

1. 文件通过复制、迁移、解压、还原等方式进入 `storage/documents`，保留了旧 `mtime`。
2. 数据库已经记录了该文件，但文件 `mtime` 早于增量备份 marker。
3. 增量备份不会包含该物理文件。
4. 还原数据库后，资料库前端能看到记录，但文件卷中没有对应文件。
5. 打开、预览或下载时报“文件不存在”。

因此，增量备份不能只依赖 `mtime`。

### 10.2 `documents_incremental_backup.sh` 建议修改

建议做以下修改：

1. 增量文件发现逻辑同时考虑 `mtime` 和 `ctime`。

示例方向：

```bash
find "${DOCUMENTS_PATH}" -type f \( -newer "${CONTAINER_MARKER}" -o -cnewer "${CONTAINER_MARKER}" \) -printf '%P\n'
```

2. 每次备份生成 manifest 文件。

建议 manifest 至少包含：

```text
relative_path
size
mtime
ctime 或 stat change time
sha256，可选
```

3. 每个备份包旁边保存元信息。

建议生成：

```text
documents_full_YYYYmmdd_HHMMSS.tar.gz
documents_full_YYYYmmdd_HHMMSS.manifest
documents_full_YYYYmmdd_HHMMSS.meta

documents_incr_YYYYmmdd_HHMMSS.tar.gz
documents_incr_YYYYmmdd_HHMMSS.manifest
documents_incr_YYYYmmdd_HHMMSS.meta
```

4. meta 文件建议记录：

```text
backup_type
backup_started_at
backup_finished_at
app_container
documents_path
file_count
archive_name
base_marker_time
```

5. 增量备份如果文件数为 0，也应该生成一份 meta 或日志记录，方便审计。

6. 如果后续需要支持“删除同步”，可增加 deleted manifest。

当前恢复脚本默认清空目标目录再恢复全量和增量，因此删除同步不是最高优先级；但如果未来支持不清空目标目录的覆盖式恢复，就必须记录删除清单。

### 10.3 `documents_restore.sh` 建议修改

当前脚本已有正确方向：

```bash
CLEAR_TARGET="${CLEAR_TARGET:-YES}"
```

也就是默认清空目标 `storage/documents` 后再恢复，这可以避免旧文件残留。

建议继续增强：

1. 保持 `CLEAR_TARGET=YES` 作为默认值。
2. 对全量包执行 `tar tzf` 校验。
3. 对每个增量包执行 `tar tzf` 校验。
4. 按时间顺序应用全量后的增量包。
5. 如果存在 manifest，恢复后比对 manifest 中的文件是否都存在。
6. 输出恢复报告：

```text
full_backup
incremental_count
restored_file_count
missing_from_manifest_count
target_documents_path
```

7. 在脚本提示中明确：必须选择与数据库备份时间点匹配的 documents 全量包和增量包。

8. 还原完成后提示执行资料库一致性检查。

如果暂时没有 Django management command，可以先提示人工检查；如果后续实现了命令，则提示：

```bash
python manage.py check_document_consistency --dry-run
```

### 10.4 数据库备份与 documents 备份的时间点一致性

只修复 documents 脚本还不够，还需要明确数据库备份和文件备份的配套关系。

推荐规则：

1. 数据库备份和 documents 备份必须来自同一备份周期。
2. 恢复数据库时，必须恢复同周期的 documents 全量包和其后的必要增量包。
3. 如果数据库备份时间晚于 documents 文件备份时间，可能出现数据库记录存在但物理文件缺失。
4. 如果 documents 文件备份时间晚于数据库备份时间，可能出现物理文件存在但数据库记录不存在。

因此，备份维护手册中应明确恢复顺序：

```text
停止业务容器
恢复数据库
清空 storage/documents
恢复 documents 全量包
按顺序恢复对应增量包
启动业务容器
执行一致性检查
清理缓存
```

可以使用下面的提示词让 Codex 按本方案执行：

```text

重点说明：
本次优先修复 backups/documents_incremental_backup.sh 和 backups/documents_restore.sh。
不要把主要修复放在前端列表接口，也不要在资料库列表接口中逐条执行 os.path.exists()。
Django management command 可以作为还原后兜底校验，但不是本次第一优先级。

具体要求：
1. 先阅读以下文件，不要直接改：
   - 资料库备份还原一致性修复方案.md
   - backups/documents_incremental_backup.sh
   - backups/documents_restore.sh
   - backups/备份维护手册.md
   - backups/修改建议.md

2. 修改 backups/documents_incremental_backup.sh：
   - 修复增量备份只依赖 mtime 的问题。
   - 增量文件发现逻辑至少同时考虑 mtime 和 ctime，例如 -newer marker 或 -cnewer marker。
   - 保持全量备份逻辑兼容。
   - 为全量和增量备份生成 manifest 文件。
   - manifest 至少记录相对路径、文件大小、mtime，能记录 ctime 或 sha256 更好。

3. 修改 backups/documents_restore.sh：
   - 保持 CLEAR_TARGET=YES 作为默认行为。
   - 恢复前校验全量 tar 包。
   - 恢复前校验所有待应用的增量 tar 包。

   - 明确恢复顺序：停止业务 -> 恢复数据库 -> 清空 documents -> 恢复 full -> 恢复 incrementals -> 启动业务 -> 一致性检查。
   - 说明 mtime-only 增量备份的风险已经修复为 mtime+ctime。

5. 不要修改无关业务代码。
6. 不要重构资料库模块。
7. 完成后运行 shell 语法检查，例如：
   - bash -n backups/documents_incremental_backup.sh
   - bash -n backups/documents_restore.sh
8. 如果环境无法运行 bash，说明原因，并至少做静态检查和关键逻辑复核。
9. 最后汇报修改了哪些文件、修复了什么风险、如何验证。
```
