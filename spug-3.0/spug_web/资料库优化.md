按 vibe coding 风格写通导运维平台的文件上传功能，要求如下：
技术栈：前端 React（AntD 组件）+ 后端 Django 2.2（仅用 2.2 原生特性 + 兼容库），部署在国企内网，无外网依赖
上传规则：仅针对资料库模块，文件大小 > 10MB 触发分片上传（每片 5MB），≤10MB 走普通上传
前端核心（解决性能 / 体验风险）：
基于 AntD Upload 组件封装，自定义进度条（覆盖 onProgress），总进度 = (已传分片大小之和 / 文件总大小) * 100%
分片上传：
用 spark-md5 库增量计算文件 MD5（放入 Web Worker，避免阻塞主线程），加「MD5 计算中...」loading 提示
实现秒传（MD5 校验后端是否已存在文件）、断点续传（记录已传分片）、失败自动重试（最多 3 次）
普通上传：仅做格式（pdf/zip/bin/txt/log）/ 大小校验，简化逻辑
加磁盘使用率校验：调用后端监控接口，磁盘使用率≥85% 时禁止上传并提示
后端核心（解决存储 / 并发风险）：
分片存储：按 {文件 MD5}/ 子目录存放分片（格式：/tmp/upload/{md5}/{分片序号}.part），开发环境存储路径不同，部署时需修改配置
分片接收：校验分片序号 / 总数，避免重复接收
文件合并：
合并接口仅记录任务状态（待合并 / 合并中 / 完成 / 失败），立即返回，不阻塞 Worker
前端轮询「合并状态查询接口」获取结果，合并操作加超时控制（最长 300 秒）
普通文件：直接存储到 MEDIA_ROOT 目录
兼容 Django2.2：禁用新版本特性（如异步视图），第三方库选 2.2 兼容版本
运维保障（解决运维风险）：
垃圾清理：用 django-crontab 实现定时任务（每天凌晨），清理 24 小时未合并的 MD5 子目录；补充操作系统级 cron 方案（部署文档说明）
存储监控：写接口返回上传目录磁盘使用率（df -h 解析），前端做阈值判断
文件访问：合并后的文件存 MEDIA_ROOT，配置 Nginx 反向代理 MEDIA_URL 提供下载 / 预览，接口加用户权限校验（仅授权可访问）
其他：代码加中文注释，适配内网（无跨域 / 云存储），易理解、易部署，加审计日志（记录上传人 / 时间 / 文件 MD5）
三、给你的实操小贴士（确保 AI 代码落地无坑）
1. Django2.2 兼容注意点
告诉 AI：「禁用 Django3.0 + 的 async/await、QuerySet 异步方法，用 django-crontab==0.7.1（兼容 2.2）」；
若 AI 写了 Celery 相关代码，补充：「仅在文件 > 1GB 时启用 Celery 异步合并，否则用同步合并（内网极少有超大文件）」。
2. 内网部署简化点
spark-md5 库：让 AI 把库文件直接嵌入前端代码（不用 npm 安装，避免内网 npm 源问题）；
定时任务：部署时先测试python manage.py crontab add是否生效，若失败，直接用系统 cron（0 0 * * * python /项目路径/manage.py clean_unmerged_chunks）。
3. AI 代码校验清单（你只需查这 5 点）
前端：MD5 计算是否用 Worker + 增量、进度条是否手动聚合、磁盘使用率是否校验；
后端：分片是否按 MD5 建目录、合并接口是否异步返回状态、定时任务是否配置；
存储：文件是否存 MEDIA_ROOT、Nginx 配置是否包含 MEDIA_URL 反向代理；
合规：上传 / 下载是否有审计日志、权限校验；
兼容：是否用到 Django2.2 不支持的特性。
