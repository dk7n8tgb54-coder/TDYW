# 系统升级模块改造方案

> 范围：① 升级方案步骤的"阶段"可自定义；② 状态时间线"记录状态"交互简化。

---

## 一、步骤阶段自定义

### 现状问题
- `UpgradePlanStep.phase` / `UpgradeRecordStep.phase`（`max_length=20`）存的是固定枚举 value（`start`/`backup`/`gray_release`/`test`/`full_release`/`observe`），共 6 个执行阶段。
- 前端两处用 `Select` 下拉只能选这 6 个：`plan/PlanForm.js:206`（构建方案）、`WorkbenchForm.js:777`（升级表单添加步骤）。
- 实际升级步骤数量、阶段名称因系统而异，固定 6 项不够灵活。

### 方案：AutoComplete（预设 + 自由输入）
将"阶段"由"枚举选择"改为"可输入的预设候选"——保留 6 个预设阶段作为快捷候选，同时允许自由输入任意阶段名。

**字段语义调整**：`phase` 字段由"存枚举 value"改为"直接存阶段显示名（中文）"。
- 预设阶段：直接存中文 label（如"备份"），不再存 `backup`。
- 自定义阶段：存用户输入文本。
- 老数据迁移：`UPDATE` 把 value 替换为 label（`start→升级启动`、`backup→备份`、`gray_release→灰度发布`、`test→升级测试`、`full_release→全量发布`、`observe→上线观察期`），空串保持空。

> 不采用"方案级先定义阶段再选"的方案——增加一层管理负担，YAGNI。AutoComplete 一处输入即完成，最轻量。

### 改动点

**后端**
- `models_template.py` / `models_checklist.py`：`phase` 字段注释更新（语义为显示名），`max_length` 由 20 调到 50（中文阶段名可能更长）。
- 新增迁移：① `AlterField` 放宽 max_length；② `RunSQL` 做 value→label 回填（按 `PHASE_LABEL_MAP` 映射）。
- `constants.py`：`UPGRADE_PHASES` 保留（作为前端预设候选 + 历史系统合并来源），`PHASE_LABEL_MAP`/`PHASE_ORDER` 保留供状态时间线参考条使用（与步骤阶段解耦，不受影响）。
- `services/record_service.py` 的 `get_filter_options`：`phases` 仍返回预设 6 项（作为候选），同时可合并历史步骤中出现过的自定义阶段名（去重），让候选越来越贴合实际。
- 序列化/校验：`phase` 非枚举校验，仅做长度/空白处理。

**前端**
- `plan/PlanForm.js:206`、`WorkbenchForm.js:777`：`Select` → `AutoComplete`，`dataSource` 取预设 + 历史自定义阶段，允许任意输入，`allowClear`。
- `WorkbenchForm.js:462` `renderStepsPanel` 分组逻辑改写：不再用 `phaseOrder`/`phaseLabel` 映射，改为按 `step.phase` 文本直接分组，组顺序按"首次出现顺序"（保序去重），空 phase 归"未分组"。
- `WorkbenchForm.js:245` `handlePrintSteps` 打印分组同步改为按文本分组（逻辑与展示一致，复用一个分组函数）。
- `shared.js`：步骤分组辅助函数抽出（展示/打印复用）。

### 不受影响
- 状态时间线参考条（`STANDARD_FLOW` 7 节点）、状态动作（12 种 `ACTION_CHOICES`）、流程归约 `computeFlowState`——这些是"升级里程碑"，与"步骤阶段"是两套独立概念，本次不动。
- 步骤排序仍由 `sequence` 字段决定，`phase` 仅用于分组展示，改语义不影响排序。

### 注意事项
- 迁移用 `makemigrations upgrade` 指定 app（避免扫描全项目）。
- 回填 SQL 用 `CASE WHEN` 一次性更新，避免多次 ALTER。
- 老数据 value 若不在映射表（脏数据）原样保留，归"未分组"显示。

## 二、状态时间线"记录状态"交互简化

### 现状问题
当前流程：点"记录状态"按钮 → 弹 Modal → 选动作类型（12 选 1）→ （回退还要选目标）→ （跳步要勾 switch）→ 填备注 → 确认。每次记录至少 3 次点击 + 1 次弹窗，操作被打断。

### 方案：Dropdown 快捷动作 + 智能顺位 + 仅特殊情况弹窗
把"记录状态"按钮改为 `Dropdown` 菜单，按当前流程进度智能排列动作；顺位动作一键提交，仅回退/跳步需轻量确认。

**交互规则：**
1. **菜单分组**：
   - 「下一步」（高亮）：根据 `computeFlowState(statusLogs)` 的 `currentIndex` 推算下一个主线动作（如当前在"备份"，下一步=灰度发布完成），置顶高亮。
   - 「异常/分支动作」：测试失败、暂停、继续、回退。
   - 「补录其他节点」：其余主线动作（用于跳步补录）。
2. **顺位动作**（下一步/暂停/继续/测试失败）：点击 → 用 `Popconfirm` 带 `TextArea` 的轻量确认（备注选填）→ 提交。比 Modal 轻，不离开当前页面上下文。
3. **回退**：点击 → 弹小 `Modal` 仅含"回退到"单选（`ROLLBACK_TARGETS`，默认选当前节点的上一个）+ 备注 → 确认。
4. **补录跳步**（点非顺位主线动作）：自动视为 `is_override=true`，弹小 `Modal` 仅含备注（必填）→ 确认。

> 不采用"全部一键提交无确认"——回退需选目标、跳步需备注说明，后端有强校验，必须收集信息；但用 Popconfirm/小 Modal 替代当前大 Modal，且顺位动作默认无需填表，大幅减少打断。

### 改动点

**前端（`WorkbenchForm.js`）**
- 第 335 行"记录状态" `Button` → 包裹 `Dropdown`，`overlay` 为动作菜单（`Menu` 分组 + `Menu.Item`，每项带颜色 `Tag`）。
- 新增 `handleQuickLog(action, opts)`：根据 action 类型走不同确认流程（Popconfirm 直提 / 小 Modal 收集 target_action 或 remark），复用现有 `handleAddStatusLog` 提交逻辑。
- 顺位判断：调用 `computeFlowState(store.statusLogs)` 取 `currentIndex`，映射出"下一个主线 action"。
- 现有大 `Modal`（735-770 行）保留作为"高级/补录"入口（菜单底部"更多…"打开），或移除——倾向移除，避免双入口。
- 菜单项 `disabled` 规则：无日志时"回退/继续"禁用；已完成时除"回退"外禁用。

**后端**
- 无需改动。`status-log` 创建接口已支持 `action`/`target_action`/`is_override`/`remark`，前端按规则传参即可。顺序校验逻辑（`_compute_current_index`）保持不变，非法顺序由后端拒绝并返回错误，前端 catch 后提示"需补录请走补录入口"。

### 交互细节
- Popconfirm 备注框：`TextArea` 1 行，回车提交，Esc 取消。
- 回退小 Modal：`target_action` 默认选 `currentIndex` 对应节点的前一个主线节点（最常见回退目标）。
- 提交成功后 `store.statusLogs` 前插新日志（已有逻辑），参考条/时间线自动刷新。
- 失败时 `message.error(res.msg)` 提示原因（如"前置节点未完成，请勾选补录"）。

## 三、实施顺序建议
1. 先做需求一（阶段自定义）：后端迁移 + 前端 AutoComplete + 分组逻辑改写。
2. 再做需求二（状态记录简化）：纯前端改造，独立可测。
3. 各自验证：`read_lints` + 容器内 `py_compile` + 手动走查构建方案/记录状态流程。
