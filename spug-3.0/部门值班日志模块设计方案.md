# 部门值班日志模块设计方案

> 状态：可进入实施评审
> 日期：2026-07-17
> 负责模块：`apps.department_duty_log`（新建独立 app）
> 适用场景：机房、基站等技术值守的日常环境参数与值班情况记录

---

## 一、方案总览

本模块采用以下设计：

1. 新建 `apps.department_duty_log`，不与 `apps.duty` 共表。
2. `duty_date` 使用 `DateField`，保证日期查询、排序和索引语义正确。
3. 市电和 UPS 均采用文本字段，完整保存值班员输入，接受 `220V`、`220伏`、`正常`、`停电`、`检修` 等混合值。
4. `department_name` 作为必填快照字段；若后续建立部门主数据，再增加外键并迁移，不能用历史下拉值冒充主数据。
5. 值班员选择租户内有效用户，保存用户 ID 和姓名快照；创建人仍由系统记录，二者语义不同。
6. `duty_record` 必填，空日志不允许落库。
7. 采用软删除并记录审计，不提供物理删除入口。

## 二、模块定位与业务边界

### 2.1 与现有模块的关系

| 模块 | app | 职责 | 与本模块关系 |
|---|---|---|---|
| 值班日志 | `apps.duty` | 行政值班事项聚合，支持从运行日志、干扰记录引入 | 保持不变，不复用其数据表和 PDF 模板 |
| 部门值班日检查单 | `apps.checksheet` | 基于模板逐项检查，含提交、复核、归档流程 | 本模块不复用状态机和模板模型 |
| 部门值班日志 | `apps.department_duty_log` | 记录技术值守参数、供电情况和当班情况 | 新建独立 app；只复用租户、权限、审计等基础能力 |

### 2.2 实施范围

当前实施范围包括：

- 值班日志新增、查看、编辑、软删除；
- 按日期、值班员、部门筛选；
- 服务端分页与默认排序；
- 市电和 UPS 情况记录；
- 租户隔离、方法级权限、操作审计；
- 多人编辑冲突检测；
- 列表、详情和表单的桌面端/窄屏适配。

当前实施范围不包括：

- 从 `duty`、`runlog`、`interference` 自动导入；
- 检查项模板、提交、复核、归档状态机；
- PDF/Excel 导出；
- 电压趋势图和自动告警；
- 附件、交接班、班次排班；
- 回收站和永久删除。

上述功能没有明确业务需求时不预埋空接口或空字段；但数据类型应保证后续可以低成本统计和扩展。

## 四、数据模型

### 4.1 字段设计

| 字段 | 类型 | 必填 | 来源/约束 | 说明 |
|---|---|---:|---|---|
| `id` | `AutoField` | 是 | 系统生成 | 主键 |
| `tenant_id` | `CharField(50)` | 是 | `make_tenant_id()`，服务端赋值 | 租户隔离键，客户端不得传入或修改 |
| `duty_date` | `DateField` | 是 | `YYYY-MM-DD` | 支持正确的日期比较、排序和索引 |
| `duty_person` | `ForeignKey(User, PROTECT)` | 是 | 仅限目标租户内有效用户 | 值班员账号 |
| `duty_person_name` | `CharField(100)` | 是 | 服务端从用户昵称/账号生成 | 姓名快照，避免账号资料变更影响历史显示 |
| `department_name` | `CharField(100)` | 是 | 去首尾空格，1~100 字符 | 部门快照；当前尚无部门主数据可关联 |
| `mains_voltage` | `CharField(50)` | 否 | 去首尾空格，最长 50 字符 | 市电情况原文，如 `220V`、`正常`、`停电检修` |
| `ups_voltage` | `CharField(50)` | 否 | 去首尾空格，最长 50 字符 | UPS 情况原文，如 `220伏`、`正常`、`旁路` |
| `weather` | `CharField(50)` | 否 | 去首尾空格 | 天气简述 |
| `duty_record` | `TextField` | 是 | 去首尾空格，1~10000 字符 | 当班情况，是日志的核心内容 |
| `remark` | `TextField` | 否 | 最长 2000 字符 | 补充说明，不替代值班记录 |
| `version` | `PositiveIntegerField` | 是 | 默认 1，每次编辑加 1 | 乐观锁，防止静默覆盖 |
| `created_at` | `CharField(20)` | 是 | `human_datetime` | 沿用项目审计时间格式 |
| `created_by` | `ForeignKey(User, PROTECT)` | 是 | 当前登录用户 | 填报人 |
| `updated_at` | `CharField(20)` | 否 | 服务端生成 | 最近修改时间 |
| `updated_by` | `ForeignKey(User, PROTECT)` | 否 | 当前登录用户 | 最近修改人 |
| `deleted_at` | `CharField(20)` | 否 | 服务端生成 | 非空表示已软删除 |
| `deleted_by` | `ForeignKey(User, PROTECT)` | 否 | 当前登录用户 | 删除操作人 |

设计说明：

- `duty_person` 和 `created_by` 不能合并。前者是实际值班人员，后者是录入系统的人，允许代录。
- 部门不应设计成可空，否则模块最重要的筛选维度会大量出现空值。当前项目没有部门主数据，所以先保存名称快照；历史值只可用于输入建议，不作为合法性校验来源。
- 市电和 UPS 字段按原文保存，不解析数值、不自动补单位、不推断状态，确保记录与实际填写内容一致。
- `DateField` 与仓库内合同、规章、运行日志等模型保持一致，确保日期字段具备明确类型。
- 软删除后默认查询必须加 `deleted_at__isnull=True`。`TenantModelManager` 不会自动排除软删除数据，不能遗漏此条件。

### 4.2 输入校验

服务端统一执行以下校验，不能只依赖前端：

1. 日期必须是合法的 `YYYY-MM-DD`；默认不允许晚于当前自然日。若后续确认存在预填需求，再放开未来日期。
2. 值班员必须存在、有效、未删除，并与日志 `tenant_id` 一致。
3. 部门、值班记录去除首尾空白后不能为空。
4. 市电和 UPS 可为空；非空时去除首尾空格并限制为 50 字符，内容按原文保存。
5. 客户端传入的 `tenant_id`、创建人、修改人、删除人和版本增量一律忽略，由服务端控制。

### 4.3 索引

```python
class Meta:
    db_table = 'tdyw_department_duty_log'
    ordering = ('-duty_date', '-id')
    indexes = [
        models.Index(
            fields=['tenant_id', 'deleted_at', 'duty_date'],
            name='department_duty_tenant_del_ix',
        ),
        models.Index(
            fields=['tenant_id', 'duty_person', 'duty_date'],
            name='department_duty_person_date_ix',
        ),
    ]
```

不增加 `(tenant_id, department_name, duty_date, duty_person)` 唯一约束，因为同一人同一天可能有多条记录。保存按钮在请求期间必须禁用，防止双击重复创建；若后续出现网络重试导致的重复数据，再引入请求幂等键。

### 4.4 并发更新

编辑请求必须携带当前 `version`。后端更新条件同时包含 `id`、租户、`deleted_at IS NULL` 和 `version`：

```python
updated = queryset.filter(version=form.version).update(
    # 业务字段省略
    version=F('version') + 1,
    updated_at=human_datetime(),
    updated_by=request.user,
)
if updated == 0:
    return json_response(error='记录已被他人修改，请刷新后重试')
```

这比“最后一次保存覆盖前一次保存”更适合多人值守场景。前端收到冲突后保留用户输入并提示刷新对比，不应直接关闭表单。

## 五、后端接口

### 5.1 路由

```python
urlpatterns = [
    path('records/', DepartmentDutyLogListCreateView.as_view()),
    path('records/<int:pk>/', DepartmentDutyLogDetailView.as_view()),
    path('options/', DepartmentDutyLogOptionsView.as_view()),
]
```

| 方法 | 路径 | 权限 | 功能 |
|---|---|---|---|
| GET | `/api/department-duty-log/records/` | `view` | 服务端筛选、排序、分页 |
| POST | `/api/department-duty-log/records/` | `add` | 新建并返回完整记录 |
| GET | `/api/department-duty-log/records/{id}/` | `view` | 查看单条详情 |
| PUT | `/api/department-duty-log/records/{id}/` | `edit` | 带版本号更新 |
| DELETE | `/api/department-duty-log/records/{id}/` | `del` | 软删除 |
| GET | `/api/department-duty-log/options/` | `view` | 返回租户内值班员及轻量筛选选项 |

新增、编辑、删除分别使用 POST、PUT、DELETE。现有前端 `http.put` 和 `http.delete` 已被多个模块使用。按方法拆分后，`@auth` 可以精确授权，审计中间件也能正确识别 create/update/delete。

### 5.2 列表查询

查询参数：

| 参数 | 类型 | 默认值 | 规则 |
|---|---|---|---|
| `page` | int | 1 | 最小 1 |
| `page_size` | int | 20 | 1~100 |
| `start_date` | date | 当前日期前 30 天 | 与 `end_date` 均为闭区间 |
| `end_date` | date | 当前日期 | 不得早于 `start_date` |
| `duty_person_id` | int | 空 | 精确匹配 |
| `department_name` | string | 空 | 精确匹配，由选项选择 |
| `keyword` | string | 空 | 对值班记录、备注做 `icontains`，最长 100 字符 |

处理顺序：租户和未删除过滤 -> 参数校验 -> 业务筛选 -> `count()` -> `select_related()` -> 排序 -> 分页切片。禁止把全部记录序列化后交给前端筛选。

响应结构：

```json
{
  "error": "",
  "data": {
    "records": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  }
}
```

所有列表项应包含 `version`、创建人/修改人姓名；日期在序列化函数中显式转换，不能依赖 `ModelMixin.to_dict()` 的隐式行为。

### 5.3 选项接口

`options/` 返回：

```json
{
  "duty_persons": [{"id": 1, "name": "张三"}],
  "departments": ["技术保障部"]
}
```

- 值班员仅返回目标租户内有效、未删除用户；普通用户不得获得其他租户人员信息。
- 部门列表来自当前租户未删除日志的去重值，仅用于输入建议。创建/编辑仍允许输入新部门，直至部门主数据模块上线。
- 若超级管理员可跨租户查看列表，必须显式选择目标租户后才允许新增；不能默认把记录写入任意或不明确的租户。当前没有租户选择控件时，超管新增仍写入自身 `tenant_id`，并在 UI 明示当前租户。

### 5.4 权限和租户边界

每个方法使用单一权限装饰器：

```python
@auth('department_duty_log.department_duty_log.add')
def post(...):
    ...

@auth('department_duty_log.department_duty_log.edit')
def put(...):
    ...
```

读、改、删单条记录时统一从以下基础 QuerySet 开始：

```python
DepartmentDutyLog.objects.for_user(request.user).filter(
    deleted_at__isnull=True,
    pk=pk,
)
```

注意：当前 `apply_tenant_filter` 在非严格模式下允许超级管理员和全局管理员查看全部租户。查看权限与写入权限不能混为一谈；更新、删除仍需先确定目标记录，再校验请求中的关联值班员属于该记录的租户，禁止借助全局可见性建立跨租户关联。

### 5.5 审计

在 `TARGET_MAP` 注册：

```python
'/department-duty-log/': {
    'type': 'department_duty_log',
    'name': '部门值班日志',
},
```

新增、编辑、删除成功后调用 `record_audit_event`，从而提供明确的目标 ID 并避免被中间件记成“未知对象”。审计详情原则：

- 新增：记录目标 ID、日期、值班员、部门及市电/UPS 原文摘要，不重复存整段值班记录；
- 编辑：记录 `changed_fields` 及关键字段的 `before/after`，长文本只记录摘要或哈希；
- 删除：记录删除前的日期、值班员、部门和版本；
- 业务校验失败由现有审计中间件记录失败结果；
- 不记录 `tenant_id` 的客户端输入，因为客户端无权控制该字段。

业务表软删除保留原数据，审计日志保留“谁在何时执行了什么操作”，两者职责不同，不能互相替代。

## 六、前端设计

### 6.1 目录

```text
spug_web/src/pages/departmentDutyLog/
├── index.js                         # 导出 DepartmentDutyLogIndex
├── departmentDutyLogStore.js        # DepartmentDutyLogStore
├── DepartmentDutyLogTable.js        # DepartmentDutyLogTable
├── DepartmentDutyLogForm.js         # DepartmentDutyLogForm
└── DepartmentDutyLogDetail.js       # DepartmentDutyLogDetail
```

`DepartmentDutyLogStore` 负责保存查询条件、分页信息、请求状态和弹窗状态；列表数据始终通过服务端分页接口加载。

### 6.2 页面布局与交互

- 搜索区：日期范围、值班员、部门、关键字；提供查询和重置。
- 表格区：日期、值班员、部门、市电、UPS、天气、值班记录摘要、更新时间、操作。
- 市电和 UPS 按录入原文显示，不自动补 `V` 或“伏”；空值显示 `--`。
- 值班记录列表只显示 1~2 行摘要；完整内容在详情抽屉中按原换行展示。不要用 hover 承载长文本。
- 表格采用服务端分页，页码和每页条数写入 store；筛选变化回到第 1 页。
- 新建/编辑提交期间禁用保存按钮，避免重复请求。
- 删除前二次确认，文案明确为“移出当前列表”，不宣称永久删除。
- 无 `edit`/`del` 权限时不渲染相应操作；后端仍必须独立校验。

### 6.3 表单

字段顺序：

1. 值班日期，必填；
2. 值班员，必填，从租户有效用户中选择；
3. 部门，必填，支持输入与历史建议；
4. 市电情况，允许填写 `220V`、`正常`、`停电检修` 等内容；
5. UPS 情况，允许填写 `220伏`、`正常`、`旁路` 等内容；
6. 天气；
7. 值班记录，必填，显示字数；
8. 备注，可选。

市电和 UPS 使用普通文本输入框，最大长度 50 字符。前端不得改写用户输入或根据内容自动判断状态；后端只负责去除首尾空格和长度校验。

编辑表单必须保存加载时的 `version`。发生版本冲突时展示“记录已更新”提示，并保留尚未提交的表单内容供用户对比。

## 八、测试与验收标准

### 8.1 后端自动化测试

至少新增 `spug_api/apps/department_duty_log/tests.py`，覆盖：

| 编号 | 场景 | 预期 |
|---|---|---|
| API-01 | 有 view 权限查询 | 只返回当前可见租户、未删除记录 |

## 九、实施前唯一业务确认项

需要产品或业务确认“部门”与“租户”的真实关系：

- 若一个租户只对应一个部门：删除人工输入的 `department_name`，由服务端根据 `Tenant.name` 生成快照，界面只读展示；
- 若一个租户包含多个部门：按本方案保留必填 `department_name`。当部门用于权限隔离、统计口径或跨模块引用时，应先建设部门主数据并改用外键，不能长期依赖自由文本。

在该关系确认前可以完成模型以外的技术准备，但不应生成最终迁移。这是会影响数据结构的业务边界，不应留给开发人员在编码时猜测。
