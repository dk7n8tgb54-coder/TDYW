# 部门值班日志模块设计方案

> 状态：可进入实施评审
> 日期：2026-07-17
> 负责模块：`apps.department_duty_log`（新建独立 app）
> 适用场景：机房、基站等技术值守的日常环境参数与值班情况记录

---

## 一、方案总览

本模块采用以下设计：

1. 新建 `apps.department_duty_log`，不与 `apps.duty` 共表。
2. `duty_date` 使用 `DateField`，保证日期查询、排序和索引语义正确。
3. 市电和 UPS 均采用文本字段，完整保存值班员输入，接受 `220V`、`220伏`、`正常`、`停电`、`检修` 等混合值。
4. `department_name` 作为必填快照字段；若后续建立部门主数据，再增加外键并迁移，不能用历史下拉值冒充主数据。
5. 值班员固定为当前登录用户，由后端根据 `request.user` 写入；前端只读显示，不提供人员选择器，也不接受代填或代签。
6. `duty_record` 必填，空日志不允许落库。
7. 草稿可软删除；已签记录只能作废且必须保留签署证据，不提供物理删除入口。
8. 业务数据全局共享，不设置 `tenant_id`；不同租户用户只要拥有对应权限，即访问同一张表中的数据。
9. 接入现有账号电子签能力，采用“草稿 -> 本人签署 -> 锁定”的生命周期；签署后禁止直接修改关键字段。

## 二、模块定位与业务边界

### 2.1 与现有模块的关系

| 模块 | app | 职责 | 与本模块关系 |
|---|---|---|---|
| 值班日志 | `apps.duty` | 行政值班事项聚合，支持从运行日志、干扰记录引入 | 保持不变，不复用其数据表和 PDF 模板 |
| 部门值班日检查单 | `apps.checksheet` | 基于模板逐项检查，含提交、复核、归档流程 | 本模块不复用状态机和模板模型 |
| 部门值班日志 | `apps.department_duty_log` | 记录技术值守参数、供电情况和当班情况 | 新建独立 app；复用权限、用户、电子签、证据和审计能力 |

### 2.2 实施范围

当前实施范围包括：

- 值班日志草稿新增、本人编辑、本人软删除、本人签署和授权作废；
- 按日期、值班员、部门筛选；
- 服务端分页与默认排序；
- 市电和 UPS 情况记录；
- 跨租户共享访问、方法级权限、操作审计；
- 当前用户本人电子签、签署快照固化和历史验签展示；
- 草稿、已签署、已作废三种最小签署状态；
- 多人编辑冲突检测；
- 列表、详情和表单的桌面端/窄屏适配。

当前实施范围不包括：

- 从 `duty`、`runlog`、`interference` 自动导入；
- 检查项模板、复核和审批状态机；
- PDF/Excel 导出；
- 电压趋势图和自动告警；
- 附件、交接班、班次排班；
- 回收站和永久删除。

上述功能没有明确业务需求时不预埋空接口或空字段；但数据类型应保证后续可以低成本统计和扩展。

## 四、数据模型

### 4.1 字段设计

| 字段 | 类型 | 必填 | 来源/约束 | 说明 |
|---|---|---:|---|---|
| `id` | `AutoField` | 是 | 系统生成 | 主键 |
| `duty_date` | `DateField` | 是 | `YYYY-MM-DD` | 支持正确的日期比较、排序和索引 |
| `duty_person` | `ForeignKey(User, PROTECT)` | 是 | 服务端固定为 `request.user` | 值班员账号，不允许客户端指定或修改 |
| `duty_person_name` | `CharField(100)` | 是 | 服务端从当前用户昵称/账号生成 | 值班员姓名快照 |
| `department_name` | `CharField(100)` | 是 | 去首尾空格，1~100 字符 | 部门快照；当前尚无部门主数据可关联 |
| `mains_voltage` | `CharField(50)` | 否 | 去首尾空格，最长 50 字符 | 市电情况原文，如 `220V`、`正常`、`停电检修` |
| `ups_voltage` | `CharField(50)` | 否 | 去首尾空格，最长 50 字符 | UPS 情况原文，如 `220伏`、`正常`、`旁路` |
| `weather` | `CharField(50)` | 否 | 去首尾空格 | 天气简述 |
| `duty_record` | `TextField` | 是 | 去首尾空格，1~10000 字符 | 当班情况，是日志的核心内容 |
| `remark` | `TextField` | 否 | 最长 2000 字符 | 补充说明，不替代值班记录 |
| `status` | `CharField(20, choices=...)` | 是 | 默认 `draft` | `draft/signed/void` |
| `version` | `PositiveIntegerField` | 是 | 默认 1，每次编辑加 1 | 乐观锁，防止静默覆盖 |
| `signature_usage_id` | `BigIntegerField(null=True, blank=True, unique=True)` | 否 | 签署服务返回 | 固定关联不可变 `SignatureUsage`，禁止客户端传入 |
| `signed_by` | `ForeignKey(User, PROTECT, null=True, blank=True)` | 否 | 签署时固定为当前用户 | 必须与 `duty_person` 一致 |
| `signed_by_name` | `CharField(100, null=True, blank=True)` | 否 | 签署服务返回 | 签署人姓名快照 |
| `signed_at` | `CharField(20, null=True, blank=True)` | 否 | 签署服务返回 | 服务器签署时间 |
| `signature_version` | `PositiveIntegerField(null=True, blank=True)` | 否 | 签署服务返回 | 签署时使用的账号签名版本 |
| `signature_sha256` | `CharField(64, null=True, blank=True)` | 否 | 签署服务返回 | 签名图片哈希快照 |
| `business_snapshot_hash` | `CharField(64, null=True, blank=True)` | 否 | 签署服务返回 | 待签业务数据哈希 |
| `supersedes` | `ForeignKey('self', PROTECT, null=True, blank=True)` | 否 | 更正时由服务端写入 | 指向被更正的已作废记录 |
| `created_at` | `CharField(20)` | 是 | `human_datetime` | 沿用项目审计时间格式 |
| `created_by` | `ForeignKey(User, PROTECT)` | 是 | 当前登录用户 | 填报人 |
| `updated_at` | `CharField(20)` | 否 | 服务端生成 | 最近修改时间 |
| `updated_by` | `ForeignKey(User, PROTECT)` | 否 | 当前登录用户 | 最近修改人 |
| `deleted_at` | `CharField(20)` | 否 | 服务端生成 | 非空表示已软删除 |
| `deleted_by` | `ForeignKey(User, PROTECT)` | 否 | 当前登录用户 | 删除操作人 |
| `voided_at` | `CharField(20, null=True, blank=True)` | 否 | 服务端生成 | 已签记录作废时间 |
| `voided_by` | `ForeignKey(User, PROTECT, null=True, blank=True)` | 否 | 当前登录用户 | 作废操作人 |
| `void_reason` | `CharField(500, null=True, blank=True)` | 否 | 作废时必填 | 作废原因 |

设计说明：

- 新建时 `duty_person_id` 与 `created_by_id` 必须同时等于 `request.user.id`，不支持代录；后续其他用户执行作废等管理动作时，原值班员快照保持不变。
- 部门不应设计成可空，否则模块最重要的筛选维度会大量出现空值。当前项目没有部门主数据，所以先保存名称快照；历史值只可用于输入建议，不作为合法性校验来源。
- 市电和 UPS 字段按原文保存，不解析数值、不自动补单位、不推断状态，确保记录与实际填写内容一致。
- `DateField` 与仓库内合同、规章、运行日志等模型保持一致，确保日期字段具备明确类型。
- `signature_usage_id` 是业务表与电子签证据链的唯一关联。不得只保存签名图片地址，也不得按用户当前签名渲染历史记录。
- `draft` 可由值班员本人编辑和软删除；`signed` 的关键业务字段全部锁定；`void` 保留原记录、签署证据和作废原因。
- `DepartmentDutyLog` 继承 `models.Model` 和项目通用 `ModelMixin`，不继承 `TenantModelMixin`，不使用 `TenantModelManager`。
- 软删除后默认查询必须加 `deleted_at__isnull=True`，不能遗漏此条件。

模型声明必须采用普通全局模型：

```python
from django.db import models
from libs import ModelMixin


class DepartmentDutyLog(models.Model, ModelMixin):
    """部门值班日志（全局共享，不按租户隔离）"""
    # 字段定义见上表；不得增加 tenant_id 或租户 Manager。
    ...
```

### 4.2 输入校验

服务端统一执行以下校验，不能只依赖前端：

1. 日期必须是合法的 `YYYY-MM-DD`；默认不允许晚于当前自然日。若后续确认存在预填需求，再放开未来日期。
2. 服务端检测到客户端提交 `duty_person_id`、`duty_person_name`、`signed_by_id` 或任何签名快照字段时直接拒绝请求；值班员只取当前登录用户。
3. 部门、值班记录去除首尾空白后不能为空。
4. 市电和 UPS 可为空；非空时去除首尾空格并限制为 50 字符，内容按原文保存。
5. 当前用户必须有效且未逻辑删除；创建、编辑和签署草稿时必须满足 `record.duty_person_id == request.user.id`。
6. 创建人、修改人、删除人、作废人、状态、版本和签名字段均由服务端控制；业务模型和接口响应中不定义 `tenant_id`。

### 4.3 签署状态

```python
STATUS_DRAFT = 'draft'
STATUS_SIGNED = 'signed'
STATUS_VOID = 'void'

STATUS_CHOICES = (
    (STATUS_DRAFT, '草稿'),
    (STATUS_SIGNED, '已签署'),
    (STATUS_VOID, '已作废'),
)
```

允许的状态迁移只有：

```text
draft --本人电子签--> signed --有 void 权限且填写原因--> void
```

不允许 `signed -> draft`、`void -> signed` 或覆盖已有 `signature_usage_id`。需要更正时，以原记录为 `supersedes` 新建草稿，由新草稿的当前值班员重新签署。

状态与字段必须保持一致：

- `draft`：所有签署字段和作废字段为空；
- `signed`：`signature_usage_id`、签署人、签署时间、签名版本及两个哈希均非空，作废字段为空；
- `void`：保留全部签署字段，且 `voided_at`、`voided_by`、`void_reason` 均非空；
- `supersedes` 只能指向 `void` 记录，不能指向自身或形成循环引用。

### 4.4 索引

```python
class Meta:
    db_table = 'tdyw_department_duty_log'
    ordering = ('-duty_date', '-id')
    indexes = [
        models.Index(
            fields=['status', 'deleted_at', 'duty_date'],
            name='department_duty_status_date_ix',
        ),
        models.Index(
            fields=['duty_person', 'duty_date'],
            name='department_duty_person_date_ix',
        ),
    ]
```

不增加 `(department_name, duty_date, duty_person)` 唯一约束，因为同一人同一天可能有多条记录。`signature_usage_id` 必须唯一，确保一次签署使用记录只关联一条部门值班日志。

### 4.5 并发更新

编辑草稿请求必须携带当前 `version`。后端更新条件同时包含 `id`、`status=draft`、当前值班员、`deleted_at IS NULL` 和 `version`：

```python
updated = queryset.filter(
    version=form.version,
    status=STATUS_DRAFT,
    duty_person_id=request.user.id,
).update(
    # 业务字段省略
    version=F('version') + 1,
    updated_at=human_datetime(),
    updated_by=request.user,
)
if updated == 0:
    return json_response(error='记录已被他人修改，请刷新后重试')
```

这比“最后一次保存覆盖前一次保存”更适合多人值守场景。前端收到冲突后保留用户输入并提示刷新对比，不应直接关闭表单。

### 4.6 电子签接入

#### 4.6.1 场景注册

账号签名公共能力的生产场景当前默认为空。本模块经业务确认后，在 `apps.signature.services` 注册唯一场景：

```python
DEPARTMENT_DUTY_LOG_SIGNATURE_SCENE = (
    'department_duty_log',
    'department_duty_log',
    'duty_person',
)

SIGNATURE_SCENES = frozenset({
    DEPARTMENT_DUTY_LOG_SIGNATURE_SCENE,
})

# 仅表示历史签名可按业务权限跨租户读取，不放开通用签名查询。
GLOBAL_SHARED_SIGNATURE_SCENES = frozenset({
    DEPARTMENT_DUTY_LOG_SIGNATURE_SCENE,
})
```

固定调用参数：

| 参数 | 值 |
|---|---|
| `module` | `department_duty_log` |
| `object_type` | `department_duty_log` |
| `scene_code` | `duty_person` |
| `object_id` | 部门值班日志 ID |
| `actor` | `request.user`，也是该日志的 `duty_person` |

#### 4.6.2 待签业务快照

服务端从数据库重新读取草稿并生成固定结构，前端不得提交或覆盖快照：

```python
def sha256_text(value):
    return hashlib.sha256((value or '').encode('utf-8')).hexdigest()


business_snapshot = {
    'schema_version': 1,
    'record_id': record.id,
    'duty_date': record.duty_date.strftime('%Y-%m-%d'),
    'duty_person_id': record.duty_person_id,
    'duty_person_name': record.duty_person_name,
    'department_name': record.department_name,
    'mains_voltage': record.mains_voltage or '',
    'ups_voltage': record.ups_voltage or '',
    'weather': record.weather or '',
    'duty_record_sha256': sha256_text(record.duty_record),
    'duty_record_length': len(record.duty_record),
    'remark_sha256': sha256_text(record.remark or ''),
    'remark_length': len(record.remark or ''),
    'record_version': record.version,
}
```

快照覆盖所有会影响值班责任认定的字段。长文本只保存 UTF-8 SHA256 和长度，原文保留在已锁定业务记录中，避免在签名表重复保存完整日志；验签时从业务记录重新计算并比对。不包含更新时间、页面状态、预览 URL 等非业务数据。`apply_signature()` 负责规范化 JSON、计算 `business_snapshot_hash` 并固化签名图片版本和 SHA256。

#### 4.6.3 签署事务

签署接口在同一外层 `transaction.atomic()` 中完成：

1. 以 `select_for_update()` 锁定日志；
2. 校验 `sign` 权限、`status=draft`、未删除、版本一致；
3. 校验 `record.duty_person_id == request.user.id`，任何管理员和其他用户都不能代签；
4. 根据数据库记录生成业务快照；
5. 调用 `apply_signature(actor=request.user, ...)`，只向服务传业务标识、快照和客户端生成的 UUID `request_id`；
6. 将返回的 `usage_id`、签署人、签署时间、签名版本、图片哈希和业务快照哈希写入日志；
7. 把状态改为 `signed`，版本加 1；
8. 任一步失败则回滚日志、`SignatureUsage` 和 `EvidenceEvent`。

前端不得提交 `signer_user_id`、签名附件 ID、版本、图片路径、SHA256、签署时间或签署人租户。签名服务从 `actor` 和数据库获取这些数据。

#### 4.6.4 跨租户历史签名展示

部门值班日志不受租户限制，但现有 `get_usage()` 和 `get_signature_image_for_render()` 默认校验请求人与签署记录同租户，不能直接用于本模块的跨租户详情页。电子签公共服务需增加受控的服务端函数：

```python
get_signature_image_for_global_business(
    usage_id,
    module,
    object_type,
    object_id,
    scene_code,
)
```

该函数必须：

- 只允许 `GLOBAL_SHARED_SIGNATURE_SCENES` 中的场景；
- 校验 `SignatureUsage` 的 module、object_type、object_id、scene_code 与调用参数完全一致；
- 始终读取 `SignatureUsage.signature_attachment_id` 指向的历史版本，不读取账号当前签名；
- 重新计算物理文件 SHA256，并与 `SignatureUsage.signature_sha256` 比对；
- 只向服务端调用方返回受控文件信息，不提供通用 HTTP 接口。

部门值班日志提供 `GET records/{id}/signature-image/`：先用 `view` 权限读取共享业务记录，再以上述函数获取固定签名图片并返回 `FileResponse`。响应使用 `Content-Disposition: inline` 和 `Cache-Control: private, no-store`。因此不同租户的授权用户可以查看该业务记录的历史签名，但不能借此枚举或读取其他签名。

#### 4.6.5 作废与更正

- 已签署记录不可 PUT、不可 DELETE，也不能覆盖 `signature_usage_id`；
- 有 `void` 权限的用户可填写原因将 `signed` 改为 `void`；原签署使用记录保持不可变；
- 作废操作写业务审计，并由签名服务按原 `SignatureUsage.tenant_id` 追加 `void` 证据事件，使其与原签署证据处于同一对象链；证据事件创建失败时作废状态必须回滚；
- 更正通过新建草稿完成，新记录的 `supersedes_id` 指向原已作废记录，并由新记录的当前值班员本人重新签署；
- 详情页必须同时显示“已作废”状态、作废原因和原签署信息，不能让作废记录看起来仍然有效。

## 五、后端接口

### 5.1 路由

```python
urlpatterns = [
    path('records/', DepartmentDutyLogListCreateView.as_view()),

    path('records/<int:pk>/sign/', DepartmentDutyLogSignView.as_view()),

```

| 方法 | 路径 | 权限 | 功能 |
|---|---|---|---|
| GET | `/api/department-duty-log/records/` | `view` | 服务端筛选、排序、分页 |
| POST | `/api/department-duty-log/records/` | `add` | 以当前用户为值班员新建草稿 |
| GET | `/api/department-duty-log/records/{id}/` | `view` | 查看单条详情 |

| DELETE | `/api/department-duty-log/records/{id}/` | `del` | 当前值班员软删除自己的草稿 |
| POST | `/api/department-duty-log/records/{id}/sign/` | `sign` | 当前值班员电子签并提交 |
| POST | `/api/department-duty-log/records/{id}/void/` | `void` | 作废已签记录，原因必填 |

| GET | `/api/department-duty-log/options/` | `view` | 返回部门等轻量筛选选项 |

新增、编辑、删除分别使用 POST、PUT、DELETE。现有前端 `http.put` 和 `http.delete` 已被多个模块使用。按方法拆分后，`@auth` 可以精确授权，审计中间件也能正确识别 create/update/delete。

### 5.2 列表查询

查询参数：

| 参数 | 类型 | 默认值 | 规则 |
|---|---|---|---|
| `page` | int | 1 | 最小 1 |
| `page_size` | int | 20 | 1~100 |
| `start_date` | date | 当前日期前 30 天 | 与 `end_date` 均为闭区间 |
| `end_date` | date | 当前日期 | 不得早于 `start_date` |
| `duty_person_name` | string | 空 | 姓名快照模糊匹配，最长 100 字符 |
| `department_name` | string | 空 | 精确匹配，由选项选择 |
| `status` | enum | 空 | `draft/signed/void` 精确匹配 |
| `keyword` | string | 空 | 对值班记录、备注做 `icontains`，最长 100 字符 |

处理顺序：未删除过滤 -> 可见性过滤（已签/已作废全局可见，草稿仅本人）-> 参数校验 -> 业务筛选 -> `count()` -> `select_related()` -> 排序 -> 分页切片。禁止把全部记录序列化后交给前端筛选。

响应结构：

```json
{
  "error": "",
  "data": {
    "records": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  }
}
```

所有列表项应包含 `status`、`version`、值班员姓名、创建人/修改人姓名、签署摘要和后端计算的 `can_edit/can_delete/can_sign/can_void`。已签署记录返回 `signature_usage_id`、`signed_by_name`、`signed_at`、`signature_version` 和 `business_snapshot_hash`，但不返回文件路径。

### 5.3 选项接口

`options/` 返回：

```json
{
  "current_user": {"id": 42, "name": "张三"},
  "departments": ["技术保障部"]
}
```

- 部门列表来自已签/已作废记录及当前用户本人草稿的去重值，仅用于输入建议。创建/编辑仍允许输入新部门，直至部门主数据模块上线。
- `current_user` 只用于表单只读展示，值班员不提供候选列表。创建接口仍从 `request.user` 赋值，不信任前端回传的 current_user。

### 5.4 权限与全局共享边界

每个方法使用单一权限装饰器：

```python
@auth('department_duty_log.department_duty_log.add')
def post(...):
    ...

@auth('department_duty_log.department_duty_log.edit')
def put(...):
    ...

@auth('department_duty_log.department_duty_log.sign')
def post(...):
    ...

@auth('department_duty_log.department_duty_log.void')
def post(...):
    ...
```

所有查询从不附加租户条件的基础 QuerySet 开始：

```python
DepartmentDutyLog.objects.filter(
    deleted_at__isnull=True,
)
```

列表和详情的可见性条件为：

```python
Q(status__in=(STATUS_SIGNED, STATUS_VOID)) | Q(
    status=STATUS_DRAFT,
    duty_person_id=request.user.id,
)
```

编辑、删除和签署再额外限定 `status=draft`、`duty_person_id=request.user.id`；作废限定 `status=signed`。

本模块只使用功能权限控制数据访问：

- 拥有 `view` 权限的用户可查看全部未删除的已签/已作废日志以及本人草稿，不受用户所属租户影响；其他人的草稿不可见；
- 拥有 `add` 权限的用户可新建以本人为值班员的草稿；
- 拥有 `edit` 权限且是草稿值班员本人时才可编辑；
- 拥有 `del` 权限且是草稿值班员本人时才可软删除；
- 拥有 `sign` 权限且是草稿值班员本人时才可签署；超级管理员也不能替其他账号签署；
- 拥有 `void` 权限的用户可作废任意已签署记录，但必须填写原因且不得删除签署证据；
- 没有相应权限时，即使知道记录 ID 也必须拒绝访问或操作。

实现中禁止调用 `apply_tenant_filter`、`assign_tenant_id` 和 `.for_user()`，禁止给 Model 增加 `tenant_id`、`TenantModelMixin` 或 `TenantModelManager`。这些租户能力会破坏跨租户共享需求。

### 5.5 审计

在 `TARGET_MAP` 注册：

```python
'/department-duty-log/': {
    'type': 'department_duty_log',
    'name': '部门值班日志',
},
```

新增、编辑、删除、签署和作废成功后调用 `record_audit_event`，从而提供明确的目标 ID 并避免被中间件记成“未知对象”。审计详情原则：

- 新增：记录目标 ID、日期、值班员、部门及市电/UPS 原文摘要，不重复存整段值班记录；
- 编辑：记录 `changed_fields` 及关键字段的 `before/after`，长文本只记录摘要或哈希；
- 删除：仅限草稿，记录删除前的日期、值班员、部门和版本；
- 签署：记录 `signature_usage_id`、签署版本、签名图片哈希和业务快照哈希，不保存图片二进制；
- 作废：记录原 `signature_usage_id`、作废人、原因和时间；
- 业务校验失败由现有审计中间件记录失败结果；
- 审计日志中的 `tenant_id` 仍记录操作人所属租户，用于追责；它不属于部门值班日志业务表，也不参与业务数据查询过滤。

草稿软删除和已签记录作废都保留业务数据；审计日志另行保留“谁在何时执行了什么操作”，二者职责不同，不能互相替代。

### 6.2 页面布局与交互

- 搜索区：日期范围、值班员姓名、部门、签署状态、关键字；提供查询和重置。
- 表格区：日期、值班员、部门、市电、UPS、天气、值班记录摘要、签署状态、签署时间、操作。
- 市电和 UPS 按录入原文显示，不自动补 `V` 或“伏”；空值显示 `--`。
- 值班记录列表只显示 1~2 行摘要；完整内容在详情抽屉中按原换行展示。不要用 hover 承载长文本。
- 表格采用服务端分页，页码和每页条数写入 store；筛选变化回到第 1 页。
- 草稿提供“编辑、签署、删除”，已签署记录不提供编辑和删除，已作废记录只允许查看。
- 后端为每条记录返回 `can_edit/can_delete/can_sign/can_void`；前端据此渲染操作，不能只按状态或昵称判断。
- 保存和签署请求期间禁用对应按钮；签署使用同一 `request_id` 重试，避免重复生成签署记录。
- 草稿删除前二次确认；已签记录使用“作废”弹窗并强制作废原因，不显示删除按钮。
- 详情页通过当前业务记录的 `signature-image` 端点展示历史固定版本签名，同时显示签署人、签署时间、签名版本和业务快照哈希。
- 前端通过带认证头的 `http.get(..., {responseType: 'blob'})` 获取历史签名并生成临时 Object URL，不把需要鉴权的接口地址直接交给普通 `<img src>`。

### 6.3 表单

字段顺序：

1. 值班日期，必填；
2. 值班员，只读显示当前登录用户，不提供 Select/Input，不进入提交 payload；
3. 部门，必填，支持输入与历史建议；
4. 市电情况，允许填写 `220V`、`正常`、`停电检修` 等内容；
5. UPS 情况，允许填写 `220伏`、`正常`、`旁路` 等内容；
6. 天气；
7. 值班记录，必填，显示字数；
8. 备注，可选。

市电和 UPS 使用普通文本输入框，最大长度 50 字符。前端不得改写用户输入或根据内容自动判断状态；后端只负责去除首尾空格和长度校验。

编辑表单必须保存加载时的 `version`。发生版本冲突时展示“记录已更新”提示，并保留尚未提交的表单内容供用户对比。

## 七、实施步骤

### 与电子签方案阶段的关系

本方案即《账号签名图片公共能力设计方案》第三阶段“首个业务模块接入”在部门值班日志中的具体落地，不再单独执行一遍电子签方案第三阶段。

实施边界如下：

- 电子签第一、第二阶段的 `AccountSignature`、`SignatureUsage`、`apply_signature()`、本人签名查询、固定版本读取和证据事件能力是本方案的前置基础，直接复用；
- 第三阶段要求的生产场景注册、业务权限校验、待签快照、签署接口、签后锁定、作废/更正、历史展示和集成测试，全部以本方案第四至第八章为唯一实施清单；
- 本方案要求的全局共享场景读取、作废证据事件服务及相关公共能力测试，属于本次部门值班日志接入工作，不能因为“不单独执行第三阶段”而省略；
- 不重复创建另一套签名表、签署接口、场景码、业务快照或迁移；电子签公共表仍使用现有 `tdyw_account_signatures` 和 `tdyw_signature_usages`；
- 部门值班日志与电子签接入合并开发、合并联调、合并验收，验收通过即视为电子签第三阶段在该业务模块完成。

- 查询、重置、翻页、改变每页条数行为正确；
- 表单与后端错误都能展示，不重复提交；
- 新建和编辑表单只读显示当前用户，payload 不含任何值班员或签名身份字段；
- 编辑后列表刷新到正确页，版本冲突不丢失输入；
- 电子签确认框显示本人签名和待签摘要；签名不可用或图片加载失败时不能提交；
- 草稿、已签署、已作废的按钮和状态展示符合 `can_*` 字段；
- 签署后详情展示固定签名版本、签署人、时间和哈希，替换当前签名后历史显示不变；
- 跨租户 view 用户能查看业务记录绑定的签名，无权限用户不能通过拼 URL 读取；
- 无权限按钮不可见，直接调用接口仍被后端拒绝；
- 1366px 桌面和 768px 窄屏下无文字遮挡、按钮重叠和横向布局破损；
- 长值班记录在表格中截断，在详情中完整保留换行并按纯文本渲染。

### 8.3 完成定义（Definition of Done）

以下条件全部满足才可标记完成：

1. 迁移可在空库执行，回滚后可再次执行；
2. 自动化测试全部通过，新增代码无语法和 Django system check 错误；
3. 当前用户绑定、禁止代签、跨租户共享、权限、软删除、签署锁定、作废、并发和审计用例通过；
4. 前端生产构建通过，关键页面完成桌面/窄屏检查；
5. API 字段、权限码、路由、签署场景和业务快照结构与本文一致；
6. 未引入对 `duty`、`checksheet` 现有行为的回归修改；电子签公共能力除批准的场景注册、全局业务读取和作废证据服务外，现有规则保持不变。

## 九、访问模型结论

部门值班日志是全局共享业务数据，不属于任何单一租户。用户所属租户只用于账号签名归属和审计追责，不决定本模块的数据可见范围。值班员永远是创建草稿的当前登录用户；编辑、删除和签署还必须满足“本人草稿”条件。已签记录对有 `view` 权限的用户全局可见，但只能由有 `void` 权限的用户作废，不能修改、删除或代签。
