## 三、不可违反的硬约束

### 3.1 业务表绝对不做租户隔离

`DepartmentDutyLog` 必须是普通全局模型：

```python
class DepartmentDutyLog(models.Model, ModelMixin):
    ...
```

本模块禁止：

- `tenant_id` 字段；
- `TenantModelMixin`；
- `TenantModelManager`；
- `make_tenant_id()`；
- `apply_tenant_filter()`；
- `assign_tenant_id()`；
- `.for_user()`；
- 任何根据当前用户租户筛选部门值班日志的逻辑。

电子签公共表、证据表和审计表保留它们现有的 `tenant_id` 规则；这不代表部门值班日志业务表需要租户字段。签名使用记录的租户来自实际签署人，只用于签名资产归属、幂等和证据追踪。

### 3.2 值班员只能是当前登录用户

- 创建草稿时，`duty_person_id` 和 `created_by_id` 都由后端固定为 `request.user.id`；
- `duty_person_name` 由后端从 `request.user.nickname or request.user.username` 生成；
- 前端只读显示当前用户，不渲染用户 Select 或可编辑 Input；
- 创建和编辑 payload 不包含值班员字段；
- 如果请求体包含 `duty_person_id`、`duty_person_name`、`signed_by_id`、签名附件 ID、签名版本、签名哈希、签署时间等受保护字段，后端必须明确拒绝，而不是静默采用；
- 编辑、删除和签署草稿时，必须验证 `record.duty_person_id == request.user.id`；
- 超级管理员也不能替其他账号签署。

### 3.3 全局查看不等于全局修改

- 有 `view` 权限的用户可跨租户查看全部已签和已作废记录；
- 草稿只对草稿值班员本人可见；
- `edit`、`del`、`sign` 权限仍需同时满足“本人草稿”；
- `void` 权限可作废任意已签记录，但原因必填；
- 不能仅凭前端按钮隐藏实现边界，所有限制必须由后端 QuerySet 和状态检查保证；
- 对不可见草稿和不存在记录使用一致错误，避免泄露他人草稿是否存在。

### 3.4 签署后不可漂移

- 签署必须复用 `apply_signature(actor=request.user, ...)`；
- 不另建签名图片表、签名使用表或通用签署实现；
- 业务表只关联签署服务返回的不可变 `SignatureUsage.id`；
- 历史展示读取 `SignatureUsage.signature_attachment_id` 固定版本；
- 禁止根据签署人 ID 查询其当前签名来渲染历史记录；
- 签名替换或停用只影响未来签署，不影响历史记录；
- 已签记录不可 PUT、不可 DELETE，不得覆盖 `signature_usage_id`；
- 作废不修改或删除原 `SignatureUsage`；
- 更正通过新草稿和新签署完成，原记录继续保留。

### 3.5 跨租户签名读取只能走受控业务路径

现有通用 `get_usage()`、`get_usages_for_object()`、`get_signature_image_for_render()` 的租户边界必须保持不变。

只为经过批准的部门值班日志场景新增服务端读取能力，且必须同时校验：

```text
module       = department_duty_log
object_type  = department_duty_log
scene_code   = duty_person
object_id    = 当前业务记录 ID
usage_id     = 当前业务记录.signature_usage_id
```

不得新增可让前端任意传 module/object/usage 后读取签名的通用 HTTP 接口。

### 7.3 业务快照

从数据库中的草稿生成，不接受前端快照。固定结构：

```python
def sha256_text(value):
    return hashlib.sha256((value or '').encode('utf-8')).hexdigest()


snapshot = {
    'schema_version': 1,
    'record_id': record.id,
    'duty_date': record.duty_date.strftime('%Y-%m-%d'),
    'duty_person_id': record.duty_person_id,
    'duty_person_name': record.duty_person_name,
    'department_name': record.department_name,
    'mains_voltage': record.mains_voltage or '',
    'ups_voltage': record.ups_voltage or '',
    'weather': record.weather or '',
    'duty_record_sha256': sha256_text(record.duty_record),
    'duty_record_length': len(record.duty_record),
    'remark_sha256': sha256_text(record.remark or ''),
    'remark_length': len(record.remark or ''),
    'record_version': record.version,
}
```

长文本原文保留在签后锁定的业务记录中，签名快照只保存哈希和长度。验签时能从业务记录重新计算并比对。

### 7.4 签署事务

`sign_draft` 必须在一个外层 `transaction.atomic()` 中：

1. `select_for_update()` 获取未删除草稿；
2. 校验 `sign` 权限；
3. 校验值班员为当前用户；
4. 校验客户端 version 与数据库一致；
5. 校验 `confirm is True` 和 request_id 为合法 UUID/幂等键；
6. 生成数据库业务快照；
7. 调用：

```python
usage, error = apply_signature(
    actor=request.user,
    module='department_duty_log',
    object_type='department_duty_log',
    object_id=str(record.id),
    scene_code='duty_person',
    business_snapshot=snapshot,
    request_id=request_id,
    request=request,
)
```

8. 若 error 非空，抛出业务异常并保持草稿不变；
9. 把 usage 返回的 ID、签署人、时间、版本、图片哈希和业务哈希写入记录；
10. 设置 status=signed、version=F('version')+1；
11. 任一步失败时，业务记录、SignatureUsage、EvidenceEvent 全部回滚；
12. 相同 request_id 和相同上下文重试返回同一签署结果，不重复创建记录。

不要在 `apply_signature()` 之后另行创建第二条重复 EvidenceEvent。

### 7.5 全局共享业务的固定历史签名读取

新增服务端内部函数，名称使用：

```python
get_signature_image_for_global_business(
    usage_id,
    module,
    object_type,
    object_id,
    scene_code,
)
```

要求：

- 只允许 `GLOBAL_SHARED_SIGNATURE_SCENES`；
- 精确查询并匹配 Usage 的 module、object_type、object_id、scene_code；
- 固定使用 Usage 中的 attachment_id 和 SHA256；
- 校验附件类型、归属、路径位于 MEDIA_ROOT、文件存在；
- 重新流式计算文件 SHA256，异常时拒绝返回；
- 只返回服务端渲染所需信息，不新增通用 HTTP 入口；
- 不修改现有同租户 `get_usage()`、`get_usages_for_object()`、`get_signature_image_for_render()` 的权限行为。

业务图片接口先校验 `view` 权限和业务记录可见性，再传入数据库中的 `signature_usage_id` 和业务对象坐标。使用 `FileResponse`，设置：

```text
Content-Type: image/png
Content-Disposition: inline
Cache-Control: private, no-store
```

不可见、未签署、Usage 不匹配、文件缺失和哈希异常时返回统一安全错误，不泄露其他签名信息。

### 7.6 作废证据

新增职责明确的签名服务，例如：

```python
record_signature_void_event(
    usage_id,
    actor,
    module,
    object_type,
    object_id,
    scene_code,
    reason,
    request=None,
)
```

要求：

- 校验 Usage 业务坐标完全一致；
- 使用原 `SignatureUsage.tenant_id` 写 void EvidenceEvent，使事件进入原业务对象证据链；
- actor 仍记录真实作废人；
- 不修改 SignatureUsage；
- EvidenceEvent 创建失败时返回错误，由外层作废事务回滚业务状态；
- 同时写部门值班日志业务审计，记录 usage_id、作废人、原因和时间。
