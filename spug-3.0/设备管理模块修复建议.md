# 设备管理模块修复建议

## 检查范围

- 后端：`spug_api/apps/device/models.py`、`views.py`、`validators.py`、`urls.py`、迁移文件
- 前端：`spug_web/src/pages/device/*`
- 关联入口：故障处置记录、升级记录中的“同步到设备履历”按钮

## 结论摘要

设备管理模块主流程已经具备设备档案、事件履历、详情查看和 PDF 导出能力，但当前存在几类较明确问题：

- 查询、导出、事件编辑存在用户可感知的功能缺陷。
- 设备编号唯一性、租户过滤、事件与设备关联方式存在数据一致性风险。
- 表单提交、分页、同步入口等交互细节会造成“看起来成功但实际没有完成”的误导。

建议先处理 P0/P1 项，再补测试与交互优化。

## P0 必须修复

### 1. PDF 导出信任前端传入的设备与事件数据

位置：

- `spug_api/apps/device/views.py`：`DeviceResumeExportView.post`
- `spug_web/src/pages/device/HistoryStore.js`：`exportPDF`

现象：

- 前端直接把 `device_info` 和 `events` 发给后端生成 PDF。
- 后端只检查 `device_info.device_sn` 是否存在，没有根据当前登录用户、设备 ID、租户重新查询数据库。

风险：

- 用户可以篡改请求体导出任意伪造设备履历 PDF。
- 如果前端事件列表只加载了当前筛选或当前分页的数据，导出的 PDF 也可能不是完整履历。
- 当前接口的权限仅为 `device.device_resume.history_view`，但数据真实性完全依赖客户端。

修复建议：

- 前端只传 `device_id` 和可选筛选条件。
- 后端使用 `apply_tenant_filter(DeviceResume.objects.all(), request.user).filter(pk=device_id).first()` 查询设备。
- 后端按设备 ID 查询事件，必要时提供 `export_all=true`，默认导出全量事件而不是当前前端数组。
- PDF 中的设备信息、事件列表全部以后端查询结果为准。

验证点：

- 篡改请求体中的 `device_sn`、`device_name` 不应影响导出内容。
- 普通用户传其他租户设备 ID 应返回无权限或不存在。
- 有 30 条事件且前端只显示 20 条时，导出应符合产品定义：全量导出或明确只导出当前筛选。

### 2. 设备编号全局唯一，破坏多租户数据边界

位置：

- `spug_api/apps/device/models.py`：`DeviceResume.device_sn = models.CharField(..., unique=True)`
- `spug_api/apps/device/views.py`：创建时 `get_or_create(device_sn=form.device_sn, defaults=...)`

现象：

- `device_sn` 是全局唯一。
- 创建时也只按 `device_sn` 查询，不带 `tenant_id`。

风险：

- A 租户创建过某设备编号后，B 租户无法创建同编号设备，即使两边业务上应互不影响。
- 普通租户可能通过“编号已存在”错误推断其他租户是否存在某设备编号。

修复建议：

- 如果设备编号只要求租户内唯一：移除字段级 `unique=True`，增加数据库约束 `UniqueConstraint(fields=['tenant_id', 'device_sn'], name='uniq_device_resume_tenant_sn')`。
- 创建时改为 `get_or_create(tenant_id=tenant_id, device_sn=form.device_sn, defaults=...)`。
- 如果业务确实要求全局唯一，需要在文档和错误提示中明确，并避免泄露其他租户信息。

验证点：

- 两个不同租户可创建相同设备编号。
- 同一租户内重复创建设备编号应失败。
- 全局管理员和超级管理员创建数据时租户归属应清晰。

## P1 高优先级

### 3. 详情页事件分类 Tabs 使用了不兼容的 Ant Design 写法

位置：

- `spug_web/package.json`：`antd` 为 `4.21.5`
- `spug_web/src/pages/device/DetailView.js`：`<Tabs items={[...]} />`

现象：

- 当前项目使用 Ant Design 4.21.5。
- `Tabs` 的 `items` 写法在更高版本中才稳定支持，当前版本更稳妥的写法是 `Tabs.TabPane` 子节点。

影响：

- 详情弹窗中的事件类型 Tabs 可能不显示或行为异常。
- 文件内又渲染了 `EventTimeline`，而 `EventTimeline` 自己也有一组 `Radio.Group` 筛选，导致筛选 UI 重复。

修复建议：

- 将 `DetailView.js` 中的 `items` 改为 `<Tabs.TabPane tab="..." key="...">`。
- 保留一种筛选入口即可：建议保留 Tabs，移除 `EventTimeline` 内部的 `Radio.Group`，让时间线只负责展示和分页。

验证点：

- 打开设备详情后能看到全部、重大故障维修、设备更新、设备检修四个分类。
- 切换分类后请求参数 `event_type` 正确变化。
- 页面上不出现两套重复筛选控件。

### 4. 新增/编辑事件时弹窗会在请求完成前关闭

位置：

- `spug_web/src/pages/device/EventForm.js`：`handleSubmit`

现象：

- `store.handleAddEvent(data)` 或 `store.handleUpdateEvent(data)` 发出后，代码立即执行 `store.eventFormVisible = false`。
- 如果后端校验失败，用户已经看不到表单，容易误以为保存成功。

修复建议：

- 只在 Promise 成功后关闭弹窗。
- 失败时保持弹窗打开，保留用户输入，让用户可以修改后重试。

建议写法：

```js
const action = isEdit ? store.handleUpdateEvent(data) : store.handleAddEvent(data);
action.then(() => {
  message.success('保存成功');
  store.eventFormVisible = false;
});
```

验证点：

- 设备检修事件 `repair_time < event_time` 时，后端返回错误，弹窗不关闭。
- 网络失败时弹窗不关闭，按钮 loading 能恢复。

### 5. 事件编辑未复用新增时的完整校验逻辑

位置：

- `spug_api/apps/device/views.py`：`DeviceEventView.post`、`DeviceEventView.put`
- `spug_api/apps/device/validators.py`

现象：

- 新增事件会调用 `DeviceEventValidator.validate_maintenance_fields` 和 `validate_time_logic`。
- 编辑事件只在 `event.event_type == 3` 时做了部分时间校验，没有复用必填字段校验。

影响：

- 编辑设备检修事件时，可能把故障部件、故障现象、检修措施、修复时间改成空值。
- 新增和编辑规则不一致，后续维护容易继续分叉。

修复建议：

- `put` 中构造与新增一致的 form 后，复用 `DeviceEventValidator.validate_maintenance_fields(form)` 和 `validate_time_logic(form)`。
- 将 `post`、`put` 的事件字段解析合并为一个私有方法，减少重复。

验证点：

- 编辑检修事件时清空必填字段应失败。
- 编辑重大故障维修或设备更新事件时，不应强制要求检修专属字段。

### 6. 设备名称搜索框实际只搜索设备编号

位置：

- `spug_web/src/pages/device/index.js`
- `spug_web/src/pages/device/store.js`
- `spug_api/apps/device/views.py`

现象：

- 搜索项标题是“设备编号/名称”。
- 输入框只绑定 `store.f_device_sn`，请求参数只传 `device_sn`。
- `store.f_device_name` 定义了但没有任何输入控件使用。

影响：

- 用户输入设备名称时搜索不到结果。

修复建议：

- 方案 A：前端拆成两个搜索框：设备编号、设备名称。
- 方案 B：保留一个“设备编号/名称”关键字，后端新增 `keyword` 参数，用 `Q(device_sn__icontains=keyword) | Q(device_name__icontains=keyword)` 查询。

验证点：

- 输入设备编号能查到。
- 输入设备名称能查到。
- 清空搜索后分页回到第一页。

### 7. 事件没有外键约束，删除与跨租户数据一致性依赖手写逻辑

位置：

- `spug_api/apps/device/models.py`：`DeviceEvent.device_resume_id = models.IntegerField(...)`
- `spug_api/apps/device/views.py`：设备删除时手动删除事件

现象：

- 事件和设备之间没有数据库级外键。
- 删除设备时手写删除同租户事件，但无法防止其他路径产生孤儿事件。

风险：

- 数据库中可能出现 `device_resume_id` 指向不存在设备的事件。
- 后续跨模块同步如果直接写 `DeviceEvent`，更容易产生脏数据。

修复建议：

- 优先改为 `ForeignKey(DeviceResume, on_delete=models.CASCADE, related_name='events')`。
- 如果短期无法改表，至少封装统一的事件创建方法，创建前强制按租户查询设备。
- 增加数据修复脚本，扫描并处理孤儿事件。

验证点：

- 删除设备后事件自动删除或软删除规则一致。
- 手动构造不存在的 `device_resume_id` 创建事件应失败。

## P2 建议优化

### 8. 分页参数缺少边界限制

位置：

- `spug_api/apps/device/views.py`：设备列表和事件列表分页
- `spug_web/src/pages/device/HistoryStore.js`：设备下拉使用 `page_size: 9999`

现象：

- `page`、`page_size` 未限制最小值和最大值。
- 设备下拉一次性取 9999 条。

影响：

- 大数据量时列表接口和下拉接口可能变慢。
- 恶意请求可传超大 `page_size` 增加数据库和序列化压力。

修复建议：

- 后端限制 `page >= 1`，`page_size` 建议最大 100 或 200。
- 设备选择框改为远程搜索，避免一次性加载全部设备。

### 9. 设备状态、事件类型缺少后端枚举校验

位置：

- `spug_api/apps/device/views.py`
- `spug_api/apps/device/models.py`

现象：

- 前端限制了状态和事件类型选项，但后端只接收字符串/整数，没有校验枚举范围。

影响：

- 可通过接口写入非法状态或事件类型，导致列表 Tag 显示未知、统计失真。

修复建议：

- 后端定义常量：设备状态 `{'1','2','3','4','5'}`，事件类型 `{1,2,3}`。
- 创建和编辑时统一校验。
- 模型可增加 `choices`，提高 Django 层可读性。

### 10. 故障记录、升级记录中的“同步到设备履历”只是模拟成功

位置：

- `spug_web/src/pages/exec/fault/record/Form.js`
- `spug_web/src/pages/upgrade/RecordForm.js`

现象：

- 查看详情时有“同步到设备履历”按钮。
- 点击后只提示“已模拟同步到设备履历模块”，没有调用后端接口。

影响：

- 用户会误以为数据已经写入设备履历。

修复建议：

- 如果暂不支持同步，按钮文案改为“同步功能开发中”或隐藏按钮。
- 如果需要支持同步，新增后端接口，将故障/升级记录转换为 `DeviceEvent`：
  - 故障记录 -> 事件类型 1 或 3，按设备编号匹配 `DeviceResume.device_sn`
  - 升级记录 -> 事件类型 2
  - 同步前做租户过滤和重复同步检查

### 11. 模型字段与业务含义已有偏移

位置：

- `responsible_user_id`
- `related_user_id`

现象：

- 前端传的是人员姓名字符串。
- 后端字段名仍叫 `*_user_id`，真正保存到 `*_user_name`，`*_user_id` 置空。

影响：

- 代码可读性差，后续开发容易误以为这里需要用户 ID。

修复建议：

- API 字段改为 `responsible_user_name`、`related_user_name`。
- 保留旧字段兼容一版：如果请求仍传 `responsible_user_id`，后端映射为姓名并记录 TODO。
- 前端表单字段同步改名。

### 12. 无用字段与重复定义需要清理

位置：

- `spug_api/apps/device/models.py`
- `spug_api/apps/device/views.py`
- `spug_web/src/pages/device/store.js`

问题：

- `DeviceResume.device_sn` 在模型文件中重复定义了一次，虽然 Python 最终只保留后一份，但会增加误读。
- `is_deleted` 字段存在，但当前删除是硬删除，查询也没有统一过滤 `is_deleted=False`。
- `apps.device.views` 中导入了 `User`、`human_datetime` 等部分未使用内容。
- `store.f_device_name` 有定义但没有 UI 使用。

修复建议：

- 删除重复字段定义和无用 import。
- 明确设备与事件采用硬删除还是软删除。如果保留 `is_deleted`，列表、详情、事件查询都应过滤；如果不需要，考虑移除字段。

## 建议修复顺序

1. 修复 PDF 导出：后端按 `device_id` 查询真实数据。
2. 修复设备编号租户内唯一约束，并补迁移。
3. 修复事件弹窗提交时机和编辑校验。
4. 修复详情页 Tabs 兼容性和重复筛选控件。
5. 修复设备编号/名称搜索。
6. 处理事件外键或统一事件创建服务。
7. 整理同步入口、字段命名、分页限制和无用代码。
