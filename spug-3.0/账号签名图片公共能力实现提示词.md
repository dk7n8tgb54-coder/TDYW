## 四、不可违反的业务边界

### 4.1 赋予不等于签署

超级管理员给账号配置签名图片，只是提供签名资产，不能生成任何业务签署记录。

实际签署只能由登录账号本人在业务流程中明确确认后，通过 `apply_signature(actor=当前请求用户, ...)` 完成。本次没有接入具体业务，因此管理端任何操作都不得调用 `apply_signature()`。

### 4.2 禁止代签

- `apply_signature()` 不接受任意 `signer_user_id`；
- 签署人必须直接从 `actor` 获取；
- 不提供“超级管理员替某用户签署”的参数或分支；
- 不通过前端传入的用户名、附件 ID、版本号或哈希决定签署人和图片；
- 如未来需要委托签署，必须另建委托模型和专门流程。

### 4.3 历史版本不可漂移

- 每次上传生成新的附件记录和物理文件；
- 替换签名不能覆盖旧文件；
- `SignatureUsage` 必须固定引用签署时的附件 ID、版本号和 SHA256；
- 历史使用不能通过用户当前签名渲染；
- 已被任何 `SignatureUsage` 引用的附件禁止物理删除；
- 停用只影响后续使用，不影响历史预览。

### 4.4 后端是权限和数据真相来源

- 前端隐藏按钮只用于体验；
- 所有管理写接口第一层必须检查 `request.user.is_supper is True`；
- 普通用户和普通管理员直接调用接口必须返回 403 或项目统一的无权限响应；
- 不信任客户端提交的 `tenant_id`、目标附件 ID、哈希、版本号和文件路径。

## 六、附件与图片安全实现

### 6.1 附件归属

签名附件固定使用：

```text
module      = account_signature
object_type = user_signature
object_id   = <目标账号 ID>
tenant_id   = <目标账号 tenant_id>
```

物理路径应由现有 `AttachmentService` 生成，目标结构为：

```text
{MEDIA_ROOT}/account_signature/{target_tenant_id}/{yyyyMM}/user_signature_{user_id}/{uuid}.png
```

数据库保存相对 `MEDIA_ROOT` 的路径，不保存绝对路径。

### 6.2 向后兼容扩展 `AttachmentService`

现有 `AttachmentService.upload()` 默认从上传操作人读取租户。超级管理员可能给其他租户账号赋予签名，因此需要以目标账号租户保存。

实现一个向后兼容的关键字参数，例如：

```python
owner_tenant_id=None
```

要求：

- 旧调用方不传时行为完全不变；
- 只有内部可信服务层传入目标租户；
- HTTP 请求参数不得直接映射到 `owner_tenant_id`；
- 附件 `uploaded_by_id/name` 仍记录真实超级管理员；
- 附件 `tenant_id` 和目录使用目标账号租户；
- 补充原行为和新行为测试。

如果当前 `AttachmentService` 已有等价的安全扩展点，复用现有能力，不重复新增参数。

### 6.3 文件校验

第一期仅接受 PNG：

```text
扩展名：.png
声明 MIME：image/png
最大文件：2 MB
宽高范围：100～2000 像素
```

后端必须：

1. 检查扩展名；
2. 检查大小；
3. 使用 Pillow 实际解码；
4. 执行图片完整性校验；
5. 拒绝像素尺寸越界和解压炸弹；
6. 服务端重新编码成标准 PNG，剥离元数据和附加内容；
7. 使用服务端 UUID 作为磁盘文件名；
8. 计算重新编码后实际落盘文件的 SHA256；
9. 不调用公网服务；
10. 对用户返回简洁错误，对服务器记录可排查日志。

先检查项目依赖是否已有 Pillow。若没有，按项目依赖管理方式最小化增加并更新锁定文件；不要引入整套图片处理框架。

重新编码过程要使用临时文件或内存流安全完成。数据库事务失败时，清理本次新建且未被引用的文件；不得误删旧版本。

### 6.4 文件生命周期

- 替换：保留旧附件和旧物理文件；
- 停用：只改变 `AccountSignature.status`；
- 重新启用：继续启用当前版本，不重复上传；
- 账号逻辑删除：阻止新使用，保留历史；
- 不实现普通 DELETE 物理删除 API；
- 管理端如显示“移除”，实际语义必须是“停用”；
- 提供内部检查函数判断附件是否被 `SignatureUsage` 引用；
- 不修改现有通用附件删除行为，但签名模块绝不能调用物理删除处理已使用版本。

## 七、服务层实现

在 `spug_api/apps/signature/services.py` 中建立唯一稳定的跨模块入口。视图和未来业务模块都通过服务调用，不直接访问内部模型。

### 7.1 管理服务

实现等价能力：

```python
set_signature(operator, target_user_id, image_file, remark='', request=None)
disable_signature(operator, target_user_id, reason='', request=None)
enable_signature(operator, target_user_id, request=None)
get_signature_admin_detail(operator, target_user_id)
list_signature_versions(operator, target_user_id, page=1, page_size=20)
```

可根据现有风格调整函数参数和返回结构，但职责必须一致。

`set_signature()` 要求：

1. 校验超级管理员；
2. 查询未逻辑删除的目标账号；
3. 不接受客户端指定目标租户；
4. 校验并标准化图片；
5. 以目标账号租户上传附件；
6. 对当前绑定加锁；
7. 首次配置版本为 1，替换时严格加 1；
8. 更新当前附件指针和 active 状态；
9. 保留旧附件；
10. 写审计日志，区分首次赋予和替换；
11. 返回序列化后的当前签名详情；
12. 失败时保证数据库与文件状态可恢复。

### 7.2 普通查询服务

实现：

```python
get_my_current_signature(user)
get_current_signature_for_user(user_id, tenant_id)
```

要求：

- `get_my_current_signature()` 只查调用者本人；
- disabled、账号禁用、账号已删除时 `available=False`；
- 返回普通字典/DTO，不返回 Model；
- 不返回物理路径、绝对路径、管理员备注或历史列表；
- 公共响应中的附件 ID 不能成为越权预览凭证；
- `get_current_signature_for_user()` 是内部服务，不直接作为任意用户 HTTP 查询接口。

建议响应：

```json
{
  "available": true,
  "user_id": 42,
  "version": 3,
  "attachment_id": 126,
  "sha256": "...",
  "preview_url": "/api/signature/preview/126/?token=..."
}
```

如项目预览令牌必须通过单独请求获取，可调整响应结构，但不得返回公开永久 URL。

### 7.3 签署服务

实现：

```python
apply_signature(
    actor,
    module,
    object_type,
    object_id,
    scene_code,
    business_snapshot,
    request_id,
    request=None,
)
```

要求：

1. `actor` 必须是有效、已登录、未删除的当前账号；
2. 不允许另传签署人 ID；
3. 校验 `module/object_type/scene_code` 注册白名单；
4. 读取并锁定 actor 当前 active 签名；
5. 重新从附件表读取真实附件、租户和 SHA256；
6. 验证物理文件存在且重算哈希与记录一致；
7. 规范化 `business_snapshot` 后计算 SHA256；
8. 创建不可变 `SignatureUsage`；
9. 使用 `request_id` 保证重试幂等；
10. 能力存在时创建 `EvidenceEvent` 并回填 ID；
11. 返回普通字典，包含 usage ID、签署人快照、版本、哈希和签署时间；
12. 整体支持嵌入调用方的 `transaction.atomic()`。

幂等行为必须明确：相同签署上下文和相同 `request_id` 重试时返回既有结果，不创建第二条记录；如果相同 `request_id` 携带不同对象或快照，应返回冲突，不能静默复用。

### 7.4 业务快照规范化

提供内部函数，例如：

```python
canonicalize_business_snapshot(snapshot)
compute_business_snapshot_hash(snapshot)
```

规则：

- 仅接受可 JSON 序列化的字典/列表/基础值；
- 字典键稳定排序；
- 使用 UTF-8；
- 使用固定 JSON 分隔符；
- Unicode 处理规则固定；
- 日期、Decimal 等非原生类型要么显式标准化，要么返回参数错误；
- 同一逻辑数据必须得到同一 SHA256；
- 不在日志中打印完整敏感快照。

### 7.5 场景注册

提供显式注册机制或常量表。由于本次不接入具体业务，允许注册表初始为空，但测试可通过专用测试场景或明确的内部注册方式验证 `apply_signature()`。

## 九、HTTP API 实现

### 9.1 管理接口

建议在账号管理域下注册：

```text
GET   /api/account/user/<user_id>/signature/
POST  /api/account/user/<user_id>/signature/
PUT   /api/account/user/<user_id>/signature/
PATCH /api/account/user/<user_id>/signature/status/
GET   /api/account/user/<user_id>/signature/history/
```

语义：

- GET：当前详情；
- POST：首次赋予，无当前配置时成功，已有时返回明确冲突；
- PUT：替换，已有绑定时成功，无绑定时可返回错误并提示先赋予；
- PATCH：只接受 `active` 或 `disabled`，停用需要原因；
- history：分页返回版本摘要，默认不返回永久原图 URL。

如果为减少重复逻辑选择 POST/PUT 共同调用 `set_signature()`，HTTP 语义仍要按当前状态严格校验。

所有接口：

- 后端强制 `is_supper`；
- 目标账号不存在、已删除、无权限时使用项目统一响应；
- 上传使用 `multipart/form-data`；
- 不接受客户端 `tenant_id`、版本和 SHA256；
- 返回字段保持稳定且不包含文件路径；
- 错误消息可理解但不泄露其他租户敏感信息。

### 9.2 普通用户接口

```text
GET /api/signature/mine/
GET /api/signature/preview/<attachment_id>/
```

`mine`：

- 只返回本人当前 active 签名；
- 不返回管理备注和历史；
- 不提供任何写方法。

`preview`：

- 复用或扩展现有短期签名令牌机制；
- token 绑定 attachment ID、用户/授权上下文、租户和过期时间；
- 普通用户只能预览本人当前签名；
- 超级管理员在管理目标账号时可预览对应版本；
- 本次未开放通用历史业务 HTTP 预览；
- token 过期、篡改、跨附件、跨租户均拒绝；
- 响应使用正确的 `image/png` 和 `inline`；
- 增加 `X-Content-Type-Options: nosniff`；
- 根据项目安全策略设置合理缓存头，签名图片默认不做公共缓存。

浏览器 `<img>` 往往不能附加自定义 `X_TOKEN`，必须采用项目可用的短期 token 或同源认证方案，不能把长期登录 token永久拼进 URL。

### 9.3 URL 注册

- 新增 `apps.signature.urls`；
- 在项目根 URL 中按现有风格注册；
- 账号域管理接口可放在 account urls 或 include signature admin urls；
- 避免路由冲突；
- 补充 `GET/POST/PUT/PATCH` 方法不匹配测试。

## 十二、异常与并发

必须处理并测试：

| 场景 | 预期行为 |
|---|---|
| 两个管理员同时首次赋予 | 最终只有一条绑定，版本一致，不产生未处理 500 |
| 两个管理员同时替换 | 使用行锁串行化，版本单调递增 |
| 文件保存成功、数据库失败 | 清理本次孤立新文件，不影响旧版本 |
| 停用时另一个请求在签署 | 签署事务读取一个完整状态，不出现半更新 |
| 重复 `request_id` | 返回同一 usage，不重复写入 |
| 相同 `request_id`、不同快照 | 返回冲突 |
| 当前签名文件丢失 | 禁止使用并记录错误，不回退到其他版本 |
| 当前文件哈希不一致 | 禁止使用并记录安全异常 |
| 用户被禁用或删除 | 不能新签署，历史使用仍可查 |
| 预览 token 跨附件/跨租户 | 拒绝访问 |

文件与数据库无法天然处于同一事务。实现时必须设计补偿清理，并用测试覆盖关键失败路径；不要仅用 `transaction.atomic()` 就声称文件也会回滚。

## 十五、业务模块调用示例

本次不要修改具体业务模块，但最终交付中必须给出与真实函数签名一致的简短示例，展示未来模块应如何接入。

预期形态：

```python
from django.db import transaction
from apps.signature.services import apply_signature


@transaction.atomic
def sign_business_object(request, business_obj):
    # 1. 业务模块自己校验对象、租户、状态和业务权限
    # 2. 构建稳定、最小必要的待签快照
    snapshot = {
        'id': business_obj.id,
        'status': business_obj.status,
        'content_version': business_obj.version,
    }

    usage = apply_signature(
        actor=request.user,
        module='registered_module',
        object_type='registered_object',
        object_id=str(business_obj.id),
        scene_code='registered_scene',
        business_snapshot=snapshot,
        request_id=request.request_id,
        request=request,
    )

    business_obj.signature_usage_id = usage['id']
    business_obj.save(update_fields=['signature_usage_id'])
    return usage
```

实际示例必须以最终实现为准，并强调：业务模块先做业务权限校验，签名服务负责账号签名、版本、哈希、租户和留痕。
