# 党建文档逻辑隔离加固实现提示词

> 使用方式：将以下完整内容交给编码 Agent。  
> 本任务只加固资料库与党建文档共表架构的服务端逻辑隔离，不拆分党建文件表/目录表，不实施拖拽上传 UI，也不改造 `AttachmentManager`。

---

## 角色与任务

你是一名资深 Django/React 全栈工程师和应用安全工程师。请直接在当前仓库中完成“党建文档逻辑隔离加固”，不要只输出建议或代码片段。

当前架构事实：

- 党建文档没有独立文件表和目录表；
- 党建文档复用公共资料库的 `DocumentFolderPublic`、`DocumentFilePublic`；
- `DocumentSystemFolder` 通过目录数据库 ID 绑定党建根目录；
- 党建根目录及其全部后代目录在逻辑上构成独立作用域；
- 普通资料库和党建文档使用不同权限码；
- `DocumentTransfer.system_folder` 已用于标记传输所属作用域；
- 该设计需要保留，本任务的目标是让逻辑隔离成为统一、对称、不可绕过的服务端安全边界。

最终必须实现：

1. 普通公共资料库不能通过直接传文件/目录 ID 读取或修改党建内容；
2. 普通公共资料库不能把文件、目录或上传任务写入党建目录；
3. 党建模式不能读取普通资料库内容，也不能把内容移出党建范围；
4. 私有资料库继续执行严格租户隔离，不能携带党建作用域；
5. 上传、分片、合并、预览令牌、传输记录和异步任务都必须绑定并验证同一个作用域；
6. 所有复制和移动操作同时校验源对象与目标目录；
7. 非法或伪造的 `system_folder` 必须失败关闭，不能回退到普通资料库权限；
8. 增加足以防止跨作用域 IDOR 回归的后端测试矩阵；
9. 不破坏普通资料库、党建文档和私有资料库现有正常功能。

## 三、必须遵守的统一作用域规则

先把以下规则落实为少量统一服务端校验函数，再让各视图和任务调用。不要在每个视图里继续复制不同版本的 `if system_folder == ...`。

### 3.1 上下文定义

系统只允许以下三类文档上下文：

| 上下文 | `is_public` | 规范化 `system_folder` | 对象允许范围 |
|---|---:|---|---|
| 私有资料库 | `false` | 空 | 当前租户私有表 |
| 普通公共资料库 | `true` | 空 | 公共表中不属于任何系统目录的对象 |
| 党建文档 | `true` | `party_building_documents` | 绑定党建根目录及其后代 |

以下上下文必须拒绝：

- `is_public=false` 且携带任何 `system_folder`；
- 非空但不受支持的 `system_folder`；
- 党建 code 存在但绑定根目录缺失、被软删除或绑定异常；
- legacy code 如需兼容，应立即规范化为 canonical code，后续只比较规范化结果。

### 3.2 源对象规则

- 党建模式操作文件：文件必须位于党建根目录或其后代目录内；
- 党建模式操作目录：目录必须位于党建根目录或其后代，根目录自身是否允许操作由具体动作决定；
- 普通公共模式操作文件：文件不得位于任何受保护系统目录内；
- 普通公共模式操作目录：目录不得位于任何受保护系统目录内；
- 私有模式：对象必须来自私有模型，并通过现有严格租户过滤查询；
- 不允许通过切换 `is_public` 或省略 `system_folder` 访问另一作用域对象。

### 3.3 目标目录规则

上传、新建、复制、移动都必须校验目标：

- 党建模式目标必须位于党建根目录或其后代；
- 普通公共模式目标不得位于任何系统目录；
- 私有模式目标必须属于当前租户私有表；
- 党建对象不能移动/复制到普通区域；
- 普通对象不能移动/复制到党建区域；
- 根目录 `None` 只在原有业务允许且作用域规则允许时接受；党建上传不得以 `None` 为目标。

### 3.4 根目录保护

党建绑定根目录不得被：

- 删除或软删除；
- 重命名；
- 移动；
- 作为源目录复制；
- 通过批量操作间接修改；
- 解除绑定后遗留为无保护的普通目录。

如果现有产品允许复制根目录且有明确需求，应先保守拒绝，不要擅自扩大能力。

### 3.5 失败行为

- 安全边界采用 fail closed；校验异常、绑定缺失、非法 code 都拒绝请求。
- 对外尽量使用统一的“无权访问或资源不存在”类错误，避免泄漏跨作用域对象是否存在。
- 拒绝跨作用域操作时记录结构化安全日志：用户 ID、租户 ID、动作、对象 ID、请求作用域、实际作用域；不要记录令牌、文件内容或完整敏感路径。

## 四、后端实现要求

### 4.1 统一校验 API

在现有服务基础上整理清晰的校验入口。函数名可以根据项目风格调整，但能力必须完整：

```python
validate_document_context(system_folder, is_public)
validate_file_source_scope(context, file_obj)
validate_folder_source_scope(context, folder_obj_or_id, include_root, protect_root)
validate_target_folder_scope(context, target_folder_obj_or_id, allow_root)
validate_file_move_scope(context, file_obj, target_folder)
validate_folder_move_scope(context, folder_obj, target_folder)
validate_transfer_scope(context, transfer)
```

要求：

- 复用并增强现有函数，避免同义函数并存；
- 调用者传入规范化上下文，或函数内部统一规范化；
- 普通模式和党建模式必须是对称校验；
- source 和 target 必须分别验证；
- 文件 `folder_id=None` 的语义要明确，不能意外被判定为党建文件；
- 后续增加新的系统目录 code 时，普通资料库应自动排除，不需要再修改所有视图。

### 4.2 权限装饰器失败关闭

修改 `document_auth()`：

- 未传 `system_folder`：继续使用 `document.document.<operation>`；
- 传合法党建 code：使用 `document.party_building_document.<operation>`；
- 传 legacy code：规范化后使用党建权限；
- 传了非空但非法的 code：直接拒绝，不能回落普通权限；
- 装饰器只负责上下文合法性和权限码选择，对象级范围仍必须由视图/服务校验；
- 保持 GET、form-data、JSON body 三种取值方式兼容。

### 4.3 修复所有按 ID 的读写入口

对所有先按 `pk/id` 查询再操作的接口，查询成功后立即执行统一对象作用域校验。

重点修复当前只在党建模式执行 `ensure_*_in_scope`、却没有在普通模式反向排除系统目录的接口，包括但不限于：

- 文件下载；
- 文件删除；
- 基础文件预览、缩略图、媒体 Range 响应；
- 预览令牌生成；
- 文件夹下载；
- 文件/文件夹属性；
- 其他通过 ID 获取资源的接口。

不要把“列表已经隐藏党建目录”当成授权。攻击者可以直接构造 ID 请求。

### 4.4 上传目标闭环

增强 `validate_upload_target_scope()` 或等价入口：

- 党建上传：目标目录必须在党建范围；
- 普通公共上传：目标目录不得在任一系统目录范围；
- 私有上传：沿用租户过滤，并拒绝 `system_folder`；
- 小文件直传、分片初始化、分片写入、秒传/去重、断点续传、合并前和最终文件落库前都要保持相同上下文；
- 最终创建文件记录前，应基于服务端读取的目标目录再次校验，而不是只相信初始化时的客户端参数；
- 如果请求的 `system_folder` 与已有传输记录不一致，必须拒绝。

多个账号同时上传由现有后端并发能力处理，不要为了本任务增加前端上传并发队列。这里需要防范的是作用域串用和目录移动造成的竞态。

### 4.5 复制和移动

文件复制、目录递归复制、文件移动、目录移动必须执行：

```text
校验上下文
  -> 查询并校验源对象实际作用域
  -> 查询并校验目标目录实际作用域
  -> 校验根目录保护和循环移动规则
  -> 在事务内执行
```

特别修复：普通模式不能把普通对象复制/移动到党建目录，也不能通过普通模式把党建对象复制出来。

评估目录移动与上传并发的 TOCTOU 风险。至少做到：

- 跨作用域目录移动始终拒绝；
- 移动操作和最终写入前在事务内重新校验；
- 按现有数据库能力对相关目录/绑定记录使用稳定顺序的 `select_for_update()`，或者采用项目中已有的等价并发保护；
- 不引入长事务包裹整个物理文件上传过程。

### 4.6 传输记录作用域

`DocumentTransfer.system_folder` 已存在，必须让它成为后续传输操作的可信持久化上下文：

- 创建记录时保存规范化 code，普通模式保存空字符串；
- 传输列表按用户、租户、`is_public`、`system_folder` 同时过滤；
- 查询详情、检查分片、续传、完成、失败、取消、重试、清理时，校验请求上下文与记录上下文一致；
- owner + tenant 校验不能替代作用域校验；
- Celery 任务从传输记录读取作用域，不接受调用参数覆盖；
- 异步合并创建最终文件前再次校验目标目录仍在记录所属作用域；
- 对历史记录中空值、legacy code 做明确兼容，不允许模糊匹配到党建记录。

### 4.7 预览令牌绑定作用域

修改预览令牌，使签名载荷至少绑定：

```text
file_id
user_id
tenant_id
is_public
normalized system_folder
```

要求：

- 生成令牌前先查询文件并执行对象作用域校验；
- 使用令牌回调时同时校验 token 文件 ID、空间类型、租户和 `system_folder`；
- token 请求上下文、token 载荷和文件实际作用域三者必须一致；
- 普通模式令牌不能用于党建文件，党建令牌不能用于普通文件；
- 令牌本来只有短时效，可以不兼容旧格式；如果保留兼容，旧格式必须按更严格策略处理，不能绕过作用域；
- 更新所有 token 生成、解析、中间件和 Office 预览调用点。

### 4.8 绑定表完整性

为 `DocumentSystemFolder.folder` 增加数据库唯一约束，防止同一目录绑定多个系统模块。新增正常的 Django migration。

迁移前考虑已有重复数据：

- 测试或检查现有数据库是否存在同一 `folder_id` 多条绑定；
- 如果发现冲突，不要静默删除业务数据；迁移应明确失败或通过安全的数据迁移报告冲突；
- 保留 `code` 唯一和 `on_delete=PROTECT`。

增强初始化命令或增加轻量系统检查，验证：

- canonical/legacy code 不冲突；
- 绑定目录存在且未软删除；
- 绑定的是 `DocumentFolderPublic`；
- `protected=True`；
- 同一目录没有多个系统绑定；
- 根目录位置符合当前项目约定。

不要只依赖 `protected` 布尔字段做授权，它只是完整性状态，实际范围仍以绑定关系和目录树为准。

### 4.9 普通列表和搜索

复核普通公共资料库的目录树、文件列表、搜索、最近文件、面包屑、统计等查询：

- 普通模式排除所有系统目录及其文件；
- 党建模式只返回党建根目录及后代；
- 私有模式不受公共系统目录查询影响；
- 不能只排除党建根节点而漏出后代；
- 不能只过滤目录而漏出目录下文件。

如果当前实现已经正确，保留并增加测试，不做无意义重写。

## 五、多租户前提必须明确

当前 `DocumentFolderPublic`、`DocumentFilePublic` 是全平台共享表，没有 `tenant_id`；`DocumentSystemFolder.code` 也是全局唯一。

本任务默认业务前提为：**党建文档与公共资料库一样，是当前部署内的全平台共享区域，不要求每个租户拥有独立党建根目录。**

不要在没有产品确认的情况下给公共模型批量增加 `tenant_id`。

但是交付报告必须明确写出：如果实际需求是“每个租户拥有独立党建文档区”，则本次全局根目录方案不能提供租户级隔离，后续必须单独设计 `tenant_id + code` 绑定和公共文档租户化迁移。这属于架构前提，不得用权限码掩盖。

6. 普通上传把党建目录 ID 作为目标，被拒绝；
7. 普通新建目录把党建目录 ID 作为父目录，被拒绝；

### 6.3 必测成功场景
