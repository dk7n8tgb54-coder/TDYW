# TDYW 全量还原维护手册

## 1. 入口与边界

所有恢复统一使用 `backup_set_restore.sh`。脚本只接受成功的 schema 5 独立全量备份集，不支持旧 `backup_set.meta`、增量包或父链。

恢复前会校验：

- 备份目录名与 `backup_set_id`；
- `SHA256SUMS` 覆盖及每个产物的 SHA-256；
- 数据库逻辑/物理产物与 manifest 一致；
- documents/media 完整 manifest 与 tar 成员一致；
- 归档中没有路径穿越、符号链接或特殊文件。

## 2. 准备恢复凭据

逻辑恢复需要 `/etc/tdyw-backup/tdyw_restore.cnf`，权限必须为 `0600` 或 `0400`：

```ini
[client]
user=tdyw_restore
password=替换为真实密码
host=127.0.0.1
port=3306
```

恢复账号需要建库、删库和导入对象所需权限。不要把密码写在命令行或日志中。

## 3. 只校验、不恢复

```bash
BACKUP_SETS_DIR=/data/backups/tdyw/backup_sets \
./backups/backup_set_restore.sh backup_set_YYYYmmdd_HHMMSS
```

不传 `--mode` 时只生成并打印恢复计划，不改数据库或文件卷。生产恢复前必须先执行此步骤。

## 4. 隔离演练

```bash
APP_CONTAINER=tdyw-test \
DB_CONTAINER=tdyw-db-test \
RESTORE_CLIENT_CNF=/etc/tdyw-backup/restore-test-admin.cnf \
DRILL_ROOT=/tmp/tdyw-restore-drill \
./backups/backup_set_restore.sh --mode drill backup_set_YYYYmmdd_HHMMSS
```

drill 强制要求两个容器名包含 `test`，文件恢复到 `/tmp` 下。逻辑模式默认恢复到 `tdyw_restore`，不覆盖测试容器中的源库。物理模式会覆盖测试数据库容器的整个 MariaDB 卷，因此也必须使用隔离容器和隔离卷。

演练后检查表数量、关键记录、documents/media 文件数和 SHA-256。该模式把文件放在 `/tmp`，不会把测试应用切换到恢复后的数据库和文件，因此不能替代完整业务验收。需要验证前端预览、下载等流程时，应另建一套隔离 Compose 环境，并把它明确连接到恢复后的数据库和 volumes。

物理 drill 会停止测试应用并覆盖测试数据库 volume；由于文件仍恢复到 `/tmp`，脚本在成功后也保持测试应用停止，避免启动一个数据库与文件不一致的测试系统。

## 5. 生产逻辑恢复

```bash
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
DATABASE_RESTORE_MODE=logical \
./backups/backup_set_restore.sh --mode production backup_set_YYYYmmdd_HHMMSS
```

脚本要求输入 `RESTORE_PRODUCTION`，随后：

1. 停止应用容器并确认已停止；
2. 删除并重建生产数据库，导入 `database.sql.gz`；
3. 在 documents/media 卷内创建临时恢复区；
4. 解压并逐文件校验大小与 SHA-256；
5. 校验通过后替换目标内容；失败时回滚原文件；
6. 所有步骤成功后启动应用并等待健康检查。

生产逻辑恢复会永久丢弃备份时间点之后的数据库和文件变化。执行前应先为当前生产状态创建新的完整备份集。

文件替换前会在同一个 volume 内暂存并校验完整归档，因此恢复时该 volume 需要额外容纳一份 documents 或 media 数据。物理恢复还需要 `/tmp` 能容纳解压后的 MariaDB 物理备份。

## 6. 生产物理恢复

只有目标备份集使用 `DB_BACKUP_MODE=both` 时才可执行：

```bash
DATABASE_RESTORE_MODE=physical \
./backups/backup_set_restore.sh --mode production backup_set_YYYYmmdd_HHMMSS
```

物理恢复覆盖整个 `/var/lib/mysql`，包括该 MariaDB 实例中的全部数据库。脚本会强制确认：

- 目标数据库镜像与备份记录一致；
- `/var/lib/mysql` 使用命名 Docker volume；
- 指定卷与目标数据库容器的实际挂载完全一致；
- 数据库容器已经成功停止。

任何一项不满足都不会执行清空卷。物理恢复失败后不要手动启动应用，应先检查数据库卷和 mariabackup 日志。

## 7. 失败策略

生产恢复过程中任何步骤失败，应用容器保持停止。脚本不会自动启动处于“数据库已恢复但文件未恢复”或“物理卷只写入一部分”的系统。

处理顺序：

1. 保留终端和 Docker 日志；
2. 不接受流量，不手动启动应用；
3. 修复原因后对同一备份集重跑完整恢复，或恢复执行前创建的回退备份；
4. 数据库、documents、media 全部验证通过后再启动应用。

备份与恢复共享 `.backup.lock`。不要绕过锁并发执行，也不要从不同日期拼接数据库和文件归档。
