# TDYW 统一还原脚本维护手册

本手册说明当前 WSL `Ubuntu-22.04`、单机 Docker Compose 部署中的备份还原流程。仓库位于 `/mnt/e/TDYW/spug-3.0`，恢复操作必须在维护窗口内执行。

恢复脚本已经完成，但截至 2026-07-24 尚未对生产数据库执行恢复；隔离数据库真实导入、documents/media 完整回放和 mariabackup `prepare/copy-back` 演练属于任务 6。

## 1. 恢复入口和脚本职责

正式恢复只使用统一入口：

```text
backups/backup_set_restore.sh
├── validate_backup_chain.py       # schema 4 父链、manifest、SHA256SUMS 校验
├── mariadump_restore.sh           # 逻辑数据库恢复 worker
├── mariabackup_prepare_restore.sh # 物理数据库恢复 worker
└── restore_fileset_chain.py       # documents/media 全量基线及增量回放
```

其他文件的职责：

| 文件 | 用途 | 是否加入定时任务 |
| --- | --- | --- |
| `backup_set_restore.sh` | 统一数据库和文件恢复入口 | 否，按批准的恢复操作人工执行 |
| `mariadump_restore.sh` | 导入 `database.sql.gz` | 否，仅由统一入口调用 |
| `mariabackup_prepare_restore.sh` | `mariabackup --prepare` 和可选 `--copy-back` | 否，仅由统一入口调用 |
| `restore_fileset_chain.py` | 按父链回放 documents/media，并校验目标 manifest | 否，仅由统一入口调用 |
| `documents_restore.sh` | 旧格式 documents 归档的兼容恢复 | 否，新 schema 4 不使用 |

不要把逻辑数据库、documents 和 media 分别恢复到不同日期。数据库记录与物理文件必须来自同一个目标 backup set 及其完整父链。

## 2. 备份格式和恢复对象

### 2.1 schema 4 新格式

成功备份目录必须类似：

```text
/data/backups/tdyw/backup_sets/backup_set_YYYYmmdd_HHMMSS/
├── database.sql.gz
├── database.mariabackup.tar.gz      # 仅同时生成物理备份时存在
├── documents.tar.gz
├── documents.manifest.json
├── documents.delta.json
├── media.tar.gz
├── media.manifest.json
├── media.delta.json
├── manifest.json
└── SHA256SUMS
```

`manifest.json` 的 `schema_version=4` 表示新格式。每个成功 backup set 都有独立 MariaDB 逻辑全量；documents/media 可能是全量基线或增量。增量恢复必须从 `base_backup_set_id` 指向的全量基线开始，按 `parent_backup_set_id` 顺序回放到目标日期。

物理数据库恢复只能使用目标日期自身的 `database.mariabackup.tar.gz`。不能用另一个日期的物理文件替代目标日期，也不能只恢复物理数据库而跳过目标日期的 documents/media 链。

### 2.2 旧格式兼容

没有 schema 4 `manifest.json` 的旧 backup set 会进入兼容路径，依赖旧的 `backup_set.meta` 和旧归档命名。旧备份可以手工恢复，但不能作为新的 schema 4 增量父节点。新的定时任务不要再生成旧格式。

## 3. 恢复模式

### 3.1 计划检查（默认 dry-run）

不传 `--mode` 时，统一入口只解析备份、校验链和打印计划，不写数据库、不清空文件目录。schema 4 即使设置 `FORCE_RESTORE=YES` 也不会绕过 `--mode` 安全门槛。

```bash
cd /mnt/e/TDYW/spug-3.0
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
BACKUP_SETS_DIR=/data/backups/tdyw/backup_sets \
./backups/backup_set_restore.sh backup_set_YYYYmmdd_HHMMSS
```

计划输出至少应确认：目标 backup set、完整父链、数据库模式、源/目标数据库、documents/media 目标目录以及 `execute` 状态为未执行。

### 3.2 隔离逻辑恢复演练

`--mode drill` 是默认推荐的真实恢复演练模式，要求：

- `APP_CONTAINER` 和 `DB_CONTAINER` 名称都包含 `test`；
- `DRILL_ROOT` 位于 `/tmp`；
- 目标数据库固定为测试库 `tdyw_restore`；
- documents/media 写入 `DRILL_ROOT`，不会覆盖生产 volume；
- 目标 backup set 必须为 `SUCCESS`，整条链校验必须通过。

命令示例：

```bash
cd /mnt/e/TDYW/spug-3.0
APP_CONTAINER=tdyw-test \
DB_CONTAINER=tdyw-db-test \
RESTORE_CLIENT_CNF=/etc/tdyw-backup/restore-test-admin.cnf \
DRILL_ROOT=/tmp/tdyw-restore-drill-YYYYmmdd \
./backups/backup_set_restore.sh --mode drill backup_set_YYYYmmdd_HHMMSS
```

逻辑演练完成后，必须检查数据库表数量、关键记录、文件数量、manifest、下载、预览、应用日志和 Celery 任务状态。

### 3.3 隔离物理恢复演练

在逻辑演练通过后，才允许在独立测试数据库容器执行物理演练：

```bash
cd /mnt/e/TDYW/spug-3.0
DATABASE_RESTORE_MODE=physical \
APP_CONTAINER=tdyw-test \
DB_CONTAINER=tdyw-db-test \
RESTORE_CLIENT_CNF=/etc/tdyw-backup/restore-test-admin.cnf \
DRILL_ROOT=/tmp/tdyw-restore-drill-YYYYmmdd \
./backups/backup_set_restore.sh --mode drill backup_set_YYYYmmdd_HHMMSS
```

物理模式会检查备份数据库镜像与目标数据库镜像一致，并调用 `mariabackup --prepare`。随后物理 worker 会覆盖测试 Docker volume 的 `/var/lib/mysql`，因此不能对生产容器或生产 volume 试跑。

### 3.4 生产恢复

生产模式是破坏性操作：

```bash
cd /mnt/e/TDYW/spug-3.0
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
./backups/backup_set_restore.sh --mode production backup_set_YYYYmmdd_HHMMSS
```

执行前必须同时满足：

1. 已完成目标备份的计划检查和隔离恢复演练；
2. 已确认数据库、documents、media 来自同一目标日期和完整父链；
3. 已保留当前生产状态的可回滚备份或快照；
4. 已停止或公告业务维护窗口；
5. 已取得明确的变更批准和现场操作人确认。

生产模式会停止应用冻结写入，逻辑模式删除并重建生产数据库，清空并回放 documents/media，最后启动应用并等待健康检查。物理模式还会停止数据库容器并覆盖 MariaDB volume。不要设置 `ASSUME_YES=YES` 绕过生产二次确认。

本轮任务禁止执行上述生产命令。

## 4. 恢复凭据

恢复使用独立的 `/etc/tdyw-backup/tdyw_restore.cnf`，不要复用仅有备份权限的 cnf：

```ini
[client]
host=127.0.0.1
port=3306
user=root
password=REPLACE_WITH_RESTORE_PASSWORD
```

安装和检查：

```bash
sudo install -d -m 700 /etc/tdyw-backup
sudo install -m 600 database_maintenance/db_accounts/restore_client.cnf.template /etc/tdyw-backup/tdyw_restore.cnf
sudoedit /etc/tdyw-backup/tdyw_restore.cnf
sudo stat -c '%a %U:%G %n' /etc/tdyw-backup/tdyw_restore.cnf
```

凭据规则：

- cnf 必须是普通文件，权限只能为 0600 或 0400；
- 用户名和密码只从 cnf 的 `[client]` 读取；
- 不使用 `-p密码`、命令行密码或日志中的密码；
- 真实 cnf 不进入 Git，不复制到备份目录；
- 恢复账号必须具备创建、删除和导入目标数据库的权限。

恢复脚本会把 cnf 临时复制到数据库容器 `/tmp`，使用后通过 trap 删除。

## 5. 恢复前检查清单

在 WSL 中执行：

```bash
cd /mnt/e/TDYW/spug-3.0
python3 --version
command -v docker python3 gzip tar sha256sum
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'
docker inspect -f '{{.State.Health.Status}}' tdyw-db
stat -c '%a %U:%G' /etc/tdyw-backup/tdyw_restore.cnf
df -h /data/backups/tdyw /tmp
```

还应确认：

- 目标 backup set 目录没有 `.failed`、`.inprogress` 后缀；
- `manifest.json` 状态为 `SUCCESS`；
- `SHA256SUMS` 存在；
- 基线和所有父备份目录都在本地或已从 U 盘复制；
- 恢复目标磁盘足够容纳 dump 解压、物理 prepare 临时目录和文件回放；
- 测试恢复使用的容器名称含 `test`，生产恢复不会误指向测试容器；
- 生产恢复前已暂停定时备份，避免恢复期间再次停止应用。

## 6. 校验和链验证

单独执行 `sha256sum` 不能替代父链校验。先对每个复制到本地的 backup set 校验：

```bash
set_dir=/data/backups/tdyw/backup_sets/backup_set_YYYYmmdd_HHMMSS
cd "$set_dir"
sha256sum -c --strict SHA256SUMS
gzip -t database.sql.gz
tar -tzf documents.tar.gz >/dev/null
tar -tzf media.tar.gz >/dev/null
```

然后使用统一入口做 schema 4 计划检查：

```bash
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
./backups/backup_set_restore.sh "$set_dir"
```

链验证失败时，不要手工修改 `manifest.json`、`*.delta.json` 或 `SHA256SUMS`。应补齐缺失的父目录、重新复制 U 盘链，或选择另一个完整成功的目标日期。

## 7. 恢复后的验收

### 7.1 数据库

```bash
docker inspect -f '{{.State.Health.Status}}' tdyw-db
docker logs --tail 200 tdyw-db
```

数据库表数量和导入结果先以 `mariadump_restore.sh` / `backup_set_restore.sh` 的恢复报告为准；需要执行额外 SQL 复核时，应仿照恢复脚本把 0600 cnf 临时复制到数据库容器、完成只读查询后立即删除。不要把密码写入命令行、脚本或日志。至少核对：表数量、核心业务表记录数、迁移状态、严格 `sql_mode`、外键/唯一约束，以及恢复目标日期之后不应出现的记录。

### 7.2 文件和应用

- documents/media 文件数量与目标 manifest 一致；
- 随机抽查中文、空格、长路径和大文件；
- 前端下载和预览各抽查若干文件；
- `docker inspect` 显示应用为 healthy；
- Celery、Redis、API、WebSocket 和上传服务恢复运行；
- 日志中没有数据库连接、文件不存在或权限错误；
- 恢复后的测试业务可以登录并完成一条只读查询。

隔离演练的验收记录应包含目标 backup_set_id、基线 ID、父链成员、数据库表数、文件数、应用健康状态、开始/结束时间、操作者和异常。

## 8. 常见失败和处理

| 错误现象 | 常见原因 | 处理方式 |
| --- | --- | --- |
| `backup set is not a successful schema-v4 set` | 选择了 `.failed` 或不完整目录 | 选择无后缀且 manifest 为 SUCCESS 的目录 |
| 父链或文件缺失 | 只复制了最后一个增量 | 从目标日期沿父 ID 复制到全量基线 |
| `restore client cnf must have mode 0600 or 0400` | 权限过宽或不是普通文件 | `chmod 600` 并检查属主 |
| drill 要求容器名包含 test | 使用了生产容器名 | 设置 `APP_CONTAINER=tdyw-test`、`DB_CONTAINER=tdyw-db-test` |
| 物理产物不存在 | 目标日期只生成了逻辑备份 | 改用包含物理产物的目标日期，不借用其他日期 |
| 物理镜像不匹配 | 备份和目标 MariaDB 镜像版本不同 | 使用匹配镜像完成演练；不要随意设置 `ALLOW_PHYSICAL_IMAGE_MISMATCH=YES` |
| 目标数据库已存在 | 未设置替换选项或目标不干净 | drill 由统一入口处理；手工 worker 只在明确批准后设置 `DROP_EXISTING=YES` |
| WSL cron 恢复失败 | WSL 在计划时间已停止 | 使用 Windows 任务计划程序唤醒 `Ubuntu-22.04`，或保持 WSL 常驻 |

恢复失败时先保留日志和临时工作目录信息，不要删除原 backup set，不要把失败目录改名为成功目录。

## 9. U 盘恢复准备

增量目标不能只带最后一个目录。必须从全量基线到目标日期复制整条链，并在源端和 U 盘端分别执行：

```bash
(cd /media/backup-operator/TDYW_BACKUP/backup_set_YYYYmmdd_HHMMSS && sha256sum -c --strict SHA256SUMS)
```

复制前记录基线 ID、所有父 ID、目标 ID 和校验结果。U 盘复制由人工完成，不由恢复脚本自动挂载、上传或删除数据。

## 11. 维护规则

1. 只更新统一入口和内部 worker 的版本，不恢复或启用废弃独立备份脚本。
2. 修改恢复脚本后，重新执行 Shell 语法、Python 编译、备份链单元测试和 schema 4 计划 dry-run。
3. 任何生产恢复前都必须有变更单、目标 backup_set_id、完整链校验记录和回滚副本。
4. 恢复完成后保留恢复报告和应用验收记录，不删除源备份。
5. 每年至少进行一次隔离逻辑和物理恢复演练；恢复演练失败时暂停生产恢复权限。
