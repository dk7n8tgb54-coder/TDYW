# backups 脚本修改建议

检查对象：

- `mariabackup_backup.sh`
- `mariadb_dump_backup.sh`
- `documents_incremental_backup.sh`

检查环境：

- 目标使用场景：Linux 宿主机执行脚本，通过 Docker 操作 `tdyw` / `tdyw-db` 容器。
- 当前验证容器：`tdyw`、`tdyw-db` 均已运行并处于 healthy 状态。
- `tdyw-db` 中已存在 `mariabackup`、`mariadb-dump`、`mysqldump`、`gzip`、`tar`。
- `tdyw` 中已存在 `bash`、`find`、`tar`，且 `/data/spug/spug_api/storage/documents` 目录存在。
- 三个脚本均已通过 `bash -n` 语法检查。
- `mariadb-dump --no-data tdyw` 已验证可成功连接并导出表结构。

## 总体结论

三个脚本的方向和基础配置基本正确，容器名、数据库版本、documents 挂载路径、工具依赖与当前 Docker 环境能对上。

但如果作为生产备份长期使用，建议先处理以下问题：

1. 去掉脚本中的硬编码数据库密码。
2. documents 增量备份的 marker 更新时间已修正，避免备份过程中变更的文件被漏掉。
3. 明确 documents 增量备份不处理删除文件的恢复风险。
4. 明确 mariabackup 物理备份恢复前必须执行 `--prepare`。
5. 评估 mariabackup 临时目录写入容器 `/tmp` 的磁盘空间风险。

## `mariadb_dump_backup.sh`

### 1. 去掉硬编码数据库密码

当前脚本中存在：

```bash
DB_PASSWORD="Dt6299093"
```

虽然 `load_env` 会优先从 `docker/.env` 读取 `MYSQL_ROOT_PASSWORD` 覆盖它，但脚本一旦被单独复制到其他位置，或者 `docker/.env` 不存在，就会继续使用这个明文密码。

建议改为：

```bash
DB_PASSWORD=""
```

并保持现有的空密码检查逻辑：

```bash
if [ -z "${DB_PASSWORD}" ]; then
    log_err "未能获取 MYSQL_ROOT_PASSWORD，请检查 ${ENV_FILE} 或手动配置 DB_PASSWORD"
    exit 1
fi
```

### 2. 建议避免在命令行参数中暴露密码

当前写法：

```bash
mariadb-dump -u"${DB_USER}" -p"${DB_PASSWORD}" ...
```

在极短时间内可能被宿主机或容器内的进程列表看到。风险不算最高，但生产上建议改成临时 defaults 文件，例如：

```bash
MYSQL_CNF="$(mktemp)"
chmod 600 "${MYSQL_CNF}"
cat > "${MYSQL_CNF}" <<EOF
[client]
user=${DB_USER}
password=${DB_PASSWORD}
default-character-set=utf8mb4
EOF

docker cp "${MYSQL_CNF}" "${DB_CONTAINER}:/tmp/backup-client.cnf"
docker exec "${DB_CONTAINER}" mariadb-dump --defaults-extra-file=/tmp/backup-client.cnf ...
docker exec "${DB_CONTAINER}" rm -f /tmp/backup-client.cnf
rm -f "${MYSQL_CNF}"
```

如果暂时不想增加复杂度，至少先完成第 1 条，去掉硬编码密码。

### 3. 逻辑备份参数基本正确

当前参数：

```bash
--single-transaction
--routines
--triggers
--events
--default-character-set=utf8mb4
--set-charset
--quick
--hex-blob
```

对 InnoDB 数据库是合理的。`--single-transaction` 可以保证一致性快照，`--routines`、`--triggers`、`--events` 也覆盖了常见数据库对象。

## `mariabackup_backup.sh`

### 1. 恢复前必须执行 prepare

当前脚本生成的是 mariabackup 物理备份包，但没有执行：

```bash
mariabackup --prepare --target-dir=...
```

这不是备份错误，但恢复时必须先 prepare，否则不能直接作为 MariaDB 数据目录使用。

建议在脚本注释或单独恢复文档中明确恢复流程：

```bash
tar xzf tdyw_physical_YYYYmmdd_HHMMSS.tar.gz -C /restore/mariabackup
mariabackup --prepare --target-dir=/restore/mariabackup
systemctl stop mariadb
rm -rf /var/lib/mysql/*
mariabackup --copy-back --target-dir=/restore/mariabackup
chown -R mysql:mysql /var/lib/mysql
systemctl start mariadb
```

如果是在 Docker volume 中恢复，需要把 copy-back 的目标换成实际 volume 挂载目录或临时容器中的 `/var/lib/mysql`。

### 2. 注意容器 `/tmp` 空间风险

当前脚本先在数据库容器内生成备份目录：

```bash
BACKUP_TMP_BASE="/tmp/mariabackup_tmp"
```

然后再打包流式输出到宿主机：

```bash
docker exec "${DB_CONTAINER}" tar czf - -C "${target_dir}" . > "${out_file}"
```

如果数据库较大，`/tmp` 实际占用的是容器 writable layer 或 Docker 数据目录空间，可能把宿主机 Docker 根目录撑满。

建议二选一：

1. 确认 Docker 根目录空间充足，并监控 `/var/lib/docker` 或 Docker Desktop 的数据盘空间。
2. 给 `tdyw-db` 额外挂载一个专用备份临时卷，例如 `/backup_tmp`，然后设置：

```bash
BACKUP_TMP_BASE="/backup_tmp/mariabackup_tmp"
```

### 3. 建议增加 tar 包完整性校验

当前只检查输出文件非空：

```bash
if [ ! -s "${out_file}" ]; then
    ...
fi
```

建议增加：

```bash
if ! tar tzf "${out_file}" >/dev/null 2>&1; then
    log_err "物理备份 tar.gz 校验失败，文件可能损坏"
    rm -f "${out_file}"
    return 1
fi
```

### 4. mariabackup 命令本身可用

当前 `tdyw-db` 容器中已验证存在：

```bash
/usr/bin/mariabackup
```

版本为 MariaDB 10.8.2 对应版本，和当前数据库版本匹配。

## `documents_incremental_backup.sh`

### 1. marker 更新时间已修正，避免漏备份

原逻辑是在备份完成后执行：

```bash
touch "${MARKER_FILE}"
```

风险场景：

1. 00:00:00 开始生成文件列表。
2. 00:00:05 某个文件被新增或修改，但没有进入本次文件列表。
3. 00:00:10 备份成功，`MARKER_FILE` 被更新到 00:00:10。
4. 下次增量使用 `find -newer MARKER_FILE`，00:00:05 的文件不会被选中。

现在已改为：备份开始时先记录一个本次备份起点 marker，备份成功后把正式 marker 更新时间设为这个起点。

当前脚本中的核心逻辑：

```bash
create_run_marker() {
    RUN_MARKER_FILE="$(mktemp)"
    touch "${RUN_MARKER_FILE}"
}

commit_run_marker() {
    cp -p "${RUN_MARKER_FILE}" "${MARKER_FILE}"
    rm -f "${RUN_MARKER_FILE}"
    log_ok "标记文件已更新: ${MARKER_FILE}"
}
```

在 `backup_full` 和 `backup_incremental` 开始时调用：

```bash
create_run_marker
```

备份成功后调用：

```bash
commit_run_marker
```

这样本次备份过程中发生的文件变化，会在下一次增量备份中被包含。

#### 已修复：mtime-only 增量风险 → mtime + ctime

早期增量只依赖 `mtime`（`find -newer marker`），会遗漏“复制/迁移/解压/还原进来的、保留了旧 mtime 的文件”。此类文件 `mtime` 早于基准但 `ctime` 是新的，纯 `mtime` 增量会漏掉，导致数据库有记录但物理文件缺失（前端可见、预览/下载报“文件不存在”）。

现改为同时考虑 `mtime` 与 `ctime`：

```bash
find "${DOCUMENTS_PATH}" -type f \
    \( -newermt "@${BASE_EPOCH}" -o -newerct "@${BASE_EPOCH}" \)
```

说明：不使用 `find -cnewer <标记文件>`，因为标记文件通过 `docker cp` 进入容器时其 `ctime` 会被重置为当前时间，导致 `-cnewer` 比较失效。改为以宿主机标记文件的 `mtime epoch` 作为基准，通过 `-newermt`/`-newerct` 比较，时区无关且可靠。

#### 已实现：manifest 与 meta

每次备份生成 3 类产物：

```text
documents_(full|incr)_YYYYmmdd_HHMMSS.tar.gz     归档
documents_(full|incr)_YYYYmmdd_HHMMSS.manifest   文件清单（TSV: 相对路径/大小/mtime/ctime）
documents_(full|incr)_YYYYmmdd_HHMMSS.meta       元信息（类型/起止时间/文件数/容器/路径/基准时间）
```

`.manifest` 用于 `documents_restore.sh` 还原后校验缺失文件。0 文件的增量备份不生成归档与 manifest，但仍生成 meta 以便审计。

### 2. 增量备份不记录删除文件

当前策略只备份：

```bash
find "${DOCUMENTS_PATH}" -type f -newer "${CONTAINER_MARKER}"
```

也就是新增和修改文件，不记录删除动作。恢复时如果直接把全量包和所有增量包解压到目标目录，可能保留一些数据库已经不再引用的旧文件。

建议根据恢复目标选择策略：

- 如果只要求文件不丢，当前策略可以接受。
- 如果要求 documents 目录与数据库严格一致，建议定期做全量备份，并在恢复时先清空 documents 目录，再恢复全量和对应增量。
- 如果需要精确同步删除，需要额外生成文件清单 manifest，并在恢复时按 manifest 清理多余文件。

### 3. 文件名包含换行时 tar 列表会有风险

当前文件列表使用：

```bash
find ... -printf '%P\n'
tar ... -T "${container_list}"
```

普通业务上传文件一般不会包含换行符，实际风险较低。但严格来说，文件名如果包含换行，`tar -T` 会把它拆成多行。

如果要做成更强健的通用脚本，可以改成 null 分隔：

```bash
find "${DOCUMENTS_PATH}" -type f -printf '%P\0'
tar --null -T "${container_list}" ...
```

### 4. 当前 documents 目录为空

当前环境中验证到：

```text
/data/spug/spug_api/storage/documents 文件数为 0
```

因此只能确认脚本语法、容器路径和工具依赖正常，无法用真实 documents 文件验证全量包和增量包内容。

建议在测试环境上传 1 个资料库文件后执行：

```bash
BACKUP_DIR=/tmp/tdyw-documents-backup ./documents_incremental_backup.sh full
tar tzf /tmp/tdyw-documents-backup/full/documents_full_*.tar.gz
```

再修改或新增文件后执行：

```bash
BACKUP_DIR=/tmp/tdyw-documents-backup ./documents_incremental_backup.sh
tar tzf /tmp/tdyw-documents-backup/incremental/documents_incr_*.tar.gz
```

确认压缩包中包含预期文件。
