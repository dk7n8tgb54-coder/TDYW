对，就是这个意思。

## 生产库 vs 临时库

| | 生产库 | 临时库 |
|---|---|---|
| **库名** | `tdyw` | `tdyw_restore` |
| **是什么** | 你系统正在用的数据库，用户登录、资料库记录、运行日志都在里面 | 额外建的一个空库，只为恢复演练用 |
| **被谁用** | 生产容器 `tdyw` 真实读写 | 没人用，恢复完验证一下就删 |
| **跑错了的后果** | 数据没了，生产停摆 | 没事，删了重来 |

## 为什么要有临时库

恢复数据库 = 把旧备份灌回去。如果直接灌到生产库 `tdyw`：

```
备份是 7 月 1 日的 → 灌回去 → 7 月 2、3、4 日的所有新数据全没了
```

而且灌的过程会先 `DROP DATABASE tdyw`（删库），万一备份文件本身是坏的，**库没了、备份也读不出来，生产直接挂**。

临时库就是给你一个“试错空间”：

```
1. 把备份恢复到 tdyw_restore（生产库 tdyw 不动）
2. 进 tdyw_restore 看一眼：表数量对不对、关键数据在不在、有没有乱码
3. 确认备份是好的、数据是对的
4. 这时候才决定要不要把 tdyw_restore 的数据替换到 tdyw
```

## 实际怎么操作

### 恢复到临时库（安全，随便跑）

```bash
BACKUP_FILE=/data/backups/tdyw/mariadb/dump/tdyw_dump_20250704_020000.sql.gz \
./mariadb_dump_restore.sh
```
默认 `RESTORE_DB=tdyw_restore`，脚本会自动建这个库、灌数据，**不碰生产库 `tdyw`**。

### 验证临时库数据

```bash
# 看表数量
docker exec tdyw-db mariadb -uroot -p'密码' -N -e \
  "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='tdyw_restore';"

# 看某张表的数据
docker exec tdyw-db mariadb -uroot -p'密码' tdyw_restore -e \
  "SELECT COUNT(*) FROM document_documentfile_private;"
```

确认无误后，再决定要不要覆盖生产库。

### 覆盖生产库（三重确认，慎用）

```bash
BACKUP_FILE=/data/backups/tdyw/mariadb/dump/tdyw_dump_20250704_020000.sql.gz \
RESTORE_DB=tdyw \
ALLOW_RESTORE_TO_PRODUCTION=YES \
DROP_EXISTING=YES \
./mariadb_dump_restore.sh
```
这三个变量缺一个都不让跑——故意制造摩擦，防止手滑。`DROP_EXISTING=YES` 意思是“我知道会先删掉现在的 `tdyw` 库，我确认”。

## 生产恢复的正确节奏

```
1. 先恢复到 tdyw_restore（临时库）
2. 验证 tdyw_restore 数据没问题
3. 备份当前生产库 tdyw（保命快照，万一恢复搞砸了还能回滚）
4. 停应用 docker stop tdyw
5. 把 tdyw_restore 覆盖到 tdyw（或者重新跑一次 RESTORE_DB=tdyw 的恢复）
6. 恢复 documents 文件卷
7. 启动容器，检查
```

**核心原则**：临时库是免费的，可以反复试；生产库只有一次机会。所以先把备份恢复到临时库验证，确认没问题再动生产库。



物理备份恢复数据库：
PHYSICAL_BACKUP_FILE=/mnt/e/TDYW/spug-3.0/backups/mariabackup/physical/tdyw_physical_20260704_195029.tar.gz \
FORCE_PHYSICAL_RESTORE=YES \
START_AFTER_RESTORE=NO \
./mariabackup_prepare_restore.sh
因为脚本就是这么设计的——**恢复完故意不停容器，让你手动确认没问题再启动**。这是安全机制，不是 bug。

## 为什么故意停着不启动

物理恢复覆盖了 `/var/lib/mysql` 整个数据目录。如果立刻启动数据库，可能遇到：

- 权限不对（`mysql:mysql` 没改对）→ 数据库起不来
- 配置不匹配 → 起来但表损坏
- 备份本身有问题 → 起来一半崩了，更难排查

**停下来 = 给你一个“刹车点”**：启动前看一眼日志、确认数据目录状态，发现问题还能停下处理。如果自动启动了，有问题时容器可能反复重启、日志刷屏，反而难定位。

而且 `START_AFTER_RESTORE=NO` 是默认值，就是你显式设的。脚本最后明确提示了：

```
Containers were not restarted. Start them manually after verification:
  docker start tdyw-db
  docker start tdyw
```

## 现在怎么手动启动 + 验证

按顺序来，**先起数据库，再起应用**：

### 第一步：启动数据库容器

```bash
docker start tdyw-db
```

### 第二步：看日志有没有报错

```bash
docker logs --tail 200 tdyw-db
```

重点看有没有：
- `[ERROR]` 红字
- `InnoDB: Database page corruption`
- `Can't open file`
- `Table ... doesn't exist`

如果日志末尾出现 `ready for connections` 或 `Version: ... MariaDB` 之类，说明起来了。

### 第三步：验证数据库可用

```bash
# 看库列表
docker exec tdyw-db mariadb -uroot -p'密码' -e "SHOW DATABASES;"

# 进 tdyw 库看表
docker exec tdyw-db mariadb -uroot -p'密码' tdyw -e "SHOW TABLES;" | head -20

# 抽查一张表的行数
docker exec tdyw-db mariadb -uroot -p'密码' tdyw -e "SELECT COUNT(*) FROM auth_user;"
```

确认库、表、数据都在。

### 第四步：启动应用容器

```bash
docker start tdyw
docker logs --tail 200 tdyw
```

看应用日志有没有连数据库失败之类的报错。

### 第五步：浏览器访问验证

打开前端，登录系统，挑几个核心功能点一下（看资料库列表、运行日志、设备列表），确认能正常加载。

## 如果想让脚本自动启动

下次恢复时设 `START_AFTER_RESTORE=YES`：

```bash
PHYSICAL_BACKUP_FILE=... \
FORCE_PHYSICAL_RESTORE=YES \
START_AFTER_RESTORE=YES \
./mariabackup_prepare_restore.sh
```

脚本恢复完会自动 `docker start tdyw-db` 和 `docker start tdyw`。

**但生产环境不建议这样做**——手动启动多花 1 分钟，但能在启动前发现问题。自动启动如果数据库有问题，应用起来后报错，用户已经看到故障了，体验更差。

## 如果启动后数据库报错怎么办

**不要慌，你还有保命快照**（恢复前应该 dump 过一份）。回滚步骤：

```bash
# 1. 停掉有问题的数据库
docker stop tdyw-db

# 2. 用逻辑备份恢复（如果之前 dump 了的话）
docker exec -i tdyw-db mariadb -uroot -p'密码' < /tmp/tdyw_safety_snapshot_xxx.sql

# 3. 或者重新跑一次物理恢复（换个备份包试试）
```

如果恢复前没 dump 保命快照——下次一定要做。物理恢复前**必须**先 dump 当前生产库。

---

**一句话总结**：容器停着是故意的，按 `docker start tdyw-db` → 看日志 → 验证 → `docker start tdyw` 的顺序手动启动即可。下次想让脚本自动启动，加 `START_AFTER_RESTORE=YES`。
