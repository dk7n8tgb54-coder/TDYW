# TDYW 一致性备份维护手册

本手册适用于当前 WSL `Ubuntu-22.04` 内运行的单机 Docker Compose 部署，仓库当前位于 `/mnt/e/TDYW/spug-3.0`。每日备份只允许调度统一入口 `backup_set_create.sh`，不得分别调度数据库、documents 或 media 脚本。

当前备份策略为：每次运行都生成 MariaDB 逻辑全量；默认每周日生成 documents/media 全量基线，周一至周六生成文件增量；可选在周日同时生成 MariaDB 物理全量。每天 02:00 的运行频率由 cron 或 Windows 任务计划程序控制，不是由备份脚本自行定时。

## 1. 持久化数据边界

| 数据 | 实际位置 | 本阶段处理 |
| --- | --- | --- |
| MariaDB | `tdyw-mysql-data:/var/lib/mysql` | 每日逻辑全量；每周可选附加 mariabackup 物理全量 |
| documents | `tdyw-documents:/data/spug/spug_api/storage/documents` | 每周全量基线，其余日期做带删除清单的增量 |
| media | `tdyw-media:/data/spug/spug_api/media` | 每周全量基线，其余日期做带删除清单的增量 |
| document_chunks | `tdyw-document-chunks:/data/spug/spug_api/storage/document_chunks` | 不备份 |
| Supervisor/应用日志 | `tdyw-logs` 及应用日志目录 | 默认不备份 |
| Redis、预览缓存、临时文件 | 容器内缓存或临时目录 | 默认不备份 |

`document_chunks` 是分片上传的中间状态，不是已提交业务文件的权威副本。停写会中断尚未完成的上传；客户端应在恢复服务后重试。已完成文件已进入 documents，且对应记录已写入 MariaDB。因此备份分片既不能提高已提交数据完整性，也可能把不可继续的半成品带入恢复环境。

规章附件位于 documents 的 `regulation/` 子目录。Evidence、签名、运行日志附件和升级附件位于 `MEDIA_ROOT`，当前 Compose 中即 media volume。因此它们已经被 documents/media 文件集快照覆盖。

禁止直接复制运行中的 `/var/lib/mysql`。本阶段不包含云上传、备份加密、对象锁或 U 盘自动复制。

## 2. 脚本职责与调用关系

| 文件 | 职责 | 是否人工执行 |
| --- | --- | --- |
| `backup_set_create.sh` | 统一备份入口，协调停写、数据库、文件集、校验、发布和保留策略 | 是，唯一可加入定时任务的备份脚本 |
| `backup_set_restore.sh` | 统一恢复入口，校验 schema 4 备份链并协调数据库和文件恢复 | 是，仅在恢复计划检查或经批准的恢复操作中执行 |
| `mariabackup_backup.sh` | 统一入口内部调用的 MariaDB 物理备份 worker | 否 |
| `mariadump_restore.sh` | 统一恢复入口内部调用的逻辑恢复 worker | 否 |
| `mariabackup_prepare_restore.sh` | 统一恢复入口内部调用的物理恢复 worker | 否 |
| `create_fileset_snapshot.py` 等 `backups/*.py` | 文件差异、manifest、父链、校验、保留和增量回放工具 | 否，由 Shell 入口调用 |
| `documents_restore.sh` | 旧格式 documents 备份兼容恢复 | 仅处理旧格式时使用 |
| `mariadump_backup.sh` | 已废弃的独立逻辑备份入口 | 否，禁止加入 cron |
| `documents_incremental_backup.sh` | 已废弃的独立文件备份入口 | 否，禁止加入 cron |

Python 工具集中放在 `backups/`，其中复杂的文件扫描、JSON 和 tar 操作使用应用镜像内的 Python；父链选择、链校验和保留计算使用 WSL 宿主机的 `python3`。当前宿主机 Python 3.10.12 满足要求。不要绕过主脚本单独调度任何 Python 工具。

## 3. 一致性与停写方式

正式备份按以下顺序执行：

1. 获取 `${BACKUP_ROOT}/.backup.lock` 的非阻塞 `flock`。
2. 检查 Docker、数据库/应用容器、源目录、凭据权限和备份盘空闲率。
3. 停止 Nginx、API、上传 API 和 WebSocket，拒绝新业务请求。
4. 停止 Celery beat，防止产生新定时任务。
5. 对当前 Supervisor 中全部 Celery program 和 `spug-worker` 执行 graceful stop；无法证明只读的 worker 一律按写 worker 处理。
6. 确认无 Celery worker 进程后，停止整个 `tdyw` 容器；`tdyw-db` 始终保持运行。
7. 在同一停写窗口内生成每日 MariaDB 逻辑全量，并生成 documents/media 全量基线或增量；每周可选附加 mariabackup。
8. 校验 gzip、tar、dump 结构和 SHA-256。
9. 启动 `tdyw` 并等待 Compose healthcheck 通过。
10. 写入 `status=SUCCESS`，重新生成校验和，再把 `.inprogress` 目录原子重命名为正式目录。

Supervisor 为 API 配置 300 秒、Celery 配置 900 秒的退出等待时间。若达到上限仍未退出，备份失败；脚本的 `trap` 会尝试恢复应用。服务恢复或健康检查失败时脚本返回非零，备份目录标记为 `.failed`，不会发布为成功备份。

本方案通过停止应用实现一致静止点，维护窗口内所有用户均无法使用系统。约 100 用户的内网 CRUD 系统应把任务安排在每日 02:00，并根据首次真实运行记录的 `freeze_seconds` 评估窗口长度。

## 4. 备份集格式

成功目录示例：

```text
/data/backups/tdyw/backup_sets/backup_set_20260723_180000/
├── database.sql.gz
├── database.mariabackup.tar.gz      # 仅 DB_BACKUP_MODE=both 时存在
├── documents.tar.gz
├── documents.manifest.json
├── documents.delta.json
├── media.tar.gz
├── media.manifest.json
├── media.delta.json
├── manifest.json
└── SHA256SUMS
```

`manifest.json` 使用 schema 4，记录数据库产物类型、文件集模式、全量基线 ID、直接父备份 ID、开始/结束时间、停写秒数、镜像版本、文件统计和 SHA-256。密码、cnf 内容和连接字符串不写入产物或日志。

每周日默认生成 documents/media 全量基线；其余日期比较上一成功快照，只把新增和修改文件写入 tar，并在 `*.delta.json` 记录删除文件、删除目录和重命名形成的“删除旧路径 + 新增新路径”。`*.manifest.json` 始终描述目标日期的完整文件状态，而不是仅描述增量内容。增量不依赖单一 mtime marker。

文件 manifest 对每个文件记录相对路径、大小、mtime、ctime 和 SHA-256。归档器使用 Python 文件系统 API 处理中文、空格、换行和特殊字符文件名，拒绝符号链接及特殊文件，并在归档前后比较文件状态。应用已停止；若归档过程中仍检测到状态变化，任务立即失败。

失败目录使用 `.failed` 后缀并包含 `FAILED.json`。恢复和人工复制只能选择无后缀且 `manifest.json` 为 `SUCCESS` 的目录。

## 5. MariaDB 备份与恢复凭据

宿主机创建仅“备份任务执行用户”可读的客户端配置。当前建议由 root cron 执行，因为备份目录和日志目录均使用 root 私有权限：

```ini
[client]
host=127.0.0.1
port=3306
user=root
password=REPLACE_WITH_REAL_SECRET
```

```bash
sudo chown root:root /etc/tdyw-backup/tdyw_backup.cnf
sudo chmod 600 /etc/tdyw-backup/tdyw_backup.cnf
sudo install -d -m 700 -o root -g root /data/backups/tdyw/backup_sets
sudo install -d -m 700 -o root -g root /var/log/tdyw-backup
```

真实文件不得加入 Git。配置文件必须是普通文件、权限为 0600/0400，并且由实际执行备份的系统用户可读。脚本把该文件短暂复制到数据库容器 `/tmp`，以 `--defaults-extra-file` 读取，并在 `EXIT/INT/TERM` 时删除；连接地址强制覆盖为数据库容器内 `127.0.0.1:3306`。账号和密码仅以 cnf 的 `[client]` 配置为准，脚本不使用 `DB_USER`、`--user` 或 `-p` 覆盖。密码不会出现在命令行和日志中，实际认证账号由 `CURRENT_USER()` 查询后记录到 `manifest.json`。

当前 cnf 可配置现有的 `root` 账号，但该账号具有完整数据库权限。以后重新建立最小权限备份账号时，只需修改 cnf 中的 `user/password` 并先通过 dry-run，统一备份脚本无需再次修改。

恢复使用单独的 `/etc/tdyw-backup/tdyw_restore.cnf`，模板为 `database_maintenance/db_accounts/restore_client.cnf.template`。恢复账号必须具备创建、删除和导入目标库的权限，不能用未来仅有 SELECT 的备份账号。两个 cnf 都不得进入 Git，也不得通过 `-p密码` 或环境变量传递密码。恢复 cnf 同样必须是普通文件，权限只能为 0600 或 0400。

```bash
cd /mnt/e/TDYW/spug-3.0

```

确认 `tdyw`、`tdyw-db` 均为运行状态，备份盘可用空间不少于 20%。每周全量日应至少能容纳数据库逻辑 dump、documents、media 各一份；启用每周物理备份时还要同时容纳接近整个 MariaDB 数据目录大小的物理归档及容器临时目录。

## 7. Dry-run 与正式备份

脚本默认 `DRY_RUN=YES`。Dry-run 会做前置检查，并把 cnf 临时复制到数据库容器 `/tmp`，执行只读查询验证 cnf 中的账号能登录且具有目标库 SELECT 权限，随后立即删除临时文件。它不会获取备份锁、停止服务、创建备份或删除旧备份：

```bash
cd /mnt/e/TDYW/spug-3.0
BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf \
BACKUP_ROOT=/data/backups/tdyw/backup_sets \
./backups/backup_set_create.sh
```

确认输出后才显式执行：

```bash
BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf \
BACKUP_ROOT=/data/backups/tdyw/backup_sets \
FILESET_BACKUP_MODE=auto \
DRY_RUN=NO \
RETENTION_DELETE=NO \
./backups/backup_set_create.sh
```

`FILESET_BACKUP_MODE=auto` 默认周日（`FILESET_FULL_WEEKDAY=7`）做全量基线，其余日期做增量；找不到完整父链时自动降级为新全量。可用 `full` 强制建立新基线；显式 `incremental` 在没有完整父链时会失败。

日常定时任务只使用上述 `auto` 模式。以下命令只用于人工干预，不要额外加入 cron：

```bash
# 强制建立新的 documents/media 全量基线
FILESET_BACKUP_MODE=full DRY_RUN=NO ./backups/backup_set_create.sh

# 强制文件增量；没有完整成功的 schema 4 父链时会直接失败
FILESET_BACKUP_MODE=incremental DRY_RUN=NO ./backups/backup_set_create.sh
```

每周附加 MariaDB 物理全量需要显式设置 `WEEKLY_PHYSICAL_BACKUP=YES`，并确保数据库容器已安装与 MariaDB 版本匹配的 `mariabackup`。数据库逻辑全量始终保留，物理产物只用于缩短整实例恢复时间。

首次真实运行保持 `RETENTION_DELETE=NO`。查看停写时长、产物增长和健康检查结果后，再决定是否启用保留删除。

废弃的独立入口 `mariadump_backup.sh` 和 `documents_incremental_backup.sh` 默认返回 64，不能加入 cron。`mariabackup_backup.sh` 已改为由统一入口调用的内部 worker；旧独立模式仅为历史兼容保留，其独立产物不属于新一致性 backup_set。

## 8. 校验成功备份

```bash
set -euo pipefail
set_dir=/data/backups/tdyw/backup_sets/backup_set_YYYYmmdd_HHMMSS

cd "$set_dir"
grep -q '"status": "SUCCESS"' manifest.json
sha256sum -c --strict SHA256SUMS
gzip -t database.sql.gz
zgrep -q -E 'CREATE TABLE|Table structure for table' database.sql.gz
tar -tzf documents.tar.gz >/dev/null
tar -tzf media.tar.gz >/dev/null
```

单个增量目录校验通过不等于整条链可恢复。对目标日期执行以下 dry-run 会验证从全量基线到目标日期的所有父链、SHA256SUMS、数据库格式和增量元数据，但不会写数据库或文件：

```bash
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
./backups/backup_set_restore.sh backup_set_YYYYmmdd_HHMMSS
```

## 9. 每日 02:00 定时调度

备份脚本不是常驻程序，不会自行定时。cron 的 `0 2 * * *` 决定每天 02:00 运行；脚本内的 `FILESET_BACKUP_MODE=auto` 和 `FILESET_FULL_WEEKDAY=7` 决定周日文件全量、其他日期文件增量。只配置一条定时任务。

仓库提供 `backups/tdyw-backup.cron.example`，不会自动修改宿主机 crontab。首次安装前先完成 dry-run 和至少一次人工正式备份，然后编辑 root crontab：

```bash
cat backups/tdyw-backup.cron.example
sudo crontab -e
```

当前 WSL 路径对应的安全起始配置如下。初期保持 `RETENTION_DELETE=NO`，不要在尚未完成物理恢复演练时加入 `WEEKLY_PHYSICAL_BACKUP=YES`：

```cron
0 2 * * * cd /mnt/e/TDYW/spug-3.0 && BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf BACKUP_ROOT=/data/backups/tdyw/backup_sets FILESET_BACKUP_MODE=auto FILESET_FULL_WEEKDAY=7 DRY_RUN=NO RETENTION_DAYS=30 RETENTION_DELETE=NO ./backups/backup_set_create.sh >> /var/log/tdyw-backup/backup_set.log 2>&1
```

安装后检查：

```bash
sudo systemctl enable --now cron      # WSL 已启用 systemd 时
sudo service cron start              # 未启用 systemd 时使用
sudo crontab -l
timedatectl
sudo tail -n 200 /var/log/tdyw-backup/backup_set.log
```

WSL 完全停止时，Linux cron 不会唤醒发行版，错过的任务也不会自动补跑。如果该 WSL 实例并非持续运行，应使用 Windows 任务计划程序每天 02:00 调用：

```text
程序：C:\Windows\System32\wsl.exe
参数：-d Ubuntu-22.04 -u root -- bash -lc "cd /mnt/e/TDYW/spug-3.0 && BACKUP_CLIENT_CNF=/etc/tdyw-backup/tdyw_backup.cnf BACKUP_ROOT=/data/backups/tdyw/backup_sets FILESET_BACKUP_MODE=auto FILESET_FULL_WEEKDAY=7 DRY_RUN=NO RETENTION_DAYS=30 RETENTION_DELETE=NO ./backups/backup_set_create.sh >> /var/log/tdyw-backup/backup_set.log 2>&1"
```

每日一次备份的理论最长 RPO 约为 24 小时；若故障恰好发生在下一次备份前，最近一次成功 backup_set 可能接近 24 小时前。实际 RPO 还取决于任务是否成功及人工 U 盘副本的新鲜度。

## 10. 本地保留策略

默认保留 30 天，但 `RETENTION_DELETE=NO` 时只报告策略、不删除。启用方式：

```bash
RETENTION_DAYS=30 RETENTION_DELETE=YES DRY_RUN=NO ./backups/backup_set_create.sh
```

清理以完整文件集链为单位。只有整条链同时满足以下条件才会整组删除：

- 名称为正式的 `backup_set_时间戳`，不含 `.inprogress` 或 `.failed`；
- 该链最后一个恢复点也超过 `RETENTION_DAYS`；
- `manifest.json` 明确为 `SUCCESS`；
- `SHA256SUMS` 存在且全量校验通过。

任何条件不满足都会保留。只要仍有增量引用一个全量基线，就不会删除该基线。

## 11. 恢复操作

完整的恢复前检查、逻辑/物理演练、生产恢复审批和恢复后验收见同目录的 `还原脚本维护手册.md`。

统一恢复入口是 `backup_set_restore.sh`。schema 4 恢复会先校验从目标日期到全量基线的完整父链、每个备份集的 `SHA256SUMS`、manifest 和数据库产物；数据库、documents 和 media 必须恢复到同一个目标日期。

### 11.1 只校验并打印恢复计划

不传 `--mode` 时默认为 dry-run，不写数据库或文件：

```bash
cd /mnt/e/TDYW/spug-3.0
RESTORE_CLIENT_CNF=/etc/tdyw-backup/tdyw_restore.cnf \
BACKUP_SETS_DIR=/data/backups/tdyw/backup_sets \
./backups/backup_set_restore.sh backup_set_YYYYmmdd_HHMMSS
```

### 11.2 隔离逻辑恢复演练（任务 6 执行）

恢复演练必须使用名称包含 `test` 的独立应用和数据库容器，以及 `/tmp` 下的隔离文件目录：

```bash
APP_CONTAINER=tdyw-test \
DB_CONTAINER=tdyw-db-test \
RESTORE_CLIENT_CNF=/etc/tdyw-backup/restore-test-admin.cnf \
DRILL_ROOT=/tmp/tdyw-restore-drill-YYYYmmdd \
./backups/backup_set_restore.sh --mode drill backup_set_YYYYmmdd_HHMMSS
```

脚本会恢复目标日期的数据库逻辑全量，并从基线开始依序回放 documents/media 增量，最终逐文件校验目标 manifest。导入后仍需比对表数量、关键记录，并用测试应用验证下载和预览。物理恢复演练需额外设置 `DATABASE_RESTORE_MODE=physical`，且目标日期本身必须包含物理产物，不能借用其他日期的物理备份。

物理恢复演练命令形式如下，它会覆盖测试数据库实例的数据目录，因此只能对隔离测试容器执行：

```bash
DATABASE_RESTORE_MODE=physical \
APP_CONTAINER=tdyw-test \
DB_CONTAINER=tdyw-db-test \
RESTORE_CLIENT_CNF=/etc/tdyw-backup/restore-test-admin.cnf \
DRILL_ROOT=/tmp/tdyw-restore-drill-YYYYmmdd \
./backups/backup_set_restore.sh --mode drill backup_set_YYYYmmdd_HHMMSS
```

### 11.3 生产恢复

生产恢复会停止应用、删除并重建生产数据库、清空并回放 documents/media，然后重启应用并检查健康状态，属于破坏性操作。本阶段不得执行。真正执行前必须完成任务 6、确认 U 盘或其他独立副本可用，并取得明确变更批准。命令必须使用 `--mode production`，脚本还会要求输入 `RESTORE_PRODUCTION` 二次确认；不要在常规操作中设置 `ASSUME_YES=YES`。

2026-07-23 已生成的 schema 2 全量备份没有增量链元数据，仍可按其 `database.sql.gz`、`documents.tar.gz`、`media.tar.gz` 手工恢复，但不会被 schema 4 自动恢复入口当作增量基线。首次运行新脚本会自动建立新的 schema 4 全量基线。

- mariabackup `prepare/copy-back` 的隔离恢复演练；
- 定期自动恢复演练和失败告警。

因此可以开始按日生成备份，但不能仅凭备份成功日志断言恢复能力已经完全验证。上述三项真实恢复验证必须在任务 6 完成，生产恢复仍然禁止。

## 13. 人工复制到 U 盘

1. 先查看目标 backup_set 的 `fileset_chain.base_backup_set_id` 和 `parent_backup_set_id`。
2. 从目标日期沿父 ID 一直找到全量基线，链中每个目录都必须复制，不能只复制最后一个增量。
3. 复制前在每个链目录执行 `sha256sum -c --strict SHA256SUMS`。
4. 将整条链的 backup_set 目录复制到 U 盘，不拆分、不改名、不遗漏文件。
5. 安全卸载并重新挂载 U 盘。
6. 在 U 盘的每个链目录再次执行 SHA-256 校验。
7. 记录目标 backup_set_id、基线 ID、链成员、复制日期、操作人和校验结果。

示例：

```bash
chain_ids=(backup_set_基线 backup_set_增量1 backup_set_目标日期)
usb_root=/media/backup-operator/TDYW_BACKUP
for id in "${chain_ids[@]}"; do
  (cd "/data/backups/tdyw/backup_sets/$id" && sha256sum -c --strict SHA256SUMS)
  cp -a -- "/data/backups/tdyw/backup_sets/$id" "$usb_root/"
done
sync
for id in "${chain_ids[@]}"; do
  (cd "$usb_root/$id" && sha256sum -c --strict SHA256SUMS)
done
```

U 盘人工副本不等于自动异地备份。若 U 盘与服务器长期同地存放，仍不能抵御整机或同地点灾害。

## 14. 故障处理与回滚

脚本失败时先确认 `tdyw` 是否恢复并健康：

```bash
docker ps --filter name=tdyw
docker logs --tail 200 tdyw
docker start tdyw   # 仅在确认容器未运行时执行
```

`.failed` 目录保留用于排查，可查看 `FAILED.json` 的 `failure_stage`。不要把它改名为正式目录，也不要从中恢复。

定时任务未执行时依次检查 root crontab、cron 服务、WSL 是否在计划时间运行、系统时区和日志目录权限。备份成功但下一次增量找不到父链时，不要手工修改 manifest；保持 `FILESET_BACKUP_MODE=auto`，脚本会安全建立新的全量基线。

代码回滚只需恢复本阶段脚本、manifest 工具和 Supervisor 停机参数，然后重建/重启应用容器。回滚代码不会修改数据库或 volume。不得为了验证回滚而删除、清空或恢复生产数据。
