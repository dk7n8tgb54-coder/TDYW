# 操作审计模块修复建议

## 检查范围

- 后端审计模型与接口：`spug_api/apps/logs/models.py`、`views.py`、`audit.py`、`middleware.py`、`urls.py`
- 登录审计补充逻辑：`spug_api/apps/account/views.py`
- 前端操作审计页面：`spug_web/src/pages/system/audit/*`
- 菜单与权限入口：`spug_web/src/routes.js`、`spug_web/src/pages/system/role/codes.js`
- 代理路径：`docker/config/nginx.conf`、`config/dev/nginx.conf`、`spug_web/src/setupProxy.js`

## 总体结论

操作审计模块已经具备基础能力：系统管理菜单中存在“操作审计”入口，前端页面可调用 `/api/logs/audit/` 查询，后端也已注册 `apps.logs`、审计中间件和相关 URL。权限点 `system.audit.view` 已接入菜单、角色和后端 `AdminView`。

但当前实现仍处于基础骨架阶段，主要问题集中在“审计准确性”和“审计完整性”：

- 业务失败响应可能被记录为成功，影响审计可信度。
- 删除、导出、下载等关键动作记录不完整或动作类型不准确。
- 部分模块路径未纳入对象类型映射，会出现 `unknown`。
- 查询接口分页缺少边界保护，存在异常和性能风险。
- 前端筛选控件与后端枚举值不一致，用户输入中文可能查不到结果。

建议优先修复 P0/P1 项，再做页面交互和长期归档能力优化。

## P0 必须修复

### 1. 修复业务失败被审计为成功

位置：

- `spug_api/apps/logs/middleware.py:73`
- `spug_api/libs/utils.py:85`

现象：

审计中间件当前只根据 HTTP 状态码判断操作是否成功：

```python
is_success = True
if hasattr(response, 'status_code') and response.status_code >= 400:
    is_success = False
```

但项目通用 `json_response(error=...)` 默认仍返回 HTTP 200。大量业务失败场景，例如参数错误、权限不足、数据不存在、重复提交等，都会以 `{"error": "..."}` 的形式返回 200。

影响：

- 删除失败、编辑失败、权限校验失败可能在操作审计中显示“成功”。
- 审计日志无法真实反映用户操作结果，安全追溯价值下降。

修复建议：

- 在审计中间件中解析 JSON 响应体，如果存在非空 `error`，应判定为失败。
- 同时将错误信息写入 `detail`，方便审计页面展示失败原因。
- 兼容非 JSON 响应、文件响应和流式响应，解析失败不能影响主请求。

示例思路：

```python
def _resolve_success_and_error(self, response):
    if hasattr(response, 'status_code') and response.status_code >= 400:
        return False, None
    if not hasattr(response, 'content'):
        return True, None
    try:
        data = json.loads(response.content)
    except Exception:
        return True, None
    error = data.get('error') if isinstance(data, dict) else None
    return not bool(error), error
```

验证点：

- 创建用户时密码不合规，审计结果应为失败。
- 删除不存在的数据，审计结果应为失败，并展示错误原因。
- 正常创建、编辑、删除仍应显示成功。

### 2. 修复 DELETE 请求无法记录 query 参数中的对象 ID

位置：

- `spug_api/apps/logs/middleware.py:126`
- `spug_api/apps/logs/middleware.py:155`

现象：

中间件当前只从 URL 最后一段和 POST/PUT/PATCH 的 JSON body 中提取对象 ID。项目中大量删除接口使用 `DELETE ?id=xxx`，例如账户、设备、故障、运行日志、排班等模块。

影响：

- 删除操作审计记录中 `target_id` 为空。
- 后续追溯时只能知道“某用户删除了某类对象”，无法定位具体记录。

修复建议：

- 在 `_extract_detail` 中优先或补充读取 `request.GET.get('id')`。
- 对 RESTful 路径如 `/upgrade/records/<pk>/delete/`，保留从 URL 片段提取 ID 的逻辑。
- 对批量删除接口，支持读取 `ids` 并记录为逗号分隔或 JSON 数组。

验证点：

- `DELETE /api/account/user/?id=1` 应记录 `target_id=1`。
- `DELETE /api/device/device-resume/?id=1` 应记录 `target_id=1`。
- RESTful 删除路径仍能记录 URL 中的 ID。

### 3. 修复 POST + action=delete 被记录为创建

位置：

- `spug_api/apps/logs/audit.py:67`
- 示例：`spug_api/apps/duty/views.py:112`

现象：

当前操作类型只由 HTTP 方法决定，`POST` 固定映射为 `create`。但项目中存在用 `POST` 携带 `action='delete'` 表示删除的接口，例如值班日志。

影响：

- 实际删除动作在审计中显示为“创建”。
- 统计和筛选操作类型时会产生错误数据。

修复建议：

- 在 `resolve_action` 或中间件中结合 request body 判断业务动作。
- 如果 JSON body 中存在 `action=delete`，应优先映射为 `delete`。
- 如果存在 `action=export/import/approve`，也可映射到对应动作。

示例思路：

```python
def resolve_action(method, body_data=None):
    if isinstance(body_data, dict):
        action = str(body_data.get('action') or '').lower()
        if action in {'delete', 'export', 'import', 'approve'}:
            return action
    return METHOD_ACTION_MAP.get(method, 'other')
```

验证点：

- 值班日志通过 `POST {id, action: "delete"}` 删除时，应记录为删除。
- 普通新增 POST 仍应记录为创建。
- PATCH/PUT 状态变更仍应记录为更新。

## P1 建议尽快修复

### 4. 补全操作对象类型映射

位置：

- `spug_api/apps/logs/audit.py:44`

现象：

当前 `TARGET_MAP` 未覆盖部分实际模块路径，例如：

- `/account/tenant/`：租户管理
- `/radio-license/`：无线电台执照
- `/logs/`：审计模块自身
- `/checksheet/export/`、`/runlog/export/` 等导出类路径

影响：

- 审计日志中的对象类型可能显示为 `unknown`。
- 前端“对象类型”筛选无法覆盖所有业务模块。

修复建议：

- 根据 `spug_api/spug/urls.py` 和各模块 `urls.py` 补全路径映射。
- 对同一模块下的细分路径可先统一映射到模块级类型，例如 `radio_license`。
- 如果需要更细粒度，可逐步扩展为 `radio_license_attachment`、`radio_license_reminder` 等。

建议补充：

```python
'/account/tenant': {'type': 'tenant', 'name': '租户'},
'/radio-license/': {'type': 'radio_license', 'name': '无线电台执照'},
'/logs/': {'type': 'audit', 'name': '操作审计'},
```

验证点：

- 新建、编辑、删除租户时对象类型不再是未知。
- 新增、删除无线电台执照时对象类型显示为无线电台执照。
- 前端对象类型下拉可展示新增类型。

### 5. 为分页参数增加边界保护

位置：

- `spug_api/apps/logs/views.py:18`
- `spug_api/apps/logs/views.py:70`

现象：

`page` 和 `page_size` 只转换为整数，没有做最小值和最大值限制。传入 `page=0`、负数或超大 `page_size` 可能导致异常或性能问题。

影响：

- 负数切片可能触发 Django QuerySet 异常。
- 超大分页可能一次查询大量审计日志，拖慢数据库。

修复建议：

- `page` 最小为 1。
- `page_size` 建议限制在 10 到 100 或 200。
- 参数非法时返回明确错误，或自动钳制到安全范围。

示例思路：

```python
page = max(form.page, 1)
page_size = min(max(form.page_size, 10), 100)
```

验证点：

- `page=0` 不应报错。
- `page_size=100000` 不应返回超大数据。
- 正常分页行为不受影响。

### 6. 避免敏感字段进入审计详情

位置：

- `spug_api/apps/logs/middleware.py:136`

现象：

中间件会把 request body 中除 `password`、`token`、`secret`、`key` 等字段外的数据写入 `detail`。但项目中还存在 `old_password`、`new_password`、`private_key`、`public_key`、`api_key`、`spug_push_key`、`wx_token` 等敏感或半敏感字段。

影响：

- 修改个人密码、系统密钥、推送配置等操作可能泄露敏感信息到审计日志。
- 审计日志通常保留周期更长，一旦泄露影响更大。

修复建议：

- 使用黑名单关键字匹配，而不是只匹配固定字段名。
- 对包含 `password`、`token`、`secret`、`key`、`private`、`credential` 等关键词的字段统一脱敏。
- 对必要字段保留“已修改”标记，不记录真实值。

示例思路：

```python
SENSITIVE_KEYWORDS = ('password', 'token', 'secret', 'key', 'private', 'credential')

def _is_sensitive_field(name):
    lower = name.lower()
    return any(keyword in lower for keyword in SENSITIVE_KEYWORDS)
```

验证点：

- 修改密码时审计详情不出现旧密码和新密码。
- 修改系统密钥时审计详情不出现密钥原文。
- 普通业务字段仍能正常展示。

### 7. 明确登录失败审计的租户归属策略

位置：

- `spug_api/apps/account/views.py:504`

现象：

登录失败时，如果用户名找不到对应用户，审计日志会写入 `tenant_id='default'`。普通租户管理员只能看自己租户日志，因此可能看不到未知账号爆破、跨租户用户名尝试等失败登录行为。

影响：

- 非超管的安全审计视角不完整。
- 登录攻击可能只在超管视角可见。

修复建议：

- 明确产品策略：
  - 如果失败登录只给超管看，保持全局归档，但页面需说明。
  - 如果租户管理员也要看，应在登录请求中引入租户上下文，或按用户名归属租户写入。
- 对未知用户登录失败，可考虑写入全局日志并提供超管专用筛选。

验证点：

- 已存在租户用户密码错误，日志归属该用户租户。
- 不存在用户名登录失败，超管可查看。
- 普通租户管理员看到的失败登录范围符合产品定义。

## P2 体验和维护优化

### 8. 前端筛选控件改为枚举下拉

位置：

- `spug_web/src/pages/system/audit/index.js:25`
- `spug_web/src/pages/system/audit/Table.js:199`

现象：

页面顶部“操作类型”“对象类型”是普通输入框，但后端筛选要求传枚举值，如 `create`、`update`、`delete`。用户输入“创建”不会匹配 `action=create`。同时表格工具栏中又提供了操作类型和对象类型下拉，形成重复筛选。

影响：

- 用户输入中文无法查到数据，体验误导。
- 同一筛选项在页面上出现两处，不利于维护。

修复建议：

- 顶部筛选区域改用 `Select`，复用 `store.actionOptions` 和 `store.targetTypeOptions`。
- 或者移除表格工具栏中的重复下拉，只保留顶部筛选。
- 增加“重置”按钮，清空筛选条件并回到第一页。

验证点：

- 选择“创建”能正确传 `action=create`。
- 选择“用户”能正确传 `target_type=user`。
- 重置后列表恢复全部数据。

### 9. 打印按钮应明确打印当前页或支持导出

位置：

- `spug_web/src/pages/system/audit/index.js:44`
- `spug_api/apps/logs/views.py:84`

现象：

前端“打印”按钮只是调用 `window.print()`，实际打印的是当前浏览器页面。后端虽然提供了 `/api/logs/audit/export/`，但前端未使用。

影响：

- 用户可能误以为打印的是当前筛选条件下的全部审计记录。
- 分页数据只展示当前页，打印结果不完整。

修复建议：

- 明确按钮文案为“打印当前页”，或实现真正的“导出审计日志”。
- 如果使用后端 export 接口，应沿用当前筛选条件，并提示最多导出 5000 条。
- 后续可接入统一导出组件，输出 Excel。

验证点：

- 当前页打印与页面展示一致。
- 导出时筛选条件与列表一致。
- 超过导出上限时给出明确提示。

### 10. 增加数据库索引和归档策略

位置：

- `spug_api/apps/logs/models.py`
- `spug_api/apps/logs/migrations/`

现象：

审计日志会持续增长，但当前模型未对常用筛选字段定义索引。查询接口常按 `tenant_id`、`created_at`、`username`、`action`、`target_type` 筛选。

影响：

- 数据量增长后，操作审计列表查询会变慢。
- `detail__icontains` 模糊搜索在大表上成本较高。

修复建议：

- 增加组合索引，例如 `tenant_id + created_at`。
- 为 `action`、`target_type`、`username` 增加普通索引。
- 制定保留策略，例如保留 180 天或 365 天，支持归档到外部日志系统。

示例思路：

```python
class Meta:
    db_table = 'audit_logs'
    ordering = ('-id',)
    indexes = [
        models.Index(fields=['tenant_id', '-id']),
        models.Index(fields=['tenant_id', 'created_at']),
        models.Index(fields=['action']),
        models.Index(fields=['target_type']),
    ]
```

验证点：

- 大量数据下按时间范围查询响应稳定。
- 普通租户只能查询自己租户日志。
- 归档任务不会删除保留期内数据。

## 建议修复顺序

1. 修复成功/失败判断，保证审计结果可信。
2. 修复对象 ID 提取和 POST 删除动作识别，保证关键操作可追溯。
3. 补全对象类型映射，减少 `unknown` 数据。
4. 增加分页边界和敏感字段脱敏，降低风险。
5. 优化前端筛选、打印/导出、索引和归档能力。

## 回归测试建议

- 权限测试：无 `system.audit.view` 的普通用户不能访问 `/api/logs/audit/`。
- 租户隔离测试：普通租户用户只能看到本租户审计日志，超管可查看全部。
- 成功/失败测试：业务接口返回 `error` 时，审计结果应为失败。
- 删除测试：`DELETE ?id=xxx`、RESTful 删除路径、`POST action=delete` 均能记录正确动作和对象 ID。
- 敏感字段测试：密码、token、key、私钥、推送密钥等不出现在 `detail` 中。
- 筛选测试：操作人、操作类型、对象类型、关键词、时间范围均可正确过滤。
- 分页测试：非法 `page/page_size` 不应触发后端异常。
