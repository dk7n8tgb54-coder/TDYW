你在 `E:\TDYW\spug-3.0` 仓库工作。目标是根据根目录 `制度管理模块设计方案.md`，将“制度管理”实现为可用、可验证的前后端模块。持续执行到功能、权限、文件版本和验证闭环完成；不要在给出计划或写出第一批代码后就宣称完成。实施前先读根目录、`spug_api/`、`spug_web/` 的 `AGENTS.md`，以及触及目录的下层规则。项目中的 `loop engineering/00-intake.md` 至 `06-retro.md` 可作为循环记录结构，但其中的无线电台执照示例不是本任务的业务依据。

## 一、目标与优先级

以现行方案和用户后续确认的决定为业务基线；代码事实用于判定已有能力、约束及方案是否过时，不能悄悄覆盖业务意图。手册名称、编号、类别、数量、部门或科室归属都由页面维护，不能硬编码。制度管理的业务授权只依据账号所持角色、手册关联角色及编辑密码；`tenant_id` 不参与手册归属、查看或编辑判定。项目要求的模型租户字段可以保留，但任何跨租户查询都必须先有手册级角色授权，不能开放成全平台可见。

首期应交付一条真实闭环：创建手册和上传 `.doc`/`.docx` 原稿；按角色查看已发布版本；通过角色加每本手册密码进入编辑；保存草稿；按发布角色填写变更说明并发布不可变版本；查看、预览和下载历史版本；记录关键操作；维护章节分工和参与者。部门、科室及跨部门参与者通过配置角色取得权限。科室共用账号的审计只识别账号，不能虚构个人身份。不得把同一账号的“编辑后再审批”包装成独立审批。

现有 `regulation` 是规章台账，`document` 是资料库；新手册模块应有独立业务模型和版本规则。复用已有公开能力时遵守模块边界。前端使用现有 React 17、antd 4.21.5、MobX 风格；后端遵守 Django、MariaDB、Redis、权限、文件补偿和 HTTP 业务错误约定。

## 二、启动核查与反馈门槛

1. 先执行 `git status` 和相关文件的 `git diff`，记录并保护所有未提交修改。确认当前代码中的路由、角色分配边界、租户查询、附件预览、审计日志和 Docker 服务。不要复用旧规章附件覆盖手册历史文件。
2. 从页面/URL 到 View、Service、Model、文件存储和外部编辑服务梳理调用链。逐项列出方案要求的“已有、缺失、冲突、待决”，并给每项定义可观察的验收证据。冲突须定位到文件和行为，不能凭旧文档推断当前状态。
3. 在接入在线编辑器前，用真实、脱敏的代表性手册验证候选方案。比较 ONLYOFFICE Docs、Collabora Online；桌面 Word 编辑后上传只能作为经用户确认的降级路线，不能擅自取代“在线编辑”目标。试验至少覆盖 `.doc` 转换、复杂表格、目录与编号、页眉页脚、字体、分页、批注/修订，以及编辑保存后再用 Word 打开的结果；同时核对许可、生产部署条件和服务资源。原稿永不覆盖，试验在开发或测试环境进行。
4. 若缺少真实手册样本、许可结论或可运行的编辑服务，先完成不依赖这些条件的手册、角色、草稿、版本、审计和管理流程，并用替身服务验证接口契约；对外部服务的真实联调明确标为 `BLOCKED`，不要把模拟测试冒充兼容性结论。
5. 只有需要业务方选择且无法从现有上下文推出的事项才提问：例如在线编辑器及许可、真实手册保真验收、章节是否必须并行编制、跨部门参与者能否查看最终发布版、维护角色的责任人。一次集中提出选择、影响和推荐选项；提问后继续独立工作，不等待答案才开始所有任务。明确需要答案的功能不得自行编造口径。

## 三、循环执行协议

按最小可验收的纵向功能切片循环，而不是一次写完全部代码再测试。建议顺序：身份和授权查询；手册与原稿；草稿及密码会话；编辑服务接入；发布与历史版本；章节分工；页面和跨模块联调。顺序可依据实际依赖调整，并说明原因。

每一轮必须完成以下闭环：

1. **读取与复现**：确认当前行为、缺口或失败，列出本轮唯一主要目标、涉及文件和验收条件。
2. **设计与实现**：修改最少的文件，沿用项目的 Service/API/组件模式。涉及共享组件或权限时搜索全部调用方。迁移只针对指定 app 生成，考虑历史数据和回滚路径。
3. **验证与校准**：先跑相关真实行为测试，再跑必要的跨模块测试和代码质量门禁；前端渲染、请求、权限状态和错误状态要实际验证。失败时找根因、修复、重跑，不降低断言、不删除测试、不扩大质量 baseline。
4. **记录与续行**：更新工作清单，记录实际命令、通过/失败/未运行状态、发现的问题和下一轮目标。该轮通过且仍有目标时立即进入下一轮，不以阶段性汇报代替继续工作。

每轮只增加足以证明行为的测试。后端测试必须在 Docker 隔离测试数据库执行，并检查数据库状态、文件副作用及角色越权；不得读取源码字符串冒充行为测试。Playwright 只在开发或专用测试环境使用测试账号，不碰生产数据。构建、测试和报告产物按仓库规范处理。

## 四、不可降低的验收标准

- **角色与范围**：不同租户的领导可凭同一平台级角色或手册配置的角色获得授权；无角色者即使知道密码也无法查看草稿、编辑或发布。角色撤销后已有编辑会话失效。跨部门参与者只能访问获授权的手册和版本。
- **密码与会话**：只保存密码哈希；限制失败尝试；重置密码使旧会话失效。每个文件读取、保存回调和发布操作都在后端重新校验绑定关系，不能依赖前端按钮。
- **Word 文件**：`.doc` 原稿保留，编辑副本转换失败时给明确反馈；`.docx` 编辑过程不改写原稿。编辑服务下载地址和回调须校验签名、期限、手册、草稿及版本，不能暴露长期账号 token。
- **并发与版本**：首期同一本主 Word 草稿一次只有一个有效可写会话；同账号多标签、不同账号和迟到回调不能覆盖新内容。发布版独立存储且不可变；回退旧版必须产生新草稿与新发布版本。
- **分工与审计**：多人按章节先后参与有可见的负责人、提交和进度记录，但不得声称已实现正文段落级权限。发布需变更说明；版本历史记录内容、哈希、时间和账号；关键动作写审计。科室共用账号不声称能识别实际个人。
- **用户体验**：列表、详情、草稿编辑、历史版本、权限配置、密码重置和异常恢复可完整操作；加载、空数据、错误、无权限及文件转换失败均有明确状态。成功提示等待后端真实成功，HTTP 200 + `error` 仍视为失败且错误只提示一次。
- **工程门禁**：路由、后端权限、角色配置、API、数据库迁移、Docker 配置和测试相互一致；新源码保持 LF。运行 `scripts/code_quality_check.py`、`git diff --check`、相关前端测试及构建。具体命令以各级 `AGENTS.md` 为准。

## 五、何时继续、何时拿反馈、何时停止

**继续**：发现可复现缺陷、验收项未满足、测试失败、文件或权限边界未覆盖、编辑器回调未联通、代码与方案有可判断的普通差异时，继续下一轮调查或修复。因外部服务暂不可用时，继续做不依赖它的工作，并保留明确的阻断记录。不要用固定轮数或“已经工作很久”作为停止理由。

**拿反馈**：需要业务方在互斥产品方案中作选择，或需要真实手册、编辑器许可/部署资源、生产权限等外部条件时，给出已经完成的可审查证据、选项与推荐；保持问题集中、具体。未得到决定前不实施会锁定该决定的设计，但继续其他独立事项。若要求部署到生产、执行生产迁移或删除生产数据，先完成可审查的实施与回滚材料，再请求相应授权；不要把开发环境迁移等同于生产操作。

**停止并汇报**仅在以下情况：

1. 所有已确认范围的验收项通过，必要的真实编辑服务联调与文档往返试验完成，代码质量和相关测试通过，未完成项为零；或
2. 剩余工作全部依赖尚未获得的用户决定或外部条件，且已穷尽独立可做的调查、实现和验证；逐项标出 `BLOCKED`、影响和解除条件；或
3. 用户明确要求暂停或改变任务。

不能以“文档写完”“接口可返回 200”“测试没跑但应该没问题”作为完成。阻断项不算验收通过，不得降低阈值、默许视觉基线或用假数据掩盖。对已授权且可继续的工作，收到反馈后恢复循环，直到达到第 1 条。

## 六、交付与汇报

开始时提供简短的现状核查和迭代清单；实施期间每完成一轮更新进度及证据，持续推进。最终报告按“已实现行为、实际验证、未完成/阻断、风险与决策、文件变更、Git 状态”组织。给出执行过的命令及结果，区分 `PASS`、`FAIL`、`NOT_RUN`、`BLOCKED`。指出原有工作区修改如何得到保护，确认未创建 commit、未覆盖他人修改、未触碰生产数据。若没有达到完成条件，明确说明尚未完成，不能只报告已经做了的部分。
