# 干扰管理模块长期设计方案

## 1. 方案定位

本模块定位为“干扰事件台账 + 规律调查工具”，不负责在平台内完成上报。

干扰处理分为两种业务情景：

1. **普通记录**：记录一次干扰现象，完成信息留存后结束。上报由平台外的既有渠道完成。
2. **规律调查**：当多次事件在时间、地点、频率或现象上呈现关联时，建立调查专题，持续收集事件并进行频谱仪测量，最后形成调查结论。

普通记录是主流程，规律调查是可选的延伸流程，不能要求每条记录都进入调查流程。

## 2. 核心设计原则

### 2.1 事件与调查分离

一次实际发生的干扰是一个 `InterferenceEvent`；多次有关联的事件组成一个 `InterferenceInvestigation`。

事件不因加入调查而失去独立性。原始事件仍可单独查询、统计和审计。

### 2.2 场景分类不等于业务表

“地面”“空中”“跨场景”是事件的发生场景值，不为“跨场景”单独建表。

地面和空中的字段差异通过明细表解决，而不是通过一张包含大量可空字段的万能表解决。

### 2.3 分类字段与自由描述并存

分类字段用于筛选、统计和长期分析；`phenomenon` 等文本字段用于保留现场原始描述。不能只依靠自由文本进行分类。

### 2.4 不把上报做成平台流程

新的正式模型不设置上报状态机、上报编号、上报渠道或上报记录。旧表中的上报字段只作为历史兼容数据处理，不作为新模型设计依据。

## 3. 长期数据结构

```text
InterferenceEvent              一次干扰事件
├── GroundInterferenceDetail   地面专属明细，可选
├── AirInterferenceDetail      空中专属明细，可选
├── InvestigationEvent         调查与事件的关联
└── InterferenceInvestigation  规律调查专题，可选
    └── SpectrumMeasurement    频谱仪测量记录，可选、多条
```

### 3.1 InterferenceEvent：事件主表

主表只保存一次事件的公共信息和分类信息：

| 字段 | 用途 |
| --- | --- |
| `id` / 事件编号 | 平台内部唯一标识，供关联、附件和审计使用 |
| `datetime` | 发生时间 |
| `scene_code` | 发生场景：`ground` 地面、`air` 空中、`cross` 跨场景、`unknown` 未知 |
| `classification_status` | 分类状态：`pending` 待分类、`confirmed` 已确认；仅用于数据完整性，不代表上报状态 |
| `interference_kind_code` | 具体干扰类型，如杂音、间歇中断、完全失联、频率占用、阻塞、虚警、其他、未知 |
| `affected_system_code` | 受影响系统，如通信、导航、监视、数据链、设备电磁兼容、其他 |
| `source_type_code` | 疑似干扰源，如地面设备、车辆/电源、机载设备、外部发射源、环境、未知 |
| `flight_number` | 相关航班号，可为空 |
| `aircraft_no` | 相关机号，可为空 |
| `aircraft_type` | 相关机型，可为空 |
| `phenomenon` | 现场现象和原始描述 |
| `initial_assessment` | 初步判断，可为空，不等同于调查结论 |
| `remark` | 其他备注 |
| 租户、创建人、更新时间、软删除字段 | 系统公共审计和隔离字段 |

分类值应使用受控代码。若未来需要由管理员维护分类，可将代码迁移为字典配置；不为每一个分类值建立独立业务表。

### 3.2 GroundInterferenceDetail：地面明细

仅保存地面场景需要的字段：

```text
位置/机位
频率
地面设备或车辆
其他地面环境信息
```

与 `InterferenceEvent` 建立一对一关系。可以使用共享主键：明细表主键同时是事件外键，不再额外增加一个展示性的 `event_id` 字段。

### 3.3 AirInterferenceDetail：空中明细

仅保存空中场景需要的字段：

```text
航线
被扰频率
告警高度及单位
告警航段
持续时间及单位
```

同样与 `InterferenceEvent` 建立一对一关系并可采用共享主键。

### 3.4 InterferenceInvestigation：规律调查专题

调查专题用于归集多次事件和测量过程：

```text
调查编号
调查名称
调查范围
调查负责人
初始问题/触发原因
涉及地点
涉及频率
调查状态
开始时间
结束时间
调查结果
取消原因
调查结论
后续建议
```

调查状态（2026-10-26 起收敛为三态，旧 draft/observing/measuring/
concluded/closed 全部退役）：

```text
investigating  调查中
ended          已结束
cancelled      已取消
```

生命周期约束：

```text
- 事件是独立事实：不自动创建调查、不显示调查状态；调查只由用户从
  选中记录主动发起，新建保存后即为 investigating（调查中），不设草稿；
- 状态只能通过两个业务动作变更，通用创建/编辑接口拒绝携带
  status/result/cancel_reason（fail-closed）：
    结束调查：必须提交 result（found 发现规律 / not_found 未发现规律 /
              undetermined 暂无法确认）+ 非空调查结论，可选结束时间
              （缺省当前时间）；
    取消调查：必须提交非空取消原因；
- 历史数据迁移映射（0021，保守）：draft/observing/measuring →
  investigating；concluded/closed → ended；cancelled → cancelled；
  历史行 result 保持空串，禁止从自由文本结论推断 result；
- 回滚口径（有损）：investigating → draft、ended → concluded、
  cancelled → cancelled；observing/measuring 与 draft、concluded 与
  closed 的区分不可恢复。
```

这里不包含“已上报”等状态；“观察/测量”是活动而不是状态，不再单设状态。

### 3.5 InvestigationEvent：调查与事件关联

一项调查通常包含多条事件，因此通过关联表保存：

```text
investigation_id
event_id
sequence
relevance_note
linked_at
```

一条普通事件可以不属于任何调查。关联键是数据库内部关系，不要求在界面上单独展示。

### 3.6 SpectrumMeasurement：频谱仪测量记录

一次调查可以有多次测量，测量记录不应塞进某一条事件：

```text
调查专题
测量时间
测量地点
仪器型号/编号
频率范围
中心频率
带宽
场强或功率
测量单位
天线/极化方式
测量结果
测量结论
原始文件附件
```

测量记录必须关联调查专题；必要时可以增加关联事件，但不能用事件字段替代测量记录。

## 4. 业务流程

### 4.1 普通记录流程

```text
新建事件
  -> 选择场景并填写公共信息
  -> 填写地面或空中明细
  -> 保存
  -> 结束
```

平台不处理上报动作，也不要求填写上报结果。

### 4.2 规律调查流程

```text
连续建立多条干扰事件
  -> 按时间、地点、频率、现象筛选
  -> 选择事件并创建调查专题
  -> 持续关联新增事件
  -> 进入“测量中”并录入多次频谱测量
  -> 填写调查结论
  -> 结束调查
```

“出现 4 次、5 次或 6 次”是业务经验，不应写死为系统触发规则。系统只展示关联事件数、首次/最近发生时间等信息，由工作人员决定何时建立调查或开始测量。

跨场景调查可以同时关联地面和空中事件；不需要建立“跨场景调查表”。

## 5. 前端组织方式

### 5.1 菜单

建议干扰管理下设置两个子菜单：

```text
干扰管理
├── 干扰记录
└── 规律调查
```

不设置“待上报”“已上报”菜单。

### 5.2 干扰记录页面

干扰记录可以是一个统一列表，内部提供筛选或 Tab：

```text
全部 | 地面 | 空中 | 跨场景 | 待分类
```

统一列表只显示公共字段和分类字段：

```text
发生时间、发生场景、具体干扰类型、受影响系统、疑似干扰源、航班号、现象摘要、关联调查
```

“关联调查”列展示该事件所关联调查的名称与状态文本（调查中/已结束/已取消），
不显示单独的调查状态值；未关联调查的事件该列为空。

地面位置、频率、告警高度、航段等专属字段在详情抽屉中按场景展示，不在统一列表中全部铺开。

录入入口根据场景动态显示表单：

```text
地面       只显示地面明细
空中       只显示空中明细
跨场景     按需显示地面和空中两组明细
```

因此，前端统一的是列表和入口，数据库并没有被合并成一张宽表，也不会产生大量无意义的空字段。

### 5.3 规律调查页面

调查列表显示：

```text
调查名称、调查状态、关联事件数、首次/最近发生时间、主要地点、主要频率、负责人
```

调查详情建议分为：

```text
概览 | 关联事件 | 频谱测量 | 调查结论 | 附件
```

事件列表提供“创建调查”和“加入已有调查”操作。

## 6. 典型示例

### 普通空中事件

```text
InterferenceEvent
  scene_code = air
  affected_system_code = communication
  interference_kind_code = intermittent

AirInterferenceDetail
  route = HFE-VVO
  alert_altitude = 1200
  duration = 45 秒
```

记录保存后结束，不需要创建调查专题。

### 廊桥重复干扰

```text
事件 1：8 月 1 日，3 号廊桥，118.6MHz，出现杂音
事件 2：8 月 3 日，3 号廊桥，118.6MHz，出现杂音
事件 3：8 月 5 日，4 号廊桥，118.6MHz，出现杂音
事件 4：8 月 8 日，频谱仪测到异常信号
```

然后建立：

```text
调查专题：廊桥 118.6MHz 间歇性干扰分析
关联事件：事件 1、2、3、4
测量记录：一条或多条 SpectrumMeasurement
调查结论：规律是否确认、疑似来源、影响范围和建议措施
```

四条事件仍然独立存在，调查专题只负责归集和分析。

## 7. 与当前代码结构的关系

当前实现是两个独立模型：

```text
BridgeInterferenceRecord
AirInterferenceRecord
```

两者通过抽象基类复用字段，但没有统一的事件主表，也不能自然表达“多个事件属于同一个规律调查”。

长期迁移目标是：

```text
InterferenceEvent
GroundInterferenceDetail
AirInterferenceDetail
InterferenceInvestigation
InvestigationEvent
SpectrumMeasurement
```

旧 `Interference` 表和旧状态/上报字段只用于历史兼容和数据迁移，不作为新业务流程继续扩展。

## 8. 主要不变量

1. 每条干扰事件必须能独立保存和查询。
2. 地面、空中特有字段只能写入对应明细表。
3. 跨场景事件最多同时拥有一条地面明细和一条空中明细。
4. 一项调查可以关联多条事件和多条测量记录。
5. 调查不会改变原始事件的发生事实和原始描述。
6. 普通事件不强制创建调查专题。
7. 上报不属于本平台流程，不设置上报状态和上报菜单。
8. 统一列表统计事件主表，不能因为关联多个明细或调查而重复计数。
9. 租户隔离、附件归属、审计和软删除规则继续沿用全系统公共约束。

## 9. 有意暂不确定的内容

以下内容需要结合实际运行一段时间后再决定，不在本方案中提前复杂化：

- 分类字典是否允许管理员自定义；
- 一条事件是否允许同时属于多个调查专题；
- 频谱仪原始数据是否需要拆成“测量批次 + 测量点”；
- 是否需要保存平台外上报的事实性备注；
- 是否需要为调查结论增加审批或复核流程。
