# 用户角色委派权限稳健修复方案

## 背景

当前账号只要拥有“用户管理/创建账号”权限，就可以在创建或编辑子账号时看到并选择全部角色。由于角色中可能包含超级管理员创建的高权限角色，普通管理员可以通过给子账号绑定这些角色实现越权授权。

现有关键问题点：

- `spug_api/apps/account/views.py` 中 `RoleView.get()` 直接返回 `Role.objects.all()`，导致普通管理员可以看到全部角色。
- `UserView._handle_user_create()` 和 `UserView._handle_user_edit()` 直接执行 `user.roles.set(role_ids)`，没有校验当前操作者是否有权分配这些角色。
- `Role` 模型目前只有 `created_by`，缺少明确的租户归属、系统角色标识和可委派边界。
- 普通管理员如果拥有角色管理权限，还可能自己创建或修改高权限角色，再分配给子账号。

## 修复目标

更稳的修复不只是隐藏下拉选项，而是建立完整的“角色委派权限边界”：

1. 普通管理员只能看到自己租户内可委派的角色。
2. 普通管理员只能给子账号分配自己有权委派的角色。
3. 普通管理员不能分配超级管理员角色、系统角色、全局管理员角色。
4. 普通管理员创建或编辑角色时，角色权限不能超过自己已有权限。
5. 所有安全判断必须以后端为准，前端只做体验优化。
6. 保持超级管理员不受限制，仍可管理全部租户和全部角色。

## 推荐数据模型调整

在 `Role` 模型中增加角色归属和系统标识字段：

```python
class Role(models.Model, ModelMixin):
    name = models.CharField(max_length=50)
    desc = models.CharField(max_length=255, null=True)
    page_perms = models.TextField(null=True)
    deploy_perms = models.TextField(null=True)
    group_perms = models.TextField(null=True)
    is_global_admin = models.BooleanField(default=False)

    tenant_id = models.CharField(max_length=50, null=True, blank=True, db_index=True)
    is_system = models.BooleanField(default=False, db_index=True)

    created_at = models.CharField(max_length=20, default=human_datetime)
    created_by = models.ForeignKey(User, on_delete=models.PROTECT, related_name='+')
```

字段含义：

- `tenant_id`：角色所属租户。普通租户角色必须有值。
- `tenant_id = null`：平台级角色或历史系统角色，只允许超级管理员管理和分配。
- `is_system = true`：系统内置角色，普通管理员不可编辑、不可删除、不可分配。
- `is_global_admin = true`：全局管理员角色，只允许超级管理员创建、编辑、分配。

需要新增 Django migration，并对历史数据做一次兼容迁移。

## 历史数据迁移策略

新增字段后，建议按以下规则初始化历史角色：

1. `created_by.is_supper = true` 的角色：
   - `tenant_id = null`
   - `is_system = true`
   - 作为平台级角色处理，普通管理员不可见、不可分配。

2. `created_by.is_supper = false` 的角色：
   - `tenant_id = created_by.tenant_id`
   - `is_system = false`
   - 作为对应租户下的普通角色处理。

3. `is_global_admin = true` 的角色：
   - 强制 `tenant_id = null`
   - 强制 `is_system = true`
   - 只允许超级管理员分配。

4. 对没有 `created_by` 或历史脏数据的角色：
   - 默认按平台级角色处理，即 `tenant_id = null`、`is_system = true`。
   - 这样偏保守，避免把历史高权限角色错误开放给普通管理员。

## 后端统一授权方法

建议在 `spug_api/apps/account/views.py` 或新建 `spug_api/apps/account/permissions.py` 中增加统一方法，所有角色列表、用户创建、用户编辑、角色编辑都调用它。

```python
def get_assignable_roles(operator):
    if operator.is_supper:
        return Role.objects.all()

    return Role.objects.filter(
        tenant_id=operator.tenant_id,
        is_system=False,
        is_global_admin=False,
    )
```

该方法定义“当前操作者可以分配给别人”的角色集合。

同时建议增加：

```python
def validate_assignable_role_ids(operator, role_ids):
    if operator.is_supper:
        return None

    allowed_ids = set(
        get_assignable_roles(operator).values_list('id', flat=True)
    )
    requested_ids = set(role_ids or [])

    if not requested_ids.issubset(allowed_ids):
        return '无权分配所选角色'

    return None
```

## 角色列表接口修复

修改 `RoleView.get()`：

```python
def get(self, request):
    roles = get_assignable_roles(request.user)
    return json_response(roles)
```

效果：

- 超级管理员看到全部角色。
- 普通管理员只看到本租户普通角色。
- 超级管理员创建的系统角色、全局管理员角色、其他租户角色不会出现在下拉框和角色管理列表中。

如果未来需要区分“可查看角色”和“可分配角色”，可以拆成两个接口：

- `/api/account/role/`：角色管理列表。
- `/api/account/role/assignable/`：账号表单角色下拉。

当前场景下可以先用同一个过滤逻辑。

## 用户创建与编辑接口强校验

在 `UserView._handle_user_create()` 中，创建用户前校验 `role_ids`：

```python
error = validate_assignable_role_ids(request.user, role_ids)
if error:
    return json_response(error=error)
```

建议放在 `User.objects.create()` 之前，避免先创建用户再失败。

在 `UserView._handle_user_edit()` 中，也必须在 `user.roles.set(role_ids)` 前校验。

同时建议增加额外限制：

```python
if not request.user.is_supper and user.is_supper:
    return json_response(error='无权编辑超级管理员账号')
```

普通管理员编辑用户时：

- 只能编辑本租户用户。
- 不能编辑超级管理员账号。
- 不能给用户绑定不可委派角色。
- 不能通过提交 `tenant_id` 修改用户租户。

这些规则应全部在后端校验。

## 角色创建接口修复

修改 `RoleView.post()`：

1. 普通管理员创建角色时，强制写入当前租户：

```python
if not request.user.is_supper:
    form['tenant_id'] = request.user.tenant_id
    form['is_system'] = False
    form['is_global_admin'] = False
```

2. 超级管理员可以显式创建平台级角色或租户角色。

3. 普通管理员提交的 `is_global_admin = true` 必须忽略或拒绝。

推荐拒绝，便于审计：

```python
if not request.user.is_supper and form.is_global_admin:
    return json_response(error='无权创建全局管理员角色')
```

## 角色编辑接口修复

角色基础信息编辑和权限编辑都要做归属校验。

普通管理员只能编辑：

- `tenant_id = request.user.tenant_id`
- `is_system = false`
- `is_global_admin = false`

示例：

```python
def get_manageable_role(operator, role_id):
    queryset = Role.objects.filter(pk=role_id)

    if not operator.is_supper:
        queryset = queryset.filter(
            tenant_id=operator.tenant_id,
            is_system=False,
            is_global_admin=False,
        )

    return queryset.first()
```

`RoleView.post()` 编辑已有角色、`RoleView.patch()` 修改权限、`RoleView.delete()` 删除角色时都应使用该方法取角色。

如果取不到，返回：

```text
角色不存在或无权操作
```

不要返回过细错误，避免泄露其他租户或系统角色信息。

## 权限子集约束

这是更稳修复的关键点。

即使普通管理员不能分配超级管理员创建的角色，如果他能自己创建一个拥有全部权限的角色，再分配给子账号，仍然会越权。

因此普通管理员创建或编辑角色权限时，必须保证新角色权限是当前操作者已有权限的子集。

### 页面权限 `page_perms`

当前用户权限由 `request.user.page_perms` 聚合得到，格式类似：

```text
system.account.view
system.account.add
system.account.edit
```

角色表单提交的 `page_perms` 是嵌套字典，需要先展平成同样的权限 key，再判断：

```python
def flatten_page_perms(page_perms):
    result = set()
    for module_key, pages in (page_perms or {}).items():
        for page_key, perms in (pages or {}).items():
            for perm_key in perms or []:
                result.add(f'{module_key}.{page_key}.{perm_key}')
    return result
```

校验：

```python
if not request.user.is_supper:
    requested_perms = flatten_page_perms(form.page_perms)
    allowed_perms = request.user.page_perms

    if not requested_perms.issubset(allowed_perms):
        return json_response(error='角色权限不能超过当前账号权限范围')
```

### 发布权限 `deploy_perms` 和分组权限 `group_perms`

如果这些权限也会影响业务数据范围，也需要做子集校验。

建议规则：

- 普通管理员创建或编辑 `group_perms` 时，只能选择自己已有的 `request.user.group_perms`。
- 普通管理员创建或编辑 `deploy_perms` 时，只能选择自己已有 deploy 权限范围内的应用和环境。

如果当前系统还没有统一的 deploy 权限聚合方法，至少先禁止普通管理员编辑超出自己角色集合并集之外的 `deploy_perms`。

## 删除角色接口修复

`RoleView.delete()` 除了检查是否已有用户使用，还应先校验角色是否可管理：

```python
role = get_manageable_role(request.user, form.id)
if not role:
    return json_response(error='角色不存在或无权操作')
```

普通管理员不能删除：

- 系统角色。
- 全局管理员角色。
- 其他租户角色。
- 平台级角色。

## 前端配合调整

前端不是安全边界，只做体验优化。

建议修改：

1. 账号创建/编辑表单继续调用 `/api/account/role/`，但后端已经只返回可分配角色。
2. 如果新增 `/api/account/role/assignable/`，则账号表单改为调用该接口。
3. 普通管理员界面不展示 `is_global_admin` 字段。
4. 普通管理员界面不展示系统角色、平台角色。
5. 普通管理员编辑角色权限时，只展示自己已有权限范围内的权限项。

注意：即使前端隐藏了选项，也不能省略后端校验，因为用户可以直接构造请求。

## 审计日志建议

以下行为建议记录审计日志：

- 创建用户并分配角色。
- 编辑用户角色。
- 创建角色。
- 修改角色权限。
- 删除角色。
- 因越权分配角色被拒绝。
- 因越权编辑角色权限被拒绝。

日志中建议记录：

- 操作者 ID、用户名、租户。
- 目标用户或目标角色 ID。
- 请求的角色 ID 列表。
- 被拒绝的角色 ID 列表。
- 操作结果。

这对后续排查越权尝试很有价值。

## 推荐实施顺序

1. 增加 `Role.tenant_id` 和 `Role.is_system` 字段。
2. 编写 migration，对历史角色按保守策略初始化。
3. 增加 `get_assignable_roles()`、`validate_assignable_role_ids()`、`get_manageable_role()`。
4. 修改 `RoleView.get()`，普通管理员只返回可分配角色。
5. 修改 `UserView._handle_user_create()` 和 `UserView._handle_user_edit()`，校验 `role_ids`。
6. 修改 `RoleView.post()`，限制普通管理员创建角色的归属和全局管理员字段。
7. 修改 `RoleView.patch()`，增加角色归属校验和权限子集校验。
8. 修改 `RoleView.delete()`，禁止普通管理员删除不可管理角色。
9. 前端根据后端返回结果调整展示，避免显示不可用选项。
10. 补充测试用例。

## 必测用例

### 普通管理员创建子账号

- 只能看到本租户普通角色。
- 提交本租户普通角色 ID，创建成功。
- 直接构造请求提交超级管理员角色 ID，返回失败。
- 直接构造请求提交其他租户角色 ID，返回失败。
- 直接构造请求提交 `is_global_admin = true` 的角色 ID，返回失败。

### 普通管理员编辑子账号

- 可以给本租户用户调整本租户普通角色。
- 不能编辑其他租户用户。
- 不能给本租户用户绑定平台角色。
- 不能给本租户用户绑定全局管理员角色。
- 不能修改用户 `tenant_id`。

### 普通管理员管理角色

- 创建角色时自动归属当前租户。
- 不能创建全局管理员角色。
- 不能编辑系统角色。
- 不能编辑其他租户角色。
- 不能删除系统角色。
- 不能把角色权限设置为超过自己已有权限。

### 超级管理员

- 可以看到全部角色。
- 可以创建平台级角色。
- 可以创建租户角色。
- 可以分配全局管理员角色。
- 可以编辑和删除允许删除的角色。

## 最小安全边界

如果需要先快速止血，至少必须完成以下两点：

1. `RoleView.get()` 对普通管理员过滤角色，不返回超级管理员创建的角色、系统角色、其他租户角色、全局管理员角色。
2. `UserView._handle_user_create()` 和 `_handle_user_edit()` 对 `role_ids` 做后端强校验。

但这只是止血。完整稳健方案仍应补上角色归属字段、角色管理权限子集校验和审计日志。

## 结论

本问题本质是“用户创建权限”和“角色委派权限”混在了一起。修复时不能只依赖前端隐藏角色下拉，而要在后端明确建立角色归属、可管理范围和可委派范围。

推荐采用：

- 角色增加 `tenant_id` 和 `is_system`。
- 后端统一计算可委派角色。
- 用户创建和编辑时强校验 `role_ids`。
- 普通管理员创建和编辑角色时做权限子集校验。
- 所有越权尝试记录审计日志。

这样才能避免普通管理员通过创建子账号、编辑子账号、创建角色、修改角色权限等路径间接提权。
