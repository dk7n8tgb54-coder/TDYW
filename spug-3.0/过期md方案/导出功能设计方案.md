# 导出功能设计方案

## 1. 背景与目标

本次需要为以下模块增加导出能力：

- 日检查单
- 运行日志
- 设备管理
- 干扰管理
- 系统升级管理
- 故障管理

这些模块的数据结构、页面形态和业务用途不同，不适合强行使用同一份导出模板。设计目标是：

- 统一导出入口、下载逻辑、权限校验和异常处理。
- 每个模块保留自己的业务字段和导出格式。
- 当前阶段按业务类型分别导出 Excel 或 PDF。
- 后期可以低成本为 Excel 类模块补充 PDF 导出。
- 避免前端只导出当前页数据，确保导出结果与当前筛选条件一致。

## 2. 导出类型划分

| 类型 | 模块 | 当前导出格式 | 说明 |
|---|---|---|---|
| 普通列表型 | 故障管理、干扰管理、系统升级管理、设备管理列表 | Excel | 以结构化列表数据为主，每个模块定义自己的导出列 |
| 报表/打印型 | 日检查单 | PDF | 更接近打印报表，需要保持专门版式 |
| 详情履历型 | 设备履历、运行日志 | PDF | 更适合按详情、时间线、处理过程生成可阅读文档 |

设备管理建议同时包含两种导出：

- 设备列表：Excel
- 单台设备履历详情：PDF，必须包含设备基础信息和全生命周期事件时间线

运行日志当前先保留 PDF，后续如有统计或明细分析需求，可再增加 Excel 明细导出。

设备管理需要特别区分两个导出入口：

- 设备列表页导出：面向台账统计，导出多台设备的基础档案字段，适合 Excel。
- 查看履历弹窗/详情页导出：面向单台设备归档、审阅和打印，导出设备完整履历，必须包含基础信息和事件时间线，适合 PDF。

不能用设备列表 Excel 替代设备履历导出，否则会丢失设备全生命周期事件。

## 3. 总体设计

导出功能分为三层：

```text
前端导出按钮
  -> 调用模块导出接口
  -> 下载后端返回的文件

后端模块导出服务
  -> 校验权限
  -> 复用当前列表筛选条件查询数据
  -> 整理模块自己的导出字段

公共文件生成工具
  -> Excel 渲染
  -> PDF 渲染
  -> 文件名、响应头、中文编码、异常处理
```

统一的是导出机制，不统一业务字段。每个模块仍然维护自己的字段配置和版式。

## 4. 前端设计

### 4.1 公共下载工具

建议新增：

```text
spug_web/src/utils/exportFile.js
```

职责：

- 使用现有 `http` 封装发送请求。
- 设置 `responseType: 'arraybuffer'`。
- 从 `Content-Disposition` 中解析文件名。
- 根据 `Content-Type` 创建 Blob。
- 触发浏览器下载。
- 统一处理 loading、空数据、后端错误。

示例调用方式：

```js
exportFile({
  url: '/api/fault/faultrecord/export/',
  method: 'get',
  params: store.exportParams,
  defaultFilename: '故障处置记录.xlsx',
});
```

### 4.2 公共导出按钮组件

建议新增：

```text
spug_web/src/components/ExportButton.js
```

职责：

- 统一按钮样式。
- 统一权限控制。
- 统一 loading 状态。
- 支持 Excel/PDF 不同文案。

示例：

```jsx
<ExportButton
  auth="fault.faultrecord.view"
  url="/api/fault/faultrecord/export/"
  params={store.getExportParams()}
  filename="故障处置记录.xlsx"
>
  导出
</ExportButton>
```

后期如果某个模块同时支持 Excel 和 PDF，可以扩展为下拉按钮：

```text
导出
  - 导出 Excel
  - 导出 PDF
```

### 4.3 前端筛选参数规则

每个模块需要在 store 中提供统一方法：

```js
getExportParams = () => ({
  system_name: this.f_system_name,
  start_date: this.f_start_date,
  end_date: this.f_end_date,
});
```

导出接口使用当前筛选条件，不使用当前分页数据。

分页参数默认不传，表示导出当前筛选条件下的全部数据。若后续需要支持"只导出当前页"，再单独增加 `scope=current_page`。

## 5. 后端设计

### 5.1 公共 Excel 工具

建议新增：

```text
spug_api/apps/libs/export_utils.py
```

或放在现有公共 libs 目录下。

核心方法：

```python
def build_excel_response(filename, sheet_name, columns, rows):
    """
    filename: 导出文件名
    sheet_name: 工作表名称
    columns: [(field, title), ...] 或 [{'key': '', 'title': ''}, ...]
    rows: dict 列表、model 列表或已整理好的二维数据
    """
```

公共能力：

- 创建工作簿。
- 写入表头。
- 写入数据行。
- 设置列宽。
- 设置表头样式。
- 处理空值。
- 处理日期时间。
- 返回 `HttpResponse`。
- 设置正确的 `Content-Disposition`。

项目中已有 `openpyxl`，可以直接使用，不需要增加后端依赖。

### 5.2 公共 PDF 工具

已有日检查单、运行日志、设备履历相关 PDF 代码。当前阶段不建议强行合并这些复杂 PDF 模板。

建议先抽一个轻量表格型 PDF 工具，为后期 Excel 类模块补 PDF 做准备：

```python
def build_table_pdf_response(filename, title, columns, rows, subtitle=None):
    """
    用于普通列表数据的 PDF 导出。
    复杂报表仍然保留模块专用 PDF 模板。
    """
```

当前阶段：

- 日检查单继续使用专用 PDF。
- 运行日志继续使用专用 PDF。
- 设备履历继续使用专用 PDF。
- 普通列表先只做 Excel。

### 5.3 模块导出服务

每个模块单独维护自己的导出配置，不共享业务字段。

示例结构：

```text
spug_api/apps/fault/exporters.py
spug_api/apps/interference/exporters.py
spug_api/apps/upgrade/exporters.py
spug_api/apps/device/exporters.py
```

每个 exporter 推荐包含：

```python
EXCEL_COLUMNS = [...]

def get_export_queryset(request):
    """按当前筛选条件查询数据"""

def export_excel(request):
    """整理数据并调用公共 Excel 工具"""
```

后期增加 PDF 时，只需要补：

```python
PDF_COLUMNS = [...]

def export_pdf(request):
    """复用 get_export_queryset，调用公共 PDF 工具"""
```

## 6. 接口设计

### 6.1 日检查单

当前格式：PDF

建议继续使用现有接口：

```text
POST /api/checksheet/export/pdf/
```

说明：

- 保持专用 PDF 模板。
- 导出内容应与前端日检查单展示一致。
- 文件名建议包含年月。

### 6.2 运行日志

当前格式：PDF

建议使用现有接口：

```text
POST /api/runlog/export/pdf/
```

说明：

- 按运行日志当前筛选条件导出。
- 内容包含事件基本信息、处理状态、动态记录、时间线等。

后续可选扩展：

```text
GET /api/runlog/export/excel/
```

用于导出明细列表和动态记录明细。

### 6.3 设备管理

设备管理分为两个导出场景。

#### 6.3.1 设备列表 Excel

设备列表导出用于导出台账清单，只包含设备列表中的基础档案字段，不包含单台设备的履历事件时间线。

```text
GET /api/device/device-resume/export/
```

导出字段建议：

- 设备编号
- 设备名称
- 设备型号
- 设备呼号
- 使用单位
- 设备负责人
- 当前设备状态
- 设备用途
- 创建时间

#### 6.3.2 单台设备履历 PDF

设备履历详情导出用于导出某一台设备的完整生命周期履历，入口应放在"查看履历"或"设备详情"页面中。

```text
POST /api/device/device-resume/export/pdf/
```

当前已有类似能力，建议保留并明确导出内容。

权限点使用 `device.device_resume.history_view`（与查看履历一致，比列表 `view` 更严格），不要混用 `device.device_resume.view`。

导出内容必须包含：

- 标题：设备履历。
- 导出时间：生成 PDF 的当前时间。
- 导出人：当前请求用户姓名（后端从 `request.user` 取，不信任前端传入）。
- 设备基础信息：设备编号、设备名称、设备型号、设备呼号、使用单位、负责人、当前状态、用途等。
- 生命周期事件时间线：按事件发生时间倒序排列，包含重大故障维修、设备更新、设备检修等事件。
- 每条事件的关键字段：事件类型、事件标题、发生时间、故障件、故障现象及原因、维修措施、维修时间、记录人、创建时间。
- 如果该设备没有事件记录，PDF 中应显示"暂无生命周期事件记录"，而不是留白。

不能用设备列表 Excel 替代设备履历 PDF，否则会丢失设备全生命周期事件。

推荐格式为 PDF，原因：

- 设备履历是归档和审阅类文档，不只是数据分析表。
- 时间线、事件详情、长文本说明更适合 PDF 阅读和打印。
- PDF 版式稳定，方便作为设备全生命周期档案留存。

Word 不作为第一阶段推荐格式。只有当业务明确要求人工二次编辑、盖章流转或纳入正式文档模板时，再考虑增加 Word 导出。

Excel 可作为后续补充格式，用于批量分析事件明细，但不建议替代 PDF 履历。

#### 6.3.3 实现要求

- 后端导出接口按设备 ID 获取设备基础信息和关联事件列表，前端只传设备信息和事件数据，导出人由后端从 `request.user` 注入。
- 导出接口必须做租户隔离（`apply_tenant_filter`）和权限校验（`@auth`）。
- 设备履历 PDF 应复用当前查看履历中的设备基础信息和事件数据，保证 PDF 内容与页面展示一致。
- 前端按钮文案：
  - 列表页：导出设备列表
  - 履历详情页：导出履历 PDF
- 文件名规范：
  - 设备列表：`设备台账_导出时间.xlsx`（导出时间格式 `YYYYMMDD_HHmmss`）
  - 设备履历：`设备履历_设备编号_设备名称_导出时间.pdf`

## 7. 权限设计

当前阶段建议复用各模块 `view` 权限：

| 模块 | 导出权限 |
|---|---|
| 日检查单 | `checksheet.checksheet.view` 或现有导出权限 |
| 运行日志 | `runlog.runlog.view` |
| 设备管理（列表 Excel） | `device.device_resume.view` |
| 设备管理（履历 PDF） | `device.device_resume.history_view` |
| 干扰管理 | `interference.interference.view` |
| 系统升级管理 | `upgrade.upgrade.view` |
| 故障管理 | `fault.faultrecord.view` |

如果后续对导出数据有审计要求，可以新增独立权限：

```text
xxx.xxx.export
```

前端按钮和后端接口都必须校验权限。后端权限校验不能只依赖前端按钮隐藏。

## 8. 数据范围与性能

导出必须基于当前筛选条件，而不是当前页。

建议加导出上限：

```text
默认最多导出 10000 条
```

超过上限时后端返回错误：

```text
导出数据超过 10000 条，请缩小筛选范围后重试
```

后续如果出现大批量导出需求，再设计异步导出任务：

```text
提交导出任务 -> 后台生成文件 -> 用户下载
```

当前阶段不建议一开始做异步导出，复杂度较高。

## 9. 文件命名规范

建议格式：

```text
模块名称_筛选范围_导出时间.扩展名
```

示例：

```text
故障处置记录_20260101-20260131_20260626_153000.xlsx
干扰信息统计_all_20260626_153000.xlsx
运行日志报告_20260626_153000.pdf
2026年06月_日检查单.pdf
设备台账_20260626_153000.xlsx
设备履历_DW202601001_甚高频收发信机_20260626_153000.pdf
```

中文文件名需要后端正确设置响应头，兼容浏览器下载。

## 10. 错误处理

统一处理以下情况：

- 无数据：提示"当前筛选条件下没有可导出的数据"。
- 超过导出上限：提示用户缩小筛选范围。
- 权限不足：返回 403，并提示无权限。
- 文件生成失败：记录后端日志，前端提示"导出失败，请重试"。
- PDF 字体缺失：后端日志记录，优先使用项目已有中文字体方案。

## 11. 实施步骤

### 第一阶段：公共能力

1. 新增前端 `exportFile` 工具。
2. 新增前端 `ExportButton` 组件。
3. 新增后端 Excel 公共工具。
4. 统一二进制响应错误处理。

### 第二阶段：普通列表 Excel

1. 故障管理增加后端 Excel 导出接口。
2. 干扰管理增加后端 Excel 导出接口。
3. 系统升级管理增加后端 Excel 导出接口。
4. 设备管理增加设备列表 Excel 导出接口。
5. 替换现有前端"当前页 xlsx 导出"逻辑。

### 第三阶段：PDF 类模块整理

1. 检查日检查单导出按钮是否正确显示。
2. 检查运行日志导出按钮是否正确显示。
3. 保留设备履历详情 PDF 导出。
4. 统一按钮文案、loading 文案和错误提示。

### 第四阶段：后续扩展预留

1. 为普通列表模块预留 `export/pdf/` 接口命名。
2. 抽轻量表格 PDF 工具。
3. 按业务优先级逐步增加 PDF 格式。

## 12. 验收标准

- 六个模块页面都能看到导出入口。
- 导出按钮权限与模块查看权限一致。
- 普通列表模块导出的是当前筛选条件下的全部数据，不只是当前页。
- 日检查单、运行日志、设备履历 PDF 能正常下载并打开。
- Excel 文件中文表头、中文内容、日期时间正常显示。
- 空数据、权限不足、超量导出均有明确提示。
- 导出文件名清晰，并包含模块名称和导出时间。
- 后续增加 PDF 格式时，不需要重写查询逻辑，只需增加 PDF 渲染方法。
