# 规章管理模块设计方案

> 日期：2026-07-16
> 关联改动：现有"行业规章"系统目录改名为"党务档案"；新建独立的"规章管理"业务模块。
> 决策原则：参考成熟产品（OA/网盘）、行业惯例、增量改进 > 大爆炸重构、配置化 > 散落硬编码、向后兼容。

## 0. 写在前面：两个问题先回答

### Q1：现有"行业规章"会被这次改动影响吗？

**会被影响两处**：

| 项 | 现状 | 改后 |
|---|---|---|
| 前端菜单显示 | `资料库 → 行业规章` | `资料库 → 党务档案`（仅改显示名） |
| 后端系统目录名 | `DocumentSystemFolder(name='行业规章')` | 同步改名为 `党务档案`（`code=industry_rules` **保留不变**，避免范围校验逻辑大改） |
| 文件存储方式 | 资料库系统目录 | 不变（文件仍在 `industry_rules` 范围内） |

**不影响**：权限码、文件物理路径、已上传文件、API 路径（`/api/document/industry-rules/`）。

### Q2：上传规章的权限，是不是应该只有超级管理员？

**答：是的，应该限超管。** 推荐实现方式如下：

| 维度 | 设计 |
|---|---|
| **行业惯例** | 法规/制度类文档由具备资质的专人维护，普通用户只读 + 下载 |
| **权限码** | 保留 `regulation.upload` 权限码（用于前端按钮/菜单显示），**默认只有超管**能配置上（因为 `is_supper` 的 `has_perms` 直接 `return True`） |
| **后端强校验** | `POST /api/regulation/`（新建）和 `POST /api/regulation/<id>/attach/`（关联文件）两个写接口，在 `@auth('regulation.upload')` 装饰器之外**额外判 `is_supper`**，不通过直接返回 `403 仅超级管理员可上传规章` |
| **应急开关** | 未来如需"法规专员"角色可上传，只需在 `views.py` 把 `is_supper` 强校验改为 `is_supper OR has_role('regulation_editor')` 即可，**接口签名/权限码不动** |
| **普通用户** | 仅 `view` + `download`，不能新建/编辑/删除/上传 |

> **为什么不硬编码 `is_supper` 一刀切？** 因为权限码体系是项目核心设计（`User.has_perms` 在 `is_supper=True` 时直接放行所有），用权限码 + 后端强校验双保险，既满足"默认只有超管"，又保留未来"放权给特定角色"的扩展性，且完全符合项目现有惯例（执照/合同/检查单都是这种模式）。

## 2. 设计原则

1. **复用现状 B 已有代码**：避免重复造轮子，省 ~600 行
2. **现状 A 不动架构**：只改显示名（"行业规章"→"党务档案"），文件存储/范围保护/根目录保护全部保留
3. **分类树独立建表**：左侧"规章管理分类"是**业务分类**（国际民航/民航行业/地方文件），不等同于文件夹树
4. **物理文件继续走资料库**：通过 `IndustryRuleAttachment` 引用 `DocumentFilePublic`，受 `system_folder=industry_rules` 范围保护
5. **风格沿用资料库 + 合同协议 + 执照**（`TableCard` + `SearchForm` + `AuthButton` + `AttachmentCountBadge`）
6. **超管限权：保留权限码 + 后端 `is_supper` 强校验**（详见 Q2 回答）

```python
class RegulationCategory(models.Model):
    """规章管理分类树（左侧多级树）

    与 IndustryRule.category_id 多对一：一条规章可挂在一个叶子节点。

    name        = CharField(max_length=100)                  # "国际民航" / "Doc文件" / "民航行业" / "地方文件"

    sort_order  = IntegerField(default=0)                    # 同级排序
    code        = CharField(max_length=50, blank=True)       # 可选编码，便于数据导入
    is_leaf     = BooleanField(default=True)                 # 是否可挂规章（叶子节点）
    created_at  = DateTimeField(auto_now_add=True)
    created_by  = ForeignKey(User, null=True, on_delete=SET_NULL)

    class Meta:
        db_table = 'tdyw_regulation_category'
        verbose_name = '规章管理分类'
        verbose_name_plural = '规章管理分类'
        ordering = ['sort_order', 'id']
        indexes = [
            Index(fields=['parent', 'sort_order'], name='reg_cat_parent_sort_idx'),
        ]
```

```python
from libs import auth, json_response

def _require_supper(request):
    """写操作超管强校验（与权限码配合的双保险）"""
    if not getattr(request.user, 'is_supper', False):
        return json_response(error='仅超级管理员可操作规章'), True
    return None, False

class RegulationView(View):

    @auth('regulation.view')
    def get(self, request):
        # 列表（普通用户可访问）
        ...

    def post(self, request):
        # 写操作：先权限码，再超管
        from apps.account.models import User
        from functools import wraps

        @auth('regulation.add')
        def _do_post(request):
            err, blocked = _require_supper(request)
            if blocked:
                return err
            # 实际新建逻辑
            ...

        return _do_post(request)
```

> 实际实现建议：把 `_require_supper` 写成装饰器，与 `@auth` 叠加（`@auth('regulation.add')` + `@require_supper('add')`），避免每个写方法重复样板代码。

## 9. 风险与备选

| 风险 | 缓解 |
|---|---|
| 新建 `apps/regulation` vs 改造 `apps/industry_rule` 的命名混乱 | 推荐选新建；如果选改造，需在文档里说明"industry_rule 实际是独立业务台账而非系统目录" |
| 行业规章 → 党务档案改名，已有用户的菜单预期被打破 | 改名前发站内通知；菜单项可加过渡 tooltip "原行业规章" |
| 分类树与 IndustryRule.category 字段语义重复 | 文档里明确：category_id 决定**左侧归属**，category 字段决定**业务类型筛选** |
| 上传限超管的强校验可能被误关 | `_require_supper` 写死，不接受配置；想"放权"只能改代码（应急） |
| 物理文件已存"行业规章"目录下，改名后文件路径不变（folder_id 不变） | 范围校验按 `system_folder=industry_rules`，与目录名解耦，**零数据迁移** |
| 老 industry_rule app 的 0001_initial.py 已存在但未应用 | 新建 `apps/regulation` 不影响；如果改用 industry_rule，要 `migrate industry_rule --fake-initial` |
