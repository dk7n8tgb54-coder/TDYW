# 公告发布功能设计方案

> 编写日期：2026-07-10  
> 模块名称：公告发布  
> 建议英文模块名：announcement  
> 建议落点：后端复用并增强 `apps.home`，前端接入首页工作台和系统管理菜单  
> 参照能力：现有 `apps.home.Notice`、账号租户体系、公共附件服务、全局管理员角色

## 一、建设目标

在现有首页通知能力基础上，建设面向全平台的公告发布与展示功能，满足全局管理员发布公告、指定发布范围、控制生效时间、上传附件、撤回已发布公告，以及普通用户在首页查看、筛选、阅读和接收未读提醒的需求。

本功能首期目标如下：

1. 全局管理员可维护公告标题、内容、发布范围、生效时间和附件。
2. 公告状态对用户展示为“未发布”“已发布”“已过期”三类。
3. 首页显著位置展示当前用户可见且已发布的公告，按发布时间倒序排列。
4. 发布时间不超过 3 天的公告展示“新公告”标识。
5. 用户可按发布部门、时间范围筛选查询公告，并查看详情。
6. 用户查看详情后可标记“已读”，未读公告在首页或全局消息入口提醒。
7. 支持编辑、删除、撤回已发布公告，并保留必要的操作追溯信息。

## 二、项目现状分析

### 2.1 现有后端能力

项目当前已有 `spug_api/apps/home/models.py` 中的 `Notice` 模型和 `spug_api/apps/home/notice.py` 中的 `NoticeView`，字段包括：

| 字段 | 当前含义 | 局限 |
|---|---|---|
| `title` | 通知标题 | 可复用 |
| `content` | 通知内容 | 可复用，但缺少富文本/附件关联 |
| `is_stress` | 是否重点 | 与公告置顶或重要标识可部分复用 |
| `read_ids` | 已读用户 ID JSON | 小规模可用，大量用户下不利于查询和统计 |
| `sort_id` | 排序 | 与公告发布时间倒序需求不完全一致 |
| `created_at` | 创建时间 | 缺少发布时间、生效时间、过期时间 |

现有接口只支持简单列表、新增编辑、排序、已读、删除，缺少发布范围、状态流转、附件、筛选、租户/部门可见性和全局管理员控制。

### 2.2 现有账号和组织能力

项目账号模型 `apps.account.models.User` 已具备：

| 能力 | 项目现状 |
|---|---|
| 超级管理员 | `User.is_supper` |
| 全局管理员 | `User.is_global_admin`，由角色 `Role.is_global_admin` 派生 |
| 租户隔离 | `User.tenant_id`、`Tenant`、`TenantModelMixin`、`apply_tenant_filter` |
| 角色权限 | `User.has_perms(codes)` 和 `AdminView.PERM_MAP` |

当前项目没有独立的部门主数据表，也没有在 `User` 上维护 `department_id` 字段。因此首期建议将现有 `Tenant` 作为“部门/组织单元”的数据来源：

```text
业务需求中的“指定部门”
  -> 首期映射为 account.Tenant
  -> 公告可见性按 user.tenant_id 判断
  -> 页面文案仍可显示为“部门”
```

如果后续新增独立部门体系，只需要将公告范围表中的 `target_tenant_id` 扩展或迁移为 `target_department_id`，公告主流程不需要重写。

### 2.3 现有附件能力

项目已有公共附件能力：

| 文件 | 能力 |
|---|---|
| `spug_api/apps/evidence/models.py` | `EvidenceAttachment` 通用附件表 |
| `spug_api/apps/evidence/attachment_service.py` | 上传、列表、下载、预览、软删除 |
| `附件功能公共化设计方案.md` | 统一附件存储和 kkFileView 预览设计 |

公告附件不建议单独建一套文件上传体系，应复用 `AttachmentService`，使用：

```text
module = announcement
object_type = announcement
object_id = 公告 ID
```

物理路径落到：

```text
/data/spug/spug_api/media/announcement/{tenant_id}/{yyyyMM}/announcement_{id}/...
```

### 2.4 现有前端能力

前端为 React + Ant Design，首页位于 `spug_web/src/pages/home/index.js`。当前首页以运行日志、资料库、故障、升级、干扰概览为主，旧的 `notice` 样式仍在 `index.module.less` 中，但通知组件入口已不明显。

本次建议新增独立公告组件，并将其放在首页第一屏靠上区域，保证“系统首页显著位置展示”的需求。

## 三、总体方案

### 3.1 模块边界

建议将公告能力放在 `home` 模块下演进，原因是：

1. 现有 URL 已有 `/api/home/notice/` 语义和入口。
2. 首页展示是公告的主要消费场景。
3. 可以保留旧 `Notice` 数据迁移路径，减少业务断层。

推荐后端结构：

```text
spug_api/apps/home/
  models.py                 # 新增 Announcement、AnnouncementRead、AnnouncementScope
  announcement.py           # 新公告接口
  notice.py                 # 保留旧接口，后续可兼容转发
  urls.py                   # 注册 announcement 路由
```

推荐前端结构：

```text
spug_web/src/pages/home/
  AnnouncementPanel.js      # 首页公告展示组件
  AnnouncementDetail.js     # 公告详情弹窗或抽屉

spug_web/src/pages/system/announcement/
  index.js                  # 公告管理列表
  Form.js                   # 公告新增/编辑表单
  Detail.js                 # 管理端详情
```

### 3.2 角色分工

| 角色 | 权限 |
|---|---|
| 全局管理员 | 新增、编辑、发布、撤回、删除、上传附件、选择发布范围 |
| 超级管理员 | 拥有全局管理员全部能力，并可跨全部租户/部门管理 |
| 普通用户 | 查看可见公告、筛选公告、查看详情、标记已读 |
| 普通租户管理员 | 首期不开放公告发布；如后续需要，可增加“部门公告管理员”权限 |

### 3.3 状态定义

对用户展示只保留三种状态：

| 展示状态 | 内部状态值 | 判定规则 |
|---|---|---|
| 未发布 | `unpublished` | 未发布，或已发布后被撤回 |
| 已发布 | `published` | 已发布、未撤回，且当前时间在生效区间内 |
| 已过期 | `expired` | 已发布、未撤回，且当前时间晚于失效时间 |

建议数据库存储 `status`，同时接口返回 `computed_status`。列表展示优先使用 `computed_status`，避免定时任务延迟造成状态不准。

```python
STATUS_UNPUBLISHED = 'unpublished'
STATUS_PUBLISHED = 'published'
STATUS_EXPIRED = 'expired'
```

状态流转：

```text
未发布 -> 发布 -> 已发布 -> 到期 -> 已过期
已发布 -> 撤回 -> 未发布
已过期 -> 编辑生效时间后重新发布 -> 已发布
未发布/已过期 -> 删除
已发布 -> 删除：建议先撤回再删除，接口可内部自动撤回后软删除
```

## 四、数据模型设计

### 4.1 公告主表

建议新增模型 `Announcement`，表名 `tdyw_announcements`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 主键 |
| `tenant_id` | varchar(50) | 是 | 创建人所属租户，沿用项目租户隔离字段 |
| `title` | varchar(200) | 是 | 公告标题 |
| `content` | text | 是 | 公告内容，首期可用纯文本或富文本 HTML |
| `scope_type` | varchar(20) | 是 | 发布范围：`all` 全平台，`tenant` 指定部门/租户 |
| `publish_department_id` | varchar(50) | 否 | 发布部门 ID，首期对应 `Tenant.id` |
| `publish_department_name` | varchar(100) | 否 | 发布部门名称快照，用于列表筛选和历史展示 |
| `effective_start_at` | datetime/char | 是 | 生效开始时间 |
| `effective_end_at` | datetime/char | 否 | 生效结束时间，空表示长期有效 |
| `status` | varchar(20) | 是 | 存储状态：未发布/已发布/已过期 |
| `published_at` | datetime/char | 否 | 实际发布时间 |
| `published_by_id` | int | 否 | 发布人 ID |
| `published_by_name` | varchar(100) | 否 | 发布人姓名快照 |
| `withdrawn_at` | datetime/char | 否 | 撤回时间 |
| `withdrawn_by_id` | int | 否 | 撤回人 ID |
| `withdrawn_by_name` | varchar(100) | 否 | 撤回人姓名快照 |
| `is_important` | boolean | 是 | 是否重要，替代旧 `is_stress` 语义 |
| `is_deleted` | boolean | 是 | 软删除标识 |
| `created_at` | datetime/char | 是 | 创建时间 |
| `created_by` | FK(User) | 是 | 创建人 |
| `updated_at` | datetime/char | 否 | 更新时间 |
| `updated_by` | FK(User) | 否 | 更新人 |
| `deleted_at` | datetime/char | 否 | 删除时间 |
| `deleted_by` | FK(User) | 否 | 删除人 |

说明：

1. `scope_type=all` 表示所有租户/部门用户可见。
2. `scope_type=tenant` 时，需要在范围表中写入一个或多个目标租户。
3. `publish_department_name` 使用快照，避免部门改名后历史公告展示漂移。
4. `effective_end_at` 为空时不自动过期。
5. 撤回已发布公告后，`status` 回到 `unpublished`，同时保留 `withdrawn_at` 和 `withdrawn_by_*`。

### 4.2 发布范围表

建议新增模型 `AnnouncementScope`，表名 `tdyw_announcement_scopes`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 主键 |
| `announcement_id` | FK | 是 | 公告 ID |
| `tenant_id` | varchar(50) | 是 | 目标部门/租户 ID |
| `tenant_name` | varchar(100) | 是 | 目标部门/租户名称快照 |
| `created_at` | datetime/char | 是 | 创建时间 |

唯一约束：

```python
UniqueConstraint(
    fields=['announcement_id', 'tenant_id'],
    name='uniq_announcement_scope_tenant',
)
```

当 `scope_type=all` 时，可不写范围表；当 `scope_type=tenant` 时，范围表至少一条。

### 4.3 已读表

建议新增模型 `AnnouncementRead`，表名 `tdyw_announcement_reads`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 主键 |
| `tenant_id` | varchar(50) | 是 | 用户所属租户 |
| `announcement_id` | FK | 是 | 公告 ID |
| `user_id` | int | 是 | 用户 ID |
| `username` | varchar(100) | 是 | 登录账号快照 |
| `nickname` | varchar(100) | 是 | 姓名快照 |
| `read_at` | datetime/char | 是 | 阅读时间 |

唯一约束：

```python
UniqueConstraint(
    fields=['announcement_id', 'user_id'],
    name='uniq_announcement_read_user',
)
```

不建议继续使用旧 `read_ids` JSON 字段，原因是：

1. 难以高效查询未读数量。
2. 大量用户时单字段持续膨胀。
3. 并发标记已读时容易出现覆盖。

### 4.4 附件关联

公告附件直接复用 `EvidenceAttachment`：

| 字段 | 值 |
|---|---|
| `module` | `announcement` |
| `object_type` | `announcement` |
| `object_id` | 公告 ID |
| `tenant_id` | 上传人租户 ID |

公告删除时，调用 `AttachmentService.soft_delete_by_object(user, 'announcement', 'announcement', announcement.id)` 联动软删除附件记录。

### 4.5 推荐索引

| 索引 | 字段 | 用途 |
|---|---|---|
| `ann_status_time_idx` | `status, published_at, id` | 首页已发布公告倒序 |
| `ann_scope_idx` | `scope_type, status` | 范围过滤 |
| `ann_pub_dept_idx` | `publish_department_id, published_at` | 按发布部门筛选 |
| `ann_effective_idx` | `effective_start_at, effective_end_at` | 生效和过期判断 |
| `ann_deleted_idx` | `is_deleted, status` | 管理端列表 |
| `ann_scope_tenant_idx` | `announcement_id, tenant_id` | 指定部门可见性 |
| `ann_read_user_idx` | `user_id, announcement_id` | 已读/未读判断 |
| `ann_read_notice_idx` | `announcement_id, user_id` | 公告阅读统计 |

## 六、核心业务规则

### 6.1 可见性规则

用户可见公告条件：

```text
公告未删除
AND status = published
AND effective_start_at <= now
AND (effective_end_at IS NULL OR effective_end_at >= now)
AND (
  scope_type = all
  OR EXISTS AnnouncementScope.tenant_id = request.user.tenant_id
)
```

超级管理员和全局管理员在管理端可查看全部公告；在普通首页视图中，建议仍按用户视角展示可见公告，避免管理数据和用户数据混在一起。

### 6.2 发布时间倒序

首页和用户端列表默认排序：

```text
ORDER BY is_important DESC, published_at DESC, id DESC
```

如果不希望重要公告破坏“按发布时间倒序”的严格要求，则首页只在视觉上突出重要公告，排序统一使用：

```text
ORDER BY published_at DESC, id DESC
```

首期建议采用后者，严格满足需求。

### 6.3 新公告标识

接口直接返回 `is_new`：

```python
is_new = published_at is not None and published_at >= timezone.now() - timedelta(days=3)
```

页面显示“新公告”标签，不需要前端自行计算，避免客户端时区差异。

### 6.4 已读规则

推荐策略：

1. 用户打开公告详情时自动写入 `AnnouncementRead`。
2. 用户端也提供“标记已读”按钮，便于列表批量操作扩展。
3. 重复标记已读使用 `get_or_create`，避免并发重复。
4. 公告撤回后不再纳入未读统计。
5. 公告重新发布时是否重置已读，需要按业务选择：
   - 只修改错别字：不重置已读。
   - 内容发生实质修改：管理员勾选“重新提醒”，后端删除该公告已读记录或增加 `version` 字段。

首期建议增加 `version` 字段更稳妥：

```text
Announcement.version 默认 1
内容实质修改并重新提醒时 version + 1
AnnouncementRead 记录 announcement_id + user_id + version
```

若首期控制范围希望简化，也可以不做版本，编辑后不重置已读。

### 6.5 未读提醒规则

未读数量计算：

```text
当前用户可见公告
AND NOT EXISTS AnnouncementRead(announcement_id, user_id)
```

提醒展示建议：

1. 首页公告区域右上角显示未读数量。
2. 布局顶部消息入口如已有全局提醒，可展示红点或徽标。
3. 登录后拉取 `/api/home/announcement/unread-count/`。
4. 首页加载时拉取 `/api/home/announcement/reminders/` 返回最近未读公告。

### 6.6 编辑规则

| 公告状态 | 可编辑字段 | 说明 |
|---|---|---|
| 未发布 | 全部字段 | 允许编辑标题、内容、范围、时间、附件 |
| 已发布 | 标题、内容、附件、失效时间 | 修改范围和生效开始时间需谨慎，建议弹窗确认 |
| 已过期 | 标题、内容、失效时间 | 延长失效时间后可重新发布 |

已发布公告编辑后：

1. 不改变 `published_at`，除非执行重新发布。
2. 记录 `updated_at` 和 `updated_by`。
3. 可由管理员选择是否“重新提醒未读”。

### 6.7 删除规则

公告删除建议使用软删除：

```text
is_deleted = true
deleted_at = now
deleted_by = request.user
```

已发布公告删除前，后端可自动视为撤回，保证用户端不再可见。

### 6.8 撤回规则

撤回仅对已发布公告生效：

```text
status = unpublished
withdrawn_at = now
withdrawn_by = request.user
```

撤回后：

1. 用户端列表和首页不再展示。
2. 未读提醒不再统计。
3. 管理端可继续编辑后重新发布。
4. 已读记录保留，用于追溯；如重新发布并需要重新提醒，可提升版本。

### 6.9 过期规则

过期状态建议双轨：

1. 接口实时计算 `computed_status`，确保页面准确。
2. 定时任务每日或每小时将到期公告 `status` 更新为 `expired`，便于管理端筛选和统计。

伪代码：

```python
Announcement.objects.filter(
    is_deleted=False,
    status='published',
    effective_end_at__lt=now,
).update(status='expired')
```

## 七、权限与安全设计

### 7.1 管理权限

管理端接口不建议只继承当前 `AdminView` 的 `is_supper` 放行逻辑，因为需求明确为“全局管理员可发布公告”。建议新增判断：

```python
def ensure_announcement_admin(user):
    return getattr(user, 'is_supper', False) or getattr(user, 'is_global_admin', False)
```

或者在角色权限体系中增加页面权限：

```text
home.announcement.view
home.announcement.add
home.announcement.edit
home.announcement.delete
home.announcement.publish
home.announcement.withdraw
```

首期推荐：

1. 管理端先校验 `is_global_admin` 或 `is_supper`。
2. 同时预留 `PERM_MAP`，便于后续细粒度授权。

### 7.2 普通用户访问权限

普通用户访问详情和附件时，必须复用公告可见性规则，避免通过 ID 猜测访问其他部门公告。

### 7.3 输入校验

| 字段 | 校验 |
|---|---|
| `title` | 必填，长度 1-200，去除首尾空格 |
| `content` | 必填，限制最大长度，富文本需做 XSS 清洗 |
| `scope_type` | 仅允许 `all`、`tenant` |
| `target_tenant_ids` | `scope_type=tenant` 时必填且必须存在 |
| `effective_start_at` | 必填，合法时间 |
| `effective_end_at` | 可空；不为空时必须大于开始时间 |
| 附件 | 复用 `AttachmentConfig` 的扩展名和大小限制 |

### 7.4 审计日志

公告属于全平台触达能力，建议关键操作写入全局审计：

| 操作 | 审计动作 |

可复用 `libs.audit_logger.log_operation`，记录 `target_id=announcement.id`、标题、范围、操作人、租户等信息。

### 9.2 QuerySet 封装

建议封装可见性查询，避免详情、列表、附件权限各写一遍：

```python
def visible_announcements_for_user(user, now=None):
    base = Announcement.objects.filter(
        is_deleted=False,
        status='published',
        effective_start_at__lte=now,
    ).filter(
        Q(effective_end_at__isnull=True) | Q(effective_end_at__gte=now)
    )
    return base.filter(
        Q(scope_type='all') |
        Q(scopes__tenant_id=user.tenant_id)
    ).distinct()
```

### 9.3 旧 Notice 迁移

现有 `Notice` 数据可迁移为 `Announcement`：

| 旧字段 | 新字段 |
|---|---|
| `title` | `title` |
| `content` | `content` |
| `is_stress` | `is_important` |
| `created_at` | `created_at`、`published_at` |
| `read_ids` | 拆分为 `AnnouncementRead` |

迁移策略：

1. 新增表结构。
2. 写数据迁移脚本，将旧 `notices` 转为 `tdyw_announcements`。
3. 旧接口 `/api/home/notice/` 暂时保留，只读或转发到新公告接口。
4. 前端切换到新公告接口。
5. 稳定后再评估是否废弃旧 `Notice`。

### 9.4 定时任务

如果项目已有 Celery 或定时任务入口，增加公告过期任务：

```text
任务名：sync_announcement_status
频率：每小时或每日 00:05
动作：将超过 effective_end_at 的已发布公告置为已过期
```

即使定时任务未执行，接口也要实时计算 `computed_status`，保证用户看到的状态准确。

## 十三、风险与处理

| 风险 | 影响 | 处理建议 |
|---|---|---|
| 项目暂无独立部门表 | 指定部门需求无法直接映射 | 首期用 `Tenant` 作为部门，后续扩展部门表 |
| 旧 `read_ids` JSON 不适合大用户量 | 未读统计性能差 | 新增 `AnnouncementRead` 表 |
| 已发布公告编辑后是否重新提醒存在业务分歧 | 用户可能漏看重大变更 | 增加“重新提醒”选项或公告版本字段 |
| 富文本内容存在 XSS 风险 | 安全风险 | 后端清洗 HTML，或首期使用纯文本 |
| 附件越权下载 | 数据泄露 | 附件接口必须回查公告可见性 |
| 定时任务延迟导致状态不准 | 页面状态不一致 | 接口实时返回 `computed_status` |

## 十四、结论

公告发布功能建议在现有 `home.Notice` 基础上升级为结构化公告模块，而不是继续扩展 `read_ids` 和简单排序字段。核心设计是：

1. 公告主表负责标题、内容、生效时间、发布状态和发布部门快照。
2. 范围表负责“全平台/指定部门”的可见性，首期部门复用现有 `Tenant`。
3. 已读表负责未读提醒和阅读追踪。
4. 附件复用现有公共附件服务，避免重复实现文件上传、下载和预览。
5. 首页新增显著公告面板，管理端提供完整发布、撤回、删除流程。

该方案与项目已有账号、租户、附件、首页和审计体系保持一致，实施成本可控，也为后续独立部门体系和细粒度公告权限留下扩展空间。
