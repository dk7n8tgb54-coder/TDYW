# 02 任务拆解

## 任务树

```text
主任务：修复资料库批量上传 200 任务卡住
  - T1：补齐状态机创建失败保护
  - T2：实现状态机懒创建入口 ensureStateMachine
  - T3：改造 startWaiting 调度逻辑
  - T4：移除入队阶段批量创建状态机
  - T5：终态后释放状态机
  - T6：校准 MAX_DISPLAY_COUNT 的用途
  - T7：补充测试与手工验证清单
```

## 里程碑

| 阶段 | 内容 | 预计产物 |
| --- | --- | --- |
| 阶段一：止血 | 所有 `create()` 调用点判空，必要时提高 `MAX_MACHINES` | 不再因空状态机导致 UI 崩溃 |
| 阶段二：结构修复 | 调度时懒创建状态机，入队时只入队不创建 | 870 个任务可持续调度 |
| 阶段三：资源回收 | completed/error/cancelled 后释放状态机 | 状态机数量不随总任务数无限增长 |
| 阶段四：验证 | 单测、集成、浏览器手工验证 | 通过验收清单 |

## 依赖关系

| 任务 | 依赖 | 风险 |
| --- | --- | --- |
| T1 判空保护 | 无 | 低，改动局部 |
| T2 `ensureStateMachine` | 需要理解状态机 context | 中，context 缺失会影响 guard |
| T3 调度改造 | 依赖 T2 | 高，影响所有 waiting 任务启动 |
| T4 入队改造 | 依赖 T2/T3 | 中，需要保证新任务能自动开始 |
| T5 终态释放 | 依赖状态流转稳定 | 中，过早释放可能影响重试 |
| T7 测试 | 依赖 T2-T5 | 中，可能受本地测试环境影响 |

## 优先级

| 任务 | 优先级 | 原因 |
| --- | --- | --- |
| T1 判空保护 | P0 | 直接避免 UI 卡死 |
| T2 `ensureStateMachine` | P0 | 懒创建核心能力 |
| T3 调度改造 | P0 | 解决第 201 个任务不能启动 |
| T4 入队改造 | P0 | 消除批量创建状态机的根因 |
| T5 终态释放 | P1 | 避免内存和状态机数量增长 |
| T6 显示限制校准 | P1 | 避免未来误用显示上限 |
| T7 测试验证 | P0 | 验证修复真实有效 |

## 执行顺序

1. 阅读并确认所有 `stateMachineManager.create()` 调用点。
2. 为所有调用点补判空与日志。
3. 在 `UploadCoordinator` 中新增 `ensureStateMachine(item)`。
4. 修改 `startWaiting()`：先筛 waiting，再为即将启动的任务懒创建状态机。
5. 从 `FileUploadCoordinator._processBatch()` 与 `_processUniform()` 移除入队阶段状态机创建。
6. 在 `StateChangeHandler` 终态分支增加状态机释放。
7. 检查 `MAX_DISPLAY_COUNT` 是否只影响渲染。
8. 运行相关测试，补充 870 任务场景验证。

## 退出标准

- 每个子任务可独立执行并验证。
- 阶段顺序清晰。
- 已标记高风险改动点。
