# 数据库索引审计报告

审计时间：2026-07-02  
审计范围：`spug_api/apps` 下主要业务模块的 Django 模型、查询路径、实际测试库表规模和实际索引清单。  
审计结论：当前项目已经有一批基础索引，尤其是审计日志、文档传输、证据事件、设备档案等模块。但多租户场景下，部分核心业务列表还缺少“租户 + 过滤字段 + 排序字段”的组合索引，明细表也有一些“父记录 + 展示顺序”的索引不完整问题。

## 优先级说明

| 优先级 | 含义 |
| --- | --- |
| P0 | 建议优先处理，命中核心列表、附件列表、状态时间线等高频路径，且现有索引明显不足。 |
| P1 | 建议下一轮处理，收益明确，但当前测试库数据量还不大，可以随功能迭代一起做。 |
| P2 | 观察项，先通过慢查询、真实数据量和用户使用频率验证，再决定是否加。 |

## 本轮检查方法

- 扫描 `models*.py` 中的 `indexes`、`unique_together`、`constraints`、`db_index=True`、默认 `ordering`。
- 扫描 `views.py`、`services.py`、`exporters.py` 等入口中的 `.filter()`、`.order_by()`、`.values()`、`.distinct()`、`.aggregate()`。
- 查询本地 Docker 测试库 `spug` 的 `information_schema.tables` 和 `information_schema.statistics`，核对实际表行数与实际索引。
- 本轮没有做逐条 SQL 的 `EXPLAIN`，因此建议落地前对 P0/P1 查询再做一次 `EXPLAIN` 验证。

## 建议优先处理

| 优先级 | 模块 | 表 | 当前查询场景 | 建议索引 | 理由 |
| --- | --- | --- | --- | --- | --- |
| P0 | 升级管理 | `tdyw_upgrade_records` | 升级单列表按租户过滤，按 `upgrade_time desc, id desc` 分页；同时常按状态、系统、类型筛选。 | `tenant_id, upgrade_time, id`；必要时加 `tenant_id, status, upgrade_time, id` | 现在只有 `tenant_id,status` 和 `tenant_id,upgrade_no` 唯一索引，列表默认排序不能被充分利用。 |
| P0 | 证据附件 | `tdyw_evidence_attachments` | 按业务对象列附件：`tenant_id,module,object_type,object_id,is_deleted`，并按 `uploaded_at desc,id desc` 展示。 | `tenant_id, module, object_type, object_id, is_deleted, uploaded_at, id` | 现有 `ev_att_obj_idx` 不包含 `is_deleted` 和排序字段，附件列表、附件计数、删除后刷新都容易退化。 |
| P1 | 升级管理 | `tdyw_upgrade_status_logs` | 升级工作台状态时间线按 `upgrade_id` 查询，按 `event_seq/id` 正序或倒序展示。 | `tenant_id, upgrade_id, event_seq, id` | 当前有 `upgrade_id,event_seq`，但多租户过滤下最好把 `tenant_id` 放在组合索引前缀。 |
| P1 | 升级管理 | `tdyw_upgrade_record_steps` | 步骤清单按升级单查询，按 `sequence,id` 展示，并统计 pending/completed/skipped。 | `tenant_id, upgrade_id, sequence, id`；可选 `tenant_id, upgrade_id, status` | 当前有 `tenant_id,upgrade_id`，但不覆盖展示顺序和状态统计。 |
| P1 | 运行日志 | `tdyw_run_logs` | 列表按租户、状态/级别/类型/日期过滤，按 `created_at desc,id desc` 分页。 | `tenant_id, created_at, id`；可选 `tenant_id, status, created_at, id` | 当前只有 `tenant_id,status` 和 `tenant_id,severity`，默认排序分页不完整。 |
| P1 | 运行日志 | `tdyw_run_log_updates` | 详情页按运行日志查询动态，按 `update_date,sequence,id` 展示。 | `tenant_id, runlog_id, update_date, sequence, id` | 当前有 `runlog_id`、`tenant_id,runlog_id`、`update_date`，但没有组合覆盖详情展示顺序。 |
| P1 | 值班记录 | `tdyw_duty_records` | 值班列表按租户和日期范围过滤，按 `duty_date desc,id desc` 分页。 | `tenant_id, duty_date, id` | 目前实际库只有主键和外键索引，缺少业务列表索引。 |
| P1 | 故障管理 | `tdyw_fault_records` | 故障列表按租户、日期、系统、等级筛选，按 `fault_date desc,id desc` 展示。 | `tenant_id, fault_date, id` | 目前实际库只有主键和外键索引，列表增长后会比较吃力。 |

## 分模块审计结果

### 系统升级管理

#### `tdyw_upgrade_records`

已有索引：

- 主键 `id`
- 唯一索引 `tenant_id, upgrade_no`
- 普通索引 `tenant_id, status`
- 外键索引 `created_by_id`、`updated_by_id`

主要查询：

- 列表页：`tenant_id` 隔离后按 `status`、`system`、`upgrade_type`、`owner`、`upgrade_time` 范围筛选。
- 默认排序：`upgrade_time desc, id desc`。
- 统计页：按 `upgrade_type`、`system` 聚合。
- 系统名称删除校验：按 `system` 判断是否已有升级记录。

修改建议：

| 优先级 | 建议 |
| --- | --- |
| P0 | 增加 `tenant_id, upgrade_time, id`，服务默认列表分页。 |
| P1 | 如果状态筛选很常用，增加 `tenant_id, status, upgrade_time, id`。 |
| P1 | 如果升级类型筛选很常用，增加 `tenant_id, upgrade_type, upgrade_time, id`。 |
| P2 | `system` 当前多为 `icontains`，普通 BTree 索引帮助有限；如果改成系统清单精确值，可考虑 `tenant_id, system, upgrade_time, id`。 |

注意：`upgrade_time` 当前是字符字段，若长期要做时间范围、统计、排序，建议后续迁移为 `DateTimeField`。仅加索引不能解决日期字符串质量问题。

#### `tdyw_upgrade_systems`

已有索引：

- 主键 `id`
- 唯一索引 `tenant_id, name`
- 外键索引 `created_by_id`、`updated_by_id`

主要查询：

- 获取启用系统：`is_active=True`，按 `sort_order,name` 排序。
- 名称去重：按 `name__iexact` 查询。
- 删除校验：按升级单 `system` 是否存在。

修改建议：

| 优先级 | 建议 |
| --- | --- |
| P1 | 增加 `tenant_id, is_active, sort_order, name`，优化下拉清单和系统管理列表。 |
| P2 | 删除校验建议业务上使用系统 ID 关联升级单；如果仍保留名称字符串，`system` 的删除校验会比较脆弱。 |

#### `tdyw_upgrade_record_steps`

已有索引：

- 主键 `id`
- 单列 `tenant_id`
- 单列 `upgrade_id`
- 组合 `tenant_id, upgrade_id`

主要查询：

- 工作台步骤清单：按升级单读取，按 `sequence,id` 展示。
- 步骤统计：按 `status` 统计 pending/completed/skipped。

修改建议：

| 优先级 | 建议 |
| --- | --- |
| P1 | 增加 `tenant_id, upgrade_id, sequence, id`。 |
| P2 | 如果统计频率高，增加 `tenant_id, upgrade_id, status`。 |
| P2 | 如果经常按阶段分组展示，增加 `tenant_id, upgrade_id, phase`。 |

#### `tdyw_upgrade_status_logs`

已有索引：

- 主键 `id`
- 单列 `tenant_id`
- 单列 `upgrade_id`
- 组合 `tenant_id, upgrade_id`
- 组合 `upgrade_id, event_seq`

主要查询：

- 状态时间线列表：按升级单读取，按 `event_seq,id` 正序或倒序。
- 下一事件序号：按升级单聚合最大 `event_seq`。
- 流程校验：按升级单读取历史动作。

修改建议：

| 优先级 | 建议 |
| --- | --- |
| P1 | 增加或替换为 `tenant_id, upgrade_id, event_seq, id`。 |
| P2 | 如果按动作类型筛选或统计，增加 `tenant_id, upgrade_id, action`。 |

#### `tdyw_upgrade_templates`、`tdyw_upgrade_plan_steps`

已有索引：

- 模板表：单列 `tenant_id`。
- 模板步骤表：单列 `tenant_id`、单列 `template_id`、组合 `tenant_id,template_id`。

主要查询：

- 模板列表按 `is_default,name,id` 排序。
- 模板步骤按 `template_id` 查询，按 `sequence,id` 排序。

修改建议：

| 优先级 | 表 | 建议 |
| --- | --- | --- |
| P1 | `tdyw_upgrade_templates` | 增加 `tenant_id, is_default, name, id`。 |
| P1 | `tdyw_upgrade_plan_steps` | 增加 `tenant_id, template_id, sequence, id`。 |
| P2 | `tdyw_upgrade_templates` | 如果模板按系统/类型过滤明显增多，再考虑 `tenant_id, system`、`tenant_id, upgrade_type`。 |

### 检查表

- `tdyw_checksheet_record`：唯一 `template_id,year,month,day,item_index`。

修改建议：

| 优先级 | 建议 |
| --- | --- |
| P2 | 当前核心查询基本被唯一索引覆盖，暂不建议优先新增。 |

## 不建议立刻加索引的情况

- `icontains` 模糊搜索字段，例如 `system__icontains`、`owner__icontains`、`station_name__icontains`、`system_name__icontains`、`frequency__icontains`。普通 BTree 索引通常无法有效加速 `%keyword%` 这种查询。
- 低选择性的单列字段，例如 `status`、`is_deleted`、`is_read`、`is_active`。更推荐放入组合索引中，前面带 `tenant_id` 和高频过滤字段，后面带排序字段。
- 已经被唯一索引覆盖的字段组合，例如 `tenant_id,upgrade_no`、`tenant_id,device_sn`。不要重复建普通索引。
- 当前数据量很小且查询低频的配置表、字典表。索引太多会拖慢写入，也增加迁移和维护成本。

## 推荐落地顺序

1. 先处理升级管理和公共附件，因为它们是你最近正在改造的模块，且工作台、附件列表、状态时间线会频繁访问。
2. 第二批处理运行日志、值班记录、故障记录，这些模块长期增长后列表会明显受影响。
3. 第三批处理无线电执照明细、提醒、附件、版本表，主要优化详情页和提醒列表。
4. 最后用慢查询日志复核审计日志、文档传输这类已有较多索引的大表，避免重复加索引。
