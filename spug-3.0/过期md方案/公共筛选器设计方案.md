# 公共筛选器设计方案

## 1. 背景

当前前端各业务模块普遍都有筛选区域，例如设备履历、干扰信息、无线电执照、升级记录、故障记录、系统审计等。项目中已经存在 `spug_web/src/components/SearchForm.js`，但它目前只负责布局容器和 `Form.Item` 包装，具体字段渲染、值绑定、查询、重置、日期转换、分页重置等逻辑仍然由各模块自行实现。

这导致几个问题：

- 筛选字段写法重复，`Input`、`Select`、`RangePicker` 的绑定逻辑散落在多个页面。
- 查询和重置行为不一致，有的实时触发，有的需要按钮，有的重置后会重新查询，有的不会。
- 日期范围、空值、多选值等参数转换逻辑容易重复出错。
- 后续如果要统一筛选栏样式、响应式布局、折叠展开、默认查询按钮位置，需要逐个模块修改。

因此建议建设一个公共筛选器能力，但不建议做成过重的“万能筛选系统”。更合适的方式是：保留业务 store 的查询语义，把公共筛选器定位为“配置化筛选栏 + 常用控件渲染 + 通用操作按钮”。

## 2. 目标

### 2.1 要解决的问题

- 统一筛选区域的视觉布局和交互行为。
- 减少各模块重复编写 `Input`、`Select`、`DatePicker.RangePicker` 等控件代码。
- 统一查询、重置、分页回到第一页等通用动作。
- 支持常见字段类型，同时允许业务页面通过 `custom` 自定义复杂字段。
- 为后续统一导出参数、URL 查询参数同步、筛选条件缓存打基础。

### 2.2 不解决的问题

- 不强制统一所有模块 store 的字段命名。
- 不强制所有筛选都改成服务端查询，保留部分模块的前端本地过滤能力。
- 不一次性迁移运行日志这类筛选逻辑较复杂、混在表格 actions 中的模块。
- 不替代业务模块自己的 `fetchRecords`、`getExportParams`、权限控制和特殊查询逻辑。

## 3. 现状分析

### 3.1 已有公共组件

文件：`spug_web/src/components/SearchForm.js`

当前能力：

- 提供筛选区域外壳。
- 提供 `SearchForm.Item`，内部基于 `Col` 和 `Form.Item`。
- 支持外部自行传入任意控件。

不足：

- 不知道字段配置。
- 不管理查询按钮和重置按钮。
- 不处理表单值、日期范围、多选值、空值。
- 不负责调用 `store.fetchRecords()`。
- 各页面仍需手写大量重复 JSX。

### 3.2 代表模块

设备履历：`spug_web/src/pages/device/index.js`

- 使用 `SearchForm`。
- 筛选字段包括输入框、单选下拉、多选下拉。
- 有查询和重置按钮。
- 查询时调用 `store.fetchRecords()`。
- 重置由 `store.resetFilter()` 负责。

干扰信息：`spug_web/src/pages/interference/index.js`

- 使用 `SearchForm`。
- 筛选字段包括下拉、日期范围、输入框。
- 部分筛选在 store 的 `dataSource` 中进行前端过滤。
- 日期范围需要在 `moment` 和字符串之间转换。

无线电执照、升级记录、故障记录、系统审计：

- 都存在相似的筛选字段组合。
- 日期范围、下拉、输入框的重复度较高。

运行日志：`spug_web/src/pages/runlog/Table.js`

- 筛选控件放在 `TableCard` actions 中。
- 同时包含新增、类型管理、导出、统计等操作。
- 不建议作为第一批迁移对象。

## 4. 设计原则

1. 先抽公共交互，不抽业务语义。
2. 配置驱动常见控件，复杂场景允许自定义渲染。
3. 兼容现有 MobX store，不要求大规模改造数据层。
4. 支持渐进迁移，每个模块可以单独接入。
5. 默认行为统一，但允许模块覆盖。
6. 公共组件保持轻量，不引入新的状态管理方案。

## 5. 总体方案

建议新增组件：

`spug_web/src/components/FilterBar.js`

同时保留现有 `SearchForm.js`。短期内 `FilterBar` 可以基于 `SearchForm` 实现，避免破坏已有页面。

组件职责：

- 根据 `fields` 配置渲染筛选项。
- 将字段值绑定到业务 store。
- 提供统一的查询按钮、重置按钮。
- 支持常用控件类型。
- 支持日期范围格式化。
- 支持自定义字段渲染。
- 支持查询前重置分页。

业务职责：

- 继续维护筛选字段，例如 `store.f_device_sn`、`store.f_current_status`。
- 继续维护查询方法，例如 `store.fetchRecords()`。
- 继续维护重置方法，例如 `store.resetFilter()`。
- 继续维护导出参数方法，例如 `store.getExportParams()`。

## 6. 组件 API 设计

### 6.1 基础用法

```jsx
<FilterBar
  store={store}
  fields={[
    { key: 'f_device_sn', label: '设备编号/名称', type: 'input' },
    { key: 'f_device_model', label: '设备型号', type: 'select', options: store.deviceModels },
    { key: 'f_current_status', label: '当前状态', type: 'multipleSelect', options: statusOptions },
    { key: 'f_use_unit', label: '使用单位', type: 'select', options: store.useUnits },
  ]}
  onSearch={store.fetchRecords}
  onReset={store.resetFilter}
/>
```

### 6.2 Props

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `store` | object | 是 | 业务模块 store，字段值默认读写到该对象 |
| `fields` | array | 是 | 筛选字段配置 |
| `onSearch` | function | 否 | 点击查询时调用 |
| `onReset` | function | 否 | 点击重置时调用 |
| `showSearch` | boolean | 否 | 是否显示查询按钮，默认 `true` |
| `showReset` | boolean | 否 | 是否显示重置按钮，默认 `true` |
| `searchText` | string | 否 | 查询按钮文案，默认 `查询` |
| `resetText` | string | 否 | 重置按钮文案，默认 `重置` |
| `buttonSpan` | number | 否 | 按钮区域栅格宽度，默认自动计算 |
| `onValuesChange` | function | 否 | 字段变化后的回调 |
| `beforeSearch` | function | 否 | 查询前回调，可用于分页重置 |
| `style` | object | 否 | 外层样式 |

### 6.3 Field 配置

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `key` | string | 是 | store 上的字段名 |
| `label` | string | 是 | 筛选项标题 |
| `type` | string | 是 | 字段类型 |
| `span` | number | 否 | 栅格宽度，默认 `6` |
| `placeholder` | string/array | 否 | 占位文案 |
| `options` | array/function | 否 | 下拉选项 |
| `allowClear` | boolean | 否 | 是否允许清空，默认 `true` |
| `mode` | string | 否 | Select mode |
| `format` | string | 否 | 日期格式，默认 `YYYY-MM-DD` |
| `valueProp` | string | 否 | 选项值字段，默认 `value` |
| `labelProp` | string | 否 | 选项显示字段，默认 `label` |
| `onChange` | function | 否 | 自定义变更逻辑 |
| `render` | function | 否 | `custom` 类型渲染函数 |
| `props` | object | 否 | 透传给底层控件的属性 |

### 6.4 支持的字段类型

第一阶段支持：

- `input`
- `select`
- `multipleSelect`
- `dateRange`
- `custom`

后续可扩展：

- `date`
- `treeSelect`
- `cascader`
- `radioGroup`
- `checkboxGroup`

## 7. 行为约定

### 7.1 值绑定

默认使用 `field.key` 读写 `store`：

```js
value={store[field.key]}
onChange={value => store[field.key] = value}
```

输入框特殊处理：

```js
onChange={e => store[field.key] = e.target.value}
```

### 7.2 日期范围

组件内部显示时将字符串数组转换为 `moment`：

```js
['2026-06-01', '2026-06-26'] -> [moment(...), moment(...)]
```

用户选择后写回字符串数组：

```js
[momentA, momentB] -> ['2026-06-01', '2026-06-26']
```

默认格式为 `YYYY-MM-DD`，可通过 `field.format` 覆盖。

### 7.3 查询

点击查询按钮时：

1. 执行 `beforeSearch`。
2. 调用 `onSearch`。

常见用法：

```jsx
beforeSearch={() => {
  store.page = 1;
}}
onSearch={store.fetchRecords}
```

### 7.4 重置

优先调用业务传入的 `onReset`。如果没有传入，则组件可以根据 `fields` 自动将字段重置为空：

- `input`、`select`：重置为 `null`
- `multipleSelect`：重置为 `[]`
- `dateRange`：重置为 `[]`

建议正式落地时仍优先让业务 store 提供 `resetFilter`，因为不同模块的分页字段和默认值不完全一致。

## 8. 示例改造

### 8.1 设备履历

改造前：

- 页面手写 4 个 `SearchForm.Item`。
- 每个字段手写 `value` 和 `onChange`。
- 查询按钮手写。
- 重置按钮手写。

改造后：

```jsx
const statusOptions = [
  { value: '1', label: '正常' },
  { value: '2', label: '故障' },
  { value: '3', label: '维修中' },
  { value: '4', label: '停用' },
  { value: '5', label: '报废' },
];

<FilterBar
  store={store}
  fields={[
    { key: 'f_device_sn', label: '设备编号/名称', type: 'input', placeholder: '请输入' },
    { key: 'f_device_model', label: '设备型号', type: 'select', options: store.deviceModels },
    { key: 'f_current_status', label: '当前设备状况', type: 'multipleSelect', options: statusOptions },
    { key: 'f_use_unit', label: '使用单位', type: 'select', options: store.useUnits },
  ]}
  beforeSearch={() => {
    store.page = 1;
  }}
  onSearch={store.fetchRecords}
  onReset={store.resetFilter}
/>
```

### 8.2 干扰信息

```jsx
<FilterBar
  store={store}
  fields={[
    { key: 'f_report_dept', label: '汇报科室', type: 'select', options: store.reportDepts },
    { key: 'f_datetime', label: '日期时间', type: 'dateRange' },
    { key: 'f_interference_type', label: '干扰类型', type: 'select', options: store.interferenceTypes },
    { key: 'f_phenomenon', label: '现象', type: 'input', placeholder: '请输入关键字' },
  ]}
  showSearch={false}
  showReset={false}
/>
```

干扰信息目前是前端本地过滤，字段变化后 `store.dataSource` 会自动重新计算，所以第一阶段可以不显示查询按钮。

## 9. 迁移计划

### 第一阶段：新增公共组件，不改业务行为

目标：

- 新增 `FilterBar.js`。
- 基于现有 `SearchForm` 实现。
- 支持 `input`、`select`、`multipleSelect`、`dateRange`、`custom`。
- 不迁移所有页面，只选择 1 到 2 个低风险模块验证。

建议试点模块：

1. 设备履历：字段类型完整，有查询和重置，适合验证服务端查询场景。
2. 干扰信息：包含日期范围，适合验证前端本地过滤场景。

### 第二阶段：迁移结构相似模块

可迁移模块：

- 无线电执照
- 升级记录
- 故障记录
- 系统审计
- 系统登录日志
- 系统账号/角色等简单筛选页

迁移标准：

- 页面中已经使用 `SearchForm`。
- 筛选字段主要是输入框、下拉、日期范围。
- 没有复杂权限和混合 actions。

### 第三阶段：处理复杂模块

复杂模块包括：

- 运行日志
- 包含统计、导出、动态 actions 的表格页
- 筛选区和工具栏混合在一起的页面

这些模块建议后续结合 `TableCard` 工具栏一起设计，不急于第一批迁移。

## 10. 代码结构建议

```text
spug_web/src/components/
  FilterBar.js
  SearchForm.js
  index.js
```

`components/index.js` 中导出：

```js
import FilterBar from './FilterBar';

export {
  FilterBar,
};
```

后续如果配置和工具函数变多，可以拆分：

```text
spug_web/src/components/FilterBar/
  index.js
  fields.js
  utils.js
```

第一阶段不建议过度拆分，一个文件更容易落地。

## 11. 风险与应对

### 11.1 日期值格式不一致

风险：

部分模块使用字符串数组，部分模块可能直接使用 `moment` 对象。

应对：

- `dateRange` 默认写回字符串数组。
- 允许通过 `field.normalize` 和 `field.formatValue` 覆盖。

### 11.2 store 分页字段不一致

风险：

有的模块使用 `page/pageSize`，有的使用 `pageNum/pageSize`，有的使用 `pagination.page`。

应对：

- 公共组件不内置分页字段。
- 通过 `beforeSearch` 或业务 `resetFilter` 处理。

### 11.3 下拉 options 格式不一致

风险：

有的 options 是字符串数组，有的是 `{ label, value }` 数组。

应对：

- 同时支持字符串和对象。
- 对象默认读取 `value` 和 `label`。
- 可通过 `valueProp`、`labelProp` 覆盖。

### 11.4 自定义逻辑被公共组件限制

风险：

部分业务筛选需要特殊 UI 或特殊 onChange。

应对：

- 提供 `custom` 类型。
- 提供 `field.render`。
- 提供 `field.onChange` 覆盖默认赋值。

### 11.5 一次性迁移影响面过大

风险：

筛选行为变化会影响列表查询、导出、分页。

应对：

- 新增组件和迁移分开提交。
- 先迁移试点模块。
- 每迁移一个模块都验证查询、重置、分页、导出参数。

## 12. 验收标准

公共组件验收：

- 可以渲染输入框、单选下拉、多选下拉、日期范围。
- 字段值能正确写入 store。
- 查询按钮能调用 `onSearch`。
- 重置按钮能调用 `onReset`。
- 日期范围能正确显示和写回。
- options 支持字符串数组和对象数组。
- 支持自定义字段渲染。

试点模块验收：

- 设备履历查询结果和改造前一致。
- 设备履历重置后筛选条件清空，列表刷新。
- 干扰信息筛选结果和改造前一致。
- 日期范围选择、清空行为正常。
- 页面无明显样式错位。

## 13. 推荐实施顺序

1. 新增 `FilterBar.js`，不改任何业务页面。
2. 在 `components/index.js` 导出 `FilterBar`。
3. 迁移设备履历页面。
4. 验证设备履历查询、重置、分页。
5. 迁移干扰信息页面。
6. 验证日期范围和前端过滤。
7. 总结字段配置是否足够，再迁移无线电执照、升级记录等模块。

## 14. 结论

建议建设公共筛选器，但范围应控制在“公共筛选栏组件”而不是“全局查询框架”。当前项目已经有 `SearchForm` 布局基础，可以在其上新增 `FilterBar`，通过字段配置统一常见筛选控件和查询/重置行为。

这样既能减少重复代码，又不会强行改变各业务模块现有 store 和接口参数结构，适合当前项目渐进式改造。
