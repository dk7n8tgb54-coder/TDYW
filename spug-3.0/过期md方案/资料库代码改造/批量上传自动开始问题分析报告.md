# 批量上传自动开始问题分析报告

## 问题描述

用户反馈：
1. 上传第一批文件可以顺利上传
2. 上传第二批文件时，不会自动开启上传状态
3. 批量开始功能不好使

## 问题根本原因分析

### 问题1: 状态机创建时Context不完整 (P0 - 严重)

**位置**: `FileUploadCoordinator.js` 第163-170行

```javascript
this.core.stateMachineManager.create(uploadId, {
  queueStore: this.core.queueStore,
  transferStore: this.core.transferStore,
  md5Store: this.core.md5Store,
  file: file,
  folderId: folderId
});
```

**问题分析**:
状态机创建时传入的context缺少关键信息，导致`canStart()`守卫无法正常判断。

在`UploadStateMachine.js`第531-534行：
```javascript
canStart() {
  const item = this.context.queueStore?.findUploadItemInCurrentTenant(this.uploadId);
  return canStart({ item, isCancelledByUser: item?.isCancelledByUser });
}
```

`canStart`守卫需要检查`isCancelledByUser`，虽然从item获取，但如果item是异步创建的，可能在状态机创建时还不可用。

**更严重的问题**：在`StateMachineManager.batchResume()`中，对于`waiting`状态的任务：
```javascript
// 对于START事件，额外检查canStart守卫
if (eventName === 'START' && machine.canStart && !machine.canStart()) {
  return;
}
```

这里调用`machine.canStart()`，但`canStart()`内部通过`this.context.queueStore`查找item，如果item在队列中但状态不一致，会返回false，导致任务无法启动。

### 问题2: 全局暂停状态未重置 (P0 - 严重)

**位置**: `UploadCoordinator.js` 第20-74行

`startWaiting()`方法在开始任务前没有检查全局`isPaused`状态：
```javascript
startWaiting() {
  const tenantId = this.core.getCurrentTenantId();
  // ... 没有检查 this.core.isPaused
  
  // 如果全局暂停，应该直接返回
  if (this.core.isPaused) {
    console.log('[启动任务] 全局暂停中，不启动新任务');
    return;
  }
}
```

**影响**: 当第一批文件上传时，如果发生了某些错误导致`isPaused`被设置为true，第二批文件添加后将永远不会自动开始。

### 问题3: 批量恢复逻辑缺陷 (P1 - 高)

**位置**: `StateMachineManager.js` 第239-298行

`batchResume()`方法逻辑问题：
1. **只处理已有状态机的任务**：新添加的第二批文件的状态机虽然存在，但如果第一批任务占用了所有并发槽位，第二批任务永远不会被启动
2. **排序逻辑问题**：排序优先处理`paused`状态，但新添加的文件是`waiting`状态，优先级低

```javascript
// 【P3优化】按优先级排序：paused > waiting > 其他
machinesToResume.sort((a, b) => {
  const priority = { 'paused': 0, 'waiting': 1, 'error': 2 };
  const priorityA = priority[a.state] ?? 3;
  const priorityB = priority[b.state] ?? 3;
  return priorityA - priorityB;
});
```

新添加的waiting任务优先级为1，但如果有paused任务（优先级0），waiting任务永远不会被执行。

### 问题4: 并发槽位计算不准确 (P1 - 高)

**位置**: `UploadCoordinator.js` 第26-36行

```javascript
let activeCount = 0;
if (this.core.stateMachineManager) {
  this.core.stateMachineManager.machines.forEach((machine) => {
    const state = machine.getState();
    if (state === 'calculating' || state === 'uploading') {
      activeCount++;
    }
  });
}
```

**问题**：
1. 只统计状态机中的任务，但状态机和实际队列中的任务可能不一致
2. `merging`状态虽然不占用网络资源，但应该占用槽位以防止过多的合并任务同时轮询后端

### 问题5: 第二批文件添加时startWaiting调用时机问题 (P1 - 高)

**位置**: `FileUploadCoordinator.js` 第177-180行

```javascript
console.log('[processUploadQueue] 开始启动任务, displayItems:', displayItems.length);
if (this.core.uploadCoordinator) {
  this.core.uploadCoordinator.startWaiting();
}
```

**问题分析**:
虽然这里调用了`startWaiting()`，但如果第一批文件正在上传中（占用了所有并发槽位），新添加的第二批文件即使调用了`startWaiting()`，也会因为`availableSlots <= 0`而直接返回。

**更深层问题**：当第一批文件完成时，`onCompleted`回调会调用`startWaiting()`，但此时可能出现竞态条件：
1. 第一批文件上传完成，触发completed状态
2. `onCompleted`调用`startWaiting()`
3. 但在`startWaiting`执行期间，状态机还没有完全转换到completed状态
4. 导致并发槽位计算错误，第二批任务无法启动

## 修复建议

### 修复1: 确保startWaiting检查全局暂停状态

```javascript
// UploadCoordinator.js
startWaiting() {
  // 【新增】检查全局暂停状态
  if (this.core.isPaused) {
    console.log('[启动任务] 全局暂停中，不启动新任务');
    return;
  }
  
  // 原有逻辑...
}
```

### 修复2: 修复batchResume的并发控制逻辑

```javascript
// StateMachineManager.js
batchResume(maxConcurrent = 3, getActiveCount = null) {
  const results = [];
  let resumedCount = 0;

  // 【修复】计算活跃任务数时，也包含waiting状态的"即将启动"任务
  let activeCount = 0;
  this.machines.forEach(m => {
    const state = m.getState();
    if (['uploading', 'merging', 'calculating', 'waiting'].includes(state)) {
      activeCount++;
    }
  });

  const availableSlots = Math.max(0, maxConcurrent - activeCount);
  
  // 如果没有可用槽位，但还有waiting任务，需要设置一个标志位
  // 等待当前任务完成后再自动启动
  if (availableSlots <= 0 && this._waitingQueueFlag !== true) {
    this._waitingQueueFlag = true;
    console.log('[batchResume] 并发槽位已满，waiting任务将在当前任务完成后自动启动');
    return results;
  }

  // ... 后续逻辑
}
```

### 修复3: 添加上传完成后的自动启动机制

```javascript
// UploadLifecycle.js
onCompleted(uploadId) {
  // 【关键修复】递减活跃上传计数
  this.core.queueStore.decrementActiveUploads();
  
  // 原有的恢复逻辑
  if (this.core.recoveryCoordinator) {
    this.core.recoveryCoordinator.schedule();
  }
  
  // 【新增】强制启动所有waiting任务，不受recoveryCoordinator限制
  setTimeout(() => {
    if (this.core.uploadCoordinator) {
      // 清除暂停标志，确保新任务可以启动
      this.core.isPaused = false;
      this.core.uploadCoordinator.startWaiting();
    }
  }, 100);
}
```

### 修复4: 修复FileUploadCoordinator中的状态机创建和启动逻辑

```javascript
// FileUploadCoordinator.js 第177-180行
console.log('[processUploadQueue] 开始启动任务, displayItems:', displayItems.length);
if (this.core.uploadCoordinator) {
  // 【修复】确保在添加新文件后，强制重置暂停状态
  if (this.core.isPaused && displayItems.length > 0) {
    this.core.isPaused = false;
  }
  this.core.uploadCoordinator.startWaiting();
}
```

### 修复5: 修复canStart守卫的健壮性

```javascript
// UploadStateMachine.js
canStart() {
  // 【修复】先从context获取item
  let item = this.context.item;
  
  // 如果context中没有，从queueStore查找
  if (!item && this.context.queueStore) {
    item = this.context.queueStore.findUploadItemInCurrentTenant(this.uploadId);
  }
  
  // 【修复】如果没有找到item，返回false
  if (!item) {
    console.warn(`[canStart] ${this.uploadId}: item not found`);
    return false;
  }
  
  return canStart({ 
    item, 
    isCancelledByUser: item.isCancelledByUser || this.context.isCancelledByUser 
  });
}
```

## 临时解决方案

在完全修复之前，可以使用以下临时方案：

```javascript
// 在UploadCoreStore中添加一个强制启动方法
@action
forceStartAllWaiting() {
  this.isPaused = false;
  this.isCancelled = false;
  
  const tenantId = this.getCurrentTenantId();
  const queue = this.queueStore.uploadQueue[tenantId] || [];
  
  queue.forEach(item => {
    if (item.status === 'waiting') {
      const sm = this.stateMachineManager?.get(item.id);
      if (sm && sm.canTransition('START')) {
        sm.transition('START');
      }
    }
  });
}
```
