# 台账关联全链路追溯设计方案

> 编写日期：2026-07-10  
> 需求主题：台账关联、跨台账跳转、数据全链路追溯  
> 关联模块：设备台账、故障台账、运行日志、巡检记录、证据闭环

## 一、建设目标

实现各类台账通过“设备编号”和“流程编号”相互关联。用户在故障台账、设备台账、运行日志、巡检记录等页面中，可以一键跳转查看同一设备、同一处置流程、同一事件链路下的相关数据，形成“从设备到事件、从事件到处理、从处理到巡检/验证、从记录到证据”的完整追溯能力。

建议不要把关联能力分散写在各个模块页面里，而是抽象成统一的“台账关联服务”。各业务台账仍然维护自己的业务字段，但通过统一关联字段、统一查询接口、统一前端组件呈现链路关系。

## 二、当前代码基础判断

当前项目已有以下基础：

| 模块 | 现有模型/页面 | 可用于关联的字段 | 现状判断 |
|---|---|---|---|
| 设备台账 | `DeviceResume`、`DeviceEvent` | `device_sn`、`device_resume_id` | 设备编号已具备租户内唯一约束，是最适合作为设备维度主锚点的字段 |
| 故障台账 | `FaultRecord`、`FaultPart` | `device_code`、`system_name`、`fault_date` | 已有设备编号字段，但未看到与设备档案的显式关联校验 |
| 运行日志 | `RunLog`、`RunLogUpdate` | `system_name`、`event_type`、`created_at` | 目前偏系统/事件维度，缺少设备编号和流程编号 |
| 巡检记录 | `CheckSheetSubmission`、`CheckSheetRecord`、`CheckSheetDailySummary` | `project`、`year`、`month`、`day` | 当前按项目和日期组织，缺少精确设备编号 |
| 证据闭环 | 多模块已有 `snapshot_hash`、作废/更正字段 | 各模块主键、业务编号 | 可作为链路追溯的可信记录基础 |

因此，短期可以基于现有字段做“设备编号弱关联 + 页面跳转”；中期应补齐标准关联字段和索引，保证追溯结果准确、稳定、可解释。

## 三、核心关联键设计

### 3.1 设备编号：横向关联主键

设备编号用于把同一设备在不同台账中的记录串起来。

| 字段 | 建议含义 | 落点 |
|---|---|---|
| `device_sn` | 标准设备编号，以设备台账为准 | 设备台账主字段 |
| `device_code` | 历史故障台账中的设备编号字段 | 建议逐步统一为 `device_sn`，或保留字段但在接口层映射 |
| `device_resume_id` | 设备档案 ID | 适合设备模块内部使用，跨模块不要只依赖 ID |

建议规则：

1. 设备台账 `DeviceResume.device_sn` 是权威来源。
2. 故障台账新增或编辑时，`device_code` 应校验是否存在对应 `DeviceResume.device_sn`。
3. 运行日志、巡检记录后续新增 `device_sn` 字段，支持精确关联设备。
4. 查询时必须同时带 `tenant_id`，避免不同租户同编号数据串联。

### 3.2 流程编号：纵向追溯主键

流程编号用于把一次故障、一次运维处置、一次巡检整改、一次验证闭环串起来。

建议新增统一字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `process_no` | varchar(64) | 业务流程编号，如 `FAULT-20260710-0001` |
| `source_module` | varchar(50) | 流程发起模块，如 `fault`、`runlog`、`checksheet` |
| `source_id` | int | 流程源记录 ID |
| `related_process_no` | varchar(64) | 可选，关联到上游流程 |

流程编号生成建议：

```text
模块前缀 + 日期 + 租户内递增序号

示例：
FAULT-20260710-0001
RUNLOG-20260710-0003
CHECK-20260710-0002
```

设备编号解决“这是谁的事”，流程编号解决“这件事从哪里来、流到哪里去、最后怎么闭环”。

## 四、推荐数据模型

### 4.1 新增统一关联表

建议新增模型 `LedgerRelation`，用于保存跨台账关系，避免在每张业务表里互相加外键造成耦合。

表名建议：`tdyw_ledger_relation`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 主键 |
| `tenant_id` | int/string | 是 | 租户 ID |
| `relation_type` | varchar(30) | 是 | 关联类型：设备关联、流程关联、整改关联、证据关联 |
| `device_sn` | varchar(50) | 否 | 标准设备编号 |
| `process_no` | varchar(64) | 否 | 流程编号 |
| `source_module` | varchar(50) | 是 | 来源模块 |
| `source_model` | varchar(100) | 是 | 来源模型名 |
| `source_id` | int | 是 | 来源记录 ID |
| `target_module` | varchar(50) | 是 | 目标模块 |
| `target_model` | varchar(100) | 是 | 目标模型名 |
| `target_id` | int | 是 | 目标记录 ID |
| `target_title` | varchar(200) | 否 | 目标记录标题快照，便于列表展示 |
| `target_time` | datetime/varchar | 否 | 目标业务时间 |
| `extra` | json/text | 否 | 扩展信息，如状态、级别、跳转参数 |
| `created_at` | datetime/varchar | 是 | 创建时间 |
| `created_by_id` | int | 否 | 创建人 |

推荐索引：

```python
models.Index(fields=['tenant_id', 'device_sn'])
models.Index(fields=['tenant_id', 'process_no'])
models.Index(fields=['tenant_id', 'source_module', 'source_id'])
models.Index(fields=['tenant_id', 'target_module', 'target_id'])
models.Index(fields=['tenant_id', 'relation_type'])
```

唯一约束建议：

```python
UniqueConstraint(
    fields=['tenant_id', 'source_module', 'source_id', 'target_module', 'target_id', 'relation_type'],
    name='uniq_ledger_relation_pair'
)
```

### 4.2 业务表字段补齐建议

短期不强制大改历史表，但建议分阶段补齐字段。

| 模块 | 建议补充字段 | 说明 |
|---|---|---|
| `FaultRecord` | `process_no`、`device_resume_id` | 保留 `device_code`，但新增标准设备关联 |
| `FaultPart` | `process_no`、`fault_record_id`、`device_sn` | 故障件应能回到故障记录和设备 |
| `RunLog` | `process_no`、`device_sn`、`related_fault_id` | 支持由故障生成运维/运行日志 |
| `CheckSheetRecord` | `device_sn`、`process_no` | 巡检异常可关联设备和整改流程 |
| `CheckSheetSubmission` | `process_no` | 批次级归档追溯 |

如果担心一次性迁移风险，可以先只新增 `LedgerRelation`，业务表字段后续逐步补齐。

## 五、后端服务设计

### 5.1 新增应用或服务模块

建议新增后端应用：

```text
spug_api/apps/ledger/
```

核心文件：

```text
models.py       # LedgerRelation
services.py     # LedgerRelationService
views.py        # 关联查询 API
urls.py         # 路由
serializers.py  # 如项目无 serializer，可省略
```

如果不想新增 app，也可以先放在 `apps/device/services.py` 或 `libs/ledger_relation.py`，但长期更推荐独立 `ledger` app。

### 5.2 统一关联服务

建议封装 `LedgerRelationService`：

```python
class LedgerRelationService:
    @staticmethod
    def bind_by_device(tenant_id, device_sn, source, target, relation_type='device'):
        """建立同设备维度的跨台账关联"""

    @staticmethod
    def bind_by_process(tenant_id, process_no, source, target, relation_type='process'):
        """建立同流程维度的跨台账关联"""

    @staticmethod
    def build_trace(tenant_id, module, record_id, include_deleted=False):
        """返回某条记录的全链路追溯数据"""

    @staticmethod
    def rebuild_for_device(tenant_id, device_sn):
        """按设备编号重建关联关系，用于历史数据补偿"""
```

服务层要统一处理：

1. 租户隔离。
2. 关联去重。
3. 目标记录权限过滤。
4. 已删除/作废记录的展示策略。
5. 跳转 URL 和前端参数生成。

### 5.3 关联生成时机

| 场景 | 生成方式 |
|---|---|
| 新增故障记录 | 校验 `device_code`，生成故障记录与设备台账关系；生成 `process_no` |
| 故障转运行日志 | 创建 `RunLog` 时继承 `device_sn` 和 `process_no`，建立故障到运行日志关系 |
| 运行日志新增动态 | 动态归属已有 `RunLog`，通过 `runlog_id` 进入同一流程链 |
| 巡检发现异常 | 生成或绑定 `process_no`，关联到设备和后续整改记录 |
| 设备详情查看 | 不新建关系，只读取关联图谱 |
| 历史数据补偿 | 定时/管理命令按 `device_sn`、`device_code`、`system_name` 批量重建 |

## 六、API 设计

### 6.1 查询某条记录的全链路

```http
GET /api/ledger/trace/?module=fault&model=FaultRecord&id=123
```

返回建议：

```json
{
  "current": {
    "module": "fault",
    "id": 123,
    "title": "某设备故障处置记录",
    "device_sn": "DEV-001",
    "process_no": "FAULT-20260710-0001"
  },
  "device": {
    "id": 88,
    "device_sn": "DEV-001",
    "device_name": "短波发射设备",
    "url": "/device?device_sn=DEV-001"
  },
  "groups": [
    {
      "type": "fault",
      "title": "故障台账",
      "count": 2,
      "items": []
    },
    {
      "type": "runlog",
      "title": "运维/运行日志",
      "count": 3,
      "items": []
    },
    {
      "type": "checksheet",
      "title": "巡检记录",
      "count": 5,
      "items": []
    }
  ],
  "timeline": []
}
```

### 6.2 按设备编号查询关联台账

```http
GET /api/ledger/device/?device_sn=DEV-001
```

用途：

1. 设备详情页展示“关联台账”Tab。
2. 故障台账点击设备编号后跳转设备详情。
3. 运维和巡检模块展示同设备历史记录。

### 6.3 按流程编号查询闭环链路

```http
GET /api/ledger/process/?process_no=FAULT-20260710-0001
```

用途：

1. 故障详情中查看处置全过程。
2. 运行日志详情中回看故障来源。
3. 巡检整改中查看验证闭环。

### 6.4 手动绑定/解绑接口

```http
POST /api/ledger/relation/
DELETE /api/ledger/relation/?id=1
```

手动绑定适用于历史数据或自动匹配不准确的场景。建议只有管理员或具备台账维护权限的用户可操作，并记录审计日志。

现有设备详情弹窗已经有“全生命周期时间线”，建议新增一个 Tab：

```text
基础信息 | 全生命周期时间线 | 关联台账 | 证据包

“关联台账”中按类型分组展示：

| 分组 | 展示字段 | 操作 |

```

### 7.4 巡检记录页面

巡检当前以项目和日期组织，建议增加：

1. 检查项或每日汇总支持选择设备编号。
2. 异常项支持创建整改流程或绑定已有流程。
3. 数据视图中增加“关联设备”“追溯”操作。

## 八、历史数据处理方案

历史数据是这类功能最大的风险点，建议分三步处理。

### 8.1 字段标准化

先建立映射规则：

| 来源字段 | 映射到 |
|---|---|
| `FaultRecord.device_code` | `DeviceResume.device_sn` |
| `FaultRecord.system_name` | 可辅助匹配设备名称、使用单位或运行日志系统名 |
| `RunLog.system_name` | 可辅助匹配设备名称或业务系统 |
| `CheckSheetTemplate.project` | 可辅助匹配设备所属项目/系统 |

### 8.2 自动补偿脚本

新增管理命令：

```text
python manage.py rebuild_ledger_relations --tenant-id=xxx
python manage.py rebuild_ledger_relations --device-sn=DEV-001
python manage.py rebuild_ledger_relations --dry-run
```

脚本逻辑：

1. 读取设备台账，构建设备编号字典。
2. 扫描故障台账，按 `device_code == device_sn` 建立强关联。
3. 扫描运行日志，优先按新增 `device_sn` 关联；无设备编号时按 `system_name` 做候选弱关联。
4. 扫描巡检记录，优先按新增 `device_sn` 关联；无设备编号时按 `project` 做候选弱关联。
5. 对弱关联不直接生效，可进入“待确认关联”列表。

### 8.3 人工确认弱关联

对于只靠 `system_name`、`project` 推断的记录，不建议直接纳入正式追溯链。可以新增 `relation_status`：

| 状态 | 说明 |
|---|---|
| `confirmed` | 已确认，正式展示 |
| `candidate` | 候选关联，仅管理员可见 |
| `rejected` | 已排除 |

首期如果要控制范围，可以先不做候选表，只在文档和脚本日志中输出待人工确认清单。

## 九、权限与审计

1. 用户只能看到自己有权限查看的模块数据。
2. 追溯接口必须按目标模块权限过滤，不能因为有设备权限就绕过故障/运行日志/巡检权限。
3. 手动绑定、解绑、重建关联必须写审计日志。
4. 已软删除、已作废、已更正记录默认不在普通列表突出展示，但追溯链路中可以用灰色状态保留，避免证据断链。
5. 导出追溯链路时，应包含操作人、时间、来源模块、记录 ID、哈希值等信息。

## 十、分阶段实施建议

### 第一阶段：最小可用追溯

目标：用户能从故障台账一键查看设备台账、运维日志和巡检记录。

工作内容：

1. 新增 `ledger` 后端服务和 `LedgerRelation` 表。
2. 故障记录新增/编辑时按 `device_code` 关联设备台账。
3. 新增 `/api/ledger/device/` 和 `/api/ledger/trace/` 查询接口。
4. 设备详情新增“关联台账”Tab。
5. 故障台账新增“查看设备”“追溯”入口。
6. 写一个历史数据重建脚本，先覆盖故障和设备。

### 第二阶段：流程闭环

目标：一次故障处置能串联故障、运行日志、巡检整改和验证。

工作内容：

1. `FaultRecord`、`RunLog`、`CheckSheetRecord` 补 `process_no`。
2. 故障转运行日志时自动继承流程编号。
3. 巡检异常支持绑定流程编号。
4. 追溯抽屉支持按流程时间线展示。
5. 追溯链路支持导出 PDF/Excel。

### 第三阶段：质量治理与智能推荐

目标：历史数据更干净，关联准确率更高。

工作内容：

1. 做候选关联确认页面。
2. 对 `system_name`、`project`、`device_name` 做规则匹配。
3. 增加关联完整率统计。
4. 增加设备维度风险视图，如“近 30 天故障次数”“未闭环流程数”。

## 十一、关键边界与风险

1. 不能只靠设备名称关联，设备名称可能重复，必须优先使用设备编号。
2. 不能只靠数据库 ID 跨模块关联，历史迁移和租户隔离下 ID 可读性差。
3. 巡检记录当前缺少设备编号，若不补字段，只能做到项目级弱关联，不能承诺精确追溯。
4. 运行日志当前缺少设备编号，建议尽快补 `device_sn`，否则只能通过 `system_name` 推断。
5. 追溯接口要避免一次加载过多历史记录，应支持分页或按时间范围查询。
6. 软删除、作废、更正记录不能简单过滤掉，否则会造成证据链断裂。

## 十二、验收标准

建议按以下标准验收：

1. 在故障台账中点击设备编号，可以打开对应设备台账详情。
2. 在故障台账中点击“追溯”，可以看到同设备相关的设备档案、运行日志、巡检记录。
3. 在设备台账详情中，可以看到该设备关联的故障、运行日志、巡检记录数量和列表。
4. 同一租户下设备编号关联准确，不跨租户展示数据。
5. 用户没有权限的模块数据不会在追溯结果中泄露详情。
6. 新增故障记录后，系统自动建立设备关联关系。
7. 历史故障数据可通过脚本重建关联关系。
8. 已作废或已更正记录在追溯链中保留状态标识，不造成链路缺失。

## 十三、推荐落地结论

推荐采用“统一关联表 + 统一追溯接口 + 前端追溯组件”的方案。

短期先以设备编号为主，实现故障台账到设备台账、运行日志、巡检记录的一键跳转和关联查询；中期补齐 `process_no`，把故障处置、运维跟进、巡检整改和归档验证串成完整闭环；长期再做历史数据治理和候选关联确认。

这样实现的好处是改动范围可控，不需要一次性重构所有台账模块，同时后续新增合同、执照、干扰、资料库等模块时，也可以复用同一套关联追溯能力。
