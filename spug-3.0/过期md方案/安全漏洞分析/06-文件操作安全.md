## 漏洞 #12：文件下载一次性读入内存（DoS风险）

### 风险描述
文件下载视图使用 `f.read()` 将整个文件一次性读入内存后再返回。对于大文件（如100MB+的资料库文件），这会导致：
- 单个请求消耗大量内存
- 多个并发下载可能导致OOM（内存溢出）
- 服务器进程被kill，影响所有用户

### 涉及文件

**文件：`spug_api/apps/document/views/file/download.py` 第57-70行**
```python
with open(file.file_path, 'rb') as f:
    response = HttpResponse(f.read())  # ← 整个文件读入内存
    display_name = file.display_name or file.name
    encoded_filename = quote(display_name)
    response['Content-Disposition'] = f'attachment; filename="{encoded_filename}"; filename*=UTF-8\'\'{encoded_filename}'
    response['Content-Type'] = file.file_type
    log_operation(...)
    return response
```

### 内存消耗计算
- 系统配置：`RECYCLE_BIN_LARGE_FILE_THRESHOLD = 104857600`（100MB）
- 假设10个用户同时下载100MB文件：10 × 100MB = 1GB内存
- Docker容器内存限制：4GB
- 加上Django/Celery/Redis等基础内存占用，很容易触发OOM

### 攻击场景
1. 攻击者上传多个大文件到资料库
2. 使用多个会话并发下载这些大文件
3. 服务器内存耗尽，进程被OOM Killer终止
4. 所有用户服务中断

### 正确做法
使用Django的 `FileResponse`（基于StreamingHttpResponse），以流式方式发送文件，内存占用恒定（约8KB缓冲区）。

## 补充：文件上传安全检查

### 当前状态
系统使用分片上传机制，有以下保护：
- 文件大小限制通过Nginx `client_max_body_size 0`（无限制）
- 分片合并使用Celery异步任务
- 有文件类型检查

### 潜在风险
- `client_max_body_size 0` 意味着Nginx不限制上传大小
- 虽然有分片机制，但恶意用户可上传超大文件占满磁盘
- 建议在应用层添加总文件大小限制
