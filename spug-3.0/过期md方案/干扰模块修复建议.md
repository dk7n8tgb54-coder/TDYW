# 干扰模块修复建议

生成时间：2026-06-26

## 一、检查范围

本次主要检查干扰管理相关前后端代码：

- 后端列表、增删改、统计接口：`spug_api/apps/interference/views.py`
- 后端模型：`spug_api/apps/interference/models.py`
- 前端记录列表、筛选、导出、表单：`spug_web/src/pages/interference/`
- 干扰数据在首页和值班日志中的引用：`spug_api/apps/home/views.py`、`spug_api/apps/duty/views.py`

已执行验证：

- `npm run build`：构建成功，仅存在项目既有 ESLint warnings；干扰模块仅发现 `statisticsStore.js` 中 `moment` 未使用的 warning。

## 二、核心结论

干扰模块没有发现编译级阻断问题，但存在几类会影响实际使用的功能缺陷：

1. 列表筛选只过滤当前页，分页总数仍是全量，容易出现“明明有数据却搜不到”的问题。
2. 导出功能只导出当前页当前已加载数据，不是按筛选条件导出全部记录。
3. 新增/编辑共用一个后端权限，存在“只有新增权限也能编辑、只有编辑权限也能新增”的越权风险。
4. 表格序号翻页后仍从 1 开始。
5. 日期字段使用字符串保存，当前依赖格式一致性，后续导入或脚本写入不规范时会影响排序、筛选、统计、首页和值班引用。

建议优先修复权限、筛选分页、导出范围、序号这四项。

## 三、问题清单与修复建议

### P0：新增/编辑接口权限混用，存在越权风险

位置：

- `spug_api/apps/interference/views.py:48`
- `spug_api/apps/interference/views.py:62-76`

现状：

```python
@auth('interference.interference.add|interference.interference.edit')
def post(self, request):
    if form.id:
        ...
    else:
        ...
```

问题：

后端 `post` 同时允许 `add` 或 `edit` 任一权限通过，然后再根据 `id` 判断新增或编辑。这会导致：

- 只有新增权限的用户，只要传入 `id` 就可能编辑记录。
- 只有编辑权限的用户，不传 `id` 就可能新建记录。

建议：

在方法内部按操作类型做二次权限校验，或者拆成两个接口/两个方法：

- `form.id` 存在时必须具备 `interference.interference.edit`
- `form.id` 不存在时必须具备 `interference.interference.add`

伪代码示例：

```python
if form.id:
    if not request.user.has_perms('interference.interference.edit'):
        return json_response(error='无编辑权限')
    ...
else:
    if not request.user.has_perms('interference.interference.add'):
        return json_response(error='无新增权限')
    ...
```

具体权限判断方法需要按项目现有 `auth` / 用户权限工具实现。

验证建议：

- 仅赋予新增权限，调用编辑接口应失败。
- 仅赋予编辑权限，调用新增接口应失败。
- 同租户内有权限编辑成功，跨租户编辑仍失败。

### P1：筛选只作用于当前页，和分页总数不一致

位置：

- `spug_web/src/pages/interference/store.js:25-38`
- `spug_web/src/pages/interference/store.js:41-48`
- `spug_api/apps/interference/views.py:17-37`

现状：

前端只请求 `page` 和 `page_size`，后端返回当前页数据；筛选条件在前端 `dataSource` 中对当前页 `records` 做本地过滤。

问题：

当记录跨多页时，筛选结果只来自当前页。例如目标记录在第 3 页，用户在第 1 页按科室或干扰类型筛选，会显示为空；分页 `total` 仍是全量数量，用户体验会很混乱。

建议：

改为服务端筛选、服务端分页：

前端 `fetchRecords` 发送筛选条件：

- `report_dept`
- `interference_type`
- `phenomenon`
- `start_date`
- `end_date`
- `page`
- `page_size`

后端先按条件过滤，再计算 `total`，最后分页：

```python
records = apply_tenant_filter(Interference.objects.all(), request.user)

if report_dept:
    records = records.filter(report_dept=report_dept)
if interference_type:
    records = records.filter(interference_type=interference_type)
if phenomenon:
    records = records.filter(phenomenon__icontains=phenomenon)
if start_date:
    records = records.filter(datetime__gte=f'{start_date} 00:00:00')
if end_date:
    records = records.filter(datetime__lte=f'{end_date} 23:59:59')

total_count = records.count()
records = records[offset:offset + page_size]
```

前端筛选控件变更时应重置到第一页并重新请求：

```javascript
store.pageNum = 1;
store.fetchRecords();
```

验证建议：

- 制造 20 条以上干扰记录，目标记录放在第 2 页或第 3 页。
- 在第 1 页按目标记录科室/类型筛选，应能查到。
- 筛选后分页总数应等于筛选后的总数。

### P1：导出只导出当前页数据，不是完整查询结果

位置：

- `spug_web/src/pages/interference/Table.js:41-54`
- `spug_web/src/pages/interference/Table.js:63-90`

现状：

导出数据来源是 `store.dataSource`。由于 `store.records` 只保存当前页，导出只会覆盖当前页当前已加载数据。

问题：

用户通常会认为“导出”是导出当前筛选条件下的全部记录，而不是当前分页页码内的 10 条。这个问题和前端本地筛选叠加后更明显。

建议：

新增后端导出接口，或者在列表接口支持 `export=1` / `page_size=all`：

- 复用列表筛选逻辑。
- 导出接口不分页，或使用受控上限。
- 返回文件流或返回全部符合条件的数据给前端生成 xlsx。

如果继续前端生成 xlsx，建议前端导出前先请求完整数据：

```javascript
http.get('/api/interference/', {
  params: {
    ...store.getFilters(),
    page: 1,
    page_size: 10000,
  }
})
```

更推荐后端生成文件，避免大数据量把浏览器卡住。

验证建议：

- 准备 30 条记录，每页 10 条。
- 在第 1 页点击导出，应导出 30 条或筛选后的完整数量，而不是 10 条。
- 导出日期范围应和页面筛选逻辑一致。

### P1：分页参数缺少校验，异常输入可能导致 500 或性能问题

位置：

- `spug_api/apps/interference/views.py:30-37`

现状：

```python
page = int(request.GET.get('page', 1))
page_size = int(request.GET.get('page_size', 100))
offset = (page - 1) * page_size
records = records[offset:offset + page_size]
```

问题：

- `page=abc`、`page_size=abc` 会触发 `ValueError`。
- `page=0`、负数页码可能造成负切片异常。
- `page_size` 无上限，可能被请求成很大值，造成慢查询或大响应。

建议：

增加分页参数解析函数：

```python
def parse_positive_int(value, default, max_value=None):
    try:
        value = int(value)
    except (TypeError, ValueError):
        return default
    value = max(value, 1)
    if max_value:
        value = min(value, max_value)
    return value
```

建议约束：

- `page >= 1`
- `1 <= page_size <= 200`，如导出接口另行处理

验证建议：

- 请求 `?page=abc`
- 请求 `?page=0`
- 请求 `?page_size=999999`
- 接口都应返回正常结构，而不是 500。

### P2：表格序号翻页后仍从 1 开始

位置：

- `spug_web/src/pages/interference/Table.js:151-157`

现状：

```javascript
const pagination = store.pagination || {};
const currentPage = pagination.current || 1;
const pageSize = pagination.pageSize || 10;
return (currentPage - 1) * pageSize + index + 1;
```

问题：

`store` 中并没有 `pagination` 字段，真实字段是 `pageNum` 和 `pageSize`。因此 `currentPage` 永远回退成 1，第二页、第三页序号仍从 1 开始。

建议：

改为：

```javascript
return (store.pageNum - 1) * store.pageSize + index + 1;
```

验证建议：

- 切换到第 2 页，第一条序号应为 11。
- 切换每页 20 条后，第 2 页第一条序号应为 21。

### P2：统计接口按完整时间聚合后再截断日期，日维度数据会重复

位置：

- `spug_api/apps/interference/views.py:120-154`
- `spug_web/src/pages/interference/Statistics.js:55-70`

现状：

后端按 `datetime + frequency`、`datetime + interference_type` 聚合，然后把 `datetime[:10]` 作为日期返回。

问题：

同一天同一频率如果有多条不同时间的记录，后端会返回多条相同 `date + frequency` 数据。前端月度柱状图会再次聚合，所以月度总数通常正确，但 tooltip 和未来日维度展示会出现重复日期行，接口语义也不稳定。

建议：

后端直接按日期前缀聚合。由于当前 `datetime` 是字符串，可以先用数据库字符串截取实现；如果后续迁移成 `DateTimeField`，再用 `TruncDate` / `TruncMonth`。

当前兼容写法示意：

```python
from django.db.models import Count
from django.db.models.functions import Substr

filtered_records = filtered_records.annotate(date=Substr('datetime', 1, 10))

freq_stats = filtered_records.values('date', 'frequency').annotate(count=Count('id'))
type_stats = filtered_records.values('date', 'interference_type').annotate(count=Count('id'))
```

验证建议：

- 同一天同频率创建 3 条不同时间记录。
- 统计接口应返回 1 条该日期该频率记录，`count=3`。

### P2：日期使用 CharField 保存，长期会影响筛选、排序和统计可靠性

位置：

- `spug_api/apps/interference/models.py:20`
- `spug_api/apps/home/views.py:79`
- `spug_api/apps/duty/views.py:78-81`
- `spug_api/apps/interference/views.py:105-113`

现状：

`Interference.datetime` 是 `CharField(max_length=20)`，列表、统计、首页和值班引入都依赖 `YYYY-MM-DD HH:mm:ss` 字符串格式。

问题：

只要有导入脚本或历史数据写入非标准格式，例如：

- `2026/06/26 10:00`
- `2026-6-26 10:00`
- 空格、秒数不一致

就可能导致：

- 字符串范围筛选失准。
- 排序不符合真实时间。
- 首页今日统计和值班引入匹配不到。
- 统计默认年度范围不准确。

建议：

中长期迁移为 `DateTimeField`。如果短期不做迁移，也应在后端写入时强制校验格式：

- 新增/编辑接口校验 `datetime` 必须能按 `%Y-%m-%d %H:%M:%S` 解析。
- 数据生成脚本统一写入标准格式。
- 对历史数据做一次格式清洗。

迁移建议：

1. 新增 `occurred_at = models.DateTimeField(null=True)`。
2. 数据迁移，把合法 `datetime` 转为 `occurred_at`。
3. 前后端改用 `occurred_at`。
4. 确认无兼容需求后删除旧 `datetime` 或保留为展示字段。

### P3：前端必填校验只显示红星，不会阻止空值提交

位置：

- `spug_web/src/pages/interference/Form.js:103-134`

现状：

多个字段使用了 `required` 属性，但没有配置 `rules: [{ required: true }]`。Ant Design 的 `required` 主要用于显示必填标记，不等同于校验规则。

问题：

用户可以点击确定提交空值，最后依赖后端返回错误。体验上会出现“前端表单看起来有必填，但没有就地提示”的问题。

建议：

为必填字段补充规则：

```javascript
rules={[{ required: true, message: '请输入频率' }]}
```

涉及字段：

- `frequency`
- `report_dept`
- `datetime`
- `coordinates`
- `interference_type`
- `phenomenon`
- `is_reported`

验证建议：

- 新建记录时直接点击确定，应在表单字段下方出现校验提示，不应发起请求。

### P3：统计 store 存在无用 import

位置：

- `spug_web/src/pages/interference/statisticsStore.js:8`

现状：

```javascript
import moment from 'moment';
```

该文件没有使用 `moment`，构建时出现 warning。

建议：

删除该 import。

## 四、推荐修复顺序

1. 修复新增/编辑权限混用问题，优先消除越权风险。
2. 列表接口改为服务端筛选 + 服务端分页，前端筛选变更时重置页码并重新请求。
3. 修复导出逻辑，确保导出当前筛选条件下的完整数据。
4. 修复表格序号翻页计算。
5. 为分页参数增加输入校验和最大页大小限制。
6. 统计接口改成按日期前缀聚合，避免重复日维度数据。
7. 前端表单补齐必填校验。
8. 规划 `datetime` 字段迁移为 `DateTimeField`。

## 五、建议测试用例

### 后端接口测试

- 无权限用户不能访问列表。
- 只有新增权限不能编辑已有记录。
- 只有编辑权限不能新增记录。
- 普通租户不能编辑或删除其他租户记录。
- 列表筛选后 `total` 为筛选后的数量。
- 非法分页参数不会触发 500。
- 同一天同频率多条记录统计结果正确聚合。

### 前端交互测试

- 筛选科室、干扰类型、日期范围、现象关键字后能跨页查到数据。
- 切换筛选条件自动回到第一页。
- 第 2 页、第 3 页序号正确。
- 导出数量等于当前筛选结果数量。
- 新建表单空字段无法提交，并显示字段级提示。

### 回归场景

- 首页“干扰信息今日统计”数量正常。
- 值班日志“引入干扰记录”能按值班日期找到当天记录。
- 干扰统计页默认展示当前年度数据，选择日期范围后数据刷新正常。

## 六、备注

本次检查未修改业务源码，仅新增本报告。前端生产构建已通过，说明当前干扰模块不存在语法或打包阻断问题；以上问题主要集中在权限边界、分页筛选语义、导出范围和日期建模可靠性。
