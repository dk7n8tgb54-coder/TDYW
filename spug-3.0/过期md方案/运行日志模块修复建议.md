# 运行日志模块修复建议

## 检查范围

- 后端模型与接口：`spug_api/apps/runlog/models.py`、`views.py`、`urls.py`
- 前端页面：`spug_web/src/pages/runlog/*`
- 权限菜单与路由：`spug_web/src/pages/system/role/codes.js`、`spug_web/src/routes.js`

## 总体结论

运行日志模块主流程已经具备事件创建、动态记录、附件上传、统计、PDF 导出、事件类型管理等能力，但当前存在几类问题：

- 接口鉴权不完整，部分数据读取和附件下载接口只依赖前端隐藏菜单，存在越权访问面。
- 前后端参数契约不一致，日期范围筛选等功能可能无法按预期工作。
- 附件路径处理存在错误和安全风险，删除事件时可能无法清理实际文件。
- 前端按钮显示条件和后端权限点不完全一致，会出现“可见但无权”或“有权但不可见”的体验问题。
- 代码中残留较多调试输出和重复实现，影响维护质量。

建议按 P0/P1/P2 优先级分批处理。

## P0：优先修复

### 1. 为列表和统计接口补齐后端鉴权

**位置**

- `spug_api/apps/runlog/views.py:23`
- `spug_api/apps/runlog/views.py:595`

**问题**

`RunLogView.get` 和 `RunLogStatisticsView.get` 未使用 `@auth('runlog.runlog.view')`。前端虽然在路由和页面层使用了 `runlog.runlog.view`，但前端权限仅用于展示控制，不能替代后端接口鉴权。

**影响**

拥有登录态但没有运行日志查看权限的用户，仍可能直接请求接口获取运行日志列表和统计数据。

**建议**

为两个接口加上后端权限装饰器：

```python
@auth('runlog.runlog.view')
def get(self, request):
    ...
```

同时检查首页、待办、值班日志等入口是否依赖该接口。如果有跨模块统计需求，应明确用对应模块权限或新增专用聚合接口，而不是让运行日志接口裸露。

### 2. 修复附件下载接口鉴权和路径安全

**位置**

- `spug_api/apps/runlog/urls.py:197`

**问题**

`RunLogAttachmentDownloadView.get` 没有 `@auth`，也没有实际校验 URL 中传入的 `x-token`。另外路径只判断 `startswith('/media/runlog/')`，未做规范化路径校验。

**影响**

攻击者可构造 `/api/runlog/attachment/download/?path=/media/runlog/...` 直接下载附件。若路径规范化不足，还可能存在路径穿越风险。

**建议**

- 为下载接口增加权限校验，至少要求 `runlog.runlog.update_view` 或 `runlog.runlog.view`。
- 如果该接口必须供 kkFileView 回调访问，应显式校验 `x-token` 并解析用户，而不是只把 token 拼在 URL 上。
- 使用 `os.path.abspath` / `Path.resolve()` 校验最终路径必须位于 `MEDIA_ROOT/runlog` 下。

示例思路：

```python
base_dir = os.path.abspath(os.path.join(settings.MEDIA_ROOT, 'runlog'))
full_path = os.path.abspath(os.path.join(settings.MEDIA_ROOT, relative_path))
if not full_path.startswith(base_dir + os.sep):
    return HttpResponse('Invalid path', status=400)
```

### 3. 修复日期范围筛选前后端参数不一致

**位置**

- `spug_web/src/pages/runlog/store.js:43`
- `spug_api/apps/runlog/views.py:43`

**问题**

前端传递：

```js
filters.date_range = ['2026-06-01', '2026-06-25']
```

axios 默认会将数组序列化为 `date_range[]=...` 或类似形式；后端使用：

```python
filters = request.GET.dict()
start_date, end_date = filters['date_range']
```

这会导致后端拿不到正确的日期范围，或把字符串逐字符拆包。

**影响**

运行日志列表按日期范围筛选可能失效，用户看到的数据范围不准确。

**建议**

改成明确字段：

前端：

```js
filters.start_date = this.f_date_range[0].format('YYYY-MM-DD');
filters.end_date = this.f_date_range[1].format('YYYY-MM-DD');
```

后端：

```python
start_date = request.GET.get('start_date')
end_date = request.GET.get('end_date')
if start_date:
    logs = logs.filter(created_at__gte=f'{start_date} 00:00:00')
if end_date:
    logs = logs.filter(created_at__lte=f'{end_date} 23:59:59')
```

PDF 导出接口已使用 `start_date` / `end_date`，列表筛选建议与导出保持一致。

### 4. 修复附件清理路径错误

**位置**

- `spug_api/apps/runlog/views.py:217`

**问题**

上传接口保存的附件 URL 形如 `/media/runlog/images/xxx.png`，实际文件路径应对应：

```text
MEDIA_ROOT/runlog/images/xxx.png
```

但删除事件时当前逻辑：

```python
os.path.join(settings.MEDIA_ROOT, attachment_path.lstrip('/'))
```

会拼成：

```text
MEDIA_ROOT/media/runlog/images/xxx.png
```

大概率无法删除真实文件。

**影响**

删除事件后附件文件残留，占用磁盘并造成数据泄露风险。

**建议**

统一封装一个附件 URL 到磁盘路径的转换函数：

```python
def media_url_to_path(url):
    if not url.startswith(settings.MEDIA_URL):
        raise ValueError('invalid media url')
    relative_path = url[len(settings.MEDIA_URL):].lstrip('/')
    return os.path.abspath(os.path.join(settings.MEDIA_ROOT, relative_path))
```

并复用在删除事件、删除动态、附件预览、附件下载等路径处理中。

## P1：重要修复

### 5. 统一动态编辑权限逻辑

**位置**

- `spug_api/apps/runlog/models.py:105`
- `spug_api/apps/runlog/views.py:325`
- `spug_web/src/pages/runlog/Form.js:587`

**问题**

模型 `can_edit(user)` 表示只有创建者或超级管理员在 24 小时内可编辑；但接口 `RunLogUpdateView.put` 只校验 `runlog.runlog.update_edit` 和 24 小时，未限制创建者。

前端又只根据 `update.can_edit` 显示“可编辑”，没有同时判断 `runlog.runlog.update_edit`。

**影响**

权限语义混乱：

- 有 `update_edit` 权限的人可能能改别人动态。
- 创建者看到“可编辑”后也可能因为没有 `update_edit` 权限被后端拒绝。

**建议**

先明确业务规则，然后前后端保持一致。建议采用：

- 后端必须同时校验 `runlog.runlog.update_edit`。
- 普通用户只能编辑自己创建且未超过 24 小时的动态。
- 超级管理员或明确的管理权限可编辑所有未超过 24 小时的动态。

接口中直接调用模型方法：

```python
if not update.can_edit(request.user):
    return json_response(error='该动态不可编辑', code=403)
```

`to_view` 建议接收 `user` 参数，避免只按时间返回 `can_edit`。

### 6. 修复前端操作列权限判断

**位置**

- `spug_web/src/pages/runlog/Table.js:426`

**问题**

操作列外层只判断：

```js
hasPermission('runlog.runlog.edit|runlog.runlog.del')
```

但操作列内还有“添加动态”，权限为 `runlog.runlog.update_add`。

**影响**

只有 `update_add` 权限、没有 `edit/del` 权限的用户，看不到“添加动态”按钮。

**建议**

外层判断改为包含所有操作权限：

```js
hasPermission('runlog.runlog.update_add|runlog.runlog.edit|runlog.runlog.del')
```

### 7. 状态切换按钮增加前端权限控制

**位置**

- `spug_web/src/pages/runlog/Table.js:168`

**问题**

状态标签所有用户都可点击，点击后后端才会用 `runlog.runlog.edit` 拒绝。

**影响**

普通查看用户会看到可点击状态，但操作失败，体验不一致。

**建议**

无 `runlog.runlog.edit` 权限时渲染普通标签，不绑定 `onClick`，也不显示 pointer 光标。

### 8. 删除动态时同步清理附件

**位置**

- `spug_api/apps/runlog/views.py:369`

**问题**

删除整条事件时尝试清理附件，但删除单条动态时只删除数据库记录，没有删除动态附件文件。

**影响**

删除动态后附件残留。

**建议**

将附件清理逻辑抽成函数，在删除事件和删除动态时共用。

## P2：质量和维护优化

### 9. 移除后端 `print` 和前端 `console.log`

**位置**

- `spug_api/apps/runlog/views.py:215`
- `spug_api/apps/runlog/views.py:228`
- `spug_api/apps/runlog/views.py:451`
- `spug_api/apps/runlog/views.py:478`
- `spug_api/apps/runlog/views.py:482`
- `spug_web/src/pages/runlog/Form.js:102` 等多处

**问题**

调试输出较多，生产环境会污染日志，也可能泄露业务数据。

**建议**

- 后端改用 `logger.info/warning/error`，并控制日志级别。
- 前端删除调试 `console.log`，保留必要 `console.error` 即可。

### 10. 合并重复详情视图

**位置**

- `spug_api/apps/runlog/views.py:238`
- `spug_api/apps/runlog/urls.py:15`

**问题**

`RunLogView.get_detail` 和 `RunLogDetailView.get` 逻辑重复，实际 URL 使用的是 `urls.py` 中的 `RunLogDetailView`。

**影响**

后续修复详情逻辑时容易漏改其中一个。

**建议**

只保留一个详情视图，建议迁回 `views.py`，`urls.py` 只负责路由声明。

### 11. 明确事件类型管理权限

**位置**

- `spug_api/apps/runlog/views.py:497`
- `spug_web/src/pages/runlog/EventTypeModal.js`
- `spug_web/src/pages/system/role/codes.js`

**问题**

事件类型管理目前用 `Permission.isSuper` 和后端 `is_superuser` 控制，没有进入角色权限树。

**影响**

如果后续希望租户管理员或特定角色管理事件类型，目前权限模型无法支持。

**建议**

若业务上只有超级管理员可管理，可保持现状，但应在代码注释和 UI 上明确。若需要角色化，新增权限点：

- `runlog.runlog.event_type_view`
- `runlog.runlog.event_type_add`
- `runlog.runlog.event_type_edit`
- `runlog.runlog.event_type_del`

### 12. 长期建议：将 `RunLogUpdate.runlog_id` 改为外键

**位置**

- `spug_api/apps/runlog/models.py:87`

**问题**

当前动态表使用 `IntegerField` 保存事件 ID，而不是 `ForeignKey`。

**影响**

关联完整性、级联删除、查询表达能力都需要手工维护。

**建议**

中长期可迁移为：

```python
runlog = models.ForeignKey(RunLog, on_delete=models.CASCADE, related_name='updates')
```

考虑历史数据和租户字段，建议单独做迁移方案，不与本轮权限修复混在一起。

## 建议修复顺序

1. 补齐后端鉴权：列表、统计、附件下载。
2. 修复附件路径规范化和删除清理。
3. 修复日期范围参数契约。
4. 统一动态编辑权限逻辑。
5. 修正前端权限显示条件。
6. 清理调试输出和重复代码。
7. 补充接口测试或手工回归用例。

## 回归测试建议

### 权限测试

- 无 `runlog.runlog.view` 权限用户直接请求 `/api/runlog/`，应被拒绝。
- 无 `runlog.runlog.view` 权限用户请求 `/api/runlog/statistics/`，应被拒绝。
- 无动态查看权限用户访问 `/api/runlog/detail/?id=...`，应被拒绝。
- 无附件查看权限用户访问附件预览/下载接口，应被拒绝。

### 功能测试

- 按状态、级别、系统名称筛选列表。
- 按日期范围筛选列表，并与 PDF 导出结果范围一致。
- 新建运行日志并自动创建首次动态。
- 添加、编辑、删除动态后，`update_count`、`first_update_date`、`last_update_date` 正确。
- 删除事件后，数据库动态和磁盘附件均被清理。
- 删除单条动态后，动态附件被清理。

### 前端测试

- 只有 `update_add` 权限时，可以看到“添加动态”。
- 只有 `view` 权限时，状态标签不可点击。
- 没有 `update_edit` 权限时，不显示动态“可编辑”。
- 普通用户和超级管理员下，事件类型管理入口显示符合预期。
