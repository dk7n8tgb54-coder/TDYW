# 证据闭环优化方案

## 1. 背景与目标

当前系统已经具备基础操作审计能力，业务模块普遍也有 `created_by`、`updated_by`、`created_at`、`updated_at` 等字段。但从“证据闭环”的角度看，多数模块仍停留在“能看到谁操作过”的层面，还不能稳定证明：

- 某条业务记录由哪个实名账号在什么时间提交。
- 提交时记录内容、附件、审批意见是什么。
- 提交后是否被修改、删除或覆盖。
- 如果发生更正，原始记录和更正记录是否都能追溯。
- 导出给审计、检查、追责时，能否形成完整证据包。

本方案目标是优化以下模块，使其形成统一证据闭环：

- 全局操作审计
- 运行日志
- 检查单
- 无线电执照
- 设备管理
- 干扰管理

最终达到：

```text
实名身份
  + 业务记录快照
  + 附件哈希
  + 状态流转
  + 审批/确认
  + 操作审计
  + 防篡改哈希
  + 证据包导出
= 可追溯、可核验、可归档的证据闭环
```

## 2. 当前现状概览

### 2.1 已有能力

系统已有全局审计模块：

- `spug_api/apps/logs/models.py`
- `spug_api/apps/logs/middleware.py`
- `spug_api/apps/logs/audit.py`

当前能力包括：

- 记录用户 ID、用户名、动作、对象类型、对象 ID、IP、租户、时间。
- 自动识别 `POST / PUT / PATCH / DELETE` 写操作。
- 支持部分特殊动作映射，如 `delete`、`export`、`import`、`approve`。
- 能识别业务响应中的 `error`，避免失败操作被误记为成功。
- 对密码、token、key 等敏感字段进行脱敏。

部分业务模块已有闭环雏形：

- 运行日志有事件状态、动态记录、附件、24 小时编辑窗口。
- 排班换班/替班有审批人、审批时间、审批状态。
- 升级模块有步骤执行、完成时间、完成人。
- 资料库有文件哈希、软删除、传输状态。
- 无线电执照有附件、提醒历史、处理确认。

### 2.2 主要不足

目前还缺少统一的业务证据层：

- 操作审计日志本身没有哈希链或不可篡改机制。
- 多数业务记录提交后仍可直接更新或删除。
- 很多“人名”是文本字段，未强绑定账号 ID 和身份快照。
- 附件缺少统一哈希、上传人快照、原始文件留存策略。
- 审批/确认动作分散在各模块，没有统一证据事件模型。
- 导出 PDF/Excel 只能体现当前数据，不一定能证明原始提交内容。
- 删除多为硬删除或普通删除，证据链容易断。

## 3. 总体设计

### 3.1 设计原则

1. **业务数据可更正，不可悄悄覆盖**
   已提交、已确认、已归档的数据不能直接覆盖修改。确需修改时，走“更正记录”或“重新提交”。

2. **姓名只展示，身份以账号 ID 为准**
   业务表中应保存 `user_id`，同时固化提交时的姓名、工号、部门快照。

3. **附件必须可校验**
   上传附件时计算哈希，后续导出证据包时可重新校验文件是否被替换。

4. **关键动作必须形成证据事件**
   提交、审批、驳回、关闭、作废、删除、导出、补正，都应形成独立证据事件。

5. **审计日志和业务记录互相印证**
   全局审计回答“谁操作过系统”，业务证据回答“这条记录在某个状态下是什么内容”。

6. **内网环境优先**
   平台不能连公网时，先做内部哈希存证、每日归档、离线证据包。后续如果具备条件，再接入第三方时间戳或电子签章。

### 3.2 统一证据底座

建议新增一个通用证据服务，所有重点模块共用。

#### 3.2.1 证据事件表

建议新增表：`evidence_events`

核心字段：

```text
id
tenant_id
module                 模块：runlog/checksheet/radio_license/device/interference
object_type            对象类型
object_id              对象 ID
event_type             submit/approve/reject/close/correct/delete/export/void
event_title            事件标题

actor_user_id          操作人 ID
actor_username         登录账号快照
actor_name             姓名快照
actor_department       部门快照
actor_ip               操作 IP
actor_device           设备信息，可为空

object_snapshot        业务对象快照 JSON
before_snapshot        修改前快照 JSON，可为空
after_snapshot         修改后快照 JSON，可为空
attachment_hashes      附件哈希清单 JSON
remark                 说明

prev_hash              上一条证据事件哈希
event_hash             当前证据事件哈希
created_at             服务器时间
audit_log_id           对应全局审计日志 ID，可为空
```

其中：

```text
event_hash = SHA256(
  tenant_id
  + module
  + object_type
  + object_id
  + event_type
  + actor_user_id
  + object_snapshot
  + attachment_hashes
  + prev_hash
  + created_at
)
```

`prev_hash` 可按租户或按业务对象形成链式结构。第一期建议按业务对象形成链，便于单条记录导出证据包。

#### 3.2.2 附件证据表

建议新增或抽象统一附件证据表：`evidence_attachments`

核心字段：

```text
id
tenant_id
module
object_type
object_id
file_name
file_path
file_size
file_ext
file_hash_sha256
file_hash_md5
uploaded_by_id
uploaded_by_name
uploaded_at
is_deleted
deleted_by_id
deleted_at
delete_reason
```

要求：

- 上传即计算 SHA256。
- 原始文件名和磁盘文件名分开存。
- 删除附件优先做软删除。
- 证据包导出时重新计算 SHA256 并和入库值比对。

#### 3.2.3 业务通用状态

重点证据类业务建议统一引入状态：

```text
draft       草稿
submitted   已提交
reviewed    已复核
closed      已归档/已关闭
voided      已作废
corrected   已更正
```

状态规则：

- `draft` 可编辑。
- `submitted` 后核心字段不可直接改。
- `reviewed / closed` 后只能追加更正、补充说明或作废。
- `voided` 不物理删除，仅标记作废原因。
- 管理员也不应绕过业务流程直接改核心字段。

## 4. 全局操作审计优化

### 4.1 优化目标

全局操作审计作为证据闭环底座，需从“操作流水”升级为“可信操作流水”。

### 4.2 建议改造

1. **审计日志增加哈希字段**

   在 `audit_logs` 增加：

   ```text
   request_hash
   response_hash
   prev_hash
   log_hash
   user_agent
   request_id
   ```

   用于证明日志内容未被静默篡改。

2. **记录关键操作前后快照**

   对更新类操作，除请求 body 外，尽量记录：

   ```text
   before_snapshot
   after_snapshot
   changed_fields
   ```

   第一阶段可先对重点模块实现，不必全系统一次完成。

3. **审计日志禁止业务删除**

   审计日志只允许归档，不允许页面删除。数据库层面保留超级管理员维护能力，但业务系统不提供删除入口。

4. **审计导出也要被审计**

   查询审计日志可以不记录，导出审计日志必须记录：

   ```text
   action=export
   target_type=audit
   detail=导出条件、导出数量、导出人
   ```

5. **每日审计摘要**

   每天生成一份摘要：

   ```text
   日期
   租户
   起始日志 ID
   结束日志 ID
   日志数量
   首条 hash
   末条 hash
   汇总 hash
   生成时间
   ```

   内网环境下可定期导出到只读介质、备份服务器或离线归档目录。

## 5. 运行日志模块证据闭环

涉及文件：

- `spug_api/apps/runlog/models.py`
- `spug_api/apps/runlog/views.py`

### 5.1 当前情况

运行日志已有较好的闭环基础：

- 事件主表 `RunLog`
- 动态表 `RunLogUpdate`
- 状态 `in_progress / resolved`
- 责任人、验证人、关闭时间
- 附件字段
- 动态 24 小时内可编辑

### 5.2 主要缺口

- 动态记录允许编辑和删除，缺少修改历史。
- 附件只有路径列表，没有统一文件哈希。
- 结案/验证缺少明确复核动作。
- 记录解决后是否锁定需要进一步强化。

### 5.3 改造方案

1. **扩展状态流转**

   建议状态调整为：

   ```text
   in_progress 处理中
   resolved    已解决
   verified    已验证
   closed      已归档
   voided      已作废
   ```

2. **动态记录追加优先**

   `RunLogUpdate` 创建后 24 小时内允许创建人编辑；超过 24 小时后只能新增“补充说明”或“更正说明”。

   新增字段：

   ```text
   update_type: normal/correction/supplement/system
   corrected_update_id
   is_voided
   void_reason
   ```

3. **附件哈希化**

   将 `attachments` 从简单路径数组升级为对象数组：

   ```json
   [
     {
       "file_name": "现场照片.jpg",
       "file_path": "/media/runlog/images/xxx.jpg",
       "sha256": "...",
       "uploaded_by": 12,
       "uploaded_at": "2026-06-27 10:00:00"
     }
   ]
   ```

4. **结案证据事件**

   当运行日志从 `resolved` 到 `verified/closed` 时，生成证据事件：

   ```text
   event_type=close
   object_snapshot=事件主表 + 全部动态 + 附件哈希
   actor=验证人/关闭人
   ```

5. **导出运行日志证据包**

   证据包包含：

   ```text
   运行日志 PDF
   事件 JSON 快照
   动态记录 JSON
   附件文件
   附件哈希清单
   操作审计日志
   证据事件 hash 链
   ```

## 6. 检查单模块证据闭环

涉及文件：

- `spug_api/apps/checksheet/models.py`
- `spug_api/apps/checksheet/views.py`

### 6.1 当前情况

检查单当前有：

- 检查模板
- 每日检查记录
- 每日汇总
- `operator` 文本字段
- 备注和整改情况

### 6.2 主要缺口

- `operator` 是文本，不具备强身份绑定。
- 检查记录没有提交/复核/归档状态。
- 历史记录可被覆盖更新。
- 无附件和照片证据。
- PDF 导出更多是报表，不是证据包。

### 6.3 改造方案

1. **新增检查单批次表**

   建议新增：`CheckSheetSubmission`

   ```text
   id
   tenant_id
   year
   month
   day
   project
   status: draft/submitted/reviewed/closed/voided
   submitted_by_id
   submitted_by_name
   submitted_at
   reviewed_by_id
   reviewed_by_name
   reviewed_at
   review_comment
   snapshot_hash
   created_at
   updated_at
   ```

2. **检查项记录绑定提交批次**

   `CheckSheetRecord` 增加：

   ```text
   submission_id
   operator_user_id
   operator_name_snapshot
   operator_department_snapshot
   submitted_at
   ```

3. **提交后锁定**

   - `draft` 可保存。
   - `submitted` 后不能直接覆盖记录。
   - 复核驳回后回到 `draft`，保留驳回记录。
   - `closed` 后只能发起更正。

4. **检查项证据附件**

   支持每个检查项上传照片或文件：

   ```text
   检查项 ID
   附件路径
   附件 sha256
   上传人
   上传时间
   ```

5. **PDF 导出升级为证据包导出**

   原 PDF 保留，同时增加：

   ```text
   检查单 PDF
   原始检查记录 JSON
   每日汇总 JSON
   附件哈希清单
   提交/复核证据事件
   操作审计日志
   ```

## 7. 无线电执照模块证据闭环

涉及文件：

- `spug_api/apps/radio_license/models.py`
- `spug_api/apps/radio_license/views.py`

### 7.1 当前情况

无线电执照模块已有：

- 执照主表
- 频率明细
- 附件表
- 提醒历史
- 已处理确认 `LicenseReminderAck`
- 附件上传人和上传时间

### 7.2 主要缺口

- 附件没有 SHA256 哈希。
- 执照主表编辑后缺少版本历史。
- 执照续期、作废、附件删除没有完整证据事件。
- `responsible_user_name` 是快照字段，但需明确和 `responsible_user_id` 的关系。

### 7.3 改造方案

1. **执照版本化**

   新增：`RadioLicenseVersion`

   ```text
   license_id
   version_no
   snapshot_json
   changed_fields
   changed_by_id
   changed_by_name
   changed_at
   change_reason
   snapshot_hash
   ```

   每次修改执照核心字段时，先保存修改前版本，再更新主表。

2. **附件增加哈希**

   `RadioLicenseAttachment` 增加：

   ```text
   file_hash_sha256
   file_hash_md5
   uploaded_by_name
   is_deleted
   deleted_by_id
   deleted_at
   delete_reason
   ```

3. **续期确认事件**

   修改 `valid_to` 时生成证据事件：

   ```text
   event_type=update
   event_title=执照续期
   before_snapshot=旧 valid_to
   after_snapshot=新 valid_to
   attachment_hashes=续期附件
   ```

4. **提醒处理确认强化**

   当前 `LicenseReminderAck` 设计较好，应补充：

   ```text
   user_name 快照
   ack_ip
   ack_remark
   evidence_event_id
   ```

5. **执照证据包**

   导出内容：

   ```text
   执照基本信息
   频率明细
   附件原件和哈希
   版本历史
   提醒记录
   处理确认记录
   操作审计日志
   证据事件 hash 链
   ```

## 8. 设备管理模块证据闭环

涉及文件：

- `spug_api/apps/device/models.py`
- `spug_api/apps/device/views.py`

### 8.1 当前情况

设备管理当前有：

- 设备履历主表
- 设备事件
- 当前状态
- 创建人、更新人
- 部分唯一约束和索引

### 8.2 主要缺口

- 设备状态变化缺少强制事件化。
- 删除偏硬删除，容易断链。
- 设备事件可编辑/删除，缺少更正机制。
- 责任人、相关人员需要身份快照。
- 缺少设备证据附件和哈希。

### 8.3 改造方案

1. **设备状态变更必须生成事件**

   设备 `current_status` 变化时，必须写入设备事件：

   ```text
   event_type=status_change
   old_status
   new_status
   changed_by
   changed_at
   reason
   ```

2. **设备主表软删除**

   启用已有 `is_deleted` 字段，避免硬删除。

   增加或启用：

   ```text
   deleted_at
   deleted_by
   delete_reason
   ```

   删除设备时：

   - 主表标记删除。
   - 设备事件保留。
   - 生成 `event_type=delete` 证据事件。

3. **设备事件不可随意覆盖**

   设备事件提交后不能直接修改核心字段。修改采用：

   ```text
   correction_event_id
   correction_reason
   corrected_by
   corrected_at
   ```

4. **设备责任人身份快照**

   设备主表保存：

   ```text
   responsible_user_id
   responsible_user_name_snapshot
   responsible_department_snapshot
   ```

   展示名称可从快照显示，不能由前端自由填写。

5. **设备证据包**

   导出内容：

   ```text
   设备基本信息
   全部设备事件
   状态变更历史
   维修/报废/停用证明附件
   附件哈希
   操作审计
   证据事件 hash 链
   ```

## 9. 干扰管理模块证据闭环

涉及文件：

- `spug_api/apps/interference/models.py`
- `spug_api/apps/interference/views.py`

### 9.1 当前情况

干扰管理当前有：

- 频率
- 上报部门
- 时间
- 坐标
- 干扰类型
- 现象描述
- 航班号、机型
- 是否上报
- 创建人、更新人

### 9.2 主要缺口

- 干扰记录没有状态流转。
- `is_reported` 是简单文本，不能表达上报过程。
- 坐标、频率、时间等关键字段可被直接改。
- 缺少附件，如录音、截图、监测图、处置报告。
- 缺少复核和关闭动作。

### 9.3 改造方案

1. **新增干扰状态**

   建议增加：

   ```text
   status: draft/submitted/reviewed/reported/handled/closed/voided
   ```

2. **上报字段结构化**

   替代或补充 `is_reported`：

   ```text
   reported_at
   reported_by_id
   reported_by_name
   report_channel
   report_no
   report_attachment_id
   ```

3. **关键字段提交后锁定**

   以下字段在 `submitted` 后不可直接覆盖：

   ```text
   frequency
   datetime
   coordinates
   interference_type
   phenomenon
   flight_number
   aircraft_type
   ```

   修改必须走更正流程。

4. **干扰证据附件**

   支持上传：

   ```text
   监测截图
   录音文件
   频谱图
   上报回执
   处置报告
   现场照片
   ```

   所有附件计算哈希。

5. **复核与关闭**

   增加：

   ```text
   reviewed_by_id
   reviewed_by_name
   reviewed_at
   handled_by_id
   handled_by_name
   handled_at
   closed_by_id
   closed_by_name
   closed_at
   close_summary
   ```

6. **干扰证据包**

   导出内容：

   ```text
   干扰记录 PDF
   原始记录 JSON
   上报过程
   处置过程
   附件原件
   附件哈希清单
   操作审计日志
   证据事件 hash 链
   ```

## 10. 通用业务流程

重点模块统一采用以下流程：

```text
草稿保存
  ↓
提交
  ↓
生成业务快照 hash
  ↓
生成证据事件 submit
  ↓
复核/审批
  ↓
生成证据事件 approve/reject
  ↓
处理/整改/上报
  ↓
生成过程证据事件
  ↓
关闭/归档
  ↓
生成最终快照 hash
  ↓
证据包导出
```

## 11. 通用权限设计

建议新增权限点：

```text
evidence.view       查看证据链
evidence.export     导出证据包
evidence.correct    发起更正
evidence.void       作废记录
evidence.archive    归档记录
```

各模块再细化：

```text
runlog.evidence.export
checksheet.evidence.export
radio_license.evidence.export
device.evidence.export
interference.evidence.export
```

敏感操作必须二次确认：

- 作废记录
- 删除附件
- 导出证据包
- 更正已归档记录
- 重置审批状态
- 清空升级/检查/运行过程记录

## 13. 分阶段实施计划

### 第一阶段：统一审计增强

目标：先让全局操作审计更可信。

任务：

- 为审计日志增加 hash 字段。
- 增加每日审计摘要。
- 补充导出审计日志记录。
- 对重点模块写操作记录对象 ID、成功失败、错误原因。
- 优化审计日志保留和归档策略。

### 第二阶段：附件哈希与软删除

目标：先把文件和删除行为保住。

任务：

- 统一附件哈希计算。
- 无线电执照附件增加 SHA256。
- 运行日志附件结构化。
- 设备管理启用软删除。
- 干扰管理增加附件表。

### 第三阶段：提交/复核/锁定

目标：让核心业务记录从普通 CRUD 变为流程记录。

任务：

- 检查单新增提交批次。
- 干扰管理增加状态流转。
- 设备状态变更事件化。
- 运行日志增加验证/关闭状态。
- 各模块提交后锁定核心字段。

### 第四阶段：证据事件与证据包

目标：形成真正可导出的证据闭环。

任务：

- 新增 `evidence_events`。
- 关键动作写证据事件。
- 支持按业务对象导出证据包。
- 证据包包含 PDF、JSON、附件、哈希、审计日志。

### 第五阶段：内网归档与外部存证预留

目标：适配无公网环境，同时保留未来升级空间。

任务：

- 每日生成审计摘要和证据摘要。
- 支持离线导出存证包。
- 支持写入内网备份服务器或只读目录。
- 预留第三方时间戳/电子签章接口。

## 14. 优先级建议

建议优先级如下：

| 优先级 | 模块 | 原因 |
|---|---|---|
| P0 | 全局操作审计 | 所有模块的证据底座 |
| P0 | 检查单 | 当前 operator 为文本，证据力弱 |
| P1 | 运行日志 | 已有闭环基础，改造收益高 |
| P1 | 设备管理 | 状态变化和删除需要强追溯 |
| P1 | 干扰管理 | 涉及上报、坐标、频率等关键证据 |
| P2 | 无线电执照 | 已有附件和确认机制，主要补哈希和版本 |

## 15. 巡检模块可复用设计

后续新增机房巡检模块时，建议直接复用本方案的证据底座：

```text
巡检任务
  ↓
现场签到/密钥卡
  ↓
巡检项记录
  ↓
照片/附件 hash
  ↓
巡检人提交
  ↓
主管复核
  ↓
归档锁定
  ↓
证据包导出
```

巡检模块不建议复用当前检查单的 `operator` 文本签名模式，应直接采用：

```text
user_id
username 快照
姓名快照
部门快照
提交时间
提交 IP
附件哈希
证据事件 hash
```

## 16. 最终效果

改造完成后，各模块应具备统一能力：

- 能证明谁创建、提交、复核、关闭。
- 能证明提交时业务内容是什么。
- 能证明附件是否被替换。
- 能证明记录提交后是否被更正、作废或删除。
- 能导出完整证据包。
- 能在无公网环境下通过内部哈希和归档形成基础可信链。

最终系统从“业务管理平台”升级为：

```text
业务管理
  + 操作审计
  + 过程留痕
  + 附件校验
  + 归档锁定
  + 证据导出
= 可追溯的业务证据平台
```
