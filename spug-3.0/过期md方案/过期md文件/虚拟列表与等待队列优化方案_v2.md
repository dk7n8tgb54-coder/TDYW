## 二、项目实际架构分析

### 当前并发控制机制

```javascript
// 核心：UploadCoordinator.startWaiting()
// 使用 activeUploads 计数器 + 状态机管理

class UploadCoordinator {
  startWaiting() {
    const activeCount = this.core.activeUploads || 0;  // 计数器
    const availableSlots = maxConcurrent - activeCount;
    
    // 从 waiting 状态的任务中选择可启动的
    const waitingItems = queue.filter(item => {
      if (item.status !== 'waiting') return false;
      const sm = this.core.stateMachineManager?.get(item.id);
      return sm && sm.canTransition('START');
    });
    
    // 启动任务
    for (const item of waitingItems) {
      stateMachine.transition('START');  // 状态机驱动
    }
  }
}
```

### 状态流转与调度触发

```
用户操作
    ↓
调用 pauseUpload / cancelUpload / resumeUpload
    ↓
更新 item.status → 触发状态机转换
    ↓
状态机回调中调用 increment/decrement activeUploads
    ↓
自动触发 startWaiting() 调度下一个任务
```

**关键点**：项目使用**状态机驱动**而非手动调度，AI建议的手动调用`scheduleNextUpload`与现有架构不符。

```javascript
addToQueue(item, tenantId) {
  if (!this.uploadQueue[tenantId]) {
    this.uploadQueue[tenantId] = [];
  }
  
  // 【移除】不再判断 MAX_DISPLAY_COUNT，所有任务直接加入主队列

    delete item.file;
    Object.defineProperty(item, 'file', {

      writable: true,
      enumerable: false,
      configurable: true
    });
  }

  this.uploadQueue = { ...this.uploadQueue };
  
  // 【新增】自动清理旧任务（防内存泄漏）

}

/**
 * 【新增】自动清理已完成任务
 */
cleanOldCompletedTasks(tenantId) {
  const queue = this.uploadQueue[tenantId] || [];
  const completedTasks = queue.filter(item => item.status === 'completed');
  
  if (completedTasks.length > UPLOAD_CONSTANTS.MAX_COMPLETED_TASKS) {
    // 保留最新的，删除旧的
    const toDelete = completedTasks.slice(0, completedTasks.length - UPLOAD_CONSTANTS.MAX_COMPLETED_TASKS);
    this.uploadQueue[tenantId] = queue.filter(item => !toDelete.includes(item));
    this.uploadQueue = { ...this.uploadQueue };
    
    console.log('[自动清理] 删除', toDelete.length, '个已完成任务');
  }
}
```

## 五、关键问题解答

### Q1: 为什么不彻底删除 MAX_DISPLAY_COUNT？

**原因**：
1. **向后兼容**：项目中可能存在其他未发现的依赖
2. **安全阈值**：防止极端情况下内存溢出（如用户上传10000个文件）
3. **未来扩展**：后续可能需要基于数量的优化策略

**折中方案**：将值从30提升到200，既释放虚拟列表能力，又保留安全保护。

### Q2: 为什么不按AI建议在 pause/cancel 后手动调用 scheduleNextUpload？

**原因**：
1. **架构不匹配**：项目使用**状态机驱动**，状态转换后自动触发调度
2. **重复调度风险**：手动调用可能导致重复启动任务
3. **正确做法**：确保状态机回调中正确更新 `activeUploads` 计数器

**验证代码**：
```javascript
// 项目实际：状态机驱动
stateMachine.transition('PAUSE');  // 触发状态转换
    ↓
// 状态机回调自动处理
onPause() {
  this.core.decrementActiveUploads();  // 减少计数器
  this.core.uploadCoordinator.startWaiting();  // 触发新调度
}
```

### Q3: 内存泄漏防护是否完善？

**当前状态**：
- ✅ 有 `cleanupUploadItem()` 方法清理资源
- ✅ 有 `clearCompleted()` 方法批量清理
- ⚠️ 缺少**自动触发机制**

**新增方案**：`cleanOldCompletedTasks()` 在添加新任务时自动触发。
