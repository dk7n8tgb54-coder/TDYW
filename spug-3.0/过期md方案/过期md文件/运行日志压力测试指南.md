## 测试目标

### 主要目标
- 验证运行日志模块在高并发下的稳定性和性能
- 检测租户隔离、序号计算等核心功能的正确性
- 找出性能瓶颈和潜在问题

### 性能目标
| 并发用户数 | P95 响应时间 | P99 响应时间 | 目标 RPS | 失败率 |
|-----------|-------------|-------------|----------|--------|
| 50        | < 500ms     | < 1s        | > 100    | < 1%    |
| 100       | < 1s        | < 2s        | > 150    | < 1%    |
| 200       | < 2s        | < 3s        | > 200    | < 1%    |

- Python 3.7+

## 运行测试

### 方式一：交互式模式（推荐用于调试）

#### Windows PowerShell
```powershell

```

#### Linux/Mac


- **Number of users**: 50（并发用户数）

- **Host**: `http://localhost:80`

点击 **Start swarming** 开始测试。

### 核心测试点

#### 1. 租户隔离测试
- **验证点**: 不同租户的数据互不可见
- **测试方法**: 使用同一账号创建和查询，验证只返回当前租户数据
- **预期结果**: 无跨租户数据泄露

#### 2. 序号计算正确性测试
- **验证点**: 同一天内的动态序号正确递增
- **测试方法**: 多个并发用户同时为同一事件添加动态
- **预期结果**: 序号不重复，正确递增

#### 3. 编辑时间限制测试
- **验证点**: 24小时内的动态可编辑，超时不可编辑
- **测试方法**: 尝试编辑不同时间的动态
- **预期结果**: 符合时间限制规则

#### 4. 状态流转测试
- **验证点**: 状态流转符合业务规则
- **测试方法**: 尝试各种状态变更
- **预期结果**: 状态流转符合规则，非法流转被拒绝

#### 5. 级联删除测试
- **验证点**: 删除事件时级联删除动态
- **测试方法**: 删除事件后检查动态
- **预期结果**: 关联动态全部删除，统计信息更新

#### 6. 并发冲突测试
- **验证点**: 高并发下数据一致性
- **测试方法**: 多用户同时操作同一资源
- **预期结果**: 无数据不一致，无死锁

## 性能指标

### 关键指标说明

#### 1. RPS (Requests Per Second)
- **含义**: 每秒处理的请求数
- **目标**: 50并发 >100 RPS, 100并发 >150 RPS
- **关注**: RPS 稳定性，不应大幅波动

#### 2. 响应时间分位数
- **P50**: 50%的请求响应时间（中位数）
- **P95**: 95%的请求响应时间
- **P99**: 99%的请求响应时间
- **目标**: 见性能目标表
- **关注**: P99 不应有极端长尾

#### 3. 失败率
- **含义**: 失败请求占总请求的百分比
- **目标**: < 1%
- **关注**: 失败类型和原因

#### 4. 并发用户数
- **含义**: 当前并发用户数
- **关注**: 达到目标并发数时的稳定性

#### 5. 数据库连接数
- **含义**: 活动数据库连接数
- **目标**: 不超过连接池上限
- **关注**: 无连接泄漏

- `runlog_test_stats_history.csv`: 历史数据

### 查看测试报告

#### 使用 Excel 或 Google Sheets
1. 下载 CSV 文件
2. 使用 Excel 打开
3. 创建图表分析趋势

#### 使用 Python 分析
```python
import pandas as pd
import matplotlib.pyplot as plt

# 读取统计数据
stats = pd.read_csv('runlog_test_stats.csv')
history = pd.read_csv('runlog_test_stats_history.csv')

# 绘制 RPS 趋势图
plt.figure(figsize=(12, 6))
plt.plot(history['Timestamp'], history['User Count'], label='Users')
plt.plot(history['Timestamp'], history['RPS'], label='RPS')
plt.xlabel('Time')
plt.ylabel('Count')
plt.title('RPS Trend')
plt.legend()
plt.show()

# 查看 API 性能
print(stats[['Name', 'Request Count', 'Failures', 'Median Response Time', '95% Response Time']])
```

### 性能瓶颈分析

#### 常见瓶颈

| 瓶颈类型 | 症状 | 解决方案 |
|---------|------|----------|
| 数据库查询慢 | P99 响应时间长，RPS 低 | 优化查询，添加索引 |
| 数据库连接池满 | 失败率高，连接错误 | 增加连接池大小 |
| N+1 查询问题 | RPS 低，CPU 占用高 | 使用 select_related/prefetch_related |
| 锁等待 | 并发时响应慢 | 减少锁范围，优化事务 |
| 内存不足 | OOM 错误 | 增加内存，优化查询 |

## 常见问题

### Q1: 测试时出现大量 403 错误？
**原因**: 权限不足或租户隔离

**解决**:
1. 检查测试账号是否有 `runlog.runlog.*` 权限
2. 确认租户过滤是否生效
3. 检查请求头中的 Token 是否正确

---

### Q2: RPS 很低，响应时间很长？
**原因**: 数据库查询慢或连接池问题

**解决**:
1. 检查数据库慢查询日志
2. 添加必要的索引
3. 优化复杂查询
4. 增加数据库连接池大小

---

### Q3: 并发测试时出现死锁？
**原因**: 事务锁冲突

**解决**:
1. 减少事务范围
2. 降低隔离级别
3. 使用乐观锁替代悲观锁
4. 优化业务逻辑减少锁竞争

---

### Q4: 测试数据越来越多，影响测试结果？
**原因**: 测试数据未清理

**解决**:
```sql
-- 清理最近1小时的测试数据
DELETE FROM runlog_run_log_updates
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 1 HOUR);

DELETE FROM runlog_run_logs
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 1 HOUR);
```

---

### Q5: Locust 连不上服务？
**原因**: 主机地址或端口错误

**解决**:
1. 检查服务是否运行：`docker ps` 或查看进程
2. 检查端口映射：`docker-compose.yml` 中的 ports 配置
3. 使用正确的 Host：
   - 本地：`http://localhost:80`
   - Docker：`http://host.docker.internal:80`
   - 远程：`http://IP:PORT`

---

### Q6: 如何模拟真实生产环境？
**建议**:
1. 使用与生产相同的数据量（或按比例缩放）
2. 使用与生产相同的服务器配置
3. 模拟真实的用户行为分布
4. 测试时间覆盖业务高峰期

---

### Q7: 测试时内存占用很高？
**原因**: Locust 用户数过多或请求响应数据量大

**解决**:
1. 减少并发用户数
2. 降低请求频率
3. 分阶段增加负载
4. 使用分布式 Locust
