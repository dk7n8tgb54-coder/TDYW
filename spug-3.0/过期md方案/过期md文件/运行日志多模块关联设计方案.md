# 运行日志多模块关联设计方案

## 概述
支持运行日志与系统中其他业务模块（发布、监控、故障、变更等）建立关联，形成完整的运维事件链路。

---

## 核心方案：统一关联表

### 1. 数据模型设计

**关联表 `runlog_relation`**

| 字段 | 说明 |
|------|------|
| `runlog_id` | 运行日志ID |
| `module_type` | 模块类型枚举（deploy/monitor/alert/fault/change/task） |
| `module_id` | 关联模块记录ID |
| `relation_type` | 关系类型（trigger/cause/fix/related） |
| `created_at` | 关联时间 |

### 2. 模块类型定义

| 类型标识 | 说明 | 典型场景 |
|----------|------|----------|
| `deploy` | 应用发布 | 系统升级、版本发布 |
| `monitor` | 监控告警 | 性能指标异常 |
| `alert` | 告警事件 | 故障报警 |
| `fault` | 故障管理 | 已登记的故障单 |
| `change` | 变更管理 | 配置变更、架构调整 |
| `task` | 运维任务 | 日常巡检、维护任务 |

### 3. 关系类型定义

| 关系 | 含义 |
|------|------|
| `trigger` | 触发 - 模块事件触发了当前日志 |
| `cause` | 原因 - 模块是导致日志记录的根本原因 |
| `fix` | 修复 - 日志记录了对模块问题的处理 |
| `related` | 关联 - 两者相关但无直接因果 |

---

## 典型关联场景

### 场景1：发布导致故障
```
运行日志："2024-01-15 14:30 支付服务异常"
关联记录：
  - module: deploy, id: 128, relation: cause
    （表示是刚才的发布导致了故障）
```

### 场景2：监控告警触发日志
```
运行日志："2024-01-15 15:00 CPU使用率过高"
关联记录：
  - module: monitor, id: 456, relation: trigger
    （表示这条日志由监控告警触发）
```

### 场景3：处理故障后登记
```
运行日志："2024-01-15 16:00 完成数据库连接池扩容"
关联记录：
  - module: fault, id: 789, relation: fix
    （表示这是对某个故障的处理）
```

## 扩展性设计

### 1. 新模块接入
新增模块只需：
1. 在 `module_type` 枚举中添加标识
2. 实现获取模块摘要的接口
3. 前端添加对应的图标和跳转链接

### 2. 批量关联
支持通过标签、时间范围自动关联：
- 同一时间段内的告警和日志自动建议关联
- 相同主机/IP的事件智能推荐关联

---

## 查询优化

### 索引设计
```sql
-- 支持按运行日志查关联
INDEX (`runlog_id`, `module_type`)

-- 支持按模块反向查询
INDEX (`module_type`, `module_id`)
```

### 缓存策略
- 关联模块摘要信息缓存24小时
- 热点关联数据预热

---

## 权限控制

- 运行日志的查看权限继承被关联模块的权限
- 无模块权限时显示"无权限查看"占位
- 关联操作仅限日志创建者和管理员
