# 合并状态查询错误修复报告

## 问题描述

在上传多个文件时，第一个文件上传成功，但第二个文件在合并阶段出现错误：

```
[传输] 合并状态查询失败 (第1/5次): undefined
```

进一步测试发现真正的问题：

```
查询合并状态失败: 'Job' object has no attribute 'next_run_time'
```

## 问题分析

### 根本原因

**后端代码问题**：在 `scheduler.py` 的 `get_job_status` 函数中，直接访问 `job.next_run_time` 属性，但某些 Job 对象可能没有这个属性或该属性为 `None`，导致 `AttributeError`。

**错误代码**（第173行）：
```python
return {
    'status': 'scheduled',
    'job_id': job_id,
    'name': job.name,
    'next_run_time': job.next_run_time.isoformat() if job.next_run_time else None,
}
```

**问题**：
1. 当 Job 对象正在执行时，`next_run_time` 属性可能不存在
2. 直接访问可能导致 `AttributeError`
3. 错误被前端捕获，但 `error.message` 为 `undefined`（因为 error 是字符串）

### 错误流程

```
用户上传第二个文件
    ↓
分片上传完成，提交合并请求
    ↓
前端收到 merge_task_id，开始轮询合并状态
    ↓
调用 /api/document/merge_status/ 接口
    ↓
后端 get_job_status 访问 job.next_run_time
    ↓
AttributeError: 'Job' object has no attribute 'next_run_time'
    ↓
后端返回 json_response(error="查询合并状态失败: ...")
    ↓
前端 catch 块捕获 error（字符串）
    ↓
访问 error.message → undefined (error 是字符串)
    ↓
日志输出: "合并状态查询失败 (第1/5次): undefined"
```

## 修复方案

### 修复1: 后端安全获取 next_run_time

**文件**: `data/backend/apps/document/libs/scheduler.py`

**修改位置**: 第168-174行

**修改前**:
```python
if job:
    return {
        'status': 'scheduled',
        'job_id': job_id,
        'name': job.name,
        'next_run_time': job.next_run_time.isoformat() if job.next_run_time else None,
    }
```

**修改后**:
```python
if job:
    # 安全获取 next_run_time 属性
    next_run_time = None
    try:
        if hasattr(job, 'next_run_time') and job.next_run_time:
            next_run_time = job.next_run_time.isoformat()
    except Exception as e:
        logger.warning(f'[APScheduler] Failed to get next_run_time: {e}')
    
    return {
        'status': 'scheduled',
        'job_id': job_id,
        'name': job.name,
        'next_run_time': next_run_time,
    }
```

**改进点**:
- 使用 `hasattr()` 检查属性是否存在
- 添加 try-except 捕获可能的异常
- 记录警告日志便于调试
- 确保总是返回有效的 `next_run_time` 值

### 修复2: 前端错误对象处理

**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

**修改位置**: 第1212-1214行

**修改前**:
```javascript
} catch (error) {
  consecutiveErrors++;
  console.warn(`[传输] 合并状态查询失败 (第${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}次):`, error.message);
```

**修改后**:
```javascript
} catch (error) {
  consecutiveErrors++;
  const errorMessage = error?.message || String(error);
  console.warn(`[传输] 合并状态查询失败 (第${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}次):`, errorMessage);
  console.warn('[传输] 错误对象详情:', error);
```

**改进点**:
- 使用可选链 `error?.message` 避免访问 `undefined` 的属性
- 使用 `String(error)` 作为备用，确保总能得到有意义的错误信息
- 添加完整错误对象的日志，便于调试

### 修复3: 前端增加状态处理

**文件**: `spug_web/src/pages/document/stores/UploadCoreStore.js`

**修改位置**: 第1199-1208行

**修改前**:
```javascript
if (status.status === 'completed') {
  console.log('[传输] 合并完成');
  return;
} else if (status.status === 'failed') {
  throw new Error(status.error || '合并失败');

```

**修改后**:
```javascript
if (status.status === 'completed') {
  console.log('[传输] 合并完成');
  return;
} else if (status.status === 'failed') {
  throw new Error(status.error || '合并失败');
} else if (status.status === 'timeout') {
  throw new Error('合并超时');
} else if (status.status === 'not_found') {
  // 任务不存在，可能是已被清理
  console.warn('[传输] 合并任务不存在，可能已被清理');
  throw new Error('合并任务不存在');
} else if (status.status === 'error') {
  throw new Error(status.error || '合并任务错误');
}
```

**改进点**:
- 处理 `not_found` 状态（任务文件不存在）
- 处理 `error` 状态（任务执行出错）
- 为每种状态提供明确的错误信息

## 后端状态说明

后端 `get_job_status` 函数可能返回的状态：

| 状态 | 含义 | 处理方式 |
|-----|------|---------|
| `scheduled` | 任务在调度器中等待执行 | 继续轮询 |
| `completed` | 任务已完成 | 返回成功 |
| `failed` | 任务执行失败 | 抛出异常 |
| `pending` | 任务正在等待 | 继续轮询 |
| `merging` | 任务正在合并中 | 继续轮询 |
| `not_found` | 任务不存在（可能已被清理） | 抛出异常 |
| `error` | 任务出错 | 抛出异常 |
| `timeout` | 任务超时 | 抛出异常 |
