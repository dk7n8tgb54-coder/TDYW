## 二、问题详细分析

### 问题1: 状态机状态切换异常

**错误信息**:
```
useDataFetching.js:64 [Explorer] fetchItems error: 请求异常: 网络连接失败，请检查网络后重试
```

**问题分析**:

1. **错误来源定位**
   - 错误发生在 `useDataFetching.js:64`，这是文件列表数据获取的错误
   - 但用户反馈是在上传完成后清理已完成任务时触发
   - 堆栈跟踪显示: `UploadPanel.handleClearCompleted` → `removeItem` → `ItemOperationController.js:171`

2. **状态机与数据获取的耦合问题**
   - 在 `UploadStateMachine.js` 的 `onCalculatingEntry` 方法中（第365行），直接访问了 `queueStore`:
   ```javascript
   const item = this.context.queueStore?.findUploadItemInCurrentTenant(this.uploadId);
   ```
   - 如果 `queueStore` 已被清理或 `uploadId` 不存在，会导致异常

3. **清理操作的时序问题**
   - `UploadPanel.js` 的 `handleClearCompleted` 会调用 `removeItem`
   - 如果此时状态机还在运行（如正在合并），清理后状态机回调时找不到数据

4. **状态机未正确进入终态**
   - 从代码看，`merging` 状态可以转换到 `completed` 或 `error`
   - 但如果合并过程中前端认为已完成并清理，状态机可能处于不一致状态

**根本原因**:
- 状态机与 Store 之间存在隐式耦合
- 清理已完成任务时没有检查状态机是否真正完成
- `useDataFetching` 的错误可能是状态混乱导致的副作用

### 问题2: 上传并发限制失效

**问题分析**:

1. **并发控制配置**
   ```javascript
   // constants/upload.js
   MAX_CONCURRENT_UPLOADS: 3,
   MAX_CONCURRENT_CHUNKS: 3,
   ```

2. **UploadCoordinator 中的并发控制**
   ```javascript
   // UploadCoordinator.js 第24-28行
   const activeCount = queue.filter(queueItem => {
     const sm = this.core.stateMachineManager?.get(queueItem.id);
     return sm && ACTIVE_STATES.includes(sm.getState());
   }).length;
   ```

3. **发现的问题**
   
   a) **并发槽位计算不准确**
   - `UploadCoordinator.startWaiting()` 只检查有状态机的任务
   - 但 `processPending()` 方法（第87行）使用的是 `this.core.activeUploads`，这是另一个计数器
   - 两个计数器可能不一致

   b) **缺少分片级别的并发控制**
   - `MAX_CONCURRENT_CHUNKS: 3` 配置存在，但在 `chunkUpload.js` 中没有使用
   - 分片上传是顺序执行的（第128行 `for` 循环），没有并发控制
   ```javascript
   for (let chunkIndex = startChunkIndex; chunkIndex < chunkCount; chunkIndex++) {
     // 顺序上传，没有并发
   }
   ```

   c) **全局并发与租户并发混淆**
   - 代码中有 `tenantId` 的概念，但并发控制没有按租户隔离
   - 不同租户的上传会共享同一个并发槽位池

4. **batchResume 中的并发控制**
   ```javascript
   // StateMachineManager.js 第239-299行
   batchResume(maxConcurrent = 3, getActiveCount = null) {
     // 计算活跃任务数
     let activeCount = 0;
     this.machines.forEach(m => {
       if (m.isInState('uploading') || m.isInState('merging') || m.isInState('calculating')) {
         activeCount++;
       }
     });
   }
   ```
   - 这里计算的是全局状态机数量，不是按租户

**根本原因**:
- 并发控制逻辑分散在多个文件中，没有统一的管理
- 分片上传没有实现并发控制
- 租户隔离的并发控制缺失

### 问题3: 进度未到99%就开始合并

**问题分析**:

1. **进度计算逻辑**
   ```javascript
   // chunkUpload.js 第323-354行
   xhr.upload.addEventListener('progress', (e) => {
     if (e.lengthComputable) {
       const uploadedBytesInChunk = e.loaded;
       const bytesFromPrevChunks = chunkIndex * UPLOAD_CONSTANTS.CHUNK_SIZE;
       const currentChunkSize = end - start;
       const chunkProgress = uploadedBytesInChunk / currentChunkSize;
       const totalUploadedBytes = bytesFromPrevChunks + (chunkProgress * currentChunkSize);
       const newPercent = Math.min(Math.round((totalUploadedBytes / file.size) * 100), 99);
       // ...
     }
   });
   ```

2. **合并触发条件**
   ```javascript
   // chunkUpload.js 第188-199行
   // 【关键修复】检查是否所有分片都上传成功
   const totalUploadedCount = uploadedChunks.size + sessionUploadedChunks.size;
   if (totalUploadedCount !== chunkCount) {
     throw new Error(`上传未完成，成功 ${totalUploadedCount}/${chunkCount} 个分片`);
   }

   // 检查是否暂停
   const finalItem = this.queueStore.findUploadItemInCurrentTenant(uploadId);
   if (finalItem && finalItem.status !== 'paused') {
     // 合并分片
     await this.mergeChunks(file, uploadId, chunkCount, fileHash, folderId, targetIsPublic);
   }
   ```

3. **发现的问题**

   a) **进度计算精度问题**
   - 进度计算使用 `Math.round()` 四舍五入
   - 当最后一个分片上传完成时，计算可能显示98%或99%
   - 但合并条件检查的是分片数量，不是进度百分比

   b) **进度更新延迟**
   - 进度更新有节流控制（`PROGRESS_THROTTLE_DELAY`）
   - 最后一个分片上传完成后，进度可能还没来得及更新到99%
   - 合并就已经开始

   c) **断点续传的进度显示**
   ```javascript
   // chunkUpload.js 第90-101行
   if (checkResult.uploaded_chunks?.length > 0) {
     uploadedChunks = new Set(checkResult.uploaded_chunks);
     startChunkIndex = Math.max(...checkResult.uploaded_chunks) + 1;
     
     const uploadedCount = checkResult.uploaded_chunks.length;
     const uploadedPercent = Math.min(Math.round((uploadedCount / chunkCount) * 100), 99);
     
     // 更新进度显示
     this.queueStore.updateUploadItem(uploadId, {
       percent: uploadedPercent,
       currentChunk: startChunkIndex,
     });
   }
   ```
   - 断点续传时，已上传的分片直接显示为已完成进度
   - 但实际还需要上传剩余分片

**根本原因**:
- 进度计算和合并触发条件不一致
- 进度更新有延迟，合并触发是立即的
- 断点续传时进度显示可能不准确

## 三、修复方案

### 修复1: 状态机状态切换问题

**方案**: 添加状态一致性检查和防御性编程

1. **在状态机 entry/exit 钩子中添加空值检查**
2. **清理任务时先停止状态机**
3. **添加状态机状态与 Store 状态的同步机制**

```javascript
// UploadStateMachine.js 修改建议
onCalculatingEntry() {
  // 添加防御性检查
  const item = this.context.queueStore?.findUploadItemInCurrentTenant(this.uploadId);
  if (!item) {
    console.warn(`[UploadStateMachine] ${this.uploadId}: item not found, transitioning to error`);
    this.transition('ERROR', { error: '上传项不存在' });
    return;
  }
  // ... 原有逻辑
}
```

### 修复2: 上传并发限制

**方案**: 统一并发控制逻辑，实现分片级并发

1. **统一并发槽位管理**
   - 使用 `UploadCoordinator` 作为唯一的并发控制入口
   - 移除其他地方的并发控制逻辑

2. **实现分片级并发控制**
   ```javascript
   // 使用 Promise.all + 并发池
   const CONCURRENT_CHUNKS = 3;
   const uploadChunkBatch = async (startIdx) => {
     const batch = [];
     for (let i = 0; i < CONCURRENT_CHUNKS && startIdx + i < chunkCount; i++) {
       batch.push(uploadSingleChunk(startIdx + i));
     }
     await Promise.all(batch);
   };
   ```

3. **按租户隔离并发控制**
   - 每个租户有独立的并发槽位池
   - 全局总并发数 = 租户数 × 每租户并发数

### 修复3: 进度与合并同步

**方案**: 确保进度100%时才触发合并

1. **修改合并触发条件**
   ```javascript
   // 确保进度显示100%才合并
   const finalItem = this.queueStore.findUploadItemInCurrentTenant(uploadId);
   if (finalItem && finalItem.percent >= 99 && finalItem.status !== 'paused') {
     await this.mergeChunks(...);
   }
   ```

2. **优化进度计算**
   - 最后一个分片上传完成后，立即设置进度为100%
   - 合并完成后再显示最终状态
