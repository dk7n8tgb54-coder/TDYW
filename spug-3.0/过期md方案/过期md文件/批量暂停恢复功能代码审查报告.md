## 3. 核心方法实现分析

### 3.1 pauseAll (全部暂停)

**位置**: `index.js:322-378`

**执行流程**:
```
1. 设置全局状态 isPaused = true
2. 遍历所有租户的上传队列
3. 对 status === 'uploading' || 'waiting' 且 canAbort 为 true 的项:
   - 更新状态为 'paused'
   - 立即调用 abortController.abort('用户暂停')
   - 收集 transferId 用于后端批量暂停
4. 清空 pendingFiles
5. 调用后端批量暂停 API
```

**关键代码**:
```javascript
// 【关键修复】立即触发abort，避免延迟导致竞态条件
if (abortController) {
  try {
    abortController.abort('用户暂停');
  } catch (e) {
    // 忽略abort错误
  }
}
```

### 3.2 resumeAll (全部恢复)

**位置**: `index.js:381-505`

**执行流程**:
```
1. 设置全局状态 isPaused = false, isCancelled = false
2. 收集所有 status === 'paused'|'waiting'|'error' 的项
3. 调用后端批量恢复 API（带5秒超时）
4. 并发恢复所有暂停的项:
   - 重置状态为 'uploading'
   - 创建新的 AbortController
   - 大文件: 先检查已上传分片，然后调用 resumeChunkedUpload
   - 小文件: 调用 uploadSingleFile
5. 处理 pendingFiles（去重后）
```

**关键代码**:
```javascript
// 【关键修复】先检查已上传分片，同步后端状态
if (queueItem.fileHash) {
  const checkResult = await this.transferStore.checkUploadedChunks(
    queueItem.fileHash, queueItem.fileSize, chunkCount, queueItem.isPublic
  );
  
  if (checkResult.exists && checkResult.uploaded_chunks.length > 0) {
    // 同步已上传分片状态
    queueItem.currentChunk = uploadedCount;
    queueItem.percent = percent;
    queueItem.chunks = checkResult.uploaded_chunks.map(idx => ({ index: idx, uploaded: true }));
  }
}
```

## 4. 发现的问题及修复

### 4.1 问题1: 竞态条件 - 延迟 abort 导致新上传被中断

**严重性**: P0 (严重)

**现象**: 用户快速点击"全部暂停"再点击"全部开始"，新的上传会被旧的 abort 中断

**根因**: 原代码使用 `setTimeout(..., 0)` 延迟触发 abort，如果用户快速操作，新的上传开始后延迟的 abort 才触发

**修复**:
```javascript
// 修复前
setTimeout(() => {
  abortController.abort('用户暂停');
}, 0);

// 修复后
abortController.abort('用户暂停'); // 立即执行
```

### 4.2 问题2: 缺少分片 - 前端状态与后端不同步

**严重性**: P0 (严重)

**现象**: 恢复上传后提示"缺少分片: [5,6]"

**根因**: 
- 暂停时前端记录 `currentChunk = 6`，但分片5可能还在传输中
- 恢复时直接使用前端记录的 `currentChunk`，跳过了未完成的5
- 合并时后端检查发现分片5缺失

**修复**: 恢复前先调用 `checkUploadedChunks` 同步后端实际状态

### 4.3 问题3: AbortSignal 竞态 - 新监听器触发旧 abort

**严重性**: P1 (高)

**现象**: 分片上传报错"上传取消"，但用户未点击暂停

**根因**: 
- `pauseAll` 调用了 `abortController.abort()`
- `resumeAll` 创建了新的 `AbortController`
- 但在 `uploadSingleChunk` 中，如果 signal 已经被 abort，添加监听器会立即触发

**修复**:
```javascript
// 添加前置检查
if (abortController.signal.aborted) {
  reject(new Error('用户暂停'));
  return;
}
```

### 4.4 问题4: pendingFiles 重复处理

**严重性**: P1 (高)

**现象**: 全部暂停恢复后，文件被重复上传

**根因**: `pauseAll` 没有清空 `pendingFiles`，`resumeAll` 会同时处理 `pausedItems` 和 `pendingFiles`

**修复**:
```javascript
// pauseAll 中添加
this.pendingFiles = [];

// resumeAll 的 pendingFiles 处理添加去重
const newFiles = this.pendingFiles.filter(file => {
  const uniqueKey = this.queueStore.generateUniqueKey(file, targetFolderId, isPublic);
  return !this.queueStore.uploadingUniqueKeys.has(uniqueKey);
});
```

### 4.5 问题5: 批量恢复 API 超时无处理

**严重性**: P1 (高)

**现象**: 批量恢复 API 卡住，loading 不消失

**修复**:
```javascript
const timeoutPromise = new Promise((_, reject) => 
  setTimeout(() => reject(new Error('批量恢复超时')), 5000)
);
await Promise.race([
  this.transferStore.batchResumeTransfers(transferIds),
  timeoutPromise
]);
```

### 4.6 问题6: MD5 重复计算

**严重性**: P2 (中)

**现象**: 全部暂停恢复后，大文件重新计算 MD5

**根因**: `resumeAll` 直接调用 `uploadFileChunked`，无条件计算 MD5

**修复**: 大文件使用 `resumeChunkedUpload`，它会检查 `item.fileHash`

### 4.7 问题7: AbortController 引用未彻底清理

**严重性**: P2 (中)

**现象**: 潜在的内存泄漏风险

**根因**: `pauseAll` 中调用 `abort()` 后未将引用置 null

**修复建议**:
```javascript
// 在 pauseAll 中添加清理
if (abortController) {
  try {
    abortController.abort('用户暂停');
  } catch (e) {}
  item.abortController = null; // 添加清理
}

if (abortToken) {
  try {
    abortToken.cancel('用户暂停');
  } catch (e) {}
  item.abortToken = null; // 添加清理
}
```

### 4.8 问题8: API 失败缺乏补偿机制

**严重性**: P2 (中)

**现象**: 前端显示"已暂停"但后端实际未暂停，刷新后状态不一致

**根因**: 批量 API 失败时仅 console.warn，无用户提示和补偿机制

**修复建议**:
```javascript
// 添加弱提示和状态校对机制
try {
  await this.transferStore.batchPauseTransfers(transferIds);
} catch (error) {
  console.warn('[pauseAll] 批量暂停后端记录失败:', error);
  // 添加弱提示
  message.warning('部分任务状态同步失败，刷新页面后将自动校正');
  // 记录失败项用于后续重试
  this.failedSyncTransfers = transferIds;
}
```

## 5. 数据流分析

### 5.1 暂停流程

```
用户点击"全部暂停"
    ↓
pauseAll()
    ↓
遍历队列 → 更新状态为'paused' → abortController.abort()
    ↓
清空 pendingFiles
    ↓
batchPauseTransfers(后端API)
```

### 5.2 恢复流程

```
用户点击"全部开始"
    ↓
resumeAll()
    ↓
收集暂停项 → batchResumeTransfers(后端API, 带超时)
    ↓
并发恢复每个项:
    - 大文件(>32MB): checkUploadedChunks → resumeChunkedUpload
    - 小文件: uploadSingleFile
    ↓
处理 pendingFiles(去重)
```

## 6. 并发控制

### 6.1 暂停时的并发处理

- 立即更新前端状态（同步）
- 立即调用 abort（同步）
- 批量暂停后端记录（异步，失败不影响前端）

### 6.2 恢复时的并发处理

- 使用 `Promise.allSettled` 并发恢复所有项
- 每个项独立创建新的 AbortController
- 大文件断点续传从同步后的位置开始

## 7. 边界情况处理

| 场景 | 处理策略 |
|------|---------|
| 快速暂停/开始 | 立即执行abort，添加signal.aborted检查 |
| 分片上传中暂停 | 记录currentChunk，恢复时同步后端状态 |
| 后端API超时 | 5秒超时，超时后继续前端恢复逻辑 |
| 分片缺失 | 同步后端状态，从实际已上传位置继续 |
| 重复文件 | 使用uniqueKey去重 |
| 用户刷新页面 | 从后端传输记录恢复fileHash |

### 8.2 添加操作队列 (建议评估后采纳)

**必要性**: 中

适用于极端高频操作场景，确保暂停/恢复操作按顺序执行。

```javascript
// 实现参考
class OperationQueue {
  constructor() {
    this.queue = [];
    this.isProcessing = false;
  }

  async add(fn) {
    this.queue.push(fn);
    if (!this.isProcessing) this.process();
  }

  async process() {
    if (this.isProcessing || this.queue.length === 0) return;
    this.isProcessing = true;
    
    const currentOp = this.queue.shift();
    try {
      await currentOp();
    } finally {
      this.isProcessing = false;
      this.process(); // 递归处理下一个
    }
  }
}

// 使用
this.opQueue = new OperationQueue();

pauseAll = () => {
  this.opQueue.add(async () => {
    // 原 pauseAll 逻辑
  });
}
```

**评估**: 当前项目暂停/恢复操作频率较低，建议优先实现 8.1 防抖机制。如后续用户反馈快速点击问题，再考虑实现操作队列。

### 8.3 优化分片检查性能

当前每次恢复都调用 `checkUploadedChunks`，对于大量文件可能有性能问题，建议：
- **短期**: 添加本地缓存（已上传分片列表在内存中缓存5分钟）
- **长期**: 后端支持批量检查接口 `POST /api/document/transfers/batch-check-chunks`

### 8.4 添加状态校对机制 (建议采纳)

**必要性**: 高

在页面初始化时同步前后端状态，解决 API 失败导致的状态不一致。

```javascript
@action
async syncTransferStatus() {
  try {
    const transfers = await this.transferStore.fetchTransfers();
    const uploadQueue = this.queueStore.currentUploadQueue;
    
    // 校对状态不一致的项
    uploadQueue.forEach(item => {
      if (item.transferId) {
        const backendTransfer = transfers.find(t => t.id === item.transferId);
        if (backendTransfer && backendTransfer.status !== item.status) {
          console.warn(`[sync] 状态不一致: ${item.name}, 前端=${item.status}, 后端=${backendTransfer.status}`);
          // 以后端状态为准
          item.status = this.mapBackendStatus(backendTransfer.status);
        }
      }
    });
  } catch (error) {
    console.error('[sync] 状态校对失败:', error);
  }
}
```
