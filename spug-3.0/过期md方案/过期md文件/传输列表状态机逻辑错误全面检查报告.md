## 一、严重级别错误 (P0)

### 错误 1: cleanup 方法未处理 cancelled 状态

**问题描述**:
`StateMachineManager.cleanup()` 只清理 `completed` 和 `error` 状态的状态机，但 `cancelled` 也是终态，应该被清理。

**代码位置**:
```javascript
// StateMachineManager.js:276-289
if (lastTransition && 
    (machine.isInState('completed') || machine.isInState('error')) &&
    (now - lastTransition.timestamp > maxAge)) {
  toRemove.push(uploadId);
}
```

**影响**:
- 已取消任务的状态机不会被自动清理，可能导致内存泄漏
- 状态机数量可能超过 maxInstances 限制

**修复方案**:
```javascript
const FINAL_STATES = ['completed', 'error', 'cancelled'];
if (lastTransition && 
    FINAL_STATES.some(state => machine.isInState(state)) &&
    (now - lastTransition.timestamp > maxAge)) {
  toRemove.push(uploadId);
}
```

### 错误 2: 批量恢复缺少 CANCELLED 状态检查

**问题描述**:
`TransferBatchResumeView` 中没有检查当前状态是否为 `CANCELLED`（终态），如果尝试恢复已取消的任务，会错误地返回"无效状态转换"。

**代码位置**:
```python
# batch.py:117-140
for transfer in permitted_transfers:
    if transfer.status == TransferStatus.UPLOADING.value:
        success_ids.append(transfer.id)
        updated_count += 1
        continue
    # 缺少对 CANCELLED 和 COMPLETED 的检查
```

**影响**:
- 用户批量恢复时，已取消的任务会被错误地标记为失败
- 与前端状态机逻辑不一致（前端 cancelled 是终态，不应该被恢复）

**修复方案**:
```python
# 跳过终态任务
if transfer.status in [TransferStatus.COMPLETED.value, TransferStatus.CANCELED.value]:
    skipped_ids.append(transfer.id)
    skipped_reasons[transfer.id] = f'任务已是终态: {transfer.status}'
    continue
```

## 二、高优先级错误 (P1)

### 错误 3: FAILED 状态转换规则不完整

**问题描述**:
后端 `ALLOWED_STATUS_TRANSITIONS` 中定义 `FAILED` 可以转换到 `PENDING` 和 `CANCELED`，但在实际业务中，FAILED 状态的任务应该可以直接重试（即转换到 `UPLOADING`）。

**代码位置**:
```python
# constants.py:107
TransferStatus.FAILED: [TransferStatus.PENDING, TransferStatus.CANCELED],
```

**影响**:
- 重试失败任务时，如果前端直接尝试将状态改为 UPLOADING，会被后端拒绝
- 需要额外的一次状态转换（FAILED -> PENDING -> UPLOADING）

**修复方案**:
```python
TransferStatus.FAILED: [TransferStatus.UPLOADING, TransferStatus.CANCELED],
```

### 错误 4: paused 状态恢复逻辑存在竞态条件

**问题描述**:
在 `shouldResumeWaiting` 守卫条件中，使用了 `item?.status` 来判断历史状态，但 `item.status` 可能已经被外部修改，导致判断不准确。

**代码位置**:
```javascript
// UploadStateMachine.js:481-493
shouldResumeWaiting() {
  const item = this.getItem();
  const wasWaiting = this.history.some(h => h.from === 'waiting' || h.to === 'waiting') ||
                     (item?.status === 'waiting');  // 这里可能不准确
  // ...
}
```

**影响**:
- 恢复暂停任务时可能选择错误的目标状态
- 可能导致有 fileHash 的任务错误地回到 waiting 状态

**修复方案**:
```javascript
shouldResumeWaiting() {
  const item = this.getItem();
  if (!item?.file) {
    return true;
  }
  // 仅使用历史记录判断，不依赖外部状态
  const wasWaiting = this.history.some(h => h.from === 'waiting' || h.to === 'waiting');
  const hasFileHash = !!item?.fileHash;
  const isMerging = item?.isMerging || (item?.currentChunk >= item?.chunkCount);
  return wasWaiting && !hasFileHash && !isMerging;
}
```

**问题描述**:
在 `merge.py` 中，更新传输记录状态时没有使用数据库事务保护，如果在更新过程中发生异常，可能导致状态不一致。

**代码位置**:
```python

if transfer_obj and transfer_obj.user == request.user:

**影响**:
- 高并发情况下可能出现状态竞争
- 状态更新可能部分成功

from django.db import transaction

with transaction.atomic():
    transfer_obj = DocumentTransfer.objects.select_for_update().filter(id=transfer_id).first()
    if transfer_obj and transfer_obj.user == request.user:
        if transfer_obj.status in [TransferStatus.UPLOADING.value, TransferStatus.PAUSED.value]:
            transfer_obj.status = TransferStatus.MERGING.value
            transfer_obj.save()
```

## 四、新发现的状态机批量转换问题 (2026-03-27)

### 问题 9: batchCancel 未排除 merging 状态 [P1]

**问题描述**:
`merging` 状态允许 CANCEL 转换，但合并中的任务取消可能导致文件损坏。

**代码位置**:
```javascript
// StateMachineManager.js:264-266
batchCancel() {
  return this.batchTransition('CANCEL', (machine) => machine.canTransition('CANCEL'));
}
```

**风险**:
- 用户批量取消时，正在合并的任务会被中断
- 可能导致后端文件处于不完整状态
- 数据库记录与实际文件不一致
- 临时分片文件残留

**修复建议**:
```javascript
batchCancel() {
  const NON_CANCELLABLE_STATES = ['completed', 'error', 'cancelled', 'merging'];
  return this.batchTransition('CANCEL', (machine) => {
    if (NON_CANCELLABLE_STATES.some(state => machine.isInState(state))) {
      return false;
    }
    return machine.canTransition('CANCEL');
  });
}
```

**问题描述**:
`batchResume` 只计算 `uploading` 和 `merging` 作为占用并发槽位的状态，但 `calculating` 状态也会占用资源（CPU计算MD5）。

this.machines.forEach(m => {

### 问题 11: batchTransition 终态统计偏差 [P2]

**问题描述**:
通用 `batchTransition` 方法未对终态任务进行过滤，终态任务会被计入 `results.length` 但不执行转换，导致成功率计算偏差。

**代码位置**:
```javascript
// StateMachineManager.js:133-143
batchTransition(event, filterFn = null) {
  const results = [];
  this.machines.forEach((machine, uploadId) => {
    if (!filterFn || filterFn(machine, uploadId)) {
      const success = machine.transition(event);
      results.push({ uploadId, success, state: machine.getState() });
    }
  });
  // ...
}
```

**当前行为**:
```
批量转换 CANCEL: 0/100 成功  // 100个终态任务，看起来都失败了
```

**修复建议**:
```javascript
batchTransition(event, filterFn = null) {
  const results = [];
  this.machines.forEach((machine, uploadId) => {
    // 跳过终态任务，不计入统计
    if (['completed', 'error', 'cancelled'].includes(machine.getState())) {
      return;
    }
    if (!filterFn || filterFn(machine, uploadId)) {
      const success = machine.transition(event);
      results.push({ uploadId, success, state: machine.getState() });
    }
  });
  // ...
}
```

### 问题 12: batchResume 恢复顺序可优化 [P3]

**问题描述**:
当前按 Map 插入顺序恢复，可能不是最优策略。`waiting` 状态的任务（新任务）可能比 `paused` 状态的任务（暂停的进行中任务）先恢复。

**优化建议**:
```javascript
// 按优先级排序：paused > waiting
const machinesToResume = [];
this.machines.forEach((machine, uploadId) => {
  if (resumedCount >= availableSlots) return;
  machinesToResume.push({ machine, uploadId, state: machine.getState() });
});

// paused 状态优先
machinesToResume.sort((a, b) => {
  if (a.state === 'paused' && b.state !== 'paused') return -1;
  if (a.state !== 'paused' && b.state === 'paused') return 1;
  return 0;
});
```

## 九、部署环境问题发现 (2026-03-27)

### 问题 13: Nginx worker_connections 不足导致 503 [P1]

**问题描述**:
上传文件时出现 `503 Service Unavailable` 错误，Nginx 错误日志显示：
```
1024 worker_connections are not enough while connecting to upstream
```

**根本原因**:
Nginx 默认的 `worker_connections` 配置为 1024，在高并发上传场景下（特别是批量上传和分片上传），连接数耗尽导致无法建立新连接到后端服务。

**影响**:
- 用户上传文件时频繁遇到 503 错误
- 后端服务实际正常，但 Nginx 无法转发请求
- 严重影响用户体验

**解决方案**:

1. **进入容器修改 Nginx 配置**:
```bash
docker exec -it tdyw bash

# 修改 worker_connections 从 1024 改为 4096
sed -i 's/worker_connections 1024/worker_connections 4096/' /etc/nginx/nginx.conf

# 添加文件描述符限制
grep -q 'worker_rlimit_nofile' /etc/nginx/nginx.conf || echo 'worker_rlimit_nofile 65535;' >> /etc/nginx/nginx.conf

# 测试并重载配置
nginx -t && nginx -s reload
```

### 问题 14: 前端路由重定向循环 [P2]

**问题描述**:
Nginx 错误日志出现：
```
rewrite or internal redirection cycle while internally redirecting to "/index.html"
```

**根本原因**:
Nginx 的 `try_files` 配置错误，导致前端路由（SPA）重定向时出现循环。

**影响**:
- 页面刷新或直接访问子路由时出现 500 错误
- 影响单页应用（SPA）的正常路由跳转

**解决方案**:

检查并修正 Nginx 配置 (`/etc/nginx/conf.d/default.conf`):

```nginx
server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        # 正确的配置
        try_files $uri $uri/ /index.html;
        
        # 错误的配置示例（会导致循环）:
        # try_files $uri $uri/ /index.html/index.html/index.html;
    }

    # API 代理配置
    location /api/ {
        proxy_pass http://127.0.0.1:9001/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }
}
```

**验证修复**:
```bash
# 测试 Nginx 配置
docker exec tdyw nginx -t

# 重载配置
docker exec tdyw nginx -s reload
```
