# 资料库文档管理与党建文档拖拽上传实现提示词

> 使用方式：将以下完整内容交给编码 Agent，并要求其同时阅读项目根目录的 `文档与附件拖拽上传设计方案.md`。  
> 本提示词只实施资料库下“文档管理”和“党建文档”的拖拽上传，不实施或修改 `AttachmentManager` 业务附件拖拽方案。

---

## 角色与任务

你是一名资深前端/全栈工程师，需要在现有 Django + React 16 + MobX + Ant Design 4 项目中，为资料库模块增加拖拽上传能力，覆盖：

1. 普通资料库文档管理；
2. 党建文档系统目录；
3. 拖入一个或多个普通文件；
4. 在 Chromium 浏览器中拖入一个或多个文件夹，并保留目录结构；
5. 混合拖入普通文件和文件夹；
6. 继续复用现有上传队列、小文件上传、分片上传、断点续传、动态压力调度、`MiniBar` 和 `UploadPanel`；
7. 确保拖入批次始终上传到用户松开鼠标时显示的目录；
8. 确保党建文档任务在排队期间切换目录或离开页面后仍携带正确 `system_folder` 上下文。

请直接在仓库中完成实现和验证，不要只输出代码片段或建议。

## 三、目标架构

建议新增：

```text
spug_web/src/pages/document/components/DocumentDropUploadLayer.js
spug_web/src/pages/document/utils/dropUpload.js
```

总体调用链：

```text
DocumentIndex
  -> DocumentDropUploadLayer
     -> collectDroppedItems(dataTransfer)
        -> captureUploadTargetContext()
        -> 普通文件：uploadCoreStore.handleFileSelect(files, targetContext)
        -> 文件夹：uploadCoreStore.handleFolderEntries(entries, targetContext)
           -> 现有 FileUploadCoordinator / FolderUploadStore
              -> 普通上传或分片上传
                 -> 现有队列、状态机、MiniBar、UploadPanel
```

`DocumentDropUploadLayer` 只负责拖拽事件和遮罩，不负责上传请求、队列状态和业务校验。

## 四、拖拽交互要求

### 4.1 投放区域

投放监听范围放在 `DocumentIndex` 的 `.explorerArea`：

```jsx
<div className={styles.explorerArea}>
  <DocumentDropUploadLayer ...>
    <Explorer ... />
  </DocumentDropUploadLayer>
</div>
```

可以根据实际布局让投放层自身成为 `.explorerArea` 的直接子节点，但必须满足：

- 覆盖文件列表/网格区域；
- 不覆盖左侧目录树；
- 不覆盖顶部导航；
- 不覆盖 `UploadPanel`；
- 遮罩不能改变 Explorer 尺寸或导致布局跳动。

### 4.2 遮罩内容

拖入外部文件时显示全区域遮罩：

```text
[上传图标]
松开鼠标，上传到“当前目录名称”
支持多文件和文件夹
```

党建模式显示：

```text
松开鼠标，上传到“党建文档 / 当前子目录”
```

视觉要求：

- 使用现有主色和中性背景，不使用渐变、光球或装饰性插画；
- 遮罩边框清晰但克制；
- `pointer-events` 和层级设置不能阻断 drop；
- 文本在窄屏下换行，不能溢出；
- 可用 `aria-live="polite"` 提示目标目录变化；
- 不新增常驻大卡片，只有外部文件进入时显示遮罩。

### 4.3 拖拽事件规则

- 只有 `dataTransfer.types` 包含 `Files` 时才进入上传拖拽状态；
- 页面内部表格行、文字、链接、URL 和普通 DOM 拖动不得触发；
- 使用 `dragDepthRef` 或等价进入深度计数处理子元素间移动，不能只用单一 `dragenter/dragleave` 布尔值；
- `drop`、窗口失焦、拖拽取消和组件卸载时清理状态；
- 只在投放区域内处理外部文件，不在整个应用注册永久性的全局 drop 行为；
- 在投放区域内即使当前禁止上传，也要阻止浏览器默认打开文件，并给出明确原因；
- 每个 `drop` 事件只能入队一次，避免冒泡或重复监听导致双重上传。

### 4.4 禁用场景

| 场景 | 行为 |
|---|---|
| 无当前模式上传权限 | 不进入上传队列，提示“无上传权限” |
| 党建根目录尚未初始化 | 不接受投放，沿用初始化中/失败状态 |
| 搜索结果模式 | 不接受投放，提示“请退出搜索后上传” |
| 目标目录不存在或无写权限 | 后端校验失败，不得回退到根目录 |
| 拖入空文件夹 | 提示“空文件夹无需上传” |
| 浏览器不支持目录拖入 | 普通文件仍可上传，文件夹提示使用“上传文件夹”按钮 |

拖入文件夹时不得削弱现有文件夹创建权限。检查当前按钮上传文件夹和后端目录创建接口使用的权限；如果除 upload 外还需要 create_folder 权限，前端应提前提示，后端仍保留最终校验。

## 五、不可变上传目标上下文

### 5.1 为什么必须捕获快照

目录递归和大量文件入队可能耗时。用户在解析或上传期间可能：

- 切换到另一个目录；
- 从私人空间切到公共共享库；
- 离开党建文档页面；
- 进入普通资料库；
- 切换租户。

同一批文件不能因此改变目标位置或系统目录归属。

### 5.2 目标上下文结构

在 `drop` 事件发生时立即调用 Store 的统一方法捕获：

```js
uploadCoreStore.captureUploadTargetContext({
  systemFolderCode: isPartyBuildingDocuments
    ? PARTY_BUILDING_DOCUMENTS_CODE
    : null,
  targetPathLabel,
})
```

返回不可变普通对象，至少包含：

```js
{
  folderId,
  isPublic,
  tenantId,
  systemFolderCode,
  targetPathLabel,
}
```

要求：

- `folderId` 使用 `navigationStore.getUploadTargetFolderId()` 的结果；
- `isPublic` 使用捕获时空间值；
- `tenantId` 使用捕获时租户值，不能在真正发请求时重新读取可能变化的 `sessionStorage`；
- 普通资料库 `systemFolderCode=null`；
- 党建文档必须为 `party_building_documents`；
- 可使用 `Object.freeze` 或约定只读，后续流程不得修改该对象。

### 5.3 Store 入口向后兼容

把现有入口扩展为可选上下文：

```js
handleFileSelect(files, targetContext = null)
handleFolderSelect(files, targetContext = null)
handleFolderEntries(entries, targetContext = null)
```

兼容规则：

- 点击上传旧代码不传 `targetContext` 时，Store 在入口立即捕获当前上下文；
- 拖拽上传在 `drop` 时显式传入已捕获上下文；
- 所有队列项保存 `folderId/isPublic/tenantId/systemFolderCode`；
- 后续普通上传、分片上传、传输记录、合并、状态轮询和恢复都从队列项读取，不能回退到当前页面导航状态；
- 不允许为了拖拽复制一套 Coordinator。

### 5.4 党建 `system_folder` 持久传递

当前 `http.js` 只在党建路由仍激活时自动注入 `system_folder`；分片 XHR 也会读取当前全局上下文。批量任务排队后用户离开党建页面时，这种做法不足以保证后续请求仍在党建范围。

必须把 `systemFolderCode` 固化到队列项，并显式传递到与该任务有关的每个请求：

- 创建 transfer；
- 创建文件夹结构；
- 普通文件上传 FormData；
- 分片上传 FormData；
- 检查已上传分片；
- 合并分片；
- 合并状态查询；
- 暂停、恢复、取消以及需要验证业务范围的传输接口。

原则：

```text
显式任务上下文 > 当前路由自动注入
```

普通资料库任务不得携带残留的 `system_folder`。后端仍必须校验系统目录 code、权限和目标目录范围，不能只相信前端参数。

## 六、文件和文件夹解析

### 6.1 普通文件

当 `DataTransfer` 只有普通文件时：

```js
const files = collectedItems.map(item => item.file)
uploadCoreStore.refreshPressure()
uploadCoreStore.handleFileSelect(files, targetContext)
```

不得直接调用普通上传或分片上传 API。

### 6.2 文件夹

Chromium 使用：

```js
DataTransferItem.webkitGetAsEntry()
```

递归目录时必须：

- 对 `DirectoryReader.readEntries()` 循环调用直到返回空数组；
- 限制最大目录深度和最大条目数，防止浏览器卡死；
- 定期让出事件循环，避免大量文件解析时页面无响应；
- 处理读取异常和权限异常；
- 不依赖或上传客户端绝对路径。

推荐规范化结果：

```js
{
  file,
  relativePath: '顶层目录/子目录/文件.pdf',
  rootName: '顶层目录',
}
```

不要使用 `Object.defineProperty` 强行修改浏览器只读的 `File.webkitRelativePath`。应让 `FolderUploadStore` 和 `FolderStructureBuilder` 通过统一辅助函数读取：

```js
getEntryFile(entry)       // entry.file 或 File 本身
getEntryRelativePath(entry)
```

这样按钮选择的 `File[]` 和拖入的规范化条目都能走同一条文件夹流程。

### 6.3 混合拖入

同一批包含普通文件和多个顶层文件夹时：

1. 按顶层来源分组；
2. 普通文件作为一个批次进入捕获时的当前目录；
3. 每个顶层文件夹依次创建目录结构并分批入队；
4. 某一个顶层文件夹结构创建失败只回滚该文件夹本次已创建结构，不影响其他顶层文件夹和普通文件；
5. 文件真正上传仍由现有 `UploadCoordinator` 按压力等级调度；
6. 不要在目录解析层自行并发上传。

### 6.4 浏览器兼容

- Chrome/Edge：支持普通文件和目录拖入；
- Firefox/Safari：必须支持普通文件拖入；目录能力不可用时提示使用现有“上传文件夹”按钮；
- 点击“上传文件夹”的 `webkitdirectory` 行为保持不变。

## 七、状态展示：复用现有传输列表

本任务**不新增拖拽专用状态列表**。

拖拽生命周期分两段：

```text
文件进入 Explorer

  -> 用户展开现有 UploadPanel 查看：
```

- 不额外弹出新的 Drawer、Modal、浮窗或底部条；
- 不自动展开现有 UploadPanel；
- 继续支持现有暂停、继续、取消、全部暂停、失败重试和传输记录；
- 目录解析阶段如耗时明显，可在遮罩内显示“正在读取文件夹…”，但完成后立即转交现有传输列表。

## 八、权限与党建范围

### 8.1 普通文档管理

- 上传权限：`document.document.upload`；
- 创建文件夹权限按项目当前规则校验；
- 私人目录使用捕获时 `tenantId`；
- 公共共享库使用捕获时 `isPublic=true`；
- 不允许因为页面切换把私人文件上传到公共库，反之亦然。

### 8.2 党建文档

- 上传权限：`document.party_building_document.upload`；
- 创建文件夹权限：沿用 `document.party_building_document.create_folder` 和后端现有规则；
- 必须等待 `lockedRootFolderId` 初始化；
- `folderId` 必须位于党建锁定根目录内；
- 所有请求携带 `system_folder=party_building_documents`；
- 后端继续拒绝越过党建根目录的目标；
- 只有普通资料库权限、没有党建权限的用户不能通过拖拽上传；
- 离开党建页面后，既有党建上传任务继续保持正确上下文，但新进入普通资料库的上传任务不得继承党建上下文。

## 十、关键流程

### 10.1 普通文件拖入

```text
外部 Files 进入 explorerArea
  -> 检查权限和页面状态
  -> 显示目标目录遮罩
  -> drop 时捕获不可变 targetContext
  -> 提取 File[]
  -> refreshPressure 一次
  -> handleFileSelect(files, targetContext)
  -> 现有队列自动选择普通/分片上传
  -> MiniBar / UploadPanel 展示状态
```

### 10.2 文件夹拖入

```text
外部目录进入 explorerArea
  -> drop 时立即捕获 targetContext
  -> webkitGetAsEntry 递归读取
  -> 生成 {file, relativePath, rootName}
  -> 路径和条目数校验
  -> handleFolderEntries(entries, targetContext)
  -> FolderStructureBuilder 创建目录
  -> FileUploadCoordinator 分批入队
  -> 现有动态并发上传
  -> MiniBar / UploadPanel 展示状态
```

### 10.3 党建文档任务离开页面

```text
在党建文档 drop
  -> targetContext.systemFolderCode = party_building_documents
  -> 每个队列项保存 systemFolderCode
  -> 用户离开党建页面
  -> 全局页面上下文被清理
  -> 未开始的党建任务仍从队列项读取 systemFolderCode
  -> transfer / upload / chunk / merge 请求显式携带 system_folder
  -> 后端继续验证并写入党建范围
```

## 十一、安全和稳定性要求

### 11.1 前端

- 只处理 `Files` 类型；
- 不上传客户端绝对路径；
- 相对路径拒绝 `..`、绝对路径、空字节和异常分隔符；
- 目录递归最大深度建议 20；
- 单次解析最大条目数建议 5000，超过时停止并提示；
- 大批文件解析定期让出事件循环；
- 不把 `File` 对象持久化到 localStorage/sessionStorage；
- 避免重复 drop 造成重复任务；
- 组件卸载后不更新已卸载组件状态；
- 不破坏现有队列中的非枚举 File 引用和内存清理策略。

### 11.2 后端

- 不信任前端的 `folderId/isPublic/tenantId/system_folder`；
- 每个请求重新校验用户、租户、空间和系统目录权限；
- 党建目标必须位于锁定根目录；
- 文件夹相对路径必须再次做路径穿越校验；
- 分片和合并必须绑定同一 transfer、用户、租户和系统目录上下文；
- 多账号同时上传同名文件不能互相覆盖或复用错误 transfer；
- 不把前端并发控制当作服务器安全边界。

### 12.4 人工验收：文档管理

- 在私人根目录和子目录分别拖入单个、多文件；
- 在公共共享库拖入文件；
- 拖入大文件，确认进入分片上传并可暂停/恢复；
- 拖入嵌套文件夹，确认目录结构和文件数量一致；
- 混合拖入文件和多个文件夹；
- drop 后立即切换目录，确认仍上传到原目录；
- 搜索状态、无权限状态不能上传；
- 点击上传文件/文件夹保持原行为；

### 12.5 人工验收：党建文档

- 使用党建上传权限拖入普通文件和文件夹；
- 只有普通文档上传权限的账号不能拖入党建文档；
- 初始化未完成时不能上传；
- 根目录和子目录任务都不能越过党建锁定根；

### 12.6 多账号并发验收

- 至少 2 个账号在不同浏览器会话中同时上传普通文件和大文件；
- 两个账号的队列、transfer、目录和租户归属互不串用；
- 一个账号在党建文档上传，另一个在普通/公共资料库上传，系统目录上下文互不污染；
- 继续沿用现有服务器压力接口和动态并发，不为拖拽另建并发控制。
