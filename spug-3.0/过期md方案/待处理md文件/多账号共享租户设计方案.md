# 多账号共享租户设计方案

> 目标：让多个账号看到相同的内容，通过让多个账号的 `tenant_id` 相同实现数据共享

---

## 一、当前租户体系现状

### 1.1 核心架构

```
┌───────────────────────────────────────────────────────────────────────────┐
│                           请求流程                                        │
│                                                                           │
│  Request → AuthenticationMiddleware (设置 request.user)                   │
│         → View (显式调用 apply_tenant_filter)                             │
│             ↓                                                             │
│         ┌──────────┬──────────────┬──────────────┬───────────────┐        │
│         │ 超级管理 │ 全局管理员   │ 租户管理员   │ 普通用户      │        │
│         │ 员       │              │ (新增)       │               │        │
│         ├──────────┼──────────────┼──────────────┼───────────────┤        │
│  数据   │ 看所有   │ 看所有租户   │ 看本租户     │ 看本租户      │        │
│ 可见性  │ 数据     │ 数据         │ 数据         │ 数据          │        │
│         ├──────────┼──────────────┼──────────────┼───────────────┤        │
│ 用户    │ 创建任意 │              │ 创建/管理    │               │        │
│ 管理    │ 租户用户 │ 禁止         │ 本租户用户   │ 禁止          │        │
│         ├──────────┼──────────────┼──────────────┼───────────────┤        │
│ 写入    │ 可指定   │ tenant_id=   │ tenant_id=   │ tenant_id=    │        │
│ tenant  │ 任意租户 │ user.tenant  │ user.tenant  │ user.tenant   │        │
│         └──────────┴──────────────┴──────────────┴───────────────┘        │
│                                                                           │
│  当前: tenant_id = username (每用户独立租户)                              │
│  目标: tenant_id 可指定，多用户共享同一 tenant_id                          │
│                                                                           │
│  说明: "租户管理员"不是一个新字段，而是拥有 system.account 权限的非超管用户    │
│        全局管理员(is_global_admin)的职责是数据可见性，可查看所有租户数据       │
└───────────────────────────────────────────────────────────────────────────┘
```

### 1.2 现状问题

| 项目 | 现状 | 问题 |
|------|------|------|
| 用户创建 | `tenant_id = username` 硬编码 | 每个用户独占一个租户空间 |
| 用户管理权限 | `AdminView` 仅允许超管访问 | 非超管无法创建同租户用户 |
| 功能权限配置 | `codes.js` 无"系统设置"模块 | 无法通过角色配置用户管理权限 |
| 租户管理 | 无管理界面 | 无法分配/修改用户租户 |
| 数据隔离 | 按 `tenant_id` 过滤 | 同 `tenant_id` 即可共享，架构已支持 |
| 迁移工具 | `migrate_existing_data` 已定义 | 本方案不使用（新用户直接指定已有租户名即可） |

### 1.3 架构已有的多用户同租户支持

以下函数已存在于 `libs/tenant_utils.py`，但本方案不需要使用：

- `get_all_tenant_users(tenant_id)` — 查询同租户的所有用户
- `get_tenant_stats()` — 统计各租户的用户数量
- `migrate_existing_data(tenant_id_map)` — 批量将用户分配到指定租户

**结论：架构层面已完全支持多用户共享同一租户，只需修改赋值逻辑和权限控制。新用户创建时直接指定已有租户名即可共享，无需数据迁移。**

## 三、修改方案（3步）

> **核心设计决策**：
> - `is_global_admin`（全局管理员）的职责是**数据可见性**（查看所有租户数据），不涉及用户管理权限
> - "租户管理员"通过**功能权限**（`system.user`）实现，而非新增字段
> - 非超管创建用户时**强制继承创建者的 `tenant_id`**，防止越权指定其他租户

### 第一步：新增"系统设置"权限 + 修改访问控制

> **为什么需要这一步**：当前 `AdminView` 仅允许超管（`is_supper=True`）访问用户管理接口，非超管无法创建同租户用户。多账号共享租户的核心场景是"团队负责人拉人进团队"，每次都找超管不现实。同时需实现细粒度权限控制，仅有"查看"权限的用户不能执行增删改操作。

#### 1.1 前端权限配置 — 新增"系统设置"模块

**文件：`spug_web/src/pages/system/role/codes.js`**

在末尾 `}` 前新增：

```js
, {
  key: 'system',
  label: '系统设置',
  pages: [{
    key: 'user',
    label: '用户管理',
    perms: [
      {key: 'view', label: '查看用户'},
```

#### 1.2 后端访问控制 — 修改 AdminView

**文件：`spug_api/libs/mixins.py`**

当前代码：

```python
class AdminView(View):
    def dispatch(self, request, *args, **kwargs):
        if hasattr(request, 'user') and request.user.is_supper:
            return super().dispatch(request, *args, **kwargs)
        else:
            return json_response(error='权限拒绝')
```

修改为：

```python
class AdminView(View):
    # 权限键映射：HTTP方法 → 需要的权限
    PERM_MAP = {
        'GET': 'system.account.view',
        'POST': 'system.account.add',
        'PATCH': 'system.account.edit',
        'DELETE': 'system.account.del',
    }

    def dispatch(self, request, *args, **kwargs):
        if hasattr(request, 'user'):
            # 超管：放行
            if request.user.is_supper:
                return super().dispatch(request, *args, **kwargs)
            # 非超管：按操作类型校验细粒度权限
            perm_key = self.PERM_MAP.get(request.method)
            if perm_key and request.user.has_perms({perm_key}):
                return super().dispatch(request, *args, **kwargs)
        return json_response(error='权限拒绝')
```

#### 1.3 用户管理操作 — 租户范围限制

**文件：`spug_api/apps/account/views.py`**

在 `UserView` 的各方法中，非超管只能操作本租户用户：

**get 方法** — 非超管只返回本租户用户：

```python
def get(self, request):
    show_deleted = request.GET.get('show_deleted') == 'true'
    users = []
    if show_deleted:
        queryset = User.objects.filter(deleted_by_id__isnull=False)
    else:
        queryset = User.objects.filter(deleted_by_id__isnull=True)
    # 非超管只能查看本租户用户
    if not request.user.is_supper:
        queryset = queryset.filter(tenant_id=request.user.tenant_id)
    for u in queryset:
        tmp = u.to_dict(excludes=('access_token', 'password_hash'))
        tmp['role_ids'] = [x.id for x in u.roles.all()]
        tmp['password'] = '******'
        users.append(tmp)
    return json_response(users)
```

**post 方法** — 非超管强制 tenant_id 继承，详见第二步。

**patch 方法** — 非超管只能修改本租户用户，且禁止修改 tenant_id：

```python
def patch(self, request):
    form, error = JsonParser(
        Argument('id', type=int, help='参数错误'),
        Argument('password', required=False),
        Argument('is_active', type=bool, required=False),
        Argument('tenant_id', required=False),  # 仅超管可修改
    ).parse(request.body)
    if error is None:
        user = User.objects.get(pk=form.id)
        # 非超管只能操作本租户用户
        if not request.user.is_supper and user.tenant_id != request.user.tenant_id:
            return json_response(error='无权操作其他租户的用户')
        # 非超管禁止修改 tenant_id
        if not request.user.is_supper and form.tenant_id:
            return json_response(error='无权修改用户租户')
        # 超管修改 tenant_id 时，同步更新该用户的历史数据租户归属
        if request.user.is_supper and form.tenant_id and form.tenant_id != user.tenant_id:
            from libs.tenant_utils import migrate_existing_data
            migrate_existing_data({user.username: form.tenant_id})
        user.update_by_dict(form)
        # ... 后续逻辑不变
```

**delete 方法** — 非超管只能删除本租户用户：

```python
def delete(self, request):
    form, error = JsonParser(
        Argument('id', type=int, help='请指定操作对象')
    ).parse(request.GET)
    if error is None:
        user = User.objects.filter(pk=form.id).first()
        if user:
            # 非超管只能操作本租户用户
            if not request.user.is_supper and user.tenant_id != request.user.tenant_id:
                return json_response(error='无权操作其他租户的用户')
            if user.id == request.user.id:
                return json_response(error='无法删除当前登录账户')
            # ... 后续逻辑不变
```

**权限矩阵：**

```
┌──────────┬──────────────────────────────────────────────┐
│ 操作     │ 超管        │ 有用户管理权限  │ 无权限用户  │
│          │             │ 的非超管        │             │
├──────────┼─────────────┼────────────────┼─────────────┤
│ 创建用户 │ 任意租户    │ 仅本租户       │ 禁止       │
│ 查看用户 │ 所有用户    │ 本租户用户     │ 禁止       │
│ 修改用户 │ 任意用户    │ 本租户用户     │ 禁止       │
│ 删除用户 │ 任意用户    │ 本租户用户     │ 禁止       │
│ 租户赋值 │ 可指定任意  │ 强制=自身租户  │ —          │
└──────────┴─────────────┴────────────────┴─────────────┘
```

修改为：

```python
def post(self, request):
    form, error = JsonParser(
        Argument('id', type=int, required=False),
        Argument('username', help='请输入登录名'),
        Argument('password', help='请输入密码'),
        Argument('nickname', help='请输入姓名'),
        Argument('role_ids', type=list, default=[]),
        Argument('wx_token', required=False),
        Argument('tenant_id', required=False, default=None),  # 新增：允许指定租户
    ).parse(request.body)
    if error is None:
        # ...省略...
        if form.id:
            user = User.objects.get(pk=form.id)
            # 非超管只能编辑本租户用户
            if not request.user.is_supper and user.tenant_id != request.user.tenant_id:
                return json_response(error='无权编辑其他租户的用户')
            # 非超管禁止修改 tenant_id
            if not request.user.is_supper and 'tenant_id' in form:
                del form['tenant_id']
            # 超管修改 tenant_id 时，同步迁移历史数据
            if request.user.is_supper and form.tenant_id and form.tenant_id != user.tenant_id:
                from libs.tenant_utils import migrate_existing_data
                migrate_existing_data({user.username: form.tenant_id})
            user.update_by_dict(form)
        else:
            if not verify_password(password):
                return json_response(error='请设置至少8位包含数字、小写和大写字母的新密码')
            # 【修改】租户ID赋值逻辑
            if request.user.is_supper:
                # 超管：可指定任意租户，未指定则用用户名（向后兼容）
                tenant_value = form.tenant_id or form.username
                # 租户ID合法性校验
                import re
                if not re.match(r'^[a-zA-Z0-9_\-]{1,50}$', tenant_value):
                    return json_response(error='租户ID仅支持字母、数字、下划线、横线，长度1-50')
            else:
                # 非超管：强制继承创建者的 tenant_id，忽略前端传入值
                tenant_value = request.user.tenant_id
            user = User.objects.create(
                password_hash=User.make_password(password),
                created_by=request.user,
                tenant_id=tenant_value,
                **{k: v for k, v in form.items() if k not in ('tenant_id', 'password', 'role_ids')}
            )
```

**租户赋值逻辑：**

```
超管创建用户：
  - 前端传了 tenant_id → 使用传入值（可指定任意租户）
  - 前端未传 tenant_id → 使用用户名（向后兼容）

非超管创建用户（需有 system.account.add 权限）：
  - 强制 tenant_id = request.user.tenant_id（忽略前端传入，防止越权）
  - 效果：新建用户自动与创建者共享同一租户
```

## 四、关键注意事项

### 4.1 超级管理员的数据归属（P1 — 共享租户场景下必须修复）

**问题**：超级管理员创建的记录 `tenant_id` 为空（因为 `if not is_supper` 跳过了设置），普通用户看不到。在共享租户场景下，超管经常需要帮团队创建数据，这是必须修复的。

**修复**：各业务模块的创建逻辑中，超管也设置 `tenant_id`：

```python
# 当前代码（exec/views.py 等）
if not getattr(request.user, 'is_supper', False):
    form.tenant_id = getattr(request.user, 'tenant_id', 'admin')

# 修改为
form.tenant_id = getattr(request.user, 'tenant_id', 'admin')
```

即：**管理员也设置 `tenant_id`**，确保创建的数据属于其租户。管理员通过 `apply_tenant_filter` 的"超管不过滤"规则仍能查看所有数据。

### 4.2 物理文件路径

资料库私有空间路径格式为 `private/user-{id}/`，按用户ID隔离存储。

- 合并租户后，同租户用户能**看到**彼此的文件记录（数据库查询共享）
- 物理文件仍按用户ID隔离存储（安全性不受影响）
- 不建议合并物理文件路径，原因：
  - 改动量大，需迁移已有文件
  - 用户ID隔离更安全，防止误删

### 4.3 缓存自动清理

排班模块缓存 Key 格式为 `schedule:{model_name}:{tenant_id}`。超管修改用户租户时，必须自动清理相关缓存，否则排班页面会显示旧数据。

已在第二步 `patch` 方法的租户迁移逻辑中集成自动缓存清理：

```python
# 超管修改 tenant_id 时，自动迁移历史数据 + 清理缓存
if request.user.is_supper and form.tenant_id and form.tenant_id != user.tenant_id:
    from libs.tenant_utils import migrate_existing_data
    migrate_existing_data({user.username: form.tenant_id})
    # 自动清理排班缓存
    from apps.schedule.cache_utils import invalidate_schedule_cache
    invalidate_schedule_cache(tenant_id=form.tenant_id)
```

### 4.4 checksheet 模块

完全没有 `tenant_id`，所有用户共享数据，不受租户合并影响。

### 4.5 公共空间

`DocumentFolderPublic` / `DocumentFilePublic` 无 `tenant_id`，所有用户共享，不受影响。

### 4.6 租户 ID 合法性校验

**后端校验**（在 `UserView.post` 中添加）：

```python
import re

# 租户ID格式校验

```

**前端限制**：超管租户输入框做相同格式限制，输入时实时校验。

### 4.7 权限细粒度控制

`AdminView` 按 HTTP 方法映射权限（已在第一步 1.2 中实现）：

| HTTP 方法 | 权限键 | 说明 |
|-----------|--------|------|
| GET | `system.account.view` | 查看用户列表 |
| POST | `system.account.add` | 创建用户 |
| PATCH | `system.account.edit` | 编辑用户 |
| DELETE | `system.account.del` | 删除用户 |

仅有"查看用户"权限的用户无法调用创建/编辑/删除接口。

### 4.8 数据库索引优化

`User.tenant_id` 是高频查询字段（每次用户列表查询都会按租户过滤），建议添加索引：

```python
# apps/account/models.py — User 模型
tenant_id = models.CharField(max_length=50, db_index=True, ...)
```

### 4.9 权限与数据可见性分离

**关键原则**：

- `is_global_admin`（全局管理员）= **数据可见性**，可查看所有租户的数据
- `system.user` 权限 = **用户管理操作权**，可管理同租户用户
- 两者**独立**，全局管理员不自动获得用户管理权限，有用户管理权限的非超管也不自动看到其他租户数据

**前端适配**：

- 非超管用户创建表单中，"所属租户"字段应**隐藏或只读显示**（显示当前用户的租户名）
- 只有超管的表单才显示"所属租户"的输入/选择控件

### 4.10 全局管理员与租户管理员组合

两者可以同时勾选，不会冲突。组合效果：

| 角色组合 | 数据可见性 | 用户管理范围 |
|---------|-----------|-------------|
| 仅全局管理员 | 所有租户数据 | 禁止 |
| 仅租户管理员 | 本租户数据 | 本租户用户 |
| **全局管理员 + 租户管理员** | **所有租户数据** | **仅本租户用户** |
| 超管 | 所有数据 | 所有用户 |

> **注意**：同时勾选时会出现体验上的不对称 — 能看到所有租户的数据，但用户管理只能操作本租户用户。这是正确的安全设计（权限按"各自独立约束"生效），但可能让用户困惑。
>
> **建议**：前端角色配置页面，当同时勾选"全局管理员"和"用户管理"权限时，显示提示信息："该角色可查看所有租户数据，但用户管理仅限本租户范围"。

## 八、实现审查问题清单

> 以下为对照设计方案审查实际代码后发现的问题，暂不修改，仅记录。

### 问题1：权限键命名不一致（方案写 `system.user`，实际用 `system.account`）✅ 已修复

**文件**：`codes.js`、`views.py`、`mixins.py`

**现状**：方案文档中所有权限键已统一更新为 `system.account.view/add/edit/del`，与实际代码一致。

### 问题2：`interference/views.py` 的编辑和删除操作使用 `tenant_id` 过滤但未使用 `apply_tenant_filter`

**文件**：`spug_api/apps/interference/views.py` 第67-69行、第85-86行

**现状**：
```python
# 编辑操作
tenant_id = getattr(request.user, 'tenant_id', '')
updated_count = Interference.objects.filter(pk=record_id, tenant_id=tenant_id).update(**form)

# 删除操作
tenant_id = getattr(request.user, 'tenant_id', '')
deleted_count, _ = Interference.objects.filter(pk=form.id, tenant_id=tenant_id).delete()
```

**问题**：
1. 超管编辑/删除干扰记录时也被限制在本租户，因为 `tenant_id` 直接取 `request.user.tenant_id`，超管无法操作其他租户的干扰记录
2. 未使用 `apply_tenant_filter` 统一过滤，而是手动拼接 `tenant_id`，与其他模块风格不一致
3. `tenant_id` 默认值是 `''`（空字符串），而不是 `'admin'`，与其他模块不一致

### 问题3：`device/views.py` 第265行使用了不存在的 `is_superuser` 属性

**文件**：`spug_api/apps/device/views.py` 第265行

**现状**：
```python
if record.tenant_id == '' and not request.user.is_superuser:
```

**问题**：User 模型中没有 `is_superuser` 属性，正确属性名是 `is_supper`。这会导致删除全局设备时权限检查失效——`request.user.is_superuser` 始终为 `False`（Django 的 `AttributeError` 被 `not` 吞掉变为 `True`），即所有非超管用户都无法删除全局设备，即使有权限也不行。

### 问题4：`device/views.py` 创建设备时 `tenant_id` 为空字符串的问题

**文件**：`spug_api/apps/device/views.py` 第116行

**现状**：
```python
tenant_id = request.user.tenant_id if hasattr(request.user, 'tenant_id') else ''
```

**问题**：默认值是 `''`（空字符串），而不是 `'admin'`。当超管（`tenant_id` 为 `'admin'`）创建设备时没问题，但如果 User 对象因某种原因没有 `tenant_id` 属性，会赋空字符串，导致该设备成为"全局设备"，其他租户用户也看不到。

### 问题5：`migrate_existing_data` 迁移 `tenant_id=''` 的记录可能遗漏 `tenant_id=NULL` 的记录

**文件**：`spug_api/libs/tenant_utils.py` 第262行

**现状**：
```python
records = model.objects.filter(tenant_id='').select_related('created_by')
```

**问题**：只查找 `tenant_id=''` 的记录，不查找 `tenant_id IS NULL` 的记录。如果数据库中存在 `tenant_id` 为 NULL 的数据（如直接通过 SQL 插入），这些记录不会被迁移。

### 问题6：`_migrate_user_tenant` 只清理了新租户的排班缓存，未清理旧租户的

**文件**：`spug_api/apps/account/views.py` 第188-197行

**现状**：
```python
@staticmethod
def _migrate_user_tenant(user, new_tenant_id):
    migrate_existing_data({user.username: new_tenant_id})
    try:
        from apps.schedule.cache_utils import invalidate_schedule_cache
        invalidate_schedule_cache(tenant_id=new_tenant_id)
    except ImportError:
        pass
```

**问题**：用户从租户A迁移到租户B时，只清理了租户B的缓存，租户A的缓存中仍包含该用户的数据（如排班记录），其他租户A的用户可能看到已不属于他们的数据。

### 问题7：前端 `Form.js` 非超管新建用户时不显示租户字段

**文件**：`spug_web/src/pages/system/account/Form.js` 第77-81行

**现状**：
```jsx
{!isSupper && store.record.tenant_id && (
  <Form.Item label="所属租户">
    <Input value={store.record.tenant_id} disabled/>
  </Form.Item>
)}
```

**问题**：新建用户时 `store.record` 是空对象 `{}`，`store.record.tenant_id` 为 `undefined`，条件 `!isSupper && store.record.tenant_id` 为 `false`，所以非超管新建用户时完全不显示租户字段。用户不知道自己创建的用户属于哪个租户。

**建议**：新建时也应该显示当前用户的租户（只读），让用户知道新用户会归属哪个租户。

### 问题8：`AdminView` 默认空 `PERM_MAP` 导致 `RoleView`/`HistoryView` 等只允许超管访问

**文件**：`spug_api/libs/mixins.py` 第28-43行

**现状**：`AdminView` 默认 `PERM_MAP = {}`，非超管访问时 `if self.PERM_MAP:` 为 `False`，直接返回"权限拒绝"。`RoleView`、`HistoryView` 等继承 `AdminView` 的类都受此影响。

**问题**：这是设计意图（只有超管能管理角色和查看登录历史），但与方案之前的逻辑一致。如果未来需要非超管也能查看角色列表（如选择角色），需要在 `RoleView` 中添加 `PERM_MAP`。

### 问题9：`login` 返回信息中缺少 `tenant_id`

**文件**：`spug_api/apps/account/views.py` 第362-369行

**现状**：
```python
return json_response({
    'id': user.id,
    'access_token': user.access_token,
    'nickname': user.nickname,
    'is_supper': user.is_supper,
    'has_real_ip': ...,
    'permissions': [] if user.is_supper else list(user.page_perms)
})
```

**问题**：登录响应中没有返回 `tenant_id`，前端无法在 localStorage 中存储。当前 `store.js` 通过 `localStorage.getItem('is_supper')` 判断是否超管，但如果需要在前端其他地方使用 `tenant_id`（如显示当前用户所属租户），则无法获取。

### 问题10：`upgrade/views.py` 和 `runlog/views.py` 未使用 `assign_tenant_id` 统一赋值 ✅ 已修复

**文件**：`spug_api/apps/upgrade/views.py`、`spug_api/apps/runlog/views.py`

**现状**：这两个模块仍使用 `tenant_id = getattr(request.user, 'tenant_id', 'admin')` 手动赋值，而不是使用 `assign_tenant_id`。

**影响**：功能上没有问题（超管也会设置 tenant_id），但与其他模块（exec、interference、schedule）的 `assign_tenant_id` 风格不一致，增加维护成本。

### 问题11：方案文档全局管理员数据可见性描述与代码不一致 ✅ 已修复

**文件**：方案文档、`tenant_utils.py`

**原问题**：代码中全局管理员按租户过滤，只能看本租户数据，但文档写"可查看所有租户数据"。

**修复**：修改 `apply_tenant_filter` 使全局管理员在非严格模式下跳过租户过滤，与文档描述一致。全局管理员具备与超管相同的数据可见性，但不具备用户管理权限。
