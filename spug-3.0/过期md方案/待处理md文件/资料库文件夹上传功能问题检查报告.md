# 资料库文件夹上传功能问题检查报告

## 检查日期
2026-04-02

## 概述
本报告针对资料库模块的**文件夹上传功能**进行全面代码审查，识别潜在问题和风险点。

---

## 一、架构设计缺陷

### 【P0】问题1：双轨制架构（代码分叉）

**位置**：整体架构层面

**问题描述**：
代码库显示出明显的**"代码分叉"**迹象：
- **普通上传**：经过精心设计的状态机流程（`FileUploadCoordinator` → `StateMachine` → 上传执行）
- **文件夹上传**：走了一遍"脚本式"的直连流程（`folderUpload.js` 直接调用上传方法）

**架构对比**：
```
普通文件上传：
FileSelect → FileUploadCoordinator.processUploadQueue() 
    → 创建 StateMachine → 统一队列管理 → 状态流转控制 → 执行上传

文件夹文件上传：
FolderSelect → FolderUploadStore.handleFolderSelect()
    → 直接调用 uploadFileToFolder() → 独立处理逻辑
```

**深层风险**：
1. **维护成本倍增**：任何上传逻辑的修改需要在两处同步
2. **行为不一致**：暂停/恢复/重试等功能在两个流程表现不同
3. **测试覆盖困难**：需要分别测试两种上传路径

**治本之策**：
将 `folderUpload` 彻底重构为 `FileUploadCoordinator` 的一个**预处理步骤**：
```
文件夹解析 → 扁平化为文件队列 → 注入统一 Coordinator 消费
```

## 二、已确认的问题

### 【P1】问题2：传输记录重复创建

**位置**：
- `spug_web/src/pages/document/stores/upload/core/coordinators/FileUploadCoordinator.js` 第116-124行
- `spug_web/src/pages/document/stores/upload/core/fileUpload.js` 第242-259行

**问题描述**：
文件夹上传时，每个文件会**创建两次传输记录**：
1. 第一次在 `FileUploadCoordinator.processUploadQueue` 中创建（用于状态机）
2. 第二次在 `fileUploadStore.uploadFileToFolder` 中创建（用于实际上传）

**代码片段**：
```javascript
// FileUploadCoordinator.js
const transferId = await this.core.transferStore.createTransfer({
  transfer_type: 'upload',
  file_name: file.name,
  file_size: file.size,
  is_public: isPublic,
  total_chunks: estimatedChunks,
  file_hash: '',
  ...(folderId !== null && { folder_id: folderId })
});

// fileUpload.js (uploadFileToFolder)
transferId = await this.rootStore.transferStore.createTransfer({
  transfer_type: 'upload',
  file_name: file.name,
  file_size: file.size,
  is_public: targetIsPublic,
  total_chunks: totalChunks,
  folder_id: targetFolderId,
});
```

**影响**：
- 数据库中会产生重复的传输记录
- 传输列表显示重复任务
- 造成数据混乱，难以追踪真实上传状态

**修复建议**：
**重要**：在修改前需确认 `uploadFileToFolder` 是否被**其他场景**直接调用：
- [ ] 检查拖拽上传是否直接调用
- [ ] 检查是否有移动端 API 直接调用
- [ ] 检查是否有其他组件直接调用

确认安全后，删除 `uploadFileToFolder` 中的传输记录创建代码。

> **关键确认**：文件夹上传的文件，**必须全部通过 Coordinator 创建 transfer**，不再独立创建。确保文件夹上传的每个文件都走 `FileUploadCoordinator.processUploadQueue()` 统一入口，而非直接调用 `uploadFileToFolder()`。

### 【P1】问题3：状态机缺失导致的数据一致性风险

**位置**：
- `spug_web/src/pages/document/stores/upload/core/folderUpload.js`

**问题描述**：
普通文件上传通过 `FileUploadCoordinator.processUploadQueue` 创建状态机进行状态管理，但文件夹上传直接调用 `uploadFileToFolder`，**没有创建状态机**。

**代码片段**：
```javascript
// FileUploadCoordinator.js - 普通上传会创建状态机
if (this.core.stateMachineManager) {
  this.core.stateMachineManager.create(uploadId, {...});
}

// folderUpload.js - 文件夹上传没有状态机
await this.fileUploadStore.uploadFileToFolder(file, targetId, folderPath, isPublic);
```

**深层风险**：
1. **幂等性缺失**：在高并发或网络抖动情况下，没有状态机的"幂等性保护"和"状态流转校验"，直接调用 `uploadFileToFolder` 可能导致文件被重复上传
2. **断点续传失效**：断点续传时无法正确识别文件状态，可能导致文件拼接错误
3. **状态竞争**：多个文件同时上传时，状态管理混乱

**架构建议**：
**根治方案**：将 `folderUpload.js` 的逻辑彻底废弃，将文件夹"扁平化"为文件列表，**全部注入** `FileUploadCoordinator` 的队列中处理。

### 【P2】问题4：total_chunks 计算不一致

**位置**：
- `FileUploadCoordinator.js` 第114行
- `fileUpload.js` 第245-247行

**问题描述**：
两个地方计算分片数的方式有差异：

```javascript
// FileUploadCoordinator.js
const estimatedChunks = Math.ceil(file.size / UPLOAD_CONSTANTS.CHUNK_SIZE) || 1;

// fileUpload.js
const totalChunks = file.size > UPLOAD_CONSTANTS.NORMAL_UPLOAD_THRESHOLD
  ? Math.ceil(file.size / UPLOAD_CONSTANTS.CHUNK_SIZE)
  : 1;
```

**影响**：
- 小文件（<32MB但>0字节）在两种计算方式下结果可能不同
- 可能导致传输记录的 `total_chunks` 与实际不符

**修复建议**：
**中期方案**：抽离一个纯函数 `calculateUploadMeta(file)` 来统一计算 `total_chunks`、`fileHash` 等元数据。

```javascript
// utils/upload-meta.js
export function calculateUploadMeta(file) {
  const totalChunks = Math.ceil(file.size / UPLOAD_CONSTANTS.CHUNK_SIZE) || 1;
  const needsChunking = file.size > UPLOAD_CONSTANTS.NORMAL_UPLOAD_THRESHOLD;
  return { totalChunks, needsChunking, fileSize: file.size };
}
```

### 【P2】问题5：fileHash 时序问题（"先有鸡还是先有蛋"）

**位置**：
- `chunkUpload.js` 第39-64行
- `chunkUpload.js` 第70-79行

**问题描述**：
代码采用"先创建记录，后补 hash"的策略：

```javascript
// 1. 先创建传输记录（hash为空）
transferId = await this.rootStore.transferStore.createTransfer({
  file_hash: '',  // 空hash
  ...
});

// 2. 异步计算 hash
fileHash = await this.rootStore.md5Store?.calculateFileMD5(file, uploadId);

// 3. 后补 hash
await this.rootStore.transferStore.updateTransferFileHash(item.transferId, fileHash);
```

**深层风险**：
- **时间窗口风险**：如果用户在 hash 计算完成前刷新页面，断点续传信息会丢失
- **秒传失效**：无法利用 hash 实现秒传判断

**架构建议**：
**长期方案**：将 hash 计算前置到 **Web Worker 线程**，拿到 hash 后再创建传输记录。

```javascript
// 伪代码
const fileHash = await computeHashInWorker(file);
const transferId = await createTransfer({ file_hash: fileHash }); // 有hash后创建
```

**短期补丁**：若无法立即使用 Worker，至少增加**中断恢复标记**，避免 hash 未计算完成导致续传失败。

```javascript
// 在 localStorage 或 IndexedDB 中保存计算状态
const hashProgressKey = `hash_progress_${file.name}_${file.size}`;
localStorage.setItem(hashProgressKey, JSON.stringify({
  transferId: transferId,
  status: 'calculating',
  timestamp: Date.now()
}));

// hash 计算完成后更新
localStorage.setItem(hashProgressKey, JSON.stringify({
  transferId: transferId,
  status: 'completed',
  fileHash: fileHash,
  timestamp: Date.now()
}));

// 页面恢复时检查
const savedProgress = localStorage.getItem(hashProgressKey);
if (savedProgress) {
  const progress = JSON.parse(savedProgress);
  if (progress.status === 'completed') {
    // 使用已计算的 hash 恢复上传
    fileHash = progress.fileHash;
  }
}
```

### 【P2】问题6：文件夹创建缺少事务保护

**位置**：
- `spug_web/src/pages/document/stores/upload/core/folderUpload.js` 第131-179行

**问题描述**：
创建文件夹结构时，每个文件夹是**独立请求**创建的，没有事务保护：

```javascript
// folderUpload.js
createFolderStructure(folderPath, parentFolderId) {
  for (const folderName of paths) {
    // 创建文件夹
    const result = await http.post('/api/document/folder/', params);
    currentParentId = result.id;
  }
}
```

**影响**：
- 如果中途失败，会留下部分创建的文件夹
- 用户需要手动清理失败的残留文件夹

**临时补偿方案（前端）**：
在后端接口完成前，前端必须增加"回滚/清理"机制：

```javascript
// 维护已创建文件夹列表
const createdFolders = [];

try {
  for (const folderName of paths) {
    const result = await http.post('/api/document/folder/', params);
    createdFolders.push(result.id); // 记录已创建
    currentParentId = result.id;
  }
} catch (error) {
  // 失败时主动清理
  for (const folderId of createdFolders) {
    await http.delete(`/api/document/folder/${folderId}/`);
  }
  throw error;
}
```

**长期方案**：
后端提供批量创建文件夹接口，使用数据库事务保证原子性，接口必须支持**幂等键（Idempotency Key）**防止前端重试导致重复创建。

### 【P3】问题8：文件夹创建路径检查不精确

**位置**：
- `spug_web/src/pages/document/stores/upload/core/folderUpload.js` 第144-155行

**问题描述**：
检查文件夹是否已创建时，使用 `Map` 遍历而不是直接查找：

```javascript
// folderUpload.js (O(n))
let existingId = null;
for (const [path, id] of this.rootStore.pendingFolderFiles?.folderMap || []) {
  if (path === currentPath) {
    existingId = id;
    break;
  }
}
```

**修复建议**：
```javascript
// O(1) 直接查找
const existingId = this.rootStore.pendingFolderFiles?.folderMap.get(currentPath);
```

### 【P2】问题9：tenant_id 获取方式不一致（架构反模式）

**位置**：
- `folderUpload.js` 第164-167行

**问题描述**：
直接从 `localStorage` 读取 tenant_id 是典型的**反模式**：

```javascript
const tenantId = isPublic ? null : localStorage.getItem('tenant_id');
if (tenantId != null && tenantId !== '') {
  params.tenant_id = tenantId;
}
```

**架构风险**：
- localStorage 中的 tenant_id 可能被其他操作修改
- 时序问题导致文件夹归属错误

**架构规范建议**：
1. **短期**：从当前登录用户的会话信息中获取 tenant_id
2. **长期**：在 `http` 拦截器层统一注入 `tenant_id`，业务代码中**严禁**出现手动拼接 `tenant_id` 的逻辑

### 【P3】问题10：文件夹上传进度计算不精确

**位置**：
- `folderUpload.js` 第85行

**问题描述**：
文件夹上传进度只统计文件数量，不统计文件大小。

**修复建议**：

### 【P3】问题11：错误分类缺乏工程化

**位置**：
- `folderUpload.js` 第184-222行

**问题描述**：
错误处理没有分类，用户暂停也被计为失败：

```javascript
try {
  await this.fileUploadStore.uploadFileToFolder(...);
  successCount++;
} catch (error) {
  failCount++;  // 用户暂停也计入失败
}
```

**工程化建议**：
定义错误枚举（Error Enums）：

```javascript
// constants/upload-errors.js
export const UploadError = {
  USER_CANCELLED: 'USER_CANCELLED',
  USER_PAUSED: 'USER_PAUSED',
  NETWORK_FAILURE: 'NETWORK_FAILURE',
  SERVER_REJECTED: 'SERVER_REJECTED',
  VALIDATION_ERROR: 'VALIDATION_ERROR',
};

// 使用
if (error.code === UploadError.USER_PAUSED) {
  // 不计入失败
} else if (error.code === UploadError.NETWORK_FAILURE) {
  failCount++;
  // 可重试
}
```

## 三、代码逻辑对比分析

### 普通文件上传 vs 文件夹文件上传

| 特性 | 普通文件上传 | 文件夹文件上传 |
|------|-------------|---------------|
| 架构路径 | 状态机管理 | 直连调用 |
| 传输记录创建 | Coordinator 统一管理 | uploadFileToFolder 独立创建 |
| 状态机管理 | ✅ 有 | ❌ 无 |
| 队列管理 | 统一队列 | 独立处理 |
| 暂停/恢复 | 完整支持 | 部分支持 |
| 断点续传 | 完整支持 | 仅文件级别 |
| 进度显示 | 精确到字节 | 仅文件数量 |
| 幂等性保护 | ✅ 有 | ❌ 无 |

## 四、风险评估

| 风险点 | 等级 | 影响范围 | 说明 |
|--------|------|---------|------|
| 双轨制架构 | P0 | 系统可维护性 | 维护成本倍增，技术债务累积 |
| 传输记录重复 | P1 | 数据库/传输列表 | 数据混乱，用户体验差 |
| 状态机缺失 | P1 | 数据一致性 | 幂等性缺失，可能重复上传 |
| fileHash时序 | P2 | 断点续传 | 刷新后断点续传信息丢失 |
| 文件夹创建无事务 | P2 | 数据一致性 | 可能产生残留数据 |
| tenant_id反模式 | P2 | 安全性 | 归属错误风险 |
| 进度不准确 | P3 | 用户体验 | 用户无法预估时间 |
| 错误分类缺失 | P3 | 可观测性 | 难以统计真实失败率 |

## 五、修复路线图

### 阶段一：立即修复（P0-P1）
1. **解决传输记录重复创建问题**
   - 检查 `uploadFileToFolder` 是否被其他场景直接调用
   - 安全后删除重复创建逻辑

2. **修复双轨制架构（架构层面）**
   - 将文件夹解析为文件队列
   - 统一注入 `FileUploadCoordinator` 处理

### 阶段二：短期修复（2周内）
1. 统一 `total_chunks` 计算逻辑（抽离工具函数）
2. 文件夹创建前端补偿机制（失败回滚）
3. 后端批量创建文件夹接口（事务保护）

### 阶段三：中期优化（1个月内）
1. fileHash 计算前置到 Web Worker
2. 统一 tenant_id 获取方式（拦截器注入）
3. 错误分类工程化（定义错误枚举）

### 阶段四：长期演进
1. 上传元数据计算服务化
2. 全链路幂等性保证
3. 统一上传状态管理中心

## 七、结论

文件夹上传功能虽然基本实现可用，但存在严重的**架构设计缺陷**：

### 核心问题
1. **P0 - 双轨制架构**：普通上传和文件夹上传走完全不同的代码路径，维护成本倍增
2. **P1 - 数据层问题**：传输记录重复创建、状态机缺失导致幂等性缺失
3. **P2 - 架构层问题**：fileHash 时序问题、tenant_id 反模式、文件夹创建无事务
4. **P3 - 体验层问题**：进度计算不精确、错误分类缺失

### 修复优先级
- **立即**：P0/P1 级别问题必须修复后才能上线
- **短期**：P2 级别问题在2周内修复
- **中期**：P3 级别问题在1个月内优化

### 长期建议
彻底重构文件夹上传逻辑，将其纳入统一的上传架构，消除"双轨制"技术债务。
