# 文档与附件拖拽上传设计方案

> 设计日期：2026-07-17  
> 适用范围：资料库文档管理、党建文档、规章管理附件，以及后续接入公共附件组件的业务模块  
> 部署环境：Docker daemon 运行在 WSL 中，项目 Compose 文件为 `docker/docker-compose.yml`

## 一、结论先行

### 1.1 三个模块的当前实现关系

| 模块 | 当前上传入口 | 是否共用资料库上传能力 | 是否使用公共 `AttachmentManager` |
|---|---|---:|---:|
| 资料库文档管理 | `spug_web/src/pages/document/index.js` | 是 | 否 |
| 党建文档 | `PartyBuildingDocumentsIndex -> DocumentIndex` | 是 | 否 |
| 规章管理附件 | `spug_web/src/pages/regulation/Form.js` 内部的 Ant Design `Upload` | 否 | **否** |

结论如下：

1. **资料库和党建文档应当一次实现拖拽上传。** 党建文档只是以 `partyBuildingDocuments` 模式调用同一个 `DocumentIndex`，两者最终都进入 `uploadCoreStore.handleFileSelect` / `handleFolderSelect`，已有的小文件上传、分片上传、断点续传、重复校验、压力调度和上传面板都可以继续复用。
2. **规章管理当前不是通过公共附件组件调用上传。** 它在 `regulation/Form.js` 中自行维护 `attachments`、`uploading`、上传、下载、预览和删除逻辑。因此，现阶段仅修改 `AttachmentManager` 不会让规章管理自动获得拖拽上传。
3. **修改公共 `AttachmentManager` 可以影响一部分其他模块，但不是所有附件上传。** 当前静态调用方包括合同协议、公告、无线电执照、升级工作台等；规章管理、资料库和仍然直接使用 `Upload` 的页面不会自动变化。
4. **不建议把公共组件默认直接改成拖拽模式。** 推荐增加可配置的公共上传区，默认保持原按钮模式，再由规章、合同、公告等模块逐个显式开启。这样可以避免所有调用页面的高度、弹窗布局和多文件队列行为同时发生变化。

## 二、设计目标

### 2.1 必须实现

- 资料库文档管理支持将一个或多个文件拖入当前目录上传。
- 党建文档支持同样的拖拽上传，文件必须落入当前党建系统目录范围。
- 资料库和党建文档保留现有“上传文件 / 上传文件夹”按钮。
- 规章详情的附件区域支持拖入一个或多个附件上传。
- 拖入文件与点击选择文件走同一套校验、权限和后端接口，不新增第二套上传协议。
- 上传任务继续进入现有上传面板，能看到进度、暂停、恢复、取消和错误状态。
- 无上传权限、系统目录未就绪、规章未保存时不能接受文件。
- 单批部分文件失败时，成功文件不能被回滚，失败文件必须明确展示原因并可重试。

### 2.2 本次不做

- 不实现把资料库文件拖到某一行文件夹上并上传到该文件夹。第一版统一上传到页面当前目录，避免误投目录。
- 不改变资料库现有上传、分片、合并和断点续传 API。
- 不把规章附件改存到资料库文档表；规章仍保持独立附件模型和独立生命周期。
- 不依赖浏览器提供本地绝对路径，浏览器也不应向后端暴露本地绝对路径。
- 不允许把页面内部的表格行拖动误判为外部文件上传。

## 三、总体架构

```text
资料库 / 党建文档
  -> DocumentDropUploadLayer（文档区投放层）
     -> collectDroppedEntries（文件/目录解析）
        -> uploadCoreStore.handleFileSelect
        -> uploadCoreStore.handleFolderEntries
           -> 现有普通上传 / 分片上传 / 文件夹结构创建 / 上传队列

规章管理及通用附件模块
  -> AttachmentUploadArea（公共上传原语）
     -> 模块传入的 request(file)
        -> 规章独立附件 API，或其他模块附件 API

公共 AttachmentManager
  -> AttachmentUploadArea
  -> 附件列表 / 预览 / 下载 / 删除
```

这里需要区分两个公共层次：

- `DocumentDropUploadLayer` 服务于资料库类文件系统，处理当前目录、文件夹树、分片上传和上传队列。
- `AttachmentUploadArea` 服务于业务附件，负责投放交互、文件预校验和批次调度，不决定附件存储模型和接口 URL。

二者不应强行合并。资料库上传和业务附件上传的目标对象、目录语义、并发模型及后端协议并不相同。

## 四、资料库与党建文档交互设计

### 4.1 投放区域

拖拽监听范围放在 `DocumentIndex` 的 `.explorerArea`，即文件列表/网格区域，不覆盖左侧目录树、顶部导航和上传面板。

用户把外部文件拖入时，在文档区域内显示全覆盖提示层：

```text
┌──────────────────────────────────────────────┐
│                                              │
│                 [上传图标]                   │
│          松开鼠标，上传到“当前目录”          │
│       支持多文件；文件夹拖入以原结构上传      │
│                                              │
└──────────────────────────────────────────────┘
```

党建文档模式下提示文字显示为：

```text
松开鼠标，上传到“党建文档 / 当前子目录”
```

交互规则：

1. 只有 `dataTransfer.types` 包含 `Files` 时才激活，页面内部普通拖动不触发。
2. 使用 `dragenter` 深度计数处理子元素反复进入/离开，避免遮罩闪烁。
3. `drop`、窗口失焦、组件卸载时必须清空拖拽状态。
4. 拖入期间只展示目标位置，不立即上传；松开后才解析文件并入队。
5. 点击上传入口始终保留，作为键盘操作、移动端和不支持目录拖入浏览器的兼容方式。

### 4.2 上传目标快照

文件从拖入到目录递归解析完成可能经过数秒。如果用户期间切换目录，不能把同一批文件上传到新目录。

在 `drop` 事件发生时立即捕获：

```js
{
  folderId,
  isPublic,
  tenantId,
  systemFolderCode,
  targetPathLabel,
}
```

此上下文随整批任务传入上传 Store。目录解析完成后仍使用这个快照，不能再次从 `navigationStore.currentFolderId` 读取目标。

党建文档还必须满足：

- `isPartyBuildingDocumentsReady === true`；
- `navigationStore.lockedRootFolderId` 已初始化；
- 目标目录位于锁定的党建根目录内；
- 使用 `document.party_building_document.upload` 权限，而不是普通资料库上传权限。

### 4.3 文件与文件夹拖入

#### 普通文件

多个普通文件直接转为 `File[]`，调用现有 `uploadCoreStore.handleFileSelect(files, targetContext)`。现有 Store 继续负责：

- 文件名校验；
- 重复任务识别；
- 大小阈值判断；
- 小文件普通上传；
- 大文件分片上传；
- 压力等级和并发控制；
- 上传状态机及传输面板。

#### 文件夹

Chromium 内核通过 `DataTransferItem.webkitGetAsEntry()` 递归读取目录。需要注意 `DirectoryReader.readEntries()` 必须循环调用直到返回空数组，单次读取不能保证得到目录下所有条目。

建议统一成以下内部结构，不直接修改浏览器只读的 `File.webkitRelativePath`：

```js
{
  file,
  relativePath: '一级目录/二级目录/文件.pdf',
  rootName: '一级目录',
}
```

现有 `FolderUploadStore` 增加 `handleFolderEntries(entries, targetContext)`，按钮选择的文件夹也先从 `webkitRelativePath` 转成同样的结构。这样“点击上传文件夹”和“拖入文件夹”只保留一个后续流程。

同一批次同时包含普通文件和多个顶层文件夹时：

- 普通文件作为一个批次进入当前目录；
- 每个顶层文件夹依次创建目录结构并入队；
- 文件真正上传仍由现有队列按动态并发执行；
- 任一文件夹结构创建失败只影响该顶层文件夹，不阻断其他文件。

Firefox/Safari 无法可靠读取拖入目录时，提示“当前浏览器暂不支持拖动文件夹，请使用上传文件夹按钮”，普通文件仍可上传。

### 4.4 禁用状态

以下情况不接受投放：

| 场景 | 行为 |
|---|---|
| 无上传权限 | 不显示投放遮罩，松开后不拦截为上传 |
| 党建系统目录初始化中/失败 | 禁止投放，显示现有初始化或错误状态 |
| 正在搜索 | 第一版禁止投放，提示“请退出搜索后上传”，避免目标目录含义不清 |
| 上传目标目录已删除或不可写 | 入队前后端校验失败，显示明确错误，不回退到根目录 |
| 拖入空目录 | 提示“空文件夹无需上传” |

## 五、规章管理附件交互设计

### 5.1 当前事实

`spug_web/src/pages/regulation/Form.js` 当前直接使用：

```jsx
<Upload customRequest={handleUpload} ...>
  <Button>上传附件</Button>
</Upload>
```

它没有引入 `components/AttachmentManager.js`。因此答案是：**目前规章管理附件上传不是通过公共附件组件调用的。**

### 5.2 推荐界面

在规章详情的“附件”分隔线下方增加紧凑投放区，附件表格仍放在下方：

```text
┌──────────────────────────────────────────────────────┐
│ [上传图标] 将附件拖到这里，或点击选择文件            │
│ 支持 PDF/Word/Excel/PPT/图片/文本，单文件最大 200MB  │
└──────────────────────────────────────────────────────┘

附件列表……
```

规则：

- 只有已有 `info.id` 的规章显示上传区；新建规章仍然先保存元数据，再上传附件。
- 只有 `document.regulation.upload` 权限用户可以投放或点击选择。
- 支持一次拖入多个文件，不支持文件夹；附件没有目录语义。
- 保留当前 `ALLOWED_ACCEPT` 和 `MAX_FILE_SIZE_MB = 200` 前端提示，但安全边界仍以后端校验为准。
- 同一页面的批量附件按顺序逐个上传，任意时刻只有一个附件请求；多个账号在不同浏览器中上传时，由后端自然处理跨账号并发。
- “等待上传、上传中、失败”显示在拖拽区下方的本次上传临时列表；成功文件进入正式附件表并从临时列表移除，全部结束后只刷新一次附件列表。
- 部分失败时汇总提示，例如“8 个附件上传完成，2 个失败”，失败项允许单独重试。
- 不建设全局传输列表，不跨页面持久化，也不提供暂停、恢复或断点续传。

### 5.3 为什么不直接替换成完整 `AttachmentManager`

当前完整公共组件对接口形状有既定假设，例如删除使用 `deleteUrl?id=<id>`，下载使用 `<prefix><id>/download/`；规章接口则是：

```text
DELETE /api/regulation/<regulation_id>/attachments/<attachment_id>/
GET    /api/regulation/<regulation_id>/attachments/<attachment_id>/download/
```

直接替换会同时涉及接口构造、下载响应、权限、字段映射和预览行为，超出了“增加拖拽入口”的最小范围。

推荐先抽取公共 `AttachmentUploadArea`，由规章传入自己的 `request(file)`；随后如需把规章附件列表也公共化，再给 `AttachmentManager` 增加请求适配器：

```js
buildDeleteUrl(record)
buildDownloadUrl(record)
requestDownload(record)
normalizeAttachment(response)
```

## 六、公共组件设计及其他模块影响

### 6.1 新增公共上传原语

建议新增：

```text
spug_web/src/components/AttachmentUploadArea.js
```

建议 Props：

| 属性 | 默认值 | 说明 |
|---|---:|---|
| `mode` | `button` | `button` 或 `dragger` |
| `multiple` | `false` | 是否允许多文件 |
| `accept` | 空 | 选择器过滤及前端预校验 |
| `maxFileSizeMB` | `500` | 单文件前端上限 |
| `maxFilesPerBatch` | `20` | 防止误拖入海量文件 |
| `disabled` | `false` | 权限或业务状态禁止上传 |
| `request` | 必填 | `request(file) => Promise` |
| `onBatchSettled` | 空 | 批次完成后刷新列表或更新计数 |
| `hint` | 自动生成 | 文件类型、大小等提示 |

组件职责仅包括：

- 点击选择和拖拽投放交互；
- 单批文件数量、扩展名、单文件大小预校验；
- 单页面 FIFO 串行队列；
- 每个文件的成功/失败状态；
- 把文件交给模块提供的 `request`。

组件不负责：

- 拼装某个业务模块 URL；
- 业务对象是否存在；
- 后端权限、MIME、病毒或内容安全校验；
- 决定物理存储目录；
- 资料库目录递归和分片上传。

### 6.2 改造公共 `AttachmentManager`

`AttachmentManager` 内部的 `AttachmentToolbar` 改为调用 `AttachmentUploadArea`，新增：

```jsx
uploadMode="button"       // 默认保持现状
multiple={false}
```

要让某个模块拥有拖拽上传，由调用方显式声明：

```jsx
<AttachmentManager
  uploadMode="dragger"
  multiple
  {...otherProps}
/>
```

不能把当前单一的 `uploading: boolean` 直接用于多个文件。应改成逐文件 FIFO 任务队列，否则无法准确表达等待、上传中和失败状态。

这里的状态不是全局传输列表：它只显示在当前拖拽区下方。等待文件显示“等待上传”，当前文件以旋转图标显示“上传中”（不强制百分比进度），成功文件加入正式附件表后从临时列表移除，失败文件保留重试和移除操作。

### 6.3 哪些模块可以随公共组件获得拖拽能力

当前源码静态扫描到的 `AttachmentManager` 调用方：

| 业务模块/页面 | 调用位置 | 开启方式 |
|---|---|---|
| 合同协议 | `pages/contractAgreement/Form.js` | 显式传 `uploadMode="dragger"` |
| 无线电执照 | `pages/radioLicense/Form.js` | 显式传参 |
| 升级工作台 | `pages/upgrade/WorkbenchForm.js` | 显式传参 |
| 系统公告表单/详情 | `pages/system/announcement/*` | 仅可编辑态显式开启 |
| 首页公告详情 | `pages/home/AnnouncementDetail.js` | 通常只读，不出现上传区 |

所以，“改公共附件组件能否让其他模块也支持拖动上传”的准确回答是：

- **可以覆盖所有真正使用 `AttachmentManager` 且处于可上传状态的页面。**
- **不会覆盖直接使用 Ant Design `Upload`、原生文件 input 或资料库专用上传 Store 的页面。** 这些页面需要迁移到公共上传区或单独接入文档投放层。
- 推荐逐模块启用，不推荐修改默认值后一次性全局上线。

## 八、关键流程

### 8.1 资料库/党建拖入文件

```text
外部文件进入 Explorer
  -> 检查 Files 类型、上传权限、页面就绪状态
  -> 展示当前目标目录遮罩
  -> 用户松开
  -> 捕获 folderId/isPublic/tenant/systemFolder 快照
  -> 解析文件与目录
  -> 刷新一次服务器上传压力
  -> 普通文件调用 handleFileSelect
  -> 目录调用 handleFolderEntries
  -> 进入现有上传队列和状态机
  -> 上传面板展示进度
  -> 完成后按现有机制刷新 Explorer
```

### 8.2 规章拖入附件

```text
附件进入 AttachmentUploadArea
  -> 检查权限、规章 ID、文件数、扩展名、单文件大小
  -> 合法文件进入当前页面 FIFO 队列
  -> 按顺序逐个调用现有 POST /attachments/upload/
  -> 分别记录成功或失败
  -> 队列结束后刷新一次附件列表
  -> 展示批次汇总和失败项重试入口
```

## 九、校验、安全与稳定性

### 9.1 前端校验不是安全边界

`accept`、文件扩展名和大小检查只是提前反馈。后端仍必须继续校验：

- 用户权限及租户/系统目录范围；
- 业务对象存在且可写；
- 文件大小上限；
- 扩展名、MIME 和业务允许类型；
- 文件名及相对路径中的 `..`、绝对路径、空字节和非法分隔符；
- 最终存储路径仍位于允许的根目录内。

### 9.2 拖拽事件安全

- 只处理 `Files` 类型，忽略 URL、文本和页面内部对象。
- 只在组件投放范围内阻止默认 `drop` 行为，避免浏览器直接打开文件。
- 文件解析异常不能让遮罩永久停留。
- 组件卸载后移除所有窗口级监听器，避免其他页面无法正常拖动。
- 不把 `File`、Blob URL 或完整文件列表写入持久化 Store、日志或审计日志。

### 9.3 批量限制建议

| 类型 | 建议 |
|---|---|
| 资料库文件 | 延用现有队列限制；投放解析阶段增加最大条目数保护，例如 5000 |
| 资料库目录深度 | 建议最多 20 层，后端继续校验路径长度 |
| 规章附件 | 默认单批最多 20 个，同一页面严格串行；多账号由后端自然并发 |
| 单附件大小 | 当前规章保持 200MB；其他模块由各自 Props/后端配置决定 |

## 十、测试与验收

### 10.1 资料库文档管理

- 拖入 1 个小文件，上传到当前私人目录。
- 拖入多个文件，全部进入同一目标目录且上传面板状态正确。
- 拖入大于普通上传阈值的文件，仍走现有分片上传并可暂停/恢复。
- 拖入嵌套文件夹，目录层级与文件数量一致。
- 混合拖入普通文件和多个文件夹，失败隔离正确。
- 在公共共享库拖入文件，`isPublic` 快照正确。
- 拖入后立即切换目录，文件仍上传到松开时显示的目录。
- 搜索状态、无权限状态和目标目录被删除时不能误传到根目录。
- 拖入同一文件两次，沿用现有重复任务提示。

### 10.2 党建文档

- 使用 `document.party_building_document.upload` 权限可拖入上传。
- 只有普通资料库上传权限、没有党建上传权限时不能拖入。
- 初始化完成前不能投放。
- 根目录和子目录上传均不能越过党建锁定根目录。
- 离开党建页面后系统目录上下文被清理，不污染普通资料库上传。

### 10.3 规章管理

- 已保存规章可拖入单个和多个允许类型附件。
- 新建未保存规章、只读详情、无上传权限时不出现可用投放区。
- 超过 200MB、类型不允许、空文件返回明确提示。
- 多文件中一个失败，其余仍成功，列表最终只刷新一次。
- 上传完成后预览、下载、删除行为不回归。
- 快速连续拖入两批附件时仍按 FIFO 顺序上传，loading 和等待状态准确。
- 两个账号在不同浏览器会话中同时上传时，附件归属、权限和物理文件互不串用。

### 10.4 公共组件回归

- 不传 `uploadMode` 的现有调用方保持按钮式布局和单文件行为。
- 显式开启 `dragger + multiple` 的页面布局不溢出弹窗。
- `readOnly`、`recordId` 为空或权限不足时上传区不显示或不可用。
- 公告详情等只读调用方不会因为公共组件改造出现上传入口。

## 十一、WSL Docker 验证方式

Windows 侧当前不应假设能连接 Docker Desktop 的命名管道。应进入实际运行 Docker daemon 的 WSL 发行版执行：

```bash
wsl -d <你的发行版名称>
cd /mnt/e/TDYW/spug-3.0
docker compose -f docker/docker-compose.yml ps
```

本项目主应用服务名和容器名均为 `tdyw`。前端构建及容器验证建议：

```bash
cd /mnt/e/TDYW/spug-3.0/spug_web
npm run build

cd /mnt/e/TDYW/spug-3.0
docker build -t tdyw:drag-upload -f docker/Dockerfile .
docker compose -f docker/docker-compose.yml up -d tdyw
docker compose -f docker/docker-compose.yml logs -f tdyw
```

注意：当前 Compose 配置使用固定镜像 `tdyw:0704`。正式验证新镜像前，应通过环境化镜像标签或临时 Compose override 指向 `tdyw:drag-upload`，不要只构建新镜像却继续启动旧标签。

浏览器验收建议优先使用 Chrome/Edge；目录拖拽属于 Chromium 扩展能力，Firefox/Safari 只承诺普通文件拖拽和“上传文件夹”按钮回退能力。

## 十二、实施顺序与风险控制

1. 新增 `AttachmentUploadArea`，先保持 `AttachmentManager` 默认行为不变。
2. 为资料库/党建增加 `DocumentDropUploadLayer` 和普通文件拖入，验证目标目录快照、权限及大文件分片。
3. 接入目录递归及 `FolderUploadStore` 规范化条目，完成嵌套目录测试。
4. 规章管理接入公共上传区，使用现有独立附件 API，实现多文件串行上传。
5. 将公共 `AttachmentManager` 的上传按钮内部替换为 `AttachmentUploadArea`，默认仍为 `button`。
6. 合同、公告、执照、升级工作台逐模块显式开启拖拽并回归弹窗布局。
7. 在 WSL 中构建前端和镜像，使用实际 Compose 服务进行端到端验收。

主要风险及处理：

| 风险 | 处理 |
|---|---|
| 拖入期间切换目录导致传错位置 | `drop` 时捕获不可变目标上下文 |
| 子元素触发 `dragleave` 使遮罩闪烁 | 使用进入深度计数，不用单一布尔值 |
| 目录读取不完整 | `readEntries()` 循环到空数组 |
| 多文件使单个账号瞬间发出大量请求 | 公共上传区使用单页面 FIFO 串行队列 |
| 多账号同时上传发生文件或权限串用 | 后端使用独立请求上下文、业务对象校验和安全存储名，并进行多账号并发测试 |
| 改公共组件导致所有页面布局变化 | 默认 `uploadMode="button"`，逐模块显式启用 |
| 前端类型过滤被绕过 | 后端继续执行完整校验 |
| WSL 中构建了新镜像却启动旧镜像 | Compose 镜像标签参数化或使用 override |

## 十三、最终建议

本次建议按以下边界落地：

- **资料库 + 党建文档：一次实现，复用现有文档上传 Store。**
- **规章附件：可以增加拖拽，但当前不是公共组件调用；先复用新的公共上传区，不强行改造其独立附件后端。**
- **其他附件模块：公共 `AttachmentManager` 可以提供拖拽能力，但必须逐模块显式开启。**
- **不要把“修改一个公共组件”等同于“所有上传页面自动支持拖拽”。** 只有公共组件调用方会受益，专用上传页面仍需接入。
