# 资料库并发上传与状态机修复方案

> 日期：2026-06-17
> 范围：资料库批量上传、分片上传、合并队列、传输列表状态机
> 依据：`locustfile/UPLOAD_PRESSURE_TEST_PLAN.md` 中的 5 个瓶颈点，以及当前前后端代码核查结果

---

## 一、结论

当前资料库并发上传变慢不是单点问题，而是由三层叠加造成：

1. 后端合并能力有限：`document.merge` 队列并发约 6，多个终端上传中大文件时容易排队。
2. 合并阶段 I/O 放大：分片合并按顺序读写，复制缓冲区只有 1MB，合并后还可能再次全量读取计算 MD5。
3. 前端状态机适合管理单任务生命周期，但并发调度和业务副作用仍耦合，存在重复触发、晚到回调覆盖、槽位计数不一致的风险。

因此修复不建议只调大 Celery 并发。正确顺序是：

1. 先降低后端合并 I/O 成本。
2. 再拆分并调优 Celery 合并队列。
3. 同步收敛前端状态机和并发调度口径。
4. 最后再做分片内并发、WebSocket 通知、对象存储等中长期优化。

## 三、前端状态机核查

当前传输列表使用状态机是合理方向，但状态机本身不等于并发调度器。

### 3.1 优点

- 每个上传项有独立状态机，状态包括 `waiting / calculating / uploading / merging / completed / error / cancelled`。
- `UploadCoordinator.startWaiting()` 按 `calculating + uploading` 数量启动等待任务，具备基本并发控制。
- `merging` 不占前端上传槽位，这符合当前架构：合并由后端 Celery 执行，前端主要轮询状态。

### 3.2 风险

1. 状态机和业务副作用耦合。

   `StateChangeHandler` 在状态变更时直接触发 MD5、上传、合并和轮询。并发多时，状态流转和异步副作用交织，容易出现重复触发。

2. 存在绕过状态机直接写状态的路径。

   `UploadStateMachine.assertStatusConsistency()` 注释中已经说明 `chunkUpload.js / fileUpload.js` 可能绕过状态机直接写 `item.status`。并发暂停、取消、恢复时，这会产生状态不一致。

3. 并发槽位存在两套口径。

   `UploadCoordinator.startWaiting()` 使用状态机数量判断可用槽位，`StateChangeHandler.handleUploadingState()` 又使用 `activeUploads` 做 while 等待和递增递减。两套口径不一致时可能出现卡槽、超发或少发。

4. 晚到异步结果缺少版本保护。

   上传、合并、轮询都是异步操作。如果用户在请求未返回时执行暂停、取消、重试，旧请求返回后仍可能覆盖新状态。

## 四、修复目标

### 4.1 性能目标

- 10 终端并发上传时，上传请求不因合并排队明显阻塞。
- 中大文件合并耗时下降，合并队列长度可控。
- 普通 API 不被大文件上传/合并拖慢。

### 4.2 正确性目标

- 每个上传任务只有一个可信状态来源。
- 暂停、取消、重试不会被旧请求返回覆盖。
- 并发槽位不会泄漏，不会出现长期卡在 waiting/uploading/merging 的任务。

## 五、P0 修复方案

P0 目标是先解决最明显、风险最低、收益最大的后端瓶颈。

### 5.1 增大合并复制缓冲区

位置：`spug_api/apps/document/tasks/merge.py`

当前：

```python
FILE_COPY_BUFFER_SIZE = 1024 * 1024
```

建议：

```python
FILE_COPY_BUFFER_SIZE = 8 * 1024 * 1024
```

说明：

- 1MB 缓冲对大文件合并偏小，会增加 Python 层循环次数和系统调用压力。
- 建议先改为 8MB；如果服务器内存稳定，再压测 16MB。
- 不建议直接过大，避免多个 merge worker 同时合并时放大内存占用。

### 5.2 合并时顺带计算 MD5

位置：

- `spug_api/apps/document/tasks/merge.py`
- `spug_api/apps/document/libs/document_utils.py`

当前流程：

1. 顺序读取分片并写入目标文件。
2. 合并完成后，如果是全量 MD5，再打开目标文件全量读取一次校验。

建议流程：

1. 合并时每读一个 chunk 同步 `md5.update(data)`。
2. 写入完成后直接得到 merged_md5。
3. 对全量 MD5 文件直接比对，避免二次全量读取。
4. 对 `sv1_` 抽样 MD5 保持现有跳过完整校验逻辑。

收益：

- 大文件合并阶段减少一次完整磁盘读取。
- 对 500MB 以下仍使用全量 MD5 的文件尤其明显。

风险：

- 需要保持与 `calculate_file_md5()` 结果一致。
- 必须覆盖单分片、多分片、空分片异常、缺分片异常等测试。

### 5.3 拆分 Celery merge worker

位置：

- `spug_api/tools/start-celery.sh`
- `spug_api/tools/start-celery-worker.sh`
- `docker/config/supervisord.conf`

当前：

- `general-worker` 监听 `celery,document.merge,document.cleanup`，并发 4。
- `dev-worker` 监听 `document.merge,document.batch,document.cleanup`，并发 2。
- `document.merge` 被两个 worker 同时消费，总并发约 6，但队列职责混杂。

建议：

1. `general-worker` 只监听默认业务队列：

   ```bash
   -Q celery
   --concurrency=2
   ```

2. 新增或调整专用 merge worker：

   ```bash
   -Q document.merge
   -n merge-worker@%h
   --concurrency=4
   --prefetch-multiplier=1
   ```

3. `document.cleanup` 单独 worker：

   ```bash
   -Q document.cleanup
   --concurrency=1
   --prefetch-multiplier=1
   ```

   说明：

   - 即使回收站删除已移除，清理队列仍建议保留。
   - 该队列只负责上传链路相关清理，例如旧分片、过期传输记录、孤儿传输记录、卡住的 merging 任务、物理文件待清理重试等。
   - 不再把它描述为回收站删除兜底队列。

4. `document.batch` 视实际功能保留：

   ```bash
   -Q document.batch
   --concurrency=2
   ```

   说明：

   - 如果传输列表仍保留批量暂停、恢复、取消、删除传输记录，则保留 batch worker。
   - 如果这些传输记录批量操作也已移除，则可以同步移除 `document.batch` 路由和 worker。
   - `document.batch` 不应再承担回收站删除相关任务。

5. 压测后再决定 merge concurrency 是否从 4 提到 6 或 8。

原则：

- 先专队列，再调并发。
- 并发上限受磁盘 I/O 限制，不是越大越好。

## 六、P1 修复方案

P1 目标是提升并发稳定性，减少资源互相影响。

### 6.1 引入 gevent 安全 MySQL 连接池

位置：

- `spug_api/requirements.txt`
- `spug_api/spug/settings.py`

建议方案：

1. 引入 `django-db-geventpool`。
2. 将数据库 ENGINE 调整为 geventpool backend。
3. 配置连接池大小，例如：

   ```python
   'ENGINE': 'django_db_geventpool.backends.mysql',
   'CONN_MAX_AGE': 60,
   'OPTIONS': {
       'MAX_CONNS': 20,
       'REUSE_CONNS': 10,
   }
   ```

注意：

- 当前注释明确说明普通 Django 持久连接与 gevent 有兼容风险，所以不能只把 `CONN_MAX_AGE` 从 0 改成 60。
- 需要灰度验证 MySQL `Threads_connected`、`Threads_running`、接口 p95。

### 6.2 上传 API 与普通 API 隔离

位置：

- `spug_api/gunicorn.conf.py`
- `docker/config/supervisord.conf`
- `docker/config/nginx.conf`

建议：

1. 保留现有 Gunicorn 服务处理普通 API。
2. 新增上传专用 Gunicorn 服务，例如绑定 `127.0.0.1:9002`。
3. Nginx 将以下路径转发到上传专用服务：

   - `/api/document/upload/`
   - `/api/document/upload_chunk/`
   - `/api/document/check_uploaded_chunks/`
   - `/api/document/merge_chunks/`
   - `/api/document/merge_status/`

收益：

- 大文件上传落盘不会挤占普通接口 worker。
- 可以单独调整上传服务的 `timeout`、`workers`、`worker_connections`。

### 6.3 优化同 hash 幂等与锁竞争

位置：

- `spug_api/apps/document/views/upload/merge.py`
- `spug_api/apps/document/tasks/merge.py`

建议：

1. 同 hash 已完成时，直接复用文件记录或返回 completed，不再提交合并任务。
2. 同 hash 正在合并时，返回已有 `task_id`，前端直接轮询。
3. Redis lock 获取失败时优先查已有任务，不直接创建新任务 retry。

目标：

- 减少同 hash 文件重复合并。
- 避免锁失败后 30s retry 堆积。

## 七、P2 修复方案

P2 目标是把前端状态机改造成更可靠的并发调度模型。

### 7.1 状态机成为唯一状态入口

位置：

- `spug_web/src/pages/document/stores/upload/core/UploadStateMachine.js`
- `spug_web/src/pages/document/stores/upload/core/chunkUpload.js`
- `spug_web/src/pages/document/stores/upload/core/fileUpload.js`
- `spug_web/src/pages/document/stores/upload/core/lifecycle/StateChangeHandler.js`

规则：

- `chunkUpload.js` 和 `fileUpload.js` 不直接写最终状态。
- 上传成功只发事件：`UPLOAD_COMPLETE`。
- 合并成功只发事件：`MERGE_SUCCESS`。
- 失败只发事件：`ERROR`。
- 暂停/取消/重试全部通过 `transition()`。

保留可直接更新的字段：

- `percent`
- `speed`
- `currentChunk`
- `errorMessage` 的临时展示值

禁止直接更新的字段：

- `status`
- `canAbort`
- `isPausedByUser`
- `isCancelledByUser`

### 7.2 统一并发槽位口径

当前有两套口径：

- `StateMachineManager.countByStates(['calculating', 'uploading'])`
- `queueStore.activeUploads`

建议：

1. 以状态机状态计数作为唯一并发口径。
2. 删除或弱化 `activeUploads`，仅作为调试指标。
3. `handleUploadingState()` 不再 while 等槽；是否允许进入 `uploading` 由 `UploadCoordinator` 统一决定。

目标：

- 避免递增递减不对称导致卡槽。
- 避免任务已进入 `uploading` 后又在 handler 内二次等待。

### 7.3 异步操作加版本号

每个任务维护：

```js
operationVersion: number
```

规则：

1. 每次 START、RESUME、RETRY 时递增版本。
2. 上传、合并、轮询启动时捕获当前版本。
3. 异步回调返回时，如果版本不一致，直接丢弃结果。
4. CANCEL 后的任何旧回调不得更新状态。

示例：

```js
const version = item.operationVersion;
const result = await upload();
if (!this.isCurrentOperation(uploadId, version)) return;
machine.transition('UPLOAD_COMPLETE', result);
```

收益：

- 防止暂停后旧上传成功回调把任务改成 completed。
- 防止取消后旧轮询回调把任务改回 merging/completed。

### 7.4 限制待合并任务数量

虽然 `merging` 不占前端上传槽位是合理的，但无限释放上传槽会让后端 merge 队列持续堆积。

建议新增前端软限制：

```js
MAX_PENDING_MERGES = 10
```

含义：

- 当本终端 `merging` 数量达到阈值时，暂停启动新的大文件分片上传。
- 小文件可继续上传。
- 阈值后续可根据后端 `document.merge` 队列长度动态调整。

## 八、P3 中长期优化

### 8.1 分片内并发上传

当前 `MAX_CONCURRENT_CHUNKS = 3` 已配置，但 `chunkUpload.js` 实际按 `for + await uploadSingleChunk()` 顺序上传。

建议：

- 实现每个文件内部最多 2-3 个分片并发。
- 每个分片独立重试。
- 总体并发仍受全局上传槽位控制。

注意：

- 分片内并发会增加后端 `upload_chunk` 写盘并发。
- 必须结合上传专用 Gunicorn 和磁盘 I/O 指标压测。

### 8.2 WebSocket 或 SSE 推送合并状态

当前前端通过 `merge_status` 轮询。

建议：

- 短期保留渐进式轮询。
- 中长期由后端推送 Celery 合并状态，减少高并发轮询请求。

### 8.3 对象存储或同卷存储优化

当前分片目录和最终文件目录分别挂载到：

- `storage/document_chunks`
- `storage/documents`

建议：

- 优先保证分片和最终文件位于同一高速存储。
- 中长期迁移到 MinIO/S3，前端直传对象存储，后端只处理元数据和合并回调。

## 九、验证方案

### 9.1 功能回归

必须覆盖：

- 小文件普通上传。
- 中文件分片上传。
- 大文件分片上传。
- 暂停后继续。
- 取消后不再更新状态。
- 失败后重试。
- 同 hash 文件重复上传。
- 公共空间和私有空间上传。
- 多租户隔离。

### 9.2 并发回归

建议按以下矩阵执行：

| 场景 | 终端数 | 每终端并发 | 文件类型 |
| --- | --- | --- | --- |
| 基线 | 1 | 3 | 小/中/大 |
| 中压 | 3 | 3 | 中/大 |
| 高压 | 5 | 3 | 混合 |
| 极限 | 10 | 3 | 混合 |

### 9.3 关键指标

应用侧：

- `upload_chunk` avg / p95 / p99。
- `merge_chunks` avg / p95 / p99。
- `merge_status` QPS。
- 文件完成数/分钟。
- 失败率。
- 重试率。

服务侧：

- Redis `document.merge` 队列长度。
- Celery active task 数量。
- 磁盘 `%util` 和 `await`。
- MySQL `Threads_connected`、`Threads_running`。
- Gunicorn worker CPU / memory。

前端侧：

- `waiting` 是否持续堆积。
- `uploading` 数量是否超过配置。
- `merging` 是否持续增长不释放。
- 是否出现状态机与 `item.status` 不一致报警。

## 十、回滚方案

### 10.1 后端回滚

- 合并缓冲区从 8MB 改回 1MB。
- Celery worker 恢复原 `start-celery.sh` 和 `start-celery-worker.sh` 队列配置。
- 如果连接池异常，恢复 `django.db.backends.mysql` 和 `CONN_MAX_AGE = 0`。
- Nginx 上传专用路由回退到原 API upstream。

### 10.2 前端回滚

- 保留旧状态写入路径一版，通过开关控制是否启用“状态机唯一入口”。
- `operationVersion` 只做忽略旧回调，不改变请求参数，回滚风险较低。
- `MAX_PENDING_MERGES` 可配置为 `Infinity` 关闭限制。

---

## 十一、推荐实施顺序

1. P0-1：合并缓冲区 1MB -> 8MB。
2. P0-2：合并时同步计算 MD5，减少二次读盘。
3. P0-3：拆分 Celery merge 专用 worker，初始并发 4。
4. 压测 L0/L2/L4，确认 merge 队列、磁盘 I/O、失败率。
5. P1-1：引入 gevent 安全 MySQL 连接池。
6. P1-2：上传 API 与普通 API 隔离。
7. P2-1：状态机成为唯一状态入口。
8. P2-2：统一并发槽位口径。
9. P2-3：异步操作加版本号。
10. P2-4：限制待合并任务数量。

---

## 十二、预期收益

| 修复项 | 预期收益 |
| --- | --- |
| 合并缓冲区增大 | 降低大文件合并 CPU 和系统调用开销 |
| 合并时同步 MD5 | 减少一次目标文件全量读取 |
| merge 专用 worker | 队列职责清晰，避免普通任务和合并任务互相抢 worker |
| MySQL gevent 连接池 | 降低高并发接口建连成本 |
| 上传 API 隔离 | 降低大文件上传对普通 API 的影响 |
| 状态机唯一入口 | 减少并发暂停、取消、重试导致的状态错乱 |
| operationVersion | 防止旧异步回调覆盖新状态 |
| 待合并数量限制 | 防止前端持续释放上传槽导致后端合并队列爆仓 |
