# 发布安全与回滚规范

> 适用范围：所有涉及代码发布、数据库变更的生产部署
> 核心原则：**能发现**（健康检查）、**能回滚**（Expand-Contract）、**能止损**（观察窗口）

---

## 1. 概述

### 1.1 三大支柱

一次安全的发布需要三道防线，缺一不可：

| 支柱 | 作用 | 实现方式 | 效果 |
|---|---|---|---|
| **一：健康检查端点** | 发布后 90 秒内判断"服务能不能用" | Django `/healthz/` 检查 DB+Redis+存储，Docker healthcheck | 启动阶段故障 -> 自动回滚 |
| **二：Expand-Contract** | 确保"回滚镜像"这个动作真的能恢复服务 | 迁移拆三步：EXPAND -> DEPLOY -> CONTRACT | 发布阶段问题 -> 回滚镜像即可，数据无损 |
| **三：观察窗口** | 发布后 5 分钟内发现"启动检查发现不了的问题" | `post_deploy_watch.sh` 监控 5xx/Celery/磁盘/内存 | 运行阶段故障 -> 告警 -> 建议回滚 |

### 1.2 三者关系

```
Expand-Contract 规范（事前预防）
  确保迁移可安全回滚
        │
        ▼
deploy.sh 发布（事中发布）
  构建镜像 -> 重启 -> /healthz/ 检查 ── 失败 ──> 自动回滚
        │                                   │
        │ 成功                              │ 回滚完成
        ▼                                   ▼
post_deploy_watch.sh（事后观察）           发布失败，已止损
  5min 监控 -> 异常告警 ──> 建议手动回滚
        │
        │ 稳定
        ▼
   发布完成
```

- **Expand-Contract 是规范**（人的纪律）：保证"能回滚"
- **healthz 是感知器**（机器执行）：保证"能发现启动故障"
- **watch 是哨兵**（机器执行）：保证"能发现运行故障"

## 2. 问题背景

### 2.1 回滚的两个硬边界

`docker/scripts/deploy.sh` 和 `rollback.sh` 能实现镜像级一键回滚，但有两个硬边界：

**边界一：如果迁移不可逆，回滚镜像也没用。**

镜像回滚只是切回旧代码，但数据库结构已经被新迁移改了。旧代码跑在新结构上，可能直接崩溃。

**边界二：如果健康检查太浅，故障感知不到。**

Docker 默认 healthcheck 只查 `SELECT 1`，Redis 挂了、存储目录权限丢了、Celery worker 崩溃了都感知不到，healthcheck 仍是绿灯。

### 2.2 真实案例：upgrade_no 字段移除（2026-07-30）

本项目的 `upgrade_no` 字段移除就是一个**违反 Expand-Contract** 的案例：

```
发布前：
  models.py 有 upgrade_no 字段
  views/serializers/exporters 都引用 upgrade_no
  unique_together 包含 upgrade_no

一次发布做了 3 件事：
  1. 迁移：AlterUniqueTogether(set()) + RemoveField('upgrade_no')
  2. 后端：删除 generate_upgrade_no()、移除 27 处引用
  3. 前端：移除 nextUpgradeNo state、fetch、Form.Item

如果发布后发现 bug，回滚到旧镜像：
  旧代码查 upgrade_no 字段 → 字段已被迁移删除 → 报错崩溃
  旧代码的 unique_together 包含 upgrade_no → 约束已改 → 建索引失败
```

**根因**：迁移（删字段）和代码（删引用）同时上线，迁移不可逆，代码回不去。

### 2.3 真实案例：document 软删除字段移除（2026-07-30）

同理，`0018_remove_soft_delete_fields.py` 一次迁移做了：

- 移除 4 个模型的 `is_deleted` / `deleted_at` / `deleted_by` 字段
- 移除 5 个复合索引中的 `is_deleted` 列
- 移除双管理器 `objects` / `all_objects`

如果回滚到旧镜像，旧代码会查 `is_deleted` 字段 -> 字段已删 -> 崩溃。

### 2.4 为什么以前没出事

- 项目用户量小，发布窗口低峰期，出问题手动修
- 没有自动化回滚流程（`rollback.sh` 刚建立）
- 运气好，发布后没发现需要回滚的 bug

**但随着系统复杂度增长，不能继续靠运气。**

## 3. 支柱一：健康检查端点（/healthz/）

### 3.1 解决什么问题

Docker healthcheck 目前是 `SELECT 1`，只能回答"数据库连不连得上"。但实际上：

| 故障场景 | SELECT 1 结果 | 实际影响 |
|---|---|---|
| Redis 挂了 | 正常 | 登录全失败（token 缓存不可用） |
| 存储目录权限丢了 | 正常 | 上传全失败 |
| Celery worker 崩溃 | 正常 | 异步任务全部堆积 |
| 某个关键表损坏 | 正常 | 查该表才报错 |
| DB 连接池耗尽 | 可能正常 | 间歇性超时 |

**设计意图**：把"容器活着"和"服务可用"区分开。

### 3.2 端点实现

新增 `/healthz/` Django 端点，依次检查所有关键依赖：

```python
# spug_api/apps/home/views.py
import json, os
from django.db import connection
from django.http import HttpResponse
from django.views import View
from django.conf import settings
import redis

class HealthCheckView(View):
    """深度健康检查端点，供 Docker healthcheck 和 deploy.sh 使用"""

    def get(self, request):
        checks = {}
        all_ok = True

        # 1. 数据库连通性
        try:
            with connection.cursor() as cursor:
                cursor.execute("SELECT 1")
                cursor.fetchone()
            checks['db'] = 'ok'
        except Exception as e:
            checks['db'] = f'fail: {e}'
            all_ok = False

        # 2. Redis 连通性
        try:
            redis_client = redis.Redis(
                host=settings.REDIS_HOST,
                port=settings.REDIS_PORT,
                password=settings.REDIS_PASSWORD,
                socket_timeout=2,
                socket_connect_timeout=2,
            )
            redis_client.ping()
            checks['redis'] = 'ok'
        except Exception as e:
            checks['redis'] = f'fail: {e}'
            all_ok = False

        # 3. 存储目录可写
        media_root = getattr(settings, 'MEDIA_ROOT', '/data/spug/storage/media')
        try:
            if os.path.isdir(media_root) and os.access(media_root, os.W_OK):
                checks['storage'] = 'ok'
            else:
                checks['storage'] = f'fail: {media_root} not writable'
                all_ok = False
        except Exception as e:
            checks['storage'] = f'fail: {e}'
            all_ok = False

        # 4. Celery worker 存活（可选）
        try:
            from django_celery_results.models import TaskResult
            recent = TaskResult.objects.filter(
                status='SUCCESS'
            ).order_by('-date_done').first()
            checks['celery'] = 'ok' if recent else 'ok (no recent tasks)'
        except Exception:
            checks['celery'] = 'ok (check skipped)'

        status_code = 200 if all_ok else 503
        return HttpResponse(
            json.dumps(checks, ensure_ascii=False, indent=2),
            status=status_code,
            content_type='application/json'
        )
```

### 3.3 路由与 Docker 配置

```python
# spug_api/spug/urls.py
from apps.home.views import HealthCheckView
path('healthz/', HealthCheckView.as_view()),  # 不需要认证
```

```yaml
# docker/docker-compose.yml
services:
  tdyw:
    healthcheck:
      test: ["CMD-SHELL", "curl -sf http://localhost:8000/healthz/ || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s
```

### 3.4 健康检查分层设计

```
检查层         检查内容                 发现的故障
──────────────────────────────────────────────────────
L1 容器存活    docker ps                容器崩溃 / OOM Kill
L2 进程存活    supervisorctl status     gunicorn/celery 进程退出
L3 依赖连通    /healthz/ (DB+Redis+存储) DB挂 / Redis挂 / 磁盘满
L4 业务功能    post_deploy_watch.sh      业务逻辑 bug / 5xx 错误
```

`/healthz/` 覆盖 L3 层。L4 层由观察窗口的 5xx 错误监控覆盖。

### 3.5 与 deploy.sh 的集成

`deploy.sh` 发布后等 90 秒做健康检查，检查的就是 Docker healthcheck 状态（底层调 `/healthz/`）：

```
新镜像启动
  └-> entrypoint.sh 运行 migrate + 启动 gunicorn
       └-> Docker healthcheck 每 30s 调 /healthz/
            └-> 200 -> healthy -> deploy.sh 确认发布成功
            └-> 503 -> unhealthy -> deploy.sh 触发自动回滚
```

**效果**：新镜像启动后如果 Redis 连不上（比如配置改错了），`/healthz/` 返回 503 -> Docker healthcheck 变 `unhealthy` -> `deploy.sh` 触发自动回滚 -> 用户无感。

## 4. 支柱二：迁移与代码发布分离（Expand-Contract）

### 4.0 适用策略：日常不分离，破坏性才手动分离

> **本项目策略**：95% 的迁移是加法（加字段/加表/加索引），与旧代码兼容，不需要分离。
> 只有破坏性迁移（删字段/改类型/删表）才需要手动走 Expand-Contract 三步。

| 迁移类型 | 出现频率 | 与旧代码兼容 | 需要分离？ |
|---|---|---|---|
| 加字段（nullable+default） | 常见 | 兼容 | **否**，和代码一起发 |
| 加表 | 常见 | 兼容 | **否** |
| 加索引 | 常见 | 兼容 | **否** |
| 加唯一约束（先洗数据） | 偶尔 | 兼容 | **否** |
| 删字段 | 罕见 | **不兼容** | **是**，手动三步 |
| 改字段类型 | 极少 | **不兼容** | **是**，手动三步 |
| 删表 | 极少 | **不兼容** | **是**，手动三步 |

**日常发布**（加法迁移 + 代码变更一起上）：
```
deploy.sh -> entrypoint.sh 自动 migrate -> 新代码上线 -> 健康检查 -> 监控
```

**破坏性迁移**（手动三步）：
```
第 1 步：提交代码（删引用，不删字段），用 deploy.sh 发布
第 2 步：观察 1-2 天
第 3 步：docker exec tdyw python manage.py migrate <app> <migration_name>
```

deploy.sh 的迁移检查会自动扫描迁移文件中的破坏性操作（RemoveField/AlterField/DeleteModel），遇到时警告开发者。

以下 §4.1-§4.3 是破坏性迁移的手动操作规范，仅在遇到时参考。

### 4.1 核心思想

把一次数据库变更拆成 **3 个独立阶段**，每个阶段单独发布、单独验证、单独可回滚：

```
阶段 1 - EXPAND（扩展，向后兼容）
  只做加法：加字段、加表、加索引、加约束（nullable + default）
  旧代码完全不受影响
  → 可以随时回滚（DROP COLUMN），旧代码不报错

阶段 2 - DEPLOY（发布新代码，双写过渡）
  迁移已在上一步完成
  新代码同时读写新旧字段（双写）
  → 如果有 bug，回滚镜像即可，旧代码不读新字段，数据无损

阶段 3 - CONTRACT（收缩，删旧，延后做）
  新代码稳定运行 1-2 天后
  迁移：DROP 旧字段 / 加 NOT NULL / 删旧索引
  → 此后不可回滚到阶段 1 之前的版本（但此时已确认稳定，不需要回滚了）
```

### 4.2 时间线

```
时间 ──────────────────────────────────────────────────────►

T0          T1              T2              T3          T4
│           │               │               │           │
│  阶段1    │    阶段2      │   观察期       │  阶段3    │
│  EXPAND   │   DEPLOY      │  (1-2天)      │ CONTRACT  │
│           │               │               │           │
│  跑迁移    │  发布新镜像    │  监控运行      │  跑清理    │
│  旧代码    │  新代码双写    │  确认稳定      │  迁移      │
│  继续跑    │  旧代码可回滚  │               │  不可回滚  │
│           │               │               │           │
▼           ▼               ▼               ▼           ▼
可回滚      可回滚           稳定            不可回滚    完成
```

### 4.3 每个阶段的具体操作

#### 阶段 1 - EXPAND（加，向后兼容）

**目标**：数据库结构变更，但旧代码仍能正常运行。

**允许的操作**：
- 加字段（nullable + default）
- 加表
- 加索引（注意 MariaDB 加索引可能锁表，大表用 pt-online-schema-change）
- 加唯一约束（需先清洗重复数据）
- 加 CHECK 约束（需先清洗非法数据）

**禁止的操作**：
- 删字段
- 改字段类型
- 加 NOT NULL 约束（除非所有行都有合法值）
- 删索引（旧代码可能依赖）

**操作步骤**：

```bash
# 1. 在 tdyw-test 验证迁移
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw-test \
  python manage.py makemigrations <app> --name expand_add_new_field'

# 2. 检查迁移文件
# 确认只有 AddField/AddIndex/AddConstraint，没有 RemoveField/AlterField

# 3. 在 tdyw-test 跑迁移验证
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw-test \
  python manage.py migrate <app> --plan'

# 4. 生产环境跑迁移（部署前！不是部署时）
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw \
  python manage.py migrate <app> --noinput'

# 5. 验证旧代码仍正常（此时还没发布新代码）
curl -s http://localhost/api/healthz/ | jq .
```

**此时状态**：数据库有新字段，但代码还是旧的，不读写新字段。**可以随时回滚迁移。**

#### 阶段 2 - DEPLOY（发布新代码，双写过渡）

**目标**：新代码上线，同时读写新旧字段。

**代码要求**：
- 新代码写数据时，**同时写新旧两个字段**（双写）
- 新代码读数据时，优先读新字段，fallback 到旧字段
- 新代码不依赖旧字段的存在（为阶段 3 做准备）

**操作步骤**：

```bash
# 1. 确认迁移已在阶段 1 完成
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw \
  python manage.py showmigrations <app>'

# 2. 发布新镜像
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/deploy.sh'

# 3. 发布后监控
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/post_deploy_watch.sh'
```

**此时状态**：新代码运行，双写新旧字段。**如果有 bug，回滚镜像即可，数据无损。**

**双写代码示例**：

```python
# models.py - 阶段 2 的双写逻辑
class UpgradeRecord(Model):
    title = CharField(max_length=200)
    upgrade_no = CharField(max_length=50, null=True, blank=True)  # 旧字段，即将删除

    def save(self, *args, **kwargs):
        # 双写：保存时同时写 title 和 upgrade_no（兼容旧代码）
        if not self.upgrade_no:
            self.upgrade_no = self.title  # 旧字段同步新值
        super().save(*args, **kwargs)

# views.py - 阶段 2 的读取逻辑
def get_display_name(record):
    # 优先读新字段，fallback 到旧字段
    return record.title or record.upgrade_no or '(未命名)'
```

#### 阶段 3 - CONTRACT（收缩，删旧，延后做）

**目标**：确认新代码稳定后，清理旧字段/旧索引。

**前提条件**：
- 阶段 2 已稳定运行 1-2 天
- 确认不再需要回滚到旧版本
- 旧字段已无业务读取（代码不再 fallback 到旧字段）

**操作步骤**：

```bash
# 1. 生成清理迁移
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw-test \
  python manage.py makemigrations <app> --name contract_remove_old_field'

# 2. 检查迁移文件
# 确认只有 RemoveField/RemoveIndex，没有 AddField

# 3. 生产环境跑迁移
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw \
  python manage.py migrate <app> --noinput'

# 4. 后续发布移除双写代码
# （此时可以删掉 save() 中的双写逻辑和 fallback 逻辑）
```

**此时状态**：旧字段已删，代码只读写新字段。**不可回滚到阶段 1 之前的版本。**

## 5. 常见变更场景的 Expand-Contract 方案

### 5.1 删字段（如 upgrade_no 移除）

```
阶段 1 EXPAND：无需操作（字段已存在）
阶段 2 DEPLOY：
  - 代码：移除所有对 upgrade_no 的引用
  - 但不删字段（迁移不做）
  - 旧代码仍可查 upgrade_no（字段还在）
阶段 3 CONTRACT：
  - 迁移：RemoveField('upgrade_no') + AlterUniqueTogether(set())
  - 确认旧代码不再运行（已过观察期）
```

**反例（本项目 07-30 实际做法）**：
```
一次发布同时做了：
  - 迁移 RemoveField + AlterUniqueTogether
  - 代码删除 27 处引用
→ 如果回滚，旧代码查已删字段 → 崩溃
```

### 5.2 改字段类型（如 CharField -> IntegerField）

```
阶段 1 EXPAND：
  - 加新字段 age_new = IntegerField(null=True)
  - 迁移：AddField

阶段 2 DEPLOY：
  - 代码双写：保存时同时写 age（旧）和 age_new（新）
  - 数据回填脚本：遍历所有记录，age_new = int(age)
  - 验证 age_new 数据完整性

阶段 3 CONTRACT：
  - 删旧字段 age，新字段 age_new 改名 age
  - 或：代码只读 age_new，删 age
```

### 5.3 加 NOT NULL 约束

```
阶段 1 EXPAND：
  - 加字段 status = CharField(max_length=20, default='active', null=True)
  - 迁移：AddField（nullable + default）

阶段 2 DEPLOY：
  - 代码双写：保存时写 status
  - 数据回填：UPDATE table SET status='active' WHERE status IS NULL

阶段 3 CONTRACT：
  - 迁移：AlterField(status, null=False)
  - 此时所有行都有合法值，NOT NULL 不会失败
```

### 5.4 加唯一约束

```
阶段 1 EXPAND：
  - 不做迁移（先清洗数据）

阶段 1.5 数据清洗：
  - 查重：SELECT license_no, COUNT(*) FROM table GROUP BY license_no HAVING COUNT(*) > 1
  - 人工处理重复记录
  - 确认无重复

阶段 2 DEPLOY：
  - 代码层校验：创建时检查 license_no 是否已存在（应用层去重）
  - 运行 1-2 天，观察是否有重复产生

阶段 3 CONTRACT：
  - 迁移：AddUniqueConstraint(fields=['license_no'])
  - 此时数据已干净，约束不会失败
```

### 5.5 改字段名（如 name -> title）

```
阶段 1 EXPAND：
  - 加新字段 title = CharField(max_length=200, null=True)
  - 迁移：AddField

阶段 2 DEPLOY：
  - 代码双写：保存时同时写 name（旧）和 title（新）
  - 数据回填：UPDATE table SET title = name WHERE title IS NULL
  - 代码读取：优先读 title，fallback 到 name

阶段 3 CONTRACT：
  - 删旧字段 name
  - 代码移除 fallback 逻辑
```

### 5.6 删表

```
阶段 1 EXPAND：无需操作
阶段 2 DEPLOY：
  - 代码：移除所有对该表的 CRUD 操作
  - 但不删表（迁移不做）
  - 确认无任何代码引用该表
阶段 3 CONTRACT：
  - 迁移：DeleteModel
```

## 6. 禁止的迁移模式

以下模式如果与代码同一次发布，**回滚即崩溃**：

### 6.1 禁止：删字段 + 同次发布删代码

```python
# 迁移：RemoveField('upgrade_no')
# 代码：删除所有 upgrade_no 引用
# 回滚后：旧代码查 upgrade_no → 字段已删 → OperationalError
```

### 6.2 禁止：改字段类型 + 同次发布改代码

```python
# 迁移：AlterField(age, CharField → IntegerField)
# 代码：int(record.age) 改为 record.age
# 回滚后：旧代码 int('25') → 旧字段已是 IntegerField → TypeError
```

### 6.3 禁止：加 NOT NULL 约束 + 无 default

```python
# 迁移：AlterField(status, null=False)（无 default）
# 旧代码插入新记录时不写 status → NOT NULL 约束失败 → IntegrityError
```

### 6.4 禁止：删唯一约束 + 同次发布删去重逻辑

```python
# 迁移：AlterUniqueTogether(set())
# 代码：移除应用层去重逻辑
# 回滚后：旧代码依赖唯一约束去重 → 约束已删 → 重复数据
```

## 7. 判断指南：哪些变更需要 Expand-Contract

### 7.1 必须用 Expand-Contract 的变更

| 变更类型 | 原因 |
|---|---|
| 删字段 | 旧代码可能查该字段 |
| 改字段类型 | 旧代码按旧类型处理数据 |
| 改字段名 | 旧代码按旧名查询 |
| 删表 | 旧代码可能查该表 |
| 加 NOT NULL 约束 | 旧代码插入时可能不写该字段 |
| 删唯一约束 | 旧代码可能依赖约束防重 |
| 改外键 ON DELETE 策略 | 影响删除行为 |

### 7.2 可以直接发布的变更（无需 Expand-Contract）

| 变更类型 | 原因 |
|---|---|
| 加字段（nullable + default） | 旧代码不读新字段，不受影响 |
| 加表 | 旧代码不查新表，不受影响 |
| 加索引 | 不改数据结构，只影响性能 |
| 加 CHECK 约束（数据已干净） | 不影响旧代码读写 |

### 7.3 需要分步但不需 Expand-Contract 的变更

| 变更类型 | 步骤 |
|---|---|
| 加唯一约束 | 先清洗重复数据 → 加约束 |
| 加 CHECK 约束 | 先清洗非法数据 → 加约束 |
| CharField → DateField | 先洗空串 → 改类型 |

## 8. 支柱三：发布后观察窗口

### 8.1 解决什么问题

发布完不等于发布成功。`/healthz/` 能发现启动阶段故障，但很多问题在运行几分钟后才暴露：

| 延迟故障类型 | /healthz/ 能发现吗 | 何时暴露 |
|---|---|---|
| Redis 配置错误 | 能（启动时连不上） | 启动后立即 |
| Celery 任务代码 bug | 不能 | 第一次执行任务时 |
| 内存泄漏 | 不能 | 运行一段时间后 OOM |
| 慢查询（数据量触发） | 不能 | 查询大表时 |
| 连接池耗尽 | 不能 | 并发量上来后 |
| 僵尸连接 | 不能 | 旧连接超时时 |

### 8.2 设计意图

`post_deploy_watch.sh` 在发布后自动监控 5 分钟，每 30 秒检查一轮，与 `deploy.sh` 的 90 秒健康检查互补：

```
deploy.sh 发布
  └-> 90s /healthz/ 检查 -> 失败 -> 自动回滚       （启动阶段）
  └-> 成功 -> 提示运行 post_deploy_watch.sh
       └-> 5min 监控 -> 连续告警 -> 建议手动回滚    （运行阶段）
       └-> 稳定 -> 发布完成
```

### 8.3 监控指标与阈值

| 指标 | 检查方式 | 默认阈值 | 说明 |
|---|---|---|---|
| 容器健康 | `docker inspect` healthcheck 状态 | 必须 `healthy` | 直接反映 /healthz/ 结果 |
| 容器状态 | `docker inspect` state | 必须 `running` | 容器是否存活 |
| 5xx 错误 | 日志 grep `500`/`Traceback`/`ERROR` | 30s 内 >5 次 | 业务错误 |
| Celery 失败 | 日志 grep `Task.*failed` | 30s 内 >3 次 | 异步任务失败 |
| 磁盘使用率 | `df` 命令 | >90% | 防止磁盘满宕机 |
| 容器内存 | `docker stats` | 趋势观察 | 监控内存泄漏 |

### 8.4 告警策略

- **单次告警**：记录但不触发回滚（可能是偶发）
- **连续 3 次告警**（即 90 秒内持续异常）：打印告警 + 容器日志 + 回滚命令，退出码 2
- **恢复正常**：告警计数器重置为 0

### 8.5 使用方式

```bash
# 默认监控 5 分钟（300 秒）
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/post_deploy_watch.sh'

# 指定监控 10 分钟（600 秒）
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/post_deploy_watch.sh 600'
```

### 8.6 阈值调整

阈值在 `post_deploy_watch.sh` 脚本头部定义，可根据项目实际情况调整：

```bash
WATCH_SECONDS=300           # 监控时长
CHECK_INTERVAL=30           # 检查间隔
THRESHOLD_5XX=5             # 5xx 错误阈值
THRESHOLD_CELERY_FAIL=3     # Celery 失败阈值
THRESHOLD_DISK_PCT=90       # 磁盘告警阈值
MAX_ALERTS=3                # 连续告警次数上限
```

## 9. 三者协同工作

### 9.1 日常发布流程（95% 的情况）

```bash
# 一条命令完成发布（加法迁移 + 代码一起上，entrypoint 自动 migrate）
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/deploy.sh'
# 发布后监控 5 分钟
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/post_deploy_watch.sh'
# 如需回滚
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/rollback.sh'
```

### 9.2 破坏性迁移流程（5% 的情况）

仅删字段/改类型/删表时使用，手动两步：

```bash
# 第 1 步：删代码引用，不删字段，用 deploy.sh 发布
# 第 2 步：观察 1-2 天后，手动跑清理迁移
wsl bash -c 'docker exec -e PYTHONIOENCODING=utf-8 -w /data/spug/spug_api tdyw python manage.py migrate <app> --noinput'
```

### 9.3 回滚能力矩阵

| 场景 | 回滚镜像 | 回滚迁移 | 数据安全 |
|---|---|---|---|
| 日常发布（加法迁移） | **可以** | 不需要 | **安全** |
| 破坏性迁移第 1 步后（删代码不删字段） | **可以** | 不需要 | **安全**（字段还在） |
| 破坏性迁移第 2 步后（删字段） | **不可** | **不可** | 只能前进 |

### 9.4 deploy.sh 迁移检查（已实现）

deploy.sh 在发布前自动检查待执行迁移，并扫描破坏性操作：

```bash
# 检查待执行迁移数量
PENDING=$(docker exec ... tdyw-test python manage.py showmigrations --list | grep -c '\[ \]' || true)

# 扫描迁移文件中的破坏性操作
DESTRUCTIVE=$(grep -rl 'RemoveField\|AlterField\|DeleteModel\|RemoveIndex\|AlterUniqueTogether' \
  apps/*/migrations/*.py 2>/dev/null)

# 发现破坏性操作时警告并要求确认
```

## 10. 审查清单

每次提交涉及数据库迁移的变更时，对照以下清单：

### 10.1 迁移文件审查

- [ ] `makemigrations` 指定了 app 名（避免扫描全项目生成意外迁移）
- [ ] 迁移是加法（AddField/AddIndex/AddConstraint/AddModel）？-> 日常发布，和代码一起上
- [ ] 迁移是破坏性（RemoveField/AlterField/DeleteModel）？-> 需手动两步：先删代码引用，观察后再删字段
- [ ] 如果有 RunPython，确认是幂等的（重跑不出错）
- [ ] 加字段的 default 值是否合理
- [ ] 加约束前是否已清洗数据

### 10.2 代码审查

- [ ] 如果是破坏性迁移：先删代码引用，不删字段
- [ ] 如果是加法迁移：代码可直接读写新字段，无需双写
- [ ] 没有在同一发布中同时删字段和删代码引用
- [ ] 没有在同一发布中同时改字段类型和改代码

### 10.3 发布审查

- [ ] 发布前确认健康检查端点 `/healthz/` 返回 200
- [ ] deploy.sh 迁移检查通过（无破坏性操作警告，或有但已确认手动分步）
- [ ] 发布后 `deploy.sh` 健康检查通过（90s）
- [ ] 发布后运行 `post_deploy_watch.sh` 监控 5 分钟
- [ ] 如果是破坏性迁移第 2 步（删字段）：确认已过观察期，此后不可回滚

## 11. 项目历史教训总结

### 11.1 upgrade_no 移除（2026-07-30）

**做法**：一次发布同时执行迁移（RemoveField + AlterUniqueTogether）+ 代码删除（27 文件 +240 行）

**风险**：如果回滚，旧代码查已删的 `upgrade_no` 字段 -> 崩溃

**正确做法**：
```
阶段 1：无需操作
阶段 2：代码移除 upgrade_no 引用，但保留字段；发布新镜像
阶段 3：观察 1-2 天后，迁移 RemoveField + AlterUniqueTogether
```

### 11.2 document 软删除字段移除（2026-07-30）

**做法**：一次迁移移除 4 模型的 is_deleted/deleted_at/deleted_by + 5 个复合索引 + 双管理器

**风险**：如果回滚，旧代码查 `is_deleted` 字段 -> 崩溃；旧代码用 `all_objects` 管理器 -> AttributeError

**正确做法**：
```
阶段 1：无需操作
阶段 2：代码移除 is_deleted 过滤、移除双管理器、改为物理删除；但保留字段；发布新镜像
阶段 3：观察 1-2 天后，迁移 RemoveField × 12 + RemoveIndex × 5
```

### 11.3 通用教训

| 教训 | 说明 |
|---|---|
| 迁移和代码不要同次发布 | 尤其是破坏性迁移（删字段/改类型） |
| 删字段前先删代码引用 | 代码先不读该字段，确认稳定后再删字段 |
| 加字段可以直接做 | nullable + default 的 AddField 不影响旧代码 |
| 加约束前先洗数据 | 唯一约束/CHECK 约束要先清洗重复/非法数据 |

## 12. 快速参考卡

**发布前检查**：

1. `/healthz/` 返回 200？（DB + Redis + 存储 全部 ok）
2. 有数据库变更？是破坏性变更？ -> 用 Expand-Contract 三步走
3. `git status` 干净？

**发布命令**：
```bash
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/deploy.sh'
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/post_deploy_watch.sh'
```

**回滚命令**：
```bash
wsl bash -c '/mnt/e/TDYW/spug-3.0/docker/scripts/rollback.sh'
```

**Expand-Contract 判断**：
- 加字段/加表/加索引 -> 可直接发布
- 删字段/改类型/改名/删表/加NOT NULL/删约束 -> 必须三步：
  - 阶段1 EXPAND：跑迁移（只加不改不删）-> 验证旧代码
  - 阶段2 DEPLOY：发新代码（双写）-> 监控 -> 可回滚
  - 阶段3 CONTRACT：跑清理迁移（删旧）-> 不可回滚
