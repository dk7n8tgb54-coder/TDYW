# 发布安全与回滚规范

> 适用范围：所有涉及代码发布、数据库变更的生产部署
> 核心原则：**能发现**（健康检查）、**能回滚**（备份+还原）、**能止损**（观察窗口）

---

## 1. 概述

### 1.1 三道防线

| 防线 | 作用 | 实现方式 | 效果 |
|---|---|---|---|
| **一：健康检查端点** | 发布后 90 秒内判断"服务能不能用" | Django 端点检查 DB+Redis+存储，Docker healthcheck | 启动阶段故障 -> 自动回滚 |
| **二：数据库备份+还原** | 破坏性迁移出问题时能完整回滚 | 部署前 mysqldump 备份，出问题还原 | 回滚镜像+还原数据库，恢复到发布前状态 |
| **三：观察窗口** | 发布后 5 分钟内发现"启动检查发现不了的问题" | `post_deploy_watch.sh` 监控 5xx/Celery/迁移错误/磁盘/内存 | 运行阶段故障 -> 告警 -> 建议回滚 |

### 1.2 三者关系

```
数据库备份（事前保险）
  万一破坏性迁移出问题，能还原
        │
        ▼
deploy_prod.sh 部署（事中发布）
  加载镜像 -> 重启 -> entrypoint 自动 migrate
  └-> 90s 健康检查 ── 失败 ──> 自动回滚镜像
        │
        │ 成功
        ▼
post_deploy_watch.sh 观察（事后监控）
  5min 监控 -> 连续告警 -> 建议回滚镜像 + 还原数据库
        │
        │ 稳定
        ▼
   发布完成
```

## 2. 问题背景

### 2.1 为什么需要备份

Django migrate 按顺序执行，**一个迁移失败，后面全部停止**。

本项目 2026-08-02 的真实案例：

```
第 1 次 migrate：
  account.0013 失败（access_token 重复）-> 后面全部卡住

第 2 次 migrate（修了 access_token）：
  logs.0009 失败（audit_logs 有不合法 action 值）-> 后面又卡住
  -> regulation.0006 没执行 -> created_at 列不存在 -> 规章页面 500 错误
```

**教训**：迁移失败会连锁反应，一个卡住后面全停。必须有备份兜底。

### 2.2 为什么用"备份+还原"而不是 Expand-Contract

| 对比 | 备份+还原 | Expand-Contract 两步 |
|---|---|---|
| 代码复杂度 | 简单，迁移和代码一起发 | 要拆两次提交，中间留双写代码 |
| 回滚速度 | 慢（还原数据库几分钟） | 快（只切镜像，秒级） |
| 数据丢失 | 有（备份到回滚之间的新数据） | 无 |
| 适用场景 | 小系统、低峰期部署 | 大系统、不能停服 |

本项目用户量小、数据量小（mysqldump 几秒完成）、可低峰期部署，**备份+还原是最务实的方案**。

## 3. 防线一：健康检查端点

### 3.1 解决什么问题

Docker healthcheck 只查 `SELECT 1` 太浅。Redis 挂了、存储目录权限丢了、Celery 崩溃了都感知不到。

### 3.2 实现

`apps/document/views/health.py` 的 `HealthCheckView` 检查三项：

| 检查项 | 方式 | 发现的故障 |
|---|---|---|
| 数据库 | `SELECT 1` | DB 连不上 |
| Redis | `cache.set` -> `cache.get` -> `cache.delete` | 缓存服务挂了 |
| 存储目录 | `os.path.isdir` + `os.access(W_OK)` | 磁盘满/权限丢失 |

- URL：`/api/document/health/`（不需要认证）
- 正常返回 200，异常返回 503
- 不暴露错误细节（安全），错误详情写 `logger.error`

### 3.3 Docker healthcheck 配置

```yaml
# docker-compose.yml
healthcheck:
  test: ["CMD-SHELL", "curl -sf http://localhost/api/document/health/ || exit 1"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 30s
```

### 3.4 分层设计

```
L1 容器存活    docker ps                容器崩溃 / OOM Kill
L2 进程存活    supervisorctl status     gunicorn/celery 进程退出
L3 依赖连通    /health/ (DB+Redis+存储)  DB挂/Redis挂/磁盘满  <- 本防线
L4 业务功能    post_deploy_watch.sh      5xx/Celery 失败/迁移错误  <- 防线三
```

## 4. 防线二：数据库备份+还原

### 4.1 什么时候需要备份

**每次部署前都备份**，不管是不是破坏性迁移。理由：
- 备份只需几秒（本项目数据量小）
- 你不知道哪个迁移会突然失败（比如 0013 的 access_token 问题，事先无法预见）
- mysqldump 是最便宜的保险

### 4.2 备份命令

```bash
# 在生产服务器上执行（部署前）
BACKUP_FILE="/mnt/e/TDYW/dyw-server/backup_$(date +%Y%m%d_%H%M).sql"
docker exec tdyw-db mysqldump -uroot -p密码 tdyw > "$BACKUP_FILE"
echo "备份完成: $BACKUP_FILE ($(du -h "$BACKUP_FILE" | awk '{print $1}'))"
```

### 4.3 还原命令（出问题时用）

```bash
# 1. 回滚镜像
bash rollback.sh

# 2. 还原数据库
docker exec -i tdyw-db mysql -uroot -p密码 tdyw < "$BACKUP_FILE"

# 3. 验证
curl -s http://localhost/api/document/health/
```

### 4.4 注意事项

1. **低峰期部署** -- 减少备份到发现问题之间的数据量
2. **备份文件要验证** -- `head -5 backup.sql` 确认不是空文件
3. **保留多个备份** -- 至少保留最近 3 次，不要只留最新的
4. **还原后要重启容器** -- `docker restart tdyw`，让 gunicorn 重新连接数据库

### 4.5 日常发布 vs 破坏性迁移

| 场景 | 需要备份吗 | 回滚方式 | 数据安全 |
|---|---|---|---|
| 日常发布（加字段/加表/加索引） | 建议备份（几秒的事） | 只回滚镜像 | 安全（旧代码兼容新结构） |
| 破坏性迁移（删字段/改类型/删表） | **必须备份** | 回滚镜像 + 还原数据库 | 还原后恢复到备份时点 |

## 5. 防线三：发布后观察窗口

### 5.1 解决什么问题

`/health/` 能发现启动阶段故障，但很多问题在运行几分钟后才暴露：

| 延迟故障 | /health/ 能发现吗 | 何时暴露 |
|---|---|---|
| Redis 配置错误 | 能 | 启动后立即 |
| 迁移失败（entrypoint 吞掉错误） | 不能 | 用到相关功能时 |
| Celery 任务代码 bug | 不能 | 第一次执行任务时 |
| 内存泄漏 | 不能 | 运行一段时间后 OOM |
| 慢查询 | 不能 | 查询大表时 |

### 5.2 监控指标

| 指标 | 检查方式 | 阈值 |
|---|---|---|
| 容器健康 | Docker healthcheck 状态 | 必须 healthy |
| 5xx 错误 | 日志 grep Traceback/ERROR | 30s 内 >5 次 |
| Celery 失败 | 日志 grep Task.*failed | 30s 内 >3 次 |
| **迁移错误** | 日志 grep 迁移失败/OperationalError | **>0 立即告警** |
| 磁盘使用率 | df 命令 | >90% |

### 5.3 使用

```bash
# 默认监控 5 分钟
bash post_deploy_watch.sh

# 指定 10 分钟
bash post_deploy_watch.sh 600
```

连续 3 次告警（90 秒持续异常）-> 打印告警 + 容器日志 + 回滚命令。

## 6. 部署流程

### 6.1 整体流程

```
开发机                    生产服务器
───────                   ───────────
构建镜像                   接收 tar 文件
docker save 导出    ──>    docker load 加载
                          备份数据库
                          deploy_prod.sh 部署
                          post_deploy_watch.sh 监控
                          （如有问题）rollback.sh + 还原数据库
```

### 6.2 开发机操作

```bash
# 1. 确认代码已提交
git status

# 2. 构建镜像
docker build -t tdyw:YYYYMMDD-N -f docker/Dockerfile .

# 3. 导出 tar
docker save -o /mnt/e/TDYW/dyw-server/tdyw_YYYYMMDD-N.tar tdyw:YYYYMMDD-N

# 4. 把 tar 文件拷到生产服务器
```

### 6.3 生产服务器操作

```bash
# 0. 拷贝脚本到生产服务器（首次需要）
#    deploy_prod.sh, rollback.sh, post_deploy_watch.sh

# 1. 备份数据库
BACKUP_FILE="backup_$(date +%Y%m%d_%H%M).sql"
docker exec tdyw-db mysqldump -uroot -p密码 tdyw > "$BACKUP_FILE"
echo "备份完成: $BACKUP_FILE"

# 2. 部署
bash deploy_prod.sh tdyw_YYYYMMDD-N.tar
#   ├─ docker load 加载镜像
#   ├─ 保存旧镜像 tag（回滚用）
#   ├─ 更新 docker-compose.yml
#   ├─ 重启容器
#   ├─ entrypoint.sh 自动 migrate
#   ├─ 90s 健康检查（DB+Redis+存储）
#   └─ 失败 -> 自动回滚到旧镜像

# 3. 发布后监控 5 分钟
bash post_deploy_watch.sh

# 4. 如需回滚
bash rollback.sh                    # 回滚镜像
docker exec -i tdyw-db mysql -uroot -p密码 tdyw < "$BACKUP_FILE"  # 还原数据库
```

## 7. 脚本清单

| 脚本 | 运行位置 | 功能 |
|---|---|---|
| `deploy_prod.sh` | 生产服务器 | 加载 tar -> 部署 -> 健康检查 -> 失败自动回滚 |
| `rollback.sh` | 生产服务器 | 回滚到上个镜像（读 `.last_deployed_image`） |
| `post_deploy_watch.sh` | 生产服务器 | 5min 监控（健康/5xx/迁移/Celery/磁盘） |
| `deploy.sh` | 开发机（本地测试） | 构建+部署一条龙，不用于生产 |
| `build.sh` | 开发机（可选） | 构建+导出 tar，用户也可手动构建 |

### deploy_prod.sh 参数

```bash
bash deploy_prod.sh <tar文件名>
# 例如：bash deploy_prod.sh tdyw_20260802-123.tar
```

### rollback.sh 参数

```bash
bash rollback.sh           # 交互模式，确认后回滚
bash rollback.sh --auto    # 自动模式（deploy_prod.sh 失败时自动调用）
```

## 8. 迁移注意事项

### 8.1 迁移失败会连锁

Django 按顺序执行迁移，**一个失败，后面全部停止**：

```
account.0013 失败 -> logs.0009 不执行 -> regulation.0006 不执行 -> ...
```

deploy_prod.sh 的健康检查和 post_deploy_watch.sh 的迁移错误监控能发现这类问题。

### 8.2 常见迁移失败原因

| 原因 | 示例 | 预防 |
|---|---|---|
| 加唯一约束时有重复数据 | access_token 有多个空字符串 | 迁移文件加 RunPython 先清洗 |
| 加 CHECK 约束时有非法值 | audit_logs 有 upload_attachment 不在允许列表 | 迁移文件加 RunPython 先清洗 |
| 加 NOT NULL 时有 NULL 值 | CharField 禁 null=True 但老数据有 NULL | 先加 AlterField 改为 NOT NULL DEFAULT '' |

### 8.3 迁移文件编写规范

1. `makemigrations` 必须指定 app 名，避免扫描全项目
2. 加约束前加 RunPython 清洗数据
3. RunPython 必须是幂等的（重跑不出错）
4. CharField/TextField 禁止 null=True
5. 不修改已执行的迁移文件（除非确认所有环境状态一致）

### 8.4 迁移文件修改的特例

如果已执行的迁移文件有 bug（如漏了数据清洗），可以修改：
- Django 按名字记录迁移，改内容不会重新执行
- 已执行的环境不受影响（跳过）
- 未执行的环境会用新版（修复后的）
- 全新数据库会从头执行新版（正确）

本项目修过的迁移文件：
- `account/0013`：加 RunPython 给空 access_token 生成 UUID
- `logs/0009`：加 3 行把 attachment action 值转为 'other'
