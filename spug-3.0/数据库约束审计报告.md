# 1.1 数据库约束审计报告

> 审计范围：`spug_api/apps/` 下全部 17 个 app 的 models.py
> 审计时间：2026-07-29
> 审计标准：NOT NULL / UNIQUE / CHECK / FOREIGN KEY 四类约束

---

## 一、总览

| 约束维度 | 现状 | 评分 |
|---|---|---|
| **FOREIGN KEY** | 全项目统一使用 `on_delete=PROTECT`（用户引用）或 `CASCADE`（父子关系），策略正确 | A |
| **UNIQUE** | 核心业务表（设备编号、执照号、合同确认等）已覆盖；账号表严重缺失 | B- |
| **CHECK** | 新模块（device/radio_license/runlog/interference/contract_agreement/department_duty_log）做得好；老模块（fault/duty/regulation/evidence/logs）完全空白 | C+ |
| **NOT NULL** | 大部分字段正确；个别业务关键字段（duty_date、fault_date）允许 NULL 有争议 | B |

**总结：FK 策略全项目合格，UNIQUE 和 CHECK 约束呈"新模块好、老模块差"的两极分化。**

### 2.2 亮点

1. **幂等性约束**：5 个模块（radio_license x2、contract_agreement、home、signature）用 `UniqueConstraint` 实现了数据库级幂等，这是最佳实践
2. **日期顺序约束**：3 个模块（radio_license、contract_agreement、runlog）加了 `valid_to >= valid_from` 类型的 CheckConstraint，防止用户填反日期
3. **软删除一致性**：DeviceResume 用 CheckConstraint 保证 `is_deleted=True` 时 `deleted_at/deleted_by_id/delete_reason` 必须有值
4. **非负约束**：runlog/contract_agreement/radio_license 对数值字段加了 `>= 0` 的 CheckConstraint

## 三、有问题的模块（缺失约束）

### 3.1 P0 严重 -- `account/User`（核心账号表零约束）

```python
# account/models.py
class User(models.Model, ModelMixin):
    username = models.CharField(max_length=100)          # 无 unique!
    access_token = models.CharField(max_length=32)        # 无 unique!
    type = models.CharField(max_length=20, default='default')  # 无 CheckConstraint
    tenant_id = models.CharField(max_length=50, default='admin', db_index=True)  # 无联合唯一

    class Meta:
        db_table = 'users'
        ordering = ('-id',)
        # constraints = [...]  <- 完全没有!
```

**风险：**
- `username` 无唯一约束 -> 可能创建重名用户 -> 登录歧义
- `access_token` 无唯一约束 -> 理论上可能生成重复 token -> 认证串号
- `type` 字段无 CheckConstraint -> 可写入任意字符串 -> 代码分支不匹配
- 无 `(tenant_id, username)` 联合唯一 -> 跨租户重名无法阻止，同租户重名靠应用层兜底

**建议：**
```python
constraints = [
    # 同租户内用户名唯一（跨租户允许重名）
    models.UniqueConstraint(
        fields=['tenant_id', 'username'],
        name='uniq_user_tenant_username',
        condition=models.Q(deleted_by_id__isnull=True),  # 软删除的排除
    ),
    # access_token 全局唯一
    models.UniqueConstraint(
        fields=['access_token'],
        name='uniq_user_access_token',
        condition=models.Q(deleted_by_id__isnull=True),
    ),
]
```

> 注意：MariaDB 10.8 不支持 partial unique index（`condition=`），需用 `unique_together` + 软删除时将 username 改名（如加 `_deleted_{id}` 后缀），或升级到 MariaDB 10.10+。当前项目已有的 `document` 模块用 `unique_key` MD5 哈希 + `null=True` 方案绕过此限制，可参考。

### 3.3 P1 高 -- `duty/DutyRecord`（零约束 + 关键字段 nullable）

```python
# duty/models.py
class DutyRecord(models.Model, TenantModelMixin):
    duty_date = models.DateTimeField(null=True, blank=True)  # 值班日期允许 NULL?
    # ... 无任何 constraints / unique_together

    class Meta:
        db_table = 'tdyw_duty_records'
        ordering = ('-duty_date', '-id',)
        # 完全没有 constraints!
```

**风险：**
- `duty_date` 允许 NULL -> 一条值班记录可以没有值班日期，业务上不合理
- 无防重约束 -> 同一人同一天可创建多条值班记录
- 无 CheckConstraint -> 任何字段都可写入任意值

**建议：**
```python
constraints = [
    models.UniqueConstraint(
        fields=['tenant_id', 'duty_date', 'duty_person'],
        name='uniq_duty_record_date_person',
    ),
]
```
同时考虑将 `duty_date` 改为 `null=False`（需先清洗历史空值数据）。

## 四、FOREIGN KEY 策略审计

### 4.1 on_delete 策略统计

| 策略 | 使用场景 | 评估 |
|---|---|---|
| `PROTECT` | 所有 `created_by` / `updated_by` / `deleted_by` 用户引用 | 正确 -- 防止删用户导致业务数据级联删除 |
| `CASCADE` | 父子关系（LicenseReminderAck -> License, AnnouncementScope -> Announcement 等） | 正确 -- 子记录生命周期跟随父记录 |
| `IntegerField` 逻辑 FK | `runlog_id`、`device_resume_id`、`responsible_user_id` 等 | 有文档说明，为性能/灵活性取舍，可接受 |

### 4.2 问题

- `account/User.tenant_id` 是 `CharField` 而非 FK -> 无法在数据库层强制引用完整性
  - 这是多租户架构的常见取舍（tenant_id 是逻辑隔离标识，不是物理外键）
  - 应用层 `TenantModelMixin` / `TenantModelManager` 已做隔离兜底，可接受

## 六、结论

**项目约束覆盖呈"两极分化"：**

- **新模块（2026 年开发）**：device / radio_license / runlog / interference / contract_agreement / department_duty_log -- 约束完整，是标杆
- **老模块（迁移继承）**：account / fault / duty / regulation / evidence / logs -- 基本零约束

**FK 策略全项目合格**，`on_delete=PROTECT` 对用户引用的保护到位。

**最紧迫的改进**是 `account/User` 表的 `username` / `access_token` 唯一约束，这直接影响认证安全。其次是给 6 个有 choices 但无 CheckConstraint 的老模块补上约束。
