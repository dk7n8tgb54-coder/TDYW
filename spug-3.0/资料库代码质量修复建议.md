# 资料库模块代码质量修复建议

> 编写时间：2026-06-10  
> 对应报告：`资料库代码质量报告.md`  
> 原则：先修真实运行风险，再处理结构性技术债；避免一次性大重构影响上传、回收站和搜索主链路。

---

## 一、修复路线总览

| 阶段 | 目标 | 建议周期 | 风险 |
|------|------|----------|------|
| 第一阶段 | 修复状态不一致、定时器泄漏、顶层 DOM 副作用 | 1-3 天 | 低到中 |
| 第二阶段 | 补齐约束、异常类型、权限响应、清理历史文件 | 3-7 天 | 中 |
| 第三阶段 | 模型抽象、Store 依赖注入、默认排序治理 | 1-2 周 | 中到高 |

---

## 二、第一阶段：稳定性修复

### 1. 统一传输状态定义

涉及文件：

- `spug_api/apps/document/constants.py`
- `spug_api/apps/document/models.py`
- `spug_api/apps/document/migrations/`
- `spug_web/src/pages/document/stores/upload/core/upload-core-constants.js`
- `spug_web/src/pages/document/stores/constants/upload.js`

建议做法：

1. 后端只保留一个权威状态源，优先以 `TransferStatus` 为准。
2. 在 `TransferStatus` 中补齐 `DOWNLOADING`。
3. 在 `DocumentTransfer.TRANSFER_STATUS_CHOICES` 中补齐 `MERGING`。
4. 状态拼写保持当前项目已有值：`CANCELED`，不要改成 `CANCELLED`。
5. `ALLOWED_STATUS_TRANSITIONS` 补齐 `DOWNLOADING` 的转换规则。

建议转换规则：

```python
TransferStatus.DOWNLOADING: [
    TransferStatus.COMPLETED,
    TransferStatus.FAILED,
    TransferStatus.CANCELED,
]
```

注意事项：

- 如果数据库已有 `MERGING`，补 choices 通常不需要数据迁移，但仍建议生成 migration 保持模型历史一致。
- 如果前端状态常量有 `cancelled` 这种英式拼写，需要确认是否只是 UI 内部状态，不能直接映射到后端数据库状态。

验收标准：

- `TransferStatus`、模型 choices、前端传输状态映射一致。
- 合并中任务能正常显示、取消、失败、超时清理。
- 批量暂停/恢复/取消不会因为 `MERGING` 或 `DOWNLOADING` 报非法状态。

建议测试：

- 后端添加/更新 `test_constants.py` 或 `test_document_transfer.py`：
  - 枚举值全部存在于模型 choices。
  - 模型 choices 全部能转为 `TransferStatus`。
  - `DOWNLOADING -> COMPLETED/FAILED/CANCELED` 合法。
  - `MERGING -> COMPLETED/FAILED/CANCELED` 合法。

### 2. 修复 UploadCoreStore 定时器泄漏

涉及文件：

- `spug_web/src/pages/document/stores/upload/core/index.js`

建议做法：

1. 将 `_initStateMachine()` 中的 `setInterval()` 返回值保存到专用字段，例如 `stateMachineCleanupTimer`。
2. 在 `destroy()` 或现有清理方法中 `clearInterval()`。
3. 清理后将字段置空，保证多次 destroy 幂等。

示例方向：

```javascript
this.stateMachineCleanupTimer = setInterval(() => {
  if (this.stateMachineManager) {
    this.stateMachineManager.cleanup();
  }
}, 60000);
```

```javascript
if (this.stateMachineCleanupTimer) {
  clearInterval(this.stateMachineCleanupTimer);
  this.stateMachineCleanupTimer = null;
}
```

验收标准：

- Store 重建不会产生多个状态机 cleanup 定时器。
- 页面卸载或热更新后旧 Store 不再执行 cleanup。

建议测试：

- 前端用 fake timers 验证构造后注册一次 interval。
- 调用 destroy 后 interval 被清理。

---

### 3. 移除 Explorer 顶层 DOM 操作

涉及文件：

- `spug_web/src/pages/document/Explorer/index.js`
- `spug_web/src/pages/document/Explorer/index.module.less`

建议做法：

1. 删除 `document.createElement('style')` 逻辑。
2. 将排序图标样式移动到 `index.module.less` 或全局 less。
3. 如果 CSS Modules 无法覆盖 Ant Design 内部类，使用 `:global(...)`。

示例方向：

```less
:global(.file-list-container .ant-table-column-sorters) {
  justify-content: flex-start !important;
}
```

验收标准：

- 热更新不再重复插入 style 标签。
- 文件列表排序图标位置保持不变。
- Jest 或无 DOM 的导入测试不因 `document` 未定义失败。

## 三、第二阶段：一致性修复

### 4. 为私有文件夹增加唯一约束

涉及文件：

- `spug_api/apps/document/models.py`
- `spug_api/apps/document/migrations/`
- 创建/重命名/恢复文件夹接口

建议约束：

```python
models.UniqueConstraint(
    fields=['tenant_id', 'created_by', 'name', 'parent'],
    name='unique_folder_name_parent_private'
)
```

是否包含 `created_by` 取决于私有空间真实隔离粒度：

- 如果一个租户内每个用户的私有空间完全独立，包含 `created_by`。
- 如果私有空间按租户共享，不能包含 `created_by`。

上线前必须处理历史重复数据：

1. 写脚本扫描 `(tenant_id, created_by, parent, name)` 重复项。
2. 对重复项生成改名方案，例如 `name (1)`。
3. 再添加数据库约束。

验收标准：

- 同一私有目录下不能创建同名文件夹。
- 恢复回收站文件夹遇到同名冲突时有明确提示或自动改名策略。

### 5. 定义硬删除失败自定义异常

涉及文件：

- `spug_api/apps/document/models.py`
- `spug_api/apps/document/views/file/views.py`
- 回收站永久删除相关 views/tasks

建议做法：

1. 新增异常类，例如：

```python
class DocumentPhysicalDeleteError(Exception):
    pass
```

2. 替换 `raise Exception(...)`。
3. 调用方按该异常单独捕获，返回明确错误。
4. 明确外层事务策略：如果要保留 `is_pending_clean` 标记，不要让外层事务回滚这次保存。

可选方案：

- 将“标记待清理”放在独立 service 中，并在事务外执行。
- 硬删除接口返回“已加入待清理队列”，而不是直接视为普通失败。

验收标准：

- 物理文件删除失败时，数据库记录不会被误删。
- 待清理字段能可靠落库。
- 接口返回明确可理解的错误信息。

---

### 6. 统一权限错误响应

涉及文件：

- `spug_api/apps/document/libs/document_decorators.py`
- `spug_api/apps/document/views/**`

建议响应格式：

```json
{
  "error": "无权限操作该资源",
  "code": 403,
  "reason": "permission_denied"
}
```

建议做法：

1. 增加统一 helper，例如 `permission_denied_response(message, reason='permission_denied')`。
2. 装饰器和 views 统一使用该 helper。
3. 前端错误处理只依赖 `code/reason/error`，不再解析散落文本。

验收标准：

- 公共空间非创建人删除/移动/重命名返回统一结构。
- 私有空间越权访问返回统一结构。

### 7. 清理历史备份文件

涉及文件：

- `spug_web/src/pages/document/Explorer.js.bak`
- `spug_web/src/pages/document/UploadPanel.old.js`
- `spug_web/src/pages/document/recycle-bin/store.js.backup`

建议做法：

1. 确认没有 import 引用。
2. 如果仍需保留历史，移动到 `backups/` 或文档目录，不放在源码树。
3. 如果不需要，直接删除。

验收标准：

- `git grep` 搜索不到对这些旧文件的引用。
- 前端构建不受影响。
- 代码搜索不再混入旧实现。

## 四、第三阶段：架构治理

### 8. 抽象 Public/Private 模型重复逻辑

涉及文件：

- `spug_api/apps/document/models.py`
- 所有 `get_folder_model()` / `get_file_model()` 调用方

建议做法：

先不要一次性大改数据库表结构。推荐只抽象 Python 共同逻辑：

1. 新增抽象基类或 Mixin：
   - `SoftDeleteMixin`
   - `FolderPathMixin`
   - `DocumentFileDeleteMixin`
2. 保持现有四张表不变。
3. 子类保留 `db_table`、约束、租户差异字段。

优先抽象：

- `delete()`
- `restore()`
- `get_full_path()`
- 物理文件/缩略图清理逻辑

验收标准：

- Public/Private 文件删除逻辑只有一份实现。
- 原有数据库表名和字段不变。
- 回收站、永久删除、清理任务测试通过。

---

### 9. 移除模型级默认 ordering

涉及文件：

- `spug_api/apps/document/models.py`
- 文件夹/文件/传输列表接口

建议做法：

1. 先为所有列表接口补显式 `.order_by('-created_at')`。
2. 后台任务、exists/count 查询显式 `.order_by()` 清空排序或不排序。
3. 最后移除模型 `Meta.ordering`。

验收标准：

- 用户看到的列表排序不变。
- 查询计划中不再出现不必要排序。

---

### 10. 重构 RootStore 依赖注入

涉及文件：

- `spug_web/src/pages/document/stores/index.js`
- `stores/navigation/index.js`
- `stores/upload/ui/index.js`
- `stores/upload/core/index.js`

建议目标结构：

```javascript
class RootStore {
  constructor() {
    this.navigationStore = new NavigationStore(this);
    this.uploadUIStore = new UploadUIStore(this);
    this.uploadCoreStore = new UploadCoreStore(this);
  }
}
```

迁移方式：

1. 保留现有导出名，避免一次性改所有 import。
2. 子 Store 构造函数支持传入 rootStore。
3. 移除 `window.__ROOT_STORE__` fallback。

验收标准：

- 单元测试可以创建多个独立 RootStore。
- 热更新和测试环境不依赖 window 全局变量。
- 现有页面 import 不需要大面积修改。

---

### 11. 改造 `get_full_path()`

涉及文件：

- `spug_api/apps/document/models.py`

建议做法：

1. 用 while 循环替代递归。
2. 记录 visited id，发现循环直接停止并记录日志。
3. 使用 `DEFAULT_MAX_FOLDER_DEPTH` 或 settings 中的最大深度。

验收标准：

- 正常路径显示不变。
- 构造循环父级数据时不会递归溢出。

## 五、建议执行顺序

推荐顺序：

1. 状态定义统一。
2. 状态相关测试补齐。
3. 修复前端定时器。
4. 移除顶层 DOM 操作。
5. 私有文件夹唯一约束和历史数据扫描。
6. 自定义异常与硬删除事务语义。
7. 权限响应统一。
8. 清理备份文件。
9. 模型 Mixin 抽象。
10. 默认 ordering 和 Store 依赖注入治理。

不建议第一轮就做的事：

- 不建议直接合并 Public/Private 数据表。
- 不建议一次性重写上传状态机。
- 不建议把所有类组件迁移为函数组件作为质量修复前置条件。
- 不建议将 `CANCELED` 改成 `CANCELLED`。

## 六、回归测试清单

后端：

- 上传小文件、分片上传、合并中状态查询。
- 合并任务从 `UPLOADING -> MERGING -> COMPLETED`。
- 合并失败从 `MERGING -> FAILED`。
- 下载任务 `DOWNLOADING -> COMPLETED/FAILED/CANCELED`。
- 批量暂停、恢复、取消。
- 回收站软删除、恢复、永久删除。
- 物理文件删除失败后待清理标记落库。
- 私有目录同名创建/重命名/恢复冲突。
- 公共空间普通用户越权操作。

前端：

- 上传文件和上传文件夹。
- 暂停、恢复、取消、失败重试。
- 页面刷新后传输列表恢复。
- 传输列表抽屉开关。
- 文件列表排序样式。
- 热更新或重复挂载后没有重复定时器。

---

## 七、验收标准

第一阶段完成后：

- 状态枚举、模型 choices、状态转换规则一致。
- 上传核心没有未清理 interval。
- Explorer 不再在模块加载时访问 `document`。
- 状态相关测试通过。

第二阶段完成后：

- 私有目录同名冲突有数据库级保障。
- 硬删除失败有明确异常类型和待清理落库策略。
- 权限错误响应格式统一。
- 源码目录不再保留旧备份实现文件。

第三阶段完成后：

- Public/Private 共享逻辑抽象完成。
- 模型默认排序移除或显式化。
- Store 可独立实例化测试。
- 文件夹路径生成具备循环和深度保护。
